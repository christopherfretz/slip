# KB5 2.3 — Slip's review of Kiln's WP-2820 phase 0 design

Slip's answers to the design note "WP-2820 phase 0: operator and
user-defined-literal entries in the written-reference table" (Kiln's
`designs/wp2820-design.md` at `7fda60c`, base Kiln `64bc443cc`), which
answers request KB5 item 2.3. Status: **sent 2026-11-23**. Kiln owns the
design; this says what Slip's clients need of it and why.

Verdict: **go ahead with phase 1**, with the three changes marked
**change** below. The other ten decisions are accepted as proposed.

## 1. What Slip does with these entries

Three clients, in the order they will use them:

1. **The spelled-entity check** (`spec/verify.md` §10.2). An obligation
   is a byte range `[lo, hi)` of a post-image file and a key; an entry
   answers it when its name range ends at `hi` and starts at or after
   `lo`; the obligation holds when every answering entry's referent has
   the key and no answering entry is unresolved. A role Kiln adds takes
   part the day it is recorded. With these entries a transform can write
   `a + b`, `x[i]` or `12_km` and say which function the token is to
   select, and the trusted base checks it.
2. **References and calls of the transform API** (`spec/api.md` §6.5,
   §6.7): "the uses of this function" must include its uses as an
   operator; WP-086 names "a use of an overloaded operator written as an
   operator" and "a call through an object with `operator()`" as not
   calls in version 0 for want of exactly these entries.
3. **The native rename**, later: a literal operator's suffix.

Everything below follows from one property the check needs: **an entry's
absence must never be readable as agreement.** Where a written token can
select a function and the table says nothing, the check holds by default,
which is the hole this request closes.

## 3. The changes and requirements

### 3.1 The second comparison of a `<=>` rewrite (D2, §3.3 of the note)

`a < b` rewritten to `(a <=> b) < 0` selects **two** functions by
overload resolution: `operator<=>`, and the `operator<` that compares
its result with `0`. The note records the first and calls the second
"no token of its own". With a standard comparison category the second is
a library function nobody edits. With a user-defined category it is
user code:

```cpp
struct R { friend bool operator<(R, int); friend bool operator>(R, int); };
struct A { R operator<=>(const A&) const; };
bool f(A x, A y) { return x < y; }   // selects A::operator<=> and operator<(R, int)
```

Here `operator<(R, int)` has no use in the table, so "the uses of this
function" is empty and a transform that removes or changes it is told
nothing refers to it.

Wanted, one of (Kiln chooses):

- **(a)** a second entry at the written token, after the `operator<=>`
  one in application order (as D5's chains), flagged `REWRITTEN`, entity
  the selected comparison with zero; or
- **(b)** no entry, and the case named in §18.4 "Not in the table"
  with the implicit-calls table (F5) as its home.

Slip prefers (a): the written `<` is the operator the standard applies
to the result ([over.match.oper]/8), so it does have a token, and the
cost is one entry per rewritten relational comparison (100 on
`<bits/stdc++.h>` by the note's own count). Not blocking for F1; it must
be one or the other in the specification, never silent.

### 3.2 A specialisation in which a built-in is selected (D11) — change

The note proposes no row, so that "the absence of a row for an
instantiated specialization means a built-in was used **or** the token
was not reached". The check cannot use an entry that reads that way.

A transform writes `a + b` in a template's pattern and says the `+` is
`ns::operator+(S, S)`. In `g<S>` it is; in `g<int>` it is the built-in.
With no row for `g<int>`, every row the table has names the key and the
obligation holds, though in one specialisation the token denotes
nothing of the kind. The other reading of an absent row, a discarded
`if constexpr` branch, must **not** fail. One encoding for both makes
the check either unsound or useless.

Wanted: the alternative the note lists, a row flagged `SPEC_BUILTIN`
(printing `(builtin)`), so that for an instantiated specialisation a
dependent operator entry has a row exactly when the token was reached.

If the measured cost is the objection (pointer iterators, arithmetic on
`T = int`), measure it on `<bits/stdc++.h>` as §6.5 proposes for the
rest, and if the rows add more than the entries themselves, fall back
to **one flag on the entry**, set when any specialisation selected a
built-in for it (`BUILTIN_IN_SOME_SPEC`). That is enough for the check
(which asks about every specialisation at once); the per-specialisation
answer then waits for a client that asks for it. The row is preferred:
the transform API will ask "what does this operator call in this
instantiation".

The same applies to a fold's operator entry (one row per distinct
resolution, a built-in being one of them) and to a dependent `new`,
`delete` and `co_await` (a specialisation in which no function is
selected, e.g. no `operator co_await` applies).

### 3.3 Dependent calls (D12) — change

Proposed: a `DEPENDENT` entry at `(` "only when the callee is
type-dependent and is not a function name". That misses a callee that is
**not** type-dependent with **dependent arguments**, which is as common
as the covered case:

```cpp
struct Less { template <class A, class B> bool operator()(const A&, const B&) const; };
template <class T> bool f(T a, T b) { Less lt; return lt(a, b); }   // operator()<T, T> chosen per specialisation
template <class T> bool g(T a, T b) { return std::less<>{}(a, b); }
```

`lt` has a non-dependent class type; the call is type-dependent because
of its arguments, and the `operator()` (a specialisation of a template,
or one of several overloads) is selected at instantiation. Wanted: the
rule reads "the callee is not a function name, and the call is
type-dependent (the callee or an argument)". Where the callee's class is
known and its `operator()` set is not a template and has one member the
call can be resolved in the pattern and the entry need not be dependent:
Kiln's choice.

The case the note names as uncovered (`t.f(x)` where `f` turns out to be
a data member of class type) is accepted as uncovered, **stated in
§18.13** so that Slip can name it as a hole.

### 3.4 A range inside a token (D4)

Slip takes an entry's name range from `editable_file_range` (through
`slip_kiln::ranges`): the bytes of one file that became exactly the
name's tokens, at tier 0 or 1. A `ud-suffix` range starts inside a
token. Required, with a test for each:

- `editable_file_range` of a `ud-suffix` entry's range gives the
  suffix's bytes for a literal written in a file and for one written in
  a macro argument (tier 1), and no range for one in a macro body or
  made by `##`, as for names;
- a suffix the lexer cannot map byte for byte (a line splice or a
  universal-character-name inside it) gives **no range**, never a wrong
  one;
- a raw string literal's suffix (`R"x(...)x"_s`) and a suffix on a
  literal with an encoding prefix.

### 3.5 `delete` through a virtual destructor (D8)

Say in §18.13 what the entry of `delete p` names when the static type
has a virtual destructor ([expr.delete]/9: the deallocation function is
the one found at the dynamic type's destructor): the function the
static type's lookup selects, with the sentence that the call may reach
another. A client must not read it as "the function called".

## 4. Notes, no change asked

- Implicit conversion functions and constructor selection stay out
  (§3.4 of the note, F5). For "the uses of a function" a constructor is
  the next most wanted after operators; Slip will ask for F5 by name
  when a package needs it.
- No new opt-in flag: accepted. Slip parses with the table on in every
  verify job and tracks memory per job, so the measured numbers of §6.5
  (entries, rows, bytes on `<bits/stdc++.h>`) are wanted in the landed
  specification.
- Order: F1 (outside templates), then F2 (dependent, folds, rows), then
  F3. Slip moves its pin after F1 and again after F2; the sha of each is
  enough.
- On Slip's side this closes item 4 of `spec/landed/verify/WP-096.md`
  "For Kiln" (an operator used as an operator and a call through a
  user-defined literal cannot veto), and lets `spec/api.md` §6.7 ("Not
  calls in version 0") stop excluding operator calls.
