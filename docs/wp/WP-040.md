## What is decided

All of digest §4.3. In short, for orientation only:

1. A local type's key is `local(n)` under its **owner**; `n` counts the
   owner's local types by declaration, never by reference.
2. `n` comes from **numbering the owner**: a walk of the owner's own
   stream that does not enter the members of local types, reads no
   key, type or reference and writes nothing; memoised per owner.
3. A local type is written in place at its declaration: `n`, its
   stream, its listed members' streams. Met again, `n` alone.
4. What would be a derived unit were the type not local is one:
   specialisations of a generic lambda's call operator and conversion
   function, implicit members defined on use. Nothing a use makes is
   in the stream that holds the type.
5. A local object named from a unit that does not hold its declaration
   is `Ref::outer` (owner's key, index among the owner's local
   objects); inside the unit that holds it, `Ref::local` as today.
6. A lambda-expression walked inside a key or a type digest makes that
   key or type indeterminate.

## Interface

```rust
// local.rs
/// The owner of the local entity `d` (digest §4.3): the entity with a
/// key whose own stream holds its declaration. `None` when no stream
/// numbers it (digest-kinds §10.4).
pub(crate) fn owner(w: &Walk<'_>, d: DeclId) -> Option<DeclId>;

/// What numbering `owner` found: its local types and its local
/// objects, each in order. Memoised in the walk.
pub(crate) struct Numbering { /* yours */ }
pub(crate) fn numbering<'a>(w: &'a mut Walk<'_>, owner: DeclId) -> &'a Numbering;

/// `local(n)` of the local type `t`; `Err` with the cause when it has
/// no number (no owner, or its owner's numbering does not find it).
pub(crate) fn type_number(w: &mut Walk<'_>, t: DeclId) -> Result<u64, Cause>;

/// The unit whose stream holds the declaration of the local entity `d`:
/// its owner, or the owner's own unit when the owner is written in
/// place.
pub(crate) fn unit_of(w: &mut Walk<'_>, d: DeclId) -> Option<DeclId>;
```

Names and shapes are yours where the comment says so; the four
functions are what `keys.rs` and `refs.rs` call. `write_decl` and
`lambda_data` keep their signatures.

Rules the implementation must meet, each with its test:

- **One order.** The numbering and the walk meet an owner's
  declarations in the same order because they are the same traversal,
  not two that happen to agree: the statement and expression walk run
  under a mode of `Walk` in which `write_ref`, `write_type`,
  `write_key`, values and every memo are skipped and the stream is a
  sink, or a design of yours with the same guarantee. Say in the
  landed file why no code path can order children differently in the
  two. And check it: in tests, the walk records, per owner, the local
  types whose declarations it writes, in order; a test over every
  pair-test source (both sides) asserts the record equals the
  numbering. At run time, a declaration the walk meets whose owner's
  numbering lacks it or has it elsewhere is
  `Unaccounted("local/numbering")`, never a key built from a guess.
- **No key, no type, no reference** is read while numbering: a
  numbering never starts another numbering and never writes or reads a
  key (a test: numbering an owner whose body names local types of ten
  other owners numbers one owner).
- **Linear and bounded.** Each owner is numbered at most once per
  walk; a unit with no local type and no outer reference is never
  numbered (the common case pays nothing: show the counter). The stack
  rules of `lib.rs` "What bounds the stack" hold while numbering,
  including when a numbering starts deep inside another unit's walk;
  20,000 nested or chained lambdas, and a 20,000-long chain of
  functions each returning a closure that captures the previous one's
  result, digest in linear time without overflow or are indeterminate
  with a named cause at a stated limit.
- **Order of units does not matter.** The same output whichever unit
  is written first: a test that digests with the unit order reversed
  (or, if the walk has no such switch, that numbers every owner before
  any unit, and after) and compares every key and digest.
- **Kinds are matched exhaustively** (rule 3 of the common rules), in
  `owner` as everywhere: what `closure_owner` can answer is a closed
  set of `DeclKind`s; one it answers that §10.4 does not name is
  `Unaccounted("local/owner")`.

## What Kiln does

From a reading at pin `62d190007` (verify at the pin you build
against; a statement that no longer holds goes in the handback with
the new `file:line`):

- A captured variable used in a lambda's body is a `DeclRefExpr` to
  the enclosing function's variable with
  `ExprFlags::REFERS_TO_ENCLOSING` (`kiln_ast/src/expr.rs:291`,
  `kiln_sema/src/expr.rs:2866-2884`), never a member access on the
  closure; so is one in an instantiated body of a generic lambda
  (Kiln's `spec/sema-lambda.md` §9). `this` in a lambda is the
  enclosing class's.
- A closure's semantic context in a function body is the function; in
  a nested lambda the outer call operator (the `CXXMethod` pattern of
  a generic one); outside a function body the namespace, class or
  enumeration, in whose member list Kiln also puts it
  (`kiln_sema/src/lambda/mod.rs:333`, `kiln_ast/src/builder.rs:167-203`).
  A local class's or enumeration's context is the function
  (`kiln_sema/src/decl.rs:9984`), whatever block declares it.
- The call operator is not `IMPLICIT`; the closure, its capture
  fields, the conversion function and `__invoke` are
  (`lambda/mod.rs:632`, `:1357`, `:1391`, `lambda/capture.rs:1986`).
  The conversion and the invoker exist only without captures, are
  templates for a generic lambda, and get a body on first use
  (`mod.rs:1462-1515`). Special members are declared lazily.
- A generic lambda's call operator is a `FunctionTemplate` member; its
  specialisations are `Ast.templates.specs_of(template)`, with the
  closure as context, not members, made on use
  (`kiln_ast/src/templates.rs:602`, `:1771-1824`).
- An init-capture's variable is reachable only through
  `LambdaCapture.var`, is in no `DeclStmt`, has the call operator as
  context, and shares its initialiser's `ExprId` with the entry of
  `LambdaData.inits` (`capture.rs:1579`, `kiln_ast/src/decl.rs:2653`).
  A capture of a variable-length array's bound has no `var` and its
  `init` is the enclosing function's own bound expression.
- Captures are ordered: explicit ones, then implicit ones by first
  use, then array bounds (`kiln_ast/src/lambda.rs:50-68`).
- Every instantiation of an enclosing template makes new closures and
  new local classes; a local class's members are defined with the
  enclosing function (`kiln_sema/src/templ/subst/local.rs:84-186`).
- A `DeclStmt` for `struct S {} s;` holds the class and then the
  variable (`kiln_parse/src/decl.rs:5137`).
- `LambdaArena` has no iterator and its order follows analysis, which
  instantiation interleaves: never read an order from it.
- Kiln copies a default argument or default member initialiser it
  rewrites (`clone_with_children`): whether a `LambdaExpr` is copied
  with the same `LambdaId` was not determined. Find out; rule 3 above
  covers it either way.
