## Scope

The verify loop as a command (`spec/edits.md` §8, §10.1, §10.2 `check`,
§10.5, §10.6):

```
slip check  --plan <id or file> --round <n> --edits <id or file> [--declared <id or file>] …
slip rename --from <qualified name> --to <identifier> [--kind function|variable] …
```

1. **`check`**: from an edit set to a result. Apply (`slip_apply::build`,
   the overlay and its blobs published); the verify phase
   (`slip_exec::pool::run` with `post`), over the observers §8.2 says;
   the agreement (`slip_verify::agreement`); the residue (§8.4, on
   `slip_kiln::scan`); the state (`slip_verify::conclude::state`); the
   result published; the report; the transform run record.
2. **`rename`**: the request built and published (§10.1 step 2); a new
   round (`Store::next_round`); the map phase with `transform`;
   `reduce_round` (`docs/wp/WP-075.md`); then `check`'s steps; then
   `apply_result` if `--write` or `--patch` was given.
3. The lines and the exit statuses of §10.5.

Files: new `crates/slip_cli/src/transform/{check.rs, rename.rs,
residue.rs, report.rs, run_record.rs}`, new
`crates/slip_cli/tests/{rename.rs, verify_overlay.rs}`;
`crates/slip_cli/src/args.rs` and `src/commands.rs` for the two
commands (the shared options are parsed already).

If the package grows past two thousand lines, hand back `check` with
its tests first (`rename` is then one function over it) and say so.

## Interface

```rust
// slip_cli::transform::check
pub struct CheckInput<'a> {
    pub store: &'a Store, pub plan_id: Digest, pub plan: &'a Plan, pub round: u64,
    pub selected: &'a [usize], pub partial: bool,
    pub transform_id: Digest, pub transform: &'a Transform,
    pub set_id: Digest, pub set: &'a EditSet,
    pub declared: Option<(Digest, Declared)>,
    pub options: &'a TransformOptions,
    pub pool: &'a slip_exec::pool::Options,   // -j, memory, timeouts: what `parse` passes
}
/// Steps apply, verify, scan, conclude. Publishes the overlay, its blobs
/// and the result. `record` gets one `Step` per step run.
pub fn check(input: &CheckInput<'_>, record: &mut Vec<Step>, out: &mut dyn Write, err: &mut dyn Write)
    -> Result<(Digest, TransformResult), CommandError>;

// slip_cli::transform::residue
/// §8.4. `read_by_some` yields, sorted, the owned real paths in the
/// `inputs` of any `ok` map shard of the round.
pub fn residue(transform: &Transform, set: &EditSet, read_by_some: &[Vec<u8>], unparsed_mains: &[Vec<u8>],
               extensions: &[Vec<u8>], threads: usize) -> std::io::Result<Vec<Residue>>;

// slip_cli::transform::report
pub fn result_summary(result_id: Digest, result: &TransformResult, out: &mut dyn Write);
pub fn details(/* the set, the result, the plan, the verify shards */ out: &mut dyn Write);
```

Rules fixed here:

- **Who gets a verify job** (§8.2): every selected observer whose map
  shard is `ok`, when the declared rules are not empty; with no rules,
  those that read an overlay file. The others are `unchanged`.
- **A refused edit set** ends after reduce: no overlay, no verify
  phase, a result with state `refused`, status 1.
- **Cancellation** (a signal during a phase, `spec/exec.md` §7): the
  result is still concluded (`incomplete`) and published with the run
  record, as §10.6 says; nothing is written whatever was asked.
- **Residue** reads each file once, in parallel over files with at most
  `-j` threads, and its result is sorted, so it does not depend on the
  threads. The set of files some observer read is made in one pass over
  the map shards and holds owned paths only. A file that cannot be read
  is an `Input` error naming it.
- **`check` on an edit set that is not reduce's** (§10.2): the set's
  `plan`, `round` and `transform` must be the round's; its `basis` is
  not checked (a mutated set has the original's). The overlay is built
  from the set given; `--declared` given is used as it is.
- **Counting memory** for the run record: the coordinator's own peak at
  the end of each step from `/proc/self/status` (0 where there is
  none), as the phase records read theirs.
- **The report's details** are bounded as §10.5 says (64 `finding`
  groups, 200 lines of each other kind, each cut announced); the
  records hold everything.
- `--from` and `--to` are checked against §3 before the store is
  opened: usage errors, status 2.

## Tests

- `crates/slip_cli/tests/rename.rs` (`spec/edits.md` "Tests"), through
  the executable over small trees written by the test:
  a function in a header and two source files (`verified`, `--write`
  leaves the post-image, status 0); the same with `--patch`; without
  either (tree and working directory untouched, only the store grew);
  a refused run (a use in a macro body): status 1, the refusal line,
  no `overlay` line; a contested name; `--only` (a partial result that
  is not written without `--allow-partial`); an observer that does not
  parse, with and without `--allow-unparsed`; residue in a file no
  observer compiles, with and without `--allow-residue` (status 1
  both times, written the second); a mention; the usage errors; the
  output compared line by line with §10.5's forms.
- `check` as a stage: the edit set of a run given back to `check` gives
  the same result id; the same set with one edit removed (a new `EDTS`
  made with `slip_model`) is `not_verified` with a `stale` line or a
  mismatch, or `verified_with_residue` naming the range; with one edit
  added at a `kept` range: `not_verified`.
- A second declaration of a variable in another source file that the
  rename is made to miss (by `check` with a set lacking that edit): the
  `stale` line names the observer.
- `crates/slip_cli/tests/verify_overlay.rs` (`spec/verify.md` "Tests").
- Determinism: one run with `-j 1` and one with `-j 4` in fresh stores
  give the same five ids and the same standard output after the store's
  path is replaced.
- The run record: one `RUNT` per invocation, its steps in order, the
  two phase records named exist.
