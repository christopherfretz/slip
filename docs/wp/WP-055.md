## Scope

1. **`slip_digest::records`** (`spec/verify.md` §2.3 "Records",
   "Interface"): one record per unit: its `KeyId`, the `Key` behind it,
   kind, class, name, whether it is indeterminate.

   text (`read`), which parses it needs (`needs`), names resolved to

3. **`slip_verify::run`** (`spec/verify.md` §7, §7.1, §7.3): `State`,
   `state`, `RunVerdict`, `run_verdict`, `Header`, `Report` with its JSON
   and its text.
4. **The order of findings** (`spec/verify.md` §6, `spec/model.md`
   §8.3 rule 4b): by `(rank, file, key)` instead of `(kind, file, key)`,
   so that a finding that says a unit differs is never behind the ones
   that say a unit is unknown. The numbers of `FindingKind` do not
   change.

## Interface

`spec/verify.md` §2.3 "Interface" (`records`, `declare`) and §7.3
(`run`). They are fixed.

`records`:

- The units are those of the ordinary walk: `run_with` with detail
  `none` and names asked for. A unit's record takes `id`, `kind`,
  `class` and the indeterminate flag from its `Written`
  (`crates/slip_digest/src/units.rs:35`), and its name from
  `Output.names`.
- The `Key`: for a unit with an entity, `Walk::key`
  (`crates/slip_digest/src/keys.rs:215`) says whether the entity has a
  key at all; if it has none the unit was written under a fallback key
  (`units.rs:479-483`) and the record's `key` is `None`. Otherwise the
  `Key` is computed again by `compute_key` inside the same wrapper
  `Walk::key` uses (`keys.rs:226-240`: the depth guard, the unit's state
  put aside, `in_key`, and the entity's `representative` as the
  declaration read), mapped with `rules`, and **checked**: its id must
  be the unit's `KeyId`, else `Err` naming the unit. The order unit's
  `Key` is the one `units::order_unit` builds (`units.rs:571`), mapped.
- `records` adds nothing to a digest: it calls no function that writes a
  stream after the walk except `compute_key`, whose discriminator stream
  is its own.

`declare`:

- `resolve` and `finish` take records, not parses, so the tests feed
  them by hand. The mapping `m` of §2.3 is computed from the post
  records' `Key`s: follow `parent` up to a root, map each with the rules
  of the lines above, and take the id.
- Errors are reported in the order §2.3 gives (syntax first, then the
  lines `resolve` handles, then `created`).

The order of findings:

```rust
// slip_model::verdict
impl FindingKind {
    /// The place of the kind in the order of findings (spec/verify.md §6):
    /// changed 0, removed 1, added 2, derived_changed 3, indeterminate 4,
    /// derived_indeterminate 5. Not the kind's number in the format.
    pub fn rank(self) -> u8;
}
```

- One function gives the rank; the decoder's check, `compare_groups`
  and the report's groups (`run.rs`, sorted by `(rank, name, key)`) all
  call it. No second table.
- The encoding does not change. The new decoder refuses a verdict
  written in the former order only where an `indeterminate` finding
  precedes a `derived_changed` one, and no verify shard exists outside
  tests (`spec/verify.md` §6).

`run`:

- `slip_verify` depends on `slip_model` only
  (`crates/slip_verify/Cargo.toml`); the report is made from `Shard`,
  `Verdict`, `Finding`, `Declared` and counters, with
  `slip_model::json`.
- `indeterminate_only` is computed from the counters
  `verify.findings.*` (`spec/verify.md` §7.2), never from the listed
  findings: a verdict lists only its first `limit`. A shard with a
  `mismatch` verdict and without those counters is `failed`.
- `Report::add` is called once per selected observer in plan order and
  keeps no shard.

## Tests

- `crates/slip_digest/tests/records.rs`: `spec/verify.md` "Tests", and
  over every directory of the pair tests, both sides: the record ids are
  exactly the unit keys of `digest` with detail `all`, every record
  with a `Key` has `key.id() == id`, and `records` is `Ok`. A pair for
  which it is `Err` is a finding about the walk (a key that is not the
  same when computed again): list it in the handback, keep it in an
  explicit allow list with the reason.
- `crates/slip_digest/tests/determinism.rs` and the goldens do not
  move: `run_with` is the same walk.
- `crates/slip_cli/tests/declare.rs`: `spec/verify.md` "Tests". The
  cases on snippets close the loop: the pre snippet and the post snippet
  (the same entities under the new name) are digested, the post one with
  the rules `resolve` gave, and `slip_verify::compare_groups` over all
  units gives no finding other than those of units the walk leaves
  indeterminate at your base. Cases: a namespace relocated to the global
  namespace, into an existing namespace, into a namespace another line
  relocates, a member function renamed, a class renamed with `=` kept
  for its members, an overloaded function named with `[function]` and
  its parameter list.
- The order of findings. In `crates/slip_verify/tests/compare.rs`:
  `derived_changed_is_within_the_limit`: a pre and a post image with ten
  thousand indeterminate units (declared and derived both) and one
  derived unit whose digest differs; `compare_groups` then `verdict`
  with `limit` 64 lists the `derived_changed` finding first, and with
  `limit` 1 lists it alone; the same with one `changed`, one `removed`
  and one `added` unit beside it gives those three, then it. A property
  over generated findings: the output is ascending by `(rank, file,
  key)` and is a permutation of what the former order gave. In
  `crates/slip_model/tests/sections.rs`: a verdict in rank order is
  accepted in binary and JSON; one with an `indeterminate` finding
  before a `derived_changed` one is rejected by rule 4b with its offset
  and path; `FindingKind::rank` is a bijection onto 0..=5 and every
  kind's number is what it was.
- `crates/slip_verify/tests/run.rs`: `spec/verify.md` "Tests", with the
  golden JSON and text. The properties, asserted over generated sets of
  states (a fixed seed, as `tests/groups.rs`): the run's verdict is
  `verified` only if every state is `verified` or `unchanged` and there
  is at least one; `not_verified` if any is `mismatch` or `not_parsed`;
  the state counts add up to the number of `add` calls.
