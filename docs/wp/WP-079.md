## Interface

```
cargo xtask corpus rename <corpus> --from <name> --to <identifier> [--kind <k>]
        [--owned <path>]… [--expect <state>] [--accept] [--build] [-j <n>]
```

as `spec/harness.md` §6.5. Fixed here:

- The store is `<corpus build directory>/slip-store/`; the plan is
  built once and found again by later runs (`slip rename --db` finds an
  existing plan as `parse` does).
- `<target>` in the result file's name is `--from` with `::` replaced
  by `.`.
- The clang of `--accept` and `--build` is the compiler the corpus was
  configured with (`spec/harness.md` §8), not `$SLIP_CLANG`.
- `--accept` runs the plan's commands through the jobserver, at most
  `-j` at once, and compares exit statuses only.
- `--build` copies the source directory with `cp -a` semantics under
  `<corpus build directory>/rename-copy/`, applies the patch with
  `patch -p0` (or `git apply`), and builds in
  `<corpus build directory>/rename-build/`; both are removed by
  explicit path when the checks pass. It refuses to start if less free
  space is left than twice the source directory's size.
- Every long step runs under the jobserver, and the command is meant to
  be started in the background: it prints a line when each step starts
  and ends.

### What was built

- `cargo xtask corpus rename` in `xtask/src/corpus/rename.rs` (dispatched
  from `xtask/src/corpus.rs`; `run_logged` and `Ctx::say` there became
  `pub(crate)`). It runs `slip rename … --db <database> --owned <src>
  --store <corpus dir>/slip-store --allow-unparsed --allow-residue
  --patch <corpus dir>/rename/<target>.patch --relative-to <src>`
  (plus `--kind` and `-j` when given), printing its lines as they come,
  reads the result, its edit set, the transform run record that names
  the result and the two phase records, then runs the five checks in
  order and writes `bench/results/<corpus>.rename.<target>.json`.
- `--write` is given only to the inverse rename of check 5, whose
  `--owned` and database are the copy's. Every step prints
  `step <x>: started (…)` and `step <x>: done in <s>`; every check
  prints `check <name>: ok|FAIL|skipped|not run (<detail>)`.
- The copy (`copy_tree`) reads and writes every regular file's bytes
  itself (no `std::fs::copy`, no hard link, no reflink, no
  `copy_file_range`), keeps modes, modification times and symbolic
  links. The copy and its build tree are removed through
  `slip_run::remove_tree`, which refuses a path that is not strictly
  under the corpus directory.
- `--accept` runs each plan command pair (pre-image, then
  `-ivfsoverlay`) under one jobserver token, on at most `-j` threads.
  cmake, `make` and `patch` of `--build` run with the jobserver in
  `MAKEFLAGS` and no `-j`.
- No `unsafe`; no C++ text is read or changed by xtask (`patch` applies
  `slip`'s patch; files are compared byte for byte). Errors name the
  path and the step; a bad argument is a usage error, never a panic.

### Where the spec was silent (now in `spec/harness.md` §6.5 and §8.2)

1. `--from` must be identifiers joined by `::` (leading `::` allowed),
   `--to` one identifier; otherwise usage error, status 2. `<target>`
   drops a leading `::`.
2. `--slip <path>` added (as `invariants` and `demo` have it), so the
   tests use a stand-in; the default is `target/release/slip`.
3. "The corpus's build directory" is the corpus directory
   `<root>/<name>/`, beside `stores/` and `demo1/`: `slip-store/`,
   `rename/` (patch and VFS file, kept), `rename-copy/`,
   `rename-build/` (with the inverse run's store and the four logs).
4. "The source directory" is the clone `src/`, not `src/llvm`: the
   `--owned` default and `--relative-to` (demo-2 §3 wants the whole
   checkout owned). A given `--owned` must be under `src/` by real path.
5. `slip rename` statuses 2 and 3, a missing `result` line, or a
   printed state other than the record's stop the command (status 1);
   0, 1 and 4 go on to the checks.
6. The first failing check stops the rest (`not run`). A result with no
   overlay (`refused`) skips checks 3–5 even when asked: there is no
   post-image.
7. Check 1 also fails `verified`/`verified_with_residue` when no patch
   was written (`--patch` refused at apply: `not_owned`,
   `not_canonical`, `stale_file`, `spec/edits.md` §7.2); otherwise
   `--accept` alone would pass a run that produced nothing.
8. Check 2 accepts `slip reduce` status 0 or 1 and compares the `edits`
   line.
9. Check 3: the corpus's `c_compiler` for C and Objective-C, its
   `cxx_compiler` otherwise; the observer's arguments after `argv[0]`
   plus `-fsyntax-only`, its directory and environment. The VFS file
   maps only files whose post differs from pre, `use-external-names`
   off. A run that does not end within an hour, or is killed, counts as
   a difference. At most 20 differences listed, each with its first
   error line. Progress every tenth.
10. Check 4: the free-space check (`df -Pk` on the corpus directory;
    at least twice the bytes of `src/`'s regular files) and the removal
    of a `rename-copy/` or `rename-build/` left by an earlier run happen
    before `slip` runs. The copy leaves out `src/.git`. The patch is
    applied by `patch -p0 --batch --forward --no-backup-if-mismatch`
    (not `git apply`); an empty patch is not applied. Generate is §8.3's
    `make` of the `generate` entries without its promised-file check,
    then `make all`; `PYTHONDONTWRITEBYTECODE=1` on these.
11. Check 5: §6.4's inverse, `--owned` mapped into the copy; status 0 or
    1 goes on to the comparison, which covers presence, kind, bytes and
    link targets (not modes or times), `.git` left out.
12. The result file's members (listed in §6.5) hold no absolute path.
    The exact members are `state`, `counters`, `tally`, `agreement`,
    `spellings`, `residue` and `not_plain_at_macro` (the count the
    record needs: `not_plain` refusals that have a `macro`). The ids are
    not compared, because every `slip rename` takes the store's next
    round and the round is in each id.
13. The file is replaced only when every check passed and the exact
    members are equal (or there was no file); otherwise the run's file
    is `<file>.new` and the old one stays. A difference in the exact
    members alone fails the command (`FAILED (counters)`). Status 0 ok,
    1 any failure or error, 2 usage.

### Stale statements of `docs/demos/demo-2.md` (not edited)

- **§1** lists WP-060 to WP-078 as what must be in place. The rename on
  this workspace also rests on WP-147 (one spelling per file) and
  WP-157 (reduce refuses an unfinished map phase), both done. The
  corpus sits on the case-folding mount, so WP-147's counter
  `inputs.respelled` can appear in its shards.
- **§2.1** "this one site is claimed some four thousand times and is one
  edit" now holds on a case-folding volume too: since WP-147 a header
  reached under two spellings is one file from the first place a path
  enters. Before, two spellings were two files to reduce, and apply
  refused them as `not_canonical` (WP-075 F1).
- **§2.3** "there is no overlay and no verify phase; the state is
  `refused`, exit status 1, and nothing is written" holds (WP-076
  decision 7), but is incomplete:
  - a result record and a transform run record are still published, so
    `corpus rename` writes a result file for it;
  - `--patch` writes no patch (§7.2);
  - the harness skips checks 3–5 for it.
- **§3** "Each is one `slip rename … --owned <its source directory> …`"
  leaves out what the harness adds: `--store <corpus dir>/slip-store`,
  and `--kind` and `-j` as given. "Source directory" is `src/`, the
  checkout, not the cmake source directory `src/llvm`.
- **§3** "The same run can be made a stage at a time (`slip map`, `slip
  reduce`, …)": since WP-157 `slip reduce` of a round whose map phase
  did not finish refuses it (status 3, no edit set), where it used to
  count the missing observers as unparsed. `slip check` of a refused
  set of such a round errors the same way. `--allow-unparsed` (§3's
  clang-fuzzer units) does not cover an observer whose map was cut
  short.
- **§4** "Wall time of each step: map, reduce, apply, verify, scan": the
  transform run record also has `plan` (the `--db` plan step), `conclude`
  and `write` (the patch). The result file carries every step the
  record has.
- **§4** "Determinism: … the whole first run repeated once with `-j 4` —
  the same edit set, overlay and result ids": a second `slip rename` in
  the same store takes the next round, and the round is in the edit set
  (hence overlay and result) id. So the ids match only in a fresh store.
  `corpus rename` always uses `<corpus dir>/slip-store` and does not
  repeat the run. The repeat is a separate `slip rename … --store
  <another dir> -j 4` by hand, or the counters of a second `corpus
  rename` (compared exactly) stand in for it.
- **§4** "Peak resident size of the coordinator per step … reduce flat in
  the number of observers": the step's `peak_rss` is the process's at
  the end of the step, a high-water mark, so a reduce step after the
  map coordinator's peak cannot show itself flat. Reduce's own
  `reduce.peak.*` (WP-142) are returned beside the edit set, not in its
  counters, so neither the record nor the result file has them. Not one
  of the five packages; noted while reading.

### The four demo runs, as the tool is (for the supervisor)

From the repository, with `scripts/env.sh` sourced, each in the
background with its output to a log. First `cargo build --release -p
slip_cli` (the default `slip`; xtask does not build it), then `cargo

```
cargo xtask corpus rename llvm --from llvm::getAsUnsignedInteger --to parseAsUnsignedInteger \
      --kind function --accept --build -j 12
cargo xtask corpus rename llvm --from llvm::TimePassesIsEnabled --to TimePassesEnabled \
      --kind variable --accept -j 12
cargo xtask corpus rename llvm --from llvm::callDefaultCtor --to makeDefaultPass \
      --expect refused -j 12
cargo xtask corpus rename llvm --from llvm::PowerOf2Ceil --to powerOf2Ceil \
      --expect not_verified -j 12
```

demo-2 §3's commands run as they are written. `-j 12` is a bound: the
jobserver (6 tokens) gives fewer at once. `--build` needs free space of
twice `src/` on the corpus volume, and builds all of LLVM and clang
once more. Expected lines, after `slip rename`'s own:

1. `check state: ok (verified_with_residue)`;
   `check determinism: ok (edits <id>)`;
   `check accept: ok (4061 commands; 2 rejected on both images, none
   otherwise)`; `check build: ok (patched, configured, generated and
   built in …/rename-build)`; `check back: ok (the inverse rename ended
   …; the copy is the source again)`; `removed …/rename-copy`,
   `removed …/rename-build`; `counters: new (…)`;

2. `check state: ok (verified)` (or `verified_with_residue`);

3. `slip rename` prints five refusal lines and `state refused` (status
