# WP-111 — agreement for a namespace rule: `kept`, the stale check, and `slip declare`

- Status: in-progress
- Milestone: M2
- Track: C
- Needs: WP-053, WP-069, WP-070, WP-110
- Size: M
- Parallel with: the transform packages

## Scope

`spec/verify.md` §9.2 exempted namespace rules from the stale check: a
relocated namespace merges with the one that stays, so `direct` said
nothing. The review of `docs/wp/WP-105.md` showed what that leaves
open: one observer sees an owned entity in `acme`, another still sees
it in `legacy` (a second declaration in a header that was not edited),
both verify, and the program does not link. §9.2 "Stale for a namespace
rule" is the amended rule; this package builds it.

1. **The walk** (`crates/slip_digest`, where `docs/wp/WP-069.md` counts
   `via` and `direct`): for a rule of kind `namespace`, `direct(r)` and
   `kept_via(r)` as §9.2 defines them, using the ownership of
   `docs/wp/WP-110.md`. "A member of a namespace whose own, unmapped key
   is the key `r` produces, or of a namespace inside it": decide and
   state what "inside" means for an inline namespace, the unnamed
   namespace, a nested namespace that a second rule maps elsewhere, and
   a namespace reached through two rules.
2. **The record**: `Use.kept_via` (`spec/verify.md` §9.1, §9.2), its
   section invariants, readers and writers (`crates/slip_model`).
3. **The run** (`crates/slip_verify`, `docs/wp/WP-070.md`'s agreement):
   stale for a namespace rule when either count is not 0; a `kept` key
   no observer has is reported like an unused exemption; nothing else of
   §9.3 to §9.5 changes. The report's `stale` finding says which count.
4. **`slip declare`** (`docs/wp/WP-053.md`'s): the `kept <entity>` line
   (resolved in the post-images with the file's rules, `spec/verify.md`
   §2.3), the error `DependencyEntity` for a `relocate` line whose
   entity is a dependency entity and not a namespace, ~~and `files` from
   the command's `--owned` and `--readonly`~~ (landed with WP-053).
5. **Attack it**, each as a test with two observers:
   - a function declared in two owned headers, one edited: stale;
   - an owned overload for a dependency type that stays, listed in
     `kept`: not stale; the same not listed: stale; the same listed and
     moved in one observer: stale;
   - a compatibility `using` added in the old namespace, listed in
     `kept` and `created`: not stale;
   - an owned explicit specialisation of a dependency template in the
     old namespace: not counted;
   - an entity that is owned in one observer and a dependency entity in
     the other (declared by the dependency in a header only one
     includes): say what each count gives and whether the result is
     right;
   - the same key reached through `r` in one observer and directly in
     another where it is in `kept`: stale by `kept_via`;
   - a namespace that only some observers see at all.
   A case where two observers disagree and neither count shows it, or
   a correct edit that cannot be declared, is reported with its pair.

## Added after the review of WP-103 (2026-11-23)

`spec/verify.md` §2.3 resolves a `relocate` line's new parent with the
lines above it, "so a line whose new parent another line relocates
comes after that line". In the other order the first line's rule
matches nothing and verification reports differences: safe, and
baffling. `slip declare` refuses it: a line whose new parent, or a
namespace enclosing it, is relocated by a **later** line is an error
that names both lines (a test each way). With that, every file
`declare` accepts gives one rule table whatever the order of its
lines; say so in §2.3 and test it (the lines of each fixture permuted
into every accepted order give one `rules_id`).

The same review: a function a class template befriends, without
defining it, needs a rule for the friend declaration's own key beside
the function's (`docs/wp/WP-071.md` "Added after the review of
WP-103"). `slip declare` given a `rename` or `relocate` line for such a
function writes both rules; a test, and the pair that is a mismatch
without the second.

## Added after the reviews of WP-069 and WP-110 (2026-11-23)

- A `relocate` line cannot rename an `extern "C"` function: its key's
  parent is `root` whatever namespace it is written in, and a
  relocation's rule matches by parent (`spec/landed/digest/WP-069.md`).
  `slip declare` says so for such a line (an error naming the line and
  the reason; the function keeps its name, which is what the linker
  sees) rather than writing a rule that matches nothing; a test.
- "An entity that is owned in one observer and a dependency entity in
  the other" (item 5) is confirmed by WP-110's review as a wrong
  `verified` when no observer of the run includes both declarations.
  Neither count of this package shows it. It is closed by
  `docs/wp/WP-116.md` (a renamed entity is defined in owned code); here
  the test states what each count gives and points there.
- The verify job gives the walk each file's subject path computed from
  its **real** path (`spec/verify.md` §2.1, added by WP-110's fix
  round): a read-only file reached through a symbolic link under an
  owned root is read-only. Where `--owned` and `--readonly` become
  `files` (item 4), the same resolution; a test with a link each way.
