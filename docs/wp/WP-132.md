# WP-132 — version 0 without a name built from text: an identifier piece, a spelling at a name range, lookup in a scope

- Status: todo
- Milestone: M3
- Track: G
- Needs: WP-091
- Size: M
- Parallel with: WP-129 and WP-133 (all three edit `spec/api.md`; ask the supervisor which merges first), WP-092, WP-093

## Scope

The operator's rule (`docs/design/01-transform-api.md` §6): a transform
that manipulates C++ code as strings is a failure of the API. The
conformance suite (`spec/landed/api/WP-091-effects.md`,
"Disagreements") found three places where version 0 leaves a transform
no other way, all about names. The supervisor's rulings, to be written
into `spec/api.md` and built:

1. **An identifier piece.** A fourth kind of piece:

   ```cpp
   consteval code identifier(std::string_view name);
   ```

   `name` is a value, not code: it must be one identifier as §6.1
   rule 1 defines it (plain, not a keyword), else `invalid_argument`.
   The piece is recorded as an identifier (`spec/edits.md` §4 and the
   run output of §7.6: a new piece kind; propose the encoding and the
   format version to the supervisor before changing `slip_model`), so
   that reduce, apply and a later version know that a name was put
   there and which. `api.op.identifier` counts it as every operation is
   counted. `text` of an identifier keeps working and stays the escape
   hatch (`api.op.text`).
2. **`expect_renamed` and the identifier agree.** `expect_renamed(e,
   new_identifier)` stays as it is. Say in §7.5 rule 3 that the edits
   which write the new name are `identifier(new_identifier)` pieces,
   and have verification's check of a spelled piece (§7.2 rule 5,
   `spec/verify.md` §10) cover an identifier piece put at the name
   range of a reference to, or a declaration of, an entity declared
   renamed in the same run: the name written there denotes the entity
   whose key is the renamed entity's under the run's rules. An
   identifier piece anywhere else is checked by the comparison alone,
   as text is. If the obligation cannot be carried by the existing
   `spec/verify.md` §10 records without a new one, stop and report:
   that part becomes a package of its own.
3. **A spelling at a name range.** `replace(name_range_of(R), spell(E))`
   for a reference `R` whose name range is not its extent
   (`n::f`): today the fully qualified text lands after the written
   qualifier (`n::::n::g`). The rule: the sibling form of §7.2 rule 1
   applies to an edit of `name_range_of(R)` exactly as to an edit of
   `extent_of(R)` (same conditions, same recorded edit); when its
   conditions do not hold, `replace` throws `invalid_argument` (a name
   range takes a sibling's identifier; another entity is spelled at
   the extent). The same for the name range of a declaration `D`:
   `spell(E)` there is `E`'s identifier when `parent_of(E)` is the
   parent of `D`'s entity, else `invalid_argument`. The test
   `code/s7.2-r1-only-at-the-extent` changes with the rule.
4. **Lookup in a scope.**

   ```cpp
   consteval std::vector<info> lookup(info scope, std::string_view identifier);
   ```

   The entities declared with that identifier as members of `scope` (a
   namespace, a class, an enumeration), as `lookup("…::identifier")`
   gives them when the scope has a qualified name, and also when it has
   none (an unnamed namespace, a specialisation). `wrong_kind` for
   another sort; `invalid_argument` for what is not one identifier. No
   string is taken apart to find "the same scope, another name".
5. **The rename example without a string operation.**
   `resource/examples/rename_function.cpp`: `renamed()` (an `rfind` of
   `"::"`) becomes `lookup(parent_of(f), to)`; `text(to)` becomes
   `identifier(to)`. Its conformance directories must pass unchanged in
   what they expect of the subject (the pieces' kind in the expectation
   changes). `api.op.text` is absent from the counters of both
   examples; a test asserts it for every file of `resource/examples/`.
6. **Not here, recorded as the backlog of primitives** in the landed
   file: a wrap (`f(x)` to `g(f(x))`) still needs literal punctuation;
   it is M4's parsed fragment with typed holes
   (`docs/design/01-transform-api.md` §6). Count the uses of `text` in
   `crates/slip_script/tests/api/` by what they write (an identifier, a
   punctuation token, anything else) and list the third group.

## Interface

## Tests

A conformance directory per rule (`// spec:` lines; `cargo xtask
api-table` regenerated): `identifier` accepts and refuses (a keyword,
two tokens, empty, a qualified name, not UTF-8); the piece's record; a
spelling at the name range of a qualified reference to a sibling, to a
non-sibling (throws), at a declaration's name; `lookup(scope, id)` in
a namespace, a class, an unnamed namespace, an enumeration, a wrong
sort; the example's directories. For item 2: a pitfall row or a
`slip_cli` test where the identifier piece lands on a name that
denotes another entity in the post-image (the new name is hidden at
one use) and verification fails there.

## Rules

`docs/AGENTS.md`. No string manipulation of code in any example or test
transform. The gate is the full `cargo xtask ci`. Second review if
`slip_model`'s formats or verification's obligations change (items 1,
2); the reviewer's question: an identifier piece whose record a reader
of the old format version misreads; an edit that writes a name
verification then does not check.

## Done when

The gate passes with `main` merged in; `rename_function.cpp` has no
`text`, no `cat` and no operation on a string that holds a name other
than passing it on; the supervisor has ruled on the encoding.

## Out of scope

Names in declarative contexts (`docs/wp/WP-133.md`). Fragments with
