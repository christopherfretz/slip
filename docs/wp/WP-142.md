# WP-142 — slip_reduce: the memory bound is checked by what reduce holds, not by resident pages

- Status: in-progress
- Milestone: M2
- Track: D
- Needs: none
- Size: S
- Parallel with: every package that does not edit `crates/slip_reduce`

## Scope

`crates/slip_reduce/tests/memory.rs`
(`one_site_ten_thousand_shards_fan_in_two`) checks `spec/edits.md` §5.6
("memory that does not grow with the number of observers or of claims")
by the growth of the process's resident high-water mark across one
call, and asserts that ten thousand shards grow the peak by at most
256 KiB more than a thousand do. It failed the gate of WP-135's branch
on 2026-11-23 (28 KiB against 348; the retries read 872 and 932), which
changes nothing in reduce. The bound has been softened twice for host
load (`1d3d7a07`, `54c6dcd0`). Three gate logs give the same picture:

| log | 1,000 shards | 10,000 shards |
|---|---|---|
| WP-095's second gate | 8 | 276 |
| WP-135's gate, first reading | 28 | 348 |
| the same, absolute `VmHWM` after the call | 4,136 and 4,176 | 4,480, 4,480, 4,524 |

So the larger run ends about 300 KiB higher every time, and the test
passes or fails on which side of 256 the reading falls. Two things may
be true and this package says which:

1. **Is something held per shard or per run?** 300 KiB over 9,000 more
   shards is about 33 bytes a shard: the size of a digest. Find by
   reading `crates/slip_reduce/src/` everything whose size is a
   function of the number of shards, runs, or observers (a set of
   observer digests for "one observer once", a list of temporary file
   names, a list of run results, the plan, counters, the `Shards`
   implementation's own state, a vector reserved by `len()`), and say
   for each what it costs at 10,000 and at 1,000,000 shards. If §5.6's
   sentence is false as written, either remove the state (an observer
   check that is external or streamed) or correct §5.6 to state the
   term and its constant ("32 bytes an observer": a million observers
   are 32 MiB, which may well be the right trade); propose which and
   stop for the supervisor if it is the second.
2. **The measurement cannot resolve the bound it asserts.** The reading
   is `VmHWM` after minus `VmRSS` before; on this kernel (6.12) the
   resident counters are per-CPU and read approximately, so a reading
   is off by an amount that grows with the CPUs (24 here), and the
   first log line of the failing run shows `VmHWM` 4,336 against
   `VmRSS` 4,132 immediately after the reset that should make them
   equal. The workspace forbids `unsafe`, so there is no counting
   allocator. Replace what the gate checks by something exact:
   **reduce counts what it holds**: the peak number of shards' `edits`
   sections open at once, of open temporary files, of collapsed records
   in memory, and the peak length of every collection item 1 finds, as
   counters of the result (`reduce.peak.*`, beside `reduce.claims`; say
   in `spec/edits.md` §5.6 that they are informational and not part of
   the edit set's identity, or keep them out of the serialised form and
   return them beside it: say which and why). The test then asserts
   exact values: with `fan_in` 2 and one thread, at most 2 sections, 3
   files, and collections whose peak is the same for 1,000 and 10,000
   shards (or is exactly the stated term of item 1). The resident
   reading stays as what the large ignored run prints, asserted only
   against the absolute bound and only there.

## Interface

`crates/slip_reduce/src/` (the counters), `crates/slip_reduce/tests/memory.rs`,
`spec/edits.md` §5.6, `spec/landed/edits/WP-142.md` (the inventory of
item 1 with its costs).

## Tests

The exact assertions of item 2; a mutation each: a list kept per run, a
set kept per observer, one more section held than `fan_in`: each fails
an assertion by its exact number. The test passes twenty times in a row
beside a full build (say how that was run within the host's rules).

## Rules

`docs/AGENTS.md`. The gate is the full `cargo xtask ci`. The
supervisor's read is enough unless item 1 removes state from reduce
(then a second review of that change).

## Done when

The gate passes with `main` merged in; the gate's memory test has no
assertion on a resident reading that a quiet change of the kernel's
counters can fail; §5.6 says what is true.

## Out of scope

Reduce's time; the workers' memory (`spec/exec.md`).

## Ruling

The supervisor's ruling of 2026-11-23 on the inventory (`0df9900d`), verbatim:

> go on and build, as follows. Record this ruling verbatim in `docs/wp/WP-142.md` (a section "Ruling") and fix its Interface line to `spec/landed/edits/WP-142.md`.
>
> (a) Unparsed list: **state the term.** §5.6 says the edit set lists the unparsed observers (§6), 32 bytes each, and that this is the one thing reduce holds that grows with the observers; the format does not change, no golden moves. Also correct §5.6's last paragraph to name everything your section 2 found that grows with the transform (the builder's live sites, claimed sites, kept and unresolved ranges, reports, changes, failures, paths), as a statement of what is held, no new bound.
>
> (b) Waiting runs: **not the fold in any order.** Keep the fold in plan order exactly as it is, and bound the map by back-pressure: a run is not started while it is more than `W` runs ahead of the earliest run not yet folded, `W = 4 × threads` (a named constant, stated in §5.6 with the resulting bound: at most `W` joined states wait). Requirements: the earliest unfolded run can always be started and finished whatever the window holds (no deadlock: say in a comment why, and test it); with one thread nothing changes; the output is byte-identical to today's for every existing test (`tests/order.rs` across thread counts and shuffled finishing orders must pass unchanged). New tests: a `Shards` whose first run is slow (it blocks in `open` until a later run has been opened, or for a short fixed time: no sleeps longer than a second in total) with several threads: the peak of waiting runs is at most `W` by the counter, and the result equals the one-thread result; the same with the slow run last; a failing run inside a full window (the error wins as today, nothing hangs). Every blocking test has a timeout that fails it rather than hang (a hung test binary holds a host-wide cargo slot).
>
> (c) `Cleanup::levels`: recompute from `n` and `fan_in`. Yes.
>
> Counters: `reduce.peak.*` returned beside the edit set as a new field of `Reduced` (§5.7 updated), never in `EditSet.counters`: as you propose. Include `reduce.peak.waiting_runs`.
>
> Test asserts as you planned (sections ≤ 2, files ≤ 3, collapsed records equal for 1,000 and 10,000 shards, waiting runs ≤ 1 with one thread, unparsed 0), the separate exact test for the unparsed term, and the resident reading only in the `#[ignore]`d test against the absolute bound. Mutations: the three of your brief, plus: the window never blocks (the slow-run test's peak exceeds `W`); the window blocks the earliest run (the deadlock test times out and fails).
>
> Because (b) changes scheduling in reduce, an independent reviewer will read that part after your gate; write the handback so that the concurrency argument (who may block, who wakes whom, why the earliest run always proceeds, what happens on an error or a panic in a worker) is in one place. The rest of your brief stands (twenty runs, pre-gate checks, the gate, host rules).
