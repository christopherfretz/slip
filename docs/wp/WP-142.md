# WP-142 — slip_reduce: the memory bound is checked by what reduce holds, not by resident pages

- Status: review
- Milestone: M2
- Track: D
- Needs: none
- Size: S
- Parallel with: every package that does not edit `crates/slip_reduce`

## Scope

`crates/slip_reduce/tests/memory.rs`
(`one_site_ten_thousand_shards_fan_in_two`) checks `spec/edits.md` §5.6
("memory that does not grow with the number of observers or of claims")
by the growth of the process's resident high-water mark across one
call, and asserts that ten thousand shards grow the peak by at most
256 KiB more than a thousand do. It failed the gate of WP-135's branch
on 2026-11-23 (28 KiB against 348; the retries read 872 and 932), which
changes nothing in reduce. The bound has been softened twice for host
load (`1d3d7a07`, `54c6dcd0`). Three gate logs give the same picture:

| log | 1,000 shards | 10,000 shards |
|---|---|---|
| WP-095's second gate | 8 | 276 |
| WP-135's gate, first reading | 28 | 348 |
| the same, absolute `VmHWM` after the call | 4,136 and 4,176 | 4,480, 4,480, 4,524 |

So the larger run ends about 300 KiB higher every time, and the test
passes or fails on which side of 256 the reading falls. Two things may
be true and this package says which:

1. **Is something held per shard or per run?** 300 KiB over 9,000 more
   shards is about 33 bytes a shard: the size of a digest. Find by
   reading `crates/slip_reduce/src/` everything whose size is a
   function of the number of shards, runs, or observers (a set of
   observer digests for "one observer once", a list of temporary file
   names, a list of run results, the plan, counters, the `Shards`
   implementation's own state, a vector reserved by `len()`), and say
   for each what it costs at 10,000 and at 1,000,000 shards. If §5.6's
   sentence is false as written, either remove the state (an observer
   check that is external or streamed) or correct §5.6 to state the
   term and its constant ("32 bytes an observer": a million observers
   are 32 MiB, which may well be the right trade); propose which and
   stop for the supervisor if it is the second.
2. **The measurement cannot resolve the bound it asserts.** The reading
   is `VmHWM` after minus `VmRSS` before; on this kernel (6.12) the
   resident counters are per-CPU and read approximately, so a reading
   is off by an amount that grows with the CPUs (24 here), and the
   first log line of the failing run shows `VmHWM` 4,336 against
   `VmRSS` 4,132 immediately after the reset that should make them
   equal. The workspace forbids `unsafe`, so there is no counting
   allocator. Replace what the gate checks by something exact:
   **reduce counts what it holds**: the peak number of shards' `edits`
   sections open at once, of open temporary files, of collapsed records
   in memory, and the peak length of every collection item 1 finds, as
   counters of the result (`reduce.peak.*`, beside `reduce.claims`; say
   in `spec/edits.md` §5.6 that they are informational and not part of
   the edit set's identity, or keep them out of the serialised form and
   return them beside it: say which and why). The test then asserts
   exact values: with `fan_in` 2 and one thread, at most 2 sections, 3
   files, and collections whose peak is the same for 1,000 and 10,000
   shards (or is exactly the stated term of item 1). The resident
   reading stays as what the large ignored run prints, asserted only
   against the absolute bound and only there.

### The window: the concurrency argument in one place

`first_pass` in `crates/slip_reduce/src/lib.rs` (its doc comment says the
same; landed §4).

- **Shared state**, one `Mutex<Fold>`: `started` (runs handed out),
  `folded` (the earliest run not folded), `waiting` (finished runs not
  folded, by run), `joined` (the fold, in run order, as before), `stop`,
  `failed` (the first error). One `Condvar` `wake`.
- **Who may block.** Only a worker that holds no run, in
  `wake.wait`, while `started >= folded + W`, `W = 4 × threads`. A worker
  runs a run without the mutex and never waits while it holds one; a run
  needs nothing of another run.
- **Who wakes whom.** The worker that finishes a run takes the mutex,
  puts the run in `waiting`, folds every run from `folded` on that is
  there, and if `folded` moved calls `notify_all`. On a failed run it sets
  `stop`, keeps the first error, and calls `notify_all`. A run that
  panics is caught around the run: the worker sets `stop`, keeps the
  first payload, and calls `notify_all`. A woken worker checks `stop`,
  then the end, then the window, again under the mutex.
- **Why the earliest run always proceeds.** If `started == folded`, the
  window condition is false (`W >= 4`), so no worker waits and the next
  to look starts run `folded`. If `started > folded`, run `folded` is held
  by a worker that is running it, not waiting; it finishes, fails or
  panics, and each of the three ends in `notify_all` after `folded` moved
  or `stop` was set. So the waiting workers are always woken by the
  worker holding the earliest run, and every worker waiting at once is
  impossible.
- **The bound.** Run `r` starts only if `r < folded + W` and `folded` only
  grows, so `waiting` is within `folded .. folded + W`: at most `W` states,
  the run just finished included.
- **An error** in a run (`Err` of `first_pass_run`: a temporary file)
  stops the hand-out; workers finish the run they hold and return; the
  first error is the result, as with the pool before. An `Input` error of
  a shard is not a run's error: it is offered to `Least` and the pass goes
  on, as before.
- **A panic** in a run: caught (`catch_unwind`); the worker stops the
  pass, keeps the first payload under the mutex, wakes the waiting
  workers and returns; when every worker has returned, the caller
  `resume_unwind`s the payload, so the run's own panic and message reach
  the caller with any number of threads (the merges' and second pass's
  pool does the same). A panic of a worker outside a run (in the fold,
  under the mutex) is not caught: `WakeOnPanic` stops the pass and wakes
  the waiting workers as it unwinds; with one thread it reaches the caller
  as it is, with several `std::thread::scope` raises its own panic ("a
  scoped thread panicked") and the original payload is lost. The mutex may
  be poisoned then; every lock takes the guard from the poison (as the
  pool did). (Corrected in the review fix round: this paragraph said the
  scope resumes the panic, which it does not.)
- **Arithmetic.** `W = WINDOW_PER_THREAD.saturating_mul(threads)`, the
  condition `started >= folded.saturating_add(W)`; the threads spawned are
  at most the runs of the pass or level, whatever `threads` is.
- **One thread.** Runs run in order on the caller's thread and each is
  folded before the next starts: the window condition is never true.
- **Output.** The fold is in run order exactly as before; only when a run
  may start changed. `tests/order.rs` passes unchanged (thread counts 1,
  2, 8, shuffled finishing orders).
