set) and §6.3 (the `reduce.*` counters), in the crate `slip_reduce`. The

## Interface

`spec/edits.md` §5.7, exactly:

```rust
pub struct Options { pub fan_in: usize, pub threads: usize, pub scratch: PathBuf }
pub trait Shards {
    fn open(&self, index: usize) -> Result<Option<Shard>, String>;
    fn len(&self) -> usize;
    fn observer(&self, index: usize) -> Digest;
}
pub struct Reduced { pub edits: EditSet, pub declared: Option<Declared> }
pub fn reduce(plan: Digest, round: u64, shards: &dyn Shards, options: &Options)
    -> Result<Reduced, ReduceError>;
pub enum ReduceError { Input { observer: Digest, message: String }, Io(String) }
pub fn declared(set: &EditSet) -> Result<Option<Declared>, String>;
```

`reduce` returns `declared(&edits)`: there is one derivation, and
`slip check` (`docs/wp/WP-076.md`) calls the same function on an edit
set it was handed.

Fixed by this package, beyond the spec's text:

- `Shards` must be `Sync` when `threads > 1`; `fan_in < 2` and
  `threads == 0` are a panic of the caller's (documented), not an error.
- `Shards::open` returning `Some` for a shard whose `content id` the
  caller knows: the `Basis` needs each shard's content id, so the trait
  gains `fn shard_id(&self, index: usize) -> Option<Digest>` if computing
  it from the returned `Shard` (re-encoding) is not byte-exact. Decide by
  test, and record the decision in `spec/landed/edits/WP-062.md`.
- The temporary files are private to one call: created under
  `options.scratch` with names that hold the process id and a counter,
  removed when `reduce` returns, whatever it returns. Their format is not
  a container and is not specified; it must not leak into the edit set
  (no path, no order of arrival).
- Reduce is two passes over the shards and no more: pass 1 reads each
  `edits` section (subjects and links into memory, claims into runs);
  after the merge the collapsed claims are streamed once through §5.2's
  treatment and §5.4; pass 2 reads each shard's `inputs` and `files` for
  the file agreement of the live sites. At no time are more than `fan_in`
  shards open per thread.
- `Input` errors, each naming the least observer index that shows it: a
  shard with no `edits` section, another `scheme`, another `transform`
  than the first `ok` shard's; a subject whose `id` is not its key's
  digest; a link or a claim that names a key that is no subject of its
  shard; a `files` entry that disagrees with the shard's own `inputs`;
  two subjects of one id with different `key` or `renamed`; two rules
  with one match (§6.2).

## Tests

- `crates/slip_reduce/tests/reduce.rs`, over shards written by hand
  (`tests/common/` holds the builders): everything `spec/edits.md`
  "Tests" lists for it, and one test per `Input` error above. Each test
  names its section.
- `crates/slip_reduce/tests/order.rs`: for claim sets generated from a
  fixed seed (the seed is printed on failure and can be given by
  `SLIP_REDUCE_SEED`): the `EDTS` bytes and the `DECL` bytes are identical
  under every `fan_in` in {2, 3, 7, 64} and `threads` in {1, 2, 8}, and
  with a `Shards` that delays each `open` by a pseudo-random time so that
  the threads' runs finish in different orders. Under a permutation of
  the plan's order the edit set differs in `basis`, `unparsed`, `first`
  and `display` only (the test compares everything else). One site
  claimed by ten thousand shards with `fan_in` 2: the peak of live heap,
  measured by a counting allocator in the test binary, stays under a
  bound the test states and justifies from §5.6.
- A model test: a second, deliberately naive implementation of §5 inside
  the test crate (everything in memory, sorted maps, no runs), compared
  with `reduce` on every generated set. A disagreement is a defect of one
  of them; say which in the handback.
