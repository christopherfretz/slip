# WP-062 — slip_reduce: from the claims of every observer to one edit set

## Scope

`spec/edits.md` §5 (all of it), §6.2 (the declared changes of an edit
set) and §6.3 (the `reduce.*` counters and the sums of the shards'
`api.*` and `edits.*` counters), in the crate `slip_reduce`. The crate
reads shards and writes nothing but its temporary files; it links
`slip_model` and nothing else.

Reduce refuses a shard whose `edits.files` holds a path that is not
canonical or is `/` (`transform::is_file_path`), with an `Input` error
naming the shard (§5.1): WP-060's reader does not check it, and an edit
set reduced from it would be refused by its own reader
(`spec/landed/edits/WP-061.md` §8).

Reduce is written once for every producer. What M2's own producer, the
native rename, never makes (copy pieces, nested edits, groups, reports,
`changed` entries of its own shape, failed runs, `renamed` rules) is in
scope all the same and tested with shards written by hand: it is what a
run of a programmable transform hands over (`spec/api.md` §7.6,
`spec/edits.md` §4.8), and M3 adds a producer and nothing under it.

Files: everything under `crates/slip_reduce/` (the manifest's description
names `spec/reduce.md`, which never existed: `spec/edits.md` §5). Suggested
modules, one concern each: `subjects.rs` (§5.2), `collapse.rs` (§5.3, the
join of claims, reports, `changed` entries and failures), `runs.rs`
(§5.6, the temporary files and the merge), `outcome.rs` (§5.4's table),
`geometry.rs` (§5.4: `contested`, `overlap`, `cyclic`, file agreement),
`groups.rs` (§5.5: the closure, rejection, effect), `declared.rs` (§6.2),
`lib.rs` (§5.7).

Starts when WP-061 is on `main`. Needs nothing of M1 or Kiln: every test
builds its shards by hand.

## Interface

`spec/edits.md` §5.7, exactly:

```rust
pub struct Options { pub fan_in: usize, pub threads: usize, pub scratch: PathBuf }
pub trait Shards {
    fn open(&self, index: usize) -> Result<Option<Shard>, String>;
    fn len(&self) -> usize;
    fn observer(&self, index: usize) -> Digest;
}
pub struct Reduced { pub edits: EditSet, pub declared: Option<Declared> }
pub fn reduce(request: &Transform, request_id: Digest, plan: Digest, round: u64,
              shards: &dyn Shards, options: &Options) -> Result<Reduced, ReduceError>;
pub enum ReduceError { Input { observer: Digest, message: String }, Io(String) }
pub fn declared(set: &EditSet) -> Result<Option<Declared>, String>;
```

`reduce` returns `declared(&edits)`: there is one derivation, and
`slip check` (`docs/wp/WP-076.md`) calls the same function on an edit
set it was handed. `reduce` reads three things of the request: its id
(every shard must name it), its kind (`no_subject` is a rename's
refusal) and `indivisible`.

Fixed by this package, beyond the spec's text:

- `Shards` must be `Sync` when `threads > 1`; `fan_in < 2` and
  `threads == 0` are a panic of the caller's (documented), not an error.
- The `Basis` needs each shard's content id. If computing it from the
  returned `Shard` (re-encoding) is not byte-exact, the trait gains
  `fn shard_id(&self, index: usize) -> Option<Digest>`. Decide by test,
  and record the decision in `spec/landed/edits/WP-062.md`.
- The temporary files are private to one call: created under
  `options.scratch` with names that hold the process id and a counter,
  removed when `reduce` returns, whatever it returns. Their format is not
  a container and is not specified; it must not leak into the edit set
  (no path, no order of arrival).
- Reduce is two passes over the shards and no more: pass 1 reads each
  `edits` section (subjects, links, rules and group ties into memory;
  claims, reports, `changed` entries and failures into runs); after the
  merge the collapsed claims are streamed once through §5.2's treatment
  and §5.4's table; pass 2 reads each shard's `inputs` and `files` for
  the file agreement of the live sites and the copied files. At no time
  are more than `fan_in` shards open per thread.
- **What is held in memory** is what §5.6 allows and nothing else: the
  joined subjects, links and rules; one record per distinct edit that is
  in a group (none under `indivisible`); one per copy piece of a live
  edit; one per live edit that lies within another live edit or within a
  copied range. A run of a native rename has none of the last three, and
  a test shows it by the counting allocator of `order.rs`. Finding the
  nested and crossing sites is one sweep over the live sites in
  `(file, lo, hi)` order with a stack of open ranges, not a comparison
  of pairs.
- **Group ties in pass 1.** A shard's group names its members by index;
  an edit's identity across shards is `(file path, lo, hi, pieces)`.
  Pass 1 keeps, per distinct grouped edit, a digest of that identity and
  a union-find parent: memory is the number of distinct grouped edits,
  whatever the number of observers.
- The order of §5.5 is the order of the code: every rejection of §5.4
  over all live sites; then the groups rejected; then effect, repeated
  until nothing more is rejected. No rejection is undone ("Open
  questions": no fixed point).
- `Input` errors, each naming the least observer index that shows it: an
  `ok` shard with no `edits` section, another `scheme`, a `transform`
  that is not `request_id`; a link or a claim that names a key that is
  no subject of its shard; a `files` entry that disagrees with the
  shard's own `inputs`; a `replace` claim in a file the request does not
  own; two subjects of one id with different `rule`.
  That two rules disagree is not an `Input` error but the refusal
  `rule_conflict` (§6.2).

## Tests

- `crates/slip_reduce/tests/reduce.rs`, `pieces.rs`, `groups.rs`, over
  shards written by hand (`tests/common/` holds the builders):
  everything `spec/edits.md` "Tests" lists for each, and one test per
  `Input` error above. Each test names its section.
- `crates/slip_reduce/tests/order.rs`: for claim sets generated from a
  fixed seed (the seed is printed on failure and can be given by
  `SLIP_REDUCE_SEED`), with copies, nested edits, groups, reports and
  failed runs among them: the `EDTS` bytes and the `DECL` bytes are
  identical under every `fan_in` in {2, 3, 7, 64} and `threads` in
  {1, 2, 8}, and with a `Shards` that delays each `open` by a
  pseudo-random time so that the threads' runs finish in different
  orders. Under a permutation of the plan's order the edit set differs
  in `basis`, `unparsed`, `first` and `display` only (the test compares
  everything else). One site claimed by ten thousand shards with
  `fan_in` 2: the peak of live heap, measured by a counting allocator in
  the test binary, stays under a bound the test states and justifies
  from §5.6.
- A model test: a second, deliberately naive implementation of §5 inside
  the test crate (everything in memory, sorted maps, pairs compared, no
  runs), compared with `reduce` on every generated set. A disagreement
  is a defect of one of them; say which in the handback.

## Handback

Implemented in `crates/slip_reduce/`. Every decision beyond the spec is in
`spec/landed/edits/WP-062.md`; `spec/edits.md` §5.3, §5.5, §5.7 and §6.3
were corrected where they were wrong or silent (each change is named
there).

- **Interface.** As §5.7, with `Shards: Sync` always (the passes read
  from several threads) and `Shards::open` giving the stored bytes:
  reduce decodes them and the basis id is their trailer, the id of the
  bytes read (`reduce.rs` `basis_is_of_the_bytes_read`; re-encoding a
  decoded shard drops an ignorable section). Also `Options::new`,
  `Display` and `Error` on `ReduceError`, and `ReduceError::Options` for
  `fan_in < 2` and `threads == 0`. `reduce.runs` is not written (it
  depends on `fan_in`).
- **Review fix round.** Every claimed site blocks, live or rejected, so
  more disagreement never accepts more (`edits.md` §5.4, §5.5; landed
  §5), with `order.rs` `more_shards_refuse_no_less` as the generated
  property and its two exceptions (the effect, §5.2) counted. A site
  rejected only with its group is refused with the new cause
  `with_group` (17, a format change; landed §6), and every `replace` is
  explained (checked of every generated set). One observer twice in a
  plan, and a non-canonical `inputs` path, are `Input` errors (landed
  §2). The generator now varies subjects per observer, makes more than
  eight notes and tied macro sites.
- **Tests.** `reduce.rs` 50 (one per `Input` error among them),
  `pieces.rs` 22, `groups.rs` 7, `order.rs` 2 (160 generated cases, 15
  reductions each, compared with the naive model of `tests/common/model.rs`,
  and the monotone property over each case less one shard; seeds 0 to 7
  also run), `memory.rs` 2 and one ignored large run, 5 unit tests of
  `geometry.rs`. The model and reduce agree on every generated case.
- **Memory.** Not a counting allocator: the workspace forbids `unsafe` in
  tests too. `memory.rs` measures the growth of `VmHWM` instead (landed
  §9): 8 KiB for one site of 1,000 or 10,000 shards at `fan_in` 2. The
  large run (10,000 shards, 200,000 claims, 8 threads, debug build) takes
  3.5 s and grows the peak by 118 MiB, which is the output set.
- **Mutations.** After the fix round: my 47, the reviewer's 38 (adapted
  to the new code) and 8 of the rules the fix round added, each applied
  alone. All are caught but M29 (8 bytes leaked a shard, below the
  resolution of `memory.rs`, about 25 bytes a shard). M07 changes one
  round of the effect but not the set (the next round buries what the
  ineffective carrier carried); a unit test of the round catches it.
  Landed §10 has the table.
- **Not done.** The counting allocator (above). `reduce` is not yet
  driven by a real store (`docs/wp/WP-075.md`).

### Supervisor's handback (merge, 2026-11-23)

Merged after an independent review ("merge after fixes") and one fix
round, on my read of the round. What the round decided, now the text
of `spec/edits.md` §5.4 and §5.5:

- **Every claimed site blocks**, live or rejected: more disagreement
  between observers never accepts more. `geometry::effect` and
  `cyclic` are checked against a fixpoint and a closure over every
  pair; `order.rs` `more_shards_refuse_no_less` holds the property over
  generated plans.
- The two ways one more shard can accept what was refused are the
  specification's meaning and are counted by that test, not holes: a
  copy that carries an edit that was `buried`, and §5.2's selection
  (one more shard selects or deselects a subject).
- **Every `replace` is explained**: a new cause `with_group = 17`
  (`EDTS`, a format change) for a live site rejected only with its
  group.
- The shard id is of the bytes read; an observer named twice, a
  non-canonical `inputs` path and options out of range are `Input`
  and `Options` errors.
