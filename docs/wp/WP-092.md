## Scope

`spec/api.md` §2.4, §2.5, §7.6; `spec/exec.md` §5; `spec/edits.md` §3
(the transform request, kind `script`), §4 (the `edits` section of a map
shard), §4.6 (a failed run), §4.8 (the mapping from a run output) and
§10.1 (`slip map`). A map job that carries a programmable transform: the
worker compiles the transform once, and for each observer parses the
subject, digests it, runs the transform against it, and publishes one
shard.

`spec/edits.md` carries everything `spec/api.md` §7.6 hands over; this
package implements the encoding that specification gives and none of
its own. It stands on milestone M2's packages and adds a branch to each
of two of them:

- the records are `slip_model`'s (`docs/wp/WP-060.md`: `Transform`,
  `Script`, `Edits`, `Claim`, `Failure`), and a job reaches its request
  through protocol 2's `Job.transform` and the store's `Object::Transform`
  (`docs/wp/WP-064.md`);
- **in the worker**, the map job of a transform is `docs/wp/WP-074.md`'s:
  it reads the request, parses with `ParseOptions::written`, digests,
  and dispatches on the request's kind (`slip_cli::worker::transform::
  run_transform`). `rename` is the native rename; for `script` that
  package answers `Err("a script transform needs a worker built with
  slip_script")`. This package replaces that `Err` with its branch and
  adds the compile-once state the branch needs. It does not add a
  second task or a second dispatch;
- **in the command**, `slip map --transform <file.cpp> [--transform-arg
  <option>]… [--indivisible] --owned <path>… [--readonly <path>]…` is
  parsed by `docs/wp/WP-076.md`, which answers `slip: map: --transform
  needs a slip built with slip_script` (status 2) at the step that
  builds the request. This package fills in that step (item 4): load,
  compute the `TransformId`, build and publish the `Script` request.
  The rest of `map` (the round, the phase, the transform run record,
  the output lines) is WP-076's and does not change.

What is decided:

1. **The transform request** is `spec/edits.md` §3's with kind
   `script`: `Script { id, file, options, steps, bytes, depth }`, the
   ownership (§2.1) and `indivisible` (false unless the command says
   `--indivisible`). `Script.id` is `spec/api.md` §2.2's `TransformId`,
   so the request id covers it and shards of different transforms, API
   levels or header bytes are never reduced together. A worker whose
   own compilation of the transform unit gives another `TransformId`
   than `Script.id` (a file of the transform changed during the run)
   fails its jobs: no shard of it is written under the request
   (`spec/edits.md` §3, §4.8).
2. **One compile per worker process.** The worker's task holds the
   loaded transform for its lifetime. A worker is told nothing about
   the transform when it starts (protocol 2 puts the request's id in
   each job, `spec/exec.md` §5.2), so the compile happens at the first
   job that names a script request. Thread structure: at that job the
   task's thread enters `with_transform` (WP-089) with the worker's
   stack size and serves that job and the following ones inside the
   closure, for as long as they name the same request; a phase has one
   request (`spec/edits.md` §10.1), so that is the worker's lifetime.
   Each job's subject is parsed as
   WP-074's map job of a transform parses it (`parse_observer_opts` with
   `ParseOptions::written`), whose closure (on the front end's thread)
   runs the digest walk and then, at WP-074's dispatch, `Loaded::run`.
   The session crosses threads by `&mut`; the subject never leaves its
   thread. A worker that serves no job with a script request compiles
   nothing.
3. **A worker that serves one job pays the whole compile** for it
   (50 ms to 1.2 s). The default of `--worker-jobs` is therefore 16
   when the phase's request is a script, and 1 otherwise as today (a
   native rename compiles nothing). The
   value is provisional until WP-093 has measured compile time per
   worker and memory growth across jobs. This package amends
   `spec/exec.md` §5, where the default is stated, to say both values
   and that the first is provisional; an explicit `--worker-jobs` wins
   in both cases.
4. **Outcomes.** A completed run: the run output is encoded into the
   shard's `edits` section as `spec/edits.md` §4.8 says, row by row: an
   `Edit` is a `replace` claim with `subjects` empty, `reason` `none`,
   `votes` 1, `tiers` the edit's set, and `macro` absent unless the
   subject gives the invocation; `Edits.transform` is the request id,
   and `RunOutput.transform` is checked against `Script.id` and not
   written; groups, reports, `changed` and `renamed` are the same
   records; the run's counters and the `edits.*` counters of
   `spec/edits.md` §6.3 go to the shard's counters. The section
   satisfies §4.7 (`Edits::normalise`, WP-060, is called and must
   change nothing: a run output is canonical already). A failed run
   (§2.8): the shard has status `ok` for the parse
   and digests, carries the failure (`spec/edits.md` §4.6: kind,
   message, place, rendered diagnostics, the refusal) and no edits; the
   observer counts as not examined. A
   transform that does not load: every job of the worker fails the same
   way. The coordinator therefore loads the transform itself, once,
   before it starts any worker, and stops with the error of
   `spec/api.md` §12; a worker that then fails to load what the
   coordinator loaded is an internal failure. It is not 4061 failed
   observers.
5. **Budgets and cancellation.** The budgets come from the request. A
   worker does not handle signals and dies with its process group
   (`spec/exec.md` §7), so the session's cancel token is not used by the
   pipeline; a run that does not end is ended by its step budget.
6. **Ownership** reaches `KilnSubject` as a predicate over real paths,
   built from the request (`spec/edits.md` §2.1).
7. **The digests in the shard are the pre-image's and are unchanged by
   the transform**: the walk runs first and its output is sealed before
   `Loaded::run` is entered. A test proves it by running a transform
   that tries everything.

What a script's shard does not have, and why that is right: subjects,
links and the stances `keep`, `refuse` and `unresolved` are the native
rename's (`spec/edits.md` §4.2, §4.8; `spec/api.md` §7.3 rule 7), and a
script request has no residue scan (`spec/edits.md` §8.4). Pieces are
not flattened: a spelled piece keeps its key, and apply derives where
it lands (`spec/api.md` §7.6 rule 4).

**`tiers`.** `spec/api.md` §7.6 makes an edit's `tiers` a set (requests
that are one edit join their tiers by union), where the run output of
`docs/wp/WP-081.md` and `docs/wp/WP-088.md` as landed has one `tier`
and keeps the higher. Until the host is changed (`docs/wp/WP-102.md`) this package writes
the bit of that one tier, and its hand-back says which it found.

## Interface

```rust
// crates/slip_cli/src/worker/transform.rs (WP-074's file): the `script`
// branch of `run_transform`, and beside it the state a worker keeps
// from one job to the next while the request id is the same.
pub struct LoadedScript { /* the request id, the loaded transform (WP-089) */ }

// crates/slip_script/src/shard.rs
/// spec/edits.md §4.8: a completed run's output as the `edits` section
/// of the request `request`, and the counters it adds to the shard
/// (the run's, and `edits.*` of §6.3). `Err` if `out.transform` is not
/// `script.id`.
pub fn encode(request: Digest, script: &slip_model::transform::Script, out: &RunOutput)
    -> Result<(slip_model::Edits, Vec<slip_model::Counter>), String>;
/// §4.6: the record of a failed run (WP-089's failure) as the section.
pub fn encode_failure(request: Digest, script: &slip_model::transform::Script, failure: &RunFailure)
    -> Result<(slip_model::Edits, Vec<slip_model::Counter>), String>;
```

`RunFailure` stands for whatever type `docs/wp/WP-089.md` gives the
record of `spec/api.md` §7.6. The command is the one of
`spec/edits.md` §10.1, given above; this package adds no command and no
option.

## Tests

`crates/slip_cli/tests/transform_map.rs`, on the small test corpus of
`slip_cli`'s existing tests:

1. Four observers sharing a header, `swap_arguments.cpp`: every shard has
   the header's edits; the shards of observers that see the same site
   have byte-equal claims for it; every shard's `Edits.transform` is the
   request id the command printed, and the section decodes and passes
   `spec/edits.md` §4.7.
2. One compile per worker: with `--worker-jobs 4`, the counter
   `api.transform_compiles` is 1 per worker process. With a script
   request and no `--worker-jobs`, the workers are started with 16;
   with a rename request or none, with 1.
3. A transform that fails in one observer (it divides by zero when a
   name is declared): that shard carries the failure and no edits; the
   others are complete.
4. A transform that does not compile: the command stops with
   `transform-compile` before any worker starts, the diagnostics once.
5. A step budget of 1000 and a transform that loops: `step-budget` in
   every shard; wall time bounded.
6. Rule 7: digests with and without the transform are byte-equal.
7. SIGINT during a run that loops ends the phase as `spec/exec.md` §7
   says, with no worker left.
8. The transform's file rewritten between the command's load and a
   worker's: that worker's jobs fail, no shard of them carries `edits`,
   and the message names both ids.
9. `--indivisible` sets the request's flag; without it the flag is
   false. A worker given a rename request still runs the native rename
   (WP-074's test, run again here with `slip_script` linked).

`crates/slip_script/tests/shard.rs`, without a worker: each row of
`spec/edits.md` §4.8 from a `RunOutput` built by hand (a literal, a copy
and a spelled piece; a group; a report with and without a place; a
`changed` entry; a rule; counters), and a failed run with and without a
refusal; `encode` of an output whose `transform` is not the script's id
is `Err`.
