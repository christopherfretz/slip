## Scope

Launch after `spec/edits.md` (M2) is accepted with the changes
`spec/api.md` §7.6 needs, listed below; this package implements the
encoding that specification gives and none of its own.

`spec/api.md` §2.4, §2.5, §7.6; `spec/exec.md` §5; `spec/edits.md` (the
`edits` section of a map shard, the transform request). A map job that
carries a programmable transform: the worker compiles the transform once,
and for each observer parses the subject, digests it, runs the transform
against it, and publishes one shard.

What is decided:

1. **The transform request** names the transform's file, the author's
   options and the ownership; its id includes `spec/api.md` §2.2's
   transform id, so shards of different transforms, API levels or header
   bytes are never reduced together.
2. **One compile per worker process.** The worker's task holds the
   loaded transform for its lifetime. Thread structure: the task's
   thread enters `with_transform` (WP-089) with the worker's stack size
   and serves jobs inside the closure; each job's subject is parsed by
   `parse_observer_with`, whose closure (on the front end's thread) runs
   the digest walk and then `Loaded::run`. The session crosses threads
   by `&mut`; the subject never leaves its thread.
3. **A worker that serves one job pays the whole compile** for it
   (50 ms to 1.2 s). The default of `--worker-jobs` is therefore 16
   when the map job carries a transform, and 1 otherwise as today. The
   value is provisional until WP-093 has measured compile time per
   worker and memory growth across jobs. This package amends
   `spec/exec.md` §5, where the default is stated, to say both values
   and that the first is provisional; an explicit `--worker-jobs` wins
   in both cases.
4. **Outcomes.** A completed run: the run output is encoded into the
   shard. A failed run (§2.8): the shard has status `ok` for the parse
   and digests, carries the failure (kind, message, place, rendered
   diagnostics) and no edits; the observer counts as not examined. A
   transform that does not load: every job of the worker fails the same
   way. The coordinator therefore loads the transform itself, once,
   before it starts any worker, and stops with the error of
   `spec/api.md` §12; a worker that then fails to load what the
   coordinator loaded is an internal failure. It is not 4061 failed
   observers.
5. **Budgets and cancellation.** The budgets come from the request. A
   worker does not handle signals and dies with its process group
   (`spec/exec.md` §7), so the session's cancel token is not used by the
   pipeline; a run that does not end is ended by its step budget.
6. **Ownership** reaches `KilnSubject` as a predicate over real paths,
   built from the request (`spec/edits.md` §2.1).
7. **The digests in the shard are the pre-image's and are unchanged by
   the transform**: the walk runs first and its output is sealed before
   `Loaded::run` is entered. A test proves it by running a transform
   that tries everything.

What `spec/edits.md` must carry for a programmable transform (the full
list with reasons is in the design hand-back; the supervisor reconciles
the two specifications before this package launches): replacement text
with its copy sources and spelled entities, or pieces; for each spelled
piece its key and, if pieces are flattened, its offset and length in
the text (`spec/api.md` §7.6 rule 4); the two conflicts of
`spec/api.md` §7.1 rule 3, which only reduce can see: two different
edits of one range (a), and edits whose copies are not well-founded
(b), such as `replace(x, copy(r))` with `x` properly inside `r`; a
group identity derived from content; reports; `changed` entries with
their places and reasons; `renamed` rules; the record of a failed run
(`RunFailure`); the transform's counters.

## Tests

`crates/slip_cli/tests/transform_map.rs`, on the small test corpus of
`slip_cli`'s existing tests:

1. Four observers sharing a header, `swap_arguments.cpp`: every shard has
   the header's edits; the shards of observers that see the same site
   have byte-equal claims for it.
2. One compile per worker: with `--worker-jobs 4`, the counter
   `api.transform_compiles` is 1 per worker process. With a transform
   and no `--worker-jobs`, the workers are started with 16; without a
   transform, with 1.
3. A transform that fails in one observer (it divides by zero when a
   name is declared): that shard carries the failure and no edits; the
   others are complete.
4. A transform that does not compile: the command stops with
   `transform-compile` before any worker starts, the diagnostics once.
5. A step budget of 1000 and a transform that loops: `step-budget` in
   every shard; wall time bounded.
6. Rule 7: digests with and without the transform are byte-equal.
7. SIGINT during a run that loops ends the phase as `spec/exec.md` §7
   says, with no worker left.
