# WP-140 — a relocation into a namespace a dependency opens

- Status: review
- Milestone: M1
- Track: C
- Needs: WP-111
- Size: M
- Parallel with: WP-106, WP-122, WP-125, WP-126, WP-130, WP-136 (one digest branch merges at a time)

## Scope

The re-check of `docs/wp/WP-111.md` found a correct relocation that
cannot verify. It is no wrong `verified`; it is an edit the tool's
first use meets (a codebase moved into a root namespace that a
library it depends on already opens):

```cpp
// dep.h, read-only
namespace acme { struct Dep {}; }
// a.cpp, owned; before
#include "dep.h"
namespace legacy { int g(int); }
int u() { return legacy::g(1); }
// after: namespace acme { int g(int); }  int u() { return acme::g(1); }
```

with `relocate legacy => :: acme`: the member's keys agree
(`legacy::g(int)` on both sides), and the run reports `removed legacy`
with the rule's `via 0`. The post-image's `acme` is keyed as the
dependency's namespace (its first declaration is the dependency's), so
the rule on the namespace matches nothing and the pre-image's unit
`legacy` has no partner. `spec/verify.md` §2.1 states the limit since
WP-111; the fixtures are `crates/slip_digest/tests/rules/stale/
dependency-opens-target-kept-moved` and its sibling without `kept.txt`.

1. **The design question; propose and stop for the supervisor before
   building.** A namespace is open: it is the one entity that owned
   code and a dependency both declare as a matter of course, and
   ownership "by the first declaration" gives it to whichever header
   comes first, which differs between observers (one includes `dep.h`,
   one does not). Say, with the cost of each:
   - what the unit of a namespace is when both an owned file and a
     read-only file open it: one unit per view (the owned openings and
     the dependency's, the owned view mapped by the rule and so the
     partner of `legacy`; WP-111's stale counts already keep such a
     view apart, `Counting::views`), or one unit whose digest holds
     only what no opening can change;
   - what a namespace's unit digests at all (inline, attributes, the
     enclosing row, the first opening's place?) and which of those
     belongs to an opening and which to the namespace;
   - the converse case, which is the motivating use (`spec/pitfalls.md`,
     the rows on a dependency that keeps the old namespace): the
     dependency opens `legacy`, before and after, and the owned
     members move to `acme`. Show what it gives today, in an observer
     that includes the dependency and in one that does not, and that
     the answer you propose keeps both right;
   - the two observers of one run that disagree about whose the
     namespace is: what each reports, and that reduce and the stale
     check see no disagreement where there is none;
   - a nested namespace (`acme::detail` opened by both), an inline
     namespace, the unnamed namespace (a dependency header's and an
     owned file's are one entity in a translation unit), and a
     namespace alias to a namespace both open;
   - what must NOT start to verify: a dependency's declaration moved
     into `acme` by the edit (pitfall row N34, §2.1's first bullet), a
     dependency macro that opens the namespace redefined by owned
     code.
2. **Built after the ruling**: the keys and units as ruled
   (`spec/digest.md` §3.3, §3.4; `spec/verify.md` §2.1 and §9.2), the
   stale counts consistent with them (`via` is not 0 for a rule that
   was used), and the pitfall catalogue's rows (`good` trees: the case
   above, with `kept`, nested, through two observers of which one does
   not include the dependency; `bad` trees: a member left behind, the
   N34 shape, the dependency's declaration edited).
3. **A rule no observer used.** Decide with item 1 whether a rule
   whose `via`, `direct` and `kept_via` are 0 in every observer is
   reported (a line of the report, not a failure), and where
   (`spec/verify.md` §9).
