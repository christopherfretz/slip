## The cases

The table of `spec/harness.md` §10.2 fixes the hazards; you find the
sites. On the pinned corpus (`bench/corpora.toml`, row `llvm`):

- `llvm::hashing::detail` is declared in two blocks of
  `llvm/include/llvm/ADT/Hashing.h` and named in `StableHashing.h`,
  `llvm/lib/IR/StructuralHash.cpp` and
  `llvm/unittests/ADT/HashingTest.cpp`; `01-relocate` edits all of them,
  so that the tree is a consistent program and not only one that the
  selection happens to accept. Search the whole of `src/` for other
  uses before you call the list complete, and say in the `README.md`
  what you searched for. `Hashing.h` has `using ::llvm::hash_value;
  return hash_value(value);` inside the namespace: read what the rename
  does to each lookup, argument-dependent lookup included, before
  calling the edit correct, and say it in the `README.md`.
- `StringRef::find(char C, size_t From = 0) const` is in
  `llvm/include/llvm/ADT/StringRef.h`; `02-default-argument` names, as
  its second finding, one function of `llvm/lib/Support/` that calls
  `find` with one argument.
- For `03-overload`, `04-adl` and `05-shadow` the site is yours to
  choose in `llvm/lib/Support/`, under these conditions: the tree
  compiles for **every** selected observer (the edit is silent); the
  call that changes meaning is in a function that is not a template (a
  declared unit, so the finding is `changed`, and the place is one
  line); the `README.md` shows the overload resolution or the lookup,
  before and after, in two or three lines of reasoning; and the change
  of meaning is real, not a different route to the same function (an
  added overload that forwards to the old one still changes which
  function the call names, and that is what the case shows: say so).
- `06-relocate-and-change` and `07-relocate-undeclared` have `base`
  `01-relocate`. For 06 the constant is one whose unit is named in
  `expect.txt` under its **old** name (`llvm::hashing::detail::…`): the
  finding is reported in pre-image terms.
- A hazard whose site cannot be made silent on this pin is replaced by
  another site of the same hazard; if no site in the selection will do,
  hand back with what you tried. The table of §10.2 is the supervisor's
  to amend.

## The files

- **`edit.txt`** is written to the grammar of §10.1 exactly; no tool
  reads it yet, so check each by a throwaway script of your own that
  applies it under the rules of §10.1 (old text found exactly once, or
  at least once with `all`; bytes; an error otherwise). Keep each
  replacement as small as stays unique: a reviewer reads `edit.txt` as
  the diff.
- **`declared.txt`** is the text of `spec/verify.md` §2.3. Entities are
  named as §6.1 "Names" of that spec gives them; a `created` line for a
  function carries `[function]` and its parameter list.
- **`expect.txt`**: `verified`, or `mismatch` and the finding lines of
  the table, each with ` @ <file relative to src/>:<line>`. The line is
  that of the **post-image** (of the pre-image for `removed`), counted
  after the edit is applied. For 07, the two lines the table gives and
  no claim about the others.
- **`observers`**: one `--only` substring per line naming observers in
  which every entity of `declared.txt` and `expect.txt` is declared (a
  caller in `lib/Support/Path.cpp` needs `Path.cpp`). Absent where the
  first selected observer sees them all.
- **`README.md`**: what the edit is; why it is right, or exactly what
  it changes (the lookup or the overload resolution before and after);
  the files searched; the checks below with their commands and results.
  No absolute path of this host (`spec/harness.md` §3, `local-paths`):
  write `<src>` and `<tree>`.

## The checks

For each case, on a tree of your own under the corpus directory (a copy
of `src/llvm` made of hard links, each edited file written as a new
file, as §10.3 describes; the directory is removed when you are done,
and `src/` is never edited):

1. **Tier T2: the production compiler.** Each affected translation unit
   is compiled with the compiler the corpus's database names
   (`clang++-19` on this pin), with the command of the database, the
   root replaced by the tree, and `-fsyntax-only` in place of the
   output: all 151 of the selection for `01-relocate` and for the header
   edits of 02 to 04 (the headers reach most of them), the edited file
   and the named callers at least for 05, and for 01 also
   `lib/IR/StructuralHash.cpp` and the unit test that names the
   namespace. **Every one is accepted.** A wrong edit that the
   production compiler rejects is not a case; a warning that the edit
   adds is recorded in the `README.md` (a case whose wrong edit earns a
   new warning under the corpus's flags is weaker: prefer a site
   without one).
2. **Kiln.** A copy of the database with the root replaced by the tree,
   then `slip parse --db <that> --store <a store of your own> --only
   /llvm/lib/Support/`: every observer that is `ok` on the pristine
   tree is `ok` on the case's. The counts go in the `README.md`. An
   observer that Kiln fails on the tree and not on the pristine one is
   a report to Kiln: hand back with the two diagnostics.
3. **The pristine tree is untouched**: `git -C <src> status --short` is
   empty before and after.
4. **The change of meaning is shown**, for 02 to 06, by something other
   than reasoning where that is cheap: the two trees' `-ast-dump` of the
   named caller with `clang++-19` (`-Xclang -ast-dump
   -Xclang -ast-dump-filter=<function>`) differ in the callee or the
   argument the `README.md` says they differ in. Quote the two lines.
