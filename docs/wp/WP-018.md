# WP-018 — what the CLI had to work around in `slip_exec` and `slip_model`

- Status: done
- Milestone: M0
- Track: D
- Needs: WP-012
- Size: S

## Scope

Three things `slip_cli` does for itself because the crates below it do
not (`docs/wp/WP-012.md`, Handback):

1. **Scratch entries of killed workers.** A worker killed for a cap, a
   time limit, a crash or a signal leaves `tmp/<pid>.…` in the store, and
   `spec/exec.md` §2 clears it only at the next exclusive open. The pool
   holds the exclusive store and knows which workers it killed: it
   removes their entries when it reaps them, and `cleanup_on_signal` does
   the same. `remove_dead_entries` in `slip_cli/src/commands.rs` goes.
   §2 "Cleaning" and §7 say so.
2. **Names of the model's enumerations.** `slip_model` exposes `name()`
   for `Reason`, `Status` and `End` (the names of `spec/model.md` §7 to
   §9, which its JSON rendering already has); the three tables in
   `commands.rs` go.
3. **The outcome of each observer.** `pool::Summary` gains, per selected
   observer in plan order, the final shard status and the first line of
   its message; `parse` stops reading every shard again.

## Tests

The tests of `crates/slip_cli/tests/cli.rs` pass unchanged. In
`crates/slip_exec/tests/pool.rs`: a worker killed for each reason leaves
no entry under `tmp/` once `run` returns; the summary's per-observer
outcomes against the shards in the store.

## Done when

`cargo xtask ci` passes and `slip_cli` holds none of the three.

## Out of scope

A progress line for `parse`. Any change to what `slip` prints.

## Handback

Branch `wp/018-cli-workarounds`, head `49afd9a`; merged 2026-11-22 (the
merge is the tree the full gate passed on). Landed as briefed:
`Store::remove_entries_of`, the pool removing a worker's `tmp/` entries
when it reaps it, in `abandon` and on the signal path; `Summary.outcomes`
(observer, final status, first line of the message, in plan order);
`name()` on `Reason`, `Status` and `End`. Beyond the brief: a constant
`ALL` on each of the three, so that a caller printing one line per value
needs no list of its own. With the removal calls disabled, five of the
eighteen pool tests fail. What the spec did not say is in
`spec/landed/exec/WP-018.md`, the `slip_model` additions included; the
fold of M0 puts those in `spec/model.md`.

Follow-ups:

- The signal path's own removal (a run that misses the 3 s wait) has no
  test that isolates it, since `abandon` usually gets there first; a
  worker whose stream thread fails to start is dropped without its
  entries being removed; a worker killed and not yet reaped when
  `abandon` removes its entries can in principle write one more: all
  three deferred, one line in `spec/exec.md` "Open questions" (the next
  exclusive open removes whatever is left).
- `spec/landed/exec/WP-012.md` still says the CLI removes the entries of
  dead workers: dropped in the fold of `spec/landed/exec/`.
