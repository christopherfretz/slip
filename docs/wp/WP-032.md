# WP-032 — slip_digest: declarations an instantiation adds outside its class

- Status: todo
- Milestone: M1
- Track: C
- Needs: WP-026, WP-029
- Size: M
- Parallel with: the wave-2 area packages (none of them owns `units.rs`,
  `keys.rs` or `decl.rs`)

## Problem

Instantiating a class template declares its friends. A friend's
semantic context is the namespace, so Kiln puts the instantiated
declaration in the redeclaration chain of a namespace-scope entity, or
makes a new namespace-scope entity of it. The walk classifies units by
semantic context only (`units::unit_class`,
`units::in_implicit_instantiation`), so today a use that instantiates a
class changes declared units, against digest §1 rule 5 and §14 "demand
independence". Found by the independent review of WP-029; three tests
are in the tree, marked `# pending`, `# needs: units`:

- `tests/demand/_/friend-defined-in-class-template`: `template <class
  U> void g(U);` and a class template that defines `g` as a friend.
  Instantiating the class adds a declaration with a body to `g`'s chain
  and sets `TemplateTables` `instantiated_from` on `g`'s first
  declaration (`kiln_sema/src/templ/member.rs:316-329`): `g`'s declared
  unit changes.
- `tests/demand/_/member-like-friend-declared-by-instantiation`: a
  friend whose constraint names the class's parameter ([temp.friend]/9)
  exists only through instantiations, one entity per class
  specialisation; today each is a *declared* unit `g`, and two
  instantiations collide on one key.
- `tests/differ/TemplateTables/member_like_friend`.

The same holds without templates of their own: `void g(int);
template <class T> struct A { friend void g(int) {} };` and
`template <class T> struct A { friend void h(A) {} };`.

## Rule to implement (and to write into the specs)

Call a declaration **instantiated outside its class** when its lexical
context is an implicitly instantiated class specialisation or a member
of one (the test `in_implicit_instantiation` makes, applied to the
lexical context) and its semantic context is not.

1. Such a declaration is no part of a declared unit. Everything a
   declared unit reads over the chain (`Walk::redecls`, `read_decl`,
   the variable-definition helper WP-026 added, merged flags, merged
   default arguments, the attribute chain) leaves it out, and
   `Ast::definition` naming such a declaration counts as "no definition"
   for the declared unit. `TemplateTables` `instantiated_from` (by
   declaration) naming a pattern that lies in an implicit instantiation
   is written absent in a declared unit.
2. An entity all of whose declarations are instantiated outside their
   class is a **derived** unit, in the origin file of the first of
   them. It belongs to the definition class of §11.9 (a friend's
   definition is instantiated on use): expose the predicate WP-026
   added and extend it.
3. Its key: a member-like friend's parent is the class specialisation
   `member_like_friend` names (it is mangled there, digest-kinds §9.5);
   any other friend keeps its namespace as parent. Two class
   specialisations declaring member-like friends must give two keys;
   two specialisations declaring the *same* namespace-scope entity
   (`friend void k(int);` in a class template instantiated twice) give
   one derived unit whose digest does not depend on which instantiation
   came first: read it from a declaration chosen by content, not by
   arena order, or show that the declarations are indistinguishable in
   the stream and say why.
4. What the instantiation adds to an entity that also has written
   declarations (the definition in the first test) is the business of
   the class specialisation's derived units: its friend unit
   (`FriendDecl`, content-keyed, already derived as a member of the
   instantiation) refers to the entity, and the definition itself is a
   resolved unit `definition` of that entity, which the demand package
   writes. This package only makes sure the declared unit does not
   move; say in the handback what the demand package must write and
   from which declaration.

Write the rule into `spec/digest.md` §2.2 (one paragraph and one line
in the list of derived units) and `spec/digest-kinds.md` (§9.5 at
`member_like_friend` and `instantiated_from`, §11.9's definition
class). Keep both to the rule; decisions that are yours go to
`spec/landed/digest/WP-032.md`.

Before writing code, check each of these against Kiln and report what
you find, since the rule rests on them: where an instantiated friend's
lexical and semantic contexts are set (`kiln_sema/src/templ/member.rs`
around 230-345, `friend_target`); whether a friend *class* or friend
class template declared by an instantiation makes a namespace-scope
declaration the same way (`template <class T> struct A { friend struct
F; };`: if so the rule covers it and it gets its tests); whether
anything else an instantiation does appends to a chain outside the
class (an out-of-line member's redeclaration, a local extern in an
instantiated body, a default argument instantiated into a written
declaration: the last is WP-026's `default_argument` rule, only confirm
it). Anything found that the rule does not cover: a `demand` test
marked `# pending` with the reason, and a line in the handback.

## Tests

The three tests above lose their marks and pass (the `differ` one
becomes a `derived-changed` expectation if the friend is now derived:
`docs/wp/WP-024.md` "The pair tests" has the forms). Add, each seen to
fail before the change:

- `demand`: the non-template forms (`g(int)` declared at namespace
  scope and defined as a friend in a class template; `h(A)` declared
  only by the instantiation); a friend declared first by the
  instantiation and then at namespace scope in source (the later
  written declaration is a declared unit: say what its unit reads); a
  friend class, if Kiln declares one; two instantiations in one
  translation unit (`A<int>`, `A<long>`) added on side B;
- `equal`: the two instantiations in either order of use;
- `differ`: two member-like friends from two class specialisations
  have different keys (both sides have both; one side changes one
  friend's body or constraint, and only that friend's unit moves);
- unit tests of the predicate over hand-picked declarations.

Break each of rules 1 to 3 on purpose and see a test fail.
