# WP-141 — a reference redirected into a namespace that has two views

- Status: in-progress
- Milestone: M1
- Track: C
- Needs: WP-140
- Size: M
- Parallel with: the digest's area packages (one digest branch merges at a time)

## Scope

`docs/wp/WP-140.md` gives a namespace that owned code and a dependency
both open a unit under the key of each view, so a move of `legacy` into
an `acme` that a dependency opens verifies. It leaves one thing failing
closed, by the supervisor's ruling (2026-11-23): **a reference to such a
namespace is written with the namespace's own key**, the dependency's
name. So in

```cpp
// dep.h, read-only
namespace acme { struct Dep {}; }
// a.cpp, owned; before                       after
namespace legacy { int g(int); }           // namespace acme { int g(int); }
using namespace legacy;                    // using namespace acme;
namespace L = legacy;                      // namespace L = acme;
template <class T> int f(T t) {
  return legacy::h(t);                     //   return acme::h(t);
}
```

the directive is `removed` and `added`, `L` is `changed`, and `f` is
`changed`, although the edit is the correct one. The other choice (the
referrer's view) verifies these and refuses the untouched
`using namespace acme;` instead. This is the migration the tool exists
for when it is done one repository at a time: the dependency that
migrated first opens the new root namespace, and every redirected
directive, alias and dependent qualifier of the next repository is a
finding.

What is true of the program: the post-image's `acme` is the pre-image's
`acme` and its `legacy` (owned part) together. A reference to it from
owned code names both; a pre-image reference named one of them. Whether
any lookup changed is what the digests of the uses already decide
(every name's referent is written); the reference's own digest is the
structural fact "this declaration names that namespace".

**The operator's facts (2026-11-23), which make this the normal case
and not a corner.** In the migration this tool is first for: most of
the company's code is already in the new root namespace, so the
dependencies of the codebase being migrated open it; and some
dependencies in the old root will never migrate. So both roots are
shared between owned code and read-only code: the old root before the
edit (an owned part and a dependency part) and after it (the dependency
part only), the new root after it (an owned part and a dependency
part), and possibly before it too. The design phase of this package
therefore starts beside WP-140's build, from its proposal; the build
waits for WP-140 on `main`.

The case those facts make central, to be in item 1's table under every
option, in an observer that includes both dependencies:

```cpp
// old_dep.h, read-only, never migrates
namespace legacy { struct Old {}; int h(Old); }
// new_dep.h, read-only
namespace acme { struct Dep {}; }
// a.cpp, owned; before                       after
namespace legacy { int g(int); }           // namespace acme { int g(int); }
using namespace legacy;                    // using namespace acme;
                                           // using namespace legacy;
int u() { return g(1) + h(Old{}); }        // unchanged
```

The pre-image directive named a namespace with two parts; the correct
edit splits it in two directives, one per part. A correct tool
verifies this; refuses the post-image with only `using namespace acme;`
(the lookup of `h` and `Old` fails or, worse, finds something else) and
with only `using namespace legacy;` likewise for `g`; and says what it
answers when the second directive is kept although no lookup in any
observer needs it (a directive added that the rule does not explain:
`added`, or part of what the rule explains?) and when it is dropped
because nothing uses the dependency's part. The same three-way split
for an alias (`namespace L = legacy;` used as `L::g` and `L::h`: there
is no post-image alias that names both, so the edit must respell the
uses; say what verifies) and for a qualifier in a template
(`legacy::h(t)` stays, `legacy::g(t)` becomes `acme::g(t)`, and a
dependent `legacy::k(t)` whose candidates are in both parts has no
correct respelling: say that it is refused and how the user learns
why).

1. **The design question; propose and stop for the supervisor before
   building.** WP-140's landed file lists every place a namespace is
   written as a reference, the unit that holds each, and what a run
   reports today. For each, say what a correct tool answers for the
   redirected reference, the untouched one, and one retargeted to a
   namespace the rule does not explain (must differ), under each of:
   - **Both keys.** A reference to a two-view namespace is written as
     its view keys together; a content-keyed declaration (a
     using-directive) is then a unit under each. Honest (the reference
     does name both), and both the redirected and the untouched one
     differ from their pre-image: say what the user declares, and
     whether the tool that made the edit can emit that declaration.
   - **Either key, accepted by the comparison.** The post unit carries
     the digests of both readings and the verifier accepts the
     pre-image's under either. Say what it costs when one unit holds
     several such references (a function body with n redirected
     qualifiers: 2^n readings, or one reading per choice applied to
     all), what a mixed body (one qualifier redirected, one untouched)
     gives, and what wrong equal it opens: a reference retargeted from
     the dependency's part to the owned part or back, by an edit that
     compensates.
   - **A declaration.** The declared changes gain a line that says
     owned references to `legacy` now read `acme` (it follows from the

     told apart, or that it cannot be.
   - **The reference left out of the digest** where the uses decide
     (the qualifier of a resolved name), kept where nothing else does
     (an alias, a directive, a dependent name).
   Recommend one, with the table of cases × answers as WP-140's

### Addendum (after the design attack)

WP-141 ruling addendum (supervisor, 2026-11-23, after the independent attack on the design): five changes to what you build. The reviewer's full report is `.build/review-141-design/findings.md` of the workspace (read it; F-numbers below are its). Copy this addendum verbatim into `docs/wp/WP-141.md` under the Ruling as "Addendum (after the design attack)" in your next commit. Where it contradicts the ruling or the proposal, it wins.

A1 (F1; reverses my answer to Q4). **R1 takes a found declaration by the part of the named namespace that holds it**, not "as the entity it stands for":
 - a found declaration that is a member of the named namespace (or of its inline namespace set): the view of that member as WP-140 gives it (an entity by its ownership);
 - a found using-shadow that is a member of the named namespace: the ownership of the using-declaration that made the shadow (the file it is written in), NOT of the entity it stands for;
 - a declaration reached through using-directives written in the named namespace ([namespace.qual]): the ownership of the directive(s) in the named namespace through which it is reached; if they are of both ownerships, both keys;
 - a route you cannot determine: every view key (fails closed), with a counter `digest.ref.namespace_route_unknown`.
 The found SET is still written by entity as today (shadows stripped): that is what pins the functions. One key → `Ref::unit`; several → `Ref::views`.
 Rows that change: Q5 and Q8 of §6.4 are now `=` when the owned re-export `namespace acme { using legacy::k; }` is declared `created` (the same functions are found; the lookup did not change). New rows, all in an observer where a dependency opens `acme`: an owned `namespace legacy { using std::string; using std::forward; }` moved to `acme` with `using legacy::string;` → `using acme::string;` (`=`) and `legacy::forward<T>(t)` → `acme::forward<T>(t)` in a template (`=`); the same with owned overloads beside the re-export (`=`); the same through an owned `namespace legacy { using namespace std; }` (`=`); a name reached through an owned directive AND a read-only directive both written in `acme` (`Ref::views`, a finding: pin it and say so in the handback as a known limit); a retarget to the dependency's re-export (`acme::h(t)` where the shadow is written in the read-only part: differs). Mutation 1 becomes: R1 takes the entity's ownership for a shadow (the F1 rows turn to findings); add: R1 takes the owned view whenever any route is owned.
 If Kiln's found set does not keep the shadow or the route (your Q10 check), STOP and tell me what it keeps.

A2 (F2). **The qualifier of a qualified concept-id is in the inventory**: Kiln puts it in `expr_nns` for every qualified `ConceptSpecializationExpr`, resolved or not, and `templ.rs` `expr_maps` writes it by key in streams. First pin today's answer (`legacy::Small<T>` → `acme::Small<T>` in a `requires` clause and in a `static_assert`, with a dependency that opens `acme`), then treat the site by R1 with the concept as the one found declaration. Find out, by test, whether a type-constraint (`template <legacy::C T>`, `legacy::C auto`) reaches the same path, and search for any other caller that writes a namespace level for a RESOLVED name; report each. A dependent destructor name `p->N::~Q()` carries `expr_nns` with no found set: pin it as a finding, do not fix.

A3 (F4). "The using-directives of the same enclosing namespace" means the same namespace ENTITY (and the same file), never the same mapped key: a directive in `namespace acme {}` is not made whole by one in an owned `namespace legacy {}`. And stated in `spec/verify.md` §8: a using-directive written inside the moved namespace moves with it like any owned member; that it no longer nominates into the part the rule leaves is the rule's consequence, not a finding (post B of F4 verifies). Pin F4's edits A and C as they are today (`stale`), no change.

A4 (F5). **`E(k)` defined**: a namespace holds something under `k` if, in a view of it whose key is `k`, it has a read-only opening, or an entity that is not a namespace keyed under it (a using-directive, an alias, a using-declaration and a `static_assert` in an owned opening count), or a nested namespace that itself holds something in that view. An owned opening that is empty, or holds only empty nested namespaces, holds nothing. "In an owned file" is by the path of the file the declaration is written in, however it was included; if the ownership machinery on the branch says otherwise for an owned header entered through a read-only includer, do not change it: report what it does, with a fixture of one owned header entered both ways in one observer.

A5 (F7; replaces R3). An obligation on a spelled piece that names a namespace holds if its key is: at a site R1 covers, the single key R1 writes there (never with `Ref::views`); at a using-directive's or alias's target, a reading that is whole; at a qualifier of a resolved name (nothing is written; the next piece decides), any view key. Mutation 13 becomes: any view key accepted at an R1 site (the reviewer's F7 example passes).

Not yours (WP-143's): F3 (the second guard), F6 (an alternate only if every declaration that writes the unit offers it), F8. The stop conditions of your brief stand, with the rows as changed here. No answer needed unless something above cannot be built as stated.
