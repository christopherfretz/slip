# WP-130 — a using-shadow hidden by an implicit member: its record must not depend on a use elsewhere

- Status: todo
- Milestone: M1
- Track: C
- Needs: WP-119
- Size: S
- Parallel with: WP-106, WP-122, WP-125, WP-126 (one digest branch merges at a time)

## Scope

`docs/wp/WP-119.md` made a using-shadow that a declared member hides no
unit, and kept one that an **implicit** member hides (an assignment
operator or a constructor Kiln declares on use), because leaving it out
would make a class's digest depend on a use elsewhere. Its handback
says the other half is still open and older than the package: the kept
shadow's record holds Kiln's hidden mark, and Kiln sets that mark when
the implicit member is declared:

```cpp
struct B { B& operator=(const B&); };
struct D : B { using B::operator=; };
// with and without:  void u() { D d; d = d; }
```

So the shadow's unit, and what lists it, may digest differently in an
observer that assigns a `D` and in one that does not; and an edit that
adds or removes such a use elsewhere in the translation unit changes a
unit of the class. `spec/digest.md` §1 rule 5 forbids it. Kiln has the
request (KB6 amendment 1, 11.2: decide the mark when the class is
completed; its WP-3146).

1. **The facts**: a pair for the source above each way (the use added
   on side B), for an inheriting constructor
   (`using B::B;` with and without `D d(1);` and with a copy of a `D`),
   and for a move assignment. Which units differ today, and by which
   byte (the hidden mark, the list of the class, the shadow's
   existence, the implicit member's own unit if it is one).
2. **The rule**: what the digest writes for such a shadow must be a
   function of the class's definition. Either the mark is not written
   for a shadow whose hiders are all implicit (then say what else in
   the stream tells a hidden shadow from a visible one, and show a pair
   that a real change from hidden to visible still differs:
   `differ/_/wp119-hidden-shadow-made-visible-hider-removed` and its
   kin must hold), or the mark is computed from the class
   ([namespace.udecl]/14 and [over.match.funcs]: a using-declaration
   that names a base's copy or move assignment operator or constructor
   whose signature the derived class's implicit one has is hidden,
   whether or not the implicit one was declared). The second is the
   truth; say whether the `Ast` gives enough to compute it (the
   implicit member's signature before it is declared), and take the
   first, with its cost stated, if it does not.
3. **The same question for the implicit member itself**: is an
   implicit special member that Kiln declares on use a unit, or listed
   by its class? If so the class's units depend on uses in the same
   way: a pair, and the rule (`spec/digest.md` §2.1 says which
   entities are units: read it first; this may be settled already,
   then name the test that shows it).
