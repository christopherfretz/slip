## Scope

`spec/edits.md` §7 in the crate `slip_apply`, which links `slip_model`
and nothing else:

1. §7.1: `splice`, `plan` and `build` (an accepted edit set and the
   pre-image to an `Overlay`, its blobs and its spelling obligations),
   with nested edits and copy pieces as §7.1 "What the edits mean" says.
2. §7.2: `patch` (the unified diff).
3. §7.3: `write` and `recover`, with the journal's record.

Files: everything under `crates/slip_apply/`: `splice.rs`, `compose.rs`
(the text of a range, expansions, obligations), `build.rs`, `patch.rs`,
`write.rs`, `journal.rs`, `lib.rs`, and the four test files.

This is the only code of Slip that changes a user's files. It is not in
the trusted base (verification judged the bytes before `write` runs, and
`write` copies blobs whose digests the overlay names), but a defect here
loses work: it gets the independent review the trusted base gets. The
obligations are the one thing verification takes from it: an obligation
at a wrong range is checked at that range, which fails or is unseen; it
cannot make a wrong name pass (`spec/verify.md` §10.7).

Starts when WP-061 is on `main`. Needs nothing of M1 or Kiln. If the
package grows past two thousand lines, hand back parts 1 and 2 first and
say so; part 3 touches none of their files.

## Interface

`spec/edits.md` §7.4, exactly (`Files`, `Built`, `ApplyError`, `splice`,
`plan`, `build`, `build_into`, `patch`; `Stat`, `Tree`, `Blobs`,
`JournalStore`, `Refused`, `WriteError`, `Recovered`, `write`,
`recover`). Fixed here:

```rust
/// `build` with a sink: called once per overlay file, in path order, with
/// the post-image bytes.
pub fn build_into(set: &EditSet, set_id: Digest, files: &dyn Files,
                  sink: &mut dyn FnMut(&OverlayFile, &[u8]) -> std::io::Result<()>)
    -> Result<Overlay, ApplyError>;

// slip_apply::journal
pub struct Journal { pub overlay: Digest, pub files: Vec<JournalEntry> }
pub struct JournalEntry { pub path: Vec<u8>, pub staged: Vec<u8>, pub pre: Content, pub post: Content }
impl Journal { pub fn to_bytes(&self) -> Vec<u8>; pub fn from_bytes(bytes: &[u8]) -> Result<Journal, String>; }
/// The staged name of §7.3 for a real path and an overlay id.
```

- `splice`: edits are `(lo, hi, text)` ascending and disjoint (`Invalid`
  otherwise, also for a range past the end); an empty edit list returns
  the input.
- `plan`: §7.1 steps 2 and 3 without any file's bytes. It checks the set
  (`NotAccepted` for a refused one; `Invalid` for a cycle of "draws on"
  and for an edit that is not effective), orders the edits so that each
  comes after those it draws on, and computes every expansion's length
  from the files' sizes and the pieces. `TooLarge` when a post-image
  would pass 2^31 bytes, decided from lengths alone: a chain of forty
  doubling copies is refused without allocating. No recursion on the
  call stack, here or in `build`: a chain of copies a thousand deep is a
  test.
- `build`: `plan` first. `StaleFile` for a file, edited or copied from,
  that cannot be read or whose size or digest is not the `FileRef`'s.
  Files are read in path order. An edit set without copies holds one
  file's two images at a time; with copies, also the pre-images of the
  files that file's edits copy from. A file whose post-image equals its
  pre-image is an overlay entry with `post == pre` (§7.1): it is not an
  error.
- **Obligations.** One per landing of a spelled piece's text in a
  post-image: at its edit's own place when the edit is outermost, and in
  every copy that carries the edit. Its range is in the post-image
  file's offsets. The list is sorted by `(file, lo, hi, key)`; two
  landings cannot be equal in that key, and `build` asserts it.
- `patch`: the property of §7.2. A file with a `\0` or without valid
  UTF-8 is written the same way (bytes copied); the test says what
  `patch(1)` does with it. An entry with `post == pre` has no hunk and
  no header.
- `write`: steps 1 to 5 of §7.3 in order, over the entries whose `post`
  differs from `pre`. On a failure before the journal is published,
  nothing was created. On a failure after it that `write` could undo
  (staged files and journal removed), `journal_left` is false. `write`
  never removes or renames a file whose path the journal does not hold.
- `recover`: §7.3's last paragraph. It is idempotent, and safe to
  interrupt: a second `recover` after an interrupted one ends in the same
  tree.

`slip_apply::fs::DiskTree` is `Tree` over the real file system and is
part of the package: `stat` uses `symlink_metadata` on the real path,
`create` with `exclusive` uses `create_new`, every write is followed by
`sync_all`, and `sync_dir` opens the directory and syncs it. `Blobs` and
`JournalStore` over the store are `slip_cli`'s (`docs/wp/WP-075.md`,
on the store functions of `docs/wp/WP-064.md`); this crate's disk tests
use a directory.

## Tests

- `crates/slip_apply/tests/splice.rs`, `compose.rs`, `patch.rs`:
  `spec/edits.md` "Tests". `compose.rs` also holds a model: the text of
  a range computed by the definition's own recursion on small generated
  sets (fixed seed), compared with `build`. `patch.rs` also checks the
  diff against a second tool where one exists (`git apply
  --unsafe-paths`), skipped with a counted message where neither exists.
- `crates/slip_apply/tests/write.rs`: a `Tree` in memory that fails, or
  "loses power" (returns an error and performs nothing further), at the
  n-th operation, for every n until `write` completes, over a three-file
  overlay. After each: every file is wholly pre or wholly post; if a
  journal is left, `recover` returns every file to the pre-image and
  removes every staged file; if none is left, the tree is the pre-image
  or (only after the last rename) the post-image. The same sweep over
  `recover` itself. Refusals: not owned, a hard link, a directory that is
  not writable, a staged name that exists, a file changed between the two
  checks, a file changed by someone else after the commit and before
  `recover` (reported and left). An entry with `post == pre` is never
  opened for writing.
- The disk implementations: `write` and `recover` over a temporary
  directory under the target directory; permission bits kept; a symbolic
  link to an overlay file still points at the replaced file.

### Fix round 3 (re-review of f10431c)

1. **`restore` keeps a save made after its read.** For a file holding
   the post-image, the `stat` taken before the read is compared, just
   before the rename, with a fresh one (`Stat::same_file`, the commit's
   re-check); a difference reports the file, keeps it and the journal,
   and leaves the staged pre-image beside it; it is not listed as
   restored. The rollback is the same `restore`, so `write` returns `Io`
   with `journal_left: true`. §7.3 step 5's sentence now says "changed
   before the rollback's re-check of it", and the recovery paragraph
   describes the re-check and its window. Tests:
   `s7_3_recover_keeps_a_save_made_before_its_rename` (the reviewer's
   reproducer, and each identity field alone, so a byte-only compare
   fails it), `s7_3_rollback_keeps_a_save_made_before_its_rename` (a
   commit refusal, then the save just before the rollback's rename; the
   model gained a second hook for it).
2. **`DiskTree::create` checks the name before the reopen.** After the
   write and sync it `lstat`s the name (a regular file of the write
   handle's device and inode, else it fails before opening anything
   through the name), then reopens and compares as before. What is left
   is in the landed file §5.5: a swap between the `lstat` and the open
   makes the open follow it (a FIFO blocks, a device's open has its side
   effects); nothing is written or chmodded, and `recover` restores. The
   private seam (`fs::create` with a closure called after the write and
   after the `lstat`; a no-op in `DiskTree::create`) is used by the unit
   tests `fs::tests::create_compares_the_reopened_handle` (swap after
   the `lstat`: kills mutation 31 without a race) and
   `fs::tests::create_lstats_the_name_before_the_reopen` (swap before
   it, for a link to a socket, the FIFO's stand-in that fails to open
   instead of blocking, and to a regular victim).
3. **`recover` checks before it removes.** Per file, `stat F` (which
   includes the real-path check of its directory) comes first; a
   reported path has nothing removed under it, its staged name
   included; content neither image also leaves the staged name alone.
   Test: `s7_3_recover_removes_nothing_under_a_reported_path`.
4. **`recover`'s ownership.** The journal holds the overlay id, which
   names the overlay's content and not the run (two runs with different
   ownerships can apply one overlay), so checking it would not bind the
   ownership; the journal format and `recover`'s signature are
   unchanged. Written under "Open" in the landed file (§7) with what

### Supervisor's handback (merge, 2026-11-23)

Merged after three fix rounds and two looks by the independent
reviewer. Decided on the way:

- **No dependency for the rename window** (the operator, 2026-11-23:
  the tool is interactive): no `rustix`, no `cap-std`. What std alone
  cannot close is a documented limit (landed §5.5): a name swapped
  between `create`'s `lstat` and its reopen is opened for reading (a
  FIFO blocks; nothing is written or chmodded; `recover` restores).
- **The re-check before a rename** (`Stat::same_file`, the
  implementer's rule, confirmed): device, size, modification time and
  change time always; the inode too unless both times have a nanosecond
  part. This host's volume gives a file a new inode number after it or
  its directory is renamed, and comparing it made `recover` report
  untouched files. What the rule gives up, stated exactly: a file
  replaced by a rename with another of the same size goes unseen only
  if the replacement's change time equals the old file's, and a file
  system's times advance with the kernel's tick, not with the
  nanosecond: so the window is a same-size replacement within one tick
  (milliseconds) of the file's previous change. An in-place write of
  the same size within one tick is unseen with or without the inode;
  it is the window every stat-based check has.
- `recover`'s ownership is the caller's: the journal names the overlay,
  not the run. `docs/wp/WP-075.md` must pass the ownership of the run
  that wrote the journal (landed §7, "Open").

For the command packages: `recover(ownership, tree, blobs, journal)`;
`JournalStore::publish` fails when a journal exists;
`Refused::{ReadOnly, OwnerChanged, JournalNotOwned}`; `Tree::create` is
always exclusive; a rollback that had to keep a file returns `Io` with
`journal_left: true`.
