## Scope

`spec/edits.md` §7 in the crate `slip_apply`, which links `slip_model`
and nothing else:

1. §7.1: `splice` and `build` (an accepted edit set and the pre-image to
   an `Overlay` and its blobs).
2. §7.2: `patch` (the unified diff).
3. §7.3: `write` and `recover`, with the journal's record.

Files: everything under `crates/slip_apply/`: `splice.rs`, `build.rs`,
`patch.rs`, `write.rs`, `journal.rs`, `lib.rs`, and the three test files.

This is the only code of Slip that changes a user's files. It is not in
the trusted base (verification judged the bytes before `write` runs, and
`write` copies blobs whose digests the overlay names), but a defect here
loses work: it gets the independent review the trusted base gets.

Starts when WP-061 is on `main`. Needs nothing of M1 or Kiln. If the
package grows past two thousand lines, hand back parts 1 and 2 first and
say so; part 3 touches none of their files.

## Interface

`spec/edits.md` §7.4, exactly (`Files`, `Built`, `ApplyError`, `splice`,
`build`, `build_into`, `patch`; `Stat`, `Tree`, `Blobs`, `JournalStore`,
`Refused`, `WriteError`, `Recovered`, `write`, `recover`). Fixed here:

```rust
/// `build` with a sink: called once per overlay file, in path order, with
/// the post-image bytes; at most one file's two images are held.
pub fn build_into(set: &EditSet, set_id: Digest, files: &dyn Files,
                  sink: &mut dyn FnMut(&OverlayFile, &[u8]) -> std::io::Result<()>)
    -> Result<Overlay, ApplyError>;

// slip_apply::journal
pub struct Journal { pub overlay: Digest, pub files: Vec<JournalEntry> }
pub struct JournalEntry { pub path: Vec<u8>, pub staged: Vec<u8>, pub pre: Content, pub post: Content }
impl Journal { pub fn to_bytes(&self) -> Vec<u8>; pub fn from_bytes(bytes: &[u8]) -> Result<Journal, String>; }
/// The staged name of §7.3 for a real path and an overlay id.
pub fn staged_name(path: &[u8], overlay: Digest) -> Vec<u8>;
```

- `splice`: edits are `(start, end, text)` ascending and disjoint
  (`Invalid` otherwise, also for a range past the end); an empty edit
  list returns the input.
- `build`: `NotAccepted` for a refused set; `StaleFile` for a file that
  cannot be read or whose size or digest is not the `FileRef`'s;
  `Unchanged` for a file whose post-image equals its pre-image. Files are
  read in path order and each once.
- `patch`: the property of §7.2. A file with a `\0` or without valid
  UTF-8 is written the same way (bytes copied); the test says what
  `patch(1)` does with it.
- `write`: steps 1 to 5 of §7.3 in order. On a failure before the journal
  is published, nothing was created. On a failure after it that `write`
  could undo (staged files and journal removed), `journal_left` is false.
  `write` never removes or renames a file whose path the journal does not
  hold.
- `recover`: §7.3's last paragraph. It is idempotent, and safe to
  interrupt: a second `recover` after an interrupted one ends in the same
  tree.

`slip_apply::fs::DiskTree` is `Tree` over the real file system and is
part of the package: `stat` uses `symlink_metadata` on the real path,
`create` with `exclusive` uses `create_new`, every write is followed by
`sync_all`, and `sync_dir` opens the directory and syncs it. `Blobs` and
`JournalStore` over the store are `slip_cli`'s (`docs/wp/WP-075.md`,
on the store functions of `docs/wp/WP-064.md`); this crate's disk tests
use a directory.

## Tests

- `crates/slip_apply/tests/splice.rs`, `patch.rs`: `spec/edits.md`
  "Tests". `patch.rs` also checks the diff against a second tool where
  one exists (`git apply --unsafe-paths`), skipped with a counted message
  where neither exists.
- `crates/slip_apply/tests/write.rs`: a `Tree` in memory that fails, or
  "loses power" (returns an error and performs nothing further), at the
  n-th operation, for every n until `write` completes, over a three-file
  overlay. After each: every file is wholly pre or wholly post; if a
  journal is left, `recover` returns every file to the pre-image and
  removes every staged file; if none is left, the tree is the pre-image
  or (only after the last rename) the post-image. The same sweep over
  `recover` itself. Refusals: not owned, a hard link, a directory that is
  not writable, a staged name that exists, a file changed between the two
  checks, a file changed by someone else after the commit and before
  `recover` (reported and left).
- The disk implementations: `write` and `recover` over a temporary
  directory under the target directory; permission bits kept; a symbolic
  link to an overlay file still points at the replaced file.
