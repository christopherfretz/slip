# WP-088 — slip_script: the effects: code values, spelling, edits, reports, declarations

- Status: review
- Milestone: M3
- Track: E
- Needs: WP-081
- Size: L
- Parallel with: WP-080, WP-082..087, WP-089

## Scope

Needs nothing from Kiln: everything here is tested against the fake
subject of WP-081.

`spec/api.md` §7 (all), §4 (the messages of failures), and operations 64
to 84 of §3.2. This is the part of the host a transform can ask to change
the world, so it is the part that must be dull: it records requests,
checks each against the rules of §7, and hands over a canonical output.
It applies nothing and decides nothing.

Decisions to implement, not to revisit:

1. **Code values** are host objects: a vector of pieces behind a handle.
   Adjacent literals are joined when made. `cat` copies piece lists (the
   limits of §7.7 bound it).
2. **A spelled piece is turned into text when the edit is recorded**
   (§7.2), because the sibling rule depends on the place. The record
   keeps the entity's key and the text.
3. **The sibling rule narrows the edit**: `replace(extent_of(R),
   spell(E))` under the four conditions records an edit of
   `name_range_of(R)`.
4. **Nothing is checked between requests** (§7.3 rule 3). Overlap is
   reduce's.
5. **A failed request records nothing** (§4): validate everything, then
   record.
6. `finish` makes the output canonical: edits sorted and identical ones
   joined (their notes unioned); groups rewritten to the joined indices,
   groups sharing a member merged, single-member groups dropped; reports
   and declarations sorted and deduplicated.
7. **Every declared change has a place** (§7.5 rules 1, 2 and 7): the
   extent of `x`. `expect_changed` is refused with `unsupported` for an
   entity, a declaration, and a reference or expression whose extent is
   null.
8. **`spell` needs a key** (§7.1 rule 4): `Subject::entity_key` is asked
   when the piece is made; none is `unsupported`.


**From WP-081's review.** The statuses a subject may choose for
`entity_key`, `qualified`, `unit_keys` and `rename_rule` are listed on
the trait (`crates/slip_script/src/subject.rs`) and not yet enforced,
because the effects are their first callers: this package turns any
other status into a host failure naming the method and the status, as
`spec/landed/api/WP-081.md` decision 17 does for the queries, with a
test per method (a subject that lies). An effect's `Record` has no
counter field: the host is the only writer of the counters it owns
(`spec/api.md` §7.6 rule 6).

## Tests

`crates/slip_script/tests/effects.rs`, against `FakeSubject`:

1. §7.1: each piece kind; `cat` of each accepted argument sort; rule 6
   (adjacent literals, empty literal, interchangeable values). Rule 3
   (a) and (b): two different edits of one range, and
   `replace(x, copy(r))` with `x` properly inside `r`, are each recorded
   as requested, with no throw: the host does not judge them, reduce
   rejects them.
2. §7.2: the four conditions of the sibling rule, each failed alone,
   give the fully qualified text; all four give the narrowed edit; two
   references with one extent; unnamed and inline namespaces in the
   qualified text; each `unsupported` of §7.1 rule 4.
3. §7.3: each throw; a deletion; overlapping requests are both recorded;
   the same request twice is one edit with both notes; a group of one is
   dropped; two groups sharing an edit are one.
4. §7.4: each overload; an unknown severity; a place that is not the
   value's own.
5. §7.5: `expect_changed` at a reference and at an expression, each
   recorded with its extent as the place; derived keys, each with the
   same place; `unsupported` for an entity, for a declaration, for a
   reference with a null extent, for a content-keyed unit; a null `info`
   is `invalid_handle`; the same declaration twice is one;
   `expect_renamed` twice with one name and with two; an invalid
   identifier. `spell` of an entity with no key is `unsupported`.
6. §7.6: two hosts fed the same requests in different orders, with
   different handle numbers, finish with equal outputs (a property test
   over random request sequences).
7. §7.7: each limit, one below and at.
8. §4: after any failed operation, `finish` equals the output without it.

## Handback

Code: `crates/slip_script/src/effects.rs` (new: operations 64 to 84),
`host.rs` (dispatch, `Answer::Effect`, the new limits), `output.rs`
(`RunOutput::render`), `subject.rs` (documentation only), `fake.rs` (the
rename rule's direction). Decisions: `spec/landed/api/WP-088.md`. Tests:
`crates/slip_script/tests/effects.rs` (27 tests); `tests/wire.rs` lost
`s3_2_effects_are_unsupported_for_now`, which no longer holds.

**Operations implemented.** All of 64 to 84: `code_text`, `code_spell`,
`code_copy`, `code_cat`, `replace`, `new_group`, `report`,
`expect_changed`, `expect_renamed`. Each is validated in the immutable
stage of `Host::call` and recorded in `deliver` by a store that cannot
fail (landed decision 1); no departure from the staging was needed.

**Changes to `spec/api.md`.**

1. §3.2: `report`'s where-kind 1 takes `b = 0`; any other where-kind, or a
   nonzero integer the where-kind does not take, is `invalid_argument`.
   The null handle is the empty code and no group; an operation whose
   result is the empty code returns it. (The table left these values
   unspecified; the header already sends 0 for the defaults.)
2. §7.2 rule 1: several references with one extent must also have one
   name range. (Otherwise there is no single range to narrow to.)
3. §7.3 rule 2: `unsupported` when the tier of `r` is not known (it lies
   in no name range or extent). A transform can forge such a range in a
   file it was given (`WP-081.md` decision 3), and §7.6 requires a tier
   of 0 or 1 for every edit.
4. §7.3 rule 5: an empty note is no note.
5. §7.4 rule 3: a value whose place, own or nearest, the host cannot
   name gives a report with no place.
6. §7.7: the row "bytes in literal pieces, in total" became "bytes of text
   in pieces, in total: literal bytes and the text of spelled pieces"
   (2^28); new rows "pieces, in total" (2^22), "declared changes,
   distinct" (2^20), "bytes of text arguments held, in total: notes,
   messages, reasons and new identifiers" (2^26); the totals count what is
   held, once per code value, edit or declared change, so `cat` and
   `replace` count again; holding exactly a limit does not exceed it. The
   table as written let a run hold 2^22 code values of 2^16 pieces each,
   2^20 edits of 2^16 pieces or with 4 KiB notes, and any number of
   declared changes: bounded only in name (landed decision 7).

**Limits and where each is enforced** (all in `effects.rs`, in the
validation stage, before anything is recorded; `Limits` in `host.rs`):

| Limit | Enforced in |
|---|---|
| code values 2^22 | `new_code` (text, spell, copy, cat) |
| bytes of text in pieces 2^28 | `pieces_fit` from `new_code` and `replace`; early in `cat` and `spell` |
| pieces in total 2^22 | `pieces_fit` from `new_code` and `replace` |
| pieces in one code value 2^16 | `new_code`; early in `cat` (bounds the loop) |
| edits requested 2^20 | `replace` |
| groups 2^20 | `effect` (`new_group`) |
| reports 2^16 | `report` |
| declared changes 2^20 | `expect_changed` (distinct entries) |
| bytes in one note, reason or message 2^12 | `text_arg` from `replace`, `report`, `expect_changed` |
| bytes of text arguments held 2^26 | `text_fits` from `replace`, `report`, `expect_changed`, `expect_renamed` |
| bytes in one identifier argument 2^12 | `expect_renamed` (and `lookup`, WP-081) |
| integers or bytes in one answer | not reachable: every effect is convention V |

**Done differently or not done.**

- Test 2's "each of the four conditions failed alone": condition 1 ("E has
  an identifier") cannot fail alone, because `spell` refuses an entity
  with no identifier (§7.1 rule 4); the test of §7.1 rule 4 shows the
  refusal instead.
- Test 7's "one below and at" is tested as "at" (accepted) and "one past"
  (refused), for every limit, with small `Limits`; the defaults are
  checked against the rows of §7.7 by a test that reads the specification.
- The `entity_key` liar test can show only the allowed `None`
  (`unsupported`): the method has no other status and the host cannot
  check a key.
- Every new check was seen to fail without its code by mutation (each of
  18 checks removed in turn makes a test fail), except the early per-code
  piece check in `cat`, which `new_code` repeats; that check only bounds
  the work of the loop.

**Trait and interface changes.** No method of `Subject` was added or
changed in signature. Documentation was added to `tier`, `qualified`,
`references_at`, `unit_keys`, `rename_rule` and `place` stating what the
host now checks of their answers. `Limits` gained the public fields
`pieces`, `changed` and `text_total` (a struct literal without
`..Limits::default()` must name them; none exists in the workspace).
`RunOutput::render` was added as the package specifies. `FakeSubject::
rename_rule` now builds the rule that undoes the rename (it built the
rename itself).

**Wrong or doubtful in the specification.**

- §7.7, as above: the old limits did not bound what the host holds.
- §7.2 rule 1, condition 1 is implied by §7.1 rule 4.
- §7.5 rule 3 makes the output depend on the order of requests: of
  `expect_renamed(e, "a")` and `expect_renamed(e, "b")`, whichever comes
  first is recorded and the other refused. The transform sees the refusal,
  so §7.6 rule 1 still holds for transforms that do not catch it, but the
  rule "nothing in the output depends on the order of the requests" is not
  true of a transform that catches it.
- `WP-081.md` decision 3 accepts any range inside a given file, which is
  how a transform can reach the "tier not known" refusal; a stricter
  reading of §5.2 (a range not given out is forged) would refuse it as
  `invalid_handle` everywhere instead.
- §7.4 rule 3 for an entity ("the name of its first written declaration")
  says nothing of an entity whose first declaration has no name range but
  a later one does; the host takes what `Subject::place` gives.
