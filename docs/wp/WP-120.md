# WP-120 — rename: virtual families and using-declarations in templates; the unhide idiom

- Status: in-progress
- Milestone: M2
- Track: C
- Needs: WP-072, WP-073
- Size: M
- Parallel with: WP-119 (which owns the digest side and the `unsupported` flag of followers)

## Scope

The review of `docs/wp/WP-072.md` found no silent wrong result and three
places where the rename refuses ordinary code, two of them because
neither WP-072 nor WP-073 owns the case. This package lifts them. Every
item is a refusal today; none may become a silent miss: where the answer
cannot be known the refusal stays, with its reason.

1. **A candidate or follower in a template's pattern has an owner.**
   WP-072's decision 3 flags a virtual candidate, a using-declaration
   follower and an unnamed-tag follower `unsupported` when one of its
   enclosing entities is a class template, a partial specialisation or a
   function template (`families::in_pattern`), "until WP-073"; WP-073's
   `spec_members` runs only for a **seed** that is a member of a class
   template. So these refuse after both merge, and template interface
   bases are common in the motivating code:

   ```cpp
   template <class T> struct B { virtual void f(); };
   struct D : B<int> { void f() override; };              // (a) overrider of an instantiated member
   template <class T> struct E : Base { void f() override; };   // (b) overrider in a pattern, non-dependent base
   template <class T> struct F : Base { using Base::f; };       // (c) using-declaration in a pattern
   ```

   For each: say what Kiln records (the `overrides` list of the pattern's
   member and of each instantiated member; the shadows of a
   using-declaration in a pattern and in its instantiations), take every
   function to its origin (`written::origin`), and link the family
   through the pattern: an instantiated member's link is its pattern
   member's link. The members of instantiated specialisations are
   followers by WP-073's rule and carry WP-073's flag until WP-119.
   A pattern with a **dependent** base (`template <class T> struct G : T
   { void f() override; };`) has no recorded link until it is
   instantiated: instantiated in the unit, the instantiation's link
   counts for the pattern; instantiated nowhere, the name is kept and the
   subject is not claimed (WP-072's review, note 3: state it in
   `spec/edits.md` §9.5 as what the rename does not see, beside the
   residue scan's row for it).
2. **A virtual seed in a pattern.** `spec/edits.md` §9.5 as WP-073 wrote
   it says a seed that is a member of a class template is not flagged;
   `families::candidate` flags a virtual one. Make the code and §9.5 say
   the same thing once item 1 holds (not flagged when its family is
   linked through the pattern).
3. **The unhide idiom.**

   ```cpp
   struct B { virtual void f(); void f(int); };
   struct D : B { using B::f; void f() override; };
   ```

   Kiln makes a shadow for `B::f()` though `D::f()` hides it, so the
   using-declaration's `of` is `{B::f(), B::f(int)}`; a rename of the
   virtual family alone is `mixed_follower` and refuses. Decide what is
   right and build it: the using-declaration names the **name** `f`, so
   after a rename of `f()` alone to `g` it must name both `f` (for
   `f(int)`) and `g`; keeping it unchanged is right exactly when no
   selected entity is reached through it (here `B::f()` is hidden by
   `D::f()`, which is itself renamed). State the rule in §9.2 in terms
   the reducer can decide from the claims of every observer (a shadow
   that is hidden in one class is not hidden in a class derived from
   another base), and keep `mixed_follower` wherever the rule cannot
   show the kept declaration is right. The second form the review met:
   a rename seeded at `D::f` where `D` has `using B::f;` is `unsupported`
   by `spec/edits.md` §9.1 (the using-declaration is a seed of another
   kind): the same rule decides it.
4. **`in_pattern` and variable templates.** `KeyKind::VariableTemplate`
   is not in its list, so a local class in a lambda in a variable
   template's initialiser is a candidate with no flag. Either the edit
   is right for every instantiation and §9.2 says why a variable
   template is not a pattern for this purpose, or it joins the list.
   Decide with a pair under the digest.

## Tests

- One directory per shape of item 1 (a) to (c), each in three forms: no
  unit instantiates the template; one does; two observers, one of which
  sees only the base. The dependent-base pattern, instantiated and not.
- Item 3: the idiom renamed from the base and from the derived class;
  the same with a second derived class in which the shadow is not
  hidden (must refuse or rename the using-declaration's reach
  correctly: say which); with the using-declaration in a read-only
  file.
- End to end (`slip_verify::run` or `cargo xtask transform`): for (a)
  and for the idiom, the rename applied and verified; and the wrong edit
  beside each (the overrider left behind: `mismatch`, the digest writes
  what a function overrides, `spec/digest-kinds.md` `overrides`).
- Mutation: the link through the pattern dropped; the hidden test
  widened to "any shadow"; the dependent-base case claimed.
