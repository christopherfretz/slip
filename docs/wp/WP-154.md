# WP-154 — rename: a holder is compared with its edited dependent names mapped, not exempted

- Status: in-progress
- Milestone: M2
- Track: C
- Needs: WP-139
- Size: L
- Parallel with: stage 0 with everything; the build with no other digest branch (one digest branch merges at a time)

## Scope

`docs/wp/WP-139.md` made the rename edit a dependent name when the
instantiations the observers made say it binds the subject (the
offering form, `spec/edits.md` §9.4). The pattern that holds the name
then differs between the two images by the name's spelling, and WP-139
withdrew the **whole unit** of the holder from the comparison
(`Declared.changed`). Its second review
(`spec/landed/edits/WP-139.md`, "Second review") showed what that
hides. Both are a rename that is accepted and `verified` while another
name changes what it means:

```cpp
int h(int) { return 10; }
namespace n {
struct S { static int f(int) { return 1; } };
struct U : S {
  int u() { auto l = [](auto t) { return t.f(1); }; return l(S()) + h(0); }
};
}
```

Rename `n::S::f` to `h`. The holder of `t.f` is `n::U::u`, an ordinary
function every observer compiles. It is exempt. `h(0)` in it now finds
`S::h`, not `::h`: `u()` returns 2, was 11. The same in a template, for
every non-dependent name of the holder that no instantiation contains:
a discarded `if constexpr` branch, a default argument no call uses, a
branch of `#ifdef` that only an observer which does not instantiate the
template sees (the exemption one observer earned covers another
observer's different copy of the holder).

The supervisor's ruling (2026-11-24): **no unit is withdrawn from the
comparison for a token.** What a rename declares about a dependent name
is that these tokens change their spelling from `old_name` to
`new_name`; everything else in the unit that holds them, in every
observer, is compared as any unit is. Until this package lands, WP-139
exempts nothing: a rename that edits a dependent name ends `not
verified` with the holder as a `changed` unit (loud), and its default
is to leave dependent names as residue.

`spec/edits.md` "Open questions" already names the direction (a
declared spelling rule `(holder, from, to)`) and its price (a false
mismatch when the holder already uses `to` as a dependent name).

### Stage 0: design (a design agent; no code)

The proposal, `spec/landed/edits/WP-154.md`, decides and justifies each
of these against `spec/digest.md` §3 to §8, `spec/verify.md` §2 to §4
and `spec/edits.md` §6.2, §9.3, §9.4, with every alternative and why it
lost:

1. **What is declared.** Candidates, at least:
   - *by site*: the pre-image places (file, range) of the dependent
     tokens that were edited, as the edit set has them; the walk writes
     the dependent name at a declared place as `new_name` (pre-image) or
     as `old_name` (post-image). Exact; independent of the observer's
     preprocessing; the walk must read a name's spelling place, which
     the digest has never done (what "position-free" then means; a
     token in a macro body or argument; a place the overlay moves);
   - *by holder and name*: within a declared holder's unit, in both
     images, a dependent name spelled `old_name` or `new_name` is
     written as one token. Cheap; a holder that keeps one dependent
     `f` and edits another compares equal; what is no longer told
     apart, and whether the instances cover it;
   - *by name, everywhere*: the same with no holder list; say what it
     gives up beyond the second and whether it removes the need for a
     list at all;
   - *by entry*: (owner, ordinal among the owner's dependent entries),
     as `spec/landed/digest/WP-153.md` names an entry; what happens
     when two observers preprocess the holder differently.
   Say which one, and prove the two reviewer's shapes and their three
   variants differ under it, with a mixed holder (one dependent `f`
   edited, one kept), a holder that already has a dependent `h`, and a
   wrong edit (a dependent token that should have been kept) in a
   pattern that an observer instantiates and in one that none does.
2. **Keys.** A dependent name inside the holder's own key (a trailing
   return type, a deduced parameter type, a trailing requires-clause:
   `spec/landed/edits/WP-139.md` "Findings" 4) changes the key; today
   accepted and not verified. Does the declaration reach the key (the
   two keys are then one, and what a collision of two declarations
   that differ only by `old_name`/`new_name` in a dependent name does:
   it must fail closed), or is a key-to-key rule needed beside it?
   The specialisations' keys follow the pattern's.
3. **Units made from the holder.** An instantiation that contains a
   nested pattern (a generic lambda in a function template: the
   closure's call operator keeps the dependent name) differs by text
   today. A member alias, an enumerator, `alignas` of a class template:
   the unit that differs is not the unit `Keys::unit_of` gave. Which
   units the declaration reaches, by what relation, and whether "the
   holder" survives as a notion.
4. **Unqualified dependent calls** (`f(t)`: the name, the declarations
   found at the definition, argument-dependent lookup later): what the
   walk writes for the name and for the found set under the rename's
   rule, in the pattern and in an instance.
5. **Where it is written**: `Declared` (a new part, its format's
   version rule, `spec/model.md`), `slip_reduce::declared` (derived
   from the set, per site or per holder), `check --declared` given
   (WP-076's ruling: a given declaration may not exempt what the set
   does not derive: the same for this part), the report (what replaces
   the `exempt` lines: every dependent name mapped, with its place and
   the instances that vouch for it), `slip verify --declared` on two
   trees (no overlay: is the part usable there, or refused).
6. **What stays unverified**, stated exactly: a wrong decision about a
   dependent token of a pattern that no observer instantiates
   (`spec/edits.md` §9.4), and nothing else. If something else stays,
   name it and say how the report shows it.
7. **Inertness and scheme**: with no such declaration no digest moves.
8. **The build's stages** and tests: pairs per shape (`differ` when a
   name other than the declared tokens moved; `equal` for the correct
   rename), mutations, the pitfall rows (`spec/pitfalls.md`).

It gets an independent design review, then the supervisor's ruling.

## Handback

### Stage 0 (design)

The proposal is `spec/landed/edits/WP-154.md`. No product code and no
test was added. It was handed back once (commit `3d557c6e`), reviewed
independently, ruled on by the supervisor, and revised; this is the
revised handback. The proposal's section "The design review and the
rulings" maps each finding to where it landed.

**What was decided.**

1. By site, on the post-image only. `Declared` gains `tokens`: a file
   of the post-image, a range, the old name and the new. The walk of
   the post-image writes a dependent name as its old spelling when its
   node is a pattern node (Kiln `spec/ast.md` §18.9.4) of the entry at
   a token's range. The pre-image is not walked again. A node that is
   not such a pattern node is written as today, so the join fails loud;
   Kiln's draft list of eight exceptions to "every rebuilt dependent
   node is a pattern node" is answered one by one, and that part stays
   open until Kiln's list lands.
2. No unit is exempt and no holder exists: the rename makes no
   `changed` entry. Whichever unit writes the node gets the old name.
3. Keys need no rule of their own: a key is made from the same types
   by the same writer. Two declarations that collide are `removed` or
   indeterminate.
4. **Revised.** A name inside a type is respelled per use, from the
   operand the unit itself wrote, read through sugar (typedefs and
   aliases included). Probe 3 showed at the pin that every use keeps
   its own operand node beside the shared canonical one. Three
   canonical types Kiln derives (an adjusted parameter type, an
   enumeration's promotion type, the type in a conversion function's
   name) take the operands of the written type they came from. The
   first version's rule (the first spelling of a profile decides, with
   a mark `respelled` and a list entry `undeclared`) is withdrawn;
   `spec/digest-kinds.md` §4.2 rule 1 and §4.4 are amended to say that
   a unit's bytes for a type are a function of the profile and of the
   declared nodes of the spelling that unit holds, never of the
   spelling Kiln met first.
5. The found set of an unqualified dependent call is written as it is,
   mapped by the rules; only the name is respelled.
6. **Revised.** `tokens` is version 3 of `DECL`, written only when not
   empty, so no existing container changes; a container with tokens is
   bound to one post-image. It is derived by `slip_reduce::declared`
   from a new piece kind (`dependent`) and where its text lands; it is
   usable on two trees (`slip declare` gains a `respelled` line).
   `check --declared` given with an edit set whose tokens the set does
   not derive is refused as inconsistent input, with an error naming
   the token.
7. **Revised.** Everything the reports say about a token is computed
   by the verify job from its own parse (a new shard section
   `token_use`: per token, per entry declared for it, the rows with an
   entity, whether the context is kept, the failed rows). Both report
   forms print, per token, the observers that read it and those that
   vouch it. Nothing is decided from the edit set's `instances`.
8. **Corrected.** The first version said that one thing only stays
   unverified. That was wrong. A declared token is verified in an
   observer only where an instantiation of that observer keeps the
   expression that holds it. Three additions to the trusted base say
   what holds elsewhere:
   - *The kept list*: the specification marks the contexts in which an
     instantiation's unit writes the substituted expression; every
     other context is outcome-only (the list fails closed). One table
     of 49 contexts says what keeps each: today's walk (18 rows),
     WP-156, a table stage of WP-153, or Kiln.
   - *The obligation*: every specialisation's row for a declared entry
     must bind the subject of a declared rule that renames the old name
     to the new one; otherwise the run is not verified, and the finding
     names the specialisation and the entity. It is one-sided (it does
     not read what the name bound before), and the proposal says what
     it misses.
   - *Residue*: a token that some observer reads and does not vouch
     (not instantiated there, or outcome-only) is residue `dependent`
     with its reason; the result is `verified_with_residue` at best.
   The rename edits a dependent name only in a kept context and leaves
   the others `unresolved` with the reason `outcome_only`; the offering
   form becomes the default again for kept sites.
9. With no token no digest moves; `scheme` stays 2.
10. **Re-cut.** Four build stages. Stage 1, the walk (`slip_digest`,
    trusted base), comes after WP-155 and WP-156 on the digest branch;
    it marks a context as kept only by a pair that shows the
    difference, and closes no context itself. Stage 2, the formats
    (`slip_model`, `slip_apply`), needs neither and can run at once.
    Stage 3, verify, reduce and the commands (`slip_verify` is trusted
    base), needs 1 and 2. Stage 4, the rename (not trusted base), needs
    3. Of stage 1 only the marking of the operand rows needs WP-156.

**What stays loud for a correct rename**: a type Kiln holds in
canonical form only, with no written source (no source is known to
reach one); two operands of one profile in one written type respelled
differently; a name formed by a macro invocation; a parse with no
pattern nodes recorded (`unverifiable`).

**For Kiln** (the proposal's section, each item marked design or
implementation): the contract for pattern nodes with its exceptions
(implementation; Kiln's WP-3591, seen as a draft); a row for every
substitution in which the name was resolved, with the sentence of
which substitutions those are (design only there; Kiln's WP-3584 is
the known gap); three written types Kiln keeps today and Slip now
reads (a contract to keep, no request). No request for a shared
profile: the probe found the own node.

**What could not be decided.** The six questions of the first version
are ruled. Two are new and block nothing. (1) By the vouching rule, a
token in a header template is residue as soon as one observer includes
the header without instantiating the template, which on a large code
base may be most tokens. The proposal builds the rule as ruled, asks
for the number from the corpus in stage 3, and words a refinement
(cover an unvouched observer whose units for the pattern are equal to
those of an observer that vouches) for the supervisor to rule on then.
(2) What `slip verify` on two trees says of an unvouched token: that
form has no state for residue. The proposal is written with
`incomplete`, status 4, and the token lines; the alternative is
status 0 with the lines.

**What was run.** In the first round, two throwaway tests: one over
`slip_kiln` (entries, pattern nodes and node locations for eight
shapes), one over `slip_digest` (stream traces of twelve pairs: what a
respelled dependent name changes in each unit). In the revision, a
third over `slip_digest`, **the S3 probe: run, passed, the own
operand node is there** (each declaration's type as written through
its sugar, the operand node of each use and its entry, the canonical
type's first spelling; the shared-profile pair with a hand-written
library template and with `<iterator>`, in both include orders).
Each was `cargo test -p <crate> --test zz_wp154 <filter>` under
`scripts/env.sh`, removed from the checkout before the commit. The
reviewer's six runs are cited by its shape names. Kiln's statements
about its tip were not run. `cargo xtask lint` before each commit. No
prototype of the rule: stage 0 writes no product code.
