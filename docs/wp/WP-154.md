# WP-154 — rename: a holder is compared with its edited dependent names mapped, not exempted

- Status: in-progress
- Milestone: M2
- Track: C
- Needs: WP-139
- Size: L
- Parallel with: stage 0 with everything; the build with no other digest branch (one digest branch merges at a time)

## Scope

`docs/wp/WP-139.md` made the rename edit a dependent name when the
instantiations the observers made say it binds the subject (the
offering form, `spec/edits.md` §9.4). The pattern that holds the name
then differs between the two images by the name's spelling, and WP-139
withdrew the **whole unit** of the holder from the comparison
(`Declared.changed`). Its second review
(`spec/landed/edits/WP-139.md`, "Second review") showed what that
hides. Both are a rename that is accepted and `verified` while another
name changes what it means:

```cpp
int h(int) { return 10; }
namespace n {
struct S { static int f(int) { return 1; } };
struct U : S {
  int u() { auto l = [](auto t) { return t.f(1); }; return l(S()) + h(0); }
};
}
```

Rename `n::S::f` to `h`. The holder of `t.f` is `n::U::u`, an ordinary
function every observer compiles. It is exempt. `h(0)` in it now finds
`S::h`, not `::h`: `u()` returns 2, was 11. The same in a template, for
every non-dependent name of the holder that no instantiation contains:
a discarded `if constexpr` branch, a default argument no call uses, a
branch of `#ifdef` that only an observer which does not instantiate the
template sees (the exemption one observer earned covers another
observer's different copy of the holder).

The supervisor's ruling (2026-11-24): **no unit is withdrawn from the
comparison for a token.** What a rename declares about a dependent name
is that these tokens change their spelling from `old_name` to
`new_name`; everything else in the unit that holds them, in every
observer, is compared as any unit is. Until this package lands, WP-139
exempts nothing: a rename that edits a dependent name ends `not
verified` with the holder as a `changed` unit (loud), and its default
is to leave dependent names as residue.

`spec/edits.md` "Open questions" already names the direction (a
declared spelling rule `(holder, from, to)`) and its price (a false
mismatch when the holder already uses `to` as a dependent name).

### Stage 0: design (a design agent; no code)

The proposal, `spec/landed/edits/WP-154.md`, decides and justifies each
of these against `spec/digest.md` §3 to §8, `spec/verify.md` §2 to §4
and `spec/edits.md` §6.2, §9.3, §9.4, with every alternative and why it
lost:

1. **What is declared.** Candidates, at least:
   - *by site*: the pre-image places (file, range) of the dependent
     tokens that were edited, as the edit set has them; the walk writes
     the dependent name at a declared place as `new_name` (pre-image) or
     as `old_name` (post-image). Exact; independent of the observer's
     preprocessing; the walk must read a name's spelling place, which
     the digest has never done (what "position-free" then means; a
     token in a macro body or argument; a place the overlay moves);
   - *by holder and name*: within a declared holder's unit, in both
     images, a dependent name spelled `old_name` or `new_name` is
     written as one token. Cheap; a holder that keeps one dependent
     `f` and edits another compares equal; what is no longer told
     apart, and whether the instances cover it;
   - *by name, everywhere*: the same with no holder list; say what it
     gives up beyond the second and whether it removes the need for a
     list at all;
   - *by entry*: (owner, ordinal among the owner's dependent entries),
     as `spec/landed/digest/WP-153.md` names an entry; what happens
     when two observers preprocess the holder differently.
   Say which one, and prove the two reviewer's shapes and their three
   variants differ under it, with a mixed holder (one dependent `f`
   edited, one kept), a holder that already has a dependent `h`, and a
   wrong edit (a dependent token that should have been kept) in a
   pattern that an observer instantiates and in one that none does.
2. **Keys.** A dependent name inside the holder's own key (a trailing
   return type, a deduced parameter type, a trailing requires-clause:
   `spec/landed/edits/WP-139.md` "Findings" 4) changes the key; today
   accepted and not verified. Does the declaration reach the key (the
   two keys are then one, and what a collision of two declarations
   that differ only by `old_name`/`new_name` in a dependent name does:
   it must fail closed), or is a key-to-key rule needed beside it?
   The specialisations' keys follow the pattern's.
3. **Units made from the holder.** An instantiation that contains a
   nested pattern (a generic lambda in a function template: the
   closure's call operator keeps the dependent name) differs by text
   today. A member alias, an enumerator, `alignas` of a class template:
   the unit that differs is not the unit `Keys::unit_of` gave. Which
   units the declaration reaches, by what relation, and whether "the
   holder" survives as a notion.
4. **Unqualified dependent calls** (`f(t)`: the name, the declarations
   found at the definition, argument-dependent lookup later): what the
   walk writes for the name and for the found set under the rename's
   rule, in the pattern and in an instance.
5. **Where it is written**: `Declared` (a new part, its format's
   version rule, `spec/model.md`), `slip_reduce::declared` (derived
   from the set, per site or per holder), `check --declared` given
   (WP-076's ruling: a given declaration may not exempt what the set
   does not derive: the same for this part), the report (what replaces
   the `exempt` lines: every dependent name mapped, with its place and
   the instances that vouch for it), `slip verify --declared` on two
   trees (no overlay: is the part usable there, or refused).
6. **What stays unverified**, stated exactly: a wrong decision about a
   dependent token of a pattern that no observer instantiates
   (`spec/edits.md` §9.4), and nothing else. If something else stays,
   name it and say how the report shows it.
7. **Inertness and scheme**: with no such declaration no digest moves.
8. **The build's stages** and tests: pairs per shape (`differ` when a
   name other than the declared tokens moved; `equal` for the correct
   rename), mutations, the pitfall rows (`spec/pitfalls.md`).

It gets an independent design review, then the supervisor's ruling.

## Handback

### Stage 0 (design)

The proposal is `spec/landed/edits/WP-154.md`. No product code and no
test was added. It was handed back (commit `3d557c6e`), reviewed
independently, ruled on and revised (commit `185bdedf`, the first
revision); that revision had a delta review, was ruled on again, and
this is the handback of the **second revision**. The proposal's
sections "The design review and the rulings" and "The second revision"
map each finding to where it landed; the short form of the second is
at the end of this handback.

**The part to review first** is §6.6 of the proposal, the witness and
its join: it is the one place from which a wrong `verified` could come,
and it is written to be attacked (the rule, the facts it reads, the
argument, what a wrong join gives in each direction, its assumptions,
the pairs).

**What was decided.**

1. By site, on the post-image only. `Declared` gains `tokens`: a file
   of the post-image, a range, the old name and the new. The walk of
   the post-image writes a dependent name as its old spelling when its
   node is a pattern node (Kiln `spec/ast.md` §18.9.4) of the entry at
   a token's range. The pre-image is not walked again. A node that is
   not such a pattern node is written as today, so the join fails loud;
   Kiln's draft list of eight exceptions to "every rebuilt dependent
   node is a pattern node" is answered one by one, and that part stays
   open until Kiln's list lands.
2. No unit is exempt and no holder exists: the rename makes no
   `changed` entry. Whichever unit writes the node gets the old name.
3. Keys need no rule of their own: a key is made from the same types
   by the same writer. Two declarations that collide are `removed` or
   indeterminate.
4. A name inside a type is respelled per use, from the operand the use
   itself wrote, read through sugar (typedefs and aliases included).
   Every use keeps its own operand node beside the shared canonical
   one (probe 3, and the delta review's 44 shapes). For an
   expression's type the own operand is the referenced declaration's
   node, and two units sharing one written operand is the normal case.
   **Second revision**: inside an own operand the rule recurses into a
   written type nested there; inside the canonical walk of a first
   spelling it is suppressed. Three canonical types Kiln derives (an
   adjusted parameter type, an enumeration's promotion type, the type
   in a conversion function's name) take the operands of the written
   type they came from. `spec/digest-kinds.md` §4.2 rule 1 and §4.4
   are amended to say that a unit's bytes for a type are a function of
   the profile and of the declared nodes of the spelling that use
   holds, never of the spelling Kiln met first.
5. The found set of an unqualified dependent call is written as it is,
   mapped by the rules; only the name is respelled.
6. `tokens` is version 3 of `DECL`, written only when not empty, so no
   existing container changes; a container with tokens is bound to one
   post-image. It is derived by `slip_reduce::declared` from a new
   piece kind (`dependent`) and where its text lands; it is usable on
   two trees (`slip declare` gains a `respelled` line).
   `check --declared` given with an edit set whose tokens the set does
   not derive is refused as inconsistent input, with an error naming
   the token.
7. **Second revision: what vouches a token is a witness of the walk,
   per row.** Kiln's per-specialisation table has, for a dependent
   entry, a row per specialisation with the entity the name binds
   there. A row is **witnessed** when the walk of this parse wrote, in
   full-walk mode in a unit's own stream, the declaration field of a
   resolved name node (a `DeclRefExpr`, or a `MemberExpr` that is not
   an overloaded access) such that (a) the node's location is the
   entry's name location, (b) the entity written is the row's, and (c)
   the row's specialisation is the unit's entity, a declaration
   entered in place inside it, or a declaration that encloses one of
   those; the write matches that row and no other; **and the unit is
   matched**: the pre-image has a unit of the same class and key with
   the same digest. An entry is `vouched` when it has a row with an
   entity and every such row is witnessed; otherwise it is
   `outcome_only`, and the reason names the specialisation and why
   (`no_unit`, `unit_not_matched`, `ambiguous`). Never witnessed: a row
   keyed on a template or a concept; an entry whose name location is
   also another entry's; a token with two entries that have rows for
   one specialisation (the ruling). The join is a pure function over
   plain data, in a module of its own, so each part is tested alone.
   - *Why a witness in a matched unit is enough*: equal digests are
     equal streams, so the pre-image's unit holds at the same place a
     reference to the same key; had the pre-image bound another entity
     the unit would differ and would not be matched. The proposal lists
     every way a unit that holds a witness can be one-sided or unequal
     (derived or declared, changed, post-image only, exempt,
     indeterminate, doubled), with its finding today and after WP-155:
     in each the witness is not counted, so the entry is `outcome_only`
     whether or not the unit gives a finding. The rule does not depend
     on WP-155's mark.
   - *A wrong join*: a missed witness costs residue; every strictness
     of the rule and every incompleteness of the declaration path can
     only do that. A false witness is argued impossible under two
     assumptions about Kiln that the proposal names and that no
     specification states: a resolved name node at an entry's name
     location with the entry's entity was made from that entry's name
     (A0), and the nodes one row stands for, the elements of a pack
     expansion, are written together (A1).
   - *The kept list leaves the trusted base.* The table of 49 contexts,
     the column `instance` and the flag on the walk's path stay as the
     rename's planning aid and as the reports' reason text. Nothing in
     verify reads them; a wrong list costs residue or an edit not made.
8. What holds where a token is not vouched, and what the reports say:
   - *The obligation* (trusted base, unchanged): every row of a
     declared entry must bind the subject of a declared rule that
     renames the old name to the new one; otherwise the run is not
     verified, and the finding names the specialisation and the entity.
     It is one-sided, and the proposal says what it misses.
   - *Residue*: a token that some observer reads and neither vouches
     nor covers is residue `dependent` with its reason; the result is
     `verified_with_residue` at best.
   - *Cover* (ruled, with the review's conditions): an entry an
     observer reads and does not instantiate is covered when every unit
     that writes its pattern there is, by key, digest and the entry's
     ordinal among the token's entries in that unit, a unit of another
     observer that vouches the entry by witnesses. Per entry; never for
     `outcome_only`; no chains; an entry no observer instantiates stays
     `not_instantiated`. It rests on the witness rule.
   - *The reports*: a new shard section `token_use`, computed by the
     verify job from its own parse (per token, per entry: its rows,
     how many are witnessed, the first row that is not and why, the
     units for cover, the failed rows, the advisory context). Both
     report forms print, per token, the observers that read it, vouch
     it and are covered. `slip verify` on two trees says `incomplete`
     (status 4) for a token read and not vouched, with a line of its
     own, apart from the line for an unverifiable observer; a failed
     row is `not verified`, ahead of it.
   - *The rename* edits a dependent name only where every row of its
     entry is witnessed on the pre-image: the map phase's walk takes a
     watch list (the subjects' names) and gives that back in memory;
     no format. Any other site stays `unresolved` with the reason
     `outcome_only`. The offering form becomes the default again.
9. With no token and no watch list no digest moves and nothing of this
   is computed; `scheme` stays 2. The witness and the watch list write
   nothing into any stream.
10. **Re-cut again.** Four build stages. **Stage 2, the formats, goes
    first** (`slip_model`, `slip_apply`): it needs nothing and owns the
    token type, which lives in `slip_model`. Stage 1, the walk
    (`slip_digest`, `slip_kiln`; trusted base), needs stage 2 and comes
    after WP-155 and WP-156 on the digest branch; the join gets its
    targeted review before it. Stage 3, verify, reduce and the commands
    (`slip_verify` is trusted base), needs 1 and 2, decides "matched",
    folds cover, and puts the cost into the harness's tracked numbers
    (the counters `verify.tokens.*` and `parse.written.*`; the verify
    phase's `cpu_s`, `wall_s`, `peak_rss_max`, `peak_rss_p99` beside
    the identity run). Stage 4, the rename (not trusted base), needs 3.

**What stays unverified**, each said in the reports or named as a
limit: a token no observer instantiates (residue `not_instantiated`);
an entry with a row no matched unit writes (residue `outcome_only`):
at the pin a generic lambda named only in `decltype` or reached only
through the conversion to a function pointer, a default argument of a
lambda's call operator or of a local class's member, a name in a
signature, a constraint or a concept, and the operand sites until
WP-156; a specialisation Kiln resolved the name in and recorded no row
for, where no unit writes it (assumption A2: the rows are complete); a
specialisation no observer of the run makes. The defect the delta
review found in today's digest (the overload changes and no unit
differs, its `g1` to `g4`) is WP-158's; this design does not depend on
it, and those entries are `outcome_only` until WP-158 gives them a
unit.

**What stays loud for a correct rename**: a type Kiln holds in
canonical form only, with no written source (no source is known to
reach one); two operands of one profile in one written type respelled
differently; a name formed by a macro invocation; a parse with no
pattern nodes recorded (`unverifiable`); and, by the witness rule's
strictness, residue for a macro argument that is substituted twice.

**For Kiln** (the proposal's section, five items, each marked design or
implementation, each with the Slip need). (1) The contract for pattern
nodes with its exceptions (implementation; Kiln's WP-3591, seen as a
draft). (2) A row for every substitution in which the name was
resolved, with the sentence of which substitutions those are (design
only there). Seen at the pin, for information: no row for a name in a
requires-clause written on a lambda, and none for a name in a generic
lambda's body that depends only on the enclosing template's parameter;
a concept's row is keyed on the concept. Kiln's statement that an
argument-dependent call in a generic lambda has no row is not what the
pin shows. (3) Three written types Kiln keeps today and Slip reads (a
contract to keep, no request). (4) Information only. (5) **New, the
later strengthening of the witness; nothing waits for it**: each row
names the substituted expression node, one row per substituted node
(design of what a row is, and implementation). It replaces the
location, entity and path match by the node's identity and removes
assumptions A0 and A1 and the two ambiguity rules.

**What could not be decided.** Every question of the first version and
of the first revision is ruled. Three points are new; the proposal is
written with a choice for each and nothing waits. (1) The ruled rule
"two entries of one token in one specialisation are unwitnessed" is
redundant at the pin with the location check, because Kiln gives each
macro expansion its own locations; it costs two macro shapes their
`vouched`. Written as ruled. (2) A write that matches two rows of one
entry (one entity, nested specialisations) witnesses neither; it could
witness both. No such shape is known at the pin. Written strict. (3)
The advisory marks are a column of `spec/digest-kinds.md`, which is
otherwise the trusted base's table; the alternative is a list in the
rename's specification. Written with the column.
