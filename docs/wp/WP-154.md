# WP-154 — rename: a holder is compared with its edited dependent names mapped, not exempted

- Status: in-progress
- Milestone: M2
- Track: C
- Needs: WP-139
- Size: L
- Parallel with: stage 0 with everything; the build with no other digest branch (one digest branch merges at a time)

## Scope

`docs/wp/WP-139.md` made the rename edit a dependent name when the
instantiations the observers made say it binds the subject (the
offering form, `spec/edits.md` §9.4). The pattern that holds the name
then differs between the two images by the name's spelling, and WP-139
withdrew the **whole unit** of the holder from the comparison
(`Declared.changed`). Its second review
(`spec/landed/edits/WP-139.md`, "Second review") showed what that
hides. Both are a rename that is accepted and `verified` while another
name changes what it means:

```cpp
int h(int) { return 10; }
namespace n {
struct S { static int f(int) { return 1; } };
struct U : S {
  int u() { auto l = [](auto t) { return t.f(1); }; return l(S()) + h(0); }
};
}
```

Rename `n::S::f` to `h`. The holder of `t.f` is `n::U::u`, an ordinary
function every observer compiles. It is exempt. `h(0)` in it now finds
`S::h`, not `::h`: `u()` returns 2, was 11. The same in a template, for
every non-dependent name of the holder that no instantiation contains:
a discarded `if constexpr` branch, a default argument no call uses, a
branch of `#ifdef` that only an observer which does not instantiate the
template sees (the exemption one observer earned covers another
observer's different copy of the holder).

The supervisor's ruling (2026-11-24): **no unit is withdrawn from the
comparison for a token.** What a rename declares about a dependent name
is that these tokens change their spelling from `old_name` to
`new_name`; everything else in the unit that holds them, in every
observer, is compared as any unit is. Until this package lands, WP-139
exempts nothing: a rename that edits a dependent name ends `not
verified` with the holder as a `changed` unit (loud), and its default
is to leave dependent names as residue.

`spec/edits.md` "Open questions" already names the direction (a
declared spelling rule `(holder, from, to)`) and its price (a false
mismatch when the holder already uses `to` as a dependent name).

### Stage 0: design (a design agent; no code)

The proposal, `spec/landed/edits/WP-154.md`, decides and justifies each
of these against `spec/digest.md` §3 to §8, `spec/verify.md` §2 to §4
and `spec/edits.md` §6.2, §9.3, §9.4, with every alternative and why it
lost:

1. **What is declared.** Candidates, at least:
   - *by site*: the pre-image places (file, range) of the dependent
     tokens that were edited, as the edit set has them; the walk writes
     the dependent name at a declared place as `new_name` (pre-image) or
     as `old_name` (post-image). Exact; independent of the observer's
     preprocessing; the walk must read a name's spelling place, which
     the digest has never done (what "position-free" then means; a
     token in a macro body or argument; a place the overlay moves);
   - *by holder and name*: within a declared holder's unit, in both
     images, a dependent name spelled `old_name` or `new_name` is
     written as one token. Cheap; a holder that keeps one dependent
     `f` and edits another compares equal; what is no longer told
     apart, and whether the instances cover it;
   - *by name, everywhere*: the same with no holder list; say what it
     gives up beyond the second and whether it removes the need for a
     list at all;
   - *by entry*: (owner, ordinal among the owner's dependent entries),
     as `spec/landed/digest/WP-153.md` names an entry; what happens
     when two observers preprocess the holder differently.
   Say which one, and prove the two reviewer's shapes and their three
   variants differ under it, with a mixed holder (one dependent `f`
   edited, one kept), a holder that already has a dependent `h`, and a
   wrong edit (a dependent token that should have been kept) in a
   pattern that an observer instantiates and in one that none does.
2. **Keys.** A dependent name inside the holder's own key (a trailing
   return type, a deduced parameter type, a trailing requires-clause:
   `spec/landed/edits/WP-139.md` "Findings" 4) changes the key; today
   accepted and not verified. Does the declaration reach the key (the
   two keys are then one, and what a collision of two declarations
   that differ only by `old_name`/`new_name` in a dependent name does:
   it must fail closed), or is a key-to-key rule needed beside it?
   The specialisations' keys follow the pattern's.
3. **Units made from the holder.** An instantiation that contains a
   nested pattern (a generic lambda in a function template: the
   closure's call operator keeps the dependent name) differs by text
   today. A member alias, an enumerator, `alignas` of a class template:
   the unit that differs is not the unit `Keys::unit_of` gave. Which
   units the declaration reaches, by what relation, and whether "the
   holder" survives as a notion.
4. **Unqualified dependent calls** (`f(t)`: the name, the declarations
   found at the definition, argument-dependent lookup later): what the
   walk writes for the name and for the found set under the rename's
   rule, in the pattern and in an instance.
5. **Where it is written**: `Declared` (a new part, its format's
   version rule, `spec/model.md`), `slip_reduce::declared` (derived
   from the set, per site or per holder), `check --declared` given
   (WP-076's ruling: a given declaration may not exempt what the set
   does not derive: the same for this part), the report (what replaces
   the `exempt` lines: every dependent name mapped, with its place and
   the instances that vouch for it), `slip verify --declared` on two
   trees (no overlay: is the part usable there, or refused).
6. **What stays unverified**, stated exactly: a wrong decision about a
   dependent token of a pattern that no observer instantiates
   (`spec/edits.md` §9.4), and nothing else. If something else stays,
   name it and say how the report shows it.
7. **Inertness and scheme**: with no such declaration no digest moves.
8. **The build's stages** and tests: pairs per shape (`differ` when a
   name other than the declared tokens moved; `equal` for the correct
   rename), mutations, the pitfall rows (`spec/pitfalls.md`).

It gets an independent design review, then the supervisor's ruling.

## Rules

`docs/AGENTS.md`. Stage 0 is design: no code, no gate but `cargo xtask
lint`. The build: the full `cargo xtask ci`, second review (trusted
base). The reviewer's question, for the design and the build: a rename
after which any name other than the dependent tokens it declares binds
another entity, or one of those tokens was edited wrongly in a pattern
an observer instantiates, and `verified`.
