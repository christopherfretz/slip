# WP-048 — module units in snippets, and the tests of the module rows

- Status: in-progress
- Milestone: M1
- Track: C
- Needs: WP-033, WP-038, WP-044
- Size: M
- Parallel with: WP-040, WP-045, WP-046, WP-047

**Starts after WP-044 is on main** (the Kiln pin moves under
`slip_kiln`, and this package edits `crates/slip_kiln/src/snippet.rs`).

## Scope

A snippet is one translation unit with headers. It cannot import a
module, so `module m;` (an implementation unit) and `import n;` fail,
and the rows of `spec/digest-kinds.md` §10.7 that need a second module
unit have no test (`spec/landed/digest-kinds/WP-033.md` "What the
runner compiles": `UnitKind` `Implementation` and `Header`, `UnitInfo`
`imports`, `Owner` `unit` other than 0, `ModuleOwnership`'s values that
only an imported declaration has, the imports of the order unit). This
package lets a snippet name the module units it imports, by source, and
writes those tests.

1. **Find out how Kiln's front-end entry at the pin takes a module from
   source.** `kiln_driver::Args` has `-fmodule-file=<name>=<path>`
   "module files or module interface sources" (`kiln_driver/src/args.rs`,
   `module_files`; Kiln's `spec/modules.md` §2 and §11.6), header units
   (`-fmodule-header`), and `-fprebuilt-module-path=`. Read how the
   driver turns an interface source named so into something the parse
   imports (does it parse it in the same process? through the same file
   loader the snippet front end gives its in-memory files? does it
   write a module file to disk first?), and whether the library entry
   `slip_kiln` calls (`kiln_driver::front_end`, Kiln WP-2120) reaches
   that path or only the `kiln` executable's job runner does. Write
   what you find, with `file:line`, at the head of
   `spec/landed/harness/WP-048.md` before writing code.
2. **By what you find:**
   - **(a) the entry imports a module from an in-memory source**, or
     can with a file loader `slip_kiln` already controls:
     `slip_kiln::snippet` gains the module units (below), nothing is
     written to disk, and the argument stays refused in
     `Extra::args` (the snippet names its modules; a test does not
     pass `-fmodule-file=`).
   - **(b) it needs a module file on disk**: do not write one from a
     test. Draft the request to Kiln in `docs/requests/` (the form of
     the files there; say which part is design without prior art and
     which is implementation against Kiln's own `spec/modules.md`: the
     supervisor sends it), write the tests of step 4 as `# pending`
     with `# needs: kiln`, and hand back. The supervisor may then
     prototype on a Kiln branch `slip/<id>` or wait.
   - **(c) the entry does it only with changes to `slip_kiln`'s
     adapter** (it must run a second front end for the interface unit
     and hand the result over): say what the adapter must do and how
     large it is before doing it. Under about 300 lines of safe code
     with no new Kiln API: do it. Otherwise it is (b).
3. **The snippet's module units** (case a or c):

   ```rust
   // slip_kiln::snippet
   pub struct Snippet<'a> {
       // … as now …
       /// Module units the main file may import, each a source among
       /// `files`: `(module name, path)`, as
       /// `-fmodule-file=<name>=<path>` names an interface source.
       /// A partition is named `m:p`. Empty by default.
       pub modules: &'a [(&'a str, &'a str)],
   }
   ```

   `Snippet` is constructed by name in many tests: add the field so that
   existing constructions keep compiling (a `Default` and
   `..Default::default()` is a change to every caller, on open branches
   too; a constructor function beside the struct, or a second struct
   `ModularSnippet` wrapping the first and `parse_modular`, is not).
   Choose the form that changes no existing caller and say which.
   Errors: a module path that is not one of `files`, a name twice, a
   name that is not a module name: each a wrong snippet, named. A header
   unit (`import "h.h";`, `import <h>;`) if the entry supports it by
   the same means; else out of scope and said so.
4. **The pair runner** (`crates/slip_digest/tests/common/mod.rs`): a
   header line of the main file, `// module: <name>=<file>`, once per
   module unit, the file being another file of the directory (both
   sides see it, as every header; a module unit that differs between
   the sides includes `side.h` itself). `docs/wp/WP-047.md` is open in
   the same file at `run_all` and the `expect` lines: touch `Header`,
   `HEADER_KEYS`, `header` and `digest_side_with` only.
5. **The tests** the rows lacked, each seen to fail without its row's
   code (the code exists: `crates/slip_digest/src/other.rs`,
   `order.rs`, `decl.rs`): `UnitKind/Implementation`,
   `UnitKind/Header` if header units are in scope, `UnitInfo/imports`
   (a second import; the same imports in another order: decide from
   §10.7 and digest §9 which it is and test that), `Owner/unit` (the
   same declaration owned by the main unit against owned by an imported
   one), the values of `ModuleOwnership` an imported declaration has,
   `ModuleTable/explicit_defs` across units, the order unit's imports;
   and one `equal` pair: an imported module's unit digests the same
   whether it is reached through the import or parsed as the main file
   (if that is what §10.7 "the `Ast` like its own" promises; if the
   promise is something else, test what it is). Remove from
   `tests/tables/untested.txt` what these cover (`SLIP_BLESS=1`).
6. **Keys.** An entity attached to a named module has the module in its
   key or it does not (`spec/digest.md` §4; `keys.rs`): find which,
   and show by a pair that two entities of one name in two modules have
   two keys. If they share one, that is a finding to hand back, not to
   fix (`keys.rs` belongs to other packages).

## Interface

`slip_kiln::snippet` as in step 3. Nothing else.

## Tests

- `crates/slip_kiln/tests/`: a snippet importing one interface unit;
  one importing a unit that imports a partition; each error of step 3;
  a module unit with an error (the diagnostics name its path); the
  same snippet parsed twice gives the same diagnostics.
- The pair tests of step 5; `determinism.rs` covers them as it covers
  every directory.

## Done when

The full gate passes with `main` merged in; or, in case (b), the quick
gate passes, the request is drafted and the tests are pending. The
handback gives the finding of step 1, the case taken, the rows now
tested and still untested, the finding of step 6, and whatever of
Kiln's module support the tests showed wrong (smallest reproducer
each).

## Out of scope

Modules in the corpus runs (LLVM has none); `std` and `std.compat` from
the toolchain's module cache; precompiled headers; `keys.rs`; a module
file written to disk by a test.

`slip_kiln` is trusted base: second review, asking whether a snippet
without modules parses exactly as before (the goldens do not move) and
whether anything reads or writes the host's file system.
