# WP-158 — the digest: an instantiation with no unit (a generic lambda reached without a direct call; a default argument of a local callable)

- Status: review
- Milestone: M1
- Track: C
- Needs: WP-155
- Size: M
- Parallel with: WP-156 (both are digest branches; one merges at a time)

## Scope

Found by the delta review of `docs/wp/WP-154.md`'s design, on `main`,
with no part of that design in play: a name in an instantiated body
binds otherwise and every unit both images have is equal.

```cpp
struct X { int mf(int) { return 1; }
           int mf(long) { return 2; } };   // the edit renames this one
int w() {
  auto l = [](auto u) { return u.mf(1L); };
  int (*p)(X) = l;                          // the body runs: 2 before, 1 after
  return p(X());
}
```

The call operator's specialisation for `X` is instantiated (Kiln has
its row `operator()<X>(X) const => X::mf(long)`), and the digest
writes no unit for it. Four shapes are known, each run through
`tests/rules` with the template text unchanged and an empty
expectation, and each passes as equal:

- a generic lambda reached only through its conversion to a function
  pointer (the body runs);
- a generic lambda named only in an unevaluated operand
  (`decltype(l(X())) x = 0;`), alone and beside a second instantiation
  that does have a unit (`decltype(l(X())) x = l(Y());`);
- a default argument of a lambda's call operator, in an instantiated
  function;
- a default argument of a member of a local class, in an instantiated
  function.

The controls differ as they should: the lambda called directly, the
same in `sizeof`, `noexcept` and a requires-expression, a member's
default argument, a generic lambda's own default argument, a local
class's uncalled member, an `auto` function named only in `decltype`.

1. **Find the cause first and say which it is**: the digest's choice
   of units (which instantiations get one, and from where it learns
   of them), or a list Kiln gives it that lacks these. If it is
   Kiln's, write the request (what the pin gives, what is missing,
   the Slip need) in the handback for the supervisor to send, and
   build what the pin allows.
2. **The rule to reach**: every function body and every default
   argument that Kiln instantiated in this parse has a derived unit,
   whatever made the front end instantiate it (a call, an unevaluated
   operand, a conversion, a deduced return type, an address taken).
   The unit's key, group and cause follow `spec/digest.md` §2.2 as for
   the instantiations that have one today. State what "Kiln
   instantiated" is read from, so the rule can be checked against it:
   a count of instantiated bodies and default arguments with no unit,
   which is zero on every fixture and reported on the corpus.
3. **What changes**: units are added; no existing unit's stream
   changes. **List any existing pair, pitfall tree or golden whose
   verdict changes before changing it**; each is a ruling. A unit
   added on one side only by a correct transform must not be a new
   refusal: say what `spec/verify.md` §4 does with these units under
   WP-155's rule (the lambda's call operator is not emitted without a
   reference; argue it or show the tree).
4. **If a shape cannot have a unit at the pin**, it is a limit by name
   in `spec/digest.md` §2.3, with a `limit` pair, and goes on the list
   for Kiln.
5. **`scheme`** by `spec/digest.md` §11 (ask the supervisor at the
   final merge of `main`).
6. **The specs**: `spec/digest.md` §2.2 and §13 (the completeness
   test gains the count of item 2), `spec/digest-kinds.md` if a kind
   is added, `spec/pitfalls.md` rows for the four shapes.
7. **The corpus command** for the supervisor: on `llvm` `lib/Support`,
   the count of item 2 before and after, units and digest bytes and
   time against `main`, and that Demo 1's control and `01-relocate`
   stay clean.

**For Kiln** (to send as it stands):

> Kiln does not instantiate a friend function's definition when the
> declaration a call names is a later friend redeclaration instantiated
> from a pattern with no body (pin `4a83f6e3c`). Reproduction (C++20):
>
> ```cpp
> struct X { int mf(int) { return 1; } int mf(long) { return 2; } };
> struct D;
> template <class T> struct B { friend int fr(X u, D*) { return static_cast<T&>(u).mf(1L); } };
> template <class T> struct A { friend int fr(X u, D*); };
> struct D : B<X>, A<X> {};
> int w() { return fr(X(), (D*)nullptr); }
> int main() { return w() == 2 ? 0 : 1; }
> ```
>
> `fr`'s definition is never instantiated: no entry in
> `fn_def_insts`, and the declaration the call binds has no body. Two
> orders fail:
> 1. Two classes, the definition's class instantiated first (above).
> 2. One class, `friend int fr(X u, D*) { … }` and then `friend int
>    fr(X u, D*);`.
>
> The order that works is the redeclaration's class first
> (`struct D : A<X>, B<X> {};`): the definition is instantiated.
> clang++-19 instantiates it in every order: the program above exits 0,
> and with `mf(long)` renamed it exits 1 (the call binds `mf(int)`)
> ([temp.inst]/4: a friend function defined in a class template is
> instantiated when it is odr-used, whichever declaration the call
> names).
>
> A likely cause, from reading `kiln_sema/src/templ/class.rs`:
> 1. `instantiate_function_definition` (`:1626`) starts from
>    `member_redecl_instance` (`:2318`).
> 2. That function returns `f` itself whenever `instantiated_from(f)`
>    is `Some`. So the search for the redeclaration whose pattern has a
>    body (`:2329`) is never reached for an instantiated friend.
> 3. The pattern used is the later declaration's, which has no body, and
>    nothing is instantiated.
>
> Slip pins it as a limit: `rules/wp158/friend-two-classes-rev`
> (equal), pitfall R26.
