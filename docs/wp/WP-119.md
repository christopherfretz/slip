# WP-119 — a rule on an instantiated member that agrees with its pattern's is accepted

- Status: todo
- Milestone: M2
- Track: C
- Needs: WP-071, WP-072, WP-073
- Size: M
- Parallel with: nothing in `slip_digest` (one digest branch merges at a time)

## Scope

`spec/digest.md` §3.4 gives a member of an instantiation the name of its
pattern's member as the rules map it (`follow_patterns`, WP-103), and
makes its key indeterminate when any rule matches the member itself,
under its plain or its followed name (`key/rule-on-instantiated-member`):
"no source renames an instantiation's member apart from its pattern's".

The native rename met the case where that is too strict
(`spec/landed/edits/WP-071.md`, decision 14 and "For the digest"). A
function defined as a friend in a class template is a namespace-scope
entity with a key of its own:

```cpp
namespace n {
template <class T> struct S { friend int f(S) { return 1; } };
int f(S<int>);            // unit A sees only this: no pattern, its own key
}
int u() { n::S<int> s; return f(s); }   // unit B: f(S<int>) follows the pattern
```

Whether a subject has a rule is a function of its key and the request
only (`spec/edits.md` §4.1): two observers never give one subject two
rules. Unit A needs a rule on `n::f(S<int>)` (nothing else renames it
there); so the run's table holds one, and in unit B that same rule
matches an instantiated member and makes its key indeterminate. The
rename therefore keeps the rule and flags the subject `unsupported`
(§9.5): such a function cannot be renamed at all.

This package makes the digest accept the rule where it says what the
pattern says, and the rename drop the flag.

1. **The digest (`crates/slip_digest/src/keys.rs`, `follow_patterns`).**
   A rule that matches an owned instantiated member under its **plain**
   key is accepted when the key it produces is exactly the key
   following gives (`Key { name: <the patterns' mapped name>, ..key }`:
   the same parent, kind, name and discriminator). The member's key is
   then that key, with no cause. Every other case stays as it is:
   a rule on the plain key that produces any other key (another name,
   another parent) is `key/rule-on-instantiated-member`; patterns that
   disagree are `key/patterns-disagree`; under ownership a rule matches
   no dependency entity (WP-110, rule 1).
2. **A rule that matches the followed key.** Today
   `rules.map(followed) != followed` is indeterminate. Decide, and show
   with pairs, whether that stays once item 1 holds. The case to
   settle it on is a swap: two friends `f` and `g` defined in one class
   template, the post-image swaps their names, the table undoes it
   (`g → f`, `f → g`, on the patterns and on the instantiated
   functions). The plain key `g(S<int>)` maps to `f(S<int>)`, which is
   what following gives, and a rule (`f → g`) matches that followed
   key. A table maps a key once (`spec/verify.md` §2.1), so the second
   match is not a second step; but say what a rule on the followed key
   **alone** (no rule on the plain key) means and keep that
   indeterminate unless you can show it is the same statement.
   Whatever is decided must never give two entities one key without
   the collision being counted (`instantiated/member-collision`).
3. **Rule use (`spec/verify.md` §9, `crates/slip_digest/src/rule_use.rs`).**
   An instantiated member whose plain key matched an accepted rule is
   in `via(r)` of that rule, as the same entity is in a unit that does
   not instantiate the class; it is still not counted for the pattern
   member's rule (`spec/landed/verify/WP-069.md` §3 item 1). State what
   `direct(r)` holds for it. The pair to show: units A and B above give
   the rule on `n::f(S<int>)` the same use, so neither is a stale
   observer because of the other.
4. **The rename (`crates/slip_refactor`, `spec/edits.md` §9.5).** A
   subject whose key follows a pattern member keeps its rule and is no
   longer `unsupported` for that reason. The tests
   `wp103-friend-defined-in-template` and `wp103-friend-defining-
   instantiated` lose the flag; `a_seed_rule_does_not_depend_on_instantiation`
   stays as it is. A friend that does **not** define the function is
   not followed (`slip_kiln::written::origin`) and is not touched here.
   If WP-073's part C left a flag on members of instantiated
   specialisations for this cause, the same holds for them; if it left
   it for another reason, say which and leave it.
5. **End to end.** One `cargo xtask transform` or `slip_verify::run`
   case: the two units above, the rename of `n::f` to `n::g` applied,
   verified with the run's rules: both observers `verified`. And the
   wrong edits beside it, each a `mismatch` or a failed obligation:
   the friend renamed and the namespace-scope declaration not; the
   reverse; the call in `u` left spelling `f` (ADL finds nothing, or
   finds another `f`: both).

## Tests

- `instantiated/direct-rule-beside-pattern-rule` and
  `friend-redeclared-direct-rule` (B32b) become equal with no
  indeterminate unit; `direct-rule-alone` (no rule on the pattern: the
  plain key maps to a name the pattern does not give) and
  `direct-rule-on-followed-name` stay indeterminate, or change as item
  2 decides, with the reason in `expect.txt`.
- New pairs: the rule on the member gives another name than the
  pattern's (indeterminate); gives the pattern's name and another
  parent (indeterminate); a member of a class's instantiation
  (`S<int>::g`, parent a specialisation) under a rule that names it
  (say what such a rule's parent is and whether a table can hold it);
  the swap of item 2; two instantiations `S<int>`, `S<long>` with a
  rule on one instantiated friend only (the other follows with no
  rule: equal? it is what unit A's table would hold if A declared only
  `f(S<int>)`); nested class templates (the pattern is itself a member
  of an instantiation: the chain of patterns).
- `rule_use/indeterminate/rule-on-instantiated-member` moves: the
  accepted rule has a `Use`.
- Mutation: the acceptance widened to "the names agree" (parent not
  compared), to "any rule on the plain key", to "the rule on the
  followed key alone"; the `via` entry dropped. Each killed.

## Rules

`docs/AGENTS.md`; the "Rules common to the digest's area packages" of

## Done when

The full gate passes with `main` merged in; a function defined as a
friend in a class template and declared at namespace scope is renamed
and verified across a unit that instantiates the class and one that
does not; no pair that was indeterminate for this cause is now equal
without a line in the landed file saying why it is right.

## Out of scope

A friend that does not define the function; a member of an explicit
specialisation (it needs its own rule already); the spelling rule for
dependent names (`spec/edits.md` "Open questions").

Trusted base: second review. The reviewer's question: with the rule
accepted, can two programs in which an instantiated member is bound to
different entities share its key, or a rename that leaves one of the
function's declarations behind verify?
