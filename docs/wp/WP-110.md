# WP-110 — rules rename owned entities only: ownership in the walk's mapped keys

- Status: in-progress
- Milestone: M1
- Track: C
- Needs: WP-103, WP-105
- Size: M
- Parallel with: WP-108, WP-109, the digest's open area packages

## Scope

The independent review of the pitfall rows N25 to N38
(`docs/wp/WP-105.md`, row N34) confirmed a wrong `verified` in the spec
as it stood: under a namespace rule (`acme` mapped to `legacy`), an edit
that moves a **dependency's** declaration into `acme` (a dependency
header included inside a moved block; a dependency macro that opens the
namespace, redefined by owned code) gives two isomorphic translation
units, and it verifies although the dependency's binary still defines
the entity in `legacy`. `spec/verify.md` §2 and §2.1 ("Rules rename
owned entities only") and `spec/digest.md` §3.4 ("Ownership") are
amended; this package makes the walk and the container do what they
say.

1. **The container.** `Declared` gets `kept` and `files` (`DECL`
   version 2, `spec/verify.md` §2); `rules_id` covers `files`. A reader
   accepts version 1 without a rule and refuses version 1 with one.
   `kept` is only carried here (its check is `docs/wp/WP-111.md`).
   Every invariant the reader checks is a row in the spec with a test,
   as `spec/landed/edits/WP-061.md` did for `RSLT`.
2. **Ownership of a file, for the walk.** The walk under a non-empty
   rule table is given a predicate over the files of the image. Its
   maker is the verify job's (`crates/slip_cli`, `docs/wp/WP-052.md`,
   which may still be in flight: then you write the function and its
   tests against `Ownership` and a root map of your own in the test,
   and say what the job must call): `Ownership` is in subject paths
   (`spec/edits.md` §2.1, "covers"), the image's files are in the
   image's, and the job maps them. A file the image cannot map to a
   subject path is read-only.
3. **Ownership of an entity** (`spec/verify.md` §2.1, the three
   bullets): computed once per entity and cached; by the **expansion
   location** of each declaration (what Kiln gives for the outermost
   invocation of a macro expansion; `crates/slip_kiln/src/ranges.rs`
   has the walk to a file location if `docs/wp/WP-084.md` is on main,
   otherwise read the source manager as it does and say so). No
   location, or a location in a buffer that is not a file (`<built-in>`,
   the command line, scratch space): read-only.
4. **The mapping**: rule 1 (a rule matches only an owned entity) and
   rule 2 (the namespace chain is mapped from the member's point of
   view; a parent that is not a namespace has its own key). Find every
   place the walk maps a parent or applies a rule (`keys.rs`,
   `units.rs`, `RuleTable::map` in `crates/slip_model/src/keys.rs`, and
   the callers that write a reference to an entity from another unit's
   stream) and show in the landed file that each takes the same path:
   a reference to an entity and the entity's own unit must give one
   key.
5. **Attack the rule.** It was attacked once on paper (the review's
   findings are in the amended §2.1). Build each of these as a pair
   under rules and record the outcome; a case where the rule gives a
   wrong `verified`, or refuses an edit that is correct with no way to
   declare it, is reported with its pair, not decided here:
   - a member of a dependency class template instantiated with an owned
     argument (N06, N26, N28 must still verify);
   - an owned explicit specialisation, and an owned partial
     specialisation, of a dependency template, with members; the same
     removed, so that §4 step 4 (`docs/wp/WP-108.md`) must see one key
     for the declared and the derived unit;
   - an owned definition of a function, a static data member, a nested
     class that the dependency declares;
   - a friend function defined in an owned class, and one a dependency
     class befriends;
   - an owned namespace alias, using-declaration and using-directive in
     the old namespace, moved and not moved;
   - a nested namespace that only owned code opens, one that both open,
     an inline namespace, the unnamed namespace;
   - a dependency that opens the destination, before and after;
   - a dependency header with no namespace of its own, included inside
     an owned block that moves;
   - a declaration made by a dependency macro invoked in an owned file,
     and by an owned macro invoked in a dependency file; a namespace
     opened by a macro and closed by another;
   - an entity declared in an owned file and in a dependency header
     that only some observers include (two observers: say what each
     gives; `spec/verify.md` "Open questions");
   - a deduction guide, written by owned code for a dependency
     template, and the implicit ones;
   - `extern "C"` entities, builtins, the implicit `operator new`;
   - an owned template whose specialisation has a dependency type as an
     argument, and a dependency template with an owned template as a
     template template argument.

and tests; `crates/slip_model/src/keys.rs` (`RuleTable`) if the mapping

`spec/verify.md` §2, §2.1 and `spec/digest.md` §3.4: correct them where
building shows them wrong or silent, and say so.
