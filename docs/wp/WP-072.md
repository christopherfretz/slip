# WP-072 — rename: virtual families, using-declarations and the other followers

- Status: done
- Milestone: M2
- Track: F
- Needs: WP-062, WP-071
- Size: M
- Parallel with: WP-073, WP-074, WP-075

## Scope

`spec/edits.md` §9.2, the parts the core left conservative, in two files
of `slip_refactor` that this package owns:

1. **`src/rename/families.rs`**: candidates and links. Every virtual
   member function named like the old identifier is a subject of role
   `candidate` (or `seed`, if the request names it), in every observer,
   whatever class it is in; with a link to each function it overrides
   directly. A candidate declared in a file that is not owned has
   `read_only`, so that a family that reaches into a library refuses the
   run through its links (§9.5). A candidate that is a destructor, an
   operator or a conversion function cannot arise (they are not named by
   an identifier); a covariant return or a `final` changes nothing.
   Each candidate's declarations and references are claimed as a
   subject's are: reduce turns the claims of an unselected candidate
   into `keep` (§5.2).
2. **`src/rename/followers.rs`**:
   - a using-declaration that names subjects (at namespace, class and
     block scope) and each using-shadow it introduces: followers with
     `of` the entities named; the using-declaration's own name token
     (`slip_kiln::written::decl_names`, kind `UsingDeclaration`) is
     claimed with a literal piece (§9.3: Kiln does not record it as a
     reference, so no obligation could be seen there; the follower's
     rule is what checks it). A using-declaration that names subjects
     and non-subjects
     of one name (an overload set partly selected) is exactly the case
     reduce refuses as `mixed_follower`.
   - a reference with `via_using` (found through a shadow): the token
     is claimed for the referent, and the shadow is a subject already.
   - an unnamed class or enumeration that a subject variable names
     (`digest.md` §3.3, `unnamed_by`): a follower whose rule is made
     from its `Key` (`Keys::key`, `docs/wp/WP-087.md`) with the inner
     name replaced (`spec/edits.md` §9.2): the rule finds the key whose
     name is `unnamed_by` the new identifier, with the parent, kind and
     discriminator the key has, and calls it by the name it has now. A
     follower for which `Keys::key` refuses keeps `unsupported`.

**Needs nothing new of Kiln.** The name of a using-declaration is in
Kiln's declaration extents (WP-2090, `spec/ast.md` §19 of Kiln), which
`docs/wp/WP-067.md` reads; the question this package used to wait for
(follow-up K-c of [KF3](../requests/KF3-location-utilities.md) §5) is
answered by that table.

Not on Demo 2's path: the three targets have no virtual function and no
using-declaration. It is on the path of calling the rename usable.

## Interface

The hooks `docs/wp/WP-071.md` fixed, with these bodies:

```rust
pub(crate) fn families::collect(ctx: &mut Ctx<'_, '_>);
pub(crate) fn followers::collect(ctx: &mut Ctx<'_, '_>);
```

and nothing public. If a hook's signature has to change, change it in
`rename/mod.rs` only where the hook is called and say so first in the
handback: WP-073 is working against the same file's other hooks.

`families::collect` reads overriding from the AST's record of overridden
methods (cite Kiln's `file:line` in the handback), not from names and
signatures of its own.

## Tests

Directories under `crates/slip_refactor/tests/rename/`, as the core's:

- a virtual function and one override; a chain of three; a diamond; two
  unrelated classes with a virtual function of the same name (two
  candidates, no link); an override in a class template of a base that
  is not dependent; a non-virtual function of the same name in an
  unrelated class (`keep`);
- an override of a function declared under `dep/` (`read_only` on the
  candidate); a pure virtual seed with no override in this observer;
- a call through a base pointer, through `this->`, qualified
  (`Base::f()`), and a pointer to member;
- using-declarations at each scope; one naming an overload set of two
  subjects; one in a derived class that makes a base's function public;
  a call that finds the function through the shadow;
- a variable of an unnamed class type and of an unnamed enumeration.

With `docs/wp/WP-062.md`'s reduce (a dev-dependency, which
`docs/wp/WP-071.md` put in the manifest), two tests that
build two observers' `Edits` and reduce them: a family split over two
observers that share only the base class is selected whole; an
unrelated family is not, and its claims become `kept`.

### Supervisor's handback (merge, 2026-11-23)

Merged at `a2d176d2` with `main` `5d4e65f6` merged in (`a0abaf05`;
`slip_refactor`'s tests and clippy re-run after that merge; the full
gate ran at `a2d176d2`). The independent review's verdict was "merge":
no silent wrong result; every overrider or overridden function it wrote
was linked, refused or flagged, and a using-declaration's shadow left
behind is caught by the digest (a shadow's discriminator is its
target's key; a function's unit writes what it overrides).

Left open, each a refusal of code that could be renamed, none a wrong
result; all of it is `docs/wp/WP-120.md`:

- a candidate or follower in a template's pattern stays `unsupported`
  with no owner after WP-073 (an overrider of an instantiated base's
  member, an overrider or a using-declaration in a class template with a
  non-dependent base);
- the unhide idiom (`using B::f;` beside an override of `B::f()`) is
  `mixed_follower`, and a seed in a class that has such a
  using-declaration is `unsupported`;
- `in_pattern` does not list a variable template;
- `spec/edits.md` §9.5: WP-073 says a seed member of a class template is
  not flagged, and `families::candidate` flags a virtual one. WP-073
  states the exception when it merges this.

Notes for the record: an uninstantiated pattern with a dependent base
(`template <class T> struct D : T { void f() override; };`) keeps its
name, since no unit records the link (stated in WP-120 item 1);
mutation F16's premise is not what the review saw (a pasted declaration
is in `decl_names`), its conclusion stands; W16 is equivalent only while
