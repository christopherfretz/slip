## Rules

The eight rules of `docs/wp/WP-057.md` "Rules" hold, with the settings of
§3 and §4 in place of rule 3:

- **Rows R** rename one entity in place: `declared.txt` is one
  `relocate <entity> => <its parent> :: <new name>` line (R03 and R08:
  one line per renamed entity). There is no `dep/` unless the row needs
  a dependency (R04).
- **Rows E** declare nothing: `declared.txt` is absent or empty, except
  E11's `good` tree, whose removed declarations are `removed` lines.

And for these tables in particular:

- **`good: none`** (R01, R04, R07, E10, E14): the hazard has no correct
  edit of the same shape. The row has `bad/` only, and its line in
  `expect.txt` says why in a few words.
- **Rows with two `good` shapes** (R05: a harmless local rename; E03:
  redundant parentheses; E06: four respellings; E07: four edits) have
  one `good-<k>/` per shape, all on `pre/`. Each must verify by itself;
  do not fold them into one tree.
- **Every wrong edit here is silent** unless the table says
  `not_parsed` (R06): the `bad` tree compiles, with clang and with
  Kiln. If yours does not, it is not the row.
- **R03, R07, E11** allow two findings ("on the derived class or its
  function", "`changed` the caller … or `derived_changed` on the
  template"): write the one your reading of `spec/digest.md` expects,
  and say in the landed file which fact decides it. WP-056 corrects the
  line if the run shows the other.
- **R11**: the expected line is `mismatch indeterminate <entity>` (a
  collision: two entities with one key), not a `changed`.
- **E13** pins today's behaviour (`__LINE__` is a value); its
  `expect.txt` carries a `#` line saying so and naming the open
  question of `spec/digest.md`.
- **E09** expects the order unit: the entity is `<order>`.

**Hazards not covered** (the review's notes in `.build/review-058`
hold no list of sixteen; these are mine and the review's findings that
no row now covers):

1. `__PRETTY_FUNCTION__` prints a parameter's type as written: respelling
   a parameter through an alias (`a(Widget)` to `a(Handle)`) changes the
   program's string while the symbolic value is "the same". A row with
   the alias respelling and a consumer of the string.
2. A class template's member function body changed by removing the
   header with an explicit specialisation of that member
   (`template <> void S<int>::f()`): as E11 `bad-3`, for a member.
3. Renaming a member a structured binding uses: `get<0>` found as a
   member; renamed, the binding falls back to a free `get` found by
   argument-dependent lookup.
4. Renaming to a name an object-like or function-like macro defines
   (`f` to `MAX` with `#define MAX(a, b)`): calls expand differently,
   silently when the arity matches.
5. Renaming that changes a string an attribute holds:
   `__attribute__((alias("_Z1fv")))`, `[[gnu::section]]`, `asm` labels.
6. Reordering data members: layout and the order of member
   initialisation change while the member set is the same.
7. Dropping a redundant-looking `inline` or `constexpr` on a header
   variable: linkage, or a `static_assert`/`if constexpr` that read it.
8. A lambda capture default in a template, where the default decides
   what an instantiation captures (E16 is a non-template).
9. `[&]` against `[&n]` where `n` is not odr-used (`sizeof(n)`, a
   constant): the closures differ in size (`e16v/`).
10. An `#include` reordering that changes which partial specialisation
    an instantiation selects (a more specialised one declared after the
    point of instantiation in one order).
11. A rename whose new name hides a name a default template argument or
    a default member initialiser looks up.
