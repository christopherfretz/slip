# WP-114 — the verify job writes `binding` in every shard, and `rule_use` under rules, for a tree image

- Status: review
- Milestone: M2
- Track: C

## Scope

**Amended 2026-11-23.** `docs/wp/WP-121.md` (M1, cut after Demo 1's
first run on the corpus failed every observer of a relocation) took,
ahead of this package: item 1 for a rule table that is **not empty**
(`binding` and `rule_use`), item 4, and the end-to-end cases of item 3
for a relocation and a rename. WP-121 leaves a job with an empty rule
table byte for byte as it was. What stays here: `binding` in the
shards of a job with **no** rule (item 1's last sentence), the
exception's removal with its moved goldens (item 2), and whatever of
item 3 WP-121's handback does not list as done (the tests of WP-053
marked for WP-074, the stale and the unused rule through `slip
verify`). Read WP-121's handback first; this package needs WP-121.

`spec/verify.md` §9.1: "`binding` is present in every shard a verify job
writes, whatever the parse's outcome", and "`rule_use` is present when
the outcome is `ok` and the rule table is not empty". The run's
agreement (`docs/wp/WP-070.md`, `spec/verify.md` §9.3) holds every
shard to that. The verify task of `docs/wp/WP-052.md` writes neither.
So `slip verify --declared <file>` with a rule table that is not empty,
over a tree the user edited by hand or with another tool, marks every
observer `failed` and exits 4 (`docs/wp/WP-053.md`'s test of it says so
in its comment). That is the first use of Slip there is: the namespace
migration verified from a tree, before any transform exists.

This is item 3 of `docs/wp/WP-074.md` for the tree form, taken out so
that it does not wait for the overlay (`docs/wp/WP-066.md`) and the
native rename. WP-074 keeps the overlay form and `spellings`.

1. **The task** (`crates/slip_verify`, the verify task of WP-052):
   - `binding` (section 24) in every shard the task writes, whatever
     the outcome (`ok`, `rejected`, `unverifiable`, and each of the
     task's early ends): `overlay` absent, `declared` the content id of
     the `DECL` container the job was given, `pre` the round of the pre
     shard. A job with no declared changes at all (M1's `slip verify`
     with nothing declared) writes it too, with the id of the empty
     container: say where that id comes from, and that every job of
     one run writes the same one.
   - `rule_use` (section 25) when the outcome is `ok` and the table is
     not empty: `Options.rule_use` of `docs/wp/WP-069.md` on the walk
     of the **post**-image, the table's `rules_id`, the uses as that
     package gives them. Never when the table is empty, and never for
     another outcome.
   - `spellings` is never written here.
2. **The exception goes** (`spec/verify.md` §9.3, "A run with a tree
   image and no rule is M1's: its shards need no `binding` … This
   exception is temporary"): with item 1 a shard without a binding is
   never this run's. Remove the exception from the agreement
   (`crates/slip_verify`) and from the spec in the same commit, with
   the test that a shard without `binding` under no rule is now
   `failed`. Every golden of a verify shard moves by exactly the new
   section: show it (the old bytes are the new ones with section 24
   removed).
3. **The commands** (`crates/slip_cli`): the tests of WP-053 marked for
   WP-074 that concern the tree form now expect `verified` (observers
   and run), exit 0; those that concern the overlay stay as they are.
   A stale rule and an unused rule through `slip verify` with a tree:
   the report's lines and the exit status of `spec/verify.md` §9.2 and
   §9.4, one test each.
4. **`docs/wp/WP-074.md`** item 3: shorten to the overlay form and
   `spellings`, pointing here for the rest.

5. **From the review of WP-121** (2026-11-23; the run's side,
   `crates/slip_verify/src/run.rs`):
   - **A verdict is of the map shard the run reads.** A verdict holds
     `pre`, the content id of the map shard the job compared against;
     the run checks only that the observer's map shard is `ok`. A map
     shard replaced within a round (`Store::publish` renames over an
     existing shard) leaves a verdict against another pre-image's
     digests. The run compares the verdict's `pre` with the content id
     of the map shard it was given and refuses the shard otherwise
     (`failed`, with the reason, as WP-121's messages are); say in
     `spec/verify.md` §9.3 which check this is. A test with a map shard
     republished between the job and the report.
   - **The message of a shard `judge` rejects** (invalid, `ok` without
     a verdict, counters that disagree, a verdict whose map shard is
     not `ok`) is empty: `slip: failed: <main>: `. Give each its
     reason.
   - **Question to answer, not to build without the supervisor's
     word:** `read_sections` folds the `rule_use` of every accepted
     shard, the `unverifiable` ones too (§9.3). For an `unverifiable`
     whose post-image a guard refused or that changed during the job
     (G3), the counts are of an image that is not the run's (§10.6
     says so for `spellings`, which are checked and not folded). State
     what a stale pair or a use from such a shard does to the report
     and the status today, and propose: fold, or check only.

## Tests

- Per outcome of the task, a shard read back: `binding` present with
  the three fields; `rule_use` present or absent as item 1 says.
- Two jobs of one run with different observers write one `declared`
  and one `pre`.
- The agreement accepts the task's own shards under a rule table and
  under none; a shard of another run (another `declared`) is `failed`.
- Item 3's command tests.
- Mutations: `binding` left out of each non-`ok` outcome in turn;
  `rule_use` written for a rejected post-image; `rule_use` taken from
  the walk of the pre-image; the table's id replaced by the declared
  container's; the exception left in the agreement.

**Item 5's question.** Today `read_sections` folds the `rule_use` of an
`unverifiable` shard: a stale pair in it is a `stale` finding (listed,
and the run `not verified`, status 1, where the observer alone gives
`incomplete`, status 4), a use in it keeps its rule off `unused`, a kept
index counts as seen. Shown by
`crates/slip_verify/tests/agreement.rs` `s9_3_unverifiable_rule_use_is_folded_today`.
No wrong `verified` can follow (the observer is not verified). **Proposal:
check only**, as for `spellings` (§10.6): an image a guard refused or that
changed (G3) is not the run's, so its counts can report a stale pair that

post-image is the run's, loses a real stale pair until it verifies; the
run is not verified either way. Telling the two apart needs the verdict
to say whether the post-image was the run's (not its reason's text).
