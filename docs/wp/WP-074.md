## Scope

What a worker does with the two fields protocol 2 gave a job
(`spec/edits.md` §8.1, §8.3, §10.3; `spec/verify.md` §5 "The post-image
as an overlay" and "Inputs under an overlay", §9 "Rule use"), in
`slip_cli`'s worker.

**It stands on M1's worker**, which is being specified in parallel and
is not among this package's `Needs` because its files have no number
here yet: a map job that digests (the `digests` section in a map shard)
and a verify job that parses a post-image, compares it with the pre
shard and writes a verdict (`spec/verify.md` §5). This package starts
when both are on `main`, and the supervisor adds their numbers to
`Needs` then. It changes them in two places only: where the post-image
comes from, and what the shard carries besides.

1. **Map with a transform.** A map job whose `transform` is present:
   read the `TRFM` from the store; parse with the written-reference
   table on; digest as M1's map job does; if the unit is `ok`, build
   `slip_digest::Keys` over the same input and call
   `slip_refactor::run`; the shard carries `edits` and the `edits.*`
   counters. A unit that is not `ok` has no `edits` section. A map job
   without a transform is M1's, untouched: its shard is byte for byte
   what it was.
2. **Verify through an overlay.** A verify job whose `post` is present:
   read the `OVLY` and the `DECL`; load blobs as §10.3 says (those of
   the pre shard's `inputs` first; parse again with more while the
   post-image read an overlay file that was not loaded); run M1's steps
   with the post-image parsed through the overlay and digested with the
   declared rules and `rule_use` on; apply
   `slip_verify::inputs::inputs_under_overlay` after step 2 and turn a
   failure into `unverifiable` with the path; write `binding` in every
   shard and `rule_use` in every `ok` one. Step 4's second parse of the
   pre-image uses no overlay.

Files: new `crates/slip_cli/src/worker/{transform.rs, post.rs}`
(submodules of `worker`, so that `src/lib.rs`, which
`docs/wp/WP-075.md` edits, is not touched); the file M1 leaves the
tasks in (`crates/slip_cli/src/worker.rs` today) for the two `mod`
lines and the two dispatch points; new `crates/slip_cli/tests/tasks.rs`.
No manifest changes: `slip_cli` already depends on every crate used
(`crates/slip_cli/Cargo.toml`; `slip_refactor` since
`docs/wp/WP-071.md`).

## Interface

```rust
// slip_cli::worker::transform
/// The `edits` section and counters for a finished unit; called inside
/// the closure of the parse, after the digest walk.
pub fn run_transform(transform: &Transform, unit: &Unit<'_>, input: &slip_digest::Input<'_>)
    -> Result<(Edits, Vec<Counter>), String>;

// slip_cli::worker::post
pub struct Loaded { pub overlay: Overlay, pub overlay_id: Digest, pub declared: Declared,
                    pub declared_id: Digest, /* path -> bytes of the blobs loaded so far */ }
impl Loaded {
    pub fn open(store: &Store, post: &Post) -> Result<Loaded, String>;
    /// Loads the blobs of the overlay files among `paths` that are not
    /// loaded yet; returns how many it loaded. A blob that is missing or
    /// does not hash to its name is an `Err` (the job fails; the
    /// coordinator writes a `failed` shard).
    pub fn load(&mut self, store: &Store, paths: &mut dyn Iterator<Item = &[u8]>) -> Result<usize, String>;
    pub fn parse_options(&self) -> slip_kiln::ParseOptions<'_>;
    pub fn binding(&self) -> Binding;
}
```

- The worker holds the bytes of the overlay files one observer reads,
  and no others. `peak_rss` of a verify job over an overlay of ten
  thousand files of which the observer reads three is that of the same
  job over an overlay of those three (a test with a counter of bytes
  loaded, not of memory).
- A `Failed` answer, not a shard, for: a transform, overlay, declared
  or blob that is not in the store or does not validate. These are
  failures of the run, not facts about the subject.
- Determinism: the map shard of a transform is a function of the
  observer's inputs and the `TRFM`; the verify shard of the post-image's
  inputs, the pre shard, the `OVLY` and the `DECL`. The number of
  parses of the loading loop is not in the shard.

## Tests

`crates/slip_cli/tests/tasks.rs`, each task run as a task over a store
and a small tree in a temporary directory under the target directory
(no coordinator):

- map with a rename request: the shard has `inputs`, `digests` and
  `edits`; its `digests` section equals that of the same job without a
  transform; a unit with an error has no `edits`;
- verify with the overlay a correct rename makes (built by hand with
  `slip_apply::build`): `verified`, `binding` right, `rule_use` with
  `via` for the rule; the tree on disk is untouched;
- the same with one declaration left out of the overlay: the observer
  that sees only the stale declaration verifies and has `direct`; the
  one that sees both is a mismatch (the collision);
- an overlay whose edit adds an `#include` of another overlaid file: two
  parses, the right post-image, one shard;
- a subject file changed on disk after the map job; an overlay blob
  replaced by other bytes; an overlay file missing from `blobs/`;
- an observer that reads no overlay file under a rule table that is not
  empty: `verified`, `rule_use` present and empty, no blob loaded.

`crates/slip_cli/tests/verify_overlay.rs` of `spec/verify.md` "Tests" is
these last cases through the executable; it belongs to
`docs/wp/WP-076.md`, which has the commands.
