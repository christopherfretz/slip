## Scope

What a worker does with the two fields protocol 2 gave a job
(`spec/exec.md` §5.2, §8.4; `spec/edits.md` §8.1, §8.3, §10.3;
`spec/verify.md` §5.1 "The overlay form", §5.3 guards O1 and O2, §9.1,
§10.4), in `slip_cli`'s worker.

It stands on M1's worker: the map task that digests
(`docs/wp/WP-050.md`) and the verify task that makes an image from
`job.post`, parses the post-image, compares it with the pre shard and
writes a verdict (`docs/wp/WP-052.md`, as amended by M2). It changes
them in two places only: what a map job with a transform adds to its
shard, and what a verify job does when the image is an overlay.

1. **Map with a transform.** A map job whose `transform` is present:
   read the `TRFM` from the store (`Object::Transform`,
   `docs/wp/WP-064.md`) and check its content id; parse with
   `ParseOptions::written` (`docs/wp/WP-067.md`); digest as the map
   task does; if the unit is `ok`, make `slip_digest::query::Keys` over
   the same input (`docs/wp/WP-087.md`) and run the transform; the
   shard carries `edits` (section 17) and the `edits.*` counters
   (`spec/edits.md` §6.3). A unit that is not `ok` has no `edits`
   section. The digest walk's output is complete before the transform
   is entered (§8.1). A map job without a transform is M1's, untouched:
   its shard is byte for byte what it was.

   The transform is chosen by the request's kind: `rename` is
   `slip_refactor::run` (`docs/wp/WP-071.md`); `script` is
   `docs/wp/WP-092.md`'s, and until that package lands a job naming a
   script request is `Err` ("a script transform needs a worker built
   with slip_script"). An `Err` of `slip_refactor::run` fails the job
   (§4.6: the native rename has no failed run).
2. **Verify through an overlay.** A verify job whose `post.image` is
   `Overlay(id)`: the image is `Image::overlay` (`docs/wp/WP-052.md`'s
   `from_post`, the variant this package fills in); the blobs are
   loaded as `spec/verify.md` §5.1 "Loading" says (those of the pre
   shard's `inputs` first; parse again with more while the parse read
   an overlay file that was not given); M1's steps run with the
   post-image parsed through the overlay
   (`ParseOptions::overlay`, `docs/wp/WP-066.md`), the post command
   being the observer's own; guards O1 and O2 replace G1
   (`slip_verify::guards::overlay_inputs`, `docs/wp/WP-070.md`) and a
   failed guard is `unverifiable` with the reason's text. Step 4's
   second parse of the pre-image uses no overlay.
3. **What a verify shard carries besides, through an overlay.** The
   tree form is done: `binding` in every shard the task writes (its
   `overlay` absent, with or without rules; `docs/wp/WP-114.md`, which
   also removed the agreement's exception for a tree image and no rule)
   and `rule_use` (section 29 since WP-111; section 25 is retired) in an
   `ok` shard under a rule table that is not empty (`docs/wp/WP-121.md`),
   from `Params.declared_id` and `Params.pre`; the task's options gained
   no other field. What stays here: with an overlay image, the binding's
   `overlay` is the `OVLY`'s content id; and `spellings` (section 26)
   when the outcome is `ok` and the image is an overlay with at least
   one obligation, absent otherwise (`spec/verify.md` §10.4; with an
   overlay that has no obligation a `spellings` section makes the run's
   agreement fail every observer), made by
   `slip_digest::spelling::check_spellings` (`docs/wp/WP-096.md`) over
   the obligations of the overlay files this observer read, with the
   declared rules, encoded as §10.4 says (`seen`, the `held` spans, the
   `failed` entries), with the counters `verify.spelling.*` of §10.5. A
   tree image never has `spellings`. Check that WP-121's and WP-114's
   sections are what the overlay form needs.

Files: new `crates/slip_cli/src/worker/{transform.rs, post.rs}`
(submodules of `worker`, so that `src/lib.rs`, which
`docs/wp/WP-075.md` edits, is not touched); `crates/slip_cli/src/worker.rs`
for the two `mod` lines and the two dispatch points;
`crates/slip_cli/src/image.rs` (the overlay variant's parse) and
`crates/slip_cli/src/verify_job.rs` (the guard chosen by the image's
form; the three sections); new `crates/slip_cli/tests/tasks.rs`. No
manifest changes: `slip_cli` already depends on every crate used
(`slip_refactor` since `docs/wp/WP-071.md`).

## Interface

```rust
// slip_cli::worker::transform
/// The `edits` section and counters for a finished unit; called inside
/// the closure of the parse, after the digest walk, on the same input.
pub fn run_transform(transform: &Transform, unit: &slip_kiln::Unit<'_>, input: &slip_digest::Input<'_>)
    -> Result<(Edits, Vec<Counter>), String>;

// slip_cli::worker::post
/// The overlay of a job and the blobs loaded so far for one observer.
pub struct Loaded { /* the Overlay, its id; path -> Arc<[u8]> of the blobs loaded */ }
impl Loaded {
    pub fn new(overlay: std::sync::Arc<Overlay>, id: Digest) -> Loaded;
    /// Loads the blobs of the overlay files among `paths` that are not
    /// loaded yet; returns how many it loaded. A blob that is missing or
    /// does not hash to its name is an `Err` (the job fails; the
    /// coordinator writes a `failed` shard).
    pub fn load(&mut self, store: &Store, paths: &mut dyn Iterator<Item = &[u8]>) -> Result<usize, String>;
    /// The overlay files in `inputs` that are not loaded.
    pub fn missing<'a>(&self, inputs: &'a [FileRef]) -> Vec<&'a [u8]>;
    pub fn parse_options(&self) -> slip_kiln::ParseOptions<'_>;
    /// The obligations of the overlay files in `inputs`, as `check_spellings` takes them.
    pub fn obligations(&self, inputs: &[FileRef]) -> (Vec<slip_digest::spelling::Obligation>, Vec<u64> /* index in the overlay */);
}
```

- `verify_job::verify(store, job, params)` keeps its signature
  (`spec/exec.md` §8.6); `Params.image` is the `Image` with its overlay
  variant.
- The worker holds the bytes of the overlay files one observer reads,
  and no others; the `Overlay` itself is kept from one job to the next
  while the id is the same (`spec/exec.md` §8.4). A test with a counter
  of bytes loaded: a verify job over an overlay of ten thousand files
  of which the observer reads three loads those three.
- `Failed`, not a shard, for: a transform, overlay, declared or blob
  that is not in the store or does not validate. These are failures of
  the run, not facts about the subject.
- Determinism: the map shard of a transform is a function of the
  observer's inputs and the `TRFM`; the verify shard of the post-image's
  inputs, the pre shard, the `OVLY` and the `DECL`. The number of
  parses of the loading loop is not in the shard.

## Tests

`crates/slip_cli/tests/tasks.rs`, each task run as a task over a store
and a small tree in a temporary directory under the target directory
(no coordinator):

- map with a rename request: the shard has `inputs`, `digests` and
  `edits`; its `digests` section equals that of the same job without a
  transform; a unit with an error has no `edits`; a request of kind
  `script` fails the job with the message above; a request whose id is
  not the file's content id fails the job;
- verify with the overlay a correct rename makes (built by hand with
  `slip_apply::build`): `verified`; `binding` names the overlay, the
  declared changes and the pre round; `rule_use` has `via` for the
  rule; `spellings` has every obligation of the files read as held; the
  tree on disk is untouched;
- the same with one declaration left out of the overlay: the observer
  that sees only the stale declaration verifies and has `direct`; the
  one that sees both is a mismatch (the collision);
- the same with one reference's replacement spelling a name that
  resolves to another function: `spellings.failed` has the entry with
  what was found;
- an overlay whose edit adds an `#include` of another overlaid file: two
  parses, the right post-image, one shard;
- a subject file changed on disk after the map job (O2, the reason's
  text); the loading loop stopped before its end by a test hook, so
  that an overlaid file was read from disk (O1, the reason's text); an
  overlay blob replaced by other bytes and an overlay file missing from
  `blobs/` (each a failed job, not a shard);
- an observer that reads no overlay file under a rule table that is not
  empty: `verified`, `rule_use` present and empty, `spellings` present
  with `seen` empty (the overlay has an obligation; absent when it has
  none: a second case), no blob loaded;
- a verify job with a tree image: no section 26, with or without rules
  (sections 24 and 29 are `docs/wp/WP-114.md`'s and WP-121's tests).

`crates/slip_cli/tests/verify_overlay.rs` of `spec/verify.md` "Tests" is
these last cases through the executable; it belongs to
`docs/wp/WP-076.md`, which has the commands.
