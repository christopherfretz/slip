## Scope

Can start at Slip's present Kiln revision: it reads only the declaration
arena. Rebase onto WP-081 when that lands (it defines the trait this
implements; until then code against the trait as printed in WP-081).

`spec/api.md` §1 (unit order), §5.1, §5.5 (origin), §6.1 to §6.4.
`KilnSubject<'u>`: the implementation of `Subject` over
`slip_kiln::Unit`, for the methods `is_live`, `kind_bits`, `lookup`,
`identifier`, `display`, `parent`, `parameters`, `declarations`,
`entity_of`, `origin`, `qualified`, `file_len`, `text`, `owned`,
`file_ref`. The rest return "nothing" until WP-085, WP-086 and WP-095.

Decisions already taken in the specification, to implement and not to
revisit:

- An **entity** is the declaration `slip_digest` treats as the entity
  (`Walk::entity`, `crates/slip_digest/src/keys.rs`): the first
  declaration, and for the pattern of a template the template. Implement
  the same two lines here; WP-095 adds the test that the two agree on
  every declaration of the test snippets.
- `lookup` walks declared members with the transparent scopes of §6.1
  rule 3. It builds a per-scope name index on first use, not a global one.
- **Unit order** is the order of first tokens after preprocessing. Use
  WP-084's comparator; until it lands, order by the expansion location's
  (include chain, offset), which is the same thing computed slowly.
- `display` reuses the names `slip_digest` renders (`names.rs`).

**Disagreements and what is wrong or ambiguous in the spec.**

1. S1: `Subject::lookup` returns `Vec<Entity>`, so a subject cannot fail
   a lookup with a status. Rather than change the trait, I removed the
   limits: every walk is a worklist with a seen-set, bounded by the
   arena, and the chain walks stop only past the arena's size, which
   needs a cycle Kiln's AST cannot have (landed decision 18). So no
   answer is truncated and there is no limit for a test to reach. If you
   still want a limit, it needs `lookup -> Result<Vec<Entity>, Errc>`
   with `limit_exceeded` (§4) in `slip_script` and the host: say so and I
   will do it.
2. "Written" has no flag in Kiln (decision 1); WP-085 moves it to the
   extent table.
3. §6.4 r1 lists no parent for a template parameter (chosen: its
   template, decision 11); §6.4 r3 for the global namespace (empty).
4. §1 unit order needs a declaration's first token; extents are off in
   production at this pin, so the name location is used (decision 14).

**For Kiln.**

1. (Withdrawn in fix round 2.) Declarations are not numbered in parse
   order: Kiln parses default member initialisers and default arguments
   late. Slip does not rely on the numbering; lookup sorts by unit order
   (`review2_m24_delayed_parse_order`). Nothing is needed.
2. A template parameter's owner as a field (now a scan of every template
   parameter list, once).
3. Everything a lambda-expression declares (body locals, init-captures,
   local classes and their members, structured bindings, and the contents
   of lambdas in default member initialisers and default arguments) has an
   implicit context chain (closure, call operator); the extent table
   (WP-067) is what will say it is written (decision 19). Its explicit
   template parameters are written already.
4. Minor (GNU extension): in `void f(){ struct L { int fl = ({ int tf =
   2; tf; }); }; }` Kiln gives `tf` the class `L` as context and rejects
   it as "static data member 'tf' not allowed in local struct 'L'"; it
   should be a block-scope variable of the statement-expression (found by
   the second review).

(The typedef name for linkage purposes is recorded, `typedef_for_anon`;
nothing is needed there.)
