## Scope

WP-024 wrote the header every declaration starts with, the names and
the keys (`decl.rs`, `names.rs`, `keys.rs`) with unit tests and left
the per-row pair tests to the areas. The areas are on `main`; the rows
of these tables are still in `tests/tables/untested.txt`:

- §5.1, §5.2: `DeclKind` (48 rows), `DeclNode` `*.data` (31) and
  `flags`, `DeclFlags` (`0-implicit`, `0-injected`), `DeclMisc`
  (`0-module-ownership`, `0-name-independent`), `ModuleOwnership`;
- §3: `DeclName`, `DeclNameKind`, `OverloadedOperator` (as the name of
  an operator function: WP-031 tested it as the operator of a call);
- rows of landed areas that their packages left: `TagKeyword`,
  `AutoKeyword`, `ExcSpec` `Dynamic`, `Deferred`, `DependentNoexcept`,
  `NoexceptValue` `Dependent.0`, `DefinitionBits` `0-pod`,
  `0-has-inherited-assign`, `0-trivially-relocatable`, `FnSpec`
  `0-immediate-escalating`, `ParamData` `flags-static-array`,
  `VarEvalState` `Evaluating`, `StringEncoding` `Wide16`. For each,
  read the landed file and the handback of its package first: it says
  why the row was left.

This is a package of tests. The code exists; **expect it to be wrong
in places**: every independent review of an area found defects that
all its row tests passed, and these tables never had a review. So,
beyond the rows:

1. **Keys** (`keys.rs`, digest §3 and §4.3). Known:
   - `typedef struct {} *P, *T;` is not named by its first declarator
     (§3.3 "else its first declarator"): fix, with tests for each
     branch of §3.3's rule (typedef name for linkage, first declarator,
     first enumerator, none) and for the order of declarators being
     the fact (`*P, *T` against `*T, *P`: which is it? §3.3 decides;
     if it does not, the conservative reading and a landed paragraph);
   - structured bindings at namespace scope whose initialiser is
     tuple-like were reported to collide in their keys by the review
     of WP-033; neither the reviewer nor the implementer could
     reproduce it (`docs/wp/WP-033.md` Handback). Probe it once with
     the others below (two `auto [a, b] = t;` declarations in one
     namespace, and one in each of two namespaces); nothing is known
     to be wrong.
   - Then probe on your own: two different entities with one key is
     the worst defect this crate can have (a false "same"). Entities
     to try in pairs: overloads differing only in a constraint, in a
     `requires` on a template parameter, in ref-qualifier, in a
     template-template parameter's list; a hidden friend against a
     namespace-scope function; a function and a function template of
     one signature; specialisations whose arguments differ only by a
     pack against a non-pack, by a null pointer against 0, by an
     enumerator against its value; unnamed namespaces, unnamed
     enumerations in two namespaces, two unnamed bit-fields, anonymous
     unions at namespace scope and as members; local classes of two
     overloads; the same name in an `extern "C"` block and outside;
     a using-declaration against the entity it names; an alias
     template against its target. The check is mechanical: no two
     units of one digest output share a key (`tests/determinism.rs`
     or a new `tests/keys.rs` asserts it over every source of the pair
     tests: add that test first, it is the net under everything
     else).
2. **Names** (`names.rs`): the display names of the units. They are
   not in any digest but they are what a verify report prints and
   what `expect.txt` lines name. The items WP-032's landed file leaves
   for this file (`spec/landed/digest/WP-032.md`, and the Handback of
   `docs/wp/WP-032.md`); two different units of one output with one
   display name are found by the same sweep as the keys: list them,
   fix the ones that are plain omissions (a missing template argument
   list, a missing signature), report the rest.
3. **`templ::param_object`** has no unit test (WP-029's handback):
   one, in `templ.rs`'s test module, and the pair tests of
   `DeclKind/TemplateParamObject` (two specialisations on class-type
   constant arguments that differ in one member).
4. **`templ.rs` `template_info`**: done by WP-032 (`others` comes
   from the filtered `Walk::redecls`; no source at the pin shows a
   difference, see `spec/landed/digest/WP-032.md`). Nothing to do
   here but keep it in mind when probing item 1.

## Interface

No signature changes. Files you may edit: `keys.rs`, `names.rs`,
`decl.rs` (the header only), the two places in `templ.rs` named above,
`tests/determinism.rs` or a new `tests/keys.rs`, test directories.
Anything else found wrong is reported with a pending test
(`# needs: <area>`), not fixed, unless it is one line in a file no
open package owns; each such line is listed in the handback.

`DeclKind` has 48 rows and most need nothing but a declaration of that
kind on side B that side A lacks, or the kind changed with all else
equal where C++ allows (`CXXMethod` against `Function` cannot be; say
for each row which form the test takes). A `DeclKind` that is not a
unit by itself (`ParmVar`, `AccessSpec`, `Empty`, `Label`,
`UsingShadow`, `IndirectField`, `LifetimeExtendedTemporary`, the
template parameters) is shown through the unit that holds it; one that
is never written (digest §2.2, the table's `Is` column) gets the test
form the table names for it (`equal`), and one that needs a flag
(`ConstevalBlock`, `ContractResultName`) is WP-038's: leave its line.
`ModuleOwnership` and `DeclMisc` `0-module-ownership`: one module
interface unit with no import parses in the runner (`export module
m;`), so `Visible`, `ModulePrivate` (`module :private;`), `Unowned`
and the rest may be reachable without importing; rows that need an
import stay, listed.

## Tests

Per row as the common rules say (`docs/wp/WP-029.md`, rules 5 and 6,
and the second of the three further rules of `docs/wp/WP-034.md`:
every enumeration, flag and optional row fails its test when skipped
and when written as a constant). For `OverloadedOperator` and
`DeclNameKind` a generated pair per row is accepted (a script kept
under `crates/slip_digest/tests/gen/` if one exists already, else the
directories written out), with one table-driven unit test that the
key of `operator<op>` holds the row.

The uniqueness test of item 1 runs over every pair-test source, both
sides, pending tests included, in the normal test time (the gate keeps
`cargo test -p slip_digest` under a minute once built: reuse the
parses if it does not fit, or sample by a fixed rule and say so).
