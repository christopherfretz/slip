# WP-112 — the names digest: name-derived strings a unit only passes on are compared and reported

- Status: in-progress
- Milestone: M1
- Track: C
- Needs: WP-052, WP-070, WP-104, WP-108
- Size: M
- Parallel with: the digest's open area packages, WP-110

## Scope

`spec/digest.md` §9 (as `docs/wp/WP-104.md` leaves it) writes a
name-derived string by value where the program reads it at compile time,
and symbolically where it is only passed on: `__func__` handed to
`__assert_fail`, a `std::source_location` handed to a logger. The
symbolic form says which string of which entity, not what it holds. So
the unit's digest is equal when the string's **content** changes, by a
declared rename and also by anything else that changes what Kiln's
`pretty_function` prints: a parameter type requalified (`f(V)` to
`f(::legacy::V)`, which the namespace migration does to every
requalified function that holds an `assert`), an alias respelled, a
template parameter renamed, an elaborated keyword added.

That is the rule, and it is only honest if every such change is seen by
somebody. This package makes the verifier see it: a second digest per
unit, of the bytes of the name-derived strings the unit holds
symbolically, compared between the images and reported. By default the
report lists the changes and the verdict does not count them; under a
strict option each is a finding.

1. **The walk** (`crates/slip_digest`). Where `docs/wp/WP-104.md`'s code
   writes a name string symbolically, the walk also feeds the string's
   bytes (as Kiln evaluated them) to the unit's **names digest**, in
   the order of the walk, each preceded by what the symbolic form
   holds (kind, field), so that two strings swapped are seen. A unit
   that holds no such string has no names digest. Decide and state:
   - what else of a `std::source_location` object is fed. Proposed:
     `function_name()` only. `line()` and `column()` change with any
     edit above them; reporting them would bury the report. They are
     named in `spec/verify.md` §8 as passed on, not verified and not
     reported. `file_name()` is **not** in that class any more: since
     the fix round of `docs/wp/WP-104.md` the file of a passed-on
     `source_location` object is in the unit's digest by value, exactly
     as `__FILE__` is (`spec/landed/digest/WP-104.md`), so it is
     verified and is not fed here;
   - a string written by value (read at compile time) is not fed: the
     unit's digest already holds it;
   - a string reached twice (a back-reference, `spec/digest.md` §4.3):
     fed once per first writing, as the digest writes it;
   - `typeid(T).name()`: not a constant in Kiln; say what the walk sees
     and whether anything can be fed.
2. **The record.** A new section of a shard of phase `map` and `verify`
   (`spec/model.md` §8: choose the id; the `digests` section and its
   scheme do not change, so **no golden of the map phase moves** except
   by the new section): `names: list<(key: digest, names: digest)>`,
   strictly ascending by key, one entry per unit that has a names
   digest; a key with several units (`spec/verify.md` §3) has one entry
   whose digest is of its units' names digests in the units' order.
   Invariants as rows of the spec, each with a test
   (`spec/landed/edits/WP-061.md` is the model). Present whenever
   `digests` is; may be empty.
3. **The comparison** (`crates/slip_verify/src/compare.rs`, after
   `docs/wp/WP-108.md`). For a key with a names entry in both images
   and different names digests: a **note** `names_changed`, with the
   unit's name and place as any finding has them (`spec/verify.md` §6,
   §6.1). A key with an entry in one image only gives no note (the key
   was added, removed or changed, which other findings say; or the
   string was added to an unchanged unit, which cannot be: the unit's
   digest would differ). Notes are not findings: they do not change an
   observer's verdict, take no exemption and are never in `used`.
   Under the strict option (4) each note is a finding of kind
   `names_changed`, which no exemption prevents.
4. **The run and the report** (`crates/slip_verify/src/run.rs`,
   `spec/verify.md` §7.1; the command line in `crates/slip_cli`):
   - the report gains `names_changed`: the count of units over the run
     (each key once) and the first 100 by the report's order, in JSON
     and in text (`note: name-derived string changed: <name> @
     <place>`);
   - `--strict-names`: notes become findings; the run is `not_verified`
     if there is one;
   - a run without the option and without a note prints nothing new:
     **no M1 golden of the report moves** for a run in which no
     name-derived string changed.
5. **The pairs `docs/wp/WP-104.md` left pending** (`# needs: WP-112`:
   alias in a parameter and in a return type, a template parameter's
   name, an elaborated keyword, a qualifier as written, the
   source-location forms): each becomes a test here: unit digests
   equal, names digests different. The pair-test runner needs a way to
   say so (an `expect.txt` line `names-changed <unit>` in `equal/`
   directories, or what the runner's format allows: decide, and amend
   `spec/digest.md` "Tests"). Beside them: a renamed function under its
   rule (names differ: the string holds the new name), an unrelated
   edit (names equal), a string read at compile time (no names entry,
   units differ).
6. **Is the report usable on a real relocation?** Under a namespace
   rule every function of the moved namespace that holds an `assert`
   changes its string, as declared. Run the comparison over the
   `bench/demo1/` relocation of `llvm/lib/Support` (or, if `slip
   verify` cannot yet run it, over the digests of its pre- and
   post-images in process) and record: how many units have a names
   entry, how many notes, how many of the notes are a change the rules
   do not account for. Then say whether the note should tell the two
   apart (a second names digest computed with the rules' names mapped
   back, so that it is equal exactly when the rules account for the
   whole change) and what that would cost; do not build it.

**Where the package text and WP-115 disagree.**
- Scope says a passed-on string is held symbolically, so the unit is
  equal when its content changes. Item 3 says a string cannot be added
  to an unchanged unit.
- After WP-115, a shared source-location string is written by its bytes
  where its uses span entities. There, the unit digest changes with the
  string: verified, not merely noted.
- The entries fed also change when a string moves between the two
  forms, so a note can appear with no change of the string (always
  beside a `changed`). Both go away with Kiln's `kiln-srcloc-origin`.

stream with its own rule for repeats; following the unit's stream keeps
one rule. Recorded in decision 3.
