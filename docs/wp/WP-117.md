# WP-117 — negative inputs: what the map parse looked for and did not find

- Status: todo
- Milestone: M2
- Track: C
- Needs: WP-052, WP-053
- Size: M
- Parallel with: the transform packages

## Scope

A shard's `inputs` (`spec/model.md` §8) lists every file the map parse
read. Guard O2 of `spec/verify.md` §5.3 uses it: a file outside every
root that both parses read must still have the size and digest the pre
shard gives it. That says nothing of a file the map parse **looked for
and did not find**. The re-check of WP-052 (`spec/landed/verify/WP-052.md`,
F4b) showed the wrong `verified` this leaves:

```
map phase:    -Iext2 -Iext        ext2/ has no cfg.h, ext/cfg.h is read
after it:     ext2/cfg.h appears, and an edit of the post tree compensates
verify:       the post parse reads ext2/cfg.h; O2 compares only files both
              parses read; verdict `verified`
```

The verdict then says the post tree means what the subject meant, and it
does so only in a world the map parse never saw. The pending test is
`crates/slip_cli/tests/verify_job.rs`
`f4b_outside_header_added_after_the_map`.

This package makes the map parse's failed lookups part of the pre shard
and checks them at verify.

1. **What a negative input is.** Each place a lookup tried and where no
   file was found, as `slip_kiln::Lookups::tried` gives it
   (`(directory, name)`), less the places where a file was found. Say,
   form by form, what is covered, with a test each: `#include "…"` (the
   includer's directory, then the list), `#include <…>`,
   `#include_next`, `__has_include` and `__has_include_next` (an answer
   of `false` is all negatives), `#embed` and `__has_embed`, `-include`
   and `-imacros` words of the command, every kind of search directory
   (`-I`, `-iquote`, `-isystem`, `-idirafter`, the toolchain's). An
   absolute name that was not found is a negative with no directory; it
   appears in the log once Kiln's WP-2620 is in the pin, and the test
   for it waits with `# needs: kiln` until then. Anything the front end
   looks for on disk that the log does not hold is named in the landed
   file as not covered, with a finding for Kiln.
2. **The record.** A new optional section of the shard (`spec/model.md`
   §8: its number, its reader rows, its place in the shard's
   determinism rule): the negatives, unique and sorted, each a path
   written as `inputs` writes one (the subject's name for a place under
   a subject root; decide what the path of a place is when its directory
   does not exist or is reached through a symbolic link, and say why two
   hosts with the same tree write the same bytes). The map parse must
   then run with Kiln's lookup log on: **measure** what that costs on
   the three LLVM units used by WP-085 (time, peak memory, entries and
   bytes of the section) and over `llvm/lib/Support` (store growth), and
   record the figures in the landed file. Choose the encoding from the
   figures (a name is tried in every directory before the one that has
   it, so the list is about names times directories: group by directory,
   or front-code). A shard without the section is still a valid shard
   (the parse task of a validation run need not pay for it): say which
   commands write it.
3. **The guard** (`spec/verify.md` §5.3, a new row beside O2; give it a
   name): for the tree form with an image other than the identity, and
   for the overlay form when WP-074 lands,
   - a negative **outside every root** at which a file now exists is a
     drift: the task is `unverifiable` with `pre-image: <path> appeared
     since the map phase` (the first such path, in path order);
   - a negative **under a subject root** is not checked against the
     subject: the post tree stands in its place, a file the transform
     added there is the edit, and the comparison judges it. Show with a
     test that such a file is not refused;
   - the overlay form creates no file, so there every negative must
     still be absent;
   - "exists" is the test Kiln's lookup makes (a dangling symbolic link,
     a directory of that name, a file that cannot be read: state each
     and test it);
   - a pre shard **without** the section, where the guard applies: fail
     closed, `unverifiable` saying the pre shard has no negative inputs.
   The identity image is treated as O2 treats it; say so in one
   sentence. The guard is checked whether or not the comparison finds
   anything, as O2 is.
4. **Other readers of `inputs`.** Find every place that decides from a
   shard's `inputs` that the shard still describes the files on disk
   (the guards of `spec/verify.md` §5.3, anything in `slip_exec` or the
   store that reuses a shard). For each: it takes the negatives too, or
   the landed file says why it need not.
5. **Attack it.** Each a pair in `verify_job.rs` with real parses: the
   case above; a file added in the includer's directory for a quoted
   include found on the list; `__has_include` that was false and is now
   true outside the roots, with an edit that compensates; `#include_next`
   with a file added between the two directories; a directory that did
   not exist at the map phase and exists now with the header in it; a
   file added and removed again before verify (no drift); a name with
   `..` components; two spellings of one directory in the search list;
   a negative whose directory is itself under a post root by another
   route (a symbolic link): which root rule of `image::Resolver`
   applies. A case that is `verified` although a file that appeared
   outside the roots changed what the post parse read is reported with
   its pair.

## Out of scope

A file that appears and is read between the guard and the end of the
post parse (the same window every guard has; `spec/verify.md` §5.1). A
file system that ignores case (named there too).

This package is trusted base: second review. The reviewer's question:
is there a file that can appear outside the roots after the map phase,
change what the post parse reads, and leave the verdict `verified`?
