# WP-144 — owned code that is already in the target namespace before the edit

- Status: review
- Milestone: M1
- Track: C
- Needs: WP-140
- Size: M
- Parallel with: the digest's area packages (one digest branch merges at a time)

## Scope

With `relocate legacy => :: acme`, the keys of the post-image's owned
entities under `acme` are mapped back to `legacy`. An owned `acme::x`
that was there before the edit (new code of the same codebase, written
in the new root while the rest was not yet migrated) is then
`removed acme::x` and `added legacy::x`, and every reference to it
differs with it (`spec/verify.md` §2.1, "A pre-existing entity that a
rule would capture"; `spec/landed/digest/WP-141.md` §9 Q6). Fails
closed, and in a codebase that has both it is a finding on every such
entity. The operator's facts (2026-11-23, in `docs/wp/WP-141.md`) make
this likely in the first real run.

1. **Design; propose and stop for the supervisor.** What a correct
   tool answers for: an owned `acme::x` untouched beside a moved
   `legacy::g`; an owned `acme::x` and a moved `legacy::x` that collide
   (one name, two entities: the post-image does not compile, or
   overloads merge: say which cases reach a verdict); an owned
   `acme::detail` that both the old and the new owned code open; a
   class `legacy::C` whose member is defined out of line in a file that
   was already under `acme`. Options to weigh, with the table and the
   attacks as `spec/landed/digest/WP-140.md` has them:
   - the rule names what it moves by exclusion (`relocate legacy =>
     :: acme` except the entities of a list the transform emits, by
     key);
   - the rule applies to an owned entity of `acme` only if the
     pre-image has no unit of that entity's own key (say what wrong
     equal a compensating edit gets, and whether the pre-image's keys
     are available where the post-image is digested);
   - a third owner: the owned code that was already there is a view of
     its own (WP-140's views by part, three and not two), keyed
     unmapped;
   - one rule per moved entity and no namespace rule (say what it costs
     at a million entities and what happens to members, local entities
     and instantiations).
   Whatever is chosen must keep WP-111's rule (one rule for one target)
   and must not need the user to write text patterns.

   In the same proposal, **what makes a declaration owned**: its
   file's path, or the way the translation unit reached the file.
   WP-141's fixture `views/a4-owned-header-both-ways` pins what the
   ownership machinery does today: an owned header that the unit
   enters first through a read-only includer is treated as read-only,
   so its opening of the namespace falls in the dependency's view.
   Say whether that is right (the header is edited either way; two
   units then disagree about one declaration's view), what a view
   keyed by the declaration's own file gives, and what moves.
2. **Built after the ruling.**

## Handback

### Proposal (Item 1 — awaiting supervisor ruling)

**Short recommendation:**
1. **Part I (Pre-existing owned code in `acme`): Option A** — keep the single namespace rule `relocate legacy => :: acme` (preserving WP-111's "one way to each key" and WP-140/141/143's two-view namespace machinery) and add a sorted, run-wide list of **excluded (`staying`) `KeyId`s** to `Declared` (`DECL` v4 when non-empty; `rules_id` v4 covering `staying`; zero text patterns). Separate **ownership** (`owned(e)`) from **keying view** (`mapped_view(e) = owned(e) && !is_staying(e)`).
2. **Part II (What makes a declaration owned): Policy 1 — keep today's include-chain rule** (`owned.rs::in_owned_file`). `views/a4-owned-header-both-ways` is right to fail closed; dropping the include chain flips 3 WP-110 F2 fixtures, WP-118's `dependency-includes-rebuilt`, and WP-146's S17-through-dependency to wrong `verified`. Reconcile only `ns_refs.rs:563` and `:580` (`read_only_by_path` -> `in_owned_file`/`mapped_view`), keeping `:420` (`whole_reading`) conservative by path.

#### 1. Required semantics for scenarios (a)–(d)
- **(a) Untouched `acme::x` beside moved `legacy::g`:** `equal` (`verified`, with or without `dep.h` opening `acme`); editing/deleting `acme::x` is a finding (`changed`/`removed acme::x`).
- **(b) Colliding `acme::x` and moved `legacy::x`:**
  1. Redefinition / conflicting declaration in 1 TU: `not_parsed` (no verdict).
  2. Compatible merge in 1 TU (forward decl + def; identical typedef): reaches verdict — **finding** (`removed legacy::x` + `changed acme::x`, two pre-image keys cannot match one post-image entity).
  3. Cross-TU ODR collision (`a.cpp` has `acme::x`, `b.cpp` moves `legacy::x` -> `acme::x`): reaches verdict — **finding** (`not_verified`, WP-146 invariant I1).
  4. Overload merge (distinct signatures): reaches verdict — `equal` iff no resolved call / instantiation / dependent found set / `using`-decl changes; otherwise **finding** (`changed` caller / `Ref::views` / `added` shadow).
- **(c) Shared `acme::detail` opened by both old and new owned code:** `equal` (`verified`), producing both namespace units (`acme::detail` and `legacy::detail`) with `acme::detail`'s single digest (WP-140: `[[deprecated]]`/`inline` mismatch across openings stays a finding).
- **(d) Out-of-line member `legacy::C::m` in a file already under `acme` (beside `acme::x`):** `equal` (`verified`) — `C::m` follows `Scope::Unit(C)` -> `legacy::C::m`, while `acme::x` stays under `acme`.

#### 3. Concrete adversarial attacks & Option A mechanics
- **Option B (Pre-image keys) — REJECTED:**
  - *Architectural blocker:* `verify_job.rs` digests post-image before any pre-image parse exists (`verify.reparsed == 0`); map shards hold group sums only (`units: None`). Making pre-image keys available forces 2x parses or ~160 GB map shards.
  - *Attack B1a (cross-TU ODR collision -> wrong `verified`):* `a.cpp` has `acme::x` (unmapped -> `=`); `b.cpp` moves `legacy::x` -> `acme::x` with no pre-image `acme::x` (mapped -> `=`). Zero exemptions -> wrong `verified`.
  - *Attack B1b (compensating `#include` hijack -> wrong `verified`):* `u.cpp` drops `b.h` (`legacy::Tag`) and includes owned `a.h` (`acme::Tag`) while `v.cpp` keeps `a.h`; `u.cpp` maps `a.h`'s `acme::Tag` -> `legacy::Tag` (`=`) while `v.cpp` keeps `acme::Tag` (`=`) -> wrong `verified` merging two distinct types.
  - *Attack B2:* false refusals on concurrent `removed acme::x` / `acme::x => ::top_x` and semi-mapped `acme::x(legacy::S)` -> `acme::x(acme::S)`.
- **Option C (Third owner / third view) — REJECTED:**
  - By file: Attack C1 breaks mixed files (including Scenario (d) `new_file.cpp` holding `acme::x` + out-of-line `C::m`); C2 breaks under multiple rules (`old1 => acme`, `old2 => beta`); C3 breaks cross-file redeclarations; C4 never yields a third key on namespaces (unmapped key = dependency view's key).
  - By entity: collapses into Option A (if in `Declared`) or Option B (if inferred from pre-image).
- **Option D (One rule per moved entity, no namespace rule) — REJECTED:**
  - Scale at 1M entities: ~100–140 MB `DECL`, ~400–450 MB `RuleTable` RAM/worker (3–4M allocs), ~12 GB `rule_use` across 10^5 shards (vs ~3.2 MB flat `Vec<Digest>` for 100k staying keys & 1 `Use`/shard in Option A).
  - Free functions/operators/guides/non-member friends (incl. template-instantiated ones) and block-scope `extern`s are `Scope::Namespace` and all need individual rules.
  - Fatal attacks: D1 `legacy`/`legacy::detail` become `removed` (declaring `removed legacy` hides `[[deprecated]]`/`inline` mismatches -> wrong `verified`); D2 disables `ns_rules()` and breaks WP-140/141/143 redirected `using namespace`/aliases/dependent `legacy::h(t)`/A5; D3 content-keyed decls; D4 unnamed namespaces; D5 loses WP-111 stale detection for missed `#ifdef` entities.
- **Option A (Recommended — run-wide `staying: Vec<Digest>` in `Declared`):**
  - Over-excluding (`acme::g` in `staying`) and under-excluding (`acme::x` omitted) both fail closed.
  - Cross-TU ODR collision / compensating `#include` hijack fail closed (run-wide `staying` enforces WP-146 I1 across all observers).
  - Editing/deleting/resignaturing `acme::x` is caught; chained rules (`legacy => acme` + `acme => modern`) still count owned staying `acme::y` under `direct` for `acme => modern`.
  - Two stated limits (both fail closed, zero wrong `verified`): identical content-keyed decl (`static_assert(true)`) in *both* `acme` and `legacy`; identical-signature TU-local (`static int h()`) in `acme` (TU1) and moved `legacy` (TU2, same limit as WP-111 F3).
  - Mechanics: `options.staying` empty fast-path keeps `scheme = 2` and all existing digests untouched. Compute `name` + semi-mapped `disc` once, binary-search `staying` against unmapped parent chain. Build `ns_table` in 3 monotone phases (1: namespaces — staying ns holds in view `false`; 2: ordinary members; 3: R1/R2-keyed members) so `is_staying` never re-enters `ns_table`. `ns_table`/`ns_holds`/`view_units`/R1 `route`/A5 read `mapped_view`; R2 `whole_reading` and WP-111 `direct` read `owned`. Unused `staying` reported via `RuleUse`.

## Design ruling on item 1 (2026-11-28)

Short form: **1.** Option A is accepted and amended in five places
(the list also needs a per-file form for entities with no identity
across translation units; a listed entity is tested by a key formed
without the namespace table; a namespace's own key follows what it
holds; a namespace may be listed whole; the name is `existing`).
**2.** Policy 1 is accepted; the two `ns_refs.rs` sites are changed as
a commit of their own, with evidence. **3.** `existing`; `(the moved
part of acme)`. **4.** Two pull
requests: the trusted base with its wiring first, `slip declare` and
the report second.

What was checked, and not taken from the proposal: that the walk of
the post-image has no pre-image keys (`spec/verify.md` §4.1, §5.2: the
pre shard holds group sums, and the pre-image is parsed only after the
sums differ), so option B needs data that is not there; that B's
attack B1a is real (it is §9's hole: each observer verifies against
its own pre-image, and nothing joins them); that dropping the include
chain undoes §2.1's "the dependency was compiled against what it
includes"; and that two declarations with one key and one digest are
one unit (`spec/digest.md` §3.3, §3.4), which is what makes
amendment 1 necessary. The proposal's cost figures for B and D were
not checked; the ruling does not rest on them (B is rejected for B1a,
D for the namespace's own unit and for `ns_rules`).

### 1. Part I: option A, amended

**Why A.** Slip's model is that the declared changes choose which
isomorphism is tried and the comparison checks it (§2.1, "Why applying
rules to the post-image is sound"). "These entities were already
here" is a declared change of that kind: whatever the list says, the
keys are a function of the post-image and the `DECL`, the same
function in every observer, and a wrong entry in either direction
moves a key away from the pre-image's (a finding). B infers the same
fact per observer and so cannot be the same function in every
observer. C cannot tell two declarations of one file apart. D gives up
the namespace's unit. A stays.

**Amendment 1: entities with no identity across translation units are
listed with their file.** A run-wide list of keys is right exactly
where a key names one entity of the program. It is wrong for an entity
that each translation unit has for itself: `acme::(anonymous
namespace)::helper()` in `new.cpp` (existing) and `legacy::(anonymous
namespace)::helper()` in `old.cpp` (moved) are two correct entities
with one post-image key, and under the proposal `old.cpp` is a
mismatch that no declaration can remove. The proposal states it as a
limit (e5, e6). At the operator's scale, with owned code in both
roots, it is the common path: every `static` helper, unnamed-namespace
member, namespace-scope `const`, and `using std::string;` whose name
occurs under both roots. So:

- An entity is **program-wide** if WP-146's lists would take it
  (`own_lists.rs` `candidate`, less its deduction-guide clause: not of
  a `units::repeatable` kind, not of internal linkage by
  `Ast::linkage`, not in or under an unnamed namespace; a linkage the
  walk cannot read is program-wide). Every other entity that is not a
  namespace is **local**. One predicate, shared with `own_lists.rs`,
  not written twice. Typedefs and aliases are program-wide, as WP-146
  ruling 4 has them.
- A program-wide entity is listed by its key. A local entity is listed
  by its key **and the subject path of the file a declaration of it
  lies in** (its expansion location's file), once per such file.
- A key entry never makes a local entity existing, and a file entry
  never makes a program-wide entity existing. The second half is
  soundness: a per-file answer for an entity with external linkage is
  option B again (B1a). The first half only fails closed, and keeps
  one meaning per entry.

**Amendment 2: the key an entry is compared with is formed without
the namespace table.** `ns_table` needs every member's view, a
member's view needs "is it listed", and that needs the member's key,
whose discriminator may write a namespace by its views (a
using-declaration's scope, a using-directive's target, a
`decltype(acme::h(t))` in a signature, a qualified concept-id in a
template head): through the table. The proposal's three phases do not
say what a phase 3 member reads of the other phase 3 members (two
using-declarations in two namespaces, each naming the other), so its
answer can depend on order. Instead:

- The **probe key** `U(e)` of an owned entity `e` whose key's parent
  is a namespace is its key formed as a dependency entity's: namespace
  parents in the dependency view, no rule applied to its own key
  (WP-146's `post_key` formation), **in probe writing**. In probe
  writing a namespace named (to find members, or whole) is written by
  its dependency-view key, R1 and R2 are not consulted, and an entity
  mentioned is written by its own key formed in probe writing (mapped
  or not by its own `mapped`, below). No probe reads `ns_table`, and
  none reads a namespace's own key: a parent namespace is keyed in the
  member's view directly.
- Probe keys are a second memo. A key in whose formation no namespace
  was written (tracked through the keys it read) has the same name and
  discriminator in both writings; the implementer may reuse them, and
  only then.
- A probe that cannot be formed (a cycle, the depth limit, a cause)
  answers "not existing" and is not memoised if an abort happened, as
  keys are.
- When the list is right and no reference in the entity's key was
  redirected, `U(e)` is the entity's pre-image key (§2: "every `KeyId`
  is in the key space of the pre-image"), so a generator needs the
  pre-images only. Its final key is formed as any dependency entity's
  is, with R1 and R2; where that differs from the pre-image's it is a
  finding.

**Amendment 3: a namespace's own key follows what it holds.** An
owned namespace that holds an existing member was a namespace of the
pre-image under its own name. Keying its own unit mapped (the
proposal) makes every untouched reference to it from existing code
(`using namespace acme;`, `namespace A = acme;`) differ in an observer
where no dependency opens `acme`, and makes a namespace whose every
member is listed an `added legacy::…`. So its own view is the
dependency view, as for a namespace a dependency opens, and the moved
members give it the view unit.

**Amendment 4: a namespace may be listed whole.** A named namespace
whose probe key is in the list is existing with everything keyed
under it, at every depth. This is what a person writes for a
component that was born in the new root (`existing acme::newlib`), it
costs one entry, and it needs no enumeration. A namespace that both
roots had (`acme::detail`) is not listed; its existing members are.

**The mechanism.**

*Data* (`slip_model`, `Declared`):

```
existing:       list<KeyId>            program-wide entities and whole namespaces; strictly ascending
existing_local: list<ExistingLocal>    strictly ascending by (key, file)
ExistingLocal := key: KeyId, file: bytes   a canonical absolute subject path, as an `Ownership` entry is
```

*Format.* `DECL` version 4 exactly when either list is not empty:
version 3's record (with `rebuilt`, which may then be empty) followed
by the two lists; JSON members `"existing"` and `"existing_local"`
(`[{"key": …, "file": …}]`). A writer writes version 2 or 3 otherwise,
byte for byte as today. `rules_id` is `H("slip.rules.v4", rules,
owned, readonly, rebuilt, existing, existing_local)` exactly when
either list is not empty, else as today. Reader's checks, after row 4
and before row 5, each with a test in `slip_model/tests/declared.rs`:
`existing is not strictly ascending`; `existing_local is not strictly
ascending`; `not a canonical absolute path` (at the entry's `file`);
`a version 4 container has no existing entry`; `a version 2 container
has an existing entry` and the same for 3 (a value in memory);
`existing without a namespace rule` (no rule of kind `namespace`: the
lists then say nothing, and a second encoding of one meaning is
refused, as `files without a rule` is). `a version 3 container has no
rebuilt entry` stays version 3's alone.

*The walk* (`slip_digest`; `Options` gets the two lists, borrowed, and
every caller that walks under a table that is not empty passes them:
the verify job, `records`, `query.rs`, `spelling.rs`; no default at a
call site). With both lists empty nothing below is read and no byte
changes; `scheme` stays 2 (a list is covered by `rules_id` and the
`DECL`'s content id in the binding, and the pre shard is walked under
no rule).

- `listed(n)`, for an owned namespace `n`: `U(n)` is in `existing`, or
  the namespace it is keyed under is listed. An unnamed namespace is
  listed only through a namespace around it.
- `existing(e)`, for an owned entity `e` that is not a namespace and
  whose key's parent is a namespace `n`: `listed(n)`; or `e` is
  program-wide and `U(e)` is in `existing`; or `e` is local and
  `(U(e), file(d))` is in `existing_local` for **every** declaration
  `d` of `e` (a declaration in no file: not existing). Every other
  entity (a class member, a specialisation, a member of an
  instantiation, a local entity, a part, an entity with C language
  linkage) is not asked: it follows the key it is keyed under.
- `mapped(e) := owned(e) && !existing(e)`, memoised once per entity.
  **Rule 1 and rule 2 of §2.1 read `mapped` where they read `owned`**:
  `rule_applies`, the view in `namespace_parent`, the member's view in
  `ns_table`, R1's `route`, `key_namespace`'s readers. An existing
  entity is keyed exactly as a dependency entity is; no rule applies
  to its own key either.
- Everything that asks who may write reads `owned`, unchanged:
  `decide_owned`, `only_by_inclusion`, `records::facts`, the rebuilt
  accounting, and the counts of §9.2. An existing entity is a member
  for a namespace rule's counts, with its chain climbed in the
  dependency view as `only_by_inclusion`'s is: it is never `via`, and
  it is `direct` for a rule that produces a level of its chain unless
  kept (so under `legacy => acme` and `acme => modern` an existing
  `acme::y` that was left counts for the second rule, rightly).
  WP-146's lists read the view a key was formed under
  (`OwnedState::keyed`), so an existing entity is `fixed` as a
  dependency entity is; nothing there changes.
- `ns_table`: `NsInfo` gets `stays` (it is listed, or it holds an
  existing member, or a nested namespace that stays) and its own view:
  an owned namespace's own view is the owned (mapped) view unless it
  stays. A listed namespace holds in the dependency view even when
  empty, as a read-only opening does. `member` and `holds` are by
  view, with `mapped(e)` as the member's view. The table is made in
  two passes that never re-enter it: the namespaces (`owned`,
  `listed`, from chains alone), then the members (probes). Every
  reader of `NsInfo.owned` as "the namespace's own view" (`key` of a
  namespace through `rule_applies`, `ns_view_key`, `ns_view_keys`,
  `whole_reading`'s `Part`, `view_units`) reads the own view.
- `view_units` is otherwise WP-140's: the other view's unit is written
  when that view holds something and its key differs.

*`slip declare`* (outside the trusted base): `existing <entity>`,
resolved in the pre-images with no rules, as `changed` is. A
namespace gives one key (whole). A program-wide entity gives its key.
A local entity gives one `existing_local` entry per file a pre-image
record of it lies in (`Record` gets the files of a local unit's
declarations). Errors: `DependencyEntity` (it is one in a selected
observer); `Refused` for a namespace that a `relocate` line's rule
matches (the target itself listed whole says nothing moves);
`Duplicate`. A line that enumerates the owned members of a namespace
from the pre-images is not in this package (below).

*Reporting.* Section **34, `existing_use`**, in an `ok` shard of
phase `verify`, written only when not empty: `existing: list<uv>`,
`local: list<uv>`, the indices of the entries some entity matched,
strictly ascending. An entry no folded observer matched is listed in
the report like a `kept` key with 0 observers and changes no verdict.
`rule_use` (29) is not touched.

**The scenarios.**

### 3. Wording (provisional; the operator's to reword)
