# WP-144 — owned code that is already in the target namespace before the edit

- Status: in-progress
- Milestone: M1
- Track: C
- Needs: WP-140
- Size: M
- Parallel with: the digest's area packages (one digest branch merges at a time)

## Scope

With `relocate legacy => :: acme`, the keys of the post-image's owned
entities under `acme` are mapped back to `legacy`. An owned `acme::x`
that was there before the edit (new code of the same codebase, written
in the new root while the rest was not yet migrated) is then
`removed acme::x` and `added legacy::x`, and every reference to it
differs with it (`spec/verify.md` §2.1, "A pre-existing entity that a
rule would capture"; `spec/landed/digest/WP-141.md` §9 Q6). Fails
closed, and in a codebase that has both it is a finding on every such
entity. The operator's facts (2026-11-23, in `docs/wp/WP-141.md`) make
this likely in the first real run.

1. **Design; propose and stop for the supervisor.** What a correct
   tool answers for: an owned `acme::x` untouched beside a moved
   `legacy::g`; an owned `acme::x` and a moved `legacy::x` that collide
   (one name, two entities: the post-image does not compile, or
   overloads merge: say which cases reach a verdict); an owned
   `acme::detail` that both the old and the new owned code open; a
   class `legacy::C` whose member is defined out of line in a file that
   was already under `acme`. Options to weigh, with the table and the
   attacks as `spec/landed/digest/WP-140.md` has them:
   - the rule names what it moves by exclusion (`relocate legacy =>
     :: acme` except the entities of a list the transform emits, by
     key);
   - the rule applies to an owned entity of `acme` only if the
     pre-image has no unit of that entity's own key (say what wrong
     equal a compensating edit gets, and whether the pre-image's keys
     are available where the post-image is digested);
   - a third owner: the owned code that was already there is a view of
     its own (WP-140's views by part, three and not two), keyed
     unmapped;
   - one rule per moved entity and no namespace rule (say what it costs
     at a million entities and what happens to members, local entities
     and instantiations).
   Whatever is chosen must keep WP-111's rule (one rule for one target)
   and must not need the user to write text patterns.

   In the same proposal, **what makes a declaration owned**: its
   file's path, or the way the translation unit reached the file.
   WP-141's fixture `views/a4-owned-header-both-ways` pins what the
   ownership machinery does today: an owned header that the unit
   enters first through a read-only includer is treated as read-only,
   so its opening of the namespace falls in the dependency's view.
   Say whether that is right (the header is edited either way; two
   units then disagree about one declaration's view), what a view
   keyed by the declaration's own file gives, and what moves.
2. **Built after the ruling.**

## Handback

### Proposal (Item 1 — awaiting supervisor ruling)

**Short recommendation:**
1. **Part I (Pre-existing owned code in `acme`): Option A** — keep the single namespace rule `relocate legacy => :: acme` (preserving WP-111's "one way to each key" and WP-140/141/143's two-view namespace machinery) and add a sorted, run-wide list of **excluded (`staying`) `KeyId`s** to `Declared` (`DECL` v4 when non-empty; `rules_id` v4 covering `staying`; zero text patterns). Separate **ownership** (`owned(e)`) from **keying view** (`mapped_view(e) = owned(e) && !is_staying(e)`).
2. **Part II (What makes a declaration owned): Policy 1 — keep today's include-chain rule** (`owned.rs::in_owned_file`). `views/a4-owned-header-both-ways` is right to fail closed; dropping the include chain flips 3 WP-110 F2 fixtures, WP-118's `dependency-includes-rebuilt`, and WP-146's S17-through-dependency to wrong `verified`. Reconcile only `ns_refs.rs:563` and `:580` (`read_only_by_path` -> `in_owned_file`/`mapped_view`), keeping `:420` (`whole_reading`) conservative by path.

#### 1. Required semantics for scenarios (a)–(d)
- **(a) Untouched `acme::x` beside moved `legacy::g`:** `equal` (`verified`, with or without `dep.h` opening `acme`); editing/deleting `acme::x` is a finding (`changed`/`removed acme::x`).
- **(b) Colliding `acme::x` and moved `legacy::x`:**
  1. Redefinition / conflicting declaration in 1 TU: `not_parsed` (no verdict).
  2. Compatible merge in 1 TU (forward decl + def; identical typedef): reaches verdict — **finding** (`removed legacy::x` + `changed acme::x`, two pre-image keys cannot match one post-image entity).
  3. Cross-TU ODR collision (`a.cpp` has `acme::x`, `b.cpp` moves `legacy::x` -> `acme::x`): reaches verdict — **finding** (`not_verified`, WP-146 invariant I1).
  4. Overload merge (distinct signatures): reaches verdict — `equal` iff no resolved call / instantiation / dependent found set / `using`-decl changes; otherwise **finding** (`changed` caller / `Ref::views` / `added` shadow).
- **(c) Shared `acme::detail` opened by both old and new owned code:** `equal` (`verified`), producing both namespace units (`acme::detail` and `legacy::detail`) with `acme::detail`'s single digest (WP-140: `[[deprecated]]`/`inline` mismatch across openings stays a finding).
- **(d) Out-of-line member `legacy::C::m` in a file already under `acme` (beside `acme::x`):** `equal` (`verified`) — `C::m` follows `Scope::Unit(C)` -> `legacy::C::m`, while `acme::x` stays under `acme`.

#### 3. Concrete adversarial attacks & Option A mechanics
- **Option B (Pre-image keys) — REJECTED:**
  - *Architectural blocker:* `verify_job.rs` digests post-image before any pre-image parse exists (`verify.reparsed == 0`); map shards hold group sums only (`units: None`). Making pre-image keys available forces 2x parses or ~160 GB map shards.
  - *Attack B1a (cross-TU ODR collision -> wrong `verified`):* `a.cpp` has `acme::x` (unmapped -> `=`); `b.cpp` moves `legacy::x` -> `acme::x` with no pre-image `acme::x` (mapped -> `=`). Zero exemptions -> wrong `verified`.
  - *Attack B1b (compensating `#include` hijack -> wrong `verified`):* `u.cpp` drops `b.h` (`legacy::Tag`) and includes owned `a.h` (`acme::Tag`) while `v.cpp` keeps `a.h`; `u.cpp` maps `a.h`'s `acme::Tag` -> `legacy::Tag` (`=`) while `v.cpp` keeps `acme::Tag` (`=`) -> wrong `verified` merging two distinct types.
  - *Attack B2:* false refusals on concurrent `removed acme::x` / `acme::x => ::top_x` and semi-mapped `acme::x(legacy::S)` -> `acme::x(acme::S)`.
- **Option C (Third owner / third view) — REJECTED:**
  - By file: Attack C1 breaks mixed files (including Scenario (d) `new_file.cpp` holding `acme::x` + out-of-line `C::m`); C2 breaks under multiple rules (`old1 => acme`, `old2 => beta`); C3 breaks cross-file redeclarations; C4 never yields a third key on namespaces (unmapped key = dependency view's key).
  - By entity: collapses into Option A (if in `Declared`) or Option B (if inferred from pre-image).
- **Option D (One rule per moved entity, no namespace rule) — REJECTED:**
  - Scale at 1M entities: ~100–140 MB `DECL`, ~400–450 MB `RuleTable` RAM/worker (3–4M allocs), ~12 GB `rule_use` across 10^5 shards (vs ~3.2 MB flat `Vec<Digest>` for 100k staying keys & 1 `Use`/shard in Option A).
  - Free functions/operators/guides/non-member friends (incl. template-instantiated ones) and block-scope `extern`s are `Scope::Namespace` and all need individual rules.
  - Fatal attacks: D1 `legacy`/`legacy::detail` become `removed` (declaring `removed legacy` hides `[[deprecated]]`/`inline` mismatches -> wrong `verified`); D2 disables `ns_rules()` and breaks WP-140/141/143 redirected `using namespace`/aliases/dependent `legacy::h(t)`/A5; D3 content-keyed decls; D4 unnamed namespaces; D5 loses WP-111 stale detection for missed `#ifdef` entities.
- **Option A (Recommended — run-wide `staying: Vec<Digest>` in `Declared`):**
  - Over-excluding (`acme::g` in `staying`) and under-excluding (`acme::x` omitted) both fail closed.
  - Cross-TU ODR collision / compensating `#include` hijack fail closed (run-wide `staying` enforces WP-146 I1 across all observers).
  - Editing/deleting/resignaturing `acme::x` is caught; chained rules (`legacy => acme` + `acme => modern`) still count owned staying `acme::y` under `direct` for `acme => modern`.
  - Two stated limits (both fail closed, zero wrong `verified`): identical content-keyed decl (`static_assert(true)`) in *both* `acme` and `legacy`; identical-signature TU-local (`static int h()`) in `acme` (TU1) and moved `legacy` (TU2, same limit as WP-111 F3).
  - Mechanics: `options.staying` empty fast-path keeps `scheme = 2` and all existing digests untouched. Compute `name` + semi-mapped `disc` once, binary-search `staying` against unmapped parent chain. Build `ns_table` in 3 monotone phases (1: namespaces — staying ns holds in view `false`; 2: ordinary members; 3: R1/R2-keyed members) so `is_staying` never re-enters `ns_table`. `ns_table`/`ns_holds`/`view_units`/R1 `route`/A5 read `mapped_view`; R2 `whole_reading` and WP-111 `direct` read `owned`. Unused `staying` reported via `RuleUse`.
