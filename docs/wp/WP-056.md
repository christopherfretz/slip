**Waits for** WP-053 (the runner drives `slip parse`, `slip declare` and

## Scope

`spec/pitfalls.md` §1 (rewritten): the form of a row, the runner, the
outcomes, the production-compiler check, the summary.

1. **The runner**, `crates/slip_cli/tests/pitfalls.rs`: reading a row
   (`expect.txt`, the trees, `declared.txt`, `dep/`), the one-entry
   database per subject, the `slip` commands, the report, the outcome
   per tree, the catalogue against the directories, the summary, and
   the one switch for places: `const PLACES: Places`, `Places::{Advisory,
   Mandatory}` (`spec/pitfalls.md` §1 "Places").
2. **The runner's own tests**, in the same file, on rows written to a
   temporary directory (`spec/pitfalls.md` "Tests").
3. **Tier T2**: every subject and tree through `clang++-19`, else
   `clang++`; `SKIP` without one; `ERROR` under `SLIP_REQUIRE_ALL=1`.
4. **The first run and its triage** (below).

Files you own: `crates/slip_cli/tests/pitfalls.rs`,
`spec/landed/pitfalls/WP-056.md`, and, from here on, the rows'
`expect.txt` files under `crates/slip_verify/tests/pitfalls/` (WP-057 and
WP-058 have merged): you add `xfail` lines, and you correct a row only
as the triage below allows.

## Interface

`spec/pitfalls.md` §1 is the interface: the layout, the grammar of
`expect.txt`, the table of outcomes, the summary lines. The runner is a
test, not a library: nothing calls it.

- The executable is `env!("CARGO_BIN_EXE_slip")`. Each row gets a
  directory of its own under the test's temporary directory with the
  database, a store, and the declared files and reports; the row's
  directories in the repository are read, never written. Trees are used
  where they lie (`--root <row>/pre --post <row>/bad`): the image's roots
  are real paths, and the repository's path is not written anywhere.
- The rows run on a few threads; each `slip` is given `-j 1`, so the
  suite takes one token of the host's jobserver per thread at most
  (`spec/harness.md` §5).
- A finding's place is compared after the report's path is made relative
  to the tree (post side) or to the subject (pre side).

## Done when

- The full gate passes with `origin/main` merged in, with the runner in
  it (`cargo test -p slip_cli --test pitfalls`), and the summary lines
  are in the handback.
- **Triage.** Every tree that is not `PASS` at the first run is one of:
  - **the walk is not finished**: the tree's findings are all
    indeterminate, or a `good` tree is `mismatch` with
    `indeterminate_only`. `xfail <tree>: <area or package>` with the
    cause text the report gives (`pending stmt`, `pending expr`, …).
    Expected for most rows until the digest's wave 3 is on main: at
    your base every statement may still be pending
    (`crates/slip_digest/src/stmt.rs:11` before WP-034);
  - **a place that is wrong** (only once findings have a `where`): the
    finding is there, at another file or line. Either the row's line
    number is wrong (correct the row) or localisation is (`xfail
    <tree>: place, <one line>`, and a follow-up in the handback with
    the two sites). A place that is merely absent needs no line in the
    `advisory` state;
  - **the row is wrong**: clang rejects a tree that should compile, the
    edit is not the hazard the table describes, the expected entity's
    name is not what Slip prints. Correct the row, with the reason in
    the commit; a change to what the *table* of `spec/pitfalls.md` says
    the wrong edit gives is handed back, not made;
  - **Kiln and clang disagree**: `xfail`, and the two diagnostics in the
    handback for a report to Kiln;
  - **a defect of `slip_digest` or `slip_verify`**: a `bad` tree whose
    determinate findings do not include the expected one, or a `good`
    tree with a determinate finding. `xfail <tree>: <one line>`, and a
    follow-up in the handback with the row, the finding groups and the
    two unit digests.
- **A `bad` tree that verifies** is none of those. Stop, hand back with
  the row and the report; the package does not merge with one and no
  `xfail` covers it (`spec/pitfalls.md` §1).
- **The state of `PLACES` this package lands in** is decided at its
  gate, with `origin/main` merged in: `mandatory` if WP-054 is on main,
  else `advisory`. The handback says which, with the summary's `places`
  line. Landed `advisory`, the switch is WP-054's to set (a named edit
  of `docs/wp/WP-054.md`); M1's exit needs `mandatory`.
- `spec/landed/pitfalls/WP-056.md` has the table of rows by outcome and,
  for each `xfail`, its reason: this is the list M1's exit needs empty
  (`docs/design/06-engineering-plan.md` §5).

## Out of scope

Writing rows (WP-057, WP-058); fixing the walk or the comparison;
rows with several translation units, configurations or macros beyond the
catalogue (`spec/pitfalls.md` "Open questions"); running the rows in
process.
