# WP-118 — a third class of file: not edited, and rebuilt from source

- Status: in-progress
- Milestone: M2
- Track: C
- Needs: WP-110, WP-111
- Size: L
- Parallel with: the transform packages

## Design

The design is `spec/landed/verify/WP-118.md` (rulings R1 to R8, the
table of every sentence of `spec/verify.md` §2.1, the spec text to land,
the tests, the mutations, the limits). It decides what "Scope" below
leaves open, and where the two differ the landed file is the package.
Nothing of it is built. What it changes in this package's scope:

- **No default** (item 1): the compilation database's directories are
  not rebuilt unless given with `--rebuilt`. The hint line names a
  file, never a directory, and appears only for a read-only file no
  entry covers, under the observer's command's `directory`, that cut an
  include chain in an observer that did not verify (R1.3). A run that
  declares nothing rebuilt keeps every container, id, digest, key and
  verdict; its verify shards and report change only where a hint exists.
- **One exception to "counts as owned"** (item 3): an entity with C
  language linkage declared in a rebuilt file is a dependency entity:
  a declaration of one that lies in a rebuilt file lies in a read-only
  file (R2.2).
- **The overlay form holds no regenerated file** (item 4, the second
  choice). A new guard, **RB**, makes an observer `unverifiable` when a
  rebuilt file the image cannot change (any rebuilt file in the overlay
  form, one under no root in the tree form) still declares an entity
  under the name a rule says was left (R6.3); a second, **O3**, refuses
  an overlay that names a rebuilt path. A build directory beside the
  source is a second pair of roots, which the image already has.
  Regenerated files given with an overlay are `docs/wp/WP-165.md`,
  which comes before any transform-driven namespace migration over
  generated files that open the namespace.
- **The refusal is a `Reason`, not a `Cause`** (item 2): `rebuilt = 13`
  (12 stays unlisted), refused as `site_refused`; no new cause, no new
  subject flag, and `EDTS` keeps its version. The native rename is
  refused when a name of its subject is in a rebuilt file, with a count
  per file; a script's `replace` there throws `not_editable` (R7).
- **Containers** (item 1): `TRFM` and `DECL` version 3, written exactly
  when the `rebuilt` list is not empty, so a run that declares nothing
  rebuilt keeps every byte and id (R5.4). A rebuilt entry `/` is
  refused. A new shard section, 33 `rebuilt_use` (R6.4).
- **More files than "Interface" lists**: `Ownership` gains a field, so
  every place that builds one changes mechanically; `slip_kiln::Sites`
  answers the new reason; `slip_apply` validates the third list;
  `slip_reduce` gets the reason's row.
- **The pair for every case** (Tests) is a second run the rules runner
  makes of each case with a `readonly.txt`, not a second directory.
- The design had an independent review and one fix round; the landed
  file's "Review answers" lists every finding and what was done.
- `docs/wp/WP-116.md` already has item 5's sentence in its "Out of
  scope"; nothing is added there, and the test is pending.

## Scope

`spec/edits.md` §2.1 has two classes of file. An **owned** file may be
edited, and `docs/wp/WP-110.md` lets a rule rename the entities declared
in one. Every other file is **read-only**: it is not edited, and its
entities keep their names, because a binary the run cannot see may hold
them. "Generated files in a build tree" are listed there as read-only.
That is right for the first half and wrong for the second: a file the
build writes and compiles with the rest is not edited by Slip, but **no
binary outside the run holds its names**. Treating it as a dependency
makes a correct migration fail, in the safe direction, in two common
shapes:

- **Glue the build writes.** A precompiled-header file
  (`cmake_pch.hxx`) or a unity-build main file (`unity_0_cxx.cxx`)
  holds nothing but `#include`s of owned files. Under WP-110's
  include-chain rule everything it includes is read-only for that
  observer, so no rule renames anything in it (the re-check of WP-110,
  `spec/landed/digest/WP-110.md`; the rules case that pins it).
- **Generated declarations.** A header written by a generator
  (TableGen's `.inc` files in LLVM, protobuf, a configured `config.h`)
  declares entities inside the namespaces being moved, or is included
  inside an owned class or namespace. The names in it follow the
  generator's input, which the user changes with the migration; the
  regenerated file declares the moved names; today the rule does not
  rename them and every observer that includes the file differs.

This package adds the class **rebuilt**: *not edited by Slip, and
compiled from source in every binary that holds its names*. It is the
user's statement about a path, like `owned` and `readonly`, and every
run that relied on it says so.

1. **The class** (`spec/edits.md` §2.1, `slip_model::transform::Ownership`):
   a third list, `rebuilt`, with the rules of the other two (canonical
   real paths; the longest covering entry decides; an entry in two lists
   is an error). Decide the container changes (`TREQ`, `DECL`: a new
   scheme or a new optional field; `rules_id` and the request's id must
   change when the list does) and the command-line words
   (`--rebuilt <path>` beside `--owned` and `--readonly`, `slip declare`
   and the transform commands). Nothing is detected: a path is rebuilt
   only when the user says so. But where a run can see the likely case,
   it **says so**: an observer whose main file, or a file on an include
   chain, is read-only and lies under the compilation database's build
   directory gets one line in the report naming the file and the word
   to pass. State exactly when that line appears.
2. **Edits** (`spec/edits.md`): a rebuilt file is not edited. A claim in
   one is refused with a cause of its own (not `read_only`: the report
   must be able to say "regenerate these", which is an instruction, and
   "a dependency names this", which is a stop). The native rename
   reports, per rebuilt file, how many names it would have renamed
   (`docs/wp/WP-071.md`'s report; coordinate through the handback if
   that code is not yours to edit). `is_editable` is false.
3. **Ownership of entities** (`spec/verify.md` §2.1, `crates/slip_digest/src/owned.rs`):
   - a declaration in a rebuilt file is **not** a reason for its entity
     to be a dependency entity: for the rules a rebuilt file counts as
     owned;
   - a rebuilt file on an include chain does not make what it includes
     read-only, and a name token spelled in a rebuilt file's macro body
     is not a dependency's;
   - a rebuilt file entered through a read-only file is read-only, as
     an owned one is.
   Go through every sentence of §2.1 that says "owned file" or
   "read-only file" and say which the rebuilt class is for it; the
   landed file has that table.
4. **The post-image of a rebuilt file.** Slip writes no edit there, so
   the post-image has what the build regenerated, and only the user's
   build can make that.
   - **Tree form** (`spec/verify.md` §5.1): the post tree holds the
     regenerated file; nothing new, but show it end to end (a generated
     header declaring a moved entity; the regenerated one; `verified`),
     and the two failures: the file not regenerated (the observer
     differs, and the report's reason names the rebuilt file and the
     entity it still declares under the old name), and a regenerated
     file that changed something else (a difference like any other).
   - **Overlay form** (`docs/wp/WP-074.md`): an overlay names only files
     an edit set changed. Decide and specify how regenerated content is
     given (entries of the overlay supplied by the user for rebuilt
     paths only, checked against the class: an entry for an owned or
     read-only file from the user is an `Input` error), or that a run
     whose rules rename an entity declared or named in a rebuilt file
     is `unverifiable` in the overlay form and must use the tree form.
     Say which and why; the second is acceptable if the first cannot be
     made safe in this package.
   - A rebuilt file outside every root of the tree form (a build
     directory beside the source tree): the image has roots, the build
     directory is another one. Read `image::Resolver` and say how a
     second pair of roots is given, or what is refused.
5. **What a dependency's binary holds** (`docs/wp/WP-116.md`): a
   definition written in a rebuilt file counts as "defined in owned
   code" for its check (it is compiled in the run). If WP-116 has not
   landed, leave the sentence in its package file's "Added after"
   section and the test pending.
6. **The report**: every run lists the `rebuilt` entries it relied on
   (an entry is relied on when a file it covers was read by a selected
   observer and a rule renamed an entity declared in it or seen through
   it), beside the assertions of WP-116. An entry no observer relied on
   is reported like an unused rule.
7. **Attack it.** The statement "no binary outside the run holds its
   names" is the user's; what Slip must not do is make it wider than
   the user said. Each a pair: a `rebuilt` entry that covers a
   dependency's installed header by a longer-entry mistake (must be an
   error or a `readonly` win, by the longest-entry rule: show it); a
   symbolic link from a rebuilt directory to a read-only file (the real
   path decides); a rebuilt file that includes a read-only file that
   includes an owned one (read-only wins on the chain); a read-only
   file that includes a rebuilt one; a rebuilt file that declares
   `extern "C"` names (a rule cannot rename them: `docs/wp/WP-111.md`);
   a rebuilt header also installed and used by a dependency's sources
   that are in the run as read-only observers (two observers disagree:
   which check reports it); unity and precompiled-header observers
   mixed with ordinary ones over the same headers (the same entity must
   get the same key in both).

## Done when

The full gate passes with `main` merged in; WP-110's pending or
differing cases for build-generated includers are equal with the file
declared rebuilt and unchanged without; the landed file has the table
of item 3 and the decision of item 4.

## Out of scope

Running the user's generator or build (Slip never does). Detecting
generated files. A header-only dependency the user wants renamed with
the code: that is `owned` or `rebuilt` by the user's word, nothing new.

This package is trusted base: second review. The reviewer's question:
is there a file the user did not declare rebuilt whose entities a rule
now renames, or an edit written into a file that is not owned?
