# WP-146 — ownership agreed between observers

- Track: C
- Needs: WP-140

## Scope

An entity is owned when every declaration of it **that the observer
sees** lies in an owned file (`spec/verify.md` §2.1). Two observers can
therefore disagree about one entity, and a run in which each is
consistent with itself verifies an edit that broke the program. The
review of WP-140 showed it (it predates that package):

```cpp
// dep/d.h, read-only: the dependency's binary calls it
namespace old { int hook(int); }
// u1.cpp, owned; does not include d.h         after
namespace old { int hook(int x) { return x; } }   // namespace fresh { int hook(int x) { return x; } }
// u0.cpp, owned, unchanged
#include "dep/d.h"
int r = old::hook(1);
```

`relocate old => :: fresh`: in `u1` the function is owned, the rule maps
`fresh::hook` back to `old::hook`, equal. In `u0` it is a dependency's
entity, untouched, equal. The run is `verified`; the program does not
link. In one observer that sees both, the two collide and the unit is
indeterminate: the defect is only between observers. A codebase that
defines the hooks, callbacks, allocator overrides and `extern`
variables its dependencies declare has this shape wherever a
definition's file does not include the dependency's header.

The sibling case from WP-141's build
(`crates/slip_digest/tests/rules/views/a4-owned-header-both-ways` on
its branch): a file's ownership is decided by how the observer entered
it, so an owned header reached first through a read-only includer is
read-only in that observer and owned in another. `docs/wp/WP-144.md`
asks that question for its own case; the answer is one rule, given
here, and WP-144 builds on it.

What is true of the program: an entity is one thing in every
translation unit. A rule may map it only if it is owned in the whole
run, and "owned in the whole run" is a fact no single observer has.

1. **Design; propose and stop for the supervisor before building.**
   Inventory first: every place where a digest, a key, a count or a
   verdict depends on `Walk::owned` or `in_owned_file`, and for each
   whether two observers of one image can differ in it, with a pair of
   sources that shows it (the pair above; a class the dependency
   forward-declares and owned code defines; a variable a dependency
   declares `extern`; a function template an owned file defines and a
   dependency declares; a namespace, which merges by rule and is not
   the same case; an inline function defined in an owned header that a
   dependency header also declares; a specialisation of a dependency's
   template; a friend declared in a dependency's class and defined by
   owned code; `a4-owned-header-both-ways`). Then for each of these
   ways out, a table of cases × answers, the attacks, the cost, and
   what moves (shard sections, `scheme`, goldens):
   - **Detect across observers.** A unit says whether a rule made its
     key (one bit, or the rule's index). Each observer also reports the
     keys of its units that no rule made and that lie where a rule's
     product could lie (a dependency's `old::hook`). The run's fold
     reports a key that is rule-made in one observer and not in
     another, for every kind but a namespace: two entities under one
     key, the collision of §2.1 seen across observers. Say where the
     fold runs (the verify job needs the union of the second set before
     it can answer, or the run's conclusion needs both sets after: one
     more section in the shard and a reduce, as `negatives` and
     `found` are, `spec/model.md` §8.8), what it costs at 10^5
     observers and 10^7 moved entities, that the answer does not
     depend on the order of observers, and what the user sees and
     declares (`kept old::hook`: the hook stays; or the dependency is
     part of the edit).
   - **Decide ownership for the run, before the digests.** A first
     pass (the plan, or the map phase's shards) collects per key
     whether any observer saw a declaration outside owned files; the
     verify jobs take that set as an input and `owned` answers for the
     run. Then no observer maps `fresh::hook` back, `u1` reports
     `removed old::hook`, `added fresh::hook`, and the finding is the
     ordinary one. Say what the set is keyed by (a key needs the
     walk; a name is not exact), how large it is, what an incremental
     run does when one observer's answer changes it for all, and
     whether it makes the `a4` case right too.
   - **Ownership by the declaration's file alone**, never by the way in
     (the `a4` half only): what it changes, and that it does not answer
     the pair above.
   - **Both**: the second decides, the first checks that the decision
     held (an observer whose own reading disagrees with the run's set
     is a finding of the tool, not of the edit).
   Recommend one. Whatever is chosen must keep an observer's digest a
   function of its own inputs and of inputs the plan names (no hidden
   dependence on another observer's shard), or say exactly what the
   incremental and parallel execution lose.
2. **Built after the ruling**, in stages if the proposal says so, with
   pitfall rows: the pair above `bad` (a definition moved away from a
   declaration a dependency keeps), the same with `kept old::hook`
   `good`, and each shape of item 1's inventory.

## Ruling (supervisor, 2026-11-24)

On the proposal `spec/landed/verify/WP-146.md` (commit `d7522c75`).
The principle the answers follow: **the run says of an edit what one
observer that saw every declaration would say.** Whether a wrong edit
is found must not depend on which translation unit happens to include
which header.

1. **A, not B.** Accepted. Ownership inside an observer stays as §2.1
   decides it; the finding is the run's; a job reads nothing another
   observer wrote. The report prints an `ownership` finding before the
   observers' own lines, since every observer may say `verified`.
2. **The mirror (§0.1) is in this package.** It is the commoner case of
   the motivating migration (dependencies already live in the target).
   Each report is a real merge of two entities.
3. **Lists as content-addressed blobs named from the shard (section
   32): accepted provisionally.** Stage 2's corpus figures decide: if
   distinct list bytes are not far below summed list bytes, come back
   before the fold is built. A list that is missing, does not hash to
   its id or does not decode makes the observer `failed`. Retention is
   stated as a rule (a list lives while a shard names it); no collector
   is built here.
4. **Kinds: every kind that collides in one observer, less internal
   linkage** (aliases and typedefs included), by the principle above.
   A linkage the walk cannot read is contributed.
5. **Fail closed; no assertion in this package.** The third resolution
   is WP-116's to design, on this package's carrier; stage 4 is not
   part of WP-146.
6. **WP-116 after this package, on its carrier, not merged with it.**
   `spec/verify.md` §2.1's sentence that assigns three holes to WP-116
   is corrected in stage 0 (it is false today whatever is built):
   `observer-includes-owned-only` and the `-direct-first` pair have no
   planned answer where no observer shows the dependency's reading. §8
   stands; "Open questions" gains the entry "a dependency's header no
   observer includes" with the one remedy known (such headers parsed as
   observers of their own, named by the user), no package yet.
7. **Selections: keep** (`verified` of the selection). The report says
   over how many observers of the plan's the ownership fold ran, in
   the same line as the conflicts' count, so a selection cannot be
   read as the run.
8. **The include-chain rule stays; the rule for WP-144 is as worded in
   §4.**
9. **Stage 0 first: yes.** A shape that does not behave as §2.2 and
   §3.4 say comes back to the supervisor before stage 1; S10 (the
   mirror, "by reading") and S23 first.

**How it is built.** This package is stages 0 and 1 (the pins; the
walk's two lists, inert for every digest, `use` line, counter and
verdict), by an implementer, on top of WP-140's branch until that is on
`main`. Stages 2 and 3 (the record, the fold and the verdict) are a
package of their own, written when this one merges (it needs
`docs/wp/WP-114.md`, which edits the verify task and the agreement);
