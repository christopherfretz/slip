# WP-127 — rename: references the edit leaves behind that it could have seen (a using-declaration whose shadows are hidden, a dependent call)

- Status: todo
- Milestone: M2
- Track: C
- Needs: WP-119, WP-120
- Size: M
- Parallel with: the transform packages that do not edit `crates/slip_refactor`'s rename

## Scope

The review of `docs/wp/WP-119.md` found two renames that are accepted
and then fail verification. Neither is a wrong `verified`; both are a
tool that says "done" and a verifier that says "no", where the rename
had what it needed to refuse or to do the edit
(`spec/landed/` WP-119's "Known mismatches after the review", with the
tests that pin today's behaviour).

1. **A using-declaration whose shadows are all hidden.**

   ```cpp
   struct A { void f(int); };
   struct B : A { virtual void f(); };
   struct D : B { void f() override; using B::f; };
   ```

   Renaming `B::f` (or `D::f`, its family) to `g` leaves `using B::f;`
   as written: it now names `A::f(int)`, or nothing. With the
   using-declaration first it is rewritten and verifies. WP-119 made a
   hidden shadow no unit; the rename finds a using-declaration through
   its shadows. Decide what the rename reads instead (the
   using-declaration's own named set, which does not depend on the
   order of the class's members), and what the edit is in each case:
   every named declaration renamed (rewrite); some renamed and some not
   (the name now means two things: refuse with `MixedFollower`'s kind
   of error, naming the using-declaration and the declaration that
   stays); the using-declaration in a class template naming a dependent
   base (what the pattern holds; `docs/wp/WP-120.md`'s rule).
2. **A dependent call.**

   ```cpp
   template <class T> int call(T t) { return t.f(); }
   int u() { return call(n::S<int>()); }
   ```

   Renaming `n::S::f` leaves `t.f()`. Before WP-119 the followers'
   `unsupported` flag refused the run; now it is accepted. The same for
   `T::f()` and `&T::f`. The instantiation `call<n::S<int>>` binds the
   call to the renamed member, and the observer has it. Decide and
   state (`spec/edits.md` §9): the rename refuses when an instantiation
   in any observer binds a dependent name of a pattern to a renamed
   entity (the error names the pattern's site and the instantiation);
   or it offers the edit of the pattern's name when **every**
   instantiation of the pattern in every observer binds that name to a
   renamed entity, and refuses otherwise. The second is what a user
   wants and is only as good as the set of observers: say what the
   report tells the user about instantiations it did not see. This
   item is a design question first: write the proposal in the landed
   file and stop for the supervisor before building the offering form.
   The refusing form may be built at once.
3. Each of the two tests WP-119 left as known mismatches becomes a test
   of the new behaviour.

## Interface

`spec/edits.md` §9 (rename), its error kinds; `crates/slip_refactor`
(or where the rename lives: name it); `spec/landed/` under the rename's
area.

## Tests

Item 1's cases each way and in both member orders; item 2's three
forms, with one and with two instantiations of which one binds
elsewhere; a run with two observers of which only one instantiates.
Mutations: the using-declaration found by its shadows only; the
dependent call checked in the first observer only.

## Rules

`docs/AGENTS.md`. No string edit of the source: the rewritten name is
an edit of a located reference. The gate is the full `cargo xtask ci`.
Second review; the reviewer's question: a rename that is accepted and
does not verify, or one that verifies and changed what a name means.

## Done when

The gate passes with `main` merged in; item 2's proposal is ruled on;
no accepted rename of this package's cases fails verification.

## Out of scope

Dependent names that no instantiation in any observer binds (nothing
to read: the report's note of item 2).
