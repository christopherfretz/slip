# WP-131 — a rule that matches nothing changes nothing: conversion functions of instantiations, and the invariant

- Status: review
- Milestone: M1
- Track: C
- Needs: WP-103, WP-119
- Size: M
- Parallel with: WP-112, WP-123, WP-124 (one digest branch merges at a time; this one has priority: it blocks Demo 1)

## Scope

Demo 1's run of record (2026-11-23, `main` `9462d716`) failed its one
correct change: `01-relocate`, the relocation of
`llvm::hashing::detail` to `llvm::hashing::impl`, gave 159 groups of
findings that are not indeterminate (70 `changed`, 30 `removed`, 30
`added`, 29 `derived_changed`); the control, with no declaration, is
clean. Every one is a conversion function of an instantiation
(`std::atomic<int>::operator int`, `basic_string::operator
basic_string_view`, `llvm::cl::opt_storage<bool, false,
false>::operator bool`, `packed_endian_specific_integral::operator
value_type`) or a unit that refers to one. Three lines show it:

```cpp
namespace a { namespace detail { int k = 3; } int use() { return detail::k; } }
template <class T> struct W { T v; operator T() const { return v; } };
int f(W<bool> s) { if (s) return 1; return 0; }
```

with `detail` respelled `impl` and `relocate a::detail => a :: impl`
declared: `changed f(W<bool>)`, at the reference to
`W<bool>::operator bool() const`.

The cause: `Walk::follow_patterns` (`crates/slip_digest/src/keys.rs`)
gives a member of an instantiation its pattern member's name whenever
the rule table is not empty (`spec/digest.md` §3.4, WP-103). A
conversion function's name is its type (`Name::Conversion`, a type
digest): the pattern's is the digest of `T`, the member's that of
`bool`. So the member's key under any rule table is not its key under
none, and the two sides of a verification (the pre-image is keyed under
no rule) disagree about an entity no rule names.

1. **The rule for a conversion function** (the supervisor's ruling;
   write it into `spec/digest.md` §3.4): a member whose name is a
   conversion name does not take its pattern's name. No rule renames a
   conversion function apart from its type, and the type digest of the
   member's own name is already in mapped terms (a rule on the type it
   converts to reaches it there). The checks of a rule on the member's
   plain key stay as they are for a member that follows no pattern.
   Say what a rule whose `name` is a conversion name means, if
   `slip declare` can produce one (`formats/declared.rs` reads the
   form): if no declared change can, say that it matches nothing and
   test it.
2. **The same question for every name that is not an identifier**: an
   unnamed class or enumeration named by a member or declarator
   (`Name::UnnamedBy`, which wraps a name that may be a conversion
   name), an ordinal (`UnnamedOrdinal`: is the ordinal in a pattern the
   ordinal in its instantiation?), a constructor, destructor, operator,
   literal operator, deduction guide, a using-shadow of a conversion
   function (`std::atomic<int>::<shadow std::__atomic_base<int>::operator
   int() const>` is among the corpus findings), a lambda's members, an
   implicit member. For each: the pattern's name and the member's are
   equal by construction (say why), or the member keeps its own (as
   item 1), with a test.
3. **The invariant, as a test over every input the crate has**
   (`spec/digest.md` §3.4, a new numbered rule): for every translation
   unit, the walk under a rule table none of whose rules matches a key
   of that translation unit gives the units, keys, digests, causes and
   records of the walk under the empty table. Build it as one test file
   that runs both walks over every side of every pair of
   `tests/equal`, `tests/differ`, `tests/demand`, `tests/indeterminate`,
   `tests/resolved` and the subjects of `tests/rules`, with a table of
   one namespace rule on a namespace the source does not declare, and a
   second table with a rule of each kind `tests/common/rules.rs` can
   write (a class, a function, a member, a variable) on names the
   source does not declare. Say what "the same" excludes, if anything
   must be (the rule-use record, a counter), and why. Every difference
   it finds is a finding of this package: fix it, or stop and report if
   the fix is a design question.
4. **Every branch on an empty table**: `keys.rs` (`follow_patterns`,
   `mapped_name`, the decomposition's first binding, the three around
   lines 472, 623, 802 and the collisions check at 1462), `owned.rs`
   166, `records.rs` 88, `walk.rs` 567, and `slip_cli`'s
   `verify_job.rs`. For each, one line in the landed file: what differs
   between the two branches when no rule matches, and the test that
   shows it is nothing. Ownership (`owned.rs`: a rule matches no
   dependency entity) is the likeliest second instance: a
   `--owned`/`--readonly` pair where a dependency's class template has
   the conversion function.
5. **The catalogue**: a row of `crates/slip_verify/tests/pitfalls/`
   (the next free `N` number) "a relocation beside a conversion
   function of a class template": `good` trees for the three lines
   above, for the conversion function in a dependency header, for a
   conversion to a type the relocation moves (`operator detail::X()` in
   a template, and `W<detail::X>`), and for a conversion function
   template (`template <class U> operator U() const`); `bad` trees: the
   conversion's result type changed in the same edit; the call resolved
   to another conversion function.

## Handback

`spec/landed/digest/WP-131.md` (what was built, decisions, the tables of
items 2 and 4, the mutations, what the invariant excludes, For Kiln).

patterns only when `follows_pattern(&key.name)`: identifiers, operators,
constructor, destructor, literal operators, deduction guides, and
`unnamed_by` of those. `conversion`, `unnamed_by(conversion)`, `local`
and `unnamed_ordinal` keep their own name, keyed as a member that follows
no pattern. `follow_patterns`, the WP-119 acceptance and `mapped_name`
are unchanged; no existing expectation changed.

after a discarded `if constexpr` branch (`rules/inert/local-class-after-discarded`,

`digest.bytes` higher under any non-empty table (namespace views,
`mapped_name` recomputation): excluded as work, checked as never
smaller (decision for the reviewer, landed file decision 3).
