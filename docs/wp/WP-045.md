# WP-045 — slip_digest: resolved units, the `definition` of what is defined on use, and one rule for members of instantiations

- Status: in-progress
- Milestone: M1
- Track: C
- Needs: WP-024, WP-026, WP-027, WP-029, WP-032, WP-033
- Size: L
- Parallel with: WP-034..040, WP-044, WP-046 (after this package's first
  commit), WP-047

The first package of the digest's wave 3. After the area packages, the
units of every instantiation and of every implicitly defined member are
still indeterminate with `Cause::Pending(Area::Demand)`: what Kiln makes
only on use is left out of their streams and written nowhere. This
package writes it, in resolved units (`spec/digest.md` §2.2,
`spec/digest-kinds.md` §11.1 and §11.9), and settles which members of an
instantiated class are declared units.

## What is decided

Read `spec/landed/digest-kinds/WP-026.md` "The definition class",
`spec/landed/digest/WP-032.md` "What rule 4 leaves to the demand
package", `spec/landed/digest-kinds/WP-027.md` and the Handback sections
of `docs/wp/WP-026.md`, `WP-027.md`, `WP-029.md`, `WP-032.md`,
`WP-033.md`: each names what this package must write. The decisions
below settle what they left open. Each is to be shown by a `demand`
pair (a use added on side B changes no unit both sides have); if a pair
shows a rule is not independent of use, stop on it and report, do not
bend the rule.

1. **The effective kind of a member.** Kiln gives a member of an
   instantiated class a `MemberSpecInfo` whose kind depends on what was
   used first (a member class already defined stays
   `ImplicitInstantiation` under a later explicit instantiation of its
   class, `kiln_sema/src/templ/spec.rs:1366-1394`; a member function
   keeps `ImplicitInstantiation` under one), and gives fields none. The
   digest reads one kind for every member, computed from facts that do
   not move:
   - an entity with its own `SpecInfo` (a specialisation of a template)
     has that kind: nothing below applies to it;
   - a member whose `MemberSpecInfo` kind is `ExplicitSpecialization`
     has that kind;
   - any other member of a class made by instantiation (with a
     `MemberSpecInfo` of another kind, or with none) has the greater of
     its own kind and the effective kind of its class, in the order
     `ImplicitInstantiation` < `ExplicitInstantiationDeclaration` <
     `ExplicitInstantiationDefinition` (`Undeclared` and no kind count
     as least);
   - a member of an explicit specialisation, or of a class that is not
     made by instantiation, has no effective kind (it is written in
     source).

   One function computes it; `unit_class`, the kind a member's unit
   writes (`MemberSpecInfo` `kind`), the definition class and
   `decl_class::instantiated_field` all read it. Say in the landed file
   how it relates to `templ::governing_kind`,
   `templ::instantiated_declaration`, `units::in_implicit_instantiation`
   and `decl_func::instantiated_on_use`, and remove each of those that it
   replaces (`docs/wp/WP-033.md` Handback asked for the two families to
   be looked at again here).
2. **Unit class.** A member with an effective kind is a declared unit
   when that kind is an explicit instantiation (declaration or
   definition) or an explicit specialisation, and derived when it is
   `ImplicitInstantiation`. So the members of `template struct X<int>;`
   and of `extern template struct X<int>;` are declared units, all of
   them, fields and functions alike, and are listed in their class.
   Check with Kiln's source that an explicit instantiation declaration
   instantiates the class's definition and with it every member's
   declaration; if it does not, report it (the class would then be of
   the definition class).
3. **The definition class** (§11.9's list, replaced by):
   - a specialisation whose `SpecInfo` kind is `ImplicitInstantiation`
     or `ExplicitInstantiationDeclaration`;
   - every member with an effective kind other than
     `ExplicitSpecialization`, whatever the kind: under an explicit
     instantiation definition Kiln defines only the members whose
     patterns are defined at that point ([temp.explicit]/10) and the
     others on use, and a member class used before it stays as it was;
   - an implicitly declared special member function, comparison operator
     or deduction guide; the conversion functions of a closure type; a
     function explicitly defaulted on its first declaration;
   - an entity all of whose declarations are instantiated outside their
     class; and, for its definition only, an entity with a written
     declaration whose definition an instantiation added outside its
     class (WP-032 rule 4: read from `Ast::definition`).

   A specialisation whose `SpecInfo` kind is
   `ExplicitInstantiationDefinition` is not of the class: its definition
   is made at the explicit instantiation, used or not. Show that with a
   pair in which the specialisation is used before the explicit
   instantiation on one side only.
4. **Rows moved to `definition`**, in this order, each written in its
   empty form in the unit's own stream **without a cause**:

   | Entity | Rows |
   |---|---|
   | every entity of the class with a `SpecInfo` | `SpecInfo` `from`, `from_args` |
   | a function | its parameters, as the own unit writes them (so that the body's local references are numbered in this stream and no stream depends on another's state); `FunctionData` `body`; `ColdDeclData` `ctor_inits`; `FnSpec` `0-escalated`, `0-is-coroutine`; the return type and `FnSpec` `0-return-deduced`, when the function is defined on use and its pattern's declared return type holds a placeholder |
   | a variable | `VarData` `init`; `VarSpec` `0-init-style`, `0-inline`, `0-inline-implied`; the type, when the pattern's declared type holds a placeholder |
   | a class | `RecordData` `members-fields`, `members-virtual`, `members-other`, `bases`, `defn`; `ColdDeclData` `friends`, `record_pack` |
   | an enumeration | `EnumData` `members`, `int_type`, `promotion_type`, `flags-fixed`, `flags-complete` |

   `DeclMisc` `0-definition` is written clear in the own unit of every
   entity of the class and is in no stream: that `definition` exists
   says it.
5. **When `definition` exists**: when Kiln holds the definition at the
   end of the translation unit (`Ast::definition`, and for a variable
   what `units::is_var_definition` and the initialiser's holder say).
   Say per kind what is read, with Kiln's `file:line`. A function that
   is deleted is not defined by that: `= delete` is a fact of the
   declaration.
6. **What `definition` is read from**: the defining declaration, with
   the same merging over the chain the own unit does for the rows it
   keeps. For an entity of the fourth item of 3, the declaration
   `Ast::definition` names.
7. **`Pending(Area::Demand)` at the sites of §11.9 goes.** After this
   package a unit of the definition class is indeterminate only for a
   reason of its own.

The spec changes with the code: rewrite `spec/digest-kinds.md` §11.9

## Interface

```rust
// demand.rs
/// The properties of digest-kinds §11.1, by their numbers.
pub(crate) enum Property { ExceptionSpec = 1, Value = 2, KeyFunction = 4, DtorDelete = 5,
                           InheritedConstructor = 6, DefaultImmediates = 7, Definition = 8 }
/// The resolved units of the unit `owner` just written for entity `e`,
/// appended to `out`.
pub(crate) fn resolved_units(w: &mut Walk<'_>, e: DeclId, owner: &Written, out: &mut Vec<Written>);
/// The effective kind of decision 1; `None`: written in source.
pub(crate) fn effective_kind(w: &Walk<'_>, e: DeclId) -> Option<SpecKind>;
```

The names may differ where the code reads better; what is fixed is that
one function writes a resolved unit of any property, one decides the
effective kind, and WP-046 adds its properties by adding arms, not by
changing the framework. `Written.entity` of a resolved unit: decide and
document (names and `apply_taints` read it).
