# WP-090 — the script test format and its runner

- Status: in-progress
- Milestone: M3
- Track: G
- Needs: WP-083, WP-088, WP-089
- Size: M
- Parallel with: WP-085, WP-086, WP-087, WP-092

## Scope

`spec/api.md` §11. A script test is a directory with a transform, a
subject and an expected rendering; the runner compiles the transform in
the transform universe, parses the subject with the snippet front end,
runs the driver of WP-089 over `KilnSubject` and compares.

This is the API side of the transform test format. The pipeline side
(a transform test of `spec/harness.md` §6 that runs plan, map, reduce,
apply and verify) is `spec/edits.md`'s; this package makes a `.cpp`
transform nameable there (§11 rule 4) by exporting `load_script`.

What is decided:

1. One test binary, `crates/slip_script/tests/api.rs`, discovers every
   directory under `tests/api/` that has a `transform.cpp`. Each is one
   test case by name. No test framework dependency: the existing
   directory runner of `slip_kiln`'s pair tests is the model.
2. The transform is compiled once per distinct (`// args:`, bytes of
   `transform.cpp`); most directories share none, and the standard
   headers dominate the cost, so the binary keeps the tests of one
   directory group on one thread to bound memory and runs groups in
   parallel under the jobserver.
3. `SLIP_BLESS=1` rewrites `expect.txt`; a blessed file is reviewed like
   code.
4. Every `transform.cpp` has a `// spec:` line; a lint (below) checks it
   names a section that exists.
5. The exact grammar of `expect.txt` is this package's to fix, within
   §11 rule 3, and is recorded in `spec/landed/api/WP-090.md`. It is
   `RunOutput::render` (WP-088) with places as `file:line:col-line:col`
   and keys as verify's names.

## Interface

```rust
// crates/slip_script/src/script_test.rs  (behind the crate's `testing` feature)
pub struct Script { pub dir: PathBuf, pub spec: String, pub args: Vec<String>, pub budgets: Budgets, pub owned: bool, pub xfail: Option<String>, pub counters: Vec<String> }
pub fn load_script(dir: &Path) -> Result<Script, String>;
/// Compile, run on the directory's subject, render (§11 rule 3).
pub fn run_script(script: &Script, resource: &Path) -> Result<String, String>;
```

`cargo xtask lint` gains the check `api-tests`: every directory under
`crates/slip_script/tests/api/` has `transform.cpp`, `t.cpp` and
`expect.txt`; the `// spec:` line names a heading of `spec/api.md`.

## Tests

- `crates/slip_script/tests/api/format/`: one directory per header line
  of §11 rule 2; a completed run; a failed run; a transform that does
  not compile; an `xfail` that fails (passes) and one that passes
  (fails the suite); a subject with a second file.
- `crates/slip_script/tests/api/values/`: §5.1 to §5.3 from C++:
  equality, null, the sorts, a forged `info` (through `std::bit_cast` of
  an integer: `invalid_handle`), a value kept across a failed call.
- `xtask` tests for the lint.

## Done when

`cargo xtask ci` runs the directory suite and the lint.

## Out of scope

The rest of the suite's content (WP-091). Pipeline transform tests.

`expect.txt`, the mutations and the costs are in

**Proposed sentences for `spec/api.md` §11** (not edited here):

- Rule 2's table gains `// counters: a, b` | the counters rendered (rule 3).
- Rule 3: "places as `file:line:col-line:col`, the end exclusive, columns
  in bytes".
- A rule 5: "A test whose subject has errors, or whose transform reads a
  file of the test's directory, is an error of the test. A `host-failure`
  is never a rendering: it fails the test whatever `xfail` says."

**Mutations.** 58 mutations of the runner, the lint and the gate's
refusal, listed with the test that caught each in
`spec/landed/api/WP-090.md`. Nine survived the first round; each now has
a test. One survives as equivalent: the group key without `// args:`
(the header line is part of the bytes).

**Costs.** The suite is 42 s of CPU in a debug build, about 2 s per
directory with its own transform; 11 s wall on 4 free threads. Details in
the landed file.
