# WP-135 — where each found lookup led: a spelling that now reaches another file

- Status: todo
- Milestone: M2
- Track: C
- Needs: WP-117
- Size: M
- Parallel with: the transform packages

## Scope

`docs/wp/WP-117.md` closed the ways for the files the map parse read to
stop being the files a lookup reaches when a file is deleted, changed,
or shadowed by one that appeared at a place the map parse looked at and
found nothing. Its two reviews left one family open, stated as a limit
in `spec/verify.md` §5.1: **a spelling the map parse resolved now leads
somewhere else, while every path in the map shard's `inputs` and
`negatives` still passes**. Both forms give `verified` today for a pair
that gives `mismatch`:

- **A found lookup through a link outside the roots, retargeted.** A
  symbolic link outside every root through which the map parse found a
  header is pointed, after the map phase, at a directory holding another
  header of that name; the edit compensates. The place was found, so it
  is no negative; the header the map parse read is still there,
  unchanged (`o2_link_to_a_found_header_retargeted`, ignored).
- **Two recorded inputs made one file by a hard link.** `ext/a.h` and
  `ext/b.h` are equal in bytes, each `#pragma once`; after the map phase
  one is replaced by a hard link of the other. Every recorded path is
  still its own real path with the recorded size and digest; the post
  parse sees one file where the map parse saw two
  (`zz_r1b_merge_by_hardlink` of WP-117's second fix round, checked in
  as the stated limit).

The symbolic-link form of the second (a recorded input that is no
longer its own real path) and a command directory dropped as a
duplicate and then made distinct were closed in WP-117's second fix
round; read its handback first.

1. **The record** (a new section of the map shard; the next free
   critical id of `spec/model.md` §8, the unknown-section examples moved
   if they collide): for each found lookup of the map parse outside the
   subject roots, the place as written (as `negatives` writes a place:
   text, `.` and repeated `/` dropped, no link followed) and the input
   it reached (an index into `inputs`); each distinct pair once. And the
   classes of `inputs` that were one file at the map phase (the same
   device and file number): two inputs that are hard links of one
   another at the map phase are legitimate (stores that deduplicate),
   so the record is the partition, never the numbers (a device and file
   number mean nothing on another host or after a copy).
2. **The guard** (in `verify_job::image_guards`, after N1; a row of
   `spec/verify.md` §5.3): refused, `unverifiable`, when a recorded
   place resolved now does not reach the recorded input's real path, or
   when the partition of the recorded inputs by file identity now is
   not the recorded one. A map shard without the section is refused as
   one without `negatives` is (the F3 text's kin). Say what is judged
   under a subject root and why (N1's rule: by the file's real path;
   the tree form's post parse does not read the subject).
3. **What Kiln's log gives**: whether the lookup log names the place a
   found lookup was found at (the directory entry and the spelling), or
   only the file; if only the file, the place is recomputed as
   `negatives` computes a missed one. A For Kiln item if the log lacks
   what is needed; the package does not wait for it if the
   recomputation is exact.
4. **Cost**: the section's size and the guard's time on the
   measurement of `crates/slip_cli/tests/negatives_cost.rs` (extend
   it; the supervisor runs it on `llvm/lib/Support`). The number of
   found lookups is far above the number of negatives' places only if
   every includer is counted: count distinct places.
5. **`spec/verify.md` §5.1**: the two exceptions named there are
   removed; if a form remains open, it is named with a test that
   records today's answer.
