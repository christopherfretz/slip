# WP-159 — the harness and the store on a file system that confuses the names of a hard-linked file

- Status: done
- Milestone: M1
- Track: H
- Needs: none
- Size: M
- Parallel with: every package

## Scope

Found on 2026-11-24 in a merge check: `slip_cli --test
names_relocation` `measure_on_a_small_corpus` failed once with a parse
of the pre-image that read a header with the post tree's content. The
files on disk were right. The cause is the file system of the
supervisor's workspace (a container bind mount over a host share), and
a loop with no Slip in it shows it. With a file `A` and a hard link
`B` to it, 60,000 rounds each, while another build loaded the mount:

| what is done to `B` | reads of `A` or `B` that returned the wrong content |
|---|---|
| unlink `B`, create a new file `B` | 15 (`A` read as the new `B`) |
| write a temporary file, rename it over `B` | 56,909 (`A` read as the new `B`) |
| the same two with `B` a copy of `A`, never a link | 0 and 0 |

The test harness builds a post tree by hard-linking the subject tree
and replacing the edited files, which is the first row. A wrong read
there can make a correct edit fail (as it did) or make the pre-image
read as the post-image, which hides what a test seeded. Slip's
validation must not depend on a mount behaving; Slip's own store and
writer must be known not to walk into the same pattern.

1. **The probe**: `cargo xtask fscheck <dir> [--rounds N]` runs the
   rows above and those item 2 needs (a file created fresh beside
   hard-linked siblings; a hard link only read through both names; a
   temporary name created again after link-and-unlink, the store's
   publish) in `<dir>` and prints, per row, rounds and wrong reads;
   status 1 if any row a harness or the store relies on is not zero.
   `spec/harness.md` gains a section: the hazard, the rows, what the
   harness relies on.
2. **The harness never replaces a name that is a hard link.** Post
   trees (`xtask/src/demo.rs`; `link_tree` and `apply_edit` in
   `crates/slip_cli/tests/names_relocation.rs`; any other helper that
   links a tree) are built so that an edited or created file is never
   linked first: the files a case edits are known before the tree is
   made, so link what is not edited and write what is. Choose by the
   probe: if "a file created fresh beside hard-linked siblings" is not
   clean on the supervisor's mount, the tree is copied; say what a
   copied tree of the `llvm` roots costs in time and disk, and stop
   for a ruling if it is more than a minute or a gigabyte per case.
   After building a tree the harness reads back every file it wrote
   and compares (a check, not the guarantee).
3. **Every `hard_link` in tests** (`crates/slip_cli/tests/verify_job.rs`,
   `tasks.rs`, `verify.rs`, `rename.rs`, `crates/slip_apply/tests/write.rs`,
   `crates/slip_spelling/tests/walk.rs`, `crates/slip_kiln/tests/overlay.rs`):
   list each with what it is for. One that needs two names of one file
   (identity, the spelling walk) stays if nothing replaces either name
   while the test reads the other, and says so in a comment; one that
   links only to save a copy copies.
4. **The product's own links** (`crates/slip_exec/src/store.rs`,
   `crates/slip_cli/src/transform/store.rs`,
   `crates/slip_cli/src/transform/apply.rs`): for each, the sequence
   of link, unlink, rename and create it performs, and whether a name
   is ever created again while another name of its old file is alive
   (a temporary name is `<pid>.<n>.tmp`: a later process with the same
   pid is one way). Where it can: make the name unique for good, or
   say why the reader cannot be misled (the reader checks a content
   digest: name the check). State in `spec/exec.md` which reads of the
   store are checked against a digest and which are not. **No
   behaviour of a command changes**; if the audit finds a read that
   can return another entry's bytes unnoticed, stop and report: that
   is a finding for the supervisor to rule, not a fix to slip in.
5. **`apply --write`** renames a temporary file over its target. If
   the target has a second name, that name keeps the old content by
   the standard and reads the new content on this mount. Say in
   `spec/edits.md` §10 what Slip promises (the file at the path it was
   given), and that `slip_apply`'s tests with a linked target do not
   read the other name after the write on a mount that fails the
   probe (or copy).
6. **For the supervisor**: the commands to re-run Demo 1's cases on
   trees built the new way, and the probe's output on the workspace.

## Interface

`xtask` (`fscheck`, `demo.rs`), the test helpers named above,
`crates/slip_exec` and `crates/slip_cli` only as item 4 allows,
`spec/harness.md`, `spec/exec.md`, `spec/edits.md`,

## Tests

- `xtask` tests of `fscheck` over a temporary directory: the rows run,
  the output's form, status 0 on a file system that passes (the test
  says which rows it could not make fail, and does not assert that the
  workspace mount fails);
- the tree builder: an edited file and a created file are never a hard
  link at any moment (a test that records the calls, or inspects link
  counts before each write); the read-back check fails on a planted
  difference;
- `measure_on_a_small_corpus` 200 times in a loop while another cargo
  build runs: no failure (the handback gives the count; the loop is
  not a test in the gate);
- item 4's sequences, each a unit test where one is missing;
- mutations: the builder links an edited file first; the read-back
  check skipped; a temporary name reused.

## Rules

`docs/AGENTS.md`. The gate is the full `cargo xtask ci`. The probe's

### Supervisor's handback (merge, 2026-11-24)

Merged on my read alone, to keep a review seat free under the
operator's limit of two agents: the product change is the name of a
temporary (`slip_exec::store::tmp_name`, the journal's temporary), which
I read in full with its tests and the spec text of `spec/exec.md` §2.1
and `spec/edits.md` §10.4; the tree builders (`xtask/src/demo.rs`

read in full; the audit I checked against my own list of every

missing: `slip_apply::fs`, `declare.rs`, `verify_cmd.rs`,

temporary over a path, the clean row). The branch's gate predated
WP-157 and WP-078 on main: the merge check ran fmt, both clippy runs,
the whole suites of `slip_exec`, `slip_apply`, `slip_kiln`, `slip_cli`
and `xtask`, `cargo xtask transform` and lint on the merged tree.

Rulings:

- **A linked name read as absent** (`unique-tmp-link` fails on the
  workspace mount): no change here; WP-161 takes the store off the
  link-then-unlink sequence (the lock and the journal made by exclusive
  creation, their readers telling "being written" from "absent" by
  content), so that no promise of the store rests on a row this mount
  fails. Until then, on this mount: a lock left behind by a close, a
  `Busy` with pid 0, or `apply --recover` saying there is nothing to
  recover are this hazard; all loud or repeatable, none a wrong result.
  One case the handback does not name: a process that closes a store,
  reads its own lock as absent, and opens the same store again finds its
  own live pid in the lock and gets `Busy`. WP-161's tests include it.
- **`--plan <id>` and `check --declared <id>`** are checked against
  their content ids: WP-161.
- The tree builder links what a case does not edit and writes what it
  does; accepted (the two rows it rests on are clean over 60,000
  rounds, and it reads back what it wrote).
- Demo 1's cases are re-run by me on trees built this way before their
  runs of record are quoted again.

**A second hazard of the same mount, found in this merge check** (not
this package's doing): `cargo xtask transform` failed one test on the
merged tree and three on a second run (`family-virtual-three-files`
`not_parsed 1`; two mutation runs `incomplete`), different tests each
time, all passing by hand. The kept verify shard shows the post-image
parse of `x.cpp` reading `d.h` from disk and not from the overlay. A
probe (a Python loop, no Slip code) saw the inode number of about 800
of 4,800 untouched files on the mount change within two seconds, in
bursts (none in two other runs): the front end matches an overlay entry
to a file by device and inode, so a burst between the entry being added
and the file being read makes the entry miss. The guards hold (`not_parsed`,
or O1 `unverifiable` when the parse succeeds): loud, never a wrong
`verified`. Three runs with the target directory (and so the runner's
work directories) on the container's own disk: 107 passed, 0 failed,
each. Ruled, on the operator's suggestion: builds, test work directories
and corpus runs move off the mount; a test failing once on the mount
with a header read from disk is this hazard.
