# WP-116 — what a dependency's binary holds: a renamed entity is defined in owned code

- Status: todo
- Milestone: M2
- Track: C
- Needs: WP-069, WP-070, WP-110, WP-111
- Size: M
- Parallel with: the transform packages

## Scope

`docs/wp/WP-110.md` decides ownership inside one translation unit, by
where an entity's declarations are written. That is a stand-in for the
question that matters: **does a binary Slip cannot see hold this
entity's name?** The review of WP-110 (`spec/landed/digest/WP-110.md`,
"Review") showed three places where the stand-in gives the wrong
answer, each a wrong `verified` for a relocation:

- **two observers**: an owned header declares `legacy::Both`, a
  dependency header declares it too; an observer that includes only the
  owned header sees an owned entity and verifies its move;
- **a pasted name**: `#define DECL_INIT() void legacy_##init();` in a
  dependency header, invoked in an owned namespace: the name is spelled
  in no file, the declaration is owned by its expansion location, and
  the dependency's binary defines the function;
- **an inclusion the walk cannot see** (if WP-110's fix round reports
  one): an owned header entered directly first and included again by a
  dependency header behind its include guard.

All three are one fact seen from the run: the entity is renamed, and no
owned file **defines** it. This package builds that check.

1. **The walk** (`crates/slip_digest`, beside `rule_use` of
   `docs/wp/WP-069.md`): for each entity a rule renames in this unit
   (`direct` of §9.1: the rule matched the entity itself), whether the
   unit holds a **definition of it written in an owned file**, as one
   of: `defined`, `declared` (declarations only), `needs none`. Decide
   and state, per kind of entity, what "defined" is and which kinds
   need none:
   - a function, a variable, a static data member: its definition;
     an inline or `constexpr` one is defined where its body or
     initializer is;
   - a class or an enumeration: its definition. A class that is only
     ever declared (an opaque handle, a tag type) is the hard case: it
     is `declared` in every observer, and the check then reports it;
     the user answers with the assertion of item 3;
   - a template: its definition; a specialisation follows its template
     as in WP-110;
   - an alias, a `using`, an enumerator, a namespace, a concept, a
     non-static member: say which need none and why no binary can hold
     them apart from their owner;
   - an entity with internal linkage or in an unnamed namespace: needs
     none (no other binary can name it): show it with the linkage the
     walk already computes.
2. **The record and the run**: the counts travel with `rule_use`
   (`spec/verify.md` §9.1; a new field or a new section, the smaller
   change to the readers). The run (`crates/slip_verify`, beside the
   stale check) joins by the entity's pre-image key: **an entity that
   some observer renames and no observer defines in an owned file is
   reported `not defined in owned code`**, the run is not `verified`
   and permits no write. A run over part of a compilation database
   reports the same and says that the definition may be in an observer
   that was not run (`--only`): decide whether that is an error or a
   weaker outcome, and say which.
3. **The assertion**: a line of the declared file, `owned <entity>`
   (`slip declare`), for an entity the user states is theirs although
   no observer defines it (a tag type; a function defined in assembly
   or another language; a definition in a file outside the compilation
   database). It is in the `DECL` container (reader rows as for `kept`),
   in `rules_id`, in the report (every run lists the assertions it
   relied on), and an assertion no observer needed is reported like an
   unused rule.
4. **A read-only file that includes an owned file** (WP-110's fix
   round freezes what is entered through a read-only file). When Kiln's
   record of inclusion directives is in the pin (Kiln WP-2111): the
   inclusion that was skipped by an include guard is read from it, and
   the pending pair of WP-110 for that case passes. Until then the
   check of item 2 is what covers it; say for which of the reviewer's
   two F2 programs it does and for which it does not (a class that the
   owned header defines **is** defined in owned code: item 2 does not
   catch it, only the inclusion does).
5. **Attack it**, each a test with two or more observers: the three
   cases above; a function declared in an owned header and defined only
   in a file that failed to parse; an inline function defined in an
   owned header that one observer includes and another only declares; a
   class defined in two owned files (an ODR violation the run should
   not hide); a variable template; a function defined only as a
   `= default` or `= delete`; a pure virtual function with no body; a
   function whose only definition is in a read-only file (must be
   reported even though the declaration is owned); `extern "C"`.
   A case where the check passes and the dependency's binary holds the
   name, or a correct migration that cannot be declared even with
   item 3, is reported with its pair.
