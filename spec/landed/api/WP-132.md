# WP-132 — version 0 without a name built from text: an identifier piece, a spelling at a name range, lookup in a scope

`docs/wp/WP-132.md`. The supervisor's rulings on the three places where
version 0 left a transform no way to write a name but a string
(`spec/landed/api/WP-091-effects.md`, "Disagreements"), written into
`spec/api.md` and built in `crates/slip_script` and `<slip/meta.h>`.

## What was built

- **`lookup(scope, identifier)`** (`spec/api.md` §6.1 rule 8; operation
  24, `lookup_in`; counter `api.op.lookup_in`; macro
  `__slip_lib_meta_scope_lookup`). `Subject::lookup_in` answers `None`
  for an entity that is no scope (the host's `wrong_kind`).
  `KilnSubject` answers from the same per-scope index as `lookup`
  (`kiln_subject/lookup.rs`, `lookup_in_scope`): a scope of rule 4, a
  class template specialisation, or a typedef name for linkage purposes
  (the class it names, found in the index of the typedef's parent). A
  specialisation or a member class of an instantiated class is first
  taken to the declaration whose written definition it comes from
  (`written_scope`, ruling on item 4).
- **`identifier(name)`** (§7.1 rule 7; operation 68, `code_identifier`;
  counter `api.op.code_identifier`; macro `__slip_lib_meta_identifier`):
  a piece of its own kind, `HeldPiece::Identifier` in the host and
  `Piece::Identifier { text, key }` in the run output, rendered
  `identifier("name")`, or `identifier(<key> "name")` with a key, as a
  spelled piece shows its key. It is never joined with a literal or
  another identifier.
- **The identifier piece in the formats** (`spec/edits.md` §4.2, ruling
  on the encoding): `Piece::Identifier { text, key: Option<KeyId> }`,
  tag 3, `(bytes, opt<KeyId>)`, in `crates/slip_model` (encoding, JSON
  `{"identifier": bytes}` plus `"key"` only when present, the order, and
  the invariant that the text is one plain identifier, checked by every
  reader: `transform::is_plain`), and carried through reduce
  (`KPiece::Identifier`, `P2::Identifier`, tag 3 in its record
  encoding), apply (`compose.rs`: a keyed identifier piece is an
  obligation where its text lands, like a spelled piece; `build.rs`: its
  length), and xtask's transform mutations (a keyed identifier's key is
  mutated as a spelled piece's is). The scheme and the shard's version
  stay.
- **The key of an identifier piece** (`spec/api.md` §7.2 rule 6, ruling
  A). `Effects::replace` notes, for a replacement that is exactly one
  identifier piece at the name range of references, each reference's
  referent's origin and that origin's key (`Effects::named`). `Host::finish`
  gives the piece the key when every noted origin has the one key and is
  declared renamed to exactly the piece's text by then; otherwise none.
  Nothing is decided at `replace`, so the order of `replace` and
  `expect_renamed` does not matter. `spec/verify.md` §10's records,
  `slip_digest` and `slip_verify` are unchanged: an obligation from a
  keyed identifier piece is an obligation.
- **A spelling at a name range** (§7.2 rule 1, "At a name range"): in
  `Effects::replace`, after the extent's sibling rule, `at_a_name` takes
  a range that is no reference's extent and is the name range of
  references or declarations (`Subject::references_named_at`,
  `Subject::declarations_named_at`, both new; `KilnSubject` answers them
  from two lazily built maps beside `by_extent` in `references.rs`). The
  code must be exactly one spelled piece, and the conditions hold for
  every reference and declaration named there, else `invalid_argument`.
  The host checks the subject's answers (each live, none twice, each
  with that name range) and names the method on a host failure. At a
  range that names declarations only, the record is
  `identifier(E's identifier)` with no key (ruling B).
- **The rename example** (`resource/examples/rename_function.cpp`):
  `renamed()` and its `rfind("::")` are gone; the new name is checked
  with `lookup(parent_of(f), to)` and written with `identifier(to)`.
  `tests/examples.rs` `wp132_no_example_writes_text` runs every directory
  of `tests/api/examples/` asking for `api.op.code_text` and requires it
  absent, and requires every file of `resource/examples/` to be run.

## Decisions

1. **Names of the operations and counters.** The WP's `api.op.identifier`
   and `api.op.text` are, by §7.6 rule 6's rule (`api.op.<row name>`),
   `api.op.code_identifier` and `api.op.code_text`; the second lookup is
   `lookup_in` (`api.op.lookup_in`).
2. **`$` and code points outside ASCII are `unsupported`**, not
   `invalid_argument`, for `identifier` and the second `lookup` as for
   `expect_renamed` and `lookup`: §6.1 rule 1 is one check wherever an
   identifier is taken, and a test (`effects/s7.5-r3-…`) holds
   `identifier` and `expect_renamed` to the same answers.
3. **The feature-test values are `202611L`**, the month of the
   specification's change.
4. **Which rule a range takes.** A range that is some reference's extent
   takes the extent's rule (sibling, else fully qualified). A range that
   is only a name range takes the new rule, which refuses rather than
   fall back. Any other range is fully qualified, as before.
5. **A specialisation as a scope** (ruling on item 4) has the members
   written in the definition it comes from: its own for an explicit or a
   partial specialisation; for an instantiation, implicit or explicit,
   Kiln's `SpecInfo::from` (the primary's pattern or the partial
   specialisation chosen); for a member class of an instantiated class,
   `MemberSpecInfo::instantiated_from`; repeated as
   `slip_kiln::written::origin` repeats (`written_scope`, at most 256
   steps). A specialisation whose `from` is still the class template
   was never instantiated: nothing is found in it. The pin gives the
   definition in every shape the ruling names (primary, partial, member
   class, explicit instantiation definition); nothing had to stop.
   `written_scope` is a sibling of `origin`, not a call of it: `origin`
   takes an instantiation to the primary template, never to the partial
   specialisation it was instantiated from, which is what a scope needs.
   The walk ends at the definition's entity (`KilnSubject::entity`): a
   primary template's pattern is indexed under its template.
6. **The example looks in `f`'s own scope** (`parent_of(f)`, an inline
   namespace if `f` is declared in one), which is the scope the rename
   rule renames in (§7.5 rule 3), not the scope written in `RENAME_FROM`.
7. **The key is all or nothing at a name range** (ruling A). When the
   references named at one range have origins with different keys, or
   one of them is not declared renamed to the piece's text, the piece
   has no key: one piece cannot carry two keys, and a key for some of
   them would check a name against an entity it was not written for.
8. **A declaration's name takes an identifier piece** (ruling B), so a
   spelling there is never an obligation that is always `unseen`
   (`spec/verify.md` §10.7). The record then does not say which entity
   was meant; WP-133's declarative references
   (`__slip_lib_meta_declarative_references`) are where that changes.
9. **The key is decided by the references at a range alone** (review
   ruling 1). A range that is the name of references and of
   declarations too (a macro argument expanded into both) takes the
   references' key, and the obligation is theirs; the declaration there
   is judged by the digests. §7.2 rule 6 said "no key when the range is
   a declaration's name"; it now says "when the range names no
   reference", and §7.5 rule 3 says the key is given whatever
   declarations are named at the range. `code/s7.2-r6-a-declaration-and-a-reference-at-one-range`:
   the declaration is another entity (`::x`), the key is `o::x`'s.
   `code/s7.2-r6-a-redeclaration-and-a-reference-at-one-range`: the
   declaration is a redeclaration of the renamed `o::x`; the request
   written for the declaration and the one written for the reference are
   one edit, and it has `o::x`'s key, which is right: the post-image
   name there is the reference `o::g(1)`, which denotes the renamed
   entity, and the redeclaration is renamed by the rule the digests
   apply.

## Open points for the coordinator

- **(a) Names that are keywords of the implementation only.**
  `identifier()` and `expect_renamed` accept `typeof`, `__attribute__`,
  `__restrict`, `_Bool`, `defined` and `__VA_ARGS__`, as §6.1 rule 1 is
  written (they are not in [lex.key]); the post-image then fails to
  parse, loudly. Whether §6.1 rule 1 should refuse the implementation's
  keywords and the preprocessor's reserved names is not decided here.
- **(b) The shard conversion carries the key.** Nothing yet converts a
  `RunOutput` into a shard (WP-092); that conversion must carry an
  identifier piece's `key`, or every keyed identifier loses its
  obligation.
- **(c) The idiom of item 4 with `spell`**, below: `docs/wp/WP-137.md`
  (resolution 1), launched when this merges.

## Open: the idiom of item 4 with `spell`

The ruling's idiom, `lookup(parent_of(referent_of(r)), "g")` and then
`replace(name_range_of(r), spell(g))` at `w.f()` with `W<int> w`,
cannot be built as written. The lookup half works in every shape
(`tests/subject_entities.rs` `s6_1_rule8_lookup_in_an_instantiation`):
`g` is the template's own `W::g`. But `spell(W::g)` is refused when the
code is made, by §7.1 rule 4 (`unsupported`: "the entity cannot be named
by a qualified name without template arguments"), before `replace`
knows that the range is a name range that takes the sibling rule and
would write `g`. The rule was not changed here. The directory
`tests/api/lookup/r8-the-idiom-in-an-instantiation` holds the idiom
as the ruling writes it, marked `xfail` with the report it should give,
and is the reproducer. Two ways to resolve it, for the coordinator:

1. `spell` of an entity with no qualified name is made (with its key),
   and refused at `replace` only where the range takes the fully
   qualified rule; at a sibling or name range it is the identifier.
   This changes §7.1 rule 4 and the `code/s7.1-r4-*` directories.
2. The idiom writes `identifier("g")` instead of `spell`: no key (it is
   no rename, ruling A), so only the digests judge it; nothing changes
   in §7.1.

## The reviewer's question

Can the host attach a key to an identifier piece at a reference where
a correct rename may leave the name denoting something else (so a right
transform fails verification), or attach one where no observer can see
the name (a macro argument not expanded, a skipped group, a name resolved
only at instantiation), so that a correct rename becomes `unseen` and the
run fails? And conversely: is there an edit that writes the new name at a
reference, as the rename example does, whose piece gets no key and so is
checked by no obligation, only by the digests? Look at `Effects::replace`
(which references are noted: `references_named`, `named_at`) and
`Host::finish` (when the key is given), and at a reference reached
through a using-declaration, which the sibling rule of §7.2 rule 1
excludes and the key does not.
