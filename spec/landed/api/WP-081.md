# WP-081 — slip_script: the operation table, the wire encoding and the run output

`crates/slip_script` (`wire.rs`, `subject.rs`, `host.rs`, `output.rs`,
`fake.rs`) implements §3, the statuses of §4, §5.2, the queries of §3.2
and the content of §7.6. This file records where the specification left a
choice and how the code makes it. Tests are in
`crates/slip_script/tests/wire.rs`.

## Decisions

1. **Order of checks.** A call is checked in this order: the operation
   number (254), the shape (255: the integer count, and text given to an
   operation that takes none), the arguments in order, the operation's own
   refusals, then the subject's answer. The first that fails is the status.
   Absent text is empty text, so an operation that requires text (`lookup`)
   refuses empty text as `invalid_argument`, not 255.
2. **254 and 255 are failures like the others.** They take the next
   ordinal, have a message, and are in the failure list; `error_message`
   serves them (§3.5 rule 3 numbers "the failures of a run").
3. **File handles are the host's.** The host issues a file handle (from 1)
   the first time it gives out a range in that file, and a range argument
   whose file handle it did not issue in this run is `invalid_handle`
   (§3.4 "the file handle is live", read as "issued in this run", like
   every other handle). Within an issued file any `lo <= hi <=` length is
   accepted, the empty range included (§3.4 asks no more).
4. **Info handles.** Indices are issued per sort, from 0, in the order the
   host first returns a value; the same value always has the same handle in
   one host, which is what makes `==` the identity of §5.1 rule 2.
5. **`is_editable` of the null range at L0** is `invalid_handle`, like every
   other range argument. The header never sends it (it answers `false`
   itself, §6.6 rule 6).
6. **Identifiers** (`lookup`, and `host::check_identifier` for WP-088): a
   letter or `_`, then letters, digits and `_`, ASCII only. A name that is
   well formed but for bytes at or above 0x80 is `unsupported` (Open
   question 10: this version does not classify them); a malformed name is
   `invalid_argument` even when it also has such bytes. `$` is not an
   identifier character. Keywords are not rejected: they match nothing.
7. **Limits are inclusive.** A qualified name of exactly 2^12 bytes is
   accepted; one more byte is `limit_exceeded` (§7.7 "exceeding").
8. **An answer too large for the result word** (2^28 integers or bytes, or
   more; §3.3) is `limit_exceeded`, checked before any handle is issued.
9. **Sorts are checked by the host before the subject is asked**, with the
   statuses §6 names: `identifier_of` of an expression, `parent_of`,
   `declarations_of`, `references_to`, `calls_to` of a non-entity,
   `entity_of` of a non-declaration, `referent_of` of a non-reference,
   `name_range_of` of an entity or an expression, `extent_of` of an entity
   and the `callee`/`arguments` operations of a non-expression are
   `wrong_kind`; `extent_of` of a declaration is `unsupported`. An `Err` or
   `None` the subject returns for a sort it was asked about becomes the
   status the trait names (`None` is `wrong_kind`).
10. **An inconsistent subject is a host failure** (`Err`, §2.8
    `host-failure`), never a status: a value it returns that is not live, a
    range outside its file, the same value twice in one sequence (§5.3
    rule 2), text whose length is not the range's, or kind bits that
    contradict the value's sort (a kind bit of 8 to 13 on a non-entity,
    bit 16 on a non-declaration, bit 17 on a non-expression, or a sort bit
    other than the value's).
11. **The place of a failure** (§2.8 rule 3) is `Subject::place` of the
    live value the refusal concerns, own or nearest. Refusals of a handle,
    a range or text, and statuses 254 and 255, have none.
12. **Counters the host keeps.** `api.op.<name>` counts the calls of each
    operation that succeeded: a failed call is not counted, so that a
    failure changes nothing but the failure list (§3.5 rule 2) and
    `finish` after a failed call equals `finish` without it.
    `api.edits` and `api.reports` count the canonical output (identical
    requests are one edit, §7.6 rule 1). `api.host_calls`, `api.steps` and
    `api.peak_bytes` are the evaluator's (Kiln's `RunReport`) and are
    added by the driver (WP-089), not by `Host::finish`.
13. **The canonical form** (`RunOutput::canonical`): pieces are normalised
    first (§7.1 rule 6), so identity by content does not depend on how a
    code value was built. Edits are ordered by place (the file's `FileRef`
    as derived: path, size, content digest; then `lo`, `hi`), then by
    pieces in the derived order (literal before copy before spelled, then
    by content). Joining two identical requests unions their notes and
    keeps the higher tier. A group's members are rewritten to the joined
    edits, groups sharing a member are merged, and a group left with fewer
    than two members (an empty group, or one whose members were joined
    into one edit) is dropped. Reports are ordered by (place, severity,
    message) with `attached` last as a tie-break; a report without a place
    sorts first. Rules are ordered by their encoding, whose prefix is the
    self-delimiting encoding of the match, so the order is the rule
    table's; identical rules are one. Counters are sorted by name.
14. **`Report::attached`** (§7.6, §7.4 rule 3) is `true` when the report is
    attached to the nearest place the host can name instead of the place of
    the value it was given; `false` for the value's own place, a range, or
    no place.
15. **Effects (operations 64 to 84)** are shape-checked and then
    `unsupported` until WP-088 implements them.

## Not done

`api.unresolved_spelling_matches` (§6.5 rule 6, §7.6 rule 6) is not
produced: counting unresolved names spelled like an entity needs a question
the `Subject` trait does not ask. Producing a 0 would claim that nothing was
missed, so the counter is absent until the trait gains the method.
