# WP-088 — slip_script: the effects

`crates/slip_script/src/effects.rs` implements operations 64 to 84 of
§3.2 (§7.1 to §7.5, §7.7) inside `Host::call`, and
`RunOutput::render` (`output.rs`) the rendering of §7.6. This file
records where the specification left a choice and how the code makes it.
Tests are in `crates/slip_script/tests/effects.rs`. Decision 15 of
`WP-081.md` (effects are `unsupported`) no longer holds.

## Decisions

1. **The staging of `Host::call` is kept.** An effect is validated in the
   immutable stage (`Host::effect`, called from `answer`): every refusal,
   every question to the subject and every check of its answer, every
   limit, and the whole record to make (the pieces, the text chosen for a
   spelled piece, the places). `deliver` hands it to `Host::record`, which
   only stores it and cannot fail. So a refused request, and a request the
   subject answered inconsistently, record nothing (§4 rule 3, §3.5 rule
   2), and the counter `api.op.<name>` counts it only if it succeeded.
2. **The null handles** (§3.2, as amended). Code handle 0 is the empty
   code and group handle 0 is no group, wherever either is taken: they are
   the header's default `code` and `group`. An operation whose result has
   no piece (`text("")`, a `cat` of empty codes) returns 0 and holds no
   code value, so it counts against no limit. Code and group handles are
   issued from index 0 in the order made; any other value of tag 5 or 6,
   or a handle of another tag where a code or a group is taken, is
   `invalid_handle`.
3. **Order of checks**, after the shape (`WP-081.md` decision 1): the
   arguments in order (handles and ranges, then the length of the text),
   then the refusals of the operation in the order its section lists them,
   then the subject's answers, then the limits on what the run holds.
   - `replace`: range, code, group, note length; empty range
     (`invalid_argument`); `not_editable`; a range no query returns
     (`invalid_handle`, decision 6); edits requested; the spelling
     (decision 5); pieces and bytes in pieces; text held.
   - `report`: where-kind and its integers, the value or range; severity;
     message length; reports; text held.
   - `expect_changed`: value; reason length; an entity or a declaration
     (`unsupported`); a null extent (`unsupported`); `Subject::unit_keys`;
     declared changes; text held.
   - `expect_renamed`: entity (`invalid_handle`, `wrong_kind`); name
     length (`limit_exceeded`); identifier (`invalid_argument` or
     `unsupported`, `WP-081.md` decision 6); the entity's own identifier
     (`invalid_argument`); a different name declared before
     (`invalid_argument`); `Subject::rename_rule`; text held.
   - `spell`: entity; `Subject::qualified`; `Subject::entity_key`; code
     values, pieces, bytes in pieces.
4. **A spelled piece holds its fully qualified text from `spell` on.**
   §7.2 says the text is chosen when the edit is recorded; of the two
   spellings only the sibling rule depends on the place, so the qualified
   text (rule 2, which depends on the entity alone) is computed once at
   `spell`, with the key (decision 8 of the package), and `replace`
   decides between it and the identifier. The qualified text counts in
   the bytes held by the code value (decision 7).
5. **The sibling rule** (§7.2 rule 1) applies when the code is exactly one
   piece, a spelled one (after normalisation: `cat(text(""), spell(e))` is
   one piece), and `Subject::references_at(r)` is not empty. For each
   reference there, the host checks the subject's answers (live, listed
   once, extent exactly `r`, a name range that is not empty and lies in
   `r`) and evaluates the conditions; they must hold for every reference
   and the name ranges must be one range (§7.2 rule 1, as amended: two
   name ranges for one extent leave no single range to narrow to). The
   narrowed edit's tiers are `Subject::tiers` of the name range
   (`WP-102.md`). Condition 1
   ("E has an identifier") is evaluated but cannot fail for an entity
   `spell` accepted (§7.1 rule 4).
6. **`replace` takes only a range a query returns** (§7.3 rule 2 and §5.2
   rule 2, as amended). The operations that return a range are
   `name_range_of` and `extent_of` (§6.6 rules 1 to 4); no other
   operation of §3.2 returns one (`source_text_of`, `is_editable`,
   `code_copy`, `replace` and `report` take a range; the others neither
   take nor give one). `Subject::tiers(r)` (`Subject::tier` before
   `WP-102.md`) answers a set of tiers that is not empty exactly when `r`
   is a range one of those two returns for some value of the subject
   unit, whether or not the transform asked for it, and `None` for every
   other range, including one inside such a range; `replace` refuses
   `None` with `invalid_handle`. So a range built inside an extent (`M(f`
   of `M(foo) + foo`, half a token) is forged, and a forged range equal
   to a real one is that one, with that one's tier (§5.2 rule 2). The
   tiers of an edit are `Subject::tiers` of its range; the empty set is a
   host failure (`WP-102.md` decision 3; a tier other than 0 or 1 was,
   before). The other operations that take a range keep
   `WP-081.md` decision 3: any in-bounds range of an issued file, since
   only its bytes matter (§3.4, as amended). This supersedes the first
   version of this decision (any range inside a name range or an extent,
   and `unsupported` for any other), under which a forged range inside an
   extent of tier 0 that contains a macro argument was recorded at tier 0.
7. **Limits** (§7.7, as amended). Each is inclusive (`WP-081.md` decision
   7). The table's counts of code values, pieces per code, edits, groups
   and reports did not bound what a run holds: `cat` copies piece lists
   and `replace` copies a code's pieces into the edit, so 2^22 code values
   of 2^16 pieces, or 2^20 edits of 2^16 pieces or with 2^12-byte notes,
   are far beyond any memory; and `expect_changed` had no bound at all.
   Three totals were added and one restated, all counting what is held,
   once per code value, edit or declared change that holds it: pieces
   (2^22), bytes of text in pieces (literal bytes and spelled text, 2^28,
   the row that was "bytes in literal pieces"), distinct declared changes
   (2^20), and bytes of text arguments (notes, messages, reasons, new
   identifiers, 2^26). Pieces of intermediate code values count in the
   same total as pieces of edits and are never released (§7.7, as
   amended), so the total binds before the count of code values. Where
   each is enforced is in the handback of `docs/wp/WP-088.md`.

   **What a run holds at the default limits**, with the sizes of the
   types on a 64-bit target: pieces, 2^22 × 72 bytes (a held piece; a
   recorded one is 56) = 288 MiB; code values, 2^22 × 32 = 128 MiB;
   edits, 2^20 × 72 = 72 MiB; declared changes, 2^20 × 72 = 72 MiB;
   reports, 2^16 × 48 = 3 MiB; groups, 2^20 × 24 and one index per
   member = 32 MiB; note lists, 2^20 × 24 = 24 MiB; text in pieces,
   2^28 = 256 MiB; text arguments, 2^26 = 64 MiB. About 940 MiB, plus
   the allocator's overhead per allocation and the slack of growing
   vectors (under 2 GiB in all); plus one `FileRef` per file a place
   names (decision 15); plus one rule (184 bytes) and one name per entity
   declared renamed, which the subject unit bounds. The first version of
   this decision said "a few hundred megabytes": it left out the fixed
   size of each piece, code value, edit and change, and the paths
   (`Piece::Copy` and every place held a whole `FileRef`, so 2^12 copy
   pieces of a 4000-byte path held 16 MB that no counter saw).
8. **Declared changes are a set** (`Record::changed`). `expect_changed`
   records the entries `(key, place, reason)` not already recorded; a
   request whose entries are all there succeeds and records nothing
   (§7.5 rule 4), so repeating a declaration counts against no limit.
   `Subject::unit_keys` must give at least one key and no key twice.
9. **`expect_renamed`.** The host keeps the name declared for each entity.
   The same name again succeeds and records nothing (§7.5 rule 4); another
   name is `invalid_argument`; a declaration that was refused
   (`unsupported`, or a limit) does not claim the entity. The entity's
   own identifier is `invalid_argument` (§7.5 rule 3, as amended): a rule
   from a name to itself declares nothing. Two entities declared renamed
   to one name in one scope are both recorded; verification refuses the
   collision (`spec/verify.md` §2.1), not the host, which judges each
   request alone. The rule
   recorded is the subject's; the host checks that its `name` is the new
   identifier, since the rule undoes the rename (`spec/verify.md` §2.1).
   The fake built the rule the wrong way round (matching the old name);
   it now builds the undoing rule.
10. **Reports.** The place of an `info` is `Subject::place`, which
    answers one of four (`subject::PlaceOf`): the value's own place; the
    nearest place the host can name (`attached`, `WP-081.md` decision
    14); `Unnamed`, a value that has a place the host can name neither of
    nor near, which gives a report with no place and `attached` `true`
    (§7.4 rule 3, as amended: it says the place could not be named); and
    `Nowhere`, an entity with no written declaration, which gives no
    place and `attached` `false`, there being nothing to attach to. A
    refusal's subject place (§2.8 rule 3) is the range of the first two
    and none for the others. A
    where-kind other than 0, 1 or 2, or a nonzero integer the where-kind
    does not take, is `invalid_argument` (§3.2, as amended): these are
    values of the operation's arguments, not a wrong shape (255).
11. **An empty note is no note** (§7.3 rule 5, as amended): the edit's
    `notes` are empty, so a request with the default note and one without
    are the same record.
12. **`copy` of an empty range** is the empty code, not a piece
    (`WP-102.md` decision 4, §7.1 rule 2 as amended; it was a piece
    before, which `spec/edits.md` §4.2 does not allow in a claim). §7.1
    rule 2 refuses only the null range.
13. **Statuses a subject may choose** (`WP-081.md` decision 17, for the
    methods the effects call). `unit_keys` and `rename_rule` may return
    `Err(unsupported)`; any other `Err` is a host failure naming the
    method and the status. `tiers` answers `None` for a range no query
    returns (decision 6). `entity_key` and `qualified` have no status
    but `None`, which is `unsupported`; what the host checks of their
    `Some` is decision 5 for `qualified` (one or more identifiers, none
    empty, the last the entity's own), and nothing for `entity_key`,
    whose key the host cannot check. `extent` and `name_range`, asked by
    the effects, may return no `Err`, as for the queries. The trait's
    documentation says each of these.
14. **`RunOutput::render`.** One line per item in the output's order:
    `transform`, then `edit <i> <place> tiers <0|1|0,1> = <pieces> [note "…"]…`
    (`tier <t>` before `WP-102.md`),
    `group <i>…`, `report <place|-> <severity> "<message>" [attached]`,
    `changed <key> <place> "<reason>"`, `renamed <kind> <parent> <name>
    [disc <digest>] -> <parent> <name>`, `counter <name> <value>`. A place
    is `path:lo-hi`; text is quoted with `\\`, `\"`, `\n`, `\t` and `\xNN`
    for every other byte outside printable ASCII; a path is escaped the
    same way without quotes. A name other than an identifier is the name
    of its form in `spec/digest-kinds.md` §3.2, with its operand in
    parentheses if it has one: `operator(3)`, `conversion(<digest>)`,
    `literal_operator("_km")`, `local(2)`, `unnamed_by(<name>)`,
    `unnamed_ordinal(1)`, `property(7)`, `parameter(0)`, `constructor`,
    `destructor`, `deduction_guide`, `anonymous`, `content`, `order`.
    Every variant has its form: a rule's `to_name` is the subject's and
    may be any. The form is the documentation of the function; WP-090 may
    extend it.
15. **A run holds each file's identity once** (§7.7, as amended). A place
    (`output::Place`) holds an `Arc<FileRef>`, and the host makes one per
    file a place names (`Effects::files`, a memo of `Subject::file_ref`)
    that every place in the file shares, copy pieces included. An `Arc`
    rather than an index into a file table: equality and order stay the
    identity's (path, size, content), so the canonical order of §7.6 needs
    no renumbering, and an index would be a number the host assigned (§7.6
    rule 1). `slip_model`'s `FileRef` and `Place` are unchanged; only the
    field type of `slip_script::output::Place::file` changed. The memo is
    filled in the validation stage; it is a function of the subject and
    changes no output, so decision 1 holds of what a request records.
16. **The limits are judged from counts** (decision 1, stated). Each code
    value is held with its byte count beside its pieces. `cat` computes
    the size of its result (pieces, after joining adjacent literals, and
    bytes) from the counts of its arguments, in time proportional to the
    number of arguments, and `replace` takes the code's counts (or, under
    the sibling rule, one piece and the identifier's length); only when
    every limit passes is a piece copied. So a refused request does no
    work proportional to what the run holds. Each check is made once:
    `code_fits` for a new code value, `pieces_fit` and `text_fits` for an
    edit.
17. **Order** (§7.6 rule 1, as amended). The output is a function of the
    set of requests that succeeded. Which succeed may depend on their
    order through §7.5 rule 3 (the first name declared for an entity wins
    and a second different name throws at once: one evaluation's order is
    fixed by the program, and an immediate throw serves the transform's
    author better than a report after the run) and through §7.7 (which
    request reaches a limit first).
