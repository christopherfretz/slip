# WP-084 — slip_kiln: ranges, tiers 0 and 1, and unit order

`crates/slip_kiln/src/ranges.rs` and `Unit::token_end`
(`crates/slip_kiln/src/parse.rs`) bring `spec/api.md` §1 (unit order) and
§5.4 (tiers 0 and 1) and `spec/edits.md` §2.2 to code. Tests are in
`crates/slip_kiln/tests/ranges.rs`. This file records what the spec and
`docs/wp/WP-084.md` left open, how the code decides it, and where the
spec was corrected.

## The range is Kiln's

`slip_kiln::ranges` lexes nothing and has no rule of its own for a range
of file characters. The end of a token is `kiln_lex::token_end` (Kiln
`spec/lex.md` "End of a token"), called only through `Unit::token_end`,
which is the only holder in Slip of the unit's interner and lexer
options. The range of a span is `SourceManager::editable_file_range`
(Kiln `spec/source.md` "Editable file ranges"), unchanged.

## Decisions

1. **The tier** is derived from Kiln's own rules, not from the answer:
   tier 0 when `file_loc_at_macro_start(span.lo)` and
   `file_loc_at_macro_end(span.hi)` are both `Some` (both are the
   identity on a file location), which is when Kiln answered by its rules
   1 to 3 on the span as given; tier 1 when Kiln answered and that is
   not so, which is only through its rule 4. A span with one file end and
   one macro end that fails its rule gets no answer from Kiln (rule 4
   needs two macro ends), so it never reaches tier 1.
2. **An empty span** (`lo == hi`) has no range, whatever Kiln would say:
   version 0 of the API has no insertion point. So a `FileRange` always
   has `lo < hi`.
3. **A whole expansion is the invocation, at tier 0**, also when its
   tokens came from one argument: for `ID(foo)` with `#define ID(x) x`,
   the range of `foo` is the seven bytes `ID(foo)`, not `foo`. Both rows
   of §5.4's table hold for it; the range is tier 0's (§5.4 now says so).
   What a caller does with a name whose range is more than the name is
   the caller's (`spec/edits.md` §2.2).
4. **"Starts in file text and ends in an expansion"** (WP test 3) has no
   range only when the end is not the end of the expansion; a span that
   starts in file text and ends at the last token of an invocation holds
   the whole invocation and is tier 0 (Kiln's rule 3,
   `s5_4_test1_tier0_whole_invocations`).
5. **`FileRange`** derives `Clone, Copy, PartialEq, Eq, Debug` (the WP
   gave `Tier` its derives and `FileRange` none). Its fields are public;
   `lo` and `hi` are offsets in Kiln's text of the file
   (`SourceManager::text`), which are the file's bytes exactly when Kiln
   changed nothing on loading it (`spec/edits.md` §2.3, `file_recoded`,
   which `ranges` does not look at).
6. **`file_range(unit, first, last)`** ends the span at
   `unit.token_end(last)` and has no range when that is `None`; it does
   not check that `first` is a token or that `first` comes before
   `last` (Kiln's rules give no range for a span out of order).
7. **Unit order** is over locations, not only tokens. Each location has a
   chain to a root: a macro location's parent is
   `expansion_info(loc).expansion.lo` (the invocation for a macro entry,
   the parameter's place in the replacement list for an argument entry),
   a file location's parent is `include_loc` (the `#include` that
   entered its inclusion), and a location with neither is a root. Chains
   are compared from the root, element by element, by raw location; a
   chain that is a prefix of the other comes first (an invocation before
   the tokens it expands to, an `#include` before the included tokens).
   Two locations of one inclusion or one entry (`same_entry_distance`
   either way) are in raw order without walking. It is a total order on
   every location of the unit, equal exactly when the locations are
   equal; for two tokens of the sequence it is their order there. A
   location that is no token (an invocation's parentheses, an argument
   as written, a byte inside a token) is placed by the same rule.
   `Loc::INVALID` is a root. The walk is bounded at 2^16 steps, which
   only a malformed table reaches.
8. **Snippet additions** the tests need, in `slip_kiln::snippet`:
   `Parsed::unit()` (the `Unit` of a snippet parse, so that a snippet
   test calls `token_end` the way a worker does); `parse_with_tables`
   (`parse` with Kiln's written references and declaration extents
   kept, for test 6); and `preprocess` with `Preprocessed` (the token
   sequence after phase 4 of a snippet, built on the same source
   manager setup, resolver and feature queries as the parse, for test 4).

## Open questions

1. **Roots after the main file.** Roots are in raw order, and Kiln
   allocates the predefines buffer and the buffers of `-include` after
   the main file, so their tokens sort after the main file's, although
   phase 4 sees them first. No caller compares a predefined token with a
   written one in version 0 (every range is in a file of the subject).
   Placing them first needs the order in which the preprocessor entered
   the roots, which the source manager does not keep; it is a question
   to Kiln when a caller needs it.
2. **The kiln-boundary lint** (`xtask/src/lint/crates.rs`,
   `kiln_modules`) names `slip_kiln::kiln` and `slip_kiln::snippet` but
   not `slip_kiln::ranges`. Every function of `ranges` takes Kiln types,
   so only a crate that may name `slip_kiln::kiln` can call it; a later
   package that adds a Slip-typed entry should add `ranges` to the rule.

## What the tests found

- **Spans with no range in the digest pair tests** are all "invalid
  location" (an implicit expression) or "file to file, out of order": the
  semantic `CXXOperatorCallExpr` of a reversed rewritten C++20
  comparison (`a == b` found as `operator==(b, a)`), whose `begin_loc`
  and `end_loc` follow the semantic form's operands and so are out of
  written order, and the implicit member access of a structured binding. Neither
  is a disagreement with Kiln: the range of the written form is the
  caller's (`spec/api.md` §6).
- **Spans the property cannot check**: a token of the span is not in the
  phase 4 sequence (an integer literal inside `#pragma clang loop`, whose
  tokens the pragma handler consumes; an implicit `this`).
- No finding for Kiln: every range Kiln gave passed the property.
