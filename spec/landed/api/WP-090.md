# WP-090 — the script test format and its runner

Decided by work package WP-090 where `spec/api.md` §11 and the package
leave a choice. `crates/slip_script/src/script_test.rs` (behind the
crate's `testing` feature) is the runner; `crates/slip_script/tests/api.rs`
is the suite's binary; the suite is `crates/slip_script/tests/api/`; the
runner's own rules are tested by `crates/slip_script/tests/script_runner.rs`;
the lint is `xtask/src/lint/api_tests.rs`, tested by `xtask/tests/lint.rs`
`wp090_api_tests`.

## What was built

- `script_test`: `Script`, `load_script`, `run_script` (the package's
  interface), and what the suite is made of: `transform_header`,
  `subject_header` and `header_block` (the header lines), `run_group`
  (one compile, the scripts of a group in order), `run_each` and the trait
  `GroupRun` (retirement, testable without a transform that retires),
  `subject_files`, `render_completed`, `render_failed`, `line_col`,
  `load_failed`, `run_failed` (the rendering),
  `judge` and `Verdict` (the outcome), `discover`, `group_key`, `groups`,
  `run_suite`, `selects` (libtest's filter rule), `summary`, `bless_from`.
- `RunOutput::render_styled(f, &Style)`: `render` (WP-088) with the
  transform line, the positions of places and the names of keys given by
  the caller. `render` is `render_styled` with `Style::default()` and
  writes what it wrote before.
- `tests/api.rs`: a `harness = false` binary. It takes libtest's filter
  arguments, `--exact`, `--list` (as `name: test`), `--test-threads N`;
  accepts and ignores `--nocapture`, `--show-output`, `--quiet`, `-q`,
  `--include-ignored`, `--color`, `--format`; `--ignored` runs nothing
  (no script test is ignored); any other option is a usage error, exit 2.
  It prints `<OUTCOME> <name>[: what]` per case as decided, then
  `api: <n> passed, …`; exit 1 when any case is `FAIL`, `XPASS` or
  `ERROR`.
- `tests/api/format/` (one directory per header line, a completed run, a
  failed run, a transform that does not compile, one with no entry, an
  `xfail` that fails, a subject of three files, the subject's header
  lines) and `tests/api/values/` (§5.1 to §5.3: equality, null, the
  sorts, a forged `info`, a value kept across a failed call, text).
- The lint `api-tests` and the gate's refusal of `SLIP_BLESS`
  (`xtask/src/ci.rs` `bless_refusal`).

## The grammar of `expect.txt`

One of three forms; every line ends with `\n`, there is nothing after the
last.

```text
expect     = completed | failed | load-error
load-error = "error " load-name "\n"                 ; §12's name: transform-compile, entry-missing, …
failed     = "failed " kind " " quoted "\n"           ; §2.8's name; the first line of the diagnostic
completed  = "transform <id>\n" item*                 ; RunOutput::render (WP-088), items in canonical order
item       = edit | group | report | changed | renamed | counter
```

The items are `RunOutput::render`'s lines (its doc comment is their
grammar) with three differences:

1. The `transform` line is the literal `transform <id>`: the id digests
   the transform's command line, which holds absolute paths.
2. A place is `path:L1:C1-L2:C2`: the line and column of `lo` and of `hi`,
   both from 1, columns in bytes; `hi` is exclusive, so a range that ends
   at a line's end ends at that line's last column plus one, and a range
   that ends after a newline ends at column 1 of the next line. `path` is
   relative to the test's directory. A place in a file that is not one of
   the directory's keeps `path:lo-hi`.
3. A key is its name from the digest of the subject unit (`spec/verify.md`
   §6.1), quoted as text, where the digest names it; otherwise its 64
   hexadecimal digits.

Counters: only those of `// counters:` appear, in the output's order; a
listed counter the output does not have is `counter <name> absent`, after
the others, in the listed order.

`quoted` in `failed` is quoted as `render` quotes text (`\\`, `\"`, `\t`,
`\xNN`), of the diagnostic's first line only.

## The header lines

`transform.cpp`: `// spec:`, `// args:`, `// steps:`, `// bytes:`,
`// depth:`, `// owned:`, `// xfail:` (§11 rule 2) and `// counters:`
(§11 rule 3). `t.cpp`: `// std:`, `// target:`, `// args:` (§11 rule 1).

1. The header block is the leading lines that look like header lines
   (`spec/harness.md` §6.1: `//`, blanks, a word of ASCII letters and
   `-` beginning with a letter, blanks, `:`). Each must be exactly
   `// <key>: <value>` for a key of its file: one space after `//` and
   after the colon, a value that is not empty and does not begin with a
   blank. Blanks at the end of a line are not part of its value.
2. Errors, each naming the line: a line of the block that is not an exact
   header line of its file (a misspelt key, `//spec:`, `// Note:` as a
   first line, a subject key in `transform.cpp`); a key twice; an exact
   header line after the block (after a blank line, a comment, a `/* */`,
   a byte-order mark: it would be silently unread).
3. `// spec:` is required, of the form `§N` or `§N.M…` (decimal, no
   leading zero), then optionally a space and more (`§5.1 rule 2`).
4. `// steps:`, `// bytes:`, `// depth:` are decimal digits only, in the
   range of the budget's type; absent, the budget is `Budgets::default()`.
5. `// owned:` takes only `no`.
6. `// counters:` is a list separated by `,` (blanks around each name
   ignored); a name is ASCII lowercase letters, digits, `_` and `.`; a
   name twice is an error.
7. `// args:` (both files) and `// target:` split at spaces; `// target:`
   is one word. `// std:` defaults to `c++20`.

## The run

1. The groups: the directories with the same (`// args:`, bytes of
   `transform.cpp`) are one group (package rule 2); since `// args:` is
   part of the bytes, the bytes alone decide. A group compiles once, on a
   thread of `GROUP_STACK` (the driver's `STACK` and 1 MiB) bytes, and
   runs its directories in directory order. The groups run on
   `--test-threads` threads, each holding a jobserver token (of
   `MAKEFLAGS`) while it compiles and runs.
2. The subject is every file of the directory at any depth but
   `transform.cpp` and `expect.txt` at its top, by path relative to the
   directory, parsed by `slip_kiln::snippet` with `t.cpp` as the main file
   and the directory as the include root.
3. A subject with errors is an `ERROR` of the test (§2.4 rule 4: such a
   unit is not given to a transform).
4. A transform that reads, while it compiles, a file of its directory
   other than `transform.cpp` is an `ERROR` of the test: nothing of the
   subject is visible to the transform (§1), and two directories with the
   same `transform.cpp` would be different transforms.
5. A transform that does not load renders `error <name>`, except
   `host-failure`; a run that fails renders `failed …`, except
   `host-failure`. A `host-failure`, a run with no outcome, a group thread
   that panicked are `FAIL` with what happened, never a rendering: they
   are the host's, and `xfail` does not mask them.
6. Retirement (WP-089 rule 4): once a run retires the transform, each
   later directory of its group is `FAIL` "not run: the transform was
   retired by the run of `<dir>`: <why>", and is not run.

## Outcomes

`spec/harness.md` §6's: `PASS`, `FAIL`, `XFAIL`, `XPASS`, `ERROR`, and
`BLESSED`.

1. The rendering is compared with `expect.txt` byte for byte: no
   normalisation of line ends, trailing blanks or a final newline. A
   `FAIL` shows the first line that differs and the whole rendering.
2. `expect.txt` missing is `ERROR` (with the rendering), outside
   `SLIP_BLESS=1`.
3. An `xfail` test that differs is `XFAIL`; one that matches is `XPASS`,
   which fails the suite. An `ERROR` or a host's `FAIL` is never `XFAIL`.
4. A directory that is discovered and cannot be loaded (`load_script`:
   its header lines, a `t.cpp` that is missing or whose header lines are
   wrong) is `ERROR`; the others still run.
5. Discovery: a directory with a `transform.cpp` is a test; a file under
   `tests/api/` in no test's directory, a test inside another's
   directory, and no test at all end the suite with an error.
6. `SLIP_BLESS=1` writes the rendering to `expect.txt` of each selected
   test that is not `xfail` and whose file differs or is missing
   (`BLESSED`); one that matches is `PASS`. An `xfail` test is judged as
   without: its `expect.txt` holds what the host does not give yet, and is
   written by hand. Nothing is written from an `ERROR` or a `FAIL` of the
   host. `SLIP_BLESS` with any value but `1` is an error of the run.
7. `cargo xtask ci` never blesses: it fails at once when `SLIP_BLESS` is
   set, with any value, saying so.

## Decided where the spec was silent

- The transform line is `<id>` rather than the digest (above).
- Places are `file:line:col-line:col`, refining §11 rule 3's
  `file:line:col` with the end, as the package says; columns in bytes,
  `hi` exclusive.
- Keys are named by `slip_digest`'s `names` (the names verify uses); a
  key without one is its digest.
- `// counters:` is a header line of `transform.cpp`, in its block (§11
  rule 3 names it without a place); an absent listed counter is rendered
  `absent` rather than omitted, so the test says that it is absent.
- A failed run's line is `failed <kind> "<first line>"`; a load error
  `error <name>`.
- `host-failure` is never rendered (rule 5 of the run).
- Retirement fails the rest of a group (rule 6 of the run).
- `ERROR` is not masked by `xfail`; bless skips `xfail` tests;
  `SLIP_BLESS` takes only `1`.
- A transform reading a file of its directory is an `ERROR`.
- The subject is every file at any depth.
- `// owned:` takes only `no` (the only value §11 gives).
- The suite's binary is `harness = false`, so that one case is one
  directory with libtest's filter syntax; the module is behind a
  `testing` feature, enabled for the crate's own tests by a dev-dependency
  on itself.
- Threads: `SLIP_TEST_THREADS`, else the smaller of 4 and the cores,
  since each group holds a compiled transform with the standard headers.

## Costs

Measured on the shared 24-core host (load about 13), debug build:

- The suite, 20 directories in 20 groups: 42 s of CPU; 43 s wall under
  the shared jobserver with 4 threads (the tokens were taken by other
  builds, so the groups ran one at a time), 46 s with 1 thread, 11 s
  with 4 threads and no jobserver. The largest resident set is 45 MiB.
- One directory with a transform of its own: about 2.1 s of CPU (2.7 s
  wall for one alone, the binary's start included), nearly all of it
  compiling `<slip/meta.h>` and the standard headers it includes. A
  directory that shares its `transform.cpp` bytes with another adds only
  its parse and run, a few milliseconds.
- `tests/script_runner.rs`: about 8 s (it compiles about ten transforms).
- The lint: negligible (it reads the listed files and `spec/api.md`).

## For Kiln

Nothing. The limits met (no ranges or handles of the subject's files
before WP-085; `-D` refused in a snippet's arguments; a lookup of a
keyword refused) are Slip's or by design.
