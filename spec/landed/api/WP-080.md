# WP-080 — the transform session: compile once, run many

Decided by work package WP-080 where `spec/api.md` §2.1 to §2.5 and the
package leave a choice. `crates/slip_kiln/src/session.rs` is the
implementation; `crates/slip_kiln/tests/session.rs` the tests. Kiln
file:line citations are at Kiln `913a490bb`.

## Interface beyond the package's

- `TransformCommand`'s fields are private. `TransformCommand::new(resource_include,
  &author, file) -> Result<TransformCommand, OptionRefused>` is the only
  way to build one, so an unchecked word cannot reach Kiln (t8, b1).
  Accessors `resource_include()`, `file()`, and `command_line()`: the
  words given to Kiln after the program name, which is what §2.2's
  identity hashes as "the command line of §2.1".
- `OptionRefused { word, reason }` is `transform-option`: `word` is the
  word refused as given (the whole word for a joined value, the value's
  word for a separate one, the path for the file or resource directory).
- `Cancel` wraps Kiln's `CancelToken`: `new`, `cancel`, `is_cancelled`,
  `reset`, `Clone` (clones share the flag).
- `Entry` is `Copy` and carries the number of the session that gave it.
  `run` with an entry of another session is `RunFailure::ForeignEntry`
  and does not reach Kiln (f7).
- `RunFailure::Poisoned`: see "Runs" rule 6.
- `CompileError::Embed { path, line }`: see "Files read".
- `Handler: Send`, because Kiln's `HostCalls` is (see "Threads").
- `CompileError::CommandLine` also covers a front end that stopped for a
  reason other than errors in the unit: Kiln reports both the same way
  (`docs/requests/KS2-amendment-1.md` §1). It carries what Kiln wrote to
  standard error.
- `slip_kiln::Unit::inputs()` hands out the shard's inputs for the unit's
  lifetime (see "Threads" rule 3).

## The command line (§2.1 rules 1 to 3)

1. Kiln is given `-std=c++26 -fsyntax-only -fkiln-reproducible-time
   -I <resource_include>`, then each author option as two words (option,
   value) in the order given, then the transform file. The program name is
   `kiln`.
2. `-I`, `-D` and `-U` take their value joined (`-DX=1`) or as the next
   word. `-isystem` and `-include` take it as the next word only: a joined
   spelling is refused, because longer options begin with them
   (`-include-pch`, `-isystem-after`) and the author would get something
   other than what they wrote.
3. A value that is missing, empty, begins with `-` or with `@`, or holds a
   NUL byte is refused. Kiln's driver expands a word beginning with `@` as
   a response file (`kiln_driver/src/session.rs:81`, `rsp.rs:15-41`),
   which would bring in any option (b1); Kiln has no way to turn that off
   for a client's argv (K1). A value with `@` elsewhere (`-DW=a@b`) is
   kept.
4. The values of `-I`, `-isystem` and `-include`, the transform file and
   the resource directory must be absolute paths. The process's current
   directory is not stable in a worker (`parse_observer_with` changes it),
   so a relative path would name what the last subject's directory holds.
5. The transform file and the resource directory are refused as a value
   is (rule 3), and when not UTF-8.

## Entries (§2.3)

1. `entry` and `declares` use the members of the global namespace as
   `spec/api.md` §6.1 rules 3 and 5 define them: the declarations whose
   semantic context is the translation unit, or an inline or unnamed
   namespace it contains (at any depth, through linkage specifications and
   `export`). Using-directives and using-declarations are not followed:
   with `#include <numeric>` and `using namespace std;`, `declares("reduce")`
   is false, and a `transform` reached through `using namespace n;` or
   `using n::transform;` is `Missing` (t4). This answers the earlier open
   question 1.
2. A name that is not exactly an identifier (`ns::f`, `::f`, ` f `, the
   empty name) is `Missing`, and `declares` is false for it.
3. The order of §2.3 rule 2 is kept where a function fails two conditions.
   Kiln accepts a return of integral type and checks the return type
   before the definition, so a non-`void` function that is not defined is
   `Type`, not `Undefined`. A `= delete`d function is `Undefined`.
4. A member that is a function template, a variable or a type is
   `NotFunction`; two or more functions or function templates are
   `Overloaded`. `declares(name)` is true when a member named `name` is a
   function or a function template; a variable or type of a reserved name
   is not `entry-reserved`.

## Runs (§2.5, §2.8)

1. The budgets are passed to Kiln as given. Kiln checks the cancel token
   before the first step and before every host call, so a token that is
   already cancelled fails the run at once. A token cancelled from another
   thread stops a run under way; it stays cancelled for every later run
   until `Cancel::reset` (s5).
2. `RunFailure::Host` carries the handler's own message. Kiln's rendered
   note says `host call failed: <message>`.
3. `Uncaught` carries the exception's type name. Kiln's `what()` is
   dropped; the rendered diagnostic carries the object's content.
4. A Kiln failure kind this module does not know is `Host` with its debug
   text. An entry that returns a value after `entry` checked it returns
   `void` is an internal error (`unreachable!`).
5. `rendered` is the run's diagnostics as Kiln's `TextSink` writes them,
   with `DiagOptions::default()` (no colour, carets and line numbers on),
   against the transform's source manager. Kiln has no public renderer of
   a run's diagnostics (`docs/requests/KS2-amendment-1.md` §3). The sink
   is the driver's, but the driver's options (`-fdiagnostics-*` of the
   command line) are not applied, and none can be given. A run that
   completed without a diagnostic has an empty `rendered`.
6. A handler's panic unwinds out of `run`. The session is then unusable:
   Kiln has not put its run state back. Every later `run` returns
   `RunFailure::Poisoned` without calling Kiln (s2). A worker ends.

## Files read (§2.2)

1. `files()` lists each source-manager buffer that Kiln read from disk, in
   the order Kiln created the buffers: its name as Kiln recorded it (the
   path as given or as found on the search path, never resolved) and the
   digest of the bytes Kiln read. Kiln keeps one buffer per file
   (identified by device and inode, however it is spelled:
   `kiln_source/src/manager.rs:780-787`, `:864-868`), so no file is listed
   twice. A lazy buffer whose file changed gets a second buffer, with other
   bytes, and both are listed. A lazy buffer never read is not listed.
   Also not listed: in-memory buffers (the predefines, the command line's
   macros) and `__has_include` probes that found nothing.
2. After the unit compiles, every file of `files()` is scanned for a
   `#embed` directive and for `__has_embed`. A hit is
   `CompileError::Embed { path, line }` ("`#embed` is not supported in a
   transform"), because the resources they read are not in `files()` and
   so not in `TransformId` (K3). The scan works after line splices. It
   refuses `__has_embed` anywhere, comments and string literals included,
   and `embed` as an identifier on a logical line where `#`, `%:` or `*/`
   comes before it. So `// # embed` and `"__has_embed"` are refused, and
   `int embed;` is not (f1). A macro of the command line is in no file,
   so a `-D` whose replacement holds the letters `embed` is refused with
   the options (`f1_embed_in_a_macro_option_is_refused`; added at the
   merge). It costs about 19 ms over the 164 files
   (2 MB) of a transform including `<vector>` and `<string>`, measured on
   an unoptimised build. A compile of that unit takes about 2 s there.

## Threads

1. `with_transform` installs Kiln's stack guard on the calling thread for
   `stack` bytes below the call (`kiln_sema/src/stack_guard.rs:92`). The
   size is trusted. The guard overwrites the one the thread had, and stays
   installed after the call, because Kiln has no way to restore the
   previous one. That holds also when `with_transform` is called inside a
   handler or inside `parse_observer_with`'s closure: the thread's guard
   is then replaced.
2. `Session` is `Send`, and `run` may be called from another thread, for
   example a subject unit's front-end thread inside
   `parse_observer_with`'s closure. The run is checked against **the
   compiling thread's** stack guard, not the calling thread's. The unit's
   state copies the guard current when it was created
   (`kiln_sema/src/templ/mod.rs:613-617`, `stack_guard.rs:71-75`). See
   "Hazards accepted for now".
3. What is `Send` at this pin. A handler holding `&Ast`, `&SourceManager`,
   `&[FileRef]` and `&(dyn Fn(&[u8]) -> bool + Sync)` is `Send` (t1).
   `Ast` is `Sync` by its auto traits, which nothing in Kiln asserts.
   `SourceManager` is `Send + Sync`, asserted at
   `kiln_source/src/manager.rs:1784`. `&Unit` is not `Send`: its `Oven`
   holds `RefCell`s, `Cell`s and a `dyn HostCalls`, which are not `Sync`,
   so a handler cannot hold the `Oven` or a whole `slip_kiln::Unit`.
   `Unit::ast()`, `sm()` and `inputs()` hand out those parts with the
   unit's lifetime (`inputs()` added by this package), as does
   `real_path()`.
4. A panic inside Kiln before the closure is called becomes
   `CompileError::Panicked`. A panic of the closure, or after it was
   called, goes on to the caller.

## Hazards accepted for now

None at the current Kiln pin. Hazard 1 (the stack guard of a run away from
the compiling thread, K2) was lifted by Kiln WP-2410, which checks the
running thread's guard and restores Kiln's flag on leave
(`spec/landed/exec/WP-148.md` item 6).
