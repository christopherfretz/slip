# WP-085 — slip_script's subject over Kiln: references, ranges and text

`crates/slip_script/src/kiln_subject/references.rs` brings `spec/api.md`
§6.5 (references), §6.6 (ranges of references and declarations), §7.2
rule 1 (`references_at`, `found_directly`), §7.4 rule 3 (places), §5.4 and
§7.3 rule 2 (`tiers`) and §6.5 rule 6 (the unresolved-name counter) to
`KilnSubject`, and makes "written" (§6.4 rule 3) Kiln's
declaration-extent table's answer. Tests are in
`crates/slip_script/tests/subject_references.rs`; WP-083's in
`tests/subject_entities.rs` still pass, two of them with the answers this
package was to flip. This file records what the spec and
`docs/wp/WP-085.md` left open and how the code decides it.

## Everything is read when the subject is made

`Unit` is not `Sync` (it holds the Oven), and `Unit::token_end` and
`Unit::is_token_start` are the only end of a token and the only token
starts (WP-084). So `KilnSubject::new` and `from_snippet` read both of
Kiln's tables once, through `slip_kiln::written` (`written_refs`,
`decl_names`, `row`, `dependent_names`), and keep what they derive: one
record per reference (referent, first token, name range, extent, nearest
place, found directly), the name range or nearest place of each
declaration `decl_names` gives, the tiers of every range given out, the
unresolved names by spelling, and one bit per written declaration. Only
what needs no unit is built on first use: the references by origin (and
each `references_to` answer, sorted once), and the references by extent.

Making a subject **fails** over a unit parsed without the tables
(`slip_kiln::written::recorded` false): `Result<KilnSubject, String>`.

## Decisions

1. **A reference** is one `written_refs` entry in a role of §6.5 rule 3
   (Kiln's `Expr`, `Member`, `Nns`, `Type`, `Template`, `Base`,
   `MemInit`) whose referent, as the subject numbers entities, is a live
   entity. Kiln's stage 3 roles (using-declaration and -directive,
   namespace alias, elaborated, specialisation target, concept,
   designator) are §6.5 rule 4's and are skipped. So are the entries Kiln
   records in a rule 3 role inside a declarative context of rule 4: a
   name whose first token (or the macro invocation it came from) lies
   between a declaration-extent row's `qual` and its `name` (the
   qualifier of a declarator-id, of a class head, of an explicit
   specialisation's name), or within the whole of a using-declaration,
   using-directive or namespace alias. An entry whose referent is no
   entity of the subject is dropped; none was seen. "Lies between" is
   unit order (WP-084), decided without a linear scan: spans whose two
   ends are in one entry are raw intervals; the rest are intervals of the
   files their ends' expansions are in, plus, for a span whose end is
   inside a macro invocation, a list keyed by that invocation
   (`s6_5_rule4_a_declarator_qualifier_ending_in_a_macro`). A linear
   scan took 15 to 25 s per LLVM unit; this gives the same references.
2. **"An elaborated or friend reference"** (rule 4) is Kiln's
   `Elaborated` role: an elaborated type specifier that declares (`class
   X;`, `friend struct S;`). One inside a type (`struct S *p;`) is a type
   name, as Kiln records it (Kiln `spec/ast.md` §19, the role table) and
   as `spec/landed/edits/WP-067.md` lists it, and is returned
   (`s6_5_rule4_elaborated_type_specifier_is_a_type_name`). Proposed
   sentence for §6.5 rule 4 in the handback.
3. **One written name is one reference.** Entries equal in role,
   referent, where the name's first character is spelled (file and
   offset), the outermost macro invocation it came through, name range,
   extent and found-directly are one reference, whose first token is the
   first entry's: Kiln records the entries of one written name in the
   order they were preprocessed, which is unit order. (Keeping the
   earliest by unit order instead never changed an answer; mutant M24.) So an argument a macro uses twice, a header without
   a guard entered twice, an X-macro file read under two definitions of
   its macro, a default member initialiser used by two constructors give
   one reference per written name, while one written name that resolves
   differently in two entries gives one reference to each entity
   (`s6_5_rule1_a_header_resolving_differently_in_two_entries`).
4. **`name_range`** of a reference or a declaration is the range of
   Kiln's name span, kept only when both of these hold: the range starts
   where the name's first character is spelled, and the range's bytes are
   the referent's (or declaration's) identifier. An operator, constructor,
   destructor or conversion function has the empty identifier (§6.3), and
   no range is empty, so it has no name range. The range is then exactly
   one token: `ranges` never ends a range inside a token, and an
   identifier's bytes hold no token boundary. So the checks "the
   identifier is not empty" and "Kiln's end of the token is the range's
   end" were dropped; their mutants could not be told apart. So a name that is
   a whole macro expansion (`ID(foo)`, `#define foo2 foo`, `#define c c`),
   whose range is the invocation, has none, nor has a name written with a
   line splice. Its extent may still be given (decision 5).
5. **`extent`** of a reference is the range of the span from its first
   token to the end of its name (WP-084's `file_range_of_span`). The first
   token is the table's `first` (the outermost qualifier component), with
   two exceptions:
   - a **leading `::`** (the entry's `global`): the token just before
     `first`, on the line where `first` is spelled and in `first`'s own
     entry, lexed by Kiln (`is_token_start`, `token_end`), must be `::`
     (comments and blanks between are allowed, `:: /* x */ a::b`). When
     `first` comes from a macro whose invocation starts the name's range
     at tier 0 (`::NS::c` with `#define NS a`), the token before the
     invocation is looked at instead. Not found: no extent
     (`s7_4_rule3_global_not_found_then_the_written_rest`);
   - an **unqualified destructor name** (`p->~T()`), whose entry starts
     at `T`: the token just before must be `~` or `compl`, and starts the
     extent. A qualified one (`p->T::~T()`) starts at its qualifier.
   A name range outside its extent would make §7.2 rule 1 fail; it was
   never seen (a `debug_assert!`), and both would then be null.
6. **Ranges are `slip_kiln::ranges`'** and nothing else: this module
   decides which span to ask about and refuses answers (decision 4; a
   range in a buffer that has no subject path; a range in a file Kiln
   recoded on loading, whose offsets are not the file's bytes,
   `s5_4_a_recoded_file_gives_no_range`). Only `file_range_of_span` is
   used: every span comes from a table with its end, so WP-084's interim
   refusal of a span whose last token begins with `>` (which is
   `file_range`'s, finding the end of a last token) never applies, and an
   operator name ending at `>>` or `>=` has its extent
   (`s5_4_interim_span_ending_at_a_split_greater_does_not_reach_a_reference`).
   The other interim refusals reach references as WP-084 says: a range
   over a line beginning with `#` inside a comment, a span out of order
   (both: the reference is returned with no extent), `#embed` tokens (no
   name is one; the names around them keep their ranges).
7. **`tiers(r)`** is `Some` exactly for a range that a name range or an
   extent of a reference, or a name range of a declaration, is; the tiers
   of every such value with that range are joined
   (`s5_4_one_range_at_two_tiers`). Any other range is `None`, one inside
   such a range included.
8. **Places** (§7.4 rule 3). A reference: its extent; else the range of
   its written tokens `[first, end of name)` when that has one (a leading
   `::` not found), else its name range, else the outermost macro
   invocation that produced its name; else unnamed. A declaration: its
   name range; else the range of its name's tokens (an operator, a
   conversion function: `operator int`), else the invocation that
   produced its name or location; else unnamed. An entity: the place of
   its first written declaration in unit order; nowhere when it has none.
   A place other than the value's own is `Nearest`, which the report marks
   as not the value's own.
9. **`references_to(e)`** matches by the subject's own `origin` (WP-083's,
   §5.5), not `slip_kiln::written::origin`, so that it agrees with
   `Subject::origin`: an explicit specialisation is its own origin (it is
   written), so `V<int>` naming an explicit specialisation `V<int>` is a
   reference to the specialisation, while `V<long>` (implicit) is one to
   `V`. Unit order is by first token, then the longer reference first (at
   one first token, the one whose name ends later: `T::T` before `T`),
   then the table's order.
10. **Unit order** is `slip_kiln::ranges::unit_order` (WP-084), except
    that an invalid location sorts after every valid one, as WP-083's
    comparator did (its mutant M17, `review_unit_order_invalid_last`);
    `ranges` puts it first. `kiln_subject::unit_order` is the wrapper.
11. **`identifier` of a reference** (§6.3 "the identifier written there")
    is its referent's identifier: decision 4's check makes the name
    range's text equal to it whenever there is a name range, and an
    operator, constructor, destructor or conversion function name gives
    the empty identifier.
12. **The counter** (§6.5 rule 6) counts `dependent_names` records, each
    written name once (by where its first character is spelled), keyed by
    the bytes of the name's span. `unresolved_named` is always `Some`:
    the subject can tell, since the tables are recorded.
13. **`written(d)`** is: `d` has a row (`slip_kiln::written::row`) whose
    kind is not `ExplicitInstantiation`. Block-scope declarations, local
    classes and their members, template parameters, structured bindings
    and the declarations of a lambda's body have rows and are written
    (`s6_4_rule3_block_scope_and_template_parameters_are_written`,
    `review2_lambda_declares`, `review_f9_closure_call_operator`).

## Implicit declarations (WP-084 "What a consumer must not assume" 1)

Every node-to-range path, for an implicit declaration:

- **A reference**: every reference is a written name of Kiln's table;
  an implicit node (an implicit `this`, a range-for's hidden variables, an
  implicit conversion) records no entry and is no reference. A written
  name whose referent is implicit (`a.operator=(b)` naming the implicit
  copy assignment) is a reference with its written ranges: no name range
  (an operator), its extent `operator=`.
- **A declaration**: an implicit declaration has no row, so it is not
  written and no query yields it as a declaration; `name_range` and
  `place` are never asked of one.
- **An entity**: one with no written declaration (implicit, or made by
  instantiation) is `nowhere`; one with written declarations takes the
  first one's place, which is written.
(`s7_4_rule3_implicit_declarations`).

## Kiln holes pinned by tests

Each is a `kiln_hole_*` test stating today's answer:

- **K1** (`spec/landed/edits/WP-067.md`): an explicit instantiation of a
  function template has no row, so `template void a::tf<long>(long);`'s
  qualifier `a` is not known to be a declarator's and is returned
  (`kiln_hole_k1_explicit_instantiation_qualifiers_are_returned`).
  `written` is right there: no row, no declaration.
- **K3**: a later friend overwrites an earlier declaration's row, so
  `struct S;`'s name range is the friend's `S`
  (`kiln_hole_k3_a_friend_overwrites_the_row`). Found here, of the same
  kind: a qualified elaborated type specifier in a declaration (`struct
  n::S *p;`) overwrites the row of `S`'s definition, with the specifier's
  qualifier as the row's `qual`, so `n` is taken for a declarator's
  qualifier and not returned, and the definition's name range is the
  specifier's `S`
  (`kiln_hole_k3_a_qualified_elaborated_specifier_overwrites_the_row`).
- **An init-capture has no row**: not written, its entity is nowhere; its
  references are returned (`kiln_hole_an_init_capture_has_no_row`).

## What a reference without a range looks like to a transform

It is returned by `references_to` and `references_at` never gives it
(that needs an extent). `name_range_of` and `extent_of` are null;
`referent_of`, `identifier_of` and `found_directly` answer as for any
reference. `is_editable` of the null range is false and `replace` cannot
be given one, so a transform that edits every reference it can sees it,
cannot edit it, and should say so; `place` gives the nearest place (the
invocation, or the written tokens), marked as not the reference's own, so
a report about it points at the macro use. Verification (§6.5 rule 5)
catches a rename that leaves it: the post-image resolves differently.

## For Kiln

Against Kiln `913a490bb`. Each item gives what is wrong, a reproducer
and where it happens. Each one changes an answer of this subject.
Item 1 is pinned by a test. Items 2 to 7 come from the comparison
above: the kinds of declaration found without rows, each traced to the
Kiln action that makes it. Their reproducers have the shape of the
pair-test snippets where the comparison found them.

1. **A qualified elaborated type specifier overwrites the definition's
   row** (the same kind of fault as K3). Reproducer: `namespace n {
   struct S {}; } struct n::S *p;`. `decl_names` gives one `CXXRecord`
   row for `S`, whose name is line 2's `S` and whose `qual` is `n::`.
   Expected: the row stays the definition's, and a non-declaring
   specifier records nothing. Site: `crates/kiln_parse/src/decl.rs:2869-2874`
   (`ext_tag_head` records a row when `use_ == Reference`) and
   `crates/kiln_parse/src/extents.rs:271`.
2. **A range-for's declaration has no row.** Reproducer: `void f(int
   (&a)[2]) { for (int x : a) {} }`. `x` has no row. Site:
   `crates/kiln_parse/src/stmt.rs:1401` and `:1444`
   (`act_on_for_range_decl`).
3. **An exception handler's variable has no row.** Reproducer: `void f()
   { try {} catch (int e) {} }`. Site: `crates/kiln_parse/src/stmt.rs:1022`
   (`act_on_exception_decl`).
4. **An expansion statement's variable has no row.** Reproducer:
   `template for (auto x : {1, 2}) {}` in a function. Site:
   `crates/kiln_parse/src/stmt.rs:1618` (`act_on_expansion_head`).
5. **A requires-expression's parameters have no row.** Reproducer:
   `template<class T> concept C = requires (T t) { t; };`. Site:
   `crates/kiln_parse/src/templ.rs:2474` (`act_on_requires_param`).
6. **A contract result name has no row.** Reproducer: `int f() post (r: r
   > 0);`. Site: `crates/kiln_parse/src/contracts.rs:130`
   (`act_on_start_contract`).
7. **A label has no row.** Reproducer: `void f() { l: goto l; }`. Site:
   `crates/kiln_parse/src/stmt.rs:568` (`act_on_label`).
8. **An init-capture has no row.** Reproducer: `auto g = [y = 1] { return
   y; };`. This one is already known (WP-067), and is listed so the set is
   complete.

Items 2 to 8 make a written declaration "not written" (§6.4 rule 3), so
its entity is `nowhere`.
