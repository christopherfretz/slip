# WP-052 — the verify task, tree images, the worker's `PhaseTask`

What §5 (and `spec/exec.md` §2, §8.4, §8.6) left open, as
`crates/slip_cli/src/{image,verify_job,locate,worker}.rs` and
`crates/slip_exec/src/store.rs` now implement it. Written for the second
reviewer of the trusted base: every place a `verified` is made, every
early return of `verify`, every guard with its test.

## Where a `verified` is made

Two places, both in `verify_job::verify`, both through `slip_verify`:

1. **Step 3**, `AtSums::Equal => … verified(pre.id, rules_id)`: reached
   only after P1 to P3, G1, L1, G4, G5, O2 (an image other than the identity)
   and C have held. Test:
   `s5_2_verified_at_the_sums` (`verify.reparsed` 0).
2. **Step 5**, `verdict(comparison, pre.id, rules_id, params.limit)`,
   which is `verified` only for a comparison without findings: reached
   only after R1, G2 and R2 have held and `compare_groups` returned `Ok`.
   Test: `s7_2_exemptions_used` (a finding exempted by a declared
   `changed` key). Step 6 can only withdraw it (G3), and runs only when
   `total > 0`, so it never sees one.

Nothing else in `slip_cli` names `VerdictKind::Verified`.

- **C is unreachable without a defect.** Its three checks (scheme, groups
  strictly ascending, `tu == tu_digest(groups)`) are rules 1, 3 and 7 of
  the shard's digests validation (`slip_model::formats::digests`), so a
  stored pre shard that fails one is refused by the decoder in step 0
  (the job's `Err`, tested in `s5_2_pre_shard_altered_fails_the_job`),
  and the post digests come from the walk of this job. The check is kept,
  factored as `not_comparable`, and tested at unit level.
- **R2 is unreachable from real parses of one build.** The digests of a
  parse are a function of its inputs, which G2 has just found equal, and
  of the command, which is the observer's. Time does not enter (tried:
  an array sized by `__TIME__[7]` verifies at the sums 1.1 s after its
  map). R2 is what catches a map shard written by
  another build of the walk; the test edits one group's digest (and `tu`)
  in the stored shard.
- **G3 is reached by a race**: a thread replaces a header of the post
  tree by rename, alternating two contents, while the job runs; each
  attempt is a mismatch or G3, never `verified`, and G3 must be seen in
  200 attempts. Its second case alternates
  two contents that differ in a space only.
- **A `CompareError` is unreachable without a defect**: both lists come
  from walks of this job with detail for every group of `G`. Tested at
  unit level (`compared`).

## Decisions

- **`Params.pre`.** `spec/exec.md` §8.6 gave `Params` no `pre`, and also
  said `verify` reads neither the job's `post` nor the worker's arguments;
  step 0 needs `Job.post.pre`. The field is added (the more refusing
  reading: `verify` reads nothing but `Params`), and §8.6 corrected.
- **`ImageError::NotNormal`.** A root with a trailing `/`, or an empty,
  `.` or `..` component, is refused: G1 compares roots with real paths as
  bytes, so a root in another form would let a read of the subject
  through. Added to §8.6.
- **`from_post` checks the file system**: every root of a job's image must
  be, now, the real path of a directory (`canonicalize` gives it back),
  or the job fails. The coordinator made them so; one that changed since
  would make G1 compare with the wrong bytes.
- **`from_post` and `to_post` are M1** (the tree form); §8.6 listed them
  under M2. Moved.
- **The textual rule's example.** §5.1 said `-DROOT="/s"` is rewritten;
  by the bullet that defines the rule it is not (the root is followed by
  `"`). The bullet is kept and the example corrected (`-DROOT="/s/"` is
  rewritten). Either reading is safe, because a string becomes a file
  name only by naming a directory or a file to the front end, which L1
  or G1 then sees.

### The fix round (review of e9be834)

The review found five inputs giving a wrong `verified` (F1 a failed
`__has_include` through `-I../s/inc` from outside the roots; F1b the same
shadowing a header outside; F2 a response file; F3 another letter case of
the subject root; F4 drift outside the roots, compensated by the edit),
and two mutations no test killed (A7 the post-image digested without the
rules; B6 the pre-image digested under them). Each reproducer is a test,
and each fails on e9be834 with the wrong `verified` (F1, F1b, F3) or with
`verified` where a refusal is due (F2, F4, the three L1 tests); the
rules tests and `s5_1_directory_rewritten` pin the mutations.

- **"Under a root" is identity** (`image::Resolver`): device and inode of
  each directory, the nearest root ancestor deciding, paths walked as the
  kernel walks them (symbolic links followed, stopping at the first
  component that does not exist), caches by directory. A post root may
  now lie under a subject root (`Image::new`).
- **L1** reads Kiln's lookup log (`slip_kiln::ParseOptions::lookups`,
  `Unit::lookups`, `slip_kiln::Lookups`), and adds the spelled names of
  the files read, which catch a read through a symbolic link in the
  subject that the real paths of `inputs` hide.
- **The rewrite resolves** the path-bearing words, `directory` and the
  inputs, with a `-fmacro-prefix-map=` word per rewritten path that keeps
  its spelling (`s5_1_resolved_word_keeps_its_spelling`,
  `s5_1_post_command_resolves`). Words it does not list (`-Wp,`,
  `-Xclang`) keep the textual rule; L1 and G1 refuse what they reach.
- **Response files (G4).** Kiln's `rsp::expand` is public but reads from
  the process's directory and reports nothing it read, and has no reader
  to give it the post tree; reproducing its recursion here would be a
  private expander. So a command with an `@` word is `unverifiable`, the
  map job unchanged. A plan never has one: `spec/cdb.md` §4 expands
  response files when the plan is made.
- **O2 for the tree form** (item 5 of the ruling), not for the identity:
  with the identity every change since the map phase is the edit, and
  `g2_not_reached_at_the_sums` keeps it verifying.
- **`Image::parse` gives `f`'s value only with an `ok` shard**, as the map
  task drops the walk's.
- **A pre shard that is there but invalid, or of another observer, phase
  or round, is the job's `Err`**, not `unverifiable`: the store was
  altered, and an `Err` is reported as a failure of the run.
- **`pre` of an `unverifiable` verdict** is the content id of the pre
  shard whenever one was read (P2, P3 and every later guard), zero only
  for P1.
- **G3 compares the `inputs` as well as `tu`** (and needs the second parse
  `ok`): a post-image that changed in a way the digest does not see is
  still another image, and the names would come from it. The §5.3 row is
  corrected to say so.
- **Step 6 runs when `total > 0`** and `locate > 0`, also when `limit` is
  0 and no finding is kept: G3 is then still checked.
- **An empty `G` with sums that differ, an `ok` post shard without
  `inputs`, and an `ok` parse whose walk did not run are `Err`** (defects;
  no verdict is made from them).
- **G2 with an absent `inputs`** (not possible for an `ok` shard) treats it
  as an empty list, so it differs from any parse that read a file.
- **`--findings 0` and `--locate 0`** are accepted.
- **`Image` keeps the tree form only**: WP-074 adds the overlay variant
  behind the same functions.
- **`slip_cli` calls `unit.errors()`** inside the parse callback to skip
  the walk on a unit with errors, as the map task does.
- **The worker keeps `Params`** while `post.declared` and `post.image` are
  equal, updating `pre`; a job with another image or `Declared` makes new
  ones (`worker_phase_task`).

## What `locate` fills until WP-054

`name` only, of the first `locate` findings (those `limit` kept): the
first name, in byte order, of a unit of the key in the pre-image, else in
the post-image, cut to 4096 bytes at a character boundary. The pre side is
taken inside step 4's parse; the post side is a third parse (step 6).
`location` stays absent.

## What verifies at the sums today

With the walk at this base: variables, declarations, structs, namespaces,
function bodies, function template definitions, calls, enums, aliases,
member functions, `constexpr`, constructors with default member
initialisers, local variables, overloads, default arguments, string
literals, `virtual`/`override`, `static_assert`, a dependent call in a
template. Not: a class template specialisation used (`B<int>`) and a call
of a function template (`id(1)`): indeterminate, `pending.demand`, lifted
by WP-045; a local class and a lambda: `pending.local`, lifted by WP-040.

### Fix round 2 (re-check of the fix round)

The re-check found that the rewrite's `-fmacro-prefix-map=` words could
make the post parse spell one file two ways (F6: two routes to one file,
one rewritten and one not; F6s: the same through a symbolic link), that a
relative word became absolute, and that the command's own prefix maps
were not considered.

- **The invariant, and G5** (ruling 1). §5.1 now states it: every
  spelling of a file the post parse can produce is mapped to the
  spelling that file has when the post tree stands in the subject's place.
  `image::maps` checks it over every (post prefix, written prefix) pair
  the rewrite made, the identity pairs of kept words and the root pairs
  included, and the job refuses (G5) when two prefix-related pairs
  disagree, when a pair cannot be written as a map word, when a prefix map
  of the command's own overlaps one, or when a `#line` name begins with a
  mapped prefix. The maps are emitted longest post prefix first. Kiln's
  rule makes the order immaterial today: `kiln_source/src/manager.rs:691`
  (`set_macro_prefix_map`) sorts the entries by old prefix, descending,
  and `:703` (`remap_macro_path`) applies the first whose old prefix is a
  `strip_prefix` match, so the longest matching prefix wins whatever the
  command-line order. The emitted order is kept anyway, so that the
  maps do not rest on that rule; the mutation "shortest first" is killed
  only by the tests that pin the order (`s5_1_post_command`,
  `s5_1_post_command_resolves`): no parse sees it, under Kiln's sort.
  Every spelling channel goes through that one function: `__FILE__`,
  `__BASE_FILE__`, `__FILE_NAME__` (`kiln_pp/src/expand.rs:1300-1310`, the
  last the base name after the map), `__builtin_FILE()` and
  `std::source_location` (`kiln_sema/src/builtins.rs:3619`, `:3741`), and
  the presumed name of a `#line` directive. One test each in
  `f6_two_routes_to_one_file`: `__FILE__`, `__builtin_FILE()` and
  `source_location` show the change the real post-image would show
  (mismatch, and the truth differs); `__FILE_NAME__` and `__BASE_FILE__`
  (absolute and relative main file) are equal in the real post-image and
  verify; `#line` names are G5 (`g5_line_name`).
- **Decisions.** F3 (both forms) and F6s are now G5 `unverifiable`, not a
  mismatch: the rewrite resolves the word by identity to a post prefix
  another word reaches by another spelling, which is the conflict G5
  names. A prefix map of the command's own is refused, not composed:
  composing needs Kiln's longest-match rule applied across two
  independent lists, and a run with such a map is rare (`spec/cdb.md`
  keeps the word as written). Identity pairs (words kept as written, which
  name the same place from the post command) take part in the consistency
  check but are not emitted and are not checked against the command's own
  maps (they map nothing).
- **A relative word stays relative.** Only the leading part that reaches
  the subject root is replaced, by a relative path to the post root from
  the post command's directory, and the rest is kept byte for byte
  (`../s/./inc` becomes `../x/post-tree/./inc`):
  `s5_1_post_command_resolves` checks that two spellings of one directory
  stay two spellings.
- **What remains outside** (`spec/verify.md` §5.1): F7, an absolute
  `__has_include` into the subject, which Kiln's lookup log does not
  record (`f7_absolute_has_include`, ignored, needs Kiln); `Lookups::of`
  lists an absolute name under `/` already, so L1 covers it with no new
  code once the log has the entry. F4b, a header outside both roots added
  after the map where a failed lookup of the map phase tried it
  (`f4b_outside_header_added_after_the_map`, ignored, needs WP-117): O2
  sees the inputs only, so the pre shard would have to hold the negative
  inputs, each place a lookup tried and did not find (directory and name,
  as `Lookups::tried`), for the job to check that none of them exists
  now.
- **G4** is kept: it refuses a correct edit when the post command has an
  `@` word, which `slip_cdb` never gives (it expands response files when
  the plan is made, `spec/cdb.md` §4).
- **Two resolvers** (`Image::post_command` and the guards each make one):
  only G3 catches a directory swapped between the parse and the guard.

### Fix round 4 (A3)

A3: the command's directory `<s>/a/w` is a directory in the subject and,
after the edit, a link to `<b>/z/w` in the post tree; the word

### The sweep after WP-045

`h(x)` to `a::h(x)` in the `adl` tree now verifies, and is right to:
`a::h(X)` is the only viable candidate of the unqualified call, and the
only function `a::h` names, so the call, its argument and the
initialisation of its parameter are the same; only the qualifier
(`DeclRefExtra.qualifier`) and the call's `adl` bit (`CallExpr.bits-adl`)
differ, both `out`. Walking both images (`slip_digest` test helpers) on
this base and on main before WP-045 (d0f8de46): no unit differs on
either base. Before WP-045 the edit was a mismatch only because the
implicit constructors of `a::X` were indeterminate (`pending.demand`) on
both sides, edit or not. Two requalifications that change the call were
added and must be a mismatch: `r(x)` to `a::r(x)` (the qualified name
finds only the template, where the unqualified call chose the
non-template `::r(a::X)`) and `q(y)` to `::q(y)` (qualifying suppresses
the better `a::q(Y)` found by argument-dependent lookup). `n::g(1)` stays
a mismatch, `::h(x)` does not parse, `use(::S s)` verifies.
