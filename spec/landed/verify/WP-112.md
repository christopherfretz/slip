# WP-112 — the names digest: name-derived strings a unit only passes on

What was built for `docs/wp/WP-112.md`, the decisions it asked for with
the test that pins each, the `names` section's rows, the mutations, and
item 6. Normative text: `spec/digest.md` §9 "The names digest" and
§14.1 rule 6, `spec/model.md` §8.6, `spec/verify.md` §4.4, §6, §7.1, §8.

## 1. The walk

`crates/slip_digest`: `Walk::names` is the encoder of the unit (or
constant) being written; `Walk::feed()` returns it only when
`by_value == 0` and no owner is being numbered (`local::numbering_mode`).
`walk.rs` starts one per entity unit (`names_start`/`names_end`) and
attributes what a resolved unit (an inline body, an instantiation's
`<definition>`) feeds to the entity's unit, so the strings of
`h<int>`'s body are `h<int>(int, int)`'s. `canonical_decl`'s candidate
streams are suspended (`names_off`). Each constant memoised by content
digest has its own names digest (`Walk::const_names`, collected with
`by_value` at 0), fed as one `uv 4` entry where the constant is
written. `Output::name_strings` is one `NamesUnit {key, names, file,
name}` per key, sorted by key; for a key with several units,
`H("slip.names.key.v1", count, digests)` in the units' order. The
entries are the table of digest §9.

**The four decisions of item 1**, each with what pins it:

1. **`std::source_location`: `function_name()` only.** `line()` and
   `column()` are not fed; `file_name()` is written by value (WP-104 fix
   round) and not fed. Pinned by
   `equal/_/name-value-source-location-line-column` (line and column
   moved: units equal, names equal, so a fed line fails it) and
   `equal/_/name-value-source-location-alias-parameter` (only the
   printed signature changes: `names-changed f(Handle)`).
2. **A string written by value is not fed.** `feed()` is `None` under
   `by_value > 0`. Pinned by `names.rs`
   `read_at_compile_time_no_entry` (`static_assert` over the characters:
   no entry on either side), `differ/_/name-value-sizeof-template-argument`
   (no `names-changed` line: a fed by-value string would add one) and
   mutation M3. `sizeof(__func__)` reads only the array's type: the
   string stays symbolic and is fed, so those pairs note beside their
   `changed` (digest §9).
3. **A string reached twice is fed as the digest writes it.** A
   constant written by its content digest the second time feeds the same
   `uv 4` entry (its names digest, memoised with it) each time the
   digest writes it; a node is fed where the walk writes it. So the
   names digest follows the unit's stream exactly: no entry exists that
   the stream does not write. Pinned by
   `equal/_/name-value-local-constexpr-pointer` and
   `equal/_/name-value-pointer-into-backing-array` (`names-changed`,
   and `names.rs` `passed_through_a_constant_names_differ`). The
   constant's own entry (`uv 4`) is not reached by any pair: see
   mutation M8.
4. **`typeid(T).name()`.** Not a constant in Kiln: the walk sees a call
   of `type_info::name` on a `typeid` expression and writes it as a
   call. No bytes exist to feed; nothing is fed. Recorded in
   `spec/verify.md` "Open questions" (2).

## 3. The comparison and 4. the report

`slip_verify::names_changed(pre, post)` is a merge of the two sorted
lists: a key in both whose names digests differ. `Comparison.notes` is
filled by the verify job (`compare_groups` leaves it empty; `verdict`
destructures it as `notes: _`), so the verdict's kind, `total`,
`findings`, `used` and every counter are what they were. The job
computes the notes before step 3 from the whole lists, so a verdict
made at the sums carries them, and writes them to the post shard only
for `verified` and `mismatch`.

`Report`: `strict_names()` (before the first `add`); `add_at` reads the
notes of a `verified` or `mismatch` shard into a map by key (observers,
first observer in plan order, its note's name and file); under the
option the observer is `mismatch` and its `findings` and `listed` grow
by its notes. JSON member `names_changed {total, listed}` (only with a
note); text lines `note: name-derived string changed: <name> @ <file>`
then `note: <n> more (see the report)`; under the option each key is a
group `names_changed`, after every other kind.

**No command line.** `slip verify` (WP-053) reached `main` only after
this package was built, in `crates/slip_cli/src/args.rs` and
`verify_cmd.rs`, which are outside the package's files. So
`--strict-names` is `Report::strict_names()`. Wiring it needs two edits:

- a flag in `args.rs` `parse_verify`, whose `options_only` takes only
  options with a value, so a bare flag needs its support;
- a call of `report.strict_names()` right after `Report::new` in
  `verify_cmd.rs`, before the first `add`.

Left to WP-053's owner or a follow-up.

## The reviewer's two questions

**Can a note, or its absence, change a verdict without the option?**
No. `verdict()` ignores `Comparison.notes` (it is not read:
`compare.rs` `notes: _`); `Report::add_at` changes the state only
`if strict > 0`, and `strict` is 0 without the option. Tests:
`compare.rs` `notes_do_not_touch_the_verdict` (a comparison with and
without notes gives byte-equal verdicts), `run.rs`
`s7_1_names_changed_counted_once_over_observers` (ten noted observers
stay `verified`, `findings 0`), `s7_1_names_changed_beside_findings`
(a mismatch's `total` is its findings only), and `verify_job.rs`
`names_note_beside_verified` (a requalified parameter type: verdict
`verified`, `total` 0, one note). The absence of a note cannot change
a verdict either: the section is present whenever `digests` is (row 1),
so a missing section is a refused shard, not an empty list. Mutations
M4 and M5.

**Can a change to a name-derived string a unit passes on go
unreported?** Within what Kiln evaluates, no: every place digest §9
writes a string symbolically feeds its bytes (the `PredefinedExpr`
node, a pointer to a `PredefinedExpr` string or a source-location
string, a `__builtin_FUNCTION()` node, an `__impl` object's function
name, a constant holding any of these). Where the string is written by
value, the unit's digest differs: a finding. The residue: (a) a key
present on one side only gives no note, but then the key itself is a
finding (`added`, `removed`) or its unit differs; (b) a template
pattern's dependent string has no bytes, and its instantiations are fed
per instantiation key, so a pattern no observer instantiates is not
seen (the same as its digest, `spec/verify.md` §8 "Only analysed
observers"); (c) `typeid(T).name()` (item 1.4); (d) the `line()` and
`column()` of a passed-on `source_location`, by decision. Tests: every
pair of item 5 (`names-changed` lines), and the pair runners now fail
on a names change no line names (§14.1 rule 6), so the 89 pairs whose
names digests differ say so. Mutations M1, M2, M6.

## The coordinator's question: a pretty name read in a template

The case (`h<T>(T, decltype(ns::S::value))` against
`decltype(::ns::S::value)`, `sizeof(__PRETTY_FUNCTION__)` in the body,
clang 53 against 55).

1. **Reproduced** as `differ/_/name-value-template-pretty-written-read`
   (`exact derived`, `derived-changed h<int>(int, int)::<definition>`).
   `u` and the pattern `h` are equal; the instantiation's
   `<definition>` differs. So on this branch it is not a wrong equal:
   verify reports `derived_changed`, a finding. The differ runner
   ignores an unnamed derived difference, which is likely why the
   reviewer saw "no change" on the declared units.
2. **Why.** The pattern's `__PRETTY_FUNCTION__` is dependent: Kiln
   gives it type `Builtin(Dependent)` and no literal, so the pattern's
   unit writes the kind and the scope names, and nothing of the
   parameter type's written spelling (written spellings are not
   digested; WP-041's area). The instantiation's `PredefinedExpr` has
   the literal and the type `const char[53]` (`[55]`); `sizeof` reads
   the type, which is written by value, so the `<definition>` of
   `h<int>(int, int)` differs. `u` calls `h<int>` by key and holds no
   string.
3. **The sibling** (`take(__PRETTY_FUNCTION__)` in the body):
   `equal/_/name-value-template-pretty-written-passed`, `names-changed
   h<int>(int, int)`. Every unit is equal; the instantiation's body
   feeds its bytes (`void h(T, decltype(ns::S::value)) [T = int]`
   against `…(::ns::S::value)…`) to `h<int>(int, int)`'s names digest,
   so the change is a note. An `assert` inside a template is noted per
   instantiation.
4. **The rule, and its costs.** As built: the bytes Kiln evaluates in
   each instantiation are fed to the instantiation key's names digest
   where they are passed on, and written by value where they are read;
   the pattern feeds nothing because no string exists. Costs: each
   translation unit that instantiates the template notes it (the report
   counts a key once over observers, §7.1, so the cost is in the
   shards, one entry per instantiation key); a template no observer
   instantiates has no note, as it has no derived digest. The
   alternative (the pattern's unit writes its signature as written when
   its body holds a pretty-name use) would make the pattern differ on
   every respelling, which is exactly the content §9 keeps symbolic, and
   needs written spellings (WP-041). Not proposed. Nothing is left
   pending: no `# needs:` line for this case.

## WP-115's costs and holes, as the names digest sees them

`names.rs` `wp115_costs_note_beside_a_finding_or_a_real_change` digests
the six pending cost pairs (still pending for their digest
expectation, `# needs: kiln-srcloc-origin`) and pins the notes each
gives:

| Pair | Notes (units equal?) |
|---|---|
| `equal/_/name-value-cost-overload-plain-rename` | `f(int)` (no), `f(long)` (no) |
| `equal/_/name-value-plain-default-argument-holder` | `x::h()` (no) |
| `equal/_/name-value-holder-own-lambda` | `legacy::f()` (no) |
| `equal/_/name-value-cost-namespace-lambdas-shared-pretty` | `legacy::G` (yes), `legacy::H` (yes) |
| `differ/_/name-value-cost-plain-added-earlier` | `b::get()` (no) |
| `equal/_/name-value-cost-shared-plain-rename-other` | `f(int)` (yes), `f(long)` (no) |

**Can a change go unreported?** No. A cost writes a shared string by its
bytes; bytes written so are in the unit's digest, so a change of them is
a `changed` finding (and nothing is fed for them, as for any string
written by value).

**Can a note appear for no change?** Yes, but only beside a `changed`
of the same key. When a string moves between its entity's form and its
bytes (a holder gaining or losing a use elsewhere: `f(long)` above,
whose `"f"` is the same on both sides), the entries fed change (the
pointer's string is fed on one side only), so the names digest differs;
the move also changes the unit's digest, which is the cost WP-115
records. Every note on a key whose units are equal is a real change of
the string by the rule (`legacy::G`, `legacy::H` relocated; `f(int)`
renamed to `q`). Kiln's `kiln-srcloc-origin` answer removes both the
cost and these notes.

**The named holes** (C++26: reflection and contract strings sharing a
source-location string object). If such a string were written as an
entity's name and a rule made the unit equal wrongly, the bytes still
differ and are fed: the hole would give a note (a finding under
`--strict-names`), not silence. Neither is reachable at C++20 and below;
no pair.

## Mutations

Each mutant was applied, run on the narrowest tests, and restored before
the next.

| | Mutant | Tests | Result |
|---|---|---|---|
| M1 | the bytes not fed (all three feeders give `&[]`) | `slip_digest` `differ` (then `names`, `equal`) | caught: `differ` fails on the `names-changed` lines |
| M2 | the kind not fed (`uv 1` writes 0) | `differ` | caught: `name-value-func-against-function` |
| M3 | a by-value string fed (`feed()` and `feed_const` ignore `by_value`) | `differ` | caught: a names difference no line names |
| M4 | a note made a finding without the option | `slip_verify` `run` | caught: `s7_1_names_changed_counted_once_over_observers`, `s7_1_names_changed_beside_findings` |
| M5 | a note dropped under the option | `run` | caught: `s7_1_strict_names_makes_notes_findings` |
| M6 | a key on one side noted | `slip_verify` `compare` | caught: `no_note_for_a_key_on_one_side` |
| M7 | the section left out of a `verify` shard | `slip_cli` `verify_job -- names_` | caught: all `names_` tests |
| M8 | a constant's names digest not fed (`feed_const` returns early) | `equal`, `names` | **survived**, argued below |
| M10 | notes kept beside an unverifiable verdict | `verify_job` | survived the first run; then caught by the new test `names_no_note_beside_unverifiable` (R1 after the notes are computed) |

**M8, argued.** `feed_const` feeds a `uv 4` entry when a pointer's base is
an anonymous frozen constant (`PtrBase::Const`) that is not a
source-location `__impl` object, because those are written by
`write_location`, and that constant holds a fed string. Kiln makes such a base in three
places: `__builtin_source_location`'s `__impl` objects (location
objects), the oven re-freezing a pointer into a thawed anonymous
constant (`Origin::Const`), and reflection (C++26). A temporary probe
over the `equal` and `differ` runners found 364 calls of `feed_const`
and 143 constants collected, 62 of them symbolically, and none had a
names digest. A pair written to reach the entry,
`equal/_/name-value-pointer-into-backing-array`, does not: its string
is fed through another path, so it notes with M8 applied. So, on every
input found, M8 is equivalent. The code is kept because it is the fail-closed half
of decision 3: if a constant ever holds a string that is passed on, its
bytes reach the unit's names digest. A Kiln form that reaches it would
be the pair that kills M8.

## Item 6: the report on a real relocation

**The command** (from the `slip` directory, the environment script
sourced; it reads `$SLIP_CORPUS_DIR/llvm` and the `bench/demo1/`
cases):

```text
cargo test -p slip_cli --test names_relocation -- --ignored --nocapture
```

`SLIP_NAMES_CASES` selects the cases (comma separated, default
`01-relocate`). It prints, per case: observers selected and mapped,
names entries over the map shards and distinct keys, notes over the
verify shards and distinct keys (what the report counts), the verdicts,
each noted unit's name, and each finding. `slip verify` (WP-053) and
`cargo xtask demo` are not on this branch, so the test runs in
process what `spec/harness.md` §10.2 runs: plan, map, the case's tree,
`declared.txt` resolved as `slip declare` does, and verify.

**Not run over LLVM** in this package (the brief forbids it). The same
function runs on every `cargo test` over a small corpus made in the test
(`measure_on_a_small_corpus`): a header with `lib::detail` relocated to
`lib::impl`, two translation units. It gives 2 observers mapped, 6 names
entries over 3 keys, 2 `verified` verdicts, and 4 notes over 2 keys,
named by the post-image (`spec/verify.md` §6.1): `lib::impl::f(lib::impl::V)`,
which the rule relocates, and `g(lib::impl::V)`, whose parameter's type
the rule moves. `k()`'s `__func__` is unchanged and gives
no note. Both notes are changes the rules account for.

**Should a note tell a declared change from another?** Yes, eventually.
On a relocation every noted function is a declared change unless
something else moved, and a report of thousands of expected notes hides
the one that is not. The way to tell them apart is a second names
digest per entry, computed with the rules' names mapped back (the
post-image's string with `lib::impl` printed as `lib::detail`). It is
equal exactly when the rules account for the whole change. Cost:

- The bytes are Kiln's `pretty_function` output, a flat string. Mapping
  names back inside it by text would be string manipulation of code,
  which the product refuses. It would also be wrong on names that are
  substrings of others, and on template arguments.
- The right form is a Kiln request: `pretty_function` (and the
  source-location function name) returning, beside the bytes, the
  declaration and byte range of each name it printed. Slip would then
  substitute the rule's target per declaration, as a structured edit
  of a printed form, and digest the result.
- Runtime: one more digest per names entry, linear in the string's
  length. That is small beside the unit digests. The shard gains one
  digest per entry.
- The comparison needs no new pass: a note whose mapped digests are
  equal is "declared", and one whose mapped digests differ is
  "undeclared".

Not built (out of scope).
