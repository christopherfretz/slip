# WP-135 — where each found lookup led

What `slip_kiln::Lookups::found`, the shard section `found`
(`spec/model.md` §8.8) and guard N2 (`spec/verify.md` §5.3) read into the
package where it left a choice, with the figures it asked for. It closes
the two limits WP-117 left in `spec/verify.md` §5.1: a spelling the map
parse resolved that now leads elsewhere while every recorded file still
passes O2 and N1.

## 1. The record

**Section 31, `found`** (`spec/model.md` §8, §8.8), as ruled: the
unknown-section examples (30, 63) are left as they are, and the shard's
version is not changed (WP-112 owns it). Optional, phase `map` only, and
only in a shard with `inputs`, as `negatives`. An older reader refuses a
map shard with it (the id is critical); a newer verify reading an older
map shard refuses it through N2 ("the map shard has no record of where
its lookups led"), and `slip parse` makes it again.

```
Found      := places:  list<FoundPlace>     the paths front-coded as `negatives`
              classes: list<list<uv>>       the inputs that were one file
FoundPlace := shared: uv, rest: bytes, input: uv
```

- **The places**: the path (§8.6's rule: `Command.directory/d/n` as
  written, `.` and repeated `/` dropped, `..` kept, no link followed) of
  every place of `Lookups::found` (one per lookup that found its file) and
  of every name of `Lookups::read` (the main file, and each file as the
  front end first spelled it), unique, sorted. Each with the index of the
  input it led to.
- **The input of a place** is found by the map task right after the
  parse: the input whose path is the place's real path, else the input
  that is the same file (device and file number, links followed) as the
  place. A place that leads to none fails the map task ("… changed during
  the parse"), the assumption `inputs` already makes.
- **The classes**: the partition of `inputs` into files (device and file
  number), each class of two inputs or more, ascending; never the numbers.
- **Writers**: the map task only (`slip_cli::worker::map_observer`), with
  `negatives`, whenever the shard has `inputs`
  (`slip_cli::negatives::found_places` and `record`).
- **Recorded for every place, under a subject root or not** (the scope's
  "outside the subject roots" widened: decision (c)).

Tests: `crates/slip_model/tests/found.rs` (the bytes written by hand, JSON,
binary → JSON → binary, an empty section against none, F-1 to F-10 each at
its offset and JSON path, the two front-coding rules);
`crates/slip_kiln/tests/lookups.rs` `found_*` (one per form).

## 2. Decisions

**(a) What is compared, and where the input of a place comes from.** The
place is walked *now*, as written (its real path; when it does not
exist, the real path of its deepest prefix that does, then the rest as
written) and must be the recorded input's path, or the same file now as
that input. Real paths alone would refuse a legitimate tree: Kiln
identifies a file by device and file number (`SourceManager::load`), so
`#include <b.h>` after `#include <a.h>` with `b.h` a hard link of `a.h`
reads one buffer, whose input is `a.h`; the place `ext/b.h` leads to
`a.h`'s input by identity, and stays good as long as the two are one
file (`n2_hard_link_read_as_one_buffer`). The partition is compared in
both directions: two inputs in one class that are two files now
(`n2_hard_linked_inputs_separated`), and two inputs of different classes
that are one file now (`o2_inputs_merged_by_hard_link`). Device and file
numbers are read on both sides at the time of the comparison, never
stored.

**(b) What Kiln's log gives** (item 3). The log names the place a found
lookup opened exactly: `Found::Includer` with the includer
(`parent_dir(file_name(includer))`, `.` when it names none),
`Found::Dir { dir }` with the list's own entry (Kiln
`HeaderSearch::lookup` opens `join_path(dir, name)`), `Found::Embed {
path }` with the path read. So no place is recomputed as `negatives`
recomputes a missed one; only the place's input is found by the map task
(real path, then identity), and a place that matches none fails the job:
fail closed, never a guessed record. What the log lacks is the lookup of
an absolute name (Kiln WP-2620, already asked). `Lookups::read` covers it
whenever the absolute name is the file's first spelling (the front end's
`file_name`); the one form left is an absolute name for a file first read
through another spelling (§4).

**(c) Under a subject root.** N1 skips a negative under a subject root
(judged by the real path now); N2 does not skip a place there, and judges
no file's existence or content: it compares a route and an identity.
Three reasons. A place under a subject root as written can lead outside:
`s/lnk/cfg.h` with `lnk` a link of the subject to `../ext-a`, which the
post tree copies as the same bytes, so G6 sees the same link in both
trees and passes, and the post parse reads where the link leads now
(`n2_place_under_the_subject_root_retargeted`). A place can be spelled
through the subject and be outside (`s/../lnk/cfg.h`, the source's
`"../lnk/cfg.h"`: `n2_place_spelled_through_the_subject_root`). And a
link outside that led into the subject can be pointed out of it, or the
other way (`n2_link_retargeted_out_of_the_subject`,
`n2_link_retargeted_into_the_subject`). A place that still leads to its
subject file passes whatever the file now holds or whether it still
exists: the walk of a deleted file is its own path, the input's; what the
subject's files hold is the post tree's and step 4's business.

The partition is compared twice, every pair each time. The first round
compared only the pairs with an outside member, and only where the post
parse reads them. That let an outside `ext/y.h`, made a hard link of the
subject's `s/x.h`, give `verified` (the review's first finding).

- **At the recorded paths**: is the map shard still what a map parse
  would give? The front end's buffers and `#pragma once` follow
  identity, which no content check sees
  (`n2_outside_input_made_one_file_with_a_subject_input`). For two
  subject inputs this is stricter than the claim needs, and it is kept
  (decision (d); `n2_two_subject_inputs_made_one_file`).
- **Where the post parse reads them** (a subject input at its post
  counterpart): is the post tree as verified the post tree as delivered?
  A delivery that copies bytes makes two files of one again. This covers
  two subject inputs merged in the post tree only, with an edit that
  compensates (the re-check's fourth tree,
  `n2_two_subject_inputs_made_one_file_in_the_post_tree`), and an
  outside file made a hard link of the post counterpart (the re-check's
  third tree, `n2_outside_input_made_one_file_with_the_post_counterpart`).
  It also covers an outside file that was one file with a subject file
  at the map phase whose post counterpart is a copy
  (`n2_one_class_subject_and_outside_post_copy`): an edit of the
  subject's file in place would change the outside file too, which the
  post tree does not show.

None of this refuses anything legitimate: a post tree of hard links to
the subject keeps the subject's partition, and never merges two
distinct subject files.

**(d) The claim: the subject as the map phase read it** (the review's
second question, and the re-check's correction of the ruling's wording).
A tree-form verdict compares the subject as the map phase read it (the
inputs under the subject roots with their recorded sums, and nothing at
the subject's negatives) with the post tree as it is at verification.
Both are taken against the outside as it is at verification. This is
`spec/verify.md` §1's `A` and §5.1's "The claim". O2, N1 and N2
establish that the map shard is what a map parse of that subject would
give against today's outside.

Whether the subject on disk is still that subject is not part of the
verdict. Two trees, both checked in as `verified`, are refused by the
identity image:
- `s/a.cpp` edited in place after the map phase
  (`n2_subject_edited_in_place_after_the_map_phase`);
- a `cfg.h` created in the subject, shadowing `ext/cfg.h`
  (`n2_subject_header_created_after_the_map_phase`).

That question is checked by R2 at a finding, by the identity image, by
`slip apply --write` for the files it replaces (`spec/edits.md` §7.3
step 1), and, for the overlay form, by WP-074.

N2 (ii)'s identity check of subject inputs at the recorded paths is
stricter than the claim: a subject changed in content is not refused,
but one changed in identity is. It is kept because a post tree is
commonly made of hard links to the subject, so the change is usually
one in the post tree too, and the check costs nothing.

The review's tree passes under this claim. In it, `w/lnk` is retargeted
from `ext-a` to `ext-c`, whose `cfg.h` links to `ext-a/cfg.h` and whose
`sub.h` differs. The edit makes `w/lnk/cfg.h` the first spelling, so its
`"sub.h"` is found in `ext-c`, and inverts the `#if`. The result is
`verified`, rightly (`n2_first_spelling_moved_by_the_edit`; the identity
image's run is `verified` too). The lookup the post parse makes beside
its new first spelling is the edit's effect, which the comparison
judges.

Every lookup a map parse would make is a recorded place, walked again:
- a quote name beside its includer (Kiln takes the includer's directory
  from the name the file was first loaded by,
  `parent_dir(sm.file_name(f))`, itself a place);
- `#include_next` and `__has_include`, in every form;
- `#embed` and `__has_embed` (one path, `resolve_embed_req`);
- a forced include (the includer `.`);
- the main file (in `Lookups::read`).

A missed probe of each is N1's. Nothing is left but the absolute names
of §4.

The brief's third mutation is read as "a place under a subject root
judged by the place as written is skipped" (M3 below): N2 has no skip to
judge, and the mutant adds N1's.

## 3. Guard N2

`slip_cli::negatives::found_moved`, called in
`verify_job::image_guards` after N1, tree form other than the identity;
row N2 of `spec/verify.md` §5.3 and its bullet. A pre shard without the
section is refused. (i) every place, in path order: its walk now is its
input's path, or it is the same file as its input. (ii) after (i): every
two inputs, compared twice: at their recorded paths, and where the post
parse would read them (an input under a subject root, as O2 (ii) judges
it on the path as recorded, at its post counterpart). Of each pair, both
must exist there: one file there exactly when one class holds both. Reasons: `pre-image: <place> now leads to <walk>, not to
<input> (run `slip parse` again)`; `pre-image: <a> and <b> are one file
now, two at the map phase (…)`; `pre-image: <a> and <b> were one file at
the map phase, two now (…)` (the first pair by index).

O2 and N1 are unchanged, and still come first: a file deleted or changed
outside is O2's reason, a file appeared N1's.

## Cost

**How.** `crates/slip_cli/tests/negatives_cost.rs`
`measure_negatives_on_a_unit` (ignored, not part of the gate), extended:
with the log on it also prints the `found` section's places and

**Reading.** The distinct places are as many as the inputs (280 and
280): each file is reached by one spelling, so counting distinct places
(item 4's question) gives one place per input, not one per includer. The
section is about 14 B per input, 40 % of `negatives`'s size on the same
unit, and 7 % of the map shard. Front-coding, chosen as for `negatives`
(one rule, the order the section has anyway), is 5.4 times smaller than
the paths whole. N2 is two `stat`s and a `canonicalize` per place plus
one `stat` per input: 3 ms for 280 inputs, against 6 s for the parse.
Expected on `llvm/lib/Support` from WP-117's figures (395 to 703 inputs
per unit): 6 to 10 KB per map shard, a few milliseconds of guard per
verify job.
