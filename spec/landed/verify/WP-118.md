# WP-118 — a third class of file, `rebuilt`: the design

The design of `docs/wp/WP-118.md`, for an implementer. **Nothing is
built.** Every statement about the code is **by reading** (Slip `main`
3ae796f1); one rests on a run: the two fixtures of the investigation of
Demo 2 (`zz_inv079-inc-first`, `zz_inv079-direct-first`,
`.build/investigate-079/report.md`), where the first fails with `gen.inc`
read-only and passes with every file owned. No test was run for this
design. An independent review of the first text (34a6a24d) found no
blocker; what it changed is in "Review answers" at the end.

Throughout: **F** is a file, **E** an entry of `Ownership.rebuilt`, `r` a
rule; *owned-like* means "treated as an owned file is"; *by its own path*
means by the class the lists give the file's real path, before the
include-chain rule.

## 0. The design in one page

1. `Ownership` gets a third list, `rebuilt`. The **class** of a file is
   the list of the longest entry that covers its real path; a file no
   entry covers is read-only. Nothing is detected and nothing is a
   default.
2. **For every writer a rebuilt file is read-only.** `is_owned` is false
   for it, so apply, reduce, the residue scan, `is_editable` and the
   rename's sites refuse it with the code that exists. The one thing
   added is the name of the refusal: reason `rebuilt`.
3. **For the walk a rebuilt file is an owned file**, with one exception
   (an entity with C language linkage declared in one is a dependency
   entity). So an entity gets the same ownership, and the same key,
   whether an observer reaches its declarations directly or through a
   rebuilt file. This is the property that is tested over the whole
   rules suite (§8, P1), and what makes the change to the trusted base
   small: the walk's decision reads one more class and treats it as the
   class it already has.
4. The walk also **accounts**: which entries a rule's use passed through
   (`relied`), which rebuilt files declare an entity a rule touched
   (`declares`), and which read-only files cut an include chain
   (`hints`). These change no key.
5. **A post-image that cannot hold a regenerated file says so**: guard
   RB makes an observer `unverifiable` when a rebuilt file whose content
   the image cannot change (every rebuilt file in the overlay form; one
   under no root in the tree form) still declares an entity under the
   name a rule says the run's members left. The tree form holds
   regenerated files, under the subject's roots or under a second pair
   of roots, which the image already has.
6. The report lists the entries relied on, the entries unused, and one
   hint line per build-generated read-only file that cut a chain in an
   observer that did not verify.

## 1. Rulings

### R1. Which files are rebuilt (question 1)

**R1.1 Only what the user declares.** `--rebuilt <path>` (repeats), beside
`--owned` and `--readonly`, on `slip map`, `slip rename` and `slip
declare`. `--rebuilt` without `--owned` is a usage error, as
`--readonly` is. Each entry is made a real path spelled as on disk
(`slip_spelling::real_path`), sorted, deduplicated. An entry that does
not exist is an `Input` error (a build directory that was not built is
not rebuilt: there is nothing to say of it). It follows that an entry
for one **file** cannot name a file the migration makes the generator
create (`LegacyGen.inc` becoming `AcmeGen.inc`): when the run starts
only the old file exists, and the post tree's new one is covered by no
entry, so it is read-only. Only an entry for the **directory** covers
both. That is the user's choice to make, with what else the directory
holds in view; Slip does not make it (R1.3).

*Reason.* "No binary outside the run holds its names" is a fact about
binaries Slip cannot see. Only the user can state it.

**R1.2 No default. The compilation database's directories are not
rebuilt unless the user says so.** *Reasons.* (a) A command's
`directory` is not "the build tree" in general: an in-tree build has the
source root there, and a CMake build tree commonly holds fetched and
installed third-party code (`_deps/`, an `ExternalProject` prefix, a
package manager's `installed/` tree) whose binaries the run does not
compile. A default would let a rule rename a dependency's entities: the
unsafe direction, a wrong `verified`. A missing declaration costs a false
difference: the safe one. (b) A default is a statement the user did not
make, and it would change `rules_id` without a word on the command line.
(c) The hint (R1.3) gives the convenience without the risk.

**R1.3 The hint.** A verify job records a file F as a **hint** of its
observer when all of these hold:

1. the rule table is not empty and the post-image parse is `ok`;
2. F is read-only by its own path and **no entry of any list covers
   it** (a file the user carved out with `--readonly` is never hinted:
   the user has spoken about it);
3. F **cut a chain**: the walk, deciding a declaration's inclusion
   (`chain`, §4.2), reached F as the first read-only file above an
   inclusion of a file that is not read-only by its own path. (F is the
   main file, or a file on an include chain, that includes owned or
   rebuilt code. A read-only file that only declares is not hinted: a
   named limit, L3.)
4. F's subject path lies under the real path of the observer's
   command's `directory` (the plan's command, not the post command;
   component-wise, `covers`).

The shard keeps at most 16 hints per observer, in path order, and the
number left out. The **report** prints one line per hinted file, over
the observers whose state is `mismatch` or that are stale for a rule
(§9.2), and only those (in a verified observer the cut cost nothing):

```
hint: <file> is read-only, is under the build directory <directory>, and makes code of the run read-only in <n> observer(s) (first <main file>); if the build writes it again from source, pass --rebuilt <file> (only if no binary outside this run was compiled against it)
```

at most 20 lines, in path order, then `hint: <n> more (see the report)`.
The word to pass is the **file**, never its directory: a hint must not
propose more than was seen. The hint's test is close to the default R1.2 refused (a fetched
dependency's header under `_deps/` that includes owned code passes it):
that is why it is a line to read and not a class, and why it ends with
the condition the user must know to be true. A file the generator names
after an entity (R1.1) needs its directory; the hint still names only
the file it saw. With rule 2, an in-tree build gives no hint
(the owned entry covers `directory`), and neither does a vendored tree
under a `--readonly` entry.

### R2. A rebuilt file's own declarations (question 2)

**R2.1 Renamable.** A declaration in a rebuilt file is not a reason for
its entity to be a dependency entity. An entity all of whose
declarations lie in owned or rebuilt files (and that no other bullet of
§2.1 makes a dependency entity) is owned, and a rule matches it.
*Reason.* The names in a generated file follow the generator's input,
which the user changes with the migration; the regenerated file declares
the new names, and they must map back. WP-118 item 3.

**R2.2 An entity with C language linkage declared in a rebuilt file is a
dependency entity.** Stated per declaration, so that every reader of
"does this declaration lie in an owned file" has one answer: **a
declaration of an entity with C language linkage (`Walk::in_c_linkage`,
the test that gives the parent `c_linkage`) that lies in a rebuilt file
lies in a read-only file.** "Lies in a rebuilt file" is by the file's
own path: the declaration's expansion location, or its name token's
spelling location, is in a file whose class is rebuilt. So:

- the entity is a dependency entity by bullet 1, whichever of its
  declarations is the one in the rebuilt file (a function first declared
  in an owned header and declared again in a rebuilt one is a dependency
  entity, as when the second file is read-only);
- for §9.2 the declaration is read-only **by its own path**
  (`only_by_inclusion` makes the same test), so the entity is not "a
  dependency entity by the per-inclusion rule alone";
- where a C-linkage entity "counts in every namespace one of its
  declarations is in" (`spec/verify.md` §2.1; `ns_refs.rs`, the member
  count per view), that declaration counts in the **dependency** view.

An owned file's `extern "C"` name stays renamable by its `c_linkage`
rule (`spec/verify.md` §2.3), also when the owned file is entered
through a rebuilt one.

*Reasons.* (a) The class says the binaries that hold the file's names
are compiled from source in the run. A C-linkage name is the one kind of
name whose holders are routinely no C++ translation unit of the run: C
sources, assembly, linker scripts, other languages
(`spec/verify.md` §8, "Other languages and build files"). (b) An owned
file's C name is renamed by an edit Slip writes and the user reads, in
that file. A rebuilt file's is renamed by a generator Slip never sees,
and a generator that emits C names is usually emitting an interface for
consumers that are not C++. (c) Its key `(c_linkage, name)` has no
namespace: nothing narrows what a wrong statement would capture. (d)
WP-118 item 7 asks for it. *Cost*: a correct migration that renames a
generated `extern "C"` name is a difference (limit L2). The native
rename already refuses such an entity (`unsupported`, `spec/edits.md`
§9.5).

### R3. The include chain (question 3)

**R3.1 Three answers.** The chain of an inclusion is

- `ReadOnly`: a file on it (the file holding the `#include`, or one
  further up) is read-only by its own path, or the chain is longer than
  `INCLUDE_CHAIN_LIMIT`;
- `Clear(∅)`: every file on it is owned;
- `Clear(S)`, `S` not empty: none is read-only, and `S` is the set of
  `rebuilt` entries that cover a file on it.

A location is read-only when its file is read-only by its own path or
its chain is `ReadOnly`; else it is clear, with the set of its chain and,
if its file is rebuilt, that file's entry.

**R3.2 The decision reads two states.** `ReadOnly` is what `true` was;
`Clear(_)` is what `false` was. The set is accounting only (R6). So:

| Chain (outermost first) | The innermost file's inclusion is |
|---|---|
| rebuilt → owned | clear, `S = {E}`: owned-like. The entity is owned; E is relied on if a rule gives it its key |
| rebuilt → read-only → owned | `ReadOnly`: read-only wins. The dependency in the middle was compiled against what it includes |
| read-only → rebuilt | `ReadOnly`: a rebuilt file entered through a read-only file is read-only for that inclusion, as an owned one is |
| read-only → rebuilt → owned | `ReadOnly` |
| owned → rebuilt → owned | clear, `S = {E}` |
| rebuilt (the main file) → owned | clear, `S = {E}` (a unity-build main file) |
| command line (`-include`) → rebuilt → owned | clear, `S = {E}` (a precompiled-header file; an includer that is no file decides nothing) |

*Reason.* A rebuilt file is compiled in the run: nothing was "compiled
against" what it includes that the run does not compile again. A
read-only file anywhere on the chain is a binary the run does not see,
whatever is above or below it.

**R3.3 The same entity has the same key in unity, precompiled-header and
ordinary observers.** `decide_owned` reads the files only through "is
this location read-only", and by R3.2 a rebuilt file answers as an owned
file does, on its own path and on a chain. So for an entity with no
C-linkage declaration in a rebuilt file, ownership is the same function
of its declarations whether a declaration was reached directly, through
`unity_0_cxx.cxx`, or through `cmake_pch.hxx`; and a key is a function
of the entity, the rules and ownership. Stated as a property and tested
over the suite (§8, P1): *moving every entry of `rebuilt` to `owned`
changes no digest, no key and no `rule_use` count*, unless an entity
with C language linkage has a declaration in a rebuilt file.
Without the declaration the three observers disagree as today: the unity
and precompiled-header observers keep the entity unmapped and differ.

**R3.4 The guard-skipped inclusion** is as before, for one more class:
a rebuilt file entered directly first and then included by a read-only
file whose `#include` the guard skips is owned-like for its only
inclusion (limit L4; Kiln WP-2111, not assumed). The reverse order of
Demo 2 (`X86RegisterInfo.h`: the owned header first, then the generated
`.inc` whose include is skipped) and the order that failed
(`AArch64RegisterInfo.h`: the `.inc` first) now give one answer, owned,
when the `.inc` is rebuilt.

### R5. The containers (question 5)

**R5.1 `Ownership`** (`spec/edits.md` §2.1):

```
Ownership := owned:    list<path>
             readonly: list<path>     none also in `owned`
             rebuilt:  list<path>     version 3 of TRFM and DECL: sorted, no two equal; none also in `owned` or in `readonly`; none is `/`
```

**R5.2 The longest entry over three lists.** The class of a real path is
the list that holds the longest entry covering it; a path no entry
covers is read-only. Two entries that cover one path and have one length
are equal, and an entry is in one list, so the longest is unique.
`is_owned(p)` is `class(p) == owned`, and every caller of it keeps its
meaning: a rebuilt file is not owned.

**R5.3 An entry in two lists is an error**, each pair with its message,
checked after the existing rows in this order: `rebuilt is not a
canonical absolute path` / `rebuilt is not strictly ascending` (as the
other lists' rows), `a rebuilt entry is /`, `a rebuilt entry is also in
owned`, `a rebuilt entry is also in readonly`. On the command line:
`<path>: given as --owned and as --rebuilt`, `<path>: given as
--readonly and as --rebuilt` (`Input`), after links are resolved, so two
spellings of one directory in two lists are caught.

*Why `/` is refused as a rebuilt entry*: it would make every file no
other entry covers rebuilt, system headers included. `owned: /` exists
for tests and edits nothing it cannot write; `rebuilt: /` would rename
through everything. The user who means it lists the directories.

**R5.4 A new version, chosen by the value; one encoding per value.**
`TRFM` version 3 and `DECL` version 3 are version 2 with `rebuilt:
list<bytes>` after `readonly`. **A writer writes version 3 exactly when
`rebuilt` is not empty, and version 2 otherwise.** A reader reads
version 2 as `rebuilt` empty, and refuses a version 3 container whose
`rebuilt` is empty (`a version 3 container has no rebuilt entry`,
`Malformed` at the list). `DECL` version 1 is read as before.

*Reasons.* An optional trailing field in version 2 would be a second
layout under one version number. A version 3 written always would
change every request id, every `DECL` id and every id built from one
(edit sets, overlays, results, bindings, goldens) for runs that declare
nothing rebuilt. With the version chosen by the value, **a run with an
empty `rebuilt` list has byte for byte the `TRFM` and `DECL` containers,
the request id, `rules_id`, every digest, key, `rule_use` count and
verdict it had. Its verify shards gain section 33 only where a hint
exists (R1.3), and its report gains the `"rebuilt"` member and `hint:`
lines only then; the implementer lists every golden that changes for
this reason in the handback, and a change for any other reason is a
defect.** (The files that cut a chain stay in the shard, as `hints`: the
report is made from shards, and a hint for a run that declared nothing
is the hint's whole purpose.) So the shard ids of such observers, and
what is built from them, change; nothing else does,
and there is still one encoding of each value (the rule that refuses a
second encoding of the empty table, `spec/verify.md` §2 row 6).
`dump`/`undump` keep the version as they do today.

**R5.5 The ids change with the list.**

- `rules_id = H("slip.rules.v2", rules, owned, readonly)` when `files`
  is present and `rebuilt` is empty (as today), and
  `H("slip.rules.v3", rules, owned, readonly, rebuilt)` (each list a
  `list<bytes>`) when `rebuilt` is not empty. Two tables that differ only
  in `rebuilt` have different ids; so have a table with entry `/b` rebuilt
  and one with `/b` read-only, or owned.
- The **request id** is the content id of the `TRFM` container, which
  holds the list.
- JSON: `"ownership": {"owned": […], "readonly": […], "rebuilt": […]}`
  and `"files"` the same, the member `rebuilt` present exactly in
  version 3.

**R5.6 `EDTS` and the shard's `edits` stay at their versions.** `Reason`
gains **`rebuilt = 13`** (R7). 12 stays unlisted: an interim build gave
it to `no_holder`, which was removed before any release
(`spec/edits.md` §4.2), and no value gets two meanings. A new value
without a change of version is what `instantiated = 11` did
(`spec/model.md` §2); an older reader refuses the value as `Malformed`,
and refuses the version 3 request first. A version bump would change
every edit set id for nothing.

**R5.7 Where entries are checked on disk** (`spec/edits.md` §2.1, "every
entry, owned and read-only, must exist and be its own real path"): the
`rebuilt` entries too, in the same places, `slip_apply`'s own check
included.

### R6. The post-image (question 6)

**R6.1 The tree form holds regenerated files; nothing new in the image.**
`Image` is already a list of root pairs, and the k-th `--root` with the
k-th `--post` is one pair (`spec/exec.md` §8). So:

- a rebuilt directory **under a subject root** (`<src>/build`): the post
  tree holds the regenerated files; one pair;
- a rebuilt directory **beside the subject** (`/w/b` beside `/w/s`): it
  is given as a **second pair**, `--root /w/b --post /w/post-b`, with the
  rules of §5.1 for roots (none under another; a post root may lie under
  a subject root). `Resolver` needs no change: the command's `directory`
  and its `-I` words under `/w/b` are rewritten into `/w/post-b` by the
  rewrite that exists, and G1/L1 hold the parse to it;
- a rebuilt file **under no root** of an image that has roots is, by
  §5.1, "the same file in both images": the image cannot hold another
  content for it. It is **frozen** (R6.3).

End to end (the test of §8, T-cli-1):

```
/w/s/a.cpp, /w/s/own.h          owned            --owned /w/s
/w/b/gen/gen.h                  rebuilt          --rebuilt /w/b      declares legacy::G; the compile directory is /w/b
/w/post-s/…                     the edited tree  own.h declares acme::Mine
/w/post-b/gen/gen.h             regenerated      declares acme::G
slip parse   --db /w/b/compile_commands.json
slip declare --plan … --from d.txt --out d.decl --owned /w/s --rebuilt /w/b \
             --root /w/b --post /w/post-b --root /w/s --post /w/post-s      (relocate legacy => :: acme)
slip verify  --plan … --declared d.decl --root /w/b --post /w/post-b --root /w/s --post /w/post-s
→ verified; "rebuilt /w/b relied on by 1 observer(s)"
```

The two failures:

- **Not regenerated** (`/w/post-b/gen/gen.h` still declares
  `legacy::G`): `G` is an owned-like member of the namespace the rule's
  owned members left, so the observer is **stale** for the rule
  (`direct`, §9.2) and the run is not verified. If owned code names
  `acme::G`, the post-image does not parse and the observer is
  `not_parsed`. Where it parses, the report adds the line of R7.3 naming
  the file and the rule (for a rule that is no namespace rule, the rule
  names the entity; limit L6).
- **Regenerated with another change** (a member of `G` gone): a
  difference like any other, `mismatch`.

A regenerated file that includes a subject file by an absolute path (a
unity main file made by configuring the subject, then copied) trips G1,
as §8 "Derived inputs" says: regenerate in the post tree's own build.

**R6.2 The overlay form holds no regenerated file in this package.** An
overlay names the files an edit set changed; an edit in a rebuilt file
is refused (R7), so no overlay made by Slip names one. User-supplied
entries for rebuilt paths are **not** added here. *Reasons.* (a) An
`OVLY` is what `slip apply --write` writes: an entry for a file that is
not owned must be carried in a list of its own that apply never writes,
that the journal and the patch skip, that `check_owned` accepts, that
reduce's "one name per file" and the job's loading and O1 treat as
overlay files, and whose blobs something must publish and bind to the
result. That is `OVLY` version 2 across `slip_apply`, `slip_reduce`,
`slip_cli` and `slip_verify::conclude`, none of which this package may
edit beyond the cause; and "never write into a file the user does not
own" should not get a second path in the same package that introduces
the class. (b) The common cases need no entry: glue (a unity main file,
a precompiled-header file) and a generated fragment that only includes
owned code and declares nothing the rules touch are **the same bytes
after regeneration**, and verify through an overlay as they stand
(Demo 2 does). The follow-up is F1.

**R6.3 Guard RB: an image that cannot hold a regenerated file does not
verify a rule's use in it.** A rebuilt file F is **frozen** in an image
when the image cannot give it a post-image content of its own:

- overlay form: every rebuilt file (an overlay entry that names one, in
  an overlay made by hand, changes nothing of this);
- tree form with roots: F's subject path is under no subject root;
- the identity image: none (the post-image is the disk now).

**RB**, at step 2 of the job, after the form's other guards and before
`comparable`: no row of the walk's `declares` (R6.4) **with `left > 0`**
names a frozen file. Otherwise the verdict is `unverifiable`, the first
such row in `(file, rule)` order giving the reason:

```
post-image: <file> is rebuilt and still declares an entity under the name rule <index> says was left; an overlay holds no regenerated file (verify a post tree: slip verify --root … --post …)
post-image: <file> is rebuilt, is under no root of the image, and still declares an entity under the name rule <index> says was left; give its directory as a root (--root <dir> --post <regenerated dir>)
```

`left` counts only entities whose key is not in `Declared.kept`
(`left_kept` counts the others): an entity the user said stays is no
reason. **`mapped` rows are accounting only.** A frozen file has the
same bytes in both images; if an entity it declares was given its key by
a rule and compares equal, the change that moved it came from outside
the file (an owned header that includes a generated fragment inside
`namespace legacy {`, edited to `namespace acme {`: the fragment needs
no regeneration, and the observer verifies as it should); and if it does
not compare equal the observer is a `mismatch` in any case.

*What RB is.* A heuristic that turns one failure into an instruction,
not a proof. With a frozen file the image given is not the image the
user's build will make, exactly where a rule says the file's names
change, and the existing checks already fail there: a frozen file that
still declares a member under the old name is `direct`, so the observer
is stale (§9.2) and the run is not verified. RB makes that observer
`unverifiable` with the reason and the way out, and it never makes a
verdict better: it runs before the comparison and can only refuse.
*What RB does not cover*: a frozen rebuilt file that only **names** a
renamed entity (a call in a generated inline function). Its stale text
either does not parse (`not_parsed`), resolves to another entity
(`mismatch`), or resolves to the same entity through a compatibility
declaration (the image given is then the same program, and `verified`
is true of it). The native rename refuses such a name before any of
this (R7). A rebuilt file's opening of a namespace whose members are
all keyed by content has no row; the comparison has them. And a frozen
file whose regeneration would change it in a way no rule touches is
§8's "Derived inputs", unchanged (limit L8).

**O3: an overlay does not name a rebuilt file.** With RB reading only
`left` rows, the sentence "an overlay entry that names one changes
nothing" needs its own guard. Beside O1, overlay form: no path of the
overlay's `files` has class rebuilt under `Declared.files`. Otherwise
`unverifiable`, `post-image: the overlay names <path>, a rebuilt file`
(the first in path order). No overlay Slip writes has one (`apply
--write` checks `is_owned`); one made by hand is refused here. F1
(`docs/wp/WP-165.md`) replaces this guard with a list of its own.

In the tree form, a file outside every root that was regenerated in
place trips O2 (i) first. Its reason gains, when the path is rebuilt:
` (a rebuilt file under no root: give its directory as a root)`.

**R6.4 What the walk reports** (the accounting, R6.3 and R7 read it). In
the walk that counts rule use (`Options::rule_use`, a table that is not
empty), per entity the walk decided **owned**:

- `R(e)`: the set of `rebuilt` entries that cover a file F such that
  some declaration of `e` has its expansion location, or its name
  token's spelling location, in F or in an inclusion whose chain is
  `Clear(S)` with the entry in `S`. (Exactly the files that, read-only,
  would have made `e` a dependency entity by bullet 1 or the
  per-inclusion rule.)
- `D(e)`: the rebuilt files in which a declaration of `e` **lies** (its
  expansion location's file, or its name token's spelling file, is
  rebuilt by its own path).

and from `rule_use`'s traces, per entity: the rules that **gave it its
key** (`mapped`: its own trace is `Via(r)`; or it is a member and `r` is
in its chain's `via` set; or it is a namespace whose owned-view unit
counts `via(r)`), and the rules that **produce the key it kept**: its
own trace is `Direct(r)`, a namespace's included; or it is a member and
`r` is in its chain's `direct` set. The second kind is `left` when the
entity's key is not in `Declared.kept` and `left_kept` when it is. A
namespace entity is never counted in `left`: its own `Direct` rows are
accounting, counted in `left_kept`, and its members are counted by
their own rows, so a frozen rebuilt file whose `namespace old {` holds
a member that is not kept still fires RB through that member's row
(ruling, merge review).
Then:

- **`relied`**: the entries in `R(e)` of some `e` with a `mapped` rule;
  **and**, for a reference to a namespace (a using-directive, an alias,
  the other kinds `ns_refs` reads) written in a rebuilt file F that is
  not read-only for that inclusion, where a rule mapped the namespace
  named or a level of its chain: F's entry and the entries of F's
  chain. (`ns_refs` gives such a reference its readings because
  `read_only_by_path` is false for F; read-only, it would have had none
  and the observer would differ. A generated header that says `using
  namespace acme;` is relied on though no entity is declared in it.)
  An entry is relied on when a rule's use passed through it.
- **`declares`**: one row per `(F, r)` with F in `D(e)` and `r` a
  `mapped`, `left` or `left_kept` rule of `e`: how many entities each
  way.

Over-counting `relied` or `left` is safe (an entry listed that did not
matter; RB refusing a file it need not): under-counting is the mutation
to kill.

### R7. The refusal, the count and the report (question 7)

**R7.1 The cause.** `Reason` gains **`rebuilt = 13`** (R5.6): *the bytes
are in a rebuilt file; the build must write them*. `slip_kiln::Sites`
(`name_token`) answers it where it answers `not_owned`, for a file whose
class is rebuilt, and never for a read-only file or for a file that is
no file, which are as before. In the order of `spec/edits.md` §2.3's
table it stands directly after `not_owned` (one file has one class, so
the two never both hold). The claim's range is the range Kiln gave for
the name, as for `not_owned` and `not_plain`. Reduce makes it a
`site_refused` refusal like every reason; a rename is indivisible, so
one refuses the set. `Cause` and `SubjectFlags` are unchanged.

For a **declaration** of a subject in a rebuilt file the rename makes a
`refuse` claim with reason `rebuilt` at the name, with the subject, and
does **not** set `read_only` (today a declaration in a file that is not
owned sets the flag and makes no claim, `decls.rs`): so the refusal has
a place and is counted per file. A subject with one declaration in a
read-only file and another in a rebuilt one has both: `subject_read_only`
(the stop) and the site's `rebuilt`.

*Why the set is refused and not accepted with a note*: an accepted set
is verified through its own overlay (§8.1), and by R6.2 the overlay
cannot hold the regenerated file, so the run could only end `not_parsed`
or `unverifiable` after every observer was parsed again. The refusal
says the same thing after the map phase, with the places. F1 lifts it.

`is_editable(r)` is false in a rebuilt file (`spec/api.md` §6.6 rule 6:
it follows `is_owned`). **A script's `replace` there throws
`not_editable`, as in a read-only file; no claim is made**
(`slip_script` `effects.rs`: the test is `subject.owned(file)`, and
`Sites` is not asked; `spec/edits.md` §2.3: a programmable transform
"requests nothing"). Only the native rename claims `refuse` with
`rebuilt`. A shard written by hand with a `replace` claim in a rebuilt
file is refused by reduce as today ("replaces bytes of a file the
request does not own").

**R7.2 The count per file** (`spec/edits.md` §10.5). After the `refused
<cause> <n>` lines, one line per rebuilt file with a refusal of reason
`rebuilt`, in path order, at most 200:

```
rebuilt <path>: <n> name(s) the build would have to change; slip rename cannot make this change (verify a post tree, spec/verify.md §5.1)
```

`n` is the number of `site_refused` refusals of reason `rebuilt` in the
file (sites, joined over observers by reduce). Each is also a `refusal
site_refused rebuilt: <path>:<line>:<column>: …` line of the existing
form. The line does not say "regenerate and run again": there is no retry
that works. Regenerating first needs the generator's input changed,
after which the pre-image no longer parses or no longer has the old
name; regenerating after is impossible because nothing was written.
The run that works today is the edit by other means and `slip verify`
over a post tree; WP-165 makes the rename's own run work.
`subject_read_only` stays the stop it was.

`Declared.files.rebuilt` is not empty or a hint exists. Folded over **every `ok` verify shard that has section 33, whatever its
verdict** (an entry that only `unverifiable` observers relied on is not
"unused"; `rule_use`'s own fold is unchanged):

             "declares": [ { "file": <path>, "rule": <index>, "observers": <n>, "mapped": <n>, "left": <n>, "left_kept": <n> }, … ],   sorted by (file, rule); counts are the greatest over observers
             "hints":    [ { "file": <path>, "directory": <path>, "observers": <n>, "first": <main file> }, … ] }    sorted by file

## 3. Limits, by name

- **L1 The overlay form holds no regenerated file.** An observer in
  which a frozen rebuilt file still declares an entity under the name a
  rule says was left is `unverifiable` there (RB), and the native
  rename refuses a name in a rebuilt file, with no retry that works
  (R7.2). This is larger than "glue verifies as it stands" suggests: **a
  generated file that itself opens the old namespace** (`namespace
  legacy { … }` written by the generator, as TableGen-style output
  commonly is) is stale in every observer that includes it, so **a
  transform-driven migration of a root namespace cannot verify over
  such a code base until WP-165** (F1). Such a migration is verified
  today only in the tree form (`slip verify`), with the edits made by
  other means. Demo 2, and any run whose rebuilt files only include
  owned code or are included inside a block the edit moves (A8b), is
  not affected.
- **L2 A generated `extern "C"` name cannot be renamed by a rule**
  (R2.2).
- **L3 The hint sees only files that cut an include chain.** A read-only
  generated file that only declares entities gets no hint.
- **L4 The guard-skipped inclusion** (`spec/verify.md` §2.1, third
  hole) now also reads a rebuilt file as owned-like. A rebuilt
  precompiled-header file makes the hole systematic rather than rare:
  every header it includes is entered first through it, directly for
  this purpose, so a later `#include` of the same header by a read-only
  file is always the skipped one. Kiln's WP-2111 (every inclusion
  directive recorded) is what closes it; **no Kiln change is assumed**,
  and none is needed for this package.
- **L5 A rebuilt header whose copy a dependency was compiled against**,
  under a namespace rule, where no observer reads both files (A6b).
- **L6 The stale line names the file and the rule**, not the entity: for
  a namespace rule it gives a count.
- **L7 A stale reference in a rebuilt file** is `not_parsed` or
  `mismatch` with the reason the front end gives; no line says "this
  file was not regenerated".
- **L8 Derived inputs** (`spec/verify.md` §8): Slip does not run a
  generator, and never checks that a rebuilt file is what the generator
  makes of the post-image. A verdict is about the image given.
- **L9 `RSLT` does not record the entries relied on.**
- **L10 The pasted name** made in a rebuilt file from a dependency
  macro's tokens is owned-like (row 6).
