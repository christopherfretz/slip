## 1. The reader of `RSLT`: what the file alone decides (`spec/edits.md` §8.5)

- **8a.** A residue entry is an identifier token or a mention (§8.4):

  written by conclude. Row 17 reads the set-free facts only (the
  refusal, which needs the set, is `permits`'). The reasons of a
  `verified` result (rule 9 of §5.2) are checked here too, being in the
  file.
- **`unchecked`** (new, after `unused`, in the binary form and JSON;

## 2. Agreement and "this run's shard" (`spec/verify.md` §9.2 to §9.5)

`crates/slip_verify/src/run.rs`. Tests: `crates/slip_verify/tests/agreement.rs`
(`s9_*`).

### 2.1 `Report::add_at`: which shard is this run's (§9.3, §10.4)

`add_at(position, …)` takes the observer's position in the plan;
`add` is `add_at` at the next position (M1's callers, who add in plan
order). A position at or past `plan_observers`, a position added
before, or an observer added before is a defect of the caller: a panic,
checked before anything changes (review F3). Nothing the report holds
follows the call order: stale pairs, `not_verified` and the finding
groups (`first`, and `shown`: a named finding first, then the lowest
position) are keyed by position (review F4).

`ours(shard, observer)` is checked before M1's state table (`judge`); a
shard it rejects is `failed` with an empty message, like M1's shard of
another run. In order:

| # | Condition | Applies to |
|---|---|---|
| A1 | `observer`, `round`, and the verdict's `rules` are the header's | every shard (M1's rule, unchanged) |
| A2 | `binding == { overlay: the id given to Report::overlay, or none; declared: header.declared; pre: the pre round }` | a shard whose status is not `failed` (§9.1: the coordinator's `failed` shard has none) |
| A3 | `binding` present | as A2, unless the run is a tree image (no `Report::overlay`) with an empty rule table |
| A4 | `rule_use` present iff the rule table is not empty; when present, `rules == header.rules` and every `rule` below the table's length | `ok` shards |
| A5 | `spellings` present iff the overlay was given and has at least one obligation | `ok` shards |
| A6 | the fold accepts the `spellings` section (§3 below) | `ok` shards that the state table accepts with a verdict |

- **A3, the tree form without rules.** A run with a tree image and no
  rule is M1's: its shards have no `binding` and its report must be M1's
  byte for byte (§9.4). Such a shard is still this run's; one that
  carries a binding must carry the run's (A2).
  The exception is temporary (§9.3): a coordinator's package removes it
  once every verify job writes `binding` (§9.1).
- **A3, the tree form with rules.** Such a shard without `binding` and
  `rule_use` is `failed`. Resolved by the supervisor's ruling: the spec
  stands, and `docs/wp/WP-074.md` item 3 now writes both for a tree
  image under rules.
- **A4, a rule index past the table** is refused here rather than by
  the model's decoder, which cannot know the table. It also keeps
  `add`'s indexing total.
- **A5** is the presence rule of §10.4 from the run's side: an overlay
  without obligations has shards without the section, and one with a
  section is not of this run.
- **A6 after the state table.** The fold is the last check because it
  is the only one that changes state; a refusal turns an accepted state
  into `failed` before anything else of the shard (its `rule_use`) is
  read.

Trusted: the caller's `Declared` is the one whose id is
`header.declared` and whose rules' id is `header.rules`. `Report::new`
cannot check either (it is given no bytes), and M1's tests construct
headers whose ids are not those of their `Declared`; checking them would
move M1's tests. The caller (WP-076) reads both from the store, where
the id is the content id.

### 2.2 Which sections are read

The `rule_use` of an `ok` shard that passes A1 to A5 and that the
state table accepts with a verdict: `verified`, `mismatch`, or
`unverifiable`. Its `spellings` are folded only for `verified` and
`mismatch` (§3); an `unverifiable` one's are checked (`Fold::check`) and
a refusal makes the observer `failed`. A `verified` or `mismatch` verdict whose map shard is
not `ok` is `failed` (M1) and its sections are not read. §9.3 says
"this run's `ok` shards"; it is silent on an `ok` shard that the state
table turns into `failed`. Either reading is safe (the run is then not
verified on that observer's account), and not reading it keeps the
report's agreement and spellings about shards the run believed.

### 2.3 Stale pairs and unused rules (§9.2)

- A `Use` with `direct != 0` for a rule whose kind is not `namespace` is
  one stale pair `(rule, observer, direct)`. A rule is used if some read
  `Use` names it with `via` or `direct` not 0 (the model's invariant
  forbids both 0; the check does not rely on it). A namespace rule's
  uses count against `unused` and never make a pair.
- **Namespace rules are unchecked until WP-111** (§9.2, temporary).
  `unchecked()` lists, ascending, the namespace rules some read shard
  used. The report writes it as the JSON member `agreement.unchecked`
  and one text line `not checked: agreement between observers for
  namespace rule <n>` per rule, after the `unused rule` lines. The
  report's verdict does not change; conclude gives `incomplete` when it
  is not empty, whatever `Allow` says, and `permits` refuses a result
  whose `unchecked` is not empty. M1's goldens do not move (a run
  without rules has no `agreement` member).
- `stale()` is sorted by `(rule, plan position)`: §9.4's order, whatever
  the call order. An observer cannot be added twice (§2.1), so no two
  pairs share `(rule, observer)`.
- `unused()` is ascending; empty for a run without rules.

### 2.4 `combine` and `Report::verdict` (§9.3)

`combine(states, stale, not_passed)`: `NotVerified` if `states` is, or
if either count is not 0; else `states`. `Report::verdict` is `combine`
of M1's verdict of the states, the number of stale pairs and the number
of obligations whose outcome is not `Passed`. So a run with no observer
and an overlay with obligations is `not_verified` (every obligation is
`unseen`), where M1 says `incomplete` for no observer: §9.3's "some
obligation ... was seen by no observer" applies first.

### 2.5 `Report::overlay` and `Report::pre_round` (§9.5)

Both only before the first `add`; `overlay` once and only with a header
whose `image` is empty (§9.4: "image is then []"). Each violation is a
panic with a message naming it: they are defects of the caller, not
inputs. `pre_round` defaults to 0, so a caller that forgets it gets
`failed` observers, never a wrong `verified`.

### 2.6 The report's additions (§9.4, §10.5): decided here

The spec gives the members and lines but not where the members go. As
built, and as `spec/verify.md` §9.4 now says:

- JSON: `"overlay"` right after `"image"`; `"agreement"` then
  `"spellings"` after `"exemptions"`, before `"run"`. Each is present
  only when it applies (overlay given; rule table not empty; overlay
  with at least one obligation).
- Text: `image overlay <id>` in place of `image identity` (the overlay
  form has no image lines); then after the `exemption` lines
  `agreement rules <n> stale <pairs> unused <n>`, at most 100 `stale
  rule` lines and `stale: <n> more (see the report)`, every `unused
  rule` line (the spec gives no limit for them; there are at most as
  many as rules), then the `spelling` lines of §10.5 with their limit
  of 100.
- An `unseen` obligation is written with `observers` 0, `first` null,
  `found` null and `name` empty (no observer named it), and its text
  line ends after `observers 0`.
- Nothing is added to standard error (§9.4).

Goldens: `crates/slip_verify/tests/golden/agreement/report.{json,txt}`.
M1's goldens (`tests/golden/run/`) are unchanged and `tests/run.rs` is
not touched.

## 3. The spelling fold (`spec/verify.md` §10.3, §10.4, §10.6)

`crates/slip_verify/src/spelling.rs`. Tests: `crates/slip_verify/tests/spelling.rs`
(`s10_*`).

- **One slot per obligation**: held (bool), not-seen count, and the
  first failure with its count. Memory does not grow with observers.
- **Position** is the observer's position in the plan, the one given to
  `Report::add_at` (review F3; the fold position is no longer the index
  of the `add` call). `first` keeps the smallest position whatever the
  call order, with that observer's `found` and `name`.
- **Unverifiable spellings are not folded** (§10.3: "an observer's
  spellings count only when its own verdict is `verified` or
  `mismatch`"; §10.6). An unverifiable observer did not compare its
  post-image as a whole, so its `held` is no evidence; it makes the run
  not verified anyway. Its section must still be well formed
  (`Fold::check`, the refusals below without the update). Test:
  `crates/slip_verify/tests/spelling.rs` `s10_3_which_shards_are_folded`.
- **Outcome**: a failure anywhere is `DenotesOther`; else held anywhere
  is `Passed { not_seen }`, `not_seen` counting the observers whose
  `inputs` list the obligation's file and that neither held nor failed
  it (§10.3 "the observers where it is not seen are counted"); else
  `Unseen`.
- **`add` refuses, before changing anything** (each a `String` starting
  `spellings: `):
  1. the section's own invariants again (empty span; spans not
     ascending and apart; a span that overflows; failures not strictly
     ascending; an index both held and failed), since the fold is total
     over any value, not only a validated shard;
  2. an index past the overlay's obligations (the interface's first
     refusal);
  3. an index whose obligation's file `inputs` does not list (the
     second);
  4. **`seen` not equal to the number of obligations whose file
     `inputs` lists.** Not in the interface; §10.4 defines `seen` as
     exactly that number, and the fold can check it, so it does (a
     section claiming fewer would hide obligations it never looked at
     behind "not seen", which is harmless, but a section that disagrees
     with its own `inputs` was not made for them). §10.4's "at most
     `seen` indices" follows from 1, 3 and 4 and is not checked apart.
- `inputs` may be in any order and list a path twice; paths the overlay
  does not have are ignored.
- **Trusted**: the overlay satisfies `spec/edits.md` §7.1 (files sorted,
  obligations sorted by file, each `file` an index), which
  `Overlay::from_bytes` checks. Over an overlay that breaks it the fold
  stays total: an obligation whose file is no file of the overlay can be
  named by no section and is `Unseen`.

## 4. The overlay's guards (`spec/verify.md` §5.3)

`crates/slip_verify/src/guards.rs`. Tests: `crates/slip_verify/tests/agreement.rs`
(`s5_3_*`).

- O1 over every entry of `post`, then O2; within each, path order
  (both lists are sorted by the function, not trusted to be).
- O1: an entry whose path the overlay names must have the overlay's
  `post` size and digest; an entry with `post == pre` is no exception.
- O2: an entry the overlay does not name must agree, in size and
  digest, with **every** entry of `pre` for that path (a list with a
  path twice is not valid, and a guard that checked one entry would
  depend on the order). An entry of `post` listed twice is checked once
  per entry.
- A file in one list only is not an error; neither is an overlay file
  the post-image did not read.
- The overlay's file list is binary-searched when it is sorted (it is,
  when valid) and scanned otherwise, so the result does not depend on
  the overlay being valid.
- `reason()` is the table's text with the path as §5.3 writes it: UTF-8
  as is, every other byte as `\xNN` lower case. Cutting it (§6) is the
  caller's (`compare::unverifiable`).

## 5. The state of a result (`spec/edits.md` §8.5)

`crates/slip_verify/src/conclude.rs`. Tests: `crates/slip_verify/tests/conclude.rs`
(`s8_5_*`).

### 5.1 `tally`, `state`, `conclude`

| Function | Rows | Reads | Trusts |
|---|---|---|---|
| `tally` | §8.5 "The seven states ... add up to `selected` less `unparsed`" | the report's `states()`, `set.unparsed.len()`, `Σ set.failures[].observers`, `#set.reports` of severity `error`, `facts.selected` | that `selected` is the run's selection (the caller's run record) |
| `state` | §8.5 rows 1 to 5, in order | the set's state, refusals, failures, reports and unparsed; the report's `verdict()`; `allow_unparsed`; the residue's categories | the report is the verify phase's of this run when its plan, round and state count agree (below) |
| `conclude` | §8.5 "conclude copies them and decides none" | as `state`, and the report's `stale()`, `unused()`, `unchecked()`, `spellings()` | as `state`; the overlay given is the run's |

- **A report that does not describe the run is no report**: the set is
  refused (a refused set has no verify phase), the report's plan or
  round is not the set's, or its states do not add up to `selected −
  unparsed` (without overflow), or it is not of the overlay form, or its
  overlay's `edits` is not the set's content id (review F1, F2: a tree
  report compared nothing the set changed; another transform's overlay
  and report over the same plan and round verify nothing of this set).
  `conclude` adds: an overlay was given and the report was made over it
  (equal `Overlay` values). (Round 1's check for two stale pairs of one
  `(rule, observer)` is gone: `add_at` refuses an observer added
  twice.) Without a usable report: state `incomplete` (or
  `refused`), no verdict, no state counted, no stale pair or unused
  rule, and every obligation of the overlay `unseen` (no observer
  checked it). This is what makes `conclude`'s output always pass the
  reader's rows 13 and 14 (§1): a verdict comes only with states that
  add up.
- `tally` and `state` alone do not compare the overlay argument (they
  are not given it); `conclude` does.
- **`unchecked`**: with a verified report, a namespace rule used gives
  `incomplete` (§2.3).
- **Row 4's residue** is any entry whose category is not `mention`
  (`dependent`, `not_compiled`, `not_planned`); mentions alone leave
  `verified`.
- **`failed_runs`** sums `observers` over `set.failures`: a shard has
  at most one failure (§4.6), so each failed `ok` shard is counted once.
- A `refused` result's spellings are empty (`obligations` 0): a refused
  set has no overlay.

### 5.2 `permits`

`permits(result, set, allow)` reads the answer from the result again and
refuses any result its own fields or its set contradict. True only if
all of:

1. `state` is `verified` or `verified_with_residue`, and `unchecked` is
   empty;
2. not `partial`, or `allow.partial`;
3. the result and the set pass their readers' checks (`validate`);
4. the set is accepted, `result.edits` is its content id
   (`content_id(set.to_bytes())`), and the result's `plan`, `round` and
   `transform` are the set's (review F5);
5. `verdict` is `verified`, `agreement` is empty, no spelling failed;
6. `mismatch`, `not_parsed`, `unverifiable`, `never_parsed` and
   `failed` are 0, and `verified + unchanged` is not 0;
7. `unparsed` is 0 or the result has `allow_unparsed`;
8. the tally's `unparsed`, `failed_runs` and `error_reports` are the
   set's;
9. for `verified`: no reason (no residue other than mentions, no
   refusal in the set, `failed_runs` and `error_reports` 0); for
   `verified_with_residue`: at least one reason, residue or refusal only
   with `allow.residue`, failed runs or error reports only with
   `allow.errors`.

Rules 3 to 8 are not in the spec's list of what permits; they are its
consequences (a `verified` state implies each) checked again, so that a
result written by hand, or by a defective conclude, cannot permit a
write.
