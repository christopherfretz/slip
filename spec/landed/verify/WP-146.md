## 1. What must hold

The verifier compares units by key, observer by observer. That is sound
for the run only if the key function is the same function in every
observer:

- **I1 (one entity, one key).** An entity of the post-image has the same
  mapped key in every observer that holds it.
- **I2 (one key, one entity).** A mapped key denotes the same entity in
  every observer: for a non-namespace key `K`, every entity keyed `K`
  has the same `U`.

Inside one observer I1 holds by construction (one memoised key per
entity) and I2 is checked by `keys::mark_mapped_collisions` (a group of
entities with one mapped key and different keys under no rule is a
collision). Across observers neither is checked. The pair breaks I2, the
mirror breaks I1. Ownership is the only input of the key function that
differs between observers of one image: `Walk::rule_applies` is the one
gate, and it asks `Walk::owned`. So "ownership agreed between observers"
is exactly I1 and I2, and a check of I1 and I2 over the run is complete
for every way ownership can differ, known or not.

A disagreement about ownership that changes no key (the entity is owned
in X, a dependency's in Y, and no rule would touch its key either way)
is harmless by this: ownership is read for nothing else.

**When a disagreement is a wrong `verified`.** In `Y` the entity's
post-image key is its key under no rule. If the declarations `Y` sees
were moved by the edit, that key differs from the pre-image's and `Y`
is a `mismatch` (fail closed, today). The run verifies wrongly only when
the declaration that makes the entity a dependency's in `Y` is one the
edit did not move and `rule_use` does not count: a declaration in a
genuinely read-only file, in the old namespace (the pair) or already in
the new one (the mirror). Every row of the inventory is one of these
three outcomes.

## 3. The options

### 3.1 A: detect across observers (recommended)

**Why not as the package sketches it.** "A unit says whether a rule made
its key" has no carrier: a verify shard holds group sums, not units
(`spec/digest.md` §11; unit lists only with detail), and a bit in a
unit's `flags` would change every group digest and `scheme`. A list of
keys per observer, inline, is the "count per key is too much" of
`spec/verify.md` "Open questions": the sum over observers is four orders
of magnitude larger than the union (§3.5). The design below keeps the
exact join and removes the sum.

**What each observer says.** For the post-image, under a non-empty
table, the walk gives two lists. Both hold only entities that are not
namespaces, not of a `units::repeatable` kind (those do not collide in
one observer either), and not of internal linkage (`Ast::linkage`, as
`enclosing.rs` reads it; an entity in an unnamed namespace included; a
linkage the walk cannot read is contributed: fail closed).

- **made**: an owned entity whose key a rule made: its own key matched a
  rule (`Trace::Via`), or it is a member in the sense of §9.2 and a
  level of its namespace chain was matched by a rule (the entities a
  namespace rule would count in `kept_via` were they kept). The entry is
  its key `K`, the rule, and where its first declaration is.
- **fixed**: a dependency entity (rule 1 refused; only-by-inclusion ones
  included) with either
  - **T**: its own key is one a rule could make: a rule produces it
    (`RuleTable::produces`), or a level of its namespace chain, as it is
    keyed, has a key a rule produces (it lives in `old`). The entry's
    key is its own key;
  - **M**: the key it would have were it owned (its namespace parent
    keyed in the owned view, `key_in(ns, Some(true))`, then the table on
    its own key) differs from its own key (it lives in `fresh`, or a
    rule names it). The entry's key is that as-if-owned key.

  The entry also has the name as a person writes it (`spec/verify.md`
  §6.1) and where the read-only declaration is.

Both tests are on keys the front end resolved and on the table; no name
or text is read. The T test over-approximates (everything a dependency
declares in `old`); that costs bytes, never a finding, because the join
is on the key.

**What follows contributes nothing.** A class member (its parent is the
class's key), a specialisation or instantiated member (it takes its
template's or pattern's mapped name), an implicit member, a guide of a
dependency template: each has a key made from another entity's, and that
entity is in the lists. A discriminator mentions entities by their own
ownership (`spec_key`, the signature's types); if two observers disagree
about a mentioned entity, the keys of what mentions it differ and the
join misses *there*, but the mentioned entity is itself in conflict and
is reported: every disagreement bottoms out at a namespace-scope entity
or at one a rule names, which are exactly the entries. `extern "C"`
entities are never made by a namespace rule (their parent is
`c_linkage`), so they have no entry unless a rule names them.

**The run's rule.** Over the `ok` verify shards of the run:

> a key that is in some observer's **made** list and in some observer's
> **fixed** list is an ownership conflict: with a T entry, two entities
> under one key (I2, the pair); with an M entry, one entity under two
> keys (I1, the mirror, and an owned header that is read-only in one
> observer).

A conflict is a finding of the run, kind `ownership`; a run with one is
not verified and permits no write. `combine(states, stale,
obligations_not_passed)` gains a fourth count. The states of the
observers do not change. This is the cross-observer form of
`mark_mapped_collisions`, less internal linkage, which two translation
units cannot share.

That M is I1: the table has no two producers of a key (§2.1), so an
as-if-owned key equal to a made key means the same key under no rule.

**The carrier.** The lists are grouped by the file of the declaration
(the unit's origin file, `spec/digest.md` §11, for made; the first
read-only declaration's file for fixed), as the `digests` section groups
units. A file's list is nearly the same in every observer that includes
the file, so it is stored once:

```
Ownership     := lists: list<digest>      section 32 (proposed; 22, 23, 30 are also free), phase `verify`, status `ok`,
                                          rules not empty; strictly ascending; each the content id of a blob
OwnershipList := file:    bytes           subject path
                 through: bytes           empty; else the read-only file through which `file` was entered, when `file`
                                          is read-only here by the include-chain rule alone
                 made:    list<Made>      strictly ascending by key
                 fixed:   list<Fixed>     strictly ascending by (key, as)
Made  := key: KeyId, rule: uv, line: uv, column: uv
Fixed := key: KeyId, as: T | M, line: uv, column: uv, name: str
```

- **A unit** gains nothing. **`scheme`** does not move: no stream, key
  or table changes; digest goldens do not move. The as-if-owned keys are
  formed outside `rule_use::Counting` and outside `Walk::bytes`: no
  `use` line and no counter of `tests/rules/` moves (asserted in stage
  1). `tests/inert.rs` is unchanged: no rule, no lists, no section.
- **The shard** gains section 32, as 29 and 31 were added (a critical
  id, no change of the shard's version). About 33 bytes per file with an
  entry.
- **The verify job** writes each list with `Store::publish_blob`
  (`blobs/<content digest>`; a worker remembers the ids it has
  published, so a list costs one `stat` per worker at most after the
  first) and the section. It reads nothing another observer wrote: the
  shard and the blobs are a function of the observer's own inputs, the
  declared changes and the overlay, as today. No run-level input is
  given to a job.
- **Reduce** gains nothing (the lists are of the post-image; a map
  shard has none: the pre-image is keyed under no rule and has no
  ownership).
- **The run** gains one fold after the verify phase, beside the stale
  fold: collect the distinct list ids of this run's `ok` shards (with,
  per id, the first plan position and the number of observers), read
  each list once, partition the entries by the key's leading bits into
  files under `tmp/`, and per part sort and intersect made with fixed.
  `slip_verify` stays pure: the fold is a function over sorted entry
  streams, the caller does the I/O, as for reduce. A list that is
  missing, does not hash to its id, or does not decode makes the
  observer that names it `failed` (a shard that is not this run's,
  §9.3): fail closed. The report (`slip.verify.v1`, extended as §9.4
  did) gains `ownership`: the conflicts, sorted by key, listed up to the
  findings' limit with the total.

**Cases.** §3.4.

**Attacks.**

- *Order of observers.* The fold is a set intersection; the verdict is
  order-free. "First observer" in a finding is the least plan position.
  To be tested in both orders.
- *An observer added or removed.* Adding one can only add entries, so
  only add conflicts. Removing `Y` (a run over a selection) removes its
  fixed entries: the run says `verified` of the selection, the existing
  limit of §8 and §9. An observer that is not `ok` contributes nothing;
  the run is then not `verified` on its own account.
- *A dependency header only some observers include through a
  macro-conditional include.* One observer that includes it is enough.
  None: S15, §8.
- *Two declarations whose signatures are spelled differently.* The key
  holds the signature's digest in mapped terms. Different types:
  different keys, different functions, no finding, rightly. The same
  type spelled through an alias: the same key, a finding. A signature
  that mentions a moved owned type the dependency also declares: the
  keys agree if the type's ownership agrees, and if it does not, the
  type is the finding ("What follows").
- *Templates and specialisations.* A template is an entry like any
  entity (S4). A specialisation follows it (S7).
- *Internal linkage.* Not contributed (S19). Mutation: contribute it.
- *Inline and unnamed namespaces.* Levels of the chain like any other,
  as §9.2 climbs them; an unnamed level makes the entity internal.
- *C linkage.* S20: no entry, rightly; with a rule on the function
  itself it is an entry by its own key.
- *`kept`.* A kept entity that was not moved is in no made list (S11).
  One kept and moved is already stale by `kept_via`, and is a conflict
  too.
- *A list in the store that no longer matches its id, or was removed.*
  The observer is `failed`. Retention: a list lives as long as a shard
  that names it (Q3).
- *Two rules that make one key.* Refused by the table (§2.1); were it
  to happen, two made entries with one key in different files are not
  reported by this fold. Not this package's.

**Cost.** §3.5. No second parse.

**What incremental execution loses.** Nothing per job: a reused verify
shard names lists that are in the store. The fold runs once per run over
the distinct lists; it can be cached under the digest of the sorted
distinct ids (not proposed for the first build).

### 3.2 B: decide ownership for the run, before the digests

**Mechanism.** The set "keys some observer saw declared outside owned
files" must exist before the verify jobs. From the map phase: the map
task would need the run's ownership (it has none today: `EVERY_FILE`)
and would write, per read-only file, the keys under no rule of what the
file declares (the same per-file lists as A's `fixed`, without the
region test, since the rules are not known before reduce). A fold before
the verify phase makes the set `F`; the plan or the binding names it;
each verify job loads it, and `owned(e)` also answers "dependency" when
`e`'s key under no rule is in `F` (a second key computation per owned
entity, in a walk under the empty table, as `mark_mapped_collisions`
does for collisions only).

**What it gives.** `u1` no longer maps `fresh::hook` back: `removed
old::hook(int)`, `added fresh::hook(int)`, and `changed` for every unit
of `u1` that names it. The finding is the ordinary one, in the
observer; nothing in it says why (the dependency's file is not named
unless a note is added).

**What it costs and loses.**

- Every verify shard depends on `F`. Named by the binding, any change
  of `F` (one dependency header edited, one observer's includes
  changed) invalidates every verify shard of the run: 10^5 jobs. To
  avoid that a shard must record which keys it asked and what it was
  told, which is A's per-file lists again, plus the invalidation logic.
- `F` is of the pre-image. An edit that adds an include of a
  dependency header, or the overlay's own new declarations, change what
  the post-image's observers see: A's check after the verify phase is
  still needed (that is "both").
- A second key computation for every owned entity in every observer.
- The map phase learns ownership, and `slip parse` shards made without
  it are refused or made again.
- It does not make `a4` right: `Y`'s reading spreads to `X`, so both
  refuse the correct edit instead of one.

**Attacks.** Order: `F` is a union, order-free. An observer added: `F`
grows, every shard is invalid. The conditional include, signatures,
templates, internal linkage, inline namespaces, C linkage: as A (the
same keys; internal linkage must be kept out of `F` by the same test).

### 3.3 C: ownership by the declaration's file alone; and "both"

**C.** Dropping the include-chain rule (a file is owned or not by its
path, however entered) changes S9 only: `own.h` is owned in `Y` too. It
reopens `dependency-built-against-owned-*-through-dependency-first`
(WP-110's F2: a dependency compiled against an owned header; a moved
exception type is no longer caught), which that rule closed, and it does
not touch the pair, the mirror, or anything in §2.2 marked WV: there the
read-only declaration is in a read-only file by its path. Rejected as an
answer. The refused correct edits of S9 (a precompiled header, a unity

**Both** (B decides, A checks). Pays for both, and B's decision adds no
detection to A's: the join is on the same keys. Rejected unless findings
must be per observer (below).

**What would decide between A and B.** (1) If the supervisor requires
the finding in the observer's own verdict (per-file feedback, a verdict
that is right without the run), B or "both" is needed; A's finding is
the run's. (2) The measured size of the lists on the corpus: if the
distinct lists were not far smaller than the sum (many variants per
header), A's store cost approaches the inline cost and B's single set
looks better. Stage 2 measures it before the fold is built.

### 3.5 Cost at 10^5 observers and 10^7 moved entities

Assumptions, to be replaced by the corpus's figures in stage 2: an
observer keys 5 x 10^4 entities that would have an entry (most of what
it declares at namespace scope under the two roots, owned and not), in
10^3 of its files; the dependencies declare 10^6 distinct entities under
the two roots; a file's list has `v` distinct contents over the run
(conditional compilation, include order), guessed 1.2 to 2.

| | Inline lists (rejected) | A as proposed | B |
|---|---|---|---|
| bytes per observer in the shard | 5 x 10^4 x 36 = 1.8 MB | 10^3 x 33 = 33 KB (the `inputs` section is about 2 x 10^5) | the answers it was given, or nothing and full invalidation |
| bytes over the run | 180 GB | 3.3 GB in shards; lists once: 10^7 x 36 x v + 10^6 x 80 x v = 0.5 to 0.9 GB | map lists 10^6 x 36 x v; `F` 32 MB |
| objects in the store | none | one per distinct list: 2 to 5 x 10^5 (headers x v, and one per main file with a made entry) | the same for the map lists |
| worker time per observer | sort and write 1.8 MB | one pass over the keyed entities, one key formed per M candidate, sort and hash 2 MB: milliseconds; up to 10^3 `stat` on first sight | a second key per owned entity |
| fold memory | bounded by the merge | the distinct ids (10^6 x 48 B at most) and one part at a time (the lists' bytes / parts) | `F` in every worker |
| fold time | 180 GB read | the lists read once (under 1 GB), sorted in parts, parallel over parts: seconds to a minute | a fold before verify, and the verify phase waits for it |
| extra parses | none | none | none, unless `F` changes |

The number that decides is the ratio of distinct list bytes to summed
list bytes; counters `verify.ownership.made`, `.fixed`, `.lists`,
`.bytes` per shard and the fold's `distinct` and `bytes` give it. If a
main file's list is unique to its observer (it is), it could be inline
in the section to halve the object count; decided by the measurement.
A compact filter per file instead of the made keys (1 to 2 bytes per
key) was considered and rejected: a false hit would be a finding or a
second parse.

### 3.6 Where A cannot tell (each stays verified wrongly, or is a finding)

- **Observers not in the run.** A selection (`--only`), or a dependency
  header no observer includes (S15): no fixed entry. `spec/verify.md`
  §8, unchanged. Closing it needs the dependency's headers parsed as
  observers of their own; not proposed.
- **A pasted name (S16), a guard-skipped inclusion where no observer
  enters through the dependency (S17).** Owned in every observer: no
  fixed entry. WP-116 and Kiln's WP-2111.
- **A friend that only a class template's pattern declares (S22).** In
  an observer that does not instantiate the class the friend is keyed
  under the class (`keys.rs` `friend_class`) or not at all, so no
  namespace-scope fixed entry exists. By reading; to be pinned by a
  pending test in stage 0.
- **An entity the walk does not key** (no key formed: a refused table,
  a cycle): no entry; its unit is indeterminate already.
- **A linkage the walk cannot read:** contributed (a finding, not a
  hole).
- **What the dependency's binary holds and no header declares** (an
  opaque handle, a symbol named in assembly): no reading of sources
  shows it; WP-116's assertion is the user's word for it.

## 4. Recommendation

**A**, with the mirror in scope: per observer, per-file lists of the
keys a rule made and of the keys dependency entities have (or would
have were they owned), stored once by content; one fold at the run's
conclusion; a conflict is a finding of the run and the run is not
verified. Ownership inside an observer stays exactly as §2.1 decides it
(per declaration seen, per inclusion). No digest, key or `scheme`
changes, no job reads another observer's output, no second parse.

**The one rule, for WP-144 to build on:** a rule's mapping of an entity
stands for the run only if no observer of the run holds that entity, or
another entity with its mapped key, as a dependency's.

**What the user sees for the pair** (the report's member, and its line;
the positions here are illustrative):

```
ownership: old::hook(int) is one key for two entities
  made by rule 1 (relocate old => :: fresh): u1.cpp:1:21, owned in 1 observer (first: u1.cpp)
  fixed by a read-only file: old::hook(int) at dep/d.h:1:21, in 1 observer (first: u0.cpp)
  the dependency keeps the old name: what it declares is no longer what the edit defines
```

and for the mirror: `ownership: fresh::g(int) has two keys: old::g(int)
where owned (rule 1, u1.cpp:1:17), its own where dep/e.h:1:22 declares
it (first: u0.cpp)`. For S9 the second line names the owned header and
`entered through ro_inc.h (read-only)`.

**What they declare.**

- *The hook stays.* Do not move it, and declare `kept old::hook(int)`:
  the entity is then in no made list, and §9.2 already checks that no
  observer moved it (`kept_via`) and that it is seen. Nothing new.
- *The dependency is edited too.* Its header is put under the run's
  owned files and the transform moves the declaration: `u0` then reads
  `fresh::hook` as owned, there is no fixed entry, and `u0`'s own call
  is checked as any moved reference. Nothing new.
- *The declaration is spurious* (a dead declaration in a header that
  cannot be touched). Nothing in the first build: the run fails closed
  and the user must take one of the two ways above. Proposed for later,
  shared with WP-116's item 3 (Q5): the assertion `owned <entity>`,
  honoured by the fold only when no owned unit of any observer refers to
  the dependency's declaration (a bit on the fixed entry), listed in
  every report that relied on it, reported when unused.

## 6. Stages

Each merges alone; the gate is the package's.

- **Stage 0: pin.** Pending tests, one per shape of §2.2 with two
  observers (three for S12; both orders for S1 and S10), at the level
  the review's probes ran (`crates/slip_verify/tests/`, real shards
  from sources), each expecting its §3.4 answer under A; the limits
  (S15, S16, S17, S22) pinned with today's answer and the reason. This
  confirms every "by reading" above before anything is built; a shape
  that does not behave as written comes back to the supervisor.
- **Stage 1: the walk.** `Output` gains the lists (made, fixed with T
  and M); the rules runner prints them (`made <name>`, `fixed T|M
  <name>` lines, optional in `expect.txt`). Asserted: no digest, `use`
  line or counter of `tests/rules/` moves. Mutations: the M key formed
  in the dependency view; the T test on the entity's own key only (the
  chain not climbed, or one level); internal linkage contributed; a
  namespace contributed; a repeatable kind contributed; a class member
  contributed; only-by-inclusion entities left out; the first
  declaration's file instead of the first read-only one's.
- **Stage 2: the record.** Section 32, the list's encoding and reader
  rows (`spec/model.md` §8), the verify job's writer, the counters.
  Inert for the verdict. **The corpus figures** (`llvm`, `lib/Support`:
  entries, lists, bytes summed and distinct, worker time) go into this
  file here, and the estimate of §3.5 is confirmed or the supervisor is
  asked again (§3.3).
- **Stage 3: the fold and the verdict.** `slip_verify` (pure, from
  constructed lists), the caller's I/O, the report, `combine`; the
  pitfall rows: the pair `bad`, the pair with `kept` `good`, each
  shape; WP-140's pending test passes. Mutations: the join on T only,
  on M only; a missing list read as empty; a list of a shard that is
  not `ok` folded; "first" by arrival and not by plan position; the
  conflict not counted in `combine`; conflicts of namespaces reported.
  The package's "Done when" is met here.
- **Stage 4, after a ruling on Q5 and Q6:** the assertion and the
  reference bit, with WP-116.
- **Specs**, with the stage that makes them true: `spec/verify.md` §2.1
  (the paragraph "Ownership is read from the declarations the

## 7. Questions for the supervisor

1. **A, not B.** The finding is the run's, not in an observer's own
   verdict; each observer stays `verified`. Accepted? (§3.3 says what
   evidence would turn it.)
2. **The mirror (§0.1) in this package?** Recommended: the same lists
   and fold; one extra key per dependency entity under a matched
   namespace. It will report every owned name moved onto a name a
   dependency already declares in `fresh`, which in the motivating use
   may be many, and each is a real merge of two entities.
3. **Lists as blobs a verify worker publishes, named from the shard**
   (section 32). New: a verify shard is no longer self-contained, the
   store gains 10^5 to 10^6 small objects, and a retention rule is
   needed (a list lives while a shard names it). The alternative is
   inline lists at about 180 GB for the full run.
4. **Which kinds are reported.** Proposed: every kind that collides in
   one observer, less internal linkage; that includes aliases and
   typedefs (S21), which no binary holds. Restricting to external and
   module linkage reports less, and leaves "two entities alike across
   observers, verified" true for aliases. Which?
5. **The third resolution.** Fail closed first (no way to declare "the
   dependency's declaration is spurious" until stage 4), then one
   assertion `owned <entity>` shared with WP-116, honoured only where no
   owned code refers to the dependency's declaration. It changes what
   the user declares and is the user's word against a binary. Accepted,
   or no assertion at all?
6. **WP-116 after WP-146, on its carrier, not merged** (§5 (c)); and
   the correction of `spec/verify.md` §2.1 (§0.2): the fixture
   `observer-includes-owned-only` and the `-direct-first` pair have no
   planned answer when no observer shows the dependency's reading.
   Should a package be written for "dependency headers no observer
   includes" (parsed as observers of their own), or does §8 stand?
7. **Selections.** A run over part of the plan folds that part only and
   says `verified` of the selection, as §9 does today. Keep, or should a
   run with rules refuse `verified` unless every observer is selected?
8. **The include-chain rule stays** (C rejected); S9's refused correct
   edits wait for WP-118. And the rule for WP-144 as worded in §4.
9. **Stage 0 before the ruling takes effect?** Several shapes are "by
   reading" (S2 to S4, S6 to S8, S10, S22, S23). Stage 0 costs builds on
   a loaded host but turns each into a run before the walk is touched.
   Recommended.
