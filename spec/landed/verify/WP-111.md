## 1. What "inside" means (item 1)

`direct(r)` and `kept_via(r)` count the **owned entities that are not
namespaces and whose parent, in the owned view of §2.1 rule 2, is a
namespace**. For each, the walk climbs the whole chain of namespaces
above it to the global namespace. A level whose own key no rule matched,
and which rules produce, adds those rules to the entity's `direct` set.
A level that a rule matched adds that rule to its `via` set. A kept
entity (its mapped key is in `Declared.kept`) counts `kept_via` for its
`via` set. Any other entity counts `direct` for its `direct` set. Each
rule counts at most once per entity and per count.

Each decision has a fixture under `crates/slip_digest/tests/rules/stale/`:

| Case | Decision | Fixture | Counts |
|---|---|---|---|
| inline namespace | a level like any other: `legacy::v1::b` is inside `legacy` | `inline-namespace` | via 1, direct 1 |
| unnamed namespace | a level like any other: `legacy::(anonymous)::b` is inside `legacy` | `unnamed-namespace` | via 1, direct 1 |
| a nested namespace a second rule maps elsewhere | a member left in `legacy::detail` is inside both `legacy::detail` (whose key the second rule produces) and `legacy`: `direct` for both. Fail closed. The cost: an edit that deliberately leaves an owned entity in the nested namespace must list it in `kept`. | `nested-mapped-elsewhere` | each rule: via 1, direct 1 |
| a namespace reached through two rules (both produce its key) | each rule gets the count, once | `split-namespace` | each rule: via 1, direct 1 |
| two rules, one per level | each level's rule counts | `two-levels-relocated`, `two-levels-relocated-kept` | via 1, direct 1 (and kept_via 1 when kept) |

What is not counted:

- **Dependency entities.** They are keyed in the dependency view, and no
  rule reaches them.
- **Namespaces' own keys.** This is the merge of §2.1, so a namespace
  that keeps `r`'s key is not stale by itself. A namespace that a rule
  matched still counts in `via`.
- **Class members.** They follow their class.
- **Specialisations and their members.** They are keyed under their
  template.
- **Friends.** They are keyed under their class.
- **Entities with C language linkage.** Their parent is `c_linkage`.

Kept keys:

- `Declared.kept` is compared with the entity's mapped key.
- Every entity whose mapped key is in `kept`, owned or not, marks that
  key seen (`Output.kept`, `RuleUse.kept`).
- A `kept` key that no observer has is reported, like an exemption no
  observer needed (`unseen_kept`, §9.4).

## 2. The attack list (item 5)

Two observers, `a0` and `a1`. The counts are the fixture's for the rule
`relocate legacy => :: acme`. `crates/slip_verify/tests/agreement.rs`
builds the shards and checks the run's `stale`, verdict, `unused` and
`unseen_kept`.

| Case | Fixtures (a0, a1) | a0 via/direct/kept_via | a1 via/direct/kept_via | Stale | Right |
|---|---|---|---|---|---|
| a function in two owned headers, one edited | `two-headers-edited`, `two-headers-unedited` | 1/0/0 | 1/1/0 | a1 by `direct` | yes |
| an owned overload for a dependency type that stays, listed in `kept` | `overload-kept` (both) | 1/0/0 | 1/0/0 | no | yes |
| the same, not listed | `overload-not-kept`, `overload-kept` | 1/1/0 | 1/0/0 | a0 by `direct` | yes |
| the same, listed and moved in one observer (one key, reached through `r` in one observer and directly in the other, where it is kept) | `overload-kept`, `overload-kept-moved` | 1/0/0 | 1/0/1 | a1 by `kept_via` | yes |
| a compatibility `using` in the old namespace, in `kept` and `created` | `compat-using` (both) | 1/0/0 | 1/0/0 | no | yes |
| an owned explicit specialisation of a dependency template in the old namespace | `explicit-spec-of-dependency` (both) | 1/0/0 | 1/0/0 | no (not counted) | yes |
| an entity owned in one observer and a dependency entity in the other | `owned-or-dependency-dep`, `owned-or-dependency-owned` | 1/0/0 | 1/0/0 | no | **no**: `docs/wp/WP-116.md` |
| a namespace only one observer sees | none (see below), `two-headers-edited` | no `Use` | 1/0/0 | no | yes |

**The wrong case** (the pair: `owned-or-dependency-dep` and
`owned-or-dependency-owned`).

- `legacy::f(int)` is declared by the dependency in a read-only header,
  which only `a0` includes.
- In `a1` it is owned and moved to `acme`.
- `a0` does not count it (it is a dependency entity there), and `a1`
  counts it as `via`.
- Both observers verify, and the program declares `legacy::f` in the
  dependency and `acme::f` in owned code.
- Neither count can show it. WP-116 closes it: a renamed entity must be
  defined in owned code.

**A namespace no observer's file declares** cannot be a rules fixture,
because `rules.txt` resolves `legacy` in the pre-image. The run's table
covers it with a shard that has no `Use`.

The case with a compatibility `using` counts its using-declaration and
its shadow as kept: `legacy::<using acme::f>` and
`legacy::<shadow acme::f(int)>`. A compatibility declaration listed in
`created` but not in `kept` would be counted `direct`, and the observer
would be stale. That is fail closed, and it is the reason `kept` exists.

No correct edit of these cases is undeclarable.

## 3. `slip declare` (item 4 and the added items)

- **`kept <entity>`** is resolved in the post-images under the file's
  rules, like `created` (a key no observer has is reported by the run).
  The output gains the line `kept <n>`.
- **`DependencyEntity`.** A `relocate` line whose entity has a
  declaration in a read-only file, or is a specialisation or an implicit
  member of one, is refused unless it is a namespace. `slip declare`
  computes this from the pre-image (`slip_digest::records::facts`) when
  the files are known (`--owned`/`--readonly`).
- **C language linkage** (the coordinator's ruling: §2.3 stands, and
  the brief's error item is struck).
  - A `relocate` line for an entity whose key has the parent
    `c_linkage` is accepted. Its `<parent>` is resolved in the
    post-images like any other, so one that resolves to nothing is
    `NoUnit`. The rule is `Rule { parent: c_linkage, …, to_parent:
    c_linkage, to_name: name }`.
  - Before this, on main, the rule had the parent `root`, which matches
    no key (WP-056's catalogue run).
  - The parent looks nothing up, so such a line has no probe for
    `Order`.
  - Tests: `s2_3_c_linkage` (the two spellings give one rule and one
    `rules_id`; `nowhere` is `NoUnit`; no `Order`) and
    `loop_c_function_renamed` (a rename that verifies, for both
    spellings), in `crates/slip_cli/tests/declare.rs`, and
    `s2_3_declare_errors` in `tests/verify.rs`.
  - **Moved, not renamed** (`relocate legacy::c_fn(int) => acme :: c_fn`,
    or `=`): accepted, with the rule that maps the key to itself. It
    changes no key. Under §9.1 the function's key is matched by the rule,
    so it counts in `via`: the rule is used, and is not stale (it is not
    of kind `namespace`, and no entity has its key unmatched). The text
    is not silent here, so this is not a fail-closed decision. It is
    stated in §2.3.
- **`Order`.** A line whose new parent, or a namespace or class
  enclosing it, is relocated by a **later** line is refused at the later
  line, and the error names the earlier one. The check: each level of
  the new parent's chain, as the earlier line looked it up, is compared
  with each later rule's match.
  - Tests each way: `s2_3_order_of_lines` and `s2_3_declare_errors`.
  - With this check, every accepted order of a file's lines gives one
    `rules_id` (§2.3). `every_order` permutes the lines of each fixture
    of `the_rules_suite_resolves_alike` and of
    `s2_3_every_accepted_order_gives_one_table`, and checks that every
    order is either refused with `Order` or gives the one table.
- **Friend rules.** A function that a class template befriends without
  defining it (`Facts.undefined_friends`) gets a second rule for the
  friend declaration's key when its name changes.
  - `s2_3_undefined_friend_gets_its_rule` has the pair that is a
    mismatch without that rule.
  - The same rule given again is accepted.
- **`--owned` that covers nothing.** An `--owned` entry that covers no
  file a selected pre-image read is a warning, the status unchanged:
  `slip: warning: declare: --owned <real path> covers no file the
  selected observers' pre-images read` (WP-053 F2).
- **Real paths.** `--owned`/`--readonly` and the subject's files are
  compared by real path. `s2_3_dependency_entity_through_a_link_each_way`
  has a read-only header reached through a link under the owned root,
  and an owned one through a link under the read-only root.
