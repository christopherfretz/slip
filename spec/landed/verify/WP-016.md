# WP-016 — slip_verify: the comparison

Behaviour of `slip_verify::compare` (`crates/slip_verify/src/compare.rs`)
that `spec/verify.md` §3, §4, §4.1 and §6 do not state exactly. Normative
until folded into `spec/verify.md`.

WP-017 changed it to the amended spec: §4 steps 2 and 3 on the multiset
differences `R(k)`, `A(k)`; an indeterminate derived key a finding on
either side; `file`, `pre` and `post` as §6 now defines them; `at_sums` on
`(count, indeterminate, digest)` with every indeterminate group in `G`;
`verdict_at_sums` replaced by `verified`; `CompareError::IndeterminateMismatch`.
This file describes the code after WP-017.

## Interface

Re-exported at the crate root:

```rust
pub struct Exemptions { /* changed, created, removed: Vec<Digest> */ }
impl Exemptions {
    pub fn none() -> Exemptions;
    pub fn new(changed: Vec<Digest>, created: Vec<Digest>, removed: Vec<Digest>)
        -> Result<Exemptions, String>;
    pub fn changed(&self) -> &[Digest]; // and created(), removed()
}

pub fn comparable(pre: &Digests, post: &Digests) -> Result<(), String>;

pub enum AtSums { Equal, Differing(Vec<(GroupClass, Vec<u8>)>) }
pub fn at_sums(pre: &Digests, post: &Digests) -> AtSums;

pub struct Comparison { pub findings: Vec<Finding>, pub only_pre: u64, pub only_post: u64,
                        pub used: Vec<Digest> }
pub enum CompareError {   // every variant: { class: GroupClass, file: Vec<u8>, post: bool }
    MissingUnits, UnitsNotAscending, BadFlags, CountMismatch, IndeterminateMismatch,
    DigestMismatch, DuplicateGroup,
}
pub fn compare_groups(pre: &[&Group], post: &[&Group], exemptions: &Exemptions)
    -> Result<Comparison, CompareError>;

pub fn verdict(comparison: Comparison, pre_shard: Digest, rules: Digest, limit: usize) -> Verdict;
pub fn verified(pre_shard: Digest, rules: Digest) -> Verdict;
pub fn unverifiable(reason: &str, pre_shard: Digest, rules: Digest) -> Verdict;
```

and `compare::REASON_MAX` (4096), `compare::NO_REASON`. `CompareError`
implements `Display` and `Error`; `post` says which image the group came
from.

The verify job uses them as: `comparable`; then `at_sums`; `Equal` is
`verified(…)`; `Differing(G)` is `verdict(compare_groups(groups of G from
each image, …), …)`. Every finding therefore has a key.

## Preconditions

Inputs that break a stated precondition are rejected, never compared:

- `Exemptions::new`: each list strictly ascending (unsorted or a duplicate
  is `Err`). A key may be in several lists.
- `comparable`: in this order, for the pre then the post image: `scheme` is
  `digests::SCHEME`; then, per image, `groups` strictly ascending by
  `(class, file)` and `tu = tu_digest(groups)`. The last two are checked
  because §4.1 step 1 trusts `tu`; `at_sums` does not recompute it.
- `compare_groups`, per image: no `(class, file)` given twice
  (`DuplicateGroup`, reported first); then for each group in the order
  given: `units` present (`MissingUnits`), strictly ascending by
  `(key, digest)` as `digest.md` §11 and WP-015 require
  (`UnitsNotAscending`; this covers duplicates, and two units of one key
  and digest that differ only in flags), every `flags` 0 or 1 (`BadFlags`:
  an unknown flag bit would otherwise be ignored by §4, which compares
  digests only), `count = units.len()` (`CountMismatch`), `indeterminate`
  the number of units with the flag (`IndeterminateMismatch`),
  `digest = group_digest(units)` (`DigestMismatch`). The pre-image is
  checked before the post-image. Groups need not be given in order. A
  group with an empty list (count 0) is accepted.
- `at_sums` needs no precondition: it sorts the groups itself. It is
  `Equal` when the `tu` digests are equal and every group of both images
  has `indeterminate` 0. Otherwise `Differing` lists, ascending, every
  `(class, file)` whose sums `(count, indeterminate, digest)`, as a
  multiset, differ between the images, and every `(class, file)` with a
  group of `indeterminate > 0` in either image. With equal `tu` digests
  the list is the indeterminate groups. A `(class, file)` present twice in
  one image only is reported, and `compare_groups` then rejects it.

## The comparison (§4)

Implemented as written: declared and `tu` groups form `D`, derived groups
`V` (§3); each occurrence of a unit in a group counts once (§3
multiplicity); keys are walked in order over the sorted occurrences, so the
work is linear after sorting. `R(k)` and `A(k)` are computed by merging the
key's two runs, which are sorted by digest.

- **Step 1.** A key with an indeterminate unit on either side of `D` is one
  `indeterminate` finding and nothing else, whatever the exemptions; it is
  never in `used`. This includes a key present on one side only.
- **Step 2.** `changed` when `R(k)` and `A(k)` are both non-empty,
  `removed` when only `R(k)` is, `added` when only `A(k)` is. `changed`
  prevents only `changed`, `removed` only `removed`, `created` only
  `added`. A prevented finding puts `k` in `used`; an exemption whose key
  had no finding of its kind is not used.
- **Step 3.** A key with an indeterminate unit on either side of `V` is one
  `derived_indeterminate` finding, also on one side only, and is then not
  counted. Otherwise `derived_changed` when both `R(k)` and `A(k)` are
  non-empty; only `R(k)`: counted in `only_pre`; only `A(k)`: counted in
  `only_post` (once per key whatever its multiplicity). No exemption
  applies to a derived key, so `changed` on a key does not prevent
  `derived_changed`.
- A key **declared in one image and derived in the other** is in `D` on
  one side and in `V` on the other: step 2 gives `removed` (declared
  before) or `added` (declared after), which its exemption may prevent,
  and step 3 counts it in `only_post` or `only_pre`. A key in both `D` and
  `V` of one image is compared in each independently.
- `used` is ascending, no two equal (each key is visited once in `D`).

## Findings (§6)

- `key` is always present; `name` is empty and `location` is `None`.
- A group **differs** when the other image was given no group of its
  `(class, file)`, or was given one whose unit list (flags included) is not
  the same. `compare_groups` pairs the groups it is given by
  `(class, file)`; so given only the groups of `G` it decides the same as
  given all groups, since a group outside `G` has the same units in both.
- `changed`, `removed`, `added`, `derived_changed`: `pre` is the element of
  `R(k)` when it has exactly one (counting multiplicity), else absent;
  `post` likewise from `A(k)`. `file`: the file of the smallest
  `(class, file)` among the pre-image groups that differ and hold a unit
  of the key (in `D`, or in `V` for `derived_changed`); if there is none,
  among the post-image's. A group that holds the key but does not differ
  is skipped even when it comes first; a group that differs for another
  key's sake is not (`s6_file_with_a_moved_unit_beside_a_real_difference`).
  §6 says there is always one; if there were not, the code panics
  (`unreachable!`), which would be a defect of this crate.
- `indeterminate`, `derived_indeterminate`: `pre` is the digest of the
  key's indeterminate unit in the pre-image when there is exactly one
  occurrence of an indeterminate unit of the key (counting multiplicity:
  one flagged unit in two groups is two), else absent; `post` likewise.
  `file`: the smallest `(class, file)` among the pre-image groups holding
  an indeterminate unit of the key, differing or not; if none, among the
  post-image's.
- Declared groups sort before the `tu` group (class order), so a key with
  units in both reports the declared group's file, not the empty one.
- Order: `(kind, file, key)`; all keys are present.

## Verdicts (§6)

- `verdict`: `mismatch` if there is a finding, else `verified`;
  `total` is the number of findings before the cut; `findings` the first
  `limit`; `only_pre`, `only_post`, `used` copied, also for `verified`;
  `reason` empty.
- `verified(…)`: `verified`, `total` 0, no finding, counts 0, `used`
  empty, `reason` empty; the verdict of `at_sums` = `Equal`. It equals
  `verdict` of an empty comparison.
- `unverifiable(reason, …)`: `reason` cut to at most 4096 bytes at the
  last character boundary at or before byte 4096; an empty reason (also
  one whose cut is empty) becomes `NO_REASON` (`"no reason given"`), so
  the verdict satisfies WP-015's "`unverifiable` has a non-empty reason".
  `total` 0, no finding, counts 0, `used` empty.

## Open questions

1. `pre`/`post` of the indeterminate kinds, "exactly one such unit": read
   as one occurrence counting multiplicity, like `R(k)` in the other
   bullet of §6. Either reading is exact under §4.1 (every indeterminate
   unit is in `G`).
2. The `file` of a `changed` finding can name a group whose copy of the
   key did not change, when that group differs for another key's sake
   (above). It is what §6 says, and it is the same through groups; a rule
   that named the group where the key's own units differ would need the
   per-group multiset of the key, also exact, at some cost.
