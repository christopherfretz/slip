# WP-016 — slip_verify: the comparison

Behaviour of `slip_verify::compare` (`crates/slip_verify/src/compare.rs`)
that `spec/verify.md` §3, §4, §4.1 and §6 do not state exactly. Normative
until folded into `spec/verify.md`.

## Interface

Re-exported at the crate root:

```rust
pub struct Exemptions { /* changed, created, removed: Vec<Digest> */ }
impl Exemptions {
    pub fn none() -> Exemptions;
    pub fn new(changed: Vec<Digest>, created: Vec<Digest>, removed: Vec<Digest>)
        -> Result<Exemptions, String>;
    pub fn changed(&self) -> &[Digest]; // and created(), removed()
}

pub fn comparable(pre: &Digests, post: &Digests) -> Result<(), String>;

pub enum AtSums { Equal, Differing(Vec<(GroupClass, Vec<u8>)>) }
pub fn at_sums(pre: &Digests, post: &Digests) -> AtSums;

pub struct Comparison { pub findings: Vec<Finding>, pub only_pre: u64, pub only_post: u64,
                        pub used: Vec<Digest> }
pub enum CompareError {   // every variant: { class: GroupClass, file: Vec<u8>, post: bool }
    MissingUnits, UnitsNotAscending, BadFlags, CountMismatch, DigestMismatch, DuplicateGroup,
}
pub fn compare_groups(pre: &[&Group], post: &[&Group], exemptions: &Exemptions)
    -> Result<Comparison, CompareError>;

pub fn verdict(comparison: Comparison, pre_shard: Digest, rules: Digest, limit: usize) -> Verdict;
pub fn verdict_at_sums(indeterminate: u64, pre_shard: Digest, rules: Digest, limit: usize) -> Verdict;
pub fn unverifiable(reason: &str, pre_shard: Digest, rules: Digest) -> Verdict;
```

and `compare::REASON_MAX` (4096), `compare::NO_REASON`. `CompareError`
implements `Display` and `Error`; `post` says which image the group came
from. The brief's interface, with `CompareError` given the variants below.

## Preconditions

Inputs that break a stated precondition are rejected, never compared:

- `Exemptions::new`: each list strictly ascending (unsorted or a duplicate
  is `Err`). A key may be in several lists.
- `comparable`: in this order, for the pre then the post image: `scheme` is
  `digests::SCHEME`; then, per image, `groups` strictly ascending by
  `(class, file)` and `tu = tu_digest(groups)`. The last two are checked
  because §4.1 step 1 trusts `tu`; `at_sums` does not recompute it.
- `compare_groups`, per image: no `(class, file)` given twice
  (`DuplicateGroup`, reported first); then for each group in the order
  given: `units` present (`MissingUnits`), strictly ascending by
  `(key, digest)` as `digest.md` §11 and WP-015 require
  (`UnitsNotAscending`; this covers duplicates, and two units of one key
  and digest that differ only in flags), every `flags` 0
  or 1 (`BadFlags`: an unknown flag bit would otherwise be ignored by
  §4, which compares digests only), `count = units.len()`
  (`CountMismatch`), `digest = group_digest(units)` (`DigestMismatch`).
  The pre-image is checked before the post-image. Groups need not be
  given in order. A group with an empty list (count 0) is accepted.
- `at_sums` needs no precondition: it sorts the groups itself and puts in
  `Differing` every `(class, file)` whose sums `(count, digest)`, as a
  multiset, differ between the images. A `(class, file)` present twice in
  one image only is therefore reported, and `compare_groups` then rejects
  it.

## The comparison (§4)

Implemented as written: declared and `tu` groups form `D`, derived groups
`V` (§3); each occurrence of a unit in a group counts once (§3
multiplicity); keys are walked in order over the sorted occurrences, so the
work is linear after sorting.

- **Step 1.** A key with an indeterminate unit on either side of `D` is one
  `indeterminate` finding and nothing else, whatever the exemptions; it is
  never in `used`. This includes a key present on one side only.
- **Step 2.** `P(k)`, `Q(k)` are compared as sorted lists of digests.
  `changed` prevents only `changed`, `removed` only `removed`, `created`
  only `added`. A prevented finding puts `k` in `used`; an exemption whose
  key had no finding of its kind is not used.
- **Step 3.** No exemption applies to derived keys: §4 step 3 names none,
  so `changed` on a key does not prevent `derived_changed`. A derived key
  with units on one side only is counted (`only_pre` or `only_post`, once
  per key whatever its multiplicity) and is never a finding, also when its
  units are indeterminate.
- A key **declared in one image and derived in the other** is in `D` on
  one side and in `V` on the other: step 2 gives `removed` (declared
  before) or `added` (declared after), which its exemption may prevent,
  and step 3 counts it in `only_post` or `only_pre`. A key in both `D` and
  `V` of one image is compared in each independently.
- `used` is ascending, no two equal (each key is visited once in `D`).

## Findings (§6)

- `key` is always present in a finding of `compare_groups`; `name` is
  empty and `location` is `None`.
- `file`: the smallest `file` (byte order) among the pre-image groups
  given that hold a unit of the key (in `D` for steps 1–2, in `V` for
  step 3); if the pre-image holds none, the smallest among the post-image
  groups. The `tu` group's file is empty, so a key with a unit in it has
  an empty file.
- `pre` (`post`): the digest when the pre-image (post-image) has exactly
  one occurrence of the key in the groups compared, counting multiplicity;
  otherwise absent. A content-keyed unit in two files therefore has no
  `pre`; `removed` never has `post`, `added` never `pre`.
- Order: `(kind, file, key)`; all keys are present.

## Verdicts (§6)

- `verdict`: `mismatch` if there is a finding, else `verified`;
  `total` is the number of findings before the cut; `findings` the first
  `limit`; `only_pre`, `only_post`, `used` copied, also for `verified`;
  `reason` empty.
- `verdict_at_sums(n, …)`: `verified` for 0; else `mismatch`, `total = n`,
  `min(n, limit)` findings of kind `indeterminate` with no key, empty
  file, no `pre`/`post`; counts 0, `used` empty.
- `unverifiable(reason, …)`: `reason` cut to at most 4096 bytes at the
  last character boundary at or before byte 4096; an empty reason (also
  one whose cut is empty) becomes `NO_REASON` (`"no reason given"`), so
  the verdict satisfies WP-015's "`unverifiable` has a non-empty reason".
  `total` 0, no finding, counts 0, `used` empty.

## Open questions

1. **§4.1's restriction to `G` is not exact** in three cases, each pinned
   by a test at the end of `crates/slip_verify/tests/groups.rs`:
   - *An indeterminate unit in a group outside `G`*: over all units it is
     a step-1 finding; through groups it is not seen, and the observer can
     verify. Step 1 of §4.1 reports `digest.indeterminate` findings when
     the sums are equal, so step 2 is the odd one out. Proposed: the job
     adds unnamed `indeterminate` findings for the indeterminate units
     outside `G` (needs a per-group indeterminate count, e.g. in
     `GroupSum`), or asks for detail on every group with one.
   - *A key with units both inside and outside `G`* (in practice a
     content-keyed unit written in several files): step 2 classifies by
     "`Q(k)` empty", which adding equal multisets changes. A copy removed
     from one of two files is `changed` (2 against 1) over all units and
     `removed` through groups, so a `removed` exemption prevents it only
     through groups (and `changed` only over all units).
   - *The same for a derived key*: `derived_changed` over all units, a
     one-sided count (no finding) through groups.
   The generated test checks exact equality when none of these holds, and
   equality on the keys with no unit outside `G` always. With the fixed
   seed, about 1900 of 12000 pairs diverge otherwise. A rule that is
   invariant under adding equal multisets (classify by `P(k) \ Q(k)` and
   `Q(k) \ P(k)`) would make the restriction exact for steps 2 and 3, at
   the cost of changing the kind of the 2-against-1 case.
2. **The brief's "`AtSums::Equal` exactly when the comparison over all
   groups has no finding and no one-sided derived key"** does not hold
   either way: a unit that moved between groups gives no finding and
   unequal sums, and an indeterminate unit gives a finding and can have
   equal sums. What is tested instead: `Equal` exactly when every group is
   equal; then the full comparison has only `indeterminate` and
   `derived_indeterminate` findings, no one-sided key and nothing `used`.
3. **Indeterminate count at the sums**: §4.1 step 1 gives as many
   findings as `digest.indeterminate` (units), §4 step 1 one per key. A
   key with two indeterminate units is two findings at the sums and one
   through groups.
4. `pre`/`post` "exactly one unit": read as one occurrence counting
   multiplicity. A content-keyed unit in two files with one digest could
   instead report that digest.
5. A derived key indeterminate on one side only is not a finding (§4 step
   3 as written); it is counted.
