# WP-117 — negative inputs

What `slip_kiln::Lookups::missed`, the shard section `negatives`
(`spec/model.md` §8.6) and guard N1 (`spec/verify.md` §5.3) read into the
package where it left a choice, with the figures it asked for.

## 1. What a negative input is, form by form

A negative input is a place `(directory, name)` where a lookup looked for
`name` and found nothing: `Lookups::missed`, taken from Kiln's lookup log
(Kiln `kiln_pp::LookupLog`) and from Kiln's driver for what the log does
not name. Tests: `crates/slip_kiln/tests/lookups.rs` (`missed_*`, one per
row) and, end to end, `crates/slip_cli/tests/verify_job.rs` (`n1_*`).

| Form | Negatives | Covered | Test |
|---|---|---|---|
| `#include "…"` | the includer's directory (unless found there), then the search list from its start to the directory it was found in, that one excluded (all of it when not found) | yes | `missed_quoted_include_before_the_hit`, `missed_none_when_found_beside_the_includer`; `n1_quoted_include_beside_the_includer` |

## 2. The record

**Section 28, `negatives`** (`spec/model.md` §8, §8.6): 22 and 23 are left
unassigned, as §8 says, and 27 is WP-112's (`names`; the fix round moved
`negatives` from 27 to 28). Optional, phase `map`
only, and only in a shard with `inputs`. No change of the shard's
version, as for 17 and 24 to 26: an older reader refuses a map shard with
it (the ids are critical); a newer verify reading an older map shard
refuses it through N1 ("the map shard has no negative inputs"), and
`slip parse` makes it again.

**Writers.** The map task (`slip_cli::worker::map_observer`), and so
`slip parse`, is the only one: it always parses with the lookup log on
and writes the section whenever the shard has `inputs`. The verify task,
`slip declare`, `slip units`, and a parse task alone
(`slip_kiln::parse_observer`) write none.

**The path rule.** A place's path is `Command.directory/d/n` as written,
with `.` components and repeated `/` dropped; no symbolic link is
followed and `..` is kept (`spec/model.md` §8.6). Two hosts with the same
tree at the same paths therefore write the same bytes: the path is text
of the command and the source, and the tree only decides which places
are negatives. A directory that does not exist is written as any other;
a directory reached through a link is written as spelled, and N1 follows
the link as it is when the guard looks, as the post parse does.

The package asked for paths "as `inputs` writes them". `inputs` holds
real paths; a real path was tried first and given up (see "What I
disagree with" in the handback): with real paths, a link outside the
roots retargeted after the map phase moves the place the post parse
looks at away from the place recorded, and a wrong `verified` follows
(`n1_link_retargeted_since` is that case). The cost of the written path:
two spellings of one directory that differ by more than `.` and `/` are
two entries.

**Encoding.** Front-coded: each path is the bytes it shares with the
one before, as a count, then the rest. See "Costs" for the choice.

## Costs

**How.** `crates/slip_cli/tests/negatives_cost.rs`
`measure_negatives_on_a_unit` (ignored; not part of the gate) runs the
map task, `slip_cli::worker::map_observer`, on one unit given by
`SLIP_WP117_DIR` and `SLIP_WP117_ARGV` (the compilation database's
directory and arguments, `\x1f`-separated), with `SLIP_WP117_LOG=on`
(Kiln's lookup log and the section) or `off` (the map task as before
WP-117). One unit and one mode per `cargo test` process, so that the peak
is that run's: wall time of `map_observer`, the process's peak resident
memory (`VmHWM`), the shard's bytes, and the section's entries, distinct
directories and bytes (in the shard, and as each candidate encoding would
write the body). The test profile (debug), one thread, LLVM 19.1.7 from

The log costs nothing measurable: the wall times differ by −7 % to +5 %,
within the host's noise (the order of the runs alone moves them that
much), and the peak by under 2 % either way. The section adds 32 to 41 %
to a map shard (28 to 69 KB), about 6 to 8 negatives per input. A name is
tried in every directory before the one that has it (LLVM's units search
about 15 directories), so the paths share long prefixes: written whole
they would be 7 to 8 times the front-coded size; grouped by directory
(each directory once, then its names) 1.5 to 1.6 times. **Front-coding**
is chosen: smallest on every unit, one rule, and the order it needs is
the order the section has anyway (sorted, for N1's "first in path
order" and for determinism).

**The run over `llvm/lib/Support`** (store growth) is not measured here.
The one command, run once with this branch's `slip` and once with the
`slip` of the `main` it was made from, each into a store of its own:

```
time slip parse --db "$SLIP_CORPUS_DIR/llvm/build/compile_commands.json" --only /llvm/lib/Support/ --store <store> -j <n>
du -sb <store>/shards
```

Read: the two `du` totals (the growth is their difference; per observer,
divided by the number of shards, `find <store>/shards -name '*.shard' |
wc -l`), and the wall time of each run (`time` around the command). Expected from
the figures above: about 30 to 40 % more shard bytes. What it could change:
a much larger ratio of negatives to inputs on small units (where the
system headers dominate) would argue for sharing the toolchain's places
between shards (a table per plan) rather than another encoding; a
grouped encoding would win only if the paths shared their directories
but not their order, which sorting rules out.

## 3. Guard N1

`spec/verify.md` §5.3, the row after O2; `slip_cli::negatives::appeared`,
called by `verify_job::image_guards` after O2.

- **Where.** The tree form with an image other than the identity, at step
  2, after O2 and before `comparable`: it runs whatever the comparison
  then finds, at the sums or not (`f4b_outside_header_added_after_the_map`
  is refused with equal sums, `n1_checked_when_the_sums_differ` with
  different ones). The identity image is treated as O2 treats it: not
  checked, since every change since the map phase is then the edit
  compared (`n1_identity_image`). The overlay form is specified (every
  negative must still be absent) and not built: `Image::from_post` still
  refuses an overlay (WP-074).
- **A drift.** A negative, not under a subject root, at which a file now
  exists: `pre-image: <path> appeared since the map phase`, the first in
  path order (`n1_first_in_path_order`: `ext-b` is searched first,
  `ext-a` is named).
- **Under a subject root**: not checked. Decided from the real path of
  the file now at the place (links and `..` resolved, then
  `Resolver::under_subject`, its directory by identity, as G1), not from
  the place as written: `s/../wrap/cfg.h` is spelled through the subject
  root and names a file outside it. Judged by the written place, the
  resolver's nearest root is found by the spelling's ancestors and says
  "subject": the first build of N1 did that and verified
  `n1_quoted_include_beside_the_includer` wrongly; the test now pins it
  (and mutation M5b). A file whose real path cannot be read is taken as
  outside: refused. The tree form's post parse never looks
  there (L1), and a file there is the subject's, which G2 checks against
  the pre shard when the comparison reaches step 4. The ordinary case,
  a file the edit adds: `n1_subject_root_file_is_not_refused` (the map
  looked for `new.h` beside `a.cpp`, the file is now in both trees,
  verified). Under a post root, or under none: checked.
- **"Exists"** is Kiln's test (`SourceManager::load_regular_file`): the
  path, links followed now, names a regular file that opens. A dangling
  link is none (`n1_dangling_link_is_no_file`), a directory is none
  (`n1_directory_is_no_file`), a file that cannot be opened is none, and
  one that can is a file (`n1_unreadable_file`: mode 000 opens for root,
  so the test follows whichever this process is; the gate runs as root
  and so checks the "refused" half). A file Kiln opens and then fails to
  read to its end counts as one here: N1 refuses more, never less.
- **No section.** `pre-image: the map shard has no negative inputs (run
  `slip parse` again)` (`n1_pre_shard_without_negatives`).

## 3a. O2's second part (fix round F1)

`spec/verify.md` §5.3 O2 (ii); `verify_job::left_behind`, called in
`image_guards` right after O2's first part (`drifted`) and before N1.

- **The hole.** O2's first part compares only the files both parses
  read. A file outside the roots that the map parse read and the post
  parse did not was never checked: deleted after the map phase, the
  search ends at another header behind it, and an edit that compensates
  verified (review probes A and B). N1 cannot see it: the deleted file
  was found, so it is no negative (case A's negatives are `[]`).
- **The rule.** Every entry of the pre shard's `inputs` under no subject
  root (`Resolver::under_subject` on the recorded real path) whose path
  the post parse's `inputs` do not list must still be, links followed
  now, a regular file of the recorded size and content digest
  (`content_digest`, as `inputs` is written). "Read by the post parse"
  is the identity `drifted` uses: the bytes of the path (both lists hold
  real paths), by binary search, both lists sorted. The first failing
  entry in path order is named.
- **Messages.** `pre-image: <path> is gone since the map phase (run
  `slip parse` again)` (no regular file there) and `pre-image: <path>
  changed since the map phase (run `slip parse` again)` (another size,
  another digest, or unreadable).
- **Tests** (`crates/slip_cli/tests/verify_job.rs`, none ignored):

## 3b. The re-check round

The re-check of the fix round (R1 to R3, and the mutants it left alive)
and what each became.

    cannot fail. Given a unique identity, the directory duplicates
    nothing, and whatever Kiln dropped because of it at the map phase
    was itself, never its twin (clang `RemoveDuplicates` keeps one of
    the two, and the one kept is listed while it is not). No other entry
    changes.
  - M12 (the unplaced fallback taken always): conservative; nothing.
