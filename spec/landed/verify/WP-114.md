`crates/slip_cli/src/verify_job.rs` (item 1), `crates/slip_verify/src/run.rs`
(items 2 and 5), `crates/slip_cli/src/verify_cmd.rs` (the map shard's id,

`crates/slip_cli/tests/verify.rs` (`s9_2_*`),
`crates/slip_verify/tests/agreement.rs` (`s9_3_*`, `s9_4_m1_*`),

## 1. `binding` in every shard (`spec/verify.md` §9.1)

The verify job puts `Binding { overlay: None, declared: Params::declared_id,
pre: Params::pre }` on every shard it returns, whatever the rule table and
the outcome: `ok` (each verdict, every early end of steps 2 to 6 included,
since they all finish step 1's shard), `diagnosed`, `rejected`. The one
condition is the parse's status not `failed` (the parse task never returns
it; the model refuses a binding there). A job that fails returns `Err` and
writes nothing; the coordinator's `failed` shard has no binding, as before.
`rule_use` is WP-121's, unchanged: an `ok` shard under a rule table that is
not empty, from step 1's walk of the post-image, `rules` the table's
`rules_id`. `spellings` is never written.

**The empty container's id.** `slip verify` without `--declared` publishes
`Declared::none().to_bytes()` to the store (`verify_cmd::publish_declared`,
WP-053) and gives its content id to every job of the run in the one
`JobExtra.post` it plans with (`Job.post.declared`); the worker's
`make_params` reads and checks the container by that id and sets
`Params::declared_id` from it. The bytes are a function of the `DECL` format
alone, so the id is the same in every job of a run and in every run:
`1df101a21fe96c2dbac45dc569ef03a35b2a1eed5ba122510a0f7413b44c1d6e` at
`DECL` version 2 (pinned by `EMPTY_DECLARED` in `tests/verify_job.rs`; it
moves only with the format). The report's header has the same id
(`Header::declared`), so the agreement's comparison holds.

No field was added to `Params` or to the task's options: `declared_id` and
`pre` are WP-121's.

## 2. The exception goes (§9.3)

`Report::ours` requires a binding of every shard a worker wrote (status not
`failed`), whatever the image and the rules; a shard without one is
`failed`, "the shard has no binding". The spec's exception (§9.3, "A run
with a tree image and no rule is M1's: its shards need no `binding`") and
§9.1's parenthesis are removed in the same commit.

**Goldens.** The one golden of a verify shard,
`crates/slip_cli/tests/golden/verify-no-rules.txt` (WP-121's JSON view of
the shard of a job without rules, four outcomes), moved by exactly one
member per shard, `"binding": { "overlay": null, "declared": "1df101…",
"pre": 0 }`, the last section: removing those four members from the new
file (with the comma before each) gives the old file byte for byte
(checked with a script against the file as `main` has it). The shard's
bytes differ by section 24 alone. No report golden moved
(`crates/slip_verify/tests/golden/`, `crates/slip_cli/tests/golden/verify/`):
the report does not show the binding, and §9.4's "a run with a tree image
and no rule writes exactly the M1 document" holds
(`s9_4_m1_run_report_unchanged`, which now also shows that the same shards
without a binding are all `failed`).

## 4. A verdict is of the map shard the run reads (§9.3)

A `verified` or `mismatch` verdict names, as its `pre`, the content id of
the map shard the job compared against. `slip_verify::run` took the map
shard's status only, so a map shard replaced within a round left such a
verdict believed against other digests. Now the run is given the map shard
as `MapShard::Read { status, id }` (`state`, `Report::add`,
`Report::add_at`: the parameter `map: Option<Status>` of §7.3 becomes
`map: Option<MapShard>`; ruled, `docs/wp/WP-114.md`), or as
`MapShard::Unusable` for bytes at its address that are not a valid map
shard of the observer (they do not decode, or are of another observer,
phase or round): not `ok`, with its own reason (review F3a),
and §7's row "a `verified` or `mismatch` verdict whose map shard is absent
or not `ok`" is checked by id: a verdict whose `pre` is not the map shard's
id is `failed`, "the shard's verdict is verified: it was made against map
shard <16 hex>, not the run's <16 hex>". An `unverifiable` verdict is not
held to it: it is not believed as a comparison, though one ended after the
sums (R1, G2, R2) or after the full comparison (G3) did compare against
the map shard the job read (review F2). `slip verify` reads the status and
the id from one decode of the bytes (`verify_cmd::map_status`, through
`Shard::from_bytes_with_id`, added to every format's codec: review F5;
`this_runs_shard` uses it too). The spec says which check this is in §9.3 ("The
map shard a verdict compared against") and gives `MapShard` in §9.5.

Through the executable a map shard cannot be replaced between the job and
the report (the store is held exclusively); the case is the job's shard and
the report in process (`s9_3_map_shard_republished_between_job_and_report`).

## 5. The messages of the state table (§7.1)

A shard the state table refuses now carries the reason (WP-121 follow-up
(a)), in the order checked, after `ours` (which checks the phase first, so
a map shard in the verify slot, without a binding as map shards are, is
refused for its phase: review F3b):

| Cause | Message |
|---|---|
| not of phase `verify` | `the shard is of phase map, not verify` |
| `Shard::validate` refuses it | `the shard is not valid: <the model's error>` |
| `ok` without a verdict | `the shard is ok and has no verdict` |
| a counter of §7.2 by kind missing | `the shard has no counter <name>` |
| counters by kind that do not add up | `the shard's counters by kind add up to <n>, not its verdict's total <m>` (`<n>` is `at least 2^64` when the sum overflows) |
| `verify.findings` missing (review F8: the job writes it with every verdict; §7.2 now says so) | `the shard has no counter verify.findings` |
| `verify.findings` not the total | `the shard's counter verify.findings is <n>, not its verdict's total <m>` |
| more findings listed than counted | `the shard's verdict lists <n> findings of kind <kind>, its counter <c>` |
| `verified`/`mismatch`, no map shard | `the shard's verdict is <kind>: the observer has no map shard` |
| `verified`/`mismatch`, map shard there and unusable | `the shard's verdict is <kind>: its map shard is there and is not a valid map shard of the observer` |
| `verified`/`mismatch`, map shard not `ok` | `the shard's verdict is <kind>: its map shard is <status>` |
| `verified`/`mismatch`, another map shard | `the shard's verdict is <kind>: it was made against map shard <id>, not the run's <id>` |

Unchanged: a shard of status `failed` keeps its own message (the
coordinator's), and an observer without a shard has the empty one.

## 6. The `rule_use` of an `unverifiable` shard is checked, not folded (§9.3)

The question of item 5, ruled "check only" (`docs/wp/WP-114.md`, Ruling).
Before, `Report::read_sections` folded the `rule_use` of every `ok` shard
the state table accepted with a verdict, `unverifiable` ones included: a
stale pair of a post-image that may not be the run's (G3, or one a guard
refused) made the run `not verified` (status 1) where the observer's state
gives `incomplete` (4), and a use there hid an unused rule.

Now only the `rule_use` of a `verified` or `mismatch` shard is folded
(stale pairs, used rules, seen `kept` indices), as §10.6 does for
`spellings`. That of an `unverifiable` shard is still checked by `ours`
(present exactly when the run has rules, the run's `rules_id`, no rule
past the table, no `kept` index past `Declared.kept`); a shard that fails
is not this run's, `failed`. *Accepted cost* (§9.3): an observer
`unverifiable` only by its pre-image has real counts, and a stale pair
there is unreported until it verifies; the run is `incomplete` meanwhile.

Which guards are which (§5.3), for that cost (review F6):

- *The post-image parse is the run's; a check of the pre-image or of the
  pair failed*: P1 to P3 (the map shard), O2, N1 and N2 (the pre shard's
  record of files, negatives and lookups against what the post-image
  parse found: their reasons say `pre-image:`), C (the digests not
  comparable), R1, G2, R2 (the pre-image's parse at step 4). Their counts
  are real; their stale pairs are the ones not reported.
- *The post-image may not be the run's*: G1, G4, G5, G6 and O1 (a guard
  refused what the post-image parse read or was given), and G3 (the
  post-image changed during the job: the counts are of its first parse,
  and the job cannot say which image that was).

Folding the first group's and not the second's would need the verdict to
say which group it is in, other than in its reason's text. The ruling
stands as built: uses are not counted either, so a rule used only in
`unverifiable` shards is listed unused, with the line below.

A rule used only in `unverifiable` shards is listed unused, and so is a
`kept` key seen only there. So that the listing does not mislead, the
text has one line more, after the `unused rule` lines, when the run has
rules and some observer is `unverifiable` (§9.4):

```
agreement read <n> of <m> observers: rule use of <k> unverifiable not read
```

`n` the observers folded (`verified` and `mismatch`), `m` the selected,
`k` the `unverifiable`. The JSON document is unchanged: its `observers`
counts by state give the same three numbers. The name `slip.verify.v1`
stays (§9.4 adds lines that apply only when they apply).
