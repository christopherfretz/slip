# WP-155 — an instantiation emitted unreferenced, in one image only

`docs/wp/WP-155.md`. The mark "emitted unreferenced" (flag bit 1 of a
unit, `spec/digest.md` §11), the rule of `spec/verify.md` §4 step 3
that reads it, the findings `derived_only_pre` and `derived_only_post`,
and the answers to the four questions of the brief.

## 1. The mark

The walk (`crates/slip_digest/src/emitted.rs`, called by `walk.rs` after
an entity's resolved units are written) marks one unit of an entity
that the translation unit emits whether or not anything refers to it.
Kiln decides emission in its code generator, which Slip does not link
(`var_must_emit` in `kiln_codegen/src/global_init.rs`; `USED` and
`is_ctor_dtor_fn` in `kiln_codegen/src/module.rs`), so the walk decides
from the AST. Where the AST does not say, it marks.

**Which entities.** The representative declaration is a variable
(`DeclKind::Var` with `VarData`) or a function (`FunctionData`), and it
is:

- not local (`Walk::is_local`). A local entity is not marked itself;
  what it makes emitted is read on the function (or variable) around it.
  That is true of a static local: clang emits a `used` static local of an
  instantiation only where the instantiation is emitted (the second
  review ran it), so it marks nothing. It is not true of a local class's
  member function or a lambda's call operator with `constructor`,
  `destructor` or `used`: clang emits it, and runs it, whether or not
  anything refers to the function around it. So the function (or
  variable) whose body or initialiser declares one, at any depth, is
  marked (fix round, B1: `spec/digest.md` §11 "The mark" rule 2);
- not templated: no `DeclFlags::DEPENDENT_CTX`, no described template,
  and its `TemplLink` is not `Pattern` or `PartialSpecialization` (as
  `order.rs` reads "templated"). An instantiation, an explicit
  specialisation and an ordinary entity are read.

**Which unit.** The resolved unit `definition` (`digest-kinds.md`
§11.9) when the walk wrote one for the entity (`Property::Definition`,
no `default_argument`): an entity of the definition class whose
definition Kiln holds, which is every instantiated member and variable
template specialisation the rule is about. Otherwise, for an entity not
of the definition class, its own unit when the entity is defined
(`units::defining_decl`). An entity of the definition class with no
`definition` unit (declared, not defined here) is not marked.

**The facts, and the Kiln field read for each.**

| Bullet of the brief | Read | Kiln field |
|---|---|---|
| attribute `used` (variable or function) | on the representative or the defining declaration, through redeclarations and the pattern an instantiation was made from | `Ast::inherited_attr(d, AttrKind::USED)` (`AttrKind(67)`) |
| function `constructor` / `destructor` | the same | `inherited_attr(d, AttrKind::CONSTRUCTOR)` (190), `DESTRUCTOR` (191) |
| type with a non-trivial destructor | the defining declaration's type, canonical, through constant, incomplete, variable and dependent arrays and through lvalue and rvalue references (at most 256 steps), is a class (`TypeContext::as_record`) whose definition (`Ast::definition`) is missing or whose `RecordData::defn` lacks `DefinitionBits::TRIVIAL_DTOR` | `DeclNode::ty`, `TypeContext::canonical_view`, `RecordData::defn` |
| not constant-initialised | the evaluated state of the declaration that holds the initialiser (`decl_func::var_eval`, which the resolved unit `value` reads) is not `VarEvalState::Value`; except (fix round, B2) a variable with no initialiser whose type is not a class or is a class whose default constructor is trivial, or whose initialiser calls a trivial constructor with no argument (rule 1), or whose initialiser is plainly constant (rule 2, the grammar in `spec/digest.md` §11 "The mark") | `VarData::eval`, `VarData::init`, `DefinitionBits::TRIVIAL_DEFAULT_CTOR`/`NONTRIVIAL_DEFAULT_CTOR`, `Ast::is_trivial_default_construction`, the expression nodes |
| a function declared in the body, with `constructor`, `destructor` or `used` | every function declaration that is local, with the attribute (as above); its enclosing declarations through `DeclNode::ctx`, and a closure's `LambdaMangling::context` | `DeclArena::ids`, `DeclNode::ctx`, `RecordData::lambda`, `LambdaData::mangling` |
| static or thread storage | every variable that passes "Which entities" (non-local, so namespace scope or a static member); a thread-local is read as a static one | — |

**Where the rule and `var_must_emit` can disagree.** Each is a mark the
rule sets and Kiln's code generator would not (a finding too many), or
the reverse (a wrong `verified`); the second kind is none of these
unless stated.

- *Constant initialisation.* Kiln emits an initialiser when it is not
  folded (`folds`) **and** may have side effects; the walk marks when
  `eval` is not `Value`. Kiln writes `eval` when something evaluates
  the initialiser: always for a `constexpr` variable and a `const`
  integral one, otherwise only when a constant expression reads the
  variable. So a plain global `int x = 0;` is `NotEvaluated`. The first
  version marked it, and the instantiated `template <class T> int
  Z<T>::z = 0;`, a derived unit: a one-sided `Z<int>::z` was a finding
  where clang emits nothing, and the second review showed it refuses a
  migration's own requalification (B2). The fix round reads what needs
  no evaluation: such initialisers are plainly constant (rule 2;
  `tests/emitted/_/static-member-zero`, `plain-constant`), as is
  default initialisation by a trivial constructor (rule 1;
  `no-initialiser`). The same static member `const` and read by a
  `static_assert` is `Value` and not marked (`constant-not-marked`,
  `C<int>::w`); a trait's `static constexpr` member is not marked
  (`trait-constant`, the `zz153-q3` case). What stays marked though
  clang emits nothing: an initialiser outside the grammar that Kiln did
  not evaluate, such as `int x = y;` (a read; Kiln does not emit it, no
  side effect), `int a[2] = {1, 2};`, `int s = sizeof(int) + 0;`, and
  **a class initialised by a constexpr constructor**
  (`tests/emitted/_/constexpr-constructor`, `P Tr<T>::r{1};`): the
  known marks too many, the last one an `xfail` tree (E24 good-4 and
  good-8).
- *Thread-locals.* Marked under the same conditions as a static
  variable (rule 3 of the fix round): constant-initialised and trivially
  destructible, not marked (`plain-constant`, `thread_local int tl = 0;`
  and `Tr<int>::t`; `no-initialiser`, `thread_local K tk;`); a dynamic
  initialiser or a non-trivial destructor, marked
  (`tests/emitted/_/thread-local`). Clang emits such a variable and its
  initialisation wrapper only when it is odr-used, and runs the
  initialiser on first use in each thread: a mark too many, chosen (the
  brief).
- *`constinit`.* A `constinit` variable is constant-initialised by
  [dcl.constinit]; `REQUIRE_CONSTANT_INIT` (277) is not read: `eval` is
  what decides, and Kiln evaluates such a variable (it must, to
  diagnose). A `constinit` variable of a type with a non-trivial
  destructor is marked (`tests/emitted/_/constant-with-destructor`,
  `constinit D d;`), as `var_must_emit` emits it.
- *A constant-initialised variable with a non-trivial destructor.*
  Marked; Kiln emits it (`var_destructed_class`). Kiln does not count a
  variable whose destruction is constant (`const_destroyed`) or that
  has `no_destroy`; the walk does not read either: marks too many.
- *A reference.* Kiln skips the destructor test for a reference type;
  the walk looks through it (a lifetime-extended temporary of a class
  type with a destructor is destroyed at exit). Marks too many.
- *A variable template.* An instantiation is read as any variable
  (`tests/emitted/_/variable-template`: `vt<int>` with `g()` marked,
  `vc<int>` constant not).
- *An inline variable.* Read as any variable: a constant one is not
  marked (`tests/emitted/_/constant-not-marked`, `inline constexpr int k
  = 3;`). An inline variable with a dynamic initialiser is marked;
  clang emits it where it is odr-used, or, for a static member of a
  class template, where it is instantiated: a mark too many for an
  ordinary inline variable not used in this translation unit, on a
  declared unit (nothing to the rule).
- *Decompositions.* `var_must_emit` emits a decomposition whose holding
  variable must be; the walk reads the holding variable as any other
  (its initialiser is not `Value` unless constant) and the bindings are
  not variables of their own here. No difference found.
- *`asm` labels.* `ASM_LABEL` (88) changes the symbol's name, not
  whether it is emitted; the walk does not read it and neither does
  `var_must_emit`. A limit only for what a reader of the finding expects
  (the symbol name in the text is the C++ one).
- *`dllexport`.* Not read: an exported class's members are emitted
  whether referenced or not on Windows targets, which Kiln does not
  target today. A limit (`spec/verify.md` §8): a one-sided instantiated
  member of a `dllexport` class template is counted, not found.
- *A function that is not discardable.* Kiln emits every function with
  external linkage that is not inline; an instantiation is discardable
  (linkonce), so only `constructor`, `destructor` and `used` decide for
  what the rule reads. An explicit instantiation definition makes its
  members non-discardable; the walk does not mark them for that (each is
  a declared unit or a `definition` of an explicit specialisation,
  which is a declared change), so an explicit instantiation added or
  removed gives `changed`/`removed`/`added` on the declared units, not
  `derived_only_*`, unless a member is marked for one of the reasons
  above.

**Evaluation on demand (fix round, rule 4).** Slip cannot ask Kiln to
evaluate an initialiser at the pin without a change on its side. The
evaluator is the Oven (`kiln_oven::Oven::fold_constant_init`), which
needs `&mut Oven` and a `SemaBridge` over `&mut Ast` (the code
generator's `kiln_codegen/src/fold.rs` builds one, with `kiln_abi`
layouts); `slip_kiln::Unit` holds `&Ast` and `&Oven`, shared, for the
whole walk. A pre-pass in `slip_kiln` before the walk could own them
mutably, but folding interns values and lays out records in the AST the
walk then reads (`ConstValueId`s, layouts): every digest would have to be
shown unchanged by it, and the cost is a fold of every static-storage
initialiser Kiln left unevaluated in every observer. Not done; the
constexpr-constructor case stays marked and is an `xfail` tree.

**For Kiln.** No fact was missing to decide conservatively. One would
remove the marks too many above, and is what
`docs/requests/KR9-substitution-bindings.md` asks for as a predicate
("emitted whether or not referenced"): the evaluated state of every
variable of static storage that has an initialiser, or the code
generator's own answer (`folds` with `may_have_side_effects`). The
smallest source (the coordinator carries it):

```cpp
struct P { constexpr P(int v) : v(v) {} int v; };
template <class T> struct Tr { static P r; };
template <class T> P Tr<T>::r{1};
P *pp = &Tr<int>::r;   // in one image only: derived_only_pre, a finding too many
```

## 2. The rule

`spec/verify.md` §4 step 3, in `slip_verify::compare::compare_groups`:
after the indeterminate test (an indeterminate one-sided key is
`derived_indeterminate` only), after `derived_changed`, and after a key
step 4 took, a key with `R(k)` non-empty and `A(k)` empty (or the
reverse) is a finding `derived_only_pre` (`derived_only_post`) when the
image that has it has a marked unit of the key whose digest is in the
difference and whose group differs from the other image's (`G` of
§4.1). Otherwise it is counted as before. No exemption list is
consulted (`Exemptions::list_for` gives `None` for both kinds). The
finding's `pre`/`post`/`file` are those of any difference (§6).

The mark is part of no digest: not of a unit's (no stream changes) and
not of a group's (`group_digest` hashes a unit's flags without bit 1).
So a group's sum does not change with its marks, every digest of
scheme 2 is the digest of scheme 3, and the restriction to `G` is exact
because the rule is stated on `G` (`groups.rs`'s property test
generates marks, one in three derived keys, and toggles the mark of a
unit both images have).

`scheme` 3 still describes the fix round: it changes which units carry
the mark (fewer variables, more functions), not where the mark is or
what it means, and no baseline of scheme 3 has been recorded, so there
is nothing a new number would void (`spec/digest.md` §11).

## 3. The text

`slip verify`'s text prints, under a `derived_only_*` group's `first`
line:

```
  says `Reg<int>::r` is no longer instantiated in this translation unit (the translation unit emits it unreferenced: its initialiser or destructor runs, or it is a `constructor`, `destructor` or `used` function or variable)
```

(`is now instantiated` for `derived_only_post`), then the `pre` (or
`post`) line: the place of the pattern's definition (`locate` places a
`derived_only_pre` as a `removed`, a `derived_only_post` as an
`added`). The brief's sentence names the reason ("its initialiser ran
before `main`"); the mark is one bit, so the sentence names the
reasons together. A reason per finding would need the mark to carry it
(a second flag, or a reason in the names section): left for a package
that needs it.

## 4. The four questions

**Q1. The facts and the Kiln fields:** §1.

**Q2. Is the mark consistent across observers and across the two
images?** It is a function of the entity's declarations, its type and
its evaluated state, which an observer's parse fixes. Two observers
that instantiate the same entity read the same pattern and the same
arguments; `eval` can differ between them only if one evaluated the
initialiser and the other did not (Kiln evaluates static data members
and constant variables at instantiation; neither depends on the
observer's other code). Across the two images the same holds for a unit
both have; and a unit both have is never read by the rule (§2),
whatever its marks, so a mark that differed there would change nothing
(`tests/compare.rs` `s4_3_the_mark_is_read_on_the_difference_only`).
`tests/emitted.rs` checks, for every snippet, that a unit both sides
have is marked in both or in neither.

**Q3. A marked declared unit means nothing to the rule.** Steps 1, 2
and 4 read keys and digests only; step 3 reads the mark on derived
units only. Tested: `s4_3_emitted_with_indeterminate_exemptions_and_declared_units`
(a marked declared unit removed, changed and added gives the findings
and exemptions an unmarked one gives).

**Q4. The cost of the walk.** One call per written entity unit: a
kind test, `is_local`, `templated` (a few field reads), a scan of the
entity's resolved units (at most seven), and for a variable or
function that passes, up to six `inherited_attr` lookups (constant time
when the declaration has no attributes: `AttrList::has_kind`), one
type walk (one step for a non-array type), and `var_eval`, which walks
the redeclaration chain once. Fix round: the initialiser is read by the
grammar of rule 2, at most 64 nodes; and once per walk, at the first
entity read, one pass over every declaration of the AST keeps the local
functions with `constructor`, `destructor` or `used` (a kind test and
`is_local` for each function, three attribute lookups for a local one)
and climbs from each to the top: a set of the declarations around them,
empty in most translation units. No stream is written and no unit is
added. Not measured here: the suites' times on this shared host differ
by more between two runs of one tree than this walk can cost. The map
counter `digest.units.derived.emitted` (`spec/digest.md` §12) and the
supervisor's corpus run (`docs/wp/WP-155.md`, handback) give the number
of marked derived units and the map's time and memory on `llvm`
`lib/Support` against `main`.
