# WP-069 — the walk's half of rule use (`spec/verify.md` §9.1, §9.5)

## 1. What is built

- `slip_model::keys::RuleTable` gains `map_traced(key) -> (Key,
  Option<usize>)` (`map`, and the index of the rule that matched the
  key's own `(parent, kind, name, disc)`), `produces(&key) ->
  Option<usize>` (the first rule whose `(to_parent, kind, to_name,
  disc)` is the key) and `producers(&key)` (every such rule, ascending).
  `map` is `map_traced(key).0`. The table keeps the produced keys' bytes
  sorted beside the matches, so both lookups are binary searches.
- `slip_digest::Options` gains `rule_use: bool`; `Output` gains
  `rule_use: Vec<slip_model::agreement::Use>`, sorted by rule, only
  rules with `via` or `direct` not 0.
- `crates/slip_digest/src/rule_use.rs`: the counting. An entity's key is
  mapped in one place, `Walk::key` (`keys.rs`, the line that was
  `self.rules.map(key)`), which now calls `rule_use::map`. The walk's
  `rule_use` is `None` unless the option is on and the table is not
  empty; then `map` is `RuleTable::map` and nothing else runs.
- The rule index is the index in `RuleTable::rules`, which is
  `Declared.rules`' order (`spec/verify.md` §2: both sorted by the bytes
  of the match).
- `map::with_input` takes a closure and fixes no option; `digest_unit`
  and `map_unit` pass `Options` through. It gained no parameter
  (`tests/map.rs` `s9_5_map_unit_passes_rule_use_through`).

## 2. What is counted

An entity is a `Walk::entity` (a declaration's first declaration, the
template for its pattern). Its trace is kept by entity when its key is
mapped: `via(r)` if `map_traced` reports `r`, else `direct(r)` for each
`r` that `producers` reports for the mapped key. So:

- **Once per entity**, however many declarations it has, however many
  times its key is asked for (the key is memoised), and in however many
  files it is declared: `basic/renamed-function` (two declarations, two
  calls), `merge/namespace` (opened twice), `basic/namespace-in-two-files`
  (opened in a header and in the main file).
- **Declared or derived, with or without a unit**: an entity declared
  only by a block-scope `extern` declaration in a templated function has
  no unit and is counted (`refs/local-extern-only`, via 1); one declared
  only in a header and reached through a call (`refs/declared-in-header-only`).
  This is the first point of the review of WP-103 (the suite counted
  records).
- **`direct` is not counted for an entity a rule matched**, whatever key
  that rule gave it: `direct/swap` (f and g swapped, each via 1 direct
  0), `direct/two-rules-one-key` (the renamed `f2` mapped onto `h` is not
  direct for the other rule producing `h`). This is the second point of
  the review (the suite counted 2 for 1).
- A key computed again (one not memoised, below a depth limit or a
  cycle) replaces the entity's trace: the trace is that of its last key,
  which once memoised is its only one.

## 3. Decided where the spec was silent

1. **A member of an instantiation that follows its pattern's mapped
   name** (`follow_patterns`, WP-103) is not counted for the pattern
   member's rule. §9.1's `via` is "the entities whose own `(parent,
   kind, name, disc)` … matched `r`": the instantiated member's own key
   has the specialisation for parent, which no rule matches (a rule that
   does is `key/rule-on-instantiated-member`, below); its name is
   another entity's mapped name, the same case as a specialisation's.
   Nor is it `direct`: its parent is never a rule's `to_parent`. The
   pattern member is counted, and it is in every observer that has an
   instantiation of it. `templates/instantiated-member` (two
   instantiations: via 1, not 3), `templates/instantiated-member-left`
   (the pattern member left under its old name: direct 1, not 2).
2. **A specialisation whose name is mapped in `spec_key` through its
   template's rule** is not counted: its own key is matched by no rule
   (a rule of kind `specialisation` is refused, §2.1) and produced by
   none. The same holds for a decomposition, whose name is its first
   binding's mapped name: the binding is counted, the decomposition is
   not. `templates/function-template-and-specialisations` (one explicit,
   two implicit specialisations: via 1), `templates/decomposition-follows-binding`.
3. **Under a refused table** nothing is keyed (`compute_key` returns
   `key/refused-rule` for every entity), so no entity is counted and
   `Output::rule_use` is empty: every rule, the ones that would match
   included, has both counts 0. Every unit is indeterminate already, so
   the observer does not verify; a rule reported unused there changes
   no verdict (§9.2). `refused/specialisation-rule`.
4. **An entity whose key is indeterminate.** An entity with no key (no
   key formed: a cycle, a depth limit, `key/patterns-disagree`,
   `key/rule-on-instantiated-member`, a refused table) is counted for no
   rule: there is no key to match or to compare. Its unit, and every
   unit that refers to it, is indeterminate, so the observer is not
   verified either way. `indeterminate/rule-on-instantiated-member`
   (the rule on `S<int>::f` matches the member itself: no key, the rule
   has no `Use`). An entity whose key is formed and carries a cause is
   counted by that key: `indeterminate/key-with-cause` (a reflection in
   the signature, unsupported: via 1, the unit indeterminate).
5. **Two rules that produce one key.** §9.1 defines `direct(r)` for each
   rule: "the entities whose mapped key is the key `r` produces". The
   package's interface had one rule (`produces -> Option<usize>`); the
   spec wins: an entity no rule matched whose key two rules produce is
   counted in `direct` of both (`producers`). Two namespaces merged onto
   a third are the case that is not a collision.
   `direct/two-rules-one-key`, `direct/two-rules-one-key-second` (the
   entity of the second rule by table order is via that rule, not the
   first producer). `produces` is kept as the package names it.
6. **A rule of kind `namespace`** is counted as any other: the namespace
   it maps is `via`, the namespace whose own key it produces is `direct`
   (`merge/namespace`: via 1, direct 1); §9.2 makes such a `direct` no
   staleness. WP-111 changes what a namespace rule counts.

## 4. Nothing moves with `rule_use` off

- With the option off, or an empty table, `Walk::rule_use` is `None`:
  `rule_use::map` is one branch and `RuleTable::map`; no trace, no
  allocation. `RuleTable::map` is `map_traced(key).0` (the same lookup).
- Every pair test (`differ`, `equal`, `demand`, `indeterminate`,
  `resolved`), both sides, walked with `rule_use` on and off gives the
  same `Output` but for an empty `rule_use`
  (`tests/rule_use.rs` `pair_tests_on_and_off`); so does the post-image
  of every case of `tests/rules/` under its table (`tests/rules.rs`
  `post_side`), and of every case of `tests/rule_use/`.
- No golden, counter or existing expectation changed; `Output`'s
  `Debug` form has one more field, which only the determinism test reads
  (both its processes run this code).

## 5. The rules suite

`tests/rules.rs`'s `use` lines now read the walk's counts, and the
suite's own count (the `slip probe` table over records,
`spec/landed/digest/WP-103.md` "`expect.txt`") is removed. Its six `use`
lines hold under the walk's counts unchanged.

of `tests/rule_use.rs` and `tests/rules.rs` run, then restored.

| `direct` 2: only the first rule that produces the key (`produces` for `producers`) | `direct/two-rules-one-key`, `direct/two-rules-one-key-second` |
| `direct` counts an entity another rule maps onto the key (as well as its `via`) | `direct/two-rules-one-key`, `direct/two-rules-one-key-second` |
| An entity counted each time a key is mapped, at every site (`mapped_name` traced too, no map by entity) | `templates/function-template-and-specialisations`, `templates/instantiated-member`, `templates/instantiated-member-left` |
| Counted per unit written (the WP-103 suite's count: an entity with no unit not counted) | `refs/local-extern-only` |

No mutation survived. Two more are equivalent by construction and were
not run: comparing the unmapped key with `producers` (with no rule
matched, the mapped key is the key), and keying the trace by
declaration instead of entity (`Walk::key` computes once per entity, so
one declaration is ever traced; the per-site mutation above is the form
of that mistake that shows).
