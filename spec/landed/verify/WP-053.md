# WP-053 — the commands `slip verify`, `slip declare` and `slip units`

What `slip_cli::{args, commands, verify_cmd, declare::main, units}` read
into `spec/exec.md` §8.7 to §8.9 and `spec/verify.md` §7 and §7.1 where they
are silent.

## Arguments (§8, §8.6)

- `--post-image` is the one option without a value; `--post-image=<x>` is
  the usage error "`--post-image` takes no value".
- `--root` and `--post` pair by position. Unequal counts are the usage
  error "`--root` and `--post` come in pairs: <n> `--root` and <m>
  `--post` given". The image itself (a root that is no directory, a root
  under another, a root twice) is `Image::from_args`'s, an input error
  "`<command>: image: <reason>`".
- `declare` and `units` take `--store`, `--only`, `--limit` and the image;
  not `-j` or the pool's options (they run no pool).

## `slip verify` (§8.7)

- The order of the input errors is §8.7's steps: the declared file (read,
  then `Declared::from_bytes`), the image, the map run, the transform
  round. Each is checked before the phase runs; none writes a run record
  or a shard.
- The declared file's errors are "`<path as given>: <io error>`" and
  "`<path as given>: <DECL error>`", with no `verify:` (the form of the
  other file errors of §8.5). The image's, the map run's and the round's
  begin `verify:`.
- **A refused rule** (§2.1, `RuleTable::refused`, WP-103): a declared
  file whose table holds one is the input error "`<path as given>: rule
  <index>: <reason>`" (the form of the container's own rule errors), found
  when the file is decoded: before the image is made, before the file is
  published to the store and before any job is planned. Only the first
  refused rule is named.
- "No map run" names the store's root as the store resolves it
  (absolute).
- Without `--declared` the run's declared changes are `Declared::none()`,
  published like a file's, so every verify run has a `declared` id.
- **The map shard** is read for an observer whose verify shard is `ok`,
  `diagnosed` or `rejected` (§8.7 names the last two only): the state table
  of §7 gives `verified` and `mismatch` only with an `ok` map shard, and a
  map shard is only one that decodes and is of the observer, phase `map`,
  round 0. A `failed` verify shard, or none, needs no map shard.
- **This run's shard** (§7): the content id of the shard the store holds
  equals the `shard` of the observer's last `Job` entry in the run record
  (completion order); the entries' `outcome` is not read. Anything else is
  `Report::add_at` with `None` (`failed`).
- Observers are added with `add_at` at their position in the plan, so the
  report's order and `selected` are the plan's whatever the selection.
- **The `--report` file** is written before standard output: a file
  `.<name>.<pid>.tmp` beside it, renamed over the path. A failure to write
  or rename is an input error (status 3) naming the path as given, and the
  temporary file is removed. A run that ends by a signal writes none.
- Standard output: the report's text, then `wall`, `peak_rss`, `run` (the
  lines of `parse`), `report <path as given>` when `--report` is given, and
  the verdict line last. The paths of the lines `verify` adds are written
  as §7.1 writes strings (`\xNN` for bytes that are not UTF-8, controls,
  C1 controls and the backslash).
- The exit status is `Report::verdict`: verified 0, not verified 1,
  incomplete 4 (an empty selection is incomplete, after §8.2's warning).
- `verify --round <r>`: the pre shards are always round 0 of the map phase
  (`Post { pre: 0, .. }`); a round run again replaces its shards.

## `slip declare` (§8.8)

- `--from`, `--out` and the store are made absolute before any parse; the
  messages name `--from` and `--out` as given.
- The selection must keep from 1 to 64 observers, else the input error
  "`declare: the selection keeps <n> of the plan's <m> observer(s); declare
  parses every one in this process and needs from 1 to 64`", before any
  parse. `units` has the same bound and the same line with `units`.
- The text is read whole; a text that is not UTF-8 is the input error
  "`<from>: the text is not UTF-8 (<reason>)`".
- Parses: every pre-image with no rules; the post-images with no rules
  when a `relocate` names a parent (`needs().post`); the post-images under
  the file's rules when there is a `created` line (`needs().post_mapped`),
  skipping each observer whose post-image did not parse in the first pass
  (it was warned about once).
- An image whose parse is not `ok` gives no record and the warning
  "`slip: warning: declare: <main>: the <pre|post>-image is <status>`";
  the status does not change. A failure of the parse itself, or an `Err`
  of `slip_digest::records`, is an input error "`declare: <main>:
  <reason>`": no record is guessed and none is left out silently.
- Records of several observers are merged: one record given by several
  observers is one, in the order first seen.
- An error of §2.3 is one line, "`slip: <from as given>:<line>: <error>:
  <detail>`" (`<error>` from `ErrorKind::name`), status 1, nothing
  written. The first error in the order `read`, `resolve`, `finish` is
  the one printed.
- The file is written beside `--out` and renamed. Standard output:
  `declared <id>`, `rules <id> <count>`, `changed <n>`, `created <n>`,
  `removed <n>`.

## `slip units` (§8.9)

- The records of every selected observer's pre-image (with
  `--post-image`, its post-image; without an image, the subject as it
  is), with no rules, merged as `declare` merges them.
- `--match` (repeatable): a record whose name contains any of them, bytes
  compared. Sorted by `(name, KeyId)`; equal lines printed once.
- A line: the first 16 hexadecimal digits of the `KeyId`, the kind's name,
  `declared`, `derived` or `tu`, the flags (`-`, `i` indeterminate, `f`
  fallback key, `if` both), the name written as §7.1 writes strings.
- An image that does not parse: the warning of `declare` with `units:`;
  the status is 0.

## What the executable cannot reach

- A `Fallback` line error: no walk gives a fallback key today. It is
  `declare`'s unit tests' (WP-055).
- A stale shard (one in the store that is not this run's): the store is
  opened exclusively for the run, so only another process ignoring the
  lock could leave one. It is the unit test
  `s7_this_runs_shard_by_the_last_entry` of `verify_cmd`.
