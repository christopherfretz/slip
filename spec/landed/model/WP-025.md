# WP-025 — slip_kiln: the parse task on Kiln's front-end entry

`spec/model.md` §8.4 and `spec/cdb.md` §6.1–§6.2 were rewritten by this
package and say what the code does. This file records what they left open
and how the code decides it.

## Rules

- **Lazy buffers.** A buffer of origin `Lazy` comes only from a module file
  or a precompiled header (both out of scope of M1). It is an input when it
  has `original_bytes` (its file was read and held the recorded text), and
  left out otherwise. Kiln's `-MD`, which the old flow read, listed a lazy
  buffer by name when the preprocessor entered it outside a unit read from
  a module file (`DepCallbacks::file_changed`), and listed none of the
  files of a unit read from a module file; a module file itself is listed
  under `-fmodule-file-deps`. No test covers a lazy buffer.
- **A consulted file that cannot be read.** Kiln's header search reads an
  `#embed` resource or a `__has_embed` candidate whole when it looks it up
  (`HeaderSearch::lookup_embed`), so a directory or an unreadable file is
  never found: it is not consulted and not an input, and the parse is not
  `Err` (`s8_4_inputs_directory_embed_resource_is_not_found`). The `Err` of
  §8.4 ("failing that is `Err`") is reachable only when the file changes
  between Kiln's read and the parse task's (removed, or made unreadable);
  it is covered by the unit test `s8_4_inputs_unreadable_consulted_path_is_err`
  of `crates/slip_kiln/src/parse.rs` on the function that reads it.
- **Which consulted paths are read.** A consulted path is read when its
  real path is not that of a `Disk` or `Lazy` buffer that is an input; a
  `__has_include` hit is a buffer, so in practice only `#embed` resources
  and `__has_embed` hits are read.
- **`Unit::errors`** is the job engine's count when the closure is called,
  without the driver's errors (`FrontEndReport.errors` adds both); the
  closure has no way to emit through the `Unit`, so it does not change
  during the call.
- **The closure is not called** when computing the inputs failed (the
  parse is then `Err`).
- **A parse and a driver error.** Inputs and counters are present exactly
  when a parse happened, even if the first error is a driver diagnostic
  (status `rejected`). No fixture reaches that case: every driver error
  Kiln's entry reports stops it before the job.
- **`KilnCheck` and standard input.** Rejection 3 includes standard input
  as the one input (`-`, with `-x`), which the entry refuses as
  `NotOneInput`; without it the check would accept a command the parse
  rejects. The WP's list of rejection 3 did not name it.
- **`KilnCheck` and the PCH probe.** An `-include <h>` that Kiln's PCH
  probe turns into `-include-pch <h>.pch` (the file exists) is accepted by
  the check, which reads no file, and `rejected` by the parse
  (`drv_front_end_unsupported`).

## The parity test

`crates/slip_kiln/tests/parse.rs` `s8_4_parity_with_the_old_flow` runs every
fixture of WP-025 through `parse_observer` and through the parse task of
WP-010 (`crates/slip_kiln/tests/support/oracle.rs`: `run_as` with `-MD` and
JSON diagnostics). The shards are equal, field for field, except the
counter `pp.tokens` (the old flow had none) and these documented
differences:

- a `diagnosed` unit whose `#include` was not found: the old flow had no
  `inputs` and no counters (Kiln wrote no dependency rule), the new one has
  both;
- the first error's `message` under `-Werror` (or any error with an
  option): the new message ends in the ` [<option>]` suffix
  (` [-Werror,-Wunused-variable]`) that Kiln's text output prints and its
  JSON `message` field did not hold.

`s8_4_inputs_standard_library_headers` compares the two flows on a unit
that includes `<cstddef>` as well.
