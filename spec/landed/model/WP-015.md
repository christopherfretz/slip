# WP-015 — slip_model: the digests and verdict sections

Behaviour of `slip_model::formats` for shard sections 19 `digests`
(`spec/digest.md` §11) and 21 `verdict` (`spec/verify.md` §6) that those
specs and `spec/model.md` §8, §10 do not state exactly. It follows
`spec/landed/model/WP-006.md` wherever that file applies (order of checks,
`opt` tags, unlisted enumeration values, JSON reading); only what is new is
written here. Normative until folded into the specs.

Tests: `crates/slip_model/tests/sections.rs`, goldens
`crates/slip_model/tests/golden/shard-digests.json` and
`shard-verdict.json`.

## Interface

`Shard` has two more fields, `digests: Option<Digests>` and
`verdict: Option<Verdict>`; an absent section is `None`. Nothing else is
public: `Shard::{to_bytes, from_bytes, to_json, from_json, validate}`,
`dump`, `undump` and `content_id` cover both sections. Shard ids 16, 17, 18
and 20 stay reserved: a file with one is `UnknownSection`.

## Binary form

Each record is its fields in the order of the spec, in the encodings of
`spec/model.md` §2: `GroupClass`, `VerdictKind` and `FindingKind` are
enumerations (`uv`); `units`, `key`, `pre`, `post` and `where` are `opt`;
`used` is `list<digest>`. Section order is ascending id, so `digests` comes
after `counters` and before `verdict`.

## JSON form

Sections `"digests"` and `"verdict"`, after `"counters"`, not rendered when
absent. Members are named as the spec's fields (`Finding.location` is
`"where"`); enumerations by the spec's names; `opt` absent is `null`.

## Order of checks

After WP-006's steps 1–3 (container, unknown critical ids, each section's
fields in ascending id order, `digests` and `verdict` included), the
invariants are checked: WP-006's first, then those of `digests`, then those
of `verdict`. Within a section the rules are checked in the order of the
tables below. **Each rule is checked over the whole section, in field and
element order, before the next rule is checked**; the first violation is
reported. (Rule 6 of `digests` is four rules, a–d, each over every group
with a unit list in turn.)

## `digests` invariants

The section's payload starts at offset `P` (the `scheme` field).

| # | Rule | Offset | JSON path |
|---|---|---|---|
| 1 | present only if the outcome's status is `ok` | `P` | `sections.digests` |
| 2 | `scheme` = `digests::SCHEME` (1) | `P` | `sections.digests.scheme` |
| 3 | `groups` strictly ascending by `(class, file)` | the later group's first byte | `sections.digests.groups[i]` |
| 4 | a `tu` group's `file` is empty; a `declared` group's is not | the `file` field | `sections.digests.groups[i].file` |
| 5 | `count` ≥ 1 | the `count` field | `sections.digests.groups[i].count` |
| 6a | `units` strictly ascending by `(key, digest)` | the later unit's first byte | `sections.digests.groups[i].units[j]` |
| 6b | the length of `units` is `count` | the list's count (the byte after the `opt` tag) | `sections.digests.groups[i].units` |
| 6c | every `flags` is 0 or 1 | the `flags` field | `sections.digests.groups[i].units[j].flags` |
| 6d | `digest` = `group_digest(units)` | the group's `digest` field | `sections.digests.groups[i].digest` |
| 7 | `tu` = `tu_digest(groups)` | the `tu` field (`P` + 1 for scheme 1) | `sections.digests.tu` |

Rules 6a–6d apply only to a group whose `units` is present. A `derived`
group may have an empty or a non-empty `file` (builtins have the empty
path). Rule 6d and rule 7 are computed by every reader: stored digests that
do not match their content are rejected.

**Rule 6a uses `(key, digest)`, not `Unit`'s full order.** `spec/digest.md`
§11 says the list is "sorted by (key, digest)" and that two units of one
group with the same key and digest are one unit, while the brief said
"`Unit`'s order", which also orders by `flags`. The stricter reading is
implemented: two units with the same key and digest are rejected whatever
their flags.

## `verdict` invariants

The section's payload starts at offset `V` (the `kind` field).

| # | Rule | Offset | JSON path |
|---|---|---|---|
| 1 | present only if the phase is `verify`, then only if the status is `ok`, then only if `digests` is present (three messages, in that order) | `V` | `sections.verdict` |
| 2 | `reason`; each finding's `name`, then `where.pre.node`, `where.pre.what`, `where.post.node`, `where.post.what`: at most 4096 bytes | the field | `sections.verdict.reason`, `….findings[i].name`, `….findings[i].where.<pre\|post>.<node\|what>` |
| 3 | by `kind`, checking in field order: `verified`: `reason` empty, `total` 0, `findings` empty; `mismatch`: `reason` empty, `total` ≥ 1; `unverifiable`: `reason` non-empty, `total` 0, `findings` empty | the `reason` field, the `total` field, the `findings` list's count | `sections.verdict.reason`, `.total`, `.findings` |
| 4a | `findings` has at most `total` elements | the first finding beyond `total` | `sections.verdict.findings[total]` |
| 4b | for each finding in turn: ascending by `(kind, file, key)`, an absent key first (not strictly: findings with no key may tie); then, if it has a key, no earlier finding has the same `(kind, key)` | that finding's first byte | `sections.verdict.findings[i]` |
| 5 | for each finding in turn: `key` absent only for `indeterminate`; an `added` finding has no `pre`; a `removed` finding has no `post` | the `opt` tag of `key`, `pre`, `post` | `sections.verdict.findings[i].key`, `.pre`, `.post` |
| 6 | `used` strictly ascending | the later element | `sections.verdict.used[j]` |
| 7 | in each `Site` (pre, then post), `line` is 0 exactly when `column` is 0 | the `line` field | `sections.verdict.findings[i].where.<pre\|post>.line` |

`changed` and `derived_changed` have a key because only `indeterminate` may
lack one (rule 5); `derived_indeterminate` must have one too. `MESSAGE_MAX`
(4096) is the limit of rule 2, the same as `Outcome.message`'s, counted in
bytes of UTF-8.

## Not checked

The specs state these or imply them, but WP-015 does not check them (see
the handback's open questions):

- that a verify shard with status `ok` *has* a `verdict`, or that an `ok`
  shard *has* `digests` (`spec/verify.md` §6 "present when the outcome is
  ok"; `spec/digest.md` §10): today's writers (`slip_kiln`, `slip_exec`)
  produce neither section, and requiring them would reject their shards;
- `unverifiable` with `only_pre`, `only_post` or `used` non-zero, or with a
  non-zero `pre`; `verified` with `only_pre`/`only_post` non-zero;
- `findings` longer than the default limit of 64, or than 16 findings with
  a `where` (§6.1): the limit is a parameter of the job, not of the format;
- `pre`/`post` present on an unnamed `indeterminate` finding; a finding's
  `file` or `Site.file` empty or not absolute; a `where` on a finding whose
  kind cannot have one;
- that the counters `digest.units`, `digest.groups`, … agree with the
  section.
