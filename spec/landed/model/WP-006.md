# WP-006 — slip_model: binary and JSON forms of plan, shard, run record

Behaviour of `slip_model::formats` that `spec/model.md` §7–§10 do not state
exactly. Normative until folded into `spec/model.md`.

## Interface

For each of `Plan` (`PLAN`), `Shard` (`SHRD`) and `RunRecord` (`RUNR`):
`KIND`, `VERSION` (1), `to_bytes`, `from_bytes`, `to_json`, `from_json`,
`validate`, as in `docs/wp/WP-006.md`. In addition, in `slip_model::formats`:

- `undump(&json::Value) -> Result<Vec<u8>, JsonFormError>`: the inverse of
  `dump`, for any of the three kinds. It is the only JSON → binary path that
  keeps unknown ignorable sections (below).
- `encode_observer`, `decode_observer`, `encode_phase`, `decode_phase`: the
  §7 `Observer` record and the §8 `Phase` enumeration on their own, for the
  worker protocol (`spec/exec.md` §5.2). The plan and shard codecs call these
  same functions. `decode_observer` checks the rules an observer obeys on its
  own: every encoding, `id = ObserverId(command)`, `command.env` strictly
  ascending by name, `origins` non-empty and strictly ascending. The rules that
  need the plan (configuration index in range, uniqueness of ids and pairs,
  plan order) are checked only by the plan reader.
- `JsonFormError { path, message }`. `path` is empty for the top-level value;
  `Display` is `at <path>: <message>` or `at the top level: <message>`.

## Reading a file

`from_bytes`, `dump` and `content_id` all validate the whole file. The order
of checks is:

1. The container (§5 rule 5): `BadMagic`, `UnsupportedVersion`, `Truncated`,
   `Corrupt`, section framing.
2. `UnknownSection` for any critical section id the format does not define
   (for the shard this includes the reserved ids 16–20), before any section is
   interpreted.
3. Each defined section in ascending id order: absent and required is
   `Malformed` at the offset of the `end` byte (file length − 33); otherwise
   its fields, with `Malformed` at the first leftover byte (§5 rule 3).
4. The format's invariants (below), first violation in section and element
   order.

`dump` and `content_id` dispatch on bytes 8–11 of the file; a file whose kind
is none of the three is opened as a plan, which reports `BadMagic` (or
`Truncated` for a short prefix of a valid header). `content_id` returns the
trailer only once the file has been fully validated as by `from_bytes`.

An unlisted enumeration value (§1 rule 6) is `Malformed` at the value's first
byte. An `opt` tag other than 0 or 1 is `Malformed` at the tag.

A list's capacity is reserved up front only up to 1024 elements, whatever its
count says; the count itself is already bounded by the bytes remaining
(`Decoder::count`).

### Offsets of invariant violations

| Rule | Offset |
|---|---|
| configuration name not unique | the second configuration's first byte |
| observer not in plan order | that observer's first byte |
| `id ≠ ObserverId(command)`, id not unique | the observer's first byte (its id) |
| `command.env` not strictly ascending | the first `EnvVar` out of order |
| no origin | the `origins` count |
| origins not strictly ascending, configuration index out of range, pair seen before | that origin's first byte |
| excluded not strictly ascending, index out of range, pair seen before | that entry's first byte |
| message not empty for `ok`, longer than 4096 bytes | the `message` field's first byte |
| `failed` with an `inputs` section | the first byte of the `inputs` payload |
| inputs not strictly ascending by path | that `FileRef`'s first byte |
| counter name not `[a-z0-9_]+(\.[a-z0-9_]+)*` | that counter's first byte |
| counters not strictly ascending, `failed` with counters | that counter's first byte (the first, for `failed`) |

A (configuration, entry) pair is "seen before" if it occurs in an earlier
origin (observers in plan order, origins in order) or, for an exclusion, in
any origin or an earlier exclusion. Duplicates are reported at the later
occurrence.

## Unknown ignorable sections

The typed readers (`from_bytes`, `from_json`) skip them (§5 rule 2): the
value has nowhere to keep them, so `to_bytes` of that value writes the file
without them. `dump` renders them as `"#<id>": { "hex": "…" }` after the
known sections, and `undump` writes them back, so `dump` → `undump` reproduces
the bytes exactly (§10).

## Writing JSON

- An optional section that is absent (the shard's `inputs`) is not rendered;
  present and empty is `[]`.
- `"#<id>"` payloads are always in hex form, even when they are valid UTF-8.
- `kind` is the four-letter kind; `version` the number 1.

## Reading JSON

Only the rendering the writer produces is accepted, so a value has one JSON
form as it has one binary form (§1 rule 1):

- Every object has exactly the members of its record, in field order. An
  unknown member, a missing member and a member out of order (or repeated, in a
  hand-built `Value`) are errors at the member's path. `sections` has its
  members in ascending id order, required sections present.
- `"#<id>"` is accepted only for an id of 64 or above written in canonical
  decimal (no leading zero); any other key starting with `#` is an unknown
  member. Its value must be `{ "hex": "…" }`.
- `uv`: an integer number below 2^53, or a string of decimal digits without a
  leading zero whose value is at least 2^53 and fits 64 bits. A number at or
  above 2^53, a string below 2^53, a float (`1.0`) and a negative number are
  errors.
- `bytes`/`path`: a string, or `{ "hex": "…" }` (exactly that one member) with
  an even number of lower-case hexadecimal digits whose bytes are not valid
  UTF-8. Hex holding valid UTF-8 is an error at `….hex`.
- `digest`: exactly 64 lower-case hexadecimal digits.
- Enumerations: exactly the names of §7–§9.
- `kind` must be the reader's kind (`undump`: one of the three); `version`
  must be 1 (0 or above 1 is an error at `version`).
- Invariant violations are errors at the path of the table above
  (`sections.observers[2].origins[0]`, `sections.outcome.message`, …), with
  the same messages `validate` gives (`validate` returns `<path>: <message>`).

## Not checked

These look like invariants but the spec does not state them, so a reader
accepts them (see the handback's open questions): `ok` with `errors > 0`;
`diagnosed` with `errors = 0`; `attempt = 0`; a `shard` digest on a job that
did not complete; non-absolute `path`/`directory`; an `entry` beyond its
database; an observer's `main` not among a shard's `inputs`.
