# WP-105 — pitfall rows N25 to N38, and new trees in N11, N12, N14, N18, N23

What `crates/slip_verify/tests/pitfalls/n25-…` to `n38-…` and the new
trees of five existing rows are, how each was checked, and where the rows
read `spec/pitfalls.md` §2 differently from how the supervisor first wrote
it. The conventions of `spec/landed/pitfalls/WP-057.md` hold; what is new
is below.

## Conventions added

- **A declared file per subject.** `declared-<k>.txt`, when present,
  replaces `declared.txt` for the trees of `pre-<k>/`. Two rows need it:
  N12's second shape (one rule per moved entity, none for the C function)
  and N34's second subject (the same edit under rules that do not merge).
  `spec/pitfalls.md` §1 does not have this form yet; the runner (WP-056)
  needs it, or the two subjects move to rows of their own.
- **`good-<k>: none <reason>`** for a numbered subject that has no correct
  edit the row's declared file can express (N18 `pre-4/`, `pre-5/`), as
  `good: none` is for `pre/`. §1 names only the unnumbered form.
- **A dependency header included after owned code**, where the subject
  says why: N32's `dep/client.h` is a client of the owned library and so
  includes after it. Everywhere else `dep/dep.h` comes first.
- **A dependency nested namespace** (`legacy::io`, `legacy::util`,
  `legacy::lib`) where a row needs a type or a hook that is the
  dependency's and whose namespace is not `legacy`: N28, N29, N36.
- A `bad-<k>` on `pre/` while a `pre-2/` exists (N33 `bad-3`): §1's rule
  ("an edit of `pre-<k>/` if the row has it, else of `pre/`") places it.

## Where the rows differ from the table as first written

`spec/pitfalls.md` §2 lines N25 to N38 are amended to what is built.

- **N25.** The befriended function is a function template,
  `template <class T> friend int peek(const T &);`. A non-template
  dependency function cannot read a private member of an owned class: the
  dependency is included first and cannot name the class, so the
  `not_parsed` form needs a template whose body sees the class at
  instantiation. An unqualified friend template declaration follows the
  same rule as a function's ([dcl.meaning]: a prior declaration is looked
  for in the innermost enclosing namespace only, else it declares a new
  member of it). The silent form is a second subject that does not
  instantiate `legacy::peek` on `Mine`.
- **N28.** The stream type is the dependency's `legacy::io::out`, so that
  `legacy` is not associated through it: were it in `legacy`, the operator
  left in a `namespace legacy` block would still be found and the wrong
  edit would be correct. The generic operator is declared before `log`, so
  that it is found at the definition.
- **N29.** The fourth form is a nested namespace of the dependency
  (`legacy::lib::hash`) that the owned `namespace legacy` block reopens. A
  specialisation of a template of a namespace outside `legacy`
  (`::lib::hash`) cannot be written in the `legacy` block, and written
  outside it no edit of the block moves it.
- **N32.** The fallback is the global `::make(long)`, not
  `client::make(long)`: a using-directive's names are found as if declared
  in the nearest namespace enclosing both the directive and `legacy`, here
  the global namespace ([namespace.udir]/2), so a `client::make` would
  hide `legacy::make` in the subject as well and the subject would already
  call it. `dep/client.h` is included after the owned code it uses.
- **N34.** Under the merged rule, the expected finding is not one the
  spec gives (handback). A second subject, the same trees declared with
  one rule per moved entity (`declared-2.txt`), shows the finding the spec
  gives today.
- **N35.** The `not_parsed` form passes the moved class to the
  dependency's `use(Mine *)` (no conversion); "where the dependency needs
  the class complete" has no form in one translation unit whose
  dependency is included first, short of a template. The silent form is a
  second subject without that call.
- **N36.** The generic hooks are in `legacy::util`, associated through a
  base `legacy::util::Tag` that the subject gives `Mine`: the lookup is by
  argument-dependent lookup alone, so a generic in `legacy` would be found
  only if `legacy` were associated, and then the owned hooks left there
  would be found too.
- **N38.** There is no subject with conflicting types: two declarations of
  a function with C language linkage and one name are of one function
  whatever their namespaces ([dcl.link]), so with both visible the subject
  is already ill-formed (clang: rejected in `pre/` when `acme.h` declares
  `long c_fn(long)`), and the move makes neither visible. The row is
  `good` only, and its destination exists: one rule per moved entity,
  none for the C function.
- **N23** (a line not this package's to change): for a function
  template's default argument both `changed` the template and
  `derived_changed` its `default_argument` unit are found; the row names
  the second, as the table does. `spec/verify.md` §6.1 has no row for the
  name of a `default_argument` unit; the walk writes
  `legacy::take<int>(int)::<default_argument 0>`.

## Kiln

No disagreement of verdict. Diagnostic text only, each from a one-line
file at global scope (to the Kiln agent with the next batch):

- `template <> int id<int>(int) { return 1; }`: Kiln `extraneous
  'template<>' in declaration of variable 'id'` and `expected ';' after
  top level declarator`; clang `no function template matches function
  template specialization 'id'` (N29 bad-3). Kiln reads the declarator as
  a variable `id` followed by `<`.
- `template <> constexpr int width<int> = 4;`: Kiln `extraneous
  'template<>' in declaration of variable 'width'`, `constexpr variable
  'width' must be initialized by a constant expression`, `expected ';'`;
  clang `no variable template matches specialization` (N29 bad-2).
- `template <> struct hash<int> {};`: Kiln `explicit specialization of
  non-template struct 'hash'`; clang `explicit specialization of
  undeclared template struct 'hash'` (N29 bad-4; WP-057 reported the same
  for N07 and N19).
