# WP-105 — pitfall rows N25 to N38, and new trees in N11, N12, N14, N18, N20, N23

What `crates/slip_verify/tests/pitfalls/n25-…` to `n38-…` and the new
trees of six existing rows (N11, N12, N14, N18, N20, N23) are, how each was checked, and where the rows
read `spec/pitfalls.md` §2 differently from how the supervisor first wrote
it. The conventions of `spec/landed/pitfalls/WP-057.md` hold; what is new
is below.

## Conventions added

- **A declared file per subject.** `declared-<k>.txt`, when present,
  replaces `declared.txt` for every tree of `pre-<k>/`, good and bad
  (`spec/pitfalls.md` §1). Three rows use it: N12's second shape (one rule
  per moved entity, none for the C function), N34's second subject (the
  same edit under rules that do not merge), N18's `pre-6/` (a `changed`
  line added).
- **`good-<k>: none <reason>`** for a numbered subject that has no correct
  edit that can be declared without excusing its `bad` tree (N18 `pre-4/`,
  `pre-5/`). The obstacle is not the shared `declared.txt` (there is
  `declared-<k>.txt`) but that a declared file belongs to a subject and so
  applies to its `bad` tree too: the one correct edit declares
  `changed legacy::where()`, and with that line `bad-4` would verify.
  `pre-6/` is that copy: `pre-4/` again, `declared-6.txt` adding
  `changed legacy::where()`, and `good-6` (the text of `bad-4`) verifies,
  which tests that the `changed` line covers exactly the change of the
  consumed length.
- **Several `mismatch` lines for one tree**, all of which must be met (the
  supervisor's ruling, for `spec/pitfalls.md` §1): N20 `bad-2`, N23
  `bad-4`, N25 `bad-4`. Each line's comment in `expect.txt` names the
  blind verifier it defeats.
- **A dependency header included after owned code**, where the subject
  says why: N32's `dep/client.h` is a client of the owned library and so
  includes after it. Everywhere else `dep/dep.h` comes first.
- **A dependency nested namespace** (`legacy::io`, `legacy::util`,
  `legacy::lib`) where a row needs a type or a hook that is the
  dependency's and whose namespace is not `legacy`: N28, N29, N36.
- A `bad-<k>` on `pre/` while a `pre-2/` exists (N33 `bad-3`): §1's rule
  ("an edit of `pre-<k>/` if the row has it, else of `pre/`") places it.
- **A file of the destination outside `dep/`** (N38's `acme.h`): owned
  code, the same in every tree of its subject.

### For WP-056 (the runner)

- `declared-<k>.txt` replaces `declared.txt` for every tree of `pre-<k>/`,
  good and bad.
- A `declared-<k>.txt` without `pre-<k>/` is `ERROR`.
- `good-<k>: none` together with a `good-<k>/` directory is `ERROR`.
- A `pre-<k>/` with neither `good-<k>/` nor a `good-<k>: none` line is
  `ERROR`.
- Declared files stay per subject: a per-tree file would let a `bad` tree
  carry weaker rules than its `good`.
- A tree may have several `mismatch` lines; all must be met.

## Rows

Columns as in WP-057's landed file: the tree (and its subject); clang 19
(`clang++-19 -std=c++20 -fsyntax-only -I. -Idep main.cpp`); the shard of
`slip parse` on a one-entry compilation database of the tree; the line of
`expect.txt`; the digest fact that decides it; then, for each silent tree,
**which blind verifier would wrongly accept it** (or, for a `good` tree of
a row against false findings, which over-eager one would wrongly reject
it), and **how the change of meaning was proved** on a scratch copy
outside the repository. Every subject is accepted by clang and `ok` in
`slip parse`. Kiln and clang agree on every subject and tree.

## Where the rows differ from the table as first written

`spec/pitfalls.md` §2 lines N25 to N38 are amended to what is built.

- **N25.** (Further subjects, added in the fix round: the non-template
  friend of a function taking a dependency type, a collision; the access
  checked in SFINAE, silent with a change of behaviour; `friend struct
  Dep;`, `not_parsed`.) The befriended function of `pre/` is a function template,
  `template <class T> friend int peek(const T &);`. A non-template
  dependency function cannot read a private member of an owned class: the
  dependency is included first and cannot name the class, so the
  `not_parsed` form needs a template whose body sees the class at
  instantiation. An unqualified friend template declaration follows the
  same rule as a function's ([dcl.meaning]: a prior declaration is looked
  for in the innermost enclosing namespace only, else it declares a new
  member of it). The silent form is a second subject that does not
  instantiate `legacy::peek` on `Mine`.
- **N28.** The stream type is the dependency's `legacy::io::out`, so that
  `legacy` is not associated through it: were it in `legacy`, the operator
  left in a `namespace legacy` block would still be found and the wrong
  edit would be correct. The generic operator is declared before `log`, so
  that it is found at the definition.
- **N29.** The fourth form is a nested namespace of the dependency
  (`legacy::lib::hash`) that the owned `namespace legacy` block reopens. A
  specialisation of a template of a namespace outside `legacy`
  (`::lib::hash`) cannot be written in the `legacy` block, and written
  outside it no edit of the block moves it. The fix round adds a deduction
  guide and an explicit instantiation definition and declaration.
- **N32.** The fallback is the global `::make(long)`, not
  `client::make(long)`: a using-directive's names are found as if declared
  in the nearest namespace enclosing both the directive and `legacy`, here
  the global namespace ([namespace.udir]/2), so a `client::make` would
  hide `legacy::make` in the subject as well and the subject would already
  call it. `dep/client.h` is included after the owned code it uses.
- **N34.** Under the merged rule, the expected finding is not one the
  spec gives (handback). A second subject, the same trees declared with
  one rule per moved entity (`declared-2.txt`), shows the finding the spec
  gives today.
- **N35.** The `not_parsed` form passes the moved class to the
  dependency's `use(Mine *)` (no conversion); "where the dependency needs
  the class complete" has no form in one translation unit whose

  namespace b { struct M {}; w(M) -> w<M>; }`: Kiln `no template named

## Hazards

- **Dropped**: a moved namespace-scope `operator new` or `operator
  delete`. An allocation or deallocation function is a class member or
  declared in the global namespace ([basic.stc.dynamic.allocation],
  [basic.stc.dynamic.deallocation]); one in `legacy` is ill-formed, so
  there is nothing to move. A class-specific one moves with its class and
  is a member like any other.
- **To WP-109**: an owned namespace-scope `using namespace legacy;` that
  dependency headers included later rely on; and a header that two
  translation units include before and after the compatibility
  declarations, which needs the multi-unit format.
