# WP-109 — pitfall rows N39 to N42, R13 to R21, E18 to E22, and new subjects of fifteen rows

What the trees of `docs/wp/WP-109.md`'s 33 sketches are, how each was
checked, and what today's walk gives on them. The conventions of
`spec/landed/pitfalls/WP-057.md` and `WP-105.md` hold; what is new is
below. The table lines are in `spec/pitfalls.md` §2 to §4; the paragraph
on names in strings and other languages is in `spec/verify.md` §8.

## Conventions added

- **Rows that hold good trees only** (N42): rows against false findings.
  Each subject has a `good` tree and no `bad` one, and the table line
  says so.
- **A row with no declared file** where the edit renames no unit: R18 (a
  template parameter is written by position) and R21 (a local type is no
  unit, `spec/digest.md` §4.3). The Setting of §3 ("one `relocate`") does
  not apply to them, and their lines say so.
- **A declared file with more than the rule** in a rename row (R13: the
  using-shadow `removed`, the derived class `changed`), so that the `bad`
  tree is caught only by what it does wrong.
- **An empty declared file** (`e12-inserted-shadow/declared-2.txt`, a
  comment only) where the row's `declared.txt` would be wrong for the new
  subject.
- **Places that differ between the images.** A `changed` finding has both
  images' sites (`verify.md` §6.1, "Other findings"). Where the deciding
  entity would sit on different lines in the two images, the subject
  puts it on one line in both (E21's `size.h` and `y.h` define a macro
  under `#if` and use it on a line after); where it is in another file
  in each (E04 `bad-2`: the pattern is in `ptr.h` in one image, in `tr.h`
  in the other), the line has no place.

## Dropped

- **Sketch 6 (literal operators).** `spec/verify.md` §2.3's `<name>` is
  an identifier or `=`, so `operator""_km` cannot be the subject of a
  rename rule: there is no declared form for the edit to test.
- **Sketch 11 (a library builtin's name).** With C++ linkage, a global
  `strlen(const char *)` is not the builtin to clang (it is mangled
  `_Z6strlenPKc`, and calls go to it), so a rename to it verifies
  correctly and is only reserved-name undefined behaviour
  ([extern.names]); with C linkage, the rename cannot be declared (the
  rule's parent is the root, the key's is `c_linkage`).
- The other names of sketch 9 (`promise_type`, `await_ready`, a
  class-specific `operator new`, `std::hash` and `formatter`) need
  coroutines or the standard library: see "Hazards still uncovered".

`spec/pitfalls.md` §1 has one `main.cpp` per tree. A row with two
observers needs:

- **`observers.txt`** in the row: one line per observer, `<name> <main
  file>` (`a main_a.cpp`, `b main_b.cpp`), every tree parsed once per
  observer with the same include directories; absent, the row has the
  one observer `main.cpp`, so the existing rows are unchanged.
- **A line per observer or for the run.** `<tree>@<observer>: <line>` for
  an observer's own verdict, and the unprefixed line for the run's verdict
  after the agreement check of `verify.md` §9 (`mismatch stale <entity>`
  or the form §9 gives that finding).
- **`declared.txt` is one for the run**, as a user's is.

The two rows it would carry: a header included by both observers, one
before the compatibility declarations and one after (sketch 27), and the
stale observer under a namespace rule (`verify.md` §9.2), where an
observer that sees only the old declaration verifies alone and the run
must not.

## Spec questions

1. **Literal operators and `<name>`** (sketch 6): should §2.3 admit
   `operator""_id` as a `<name>`? Until it does, renaming a literal
   operator has no declared form.
2. **Renaming an `extern "C"` function** (sketch 11, and `verify.md` §8's
   new bullet): a rule's parent is a scope; the key's is `c_linkage`.
   Is `relocate f(int) => c_linkage :: g` the form, or is such a rename
   undeclarable?
3. **A using-shadow keeps its own name** (R13): a correct rename of one
   overload needs `removed Derived::<shadow Base::f(int)>` and `changed
   Derived`. Should the rule map the shadow of a renamed target instead?
4. **Places of a `changed` finding with two sites** (E21, E04): which
   site does ` @ file:line` match? The rows avoid the question.
5. **E19 has no `good` tree by design**: a redundant written `inline` is
   digested. Is that the intent of `0-inline` for `constexpr` functions,
   where `inline` is implied?

## Hazards still uncovered

- Sketch 9's other language lookups: `promise_type` and `await_ready`
  (coroutines are not represented), a class-specific `operator new` (a
  rename row with a row-local allocation is possible), `std::hash` and
  `formatter` specialisations (standard library).
- A partial specialisation selected differently in two translation units
  (the NDR case of sketch 31 with two observers): needs the format above.
- E21's two-path `#pragma once` (one header reached by two paths: a guard
  deduplicates it, `#pragma once` may not): needs a second include
  directory with a copy, which §1's `-I. -Idep` cannot express.
- The names in strings of `verify.md` §8 (asm labels, `alias`, `ifunc`,
  `weakref`, `#pragma weak`): no check exists.
