# WP-103 — mapped keys under rules (`tests/rules.rs`)

The test suite of the mapping of `spec/digest.md` §3.4 and
`spec/verify.md` §2.1: `crates/slip_digest/tests/rules.rs`, one
directory per case under `crates/slip_digest/tests/rules/`, and the
resolver `crates/slip_digest/tests/common/rules.rs`. It found two defects
in the mapping, both fixed here; one of them made two different programs
compare equal. Its review (fix round 2) found more, fixed here where the
mapping can fix them ("Fix round 2") and left to WP-113 where it cannot.

## The form of a case

```
tests/rules/<group>/<case>/a.cpp       the pre-image, digested with no rule
tests/rules/<group>/<case>/b.cpp       the post-image, digested under the table
tests/rules/<group>/<case>/rules.txt   the table (absent: no rule)
tests/rules/<group>/<case>/expect.txt  empty: equal; else the differences
```

### `rules.txt`

One line per rule; `#` starts a comment line; blank lines are skipped.
Two forms:

```
relocate [<kind>] <pre-entity> => <post-parent> :: <name|=>
rule <kind> | <parent> | <name> | <disc> | <to_parent> | <to_name>
```

- `relocate` is the line of `spec/verify.md` §2.3: the entity of the
  pre-image named by its display name (`spec/verify.md` §6.1), optionally
  with its kind in brackets where two entities share a name, is now
  called `<name>` (`=`: the same) under the post-image parent named after
  `=>` (empty: the global namespace). The resolver turns it into the rule
  that undoes it, `Rule { parent: m(P'), kind: K.kind, name: N', disc:
  K.disc, to_parent: K.parent, to_name: K.name }`, where `K` is the
  pre-image key and `m(P')` the mapped id of the post-image parent.
- `rule` is the `Rule` itself, for tables no declared change makes (wrong,
  chained, matching nothing). A parent is `root`, `c_linkage`, `builtin`,
  `pre <entity>`, `post <entity>` (the unit's id with no rule) or `mapped
  <entity>` (the post-image entity's id under the whole table). A name is
  `id <identifier>`, `name-of pre <entity>` or `name-of post <entity>`. A
  discriminator is `none`, `disc-of pre <entity>` or `disc-of post
  <entity>` (the post-image discriminator mapped under the whole table).
  An entity is `[<kind>] <display name>`.
- `# vacuous` on a line of its own: the case is equal with its table and
  also without it (see "Checks of every case").

A `relocate` line's new parent is mapped under the rules of the lines
above it, as `spec/verify.md` §2.3 says `slip declare` maps it: a line
whose new parent another line relocates comes after that line
(`parents/mapped-parent`, equal; `parents/mapped-parent-reversed`, the
same two lines in the other order, differs). A `rule` line's `mapped
<entity>` and `disc-of post <entity>` are under the table of the lines
above it too.

### `expect.txt`

The reader of the pair tests (`spec/digest.md` §14.1, `tests/common`),
with the lines it does not know handed to the suite:

- No line: the case is equal (`judge_equal`), and no unit is hard
  indeterminate.
- Otherwise the case differs exactly as the lines say: `changed`,
  `removed`, `added`, `indeterminate <name>` (a unit with a collision or
  another hard cause; compared by every display name the key has on
  either side), and the derived lines, judged loosely unless `exact
  derived` is given. A key with a hard-indeterminate unit is left out of
  `changed`, `added` and `removed`.
- `use <n> via <v> direct <d>`, the counters of `spec/verify.md` §9.1 for
  the rule on line `n` of `rules.txt`. The walk does not count yet
  (WP-069), so the suite measures them: the table is rebuilt with the
  rule's `to_name` replaced by `slip probe <n>`; `via` is the number of
  records of B with the probe's produced key, `direct` the number of
  records with the rule's produced key `(to_parent, kind, to_name, disc)`
  under the probe table (an entity the post-image still has under the
  name the rule gives). **These are not §9.1's counters**, and WP-069
  builds the real ones: they count records, not entities (one entity
  with units in two groups would count twice; §9.1 counts entities), and
  `direct` counts every record with the produced key, including one
  another rule produced (§9.1's `direct` counts the entities the walk
  reaches under the old name with no rule applied).
- `collisions <n>`: the post-image's counter `digest.collisions` is `n`
  (without the line, 0).
- `refused <text>`: the table cannot be made; the resolver's or
  `RuleTable::new`'s error contains `<text>`. Nothing else is checked.
- `# pending`: skipped and listed, as elsewhere.

### Checks of every case

- B digested twice under the table gives the same `Output` (item 11).
  Round 1 also digested B under the table of the reversed lines and
  compared the ids; that tested nothing, because `RuleTable::new` sorts
  its rules (the two tables are one value), and under §2.3 the order of
  the lines is not free. It is removed; the counter `digest.collisions`
  is now checked in every case (`collisions <n>`), which is a check of
  the walk;
- `records` of B under the table succeeds (its own check that each
  unit's key, computed again, has the unit's id);
- vacuity: an equal case with a non-empty table fails if B with no rule
  is already equal to A, unless `rules.txt` says `# vacuous`.

`SLIP_DIGEST_ONLY=<prefix>` narrows the run, `SLIP_DIGEST_DUMP=1` prints
both sides' units; `rules_txt_forms` tests the reader.

## Defects found and fixed

### 1. A collision among keys no unit has was not seen (item 9)

`units::mark_collisions` looks at written units only. An entity without
a unit is still written into references by its mapped key, so a table
that gives it another entity's key made a reference to one read as a
reference to the other, with no finding. Two different programs compared
equal:

- `wrong/named-only-specialisations`: the rule `rule specialisation |
  post W2 | id W2 | disc-of post W3<A> | post W1 | id W1` gave the only
  named `W2<A>` the key of `W1<A>`: `g(W2<A>*)` got the key and digest of
  `g(W1<A>*)`. Now `indeterminate <order>`.
- `wrong/merged-local-extern`: `relocate legacy => :: acme` while
  `legacy` still exists, a table `slip declare` makes. A block-scope
  `extern int hidden();` in a templated function in `acme` (no unit,
  digest §2.2) got the key of `legacy::hidden`. Now `indeterminate
  legacy::hidden()`.

Fix: `keys::mark_mapped_collisions`, called from `walk::run_with` after
`units::mark_collisions`. Under a non-empty table, the walk's key memo is
grouped by mapped id; in each group of two or more that is not all
namespaces, the entities are classed by their id under no rule (a
second, plain `Walk`); if there are two classes or more and one of them
has no unit with the key, every unit with the key is marked `Collision`,
or the order unit if none has it. The count of such keys joins
`collisions`. With no rule it does nothing. The call in `walk.rs` is
outside the files listed for the package: it is the one line that joins
the check to the walk's count of collisions.

### 2. A renamed template left its specialisations under the old name

A specialisation's key is (its template's key, the template's name,
its arguments). The parent was mapped, the name was not: under a rule
that renames a class, function or variable template, every
specialisation got a key A does not have (`kinds/class_template-renamed`
and the other `-renamed` template cases were false differences).

Fix: in `spec_key`, the name is the template's mapped name
(`Walk::mapped_name`: the rule table applied to the template's computed
key). With no rule the name is unchanged, so no key changes; this
changes how a key maps, not what a key is.

### F2. No rule matches a specialisation

`Rule::refusal` refuses a rule of kind `specialisation` or
`partial_specialisation` (`RULE_ON_SPECIALISATION`). The place, and why
there:

- **One definition**, `Rule::refusal` in `crates/slip_model/src/keys.rs`,
  computed once per table when it is made, by `RuleTable::new` (a
  resolver) and by `RuleTable::from_sorted` (the reader of the declared
  container), and kept as `RuleTable::refused`. No table from any source
  escapes it.
- **Not as an error of the encoding.** A first version refused in
  `Rule::validate`, so that `new` and the container reader returned an
  error. That broke WP-022's container tests
  (`crates/slip_model/tests/declared.rs`: its golden `declared.bin` holds
  a namespace rule from the unnamed namespace, and
  `every_key_kind_round_trips_in_a_container` a rule of every kind): a
  `Rule` of any kind is well formed, and the golden is not this
  package's to change. The refusal is of the use, not of the bytes.
- **Enforced where it is used.** The resolver refuses to make such a
  table (the suite's `table`, an error of the case); and the walk keys
  nothing under one: `compute_key` gives every entity `key/refused-rule`,
  so every unit is indeterminate and nothing verifies, however the table
  was made. Each `refused` case checks both.
- **Refused by `slip declare`** (round 3, finding 3):
  `slip_cli::declare::resolve` refuses a line whose rule `Rule::refusal`
  refuses, with the error `refused` (`spec/verify.md` §2.3), so that a
  `relocate` of a specialisation is a line error rather than a table
  under which every unit is indeterminate (`crates/slip_cli/tests/declare.rs`
  `refused_rules`, one line per refused kind).

A specialisation's key follows its template's (defect 2), so there is
nothing for such a rule to do that is not a wrong equal:
`wrong/named-only-spec-reparented-defined-templates` (the review's
case: `g(W2<A>*)` given the key of `g(W1<A>*)`, equal before),
`named-only-spec-reparented-relocate-form` (the same from a `relocate`
line), and `wrong/named-only-specialisations` (defect 1's case, now
refused before it is digested). `slip_model`'s unit test
`refused_rules` covers both constructors and the rules that stay allowed.

### Finding 2: a redeclared friend follows its pattern

A friend defined in a class template and declared again at namespace
scope has the namespace-scope declaration as its representative, which
no instantiation made, so round 2 left it under its plain name.
`instantiated_patterns` now asks every declaration of the entity's chain
for Kiln's link (`instantiated_from`), and collects the pattern entities,
each once; `follow_patterns` takes their mapped name.

- `instantiated/friend-redeclared-swap` (B34): two friends swapped, both
  redeclared; `changed u()` (the programs return 1 and 2; equal before).
- `friend-swap-one-redeclared` (B34c, only f redeclared): differs.
- `friend-redeclared-renamed` (B32c) and `friend-redeclared-after-use`
  (B32d, the namespace-scope declaration after the use): equal.
- `friend-redeclared-direct-rule` (B32b): a rule on `f(S<int>)` beside
  the pattern's gives `key/rule-on-instantiated-member`.

**Decided differently from the instruction's letter** ("follow when any
declaration carries the link"): a friend declaration in a pattern that
does not define the function is not followed. With it followed,
`kinds/function-first-declared-as-friend` (an ordinary function
`f(int)`, defined at namespace scope and befriended by `A`) had every
use indeterminate under `relocate f(int) => :: g`, the natural rule:
`f(int)`'s chain holds `A<int>`'s friend declaration, linked to
`A::friend f(int)`, so the direct rule counted as a rule on an
instantiated member. Such a function is not made by an instantiation:
its definition is its own, and the friend declarations name it. So a
pattern that is a friend declaration without a definition is skipped,
and the function keeps its own name and rule; the friend declaration in
`A` is its own entity, keyed in `A`, and takes its own rule
(`relocate A::friend f(int) => A :: g`; that case has both).

**Can two patterns disagree?** A chain leads to more than one pattern
only through friends (a member's declarations in and out of class lead to
one pattern member). Two patterns that both define the function cannot
both be instantiated: clang gives "redefinition of 'f'"
([basic.def.odr], [temp.inst]/3). With friend declarations without a
definition skipped, a valid program gives at most one pattern per chain.
`follow_patterns` still makes the key indeterminate
(`key/patterns-disagree`) if two mapped names differ: a backstop, which
no case reaches. `instantiated/friend-of-two-templates`: `f(int)` defined
by `S`, declared by `V`, only `S`'s rule: `f(int)` follows `S`, and `V`
differs only by its own friend declaration; `-both-rules`: equal.

The other things that can be redeclared outside their instantiation, a
case each, all equal under the pattern's rule:

- a member function and a static data member of a class template defined
  out of class: `member-function-defined-out-of-class`,
  `static-member-defined-out-of-class`;
- a member class and a member template declared in the class and defined

### Equivalent mutants

For every table the walk applies (one with no rule `Rule::refusal`
refuses: under any other the walk keys nothing), and every table `slip
declare` makes:

- **M5** (in `mark_mapped_collisions`, entities whose key cannot be
  formed under no rule join one class). Such an entity has a mapped key
  (it is in the memo as a `Key`) and no plain key. `compute_key` takes
  the same path under any table, except that `mapped_name` returns a
  name where the plain walk takes the plain one (never failing), and
  `follow_pattern` can fail under rules only; neither fails without
  rules where it succeeds with them. A depth or cycle abort is not
  memoised (`Walk::aborts`), and the plain walk asks for the entity from
  the top, the shortest path, so it aborts only if every path does. So
  no `None` class is ever made, and joining `None`s changes nothing.
- **M10** (the order unit's key not mapped). A rule that matches
  `(root, order, Name::Order, none)` has kind `order`; `slip declare`
  makes one only from `relocate <order> => P :: =`, whose rule is
  `Rule { parent: m(P'), name: Order, to_parent: root, to_name: Order }`:
  with `P'` the global namespace it maps the key to itself, and with any
  other parent it matches no key, since the order unit's parent is root.
  `map` of the order key is the identity under every such table.
- **M11** (a resolved or default argument part's key not mapped). A part
  key is `(kind, Parent::Unit(owner's mapped key), property or
  parameter index, disc)`: its parent is mapped already. A rule that
  matches it has kind `resolved` or `default_argument`, which
  `Rule::refusal` now refuses (`RULE_ON_PART`, `spec/verify.md` §2.1):
  under every table the walk applies, `map` of a part key is the
  identity. (Before the
  refusal, `relocate <part> => P :: =` could make one, saying a part
  belongs to another owner than its own, which no edit does: the
  refusal is the decision taken here, as for specialisations.)
- **Patterns that disagree** (round 3). `follow_patterns` sees two
  patterns only for a chain whose declarations are linked to different
  pattern entities. A member's declarations in and out of class link to
  one pattern member; only friends of different class templates give
  two. A friend declaration without a definition is not collected; two
  that define the function cannot both be instantiated (a redefinition,
  "Finding 2" above). So no valid program reaches the check, which is a
  backstop.
- **M17** (a fallback key not mapped). A fallback key is made only for a
  unit whose key cannot be formed, and that unit is always indeterminate
  (its cause is the key's, `units.rs`). An indeterminate unit is unequal
  to everything (`digest.md` §10), whichever key it is under, and the
  suite and the verdicts name it by its display name, not its key. So
  mapping it or not changes no verdict and no finding's name; only the
  id under which the indeterminate unit is listed.
