# WP-032 — declarations an instantiation adds outside its class

What `crates/slip_digest` reads into digest §2.2, digest-kinds §9.5 and
§11.9 for the rule of WP-032, where the specs are silent.

## The predicate

- **Instantiated outside its class** (`units::instantiated_outside_class`)
  is read from the declaration alone: its lexical context differs from its
  semantic context; the lexical context's own `SpecInfo` or
  `MemberSpecInfo` kind is `ImplicitInstantiation`, or it has none and
  `in_implicit_instantiation` holds for it (an explicit kind in between
  stops the search, as there); and `in_implicit_instantiation` does not
  hold for the declaration itself. A `Friend` declaration, an
  out-of-line member definition of an instantiation (lexical context the
  namespace) and a block-scope `extern` (lexical and semantic context the
  function) are not.
- **The chain read** (`Walk::redecls`) leaves such declarations out
  unless every declaration of the chain is one; a chain past the
  redeclaration limit is kept whole, so that the limit still shows.
  `Walk::chain` is the unfiltered chain.
- **The representative** (`Walk::representative`) of an entity is its
  earliest declaration that is not instantiated outside its class (nor
  in a templated body, below). Kiln's first declaration may be an
  instantiation's (a friend declared by `A<int>` and only then at
  namespace scope); the unit's class, its key, its declared group's file,
  the definition-class predicates, `FunctionData` and `VarData` (the
  specifiers and the language linkage), `DeclMisc` (the friend kind and
  `0-module-ownership`) and the key's language linkage are read from the
  representative. The entity `DeclId` itself stays Kiln's first
  declaration (`Walk::entity`), which references name.
- **The key is computed from the representative**, not from Kiln's
  first declaration. For a function the two give one key, but for a
  function template they do not: the friend template an instantiation
  declares has the instantiation's head (its parameters one level deeper,
  `type-parameter-1-0`) and a pattern whose type names them, so the
  written template `template <class U> void g(U);` had one key on the side
  where `A<int>` declared it first and another where it did not.
- **The chain of a template** (`Walk::chain`) is that of its pattern's
  declarations, mapped to the templates they describe (Kiln's
  `Ast::first` and `Ast::latest` go through `template_redecl`;
  `redecls_of` on a template alone gives the template). Without it a
  friend function template the instantiation declared first had no
  written declaration in its chain, and its unit went from declared to
  derived. `Ast::definition` of a template is the template asked about,
  so `defining_decl` asks through the representative.
- A specialisation's `DeclMisc` friend kind is its template's first
  declaration's: when the template is written, the specialisation is not
  `Undeclared` because the instantiation's friend template came first.
- **A definition** `Ast::definition` names that is instantiated outside
  its class is no definition of the unit, whether or not the entity has a
  written declaration; `read_decl` then falls back to the representative.
- **The friend class template form** (`template <class U> friend struct
  F;`) needs none of this: the instantiation's `Friend` names the
  pattern's declaration of `F`, whose lexical context is the class
  template's pattern, and declares nothing new, so no declaration of `F`
  is instantiated outside its class (`friend-class-template-declared-by-
  instantiation-written-later`). A friend function template is
  instantiated as a new `FunctionTemplate` per specialisation
  (`kiln_sema/src/templ/member.rs` `friend_function_template`). A
  variable template or an alias template cannot be a friend
  ([class.friend]/3, [temp.friend]/1).

## Declarations in a templated body (check 3)

- `units::in_templated_body`: a declaration that names an entity outside
  the function whose body holds it (a block-scope `extern`, or a
  declaration whose lexical and semantic contexts differ, a friend of a
  local class), where that function, or a context lexically around it
  before the namespace, is an implicit instantiation (by its own
  `SpecInfo` or `MemberSpecInfo`) or is templated (it describes a
  template, or is a partial specialisation); an explicit kind stops the
  search.
- Such a declaration is left out of `Walk::redecls` and of the
  representative, and an entity all of whose declarations are such is no
  unit (`unit_class`). Kiln records the pattern's declaration with no
  other (`Sema::note_local_extern`: not in a template), so it was an
  entity of its own whose key was the namespace entity's, and it
  collided with a namespace-scope declaration on both sides; an
  instantiation's is either a new entity with the same key (a collision
  on side B) or joins the namespace chain (which moved its unit when it
  came first). The references to it keep its key, which is the
  namespace entity's.

## Keys of friends (rule 3)

- A member-like friend: `TemplateTables` `member_like_friend` on the
  declaration, for a friend function template; for a non-template friend
  function with a requires-clause (Kiln makes it apart per specialisation,
  `kiln_sema/src/templ/subst/decls.rs:2187-2196`), the class
  specialisation that declares it, as Kiln's mangler reads it
  (`kiln_abi::mangle::constrained_friend_class`).
- **A friend in a templated class** (beyond WP-032's letter): a friend
  function or function template every declaration of which is lexically
  in a class template's pattern or a partial specialisation (Kiln's
  `Sema::in_templated_class`) and semantically elsewhere has its lexical
  class as parent. Kiln makes such a declaration an entity of its own that
  redeclares nothing (`kiln_sema/src/decl.rs:5465`), so under its
  namespace it had the key of the namespace-scope entity it befriends,
  and `void g(int); template <class T> struct A { friend void g(int) {} };`
  was a collision on both sides. A friend naming a member of another
  class joins that member's chain and is not concerned.
- A friend declared twice in one class template still collides with
  itself (Kiln does not join the two either); not seen in the corpus.
- A friend whose parent is the class that befriends it no longer has the
  key of a member of that class of the same name and signature: the
  discriminator ends with `uv` 1 for every such friend
  (digest-kinds §3.3, `function` row), and a function template inherits
  it from its pattern.

## Reading an entity declared only by instantiations (rule 3)

- `units::canonical_decl` picks the canonical candidate of digest §2.2:
  each declaration of the chain is keyed by the bytes of its lexical
  context's mapped key (`Walk::key_bytes`), once; only declarations tied
  on that key (one specialisation's) have their streams written, with
  the unit state put aside, and the least digest wins. The unit's
  stream, origin file and name are read from it once
  (`Written::read`), so the work is linear in the number of declaring
  specialisations (`units::tests::canonical_candidate_read_once`: 200
  and 2,000).
- A definition held by another candidate is no part of the unit, and
  `defining_decl` never returns an instantiation's: the candidates'
  streams then differ only where a definition would be read, and the
  definition is the class specialisation's (rule 4).

## `instantiated_from` (rule 1)

- Written absent on a declaration that is not instantiated outside its
  class when the entry names a declaration whose lexical context is a
  class and whose semantic context is not: only an instantiation's
  friend handling sets such an entry on a written declaration
  (`kiln_sema/src/templ/member.rs:316-329`). An instantiated member's
  entry names a member of the pattern, which is semantically in its class.

## What rule 4 leaves to the demand package

- The resolved unit `definition` of an entity that has a written
  declaration and a definition an instantiation added outside its class:
  its body (`FunctionData` `body`, and for a function template the
  pattern function's body) read from the declaration `Ast::definition`
  names (for a function template, the one it names for the template's
  pattern), which is the instantiated friend's: lexical context the class
  specialisation, `MemberSpecInfo` `instantiated_from` (non-template) or
  `TemplateTables` `instantiated_from` (template) the pattern's friend.
  `units::defining_decl` no longer returns it for the declared unit; the
  demand package must read it from `Ast::definition` directly.
- The `definition` of a derived entity declared only by instantiations
  (§11.9 item 4), read from its definition.

## Mutations accepted as unreachable

- `DeclMisc` `0-module-ownership` read from Kiln's first declaration
  instead of the representative (M09): the runner's snippets are not
  modules, so every declaration's ownership is the global module.
- The key's language linkage read from Kiln's first declaration (M12):
  Kiln rejects an `extern "C"` declaration after an instantiation's friend
  ("different language linkage"), so the two agree whenever the program
  is accepted.
