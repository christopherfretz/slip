5 inertness and `scheme`; 6 gaps; 7 the class, shape by shape; 8 test

## 1. First: "outcome equal, binding moved" can change behaviour

The package's Scope says: "No evaluated call changes while the outcome
is equal." That holds for the calls of the substituted expression,
which is unevaluated. It does not hold for the program. **What a name
binds decides what is instantiated, and an instantiation can emit code
that runs.**

```cpp
extern "C" int puts(const char *);
inline int note() { puts("registered"); return 1; }
template <class T> struct Reg { static int r; };
template <class T> int Reg<T>::r = note();
struct Base { static int s(); };
namespace n {
struct S : Base {
  template <class U = int> static auto s() { return (void)&Reg<U>::r, 1; }
};
}
template <class T, int = sizeof(T::s())> int call() { return 0; }
int main() { return call<n::S>(); }
```

`T::s()` binds `n::S::s<int>`. Its return type is deduced, so its body
is instantiated. The body odr-uses `Reg<int>::r`, so that variable's
definition is instantiated, and its initialiser runs at start-up. The
program prints `registered`. Rename the member template `n::S::s` to
`h`: `T::s()` binds `Base::s`, nothing is instantiated, the program
prints nothing. `sizeof` gives 4 both times and `main` returns 0 both
times. clang 19 and GCC 14 agree (run for this proposal, `-std=c++20`).
Kiln emits such a definition where its semantic analysis instantiated
it (`kiln/crates/kiln_codegen/src/module.rs` `instantiated_var_def`).

What Slip says of that rename today, by the specifications (not run
through Slip; it is the first pair of the first build stage, §8):

- every unit both images have is equal (WP-139 measured that for the
  example without `Reg`, `spec/landed/edits/WP-139.md` finding 3);
- the pre-image alone has the derived units `n::S::s<int>` and
  `Reg<int>::r`. A derived unit on one side only is no finding
  (`spec/verify.md` §4 step 3);
- the order unit lists no instantiated variable (`spec/digest.md` §2.1).

So the observer is `verified`, and the program changed. The reason
`spec/verify.md` gives for step 3 ("Why a derived unit on one side only
is not a difference": the demand "is written in the stream of the unit
that made it") is false for exactly this class: the unit that made the
demand is a substitution that is kept nowhere.

The same program with three other forms of the last two lines. Each
prints `registered` before the rename and nothing after it, with equal
exit codes, on both compilers:

```cpp
// (b) the substitution fails later, in the same substitution
template <class T, int = sizeof(T::s(), T::nope())> int call(int) { return 1; }
template <class T> int call(long) { return 0; }
int main() { return call<n::S>(0); }
```

```cpp
// (c) a partial specialisation's match fails after a name bound
template <class...> using void_t = void;
template <class T, class = void> struct has { static constexpr int v = 0; };
template <class T>
struct has<T, void_t<decltype(T::s()), typename T::nope>> { static constexpr int v = 1; };
int main() { return has<n::S>::v; }
```

```cpp
// (d) no template at the use: an operand that only a type holds
decltype(n::S::s()) v = 0;
int main() { return v; }
```

What follows from each:

| Case | Is | Closed by |
|---|---|---|
| the first program | a successful substitution, the package's class | this design: the default argument's unit differs (§4) |
| (b), (c) | **the counter-case to "successes only"**: a name bound, the substitution failed later, the binding reached the program | not by rows of successes. Open question 1 (a rule of the comparison) or failed keys (open question 2) |
| (d) | not a substitution. A transform that renames the member and leaves this use alone is `verified`: a `decltype` that is not dependent is sugar (`spec/digest.md` §1 rule 2; `crates/slip_digest/tests/equal/_/decltype-non-dependent`) | open question 5 |

Without a deduced return type or another forced instantiation, a moved
binding in an unevaluated operand changes no behaviour, and the
package's sentence stands. The statement Slip makes, "every name
resolves as it did", is false in all of these cases alike.

## 2. The design in one page

- **What is read**: Kiln's rows. `subst_keys` and `subst_rows` for the
  four kinds Kiln designed (`PartialMatch`, `Satisfaction`,
  `DefaultArg`, `Alias`); `specs()` for the substitutions Kiln keys by a
  declaration (a signature formed in deduction, a requires-expression
  in an instantiated body, an operand a type or a value holds in an
  instantiated declaration, a `noexcept` operand, a redeclaration's
  signature).
- **The unit**: one new **derived** unit per substitution. `KeyKind` 34
  `substitution`; its parent is the unit of the declaration Kiln's key
  names; its name is a new `Name` 16 `substitution(kind)`; its
  discriminator is the digest of the canonical arguments, written as a
  `specialisation`'s. It maps under a namespace rule and under a
  rename's declared changes exactly as a `specialisation` key does. No
  exemption applies to it.
- **An entry is named** by (the key of the declaration that owns the
  name, the entry's ordinal among that declaration's dependent
  entries). No position, no identifier, no dependence on which entries
  have rows.
- **A row writes** the entity as a reference; for a type name, the type
  it names; for an entry that stays dependent, that fact with the found
  set (sorted) and the argument-dependent-lookup bit. Rows are a sorted
  set.
- **Nothing existing moves.** Units are only added. With no rows there
  are none. `scheme` stays 2 if no baseline of scheme 2 is recorded
  when the first stage lands; else it becomes 3 (§5).
- **What cannot be read is never equal by silence**: an omission Kiln
  reports, an entry whose owner cannot be found, and a row left
  unresolved each make an indeterminate unit.
- **Asked of Kiln beyond its design** (KR9 §5): the owner of an entry;
  the part of a `specs()` row; selections that have no written name
  (operators first); four shapes that have no row at all; a count that
  decides open question 3.
- **Not closed by this design**: failures (§1 (b), (c)), selections
  with no written name until Kiln gives them, local declarations, a
  key only one image has. Each is a numbered open question or a stated
  limit.

## 3. Decisions

### 3.1 What is read: rows, not the substituted form

**Decided: rows.**

*Lost: the substituted form.* Kiln never truncates its arenas
(`kiln/crates/kiln_sema/src/templ/deduce_call.rs` `in_sfinae_held`
takes the expression arena's length only to flush member references),
so what a substitution built still exists. Kiln could keep its root per
key, and the digest's ordinary expression and type walk would read
every selection in it: names, operators, constructors, conversions. No
entry would need a name. It lost because: Kiln's design is rows and is
frozen for stages 0 and 1; the edit planning needs rows in any case;
the form carries the sugar of the arguments the first use happened to
write, which the digest would have to keep out; and a failed
substitution has no form to keep. Its strength, that it sees selections
no name was written for, is real, and is KR9 §5.3.

### 3.2 The unit: a derived unit per substitution

**Decided.** One unit per key of `subst_keys`, and one per
(`spec`, part) of `specs()` (§3.7).

*Lost: bytes in an existing unit* (the specialisation's `resolved`
unit for a default argument and a deduced signature; the using unit for
an alias template-id), as the facts list of `spec/digest-kinds.md` §4.4
is appended. Three reasons. An alias template-id and a satisfaction
have no unit of their own, and "the using unit" is whichever unit
wrote the use first: the row set would be in a unit chosen by order.
A specialisation's unit exists for more reasons than this substitution
(a default argument's substitution is made once per (template,
parameter, prior arguments) and serves many specialisations). And an
existing unit would gain bytes, which moves `scheme` and every recorded
digest of a translation unit that includes a standard header.

*Lost: one unit per row.* A row that only one image has would be a
one-sided derived unit and no finding. The set has to be compared as a
whole.

*Lost: one unit per template* (all its substitutions' rows together).
Its content would depend on which uses the translation unit makes, so
adding a use would be a difference (`spec/digest.md` §1 rule 5).

### 3.3 The key, and how it maps

```
key    := kind: 34 substitution
          parent: Unit(key of D)
          name:   16 substitution(k)
          disc
```

| `k` | Substitution | `D` | `disc` is the digest of |
|---|---|---|---|
| 1 | `PartialMatch` | the partial specialisation | the specialisation's arguments |
| 2 | `Satisfaction` | the concept, or the constrained declaration | the arguments shown; none for a declaration that is not a template |
| 3 | `DefaultArg` | the template | the parameter's index, then the prior arguments |
| 4 | `Alias` | the alias template | the arguments |
| 5 | `specs()`, declaration | the specialisation or instantiated member (`spec`) | nothing |
| 6 | `specs()`, definition | `spec` | nothing |
| 7 | `specs()`, exception specification | `spec` | nothing |
| 8 | `specs()`, a default argument or default member initialiser | `spec` | the parameter's index (0 for a field) |
| 9 | an omission Kiln reported (§6.1) | the root | the file's subject path, or the module's name |

Arguments are written as `spec_key` writes a specialisation's
(`crates/slip_digest/src/keys.rs`): canonical, each reference by its
mapped key. `D` always has a key unless it is local (§6.3): `keys.rs`
`key` gives one to every declaration at namespace or class scope, and
to a member of a class template specialisation under the
specialisation's key (`spec_key`). That is the check the supervisor
asked for on answer 9.

**Mapping.** The key holds a parent key id and arguments made of
references and type digests, and no name of its own. Under a namespace
rule both are mapped as they are for a `specialisation` key
(`spec/digest.md` §3.4). Under a rename's declared change the parent's
key maps and the unit follows, as a specialisation of a renamed
template does. The unit is derived, so `spec/verify.md` §4 step 3
applies: compared when both images have it, no exemption.

**Group.** The derived group of the file that holds the first
declaration of `D` (`spec/digest.md` §11), as for any derived unit.

**The unit's printed name** is `D`'s name, the arguments, and the kind:
`bindings in default argument 2 of call for <n::S>`,
`bindings in the match of swappable<T, void> for <a::X, void>`,
`bindings in alias R<n::S>`, `bindings in the satisfaction of HasS<n::S>`,
`bindings in the declaration of f<n::S>`.

*Lost: the using unit as parent.* See §3.2. *Lost: `PartialMatch` keyed
under the specialisation.* The specialisation exists whether or not the
partial specialisation matched, and several partial specialisations
match one specialisation; the partial specialisation is the pattern,
so it is the parent, and Kiln keys it so.

### 3.4 How a row names its entry

**Decided: (owner, ordinal).** The owner is the declaration at
namespace or class scope in whose declaration the name is written (a
template, a partial specialisation, an alias template, a concept, a
member). The ordinal is the entry's rank among the owner's entries
that have `DEPENDENT`, over the owner's declarations in the order of
its redeclaration chain, and in table order (parse order) within one
declaration. The row writes the owner as a reference and the ordinal as
`uv`.

Properties:

- A rename of the identifier, a move of the declaration, a qualifier
  added to a name that is not dependent, and a change of what any name
  binds leave every ordinal as it was. The two images join.
- The name does not depend on which entries have rows. An entry the
  substitution did not reach is absent under its own name.
- A row of an alias's name expanded under an enclosing key
  (`SUBST_EXPANDED`) is named by the alias template and its ordinal
  there. The flag is not needed for the name.
- An edit that adds or removes a dependent name in the owner renumbers
  the names after it, and every substitution unit with a row of that
  owner differs. That is a difference of the pattern itself, which the
  owner's own unit reports in the usual case. It is the right answer
  for the case that unit misses today: a condition added inside the
  arguments of a transparent alias (`void_t<decltype(…)>`,
  `spec/digest-kinds.md` "Hazards accepted for now").
- Reordering the redeclarations of an owner renumbers too: a false
  difference, accepted.

**The owner until Kiln gives it** (KR9 §5.1): from the entry's
`enclosing` declaration, outward through declaration contexts, the
first declaration that has a key. `enclosing` is exact for most
entries (`kiln/spec/ast.md` §18.3); for a name in a template head, an
alias declaration, or a declaration nested in a type-id it is the
lexical context, and the walk can end at a namespace or the
translation unit. A walk that ends there makes the unit
**indeterminate**, cause `Unaccounted("substitution/owner")`. It fails
closed; the counter of §6.4 says how often.

*Lost: the ordinal within the key's run of rows.* It loses the entries
that are absent. With

```cpp
namespace n {
struct S {
#ifndef B
  using a = int;
#endif
  using b = int;
};
}
template <class T> concept E = requires { typename T::a; } || requires { typename T::b; };
static_assert(E<n::S>);
```

the check binds `T::a` and never substitutes `T::b`. With `B`, `T::a`
names nothing, the first requirement fails, and the check binds
`T::b`, to the same type. Each side has one row, the first of its run,
with the same target. Named by (owner, ordinal) the rows have two
different ordinals of `E`, and the unit differs.

*Lost: the entry's profile* (what `own_spelling.rs` writes for a
dependent name). The identifier cannot be part of it, because a rename
changes it; without the identifier two entries of one pattern are
alike, and a swap of what they bind is equal.

*Lost: the position.* The digest holds none (`spec/digest.md` §1).

*Lost: the ordinal in the pattern's digest stream.* It needs a join
from a written-reference entry to the node the stream wrote, and a
canonical type has no node per use.

### 3.5 What a row writes

```
Row    := owner: ref, ordinal: uv, Target
Target := 1 entity:    ref
        | 2 type:      the digest of the type named
        | 3 dependent: adl: bool, found: list<ref>   sorted, duplicates removed
        | 4 builtin
```

- **A resolved entity that is not a type** (a function, a variable, a
  member, an enumerator, a template, a concept, a namespace): the
  reference. The callee is the fact (`spec/digest.md` §6). `how`,
  `found`, `udir` and the `adl` set are not written: they say how the
  entity was reached, and two lookups that reach one entity mean the
  same.
- **A resolved type name** (a class, an enumeration, a typedef, an
  alias): the digest of the type it names, not the typedef.
  *Lost: the reference to the typedef.* Kept code is already compared
  so: `n::S::t x;` against `Base::t x;` is equal when both name `int`
  (`spec/digest.md` §1 rule 2, `spec/digest-kinds.md` §4.2). A name in
  a substitution must not be held to a stricter standard than the same
  name written in kept code. Open question 10 asks the supervisor to
  confirm.
- **An entry that stays dependent** (a name in a generic lambda or a
  nested template of the pattern): the tag, whether argument-dependent
  lookup will run, and the declarations found now as a sorted set, the
  rule of the definition-context operator sets
  (`spec/digest-kinds.md`, `oper_lookups`).
- **A builtin candidate**: the tag.
- **A row with `REF_UNRESOLVED`** under a key of a translation unit
  that compiled: the unit is indeterminate,
  `Unaccounted("substitution/unresolved")`.

### 3.6 The unit's stream

```
stream := k: uv
          deduced: list<ArgView>     k = 1 only: the payload of the key
          rows: list<Row>            sorted by their bytes, duplicates removed
```

Sorting makes the stream independent of the order Kiln recorded rows
in, and of the number of pack elements that gave the same row. What it
loses is KR9 §5.6: two elements of a pack expansion that swap what
they bind.

A key of a kind the walk does not yet write (a later stage, or a kind
Kiln adds) is counted, `digest.substitution.unread.<kind>`, and writes
no unit.

### 3.7 `specs()` rows need a part

`specs()` keys a row by a `DeclId`. For a function specialisation that
gathers the rows of several substitutions made at different times: the
signature (in deduction,
`kiln/crates/kiln_sema/src/templ/funcs.rs`
`get_function_spec_signature`), the body, the exception specification,
each default argument. A unit holding all of them would differ between
two images that differ only in whether a use instantiated the body.
Demand may add units; it may not change one (`spec/digest.md` §1
rule 5).

**Decided**: one unit per (`spec`, part), `k` 5 to 8, and the part
comes from Kiln (KR9 §5.2). `enclosing` separates default arguments
today (a parameter claims its default argument) and does not separate
the signature from the body. **Until Kiln gives the part, the digest
reads nothing of `specs()`**, and the shapes of the supervisor's
answer 10 stay under the stated limit.

Many rows of a definition repeat what the digest already reads from
the kept body. They are written all the same: telling which names a
kept expression holds and which only a type or a value holds
(`decltype(T::s()) x;`, `int a[sizeof(T::s())]`,
`requires { T::s(); }`) would be a second walk. The price is two
findings for one moved name in a kept expression.

*Lost: put them in the `resolved` units that exist today* (`definition`,
the exception specification's). The parts match, and existing digests
would move.

### 3.8 A key that only one image has

The unit is derived, so a key on one side only is counted and not
reported. That is wanted when a transform changes what is asked for
(requalifying a call stops argument-dependent lookup from completing
associated classes; one more use instantiates one more alias). It
leaves this: a substitution made in both images that has a key in one
and none in the other, because it bound names in one and, in the
other, failed or reached none of its dependent names, with everything
it decides equal. This differs from what the supervisor told Kiln in
answer 1, so it is open question 3.

| Option | Effect |
|---|---|
| (i) Kiln makes a key for every substitution made whose pattern has a dependent entry, with its ending | exact: presence says "was asked for", the ending is in the stream. Costs keys; KR9 §5.5 asks how many |
| (ii) a one-sided substitution unit is a finding | false findings whenever a transform changes what is instantiated; a namespace migration does |
| (iii) a stated limit | nothing |

**Recommended**: (iii) now, (i) if Kiln's count is small. (ii) is
rejected.

### 3.9 Failed substitutions

**Kept: successes only** for rows, as Slip told Kiln. A failed
substitution decides nothing through its names: its candidate is not
viable, its pattern is not matched, and those outcomes are compared.
The supervisor's answer 3 already keeps what matters most: a default
argument's key is committed when it succeeds, also when a later one
fails.

The counter-cases are §1 (b) and (c). They reach the program through
what the bound name instantiated, not through the substitution. Rows
are the wrong tool for that: every other demand that no unit records
has the same effect (§1 (d)). **Recommended**: close it where it
shows, in the comparison (open question 1): a derived unit of a kind
that is emitted without being referenced, present in one image only,
is a finding.

### 3.10 Candidates that lost

- A function template candidate whose deduction succeeded has a
  specialisation, kept whether or not it wins
  (`get_function_spec_signature` creates it; only `USED` tells a
  winner). Slip already queues it as a derived unit
  (`crates/slip_digest/src/units.rs` `collect`). Its signature's rows
  are in `specs()`. **In the promise**, at no extra cost to Kiln.
- A partial specialisation that matched and lost partial ordering has a
  `PartialMatch` key (answer 2). **In the promise.** No `selected` mark
  is needed: the chosen pattern is in the specialisation's unit
  (`SpecInfo` `from`, `spec/digest-kinds.md` §9.4).
- A candidate whose deduction failed, and a conversion considered for
  a candidate that lost: **not in the promise.** They are failures
  (§3.9).

### 3.11 An alias-id with partly concrete arguments (Kiln's question 6)

```cpp
template <class X, class Y> using A2 = typename X::t (*)(typename Y::t);
```

used as `A2<n::S, T>` in a template that is never instantiated: `X::t`
binds `n::S::t` when the pattern is parsed. No key forms (the
arguments are dependent); `specs()` has a row under `A2`.

**Recommended: no partly dependent key, and the digest does not read
the row.**

- The binding happened while a pattern was parsed, with nothing
  instantiated. It is of the class "a name in a pattern", and is held
  to the standard of the same name written directly
  (`typename n::S::t (*)(typename T::t)`): seen through the pattern's
  canonical type, where the type `n::S::t` names is written. A move to
  a typedef of another type is a difference of the enclosing pattern
  today.
- Where the alias's result absorbs the binding
  (`void_t<decltype(X::s()), Y>` is `void`; an operand of which only
  the value is kept), the directly written form absorbs it just the
  same. That is case (d) of §1 and open question 5, not this one.
- Reading `specs()` as it is would give one set per alias template over
  the whole translation unit. Adding or removing a use changes the
  set: a false difference for every transform that does. And a binding
  that moves at one use can be hidden by the same binding at another.
- If the enclosing template is instantiated, the alias runs again with
  concrete arguments under an `Alias` key (Kiln's statement), and the
  binding is read there.

Default arguments and concept-ids with partly concrete arguments
follow the same rule.

## 4. Which unit differs, and what the report says

**The package's example.** `call<n::S>` takes the default argument of
parameter 2. Unit: (`substitution(3)`, parent `call`, parameter 1,
arguments `<n::S>`). Its row for `s` is (owner `call`, the ordinal of
`s` among `call`'s dependent entries) with target `n::S::s` before and
`Base::s` after. Under the rename's
declared change the first maps to `n::S::h`; it is still not `Base::s`.
Finding: `derived_changed`, unit
`bindings in default argument 2 of call for <n::S>`.

**A trait whose `swap` moved.**

```cpp
template <class T> void swap(T &, T &);
namespace legacy { struct X {}; void swap(X &, X &); }
template <class...> using void_t = void;
template <class T> T &ref();
template <class T, class = void> struct swappable { static const int v = 0; };
template <class T>
struct swappable<T, void_t<decltype(swap(ref<T>(), ref<T>()))>> { static const int v = 1; };
int u = swappable<legacy::X>::v;
```

A migration under `relocate legacy => :: acme` that moves `X` and
leaves `swap` behind:

```cpp
template <class T> void swap(T &, T &);
namespace acme { struct X {}; }
namespace legacy { void swap(acme::X &, acme::X &); }
template <class...> using void_t = void;
template <class T> T &ref();
template <class T, class = void> struct swappable { static const int v = 0; };
template <class T>
struct swappable<T, void_t<decltype(swap(ref<T>(), ref<T>()))>> { static const int v = 1; };
int u = swappable<acme::X>::v;
```

The trait says 1 both times: before through `legacy::swap(X &, X &)`
found by argument-dependent lookup, after through `::swap<acme::X>`
found by ordinary lookup. Unit: (`substitution(1)`, parent the partial
specialisation, arguments `<legacy::X, void>`), which the rule maps to
`<acme::X, void>` and so joins the post-image's. The row for `swap`
(owner the partial specialisation, the ordinal of `swap`): target
`legacy::swap`, mapped to `acme::swap`, before; `swap<acme::X>` after. Finding:
`derived_changed`, unit
`bindings in the match of swappable<T, void> for <acme::X, void>`.
The declared units report the function left behind as well; this
finding is the one that says a use was affected.

**An alias template whose argument's member moved.**

```cpp
struct Base { static int s(); };
namespace n { struct S : Base { static int s(); }; }
template <class T> using R = decltype(T::s());
R<n::S> v;
```

Unit: (`substitution(4)`, parent `R`, arguments `<n::S>`). The row for
`s` (owner `R`, the ordinal of `s`): `n::S::s` before, `Base::s` after. Finding:
`derived_changed`, unit `bindings in alias R<n::S>`. The unit is
`R<n::S>`'s, not `v`'s: every use of `R<n::S>` in the translation unit
is behind the one finding.

A finding names the unit. Which row differs is detail that the walk
can list for a unit when asked (the detail of `spec/digest.md` §11
gives the unit; printing its rows is the build's first stage, §10).

## 5. Inertness and `scheme`

- No existing unit's key, stream, digest or cause changes. The walk
  adds units, and only for keys and rows Kiln recorded.
- With the key table off, or with no such substitution, no unit is
  added: every digest is byte for byte what it is today.
- With rows, the derived groups of the files that hold the keyed
  declarations gain units, so those group digests and `tu` change.
  That is the form WP-140 took (`spec/digest.md` §11): units added, no
  stream, key or table row of an existing unit changed.
- **`scheme`**: the rule of `spec/digest.md` §11 gives the answer. The
  change closes a wrong equal. If no baseline of scheme 2 is recorded
  when the first build stage lands, it shares 2. If one is, `scheme`
  becomes 3, once, at that stage; the later stages each add units of a
  new kind and follow the same rule. No form of this design moves fewer
  digests: the alternative of §3.2 moves existing units.
- `crates/slip_digest/tests/written_on_off.rs` asserts today that the
  digest is the same with the written-reference table on and off. From
  the first stage that is true only of the declared groups and of the
  units that exist today. The test's statement changes in that stage.
- The switch is the walk's input. Verification makes both images with
  it on. Two digests are compared only when both were made with the
  same setting; whether the `Digests` header must say so is open
  question 14.

## 6. Gaps

### 6.1 Omissions Kiln reports

Kiln cannot list the keys it did not record. So the digest cannot mark
"the affected units": it writes a unit that stands for them.

| Kiln says | The digest writes |
|---|---|
| `Unrecorded::PrefixKeys { files }` | per file, one unit (`substitution(9)`, the file's subject path) in that file's derived group, indeterminate, `Unaccounted("substitution/prefix-keys")` |
| `Unrecorded::ModuleKeys { module, files }` | per file the same, `Unaccounted("substitution/module-keys")` |
| `Unrecorded::ModuleKeysLeftOut { module, keys, rows }` | one unit (`substitution(9)`, the module's name) in the derived group with the empty path, indeterminate, `Unaccounted("substitution/module-keys-left-out")` |
| `subst_keys_complete()` false and none of the three | one unit (`substitution(9)`, empty) indeterminate, `Unaccounted("substitution/incomplete")`: a defect of the facade, made loud |

An indeterminate derived unit is a finding on either side
(`spec/verify.md` §4 step 3), so an observer whose image has an
omission is never `verified`. It is blunt: a precompiled header made
without the switch makes every observer that uses it unverifiable.
Slip makes its own images with the switch on, so this is met only with
an image from elsewhere. Open question 15.

### 6.2 The table off

The walk has the option. Off, it writes no substitution unit and no
sentinel, and the digest is today's. It is for the readers of a digest
that are not verification.

### 6.3 Keys of a local declaration

A constrained generic lambda's call operator and a member of a local
class have no key (`crates/slip_digest/src/keys.rs` `is_local`). A
`Satisfaction` key or a `specs()` row set of such a declaration has no
parent to name. The walk writes no unit and counts it
(`digest.substitution.local`). It is part of the stated limit. The
design that removes it (the unit under the enclosing function's key,
named by the local entity's ordinal, `spec/digest.md` §4.3) is a later
stage and open question 12.

| `digest.substitution.rows` | rows read |

## 9. Mutations

Each must fail a named test:

- a row's target not written; the owner not written; the ordinal not
  written (the pairs of §8; `subst-two-entries` and
  `subst-disjunction` for the ordinal);
- rows not sorted (`subst-<shape>-order`);
- the ordinal counted over all entries, not the dependent ones
  (`subst-relocate-nothing-moves`: a qualifier of another length would
  not show; a pair that adds a non-dependent name before the dependent
  one is added for it);
- the arguments left out of the discriminator (two uses with
  different arguments collide; a pair with `R<n::S>` and `R<n::S2>`);
- the parameter index left out of a `DefaultArg` key;
- a typedef written by reference, not by type (an `equal` pair:
  `Base::t` and `n::S::t` both `int`);
- a sentinel of §6.1 not written, or written without the flag (a
  facade test with a synthetic `Unrecorded`);
- an unresolved row treated as absent;
- a unit added to a declared group; an existing unit's digest touched
  (the inert test: the whole `equal` and `differ` suite with the table
  off gives today's digests, and with it on the same declared groups).

## 13. Open questions

1. **A derived unit that is emitted, on one side only.** §1 shows a
   `verified` transform that removes a variable's dynamic
   initialisation. Should `spec/verify.md` §4 step 3 make a finding of
   a one-sided derived unit whose kind is emitted without a reference
   from other emitted code (the definition of an instantiated variable
   with static or thread storage duration; perhaps of one whose
   initialiser or destructor is not constant only)? **Recommended:
   yes**, with the counter of §12 first, to measure false findings on
   the corpus. It also corrects the paragraph "Why a derived unit on
   one side only is not a difference", whose premise fails here. This
   is outside this package's interface.
2. **Failed substitutions.** The counter-case exists (§1 (b), (c)).
   **Recommended**: rows stay successes only; question 1 closes the
   behaviour; the binding itself in a failed substitution is a stated
   limit.
3. **A key only one image has** (§3.8). The supervisor told Kiln
   (answer 1) that a key appearing or disappearing is a difference. In
   the comparison as specified it is not, and making it one gives
   false findings. **Recommended**: ask Kiln for the count (KR9 §5.5);
   a stated limit until then; a key for every substitution made if the
   count is small.
4. **Selections with no written name** (KR9 §5.3). Is "which
   `operator<<` a trait found" in the promise? **Recommended: yes for
   operators**; it is the lookup a namespace migration moves. Until
   Kiln gives it, it is in the stated limit by name.
5. **An operand that is not dependent and that only a type or a value
   holds** (§1 (d)): `decltype(n::S::s()) v;`,
   `int a[sizeof(n::S::s())];`. Today not digested, by rule 2. In the
   statement "every name resolves as it did", or not? Closing it writes
   a binding for the operand's names in the using unit (an entry of the
   facts list of `spec/digest-kinds.md` §4.4), flips
   `equal/_/decltype-non-dependent` only where a name moved, moves
   existing digests, and so moves `scheme`. **Recommended**: decide
   with question 1; if question 1 is ruled yes, state this as a limit
   of names and not of behaviour.
6. **Kiln's question 6** (§3.11). **Recommended**: no partly dependent
   key; the digest does not read `specs()` for it; the binding is held
   to the standard of a name written in the pattern. The supervisor's
   provisional answer 6 is **confirmed**, with the absorbed-result
   cases sent to question 5. Due before Kiln's stage 4.
7. **Provisional answer 2** (no `selected` mark on `PartialMatch`):
   **confirmed** (§3.10).
8. **Provisional answer 5**, changed at the freeze to `SUBST_EXPANDED`:
   **accepted; the design does not use the flag.** It needs the owner
   of an entry (KR9 §5.1). Until then a row whose owner cannot be found
   makes its unit indeterminate. Is that acceptable for stage d, or
   does stage d wait for §5.1?
9. **Provisional answer 6**: see question 6.
10. **A type name by the type it names**, not by the typedef (§3.5).
    **Recommended** as written; the other choice makes substitutions
    stricter than kept code.
11. **The part of a `specs()` row** (§3.7, KR9 §5.2). Without it stage
    e does not start. Is a rule ("rows whose entry lies in the body's
    extent are the definition's") acceptable if Kiln prefers no new
    field? **Recommended: no**; it reads positions and breaks for an
    out-of-line definition.
12. **Local declarations** (§6.3): counted and left out until designed.
13. **The element of a pack expansion** (KR9 §5.6): a stated limit.
14. **`scheme`** (§5): shares 2 or becomes 3, by whether a baseline is
    recorded; and whether the `Digests` header must record that the

15. **The sentinel of §6.1** makes every observer of a foreign
