# WP-145 — a default's consumed name found by its field; the depth limit not memoised

Two defects of `spec/digest.md` §9 found by the review of WP-112's
second round (pairs `crates/slip_digest/tests/{differ,equal}/_/rev112b-*`).

## 1. The function name of an `__impl` object is found by its field

Kiln makes one source-location string object per content, so where a
`#line` names the file exactly as the function's pretty name, the
`__impl` object's `_M_file_name` and `_M_function_name` point to one
object. The digest told the two apart by comparing objects ("the first
pointer whose object is not the file's"), found none, and wrote a use
of a default that consumes `function_name()` as if the object had no
name: `differ/_/rev112b-c38-line-file-collides-pretty` was equal.

The rule now: in an `__impl` object, the function name is the pointer
at the offset of the field `_M_function_name`, and the file name the
pointer at `_M_file_name`, each field found by its member of the
record's definition and its offset by Kiln's layout of the record
(`value.rs` `impl_field_offset`). Two strings are never told apart by
their objects. A string object pointed to by both fields has both
roles, so its uses are of two kinds and its bytes are written (§9, "one
kind and one entity"); a pointer at no known field counts as the file's.
Where a use built an `__impl` object and its function name is not found
so, the unit holding it is indeterminate,
`Unaccounted("value/source-location.function-name")` (at a pointer to
the object, at a `__builtin_source_location()` node, and at a use of a
default that reaches one), never written as nameless.

The other strings: a `SourceLocValues`' `file`, `file_name` and
`function` are told apart by the field Kiln records each in, and a
`PredefinedExpr`'s string by the `PredefinedExpr` that names its
literal; neither compares objects.

## 2. The nesting limit of defaults gives one verdict wherever the walk began

A default whose answer met the nesting limit memoised that error into
every default on the stack, so whether a default was indeterminate
depended on the order of first use. Now:

- the memo of a default holds its nesting (the defaults on its deepest
  chain of nested defaults, itself counted) with its answer; a
  memoised answer met with `n` defaults already on the stack is past the
  limit where `n` plus its nesting passes it;
- a depth error is memoised only at the root that met it (the default
  the walk began from, whose own nesting passes the limit), never below;
- the nesting check reads the same `limit` as the bound on a default's
  own nodes (65,536; a unit test lowers it).

So a default whose nesting passes the limit is indeterminate,
`Unsupported("default/reach-limit")`, from every starting point, and one
whose nesting does not is determinate from every starting point.
