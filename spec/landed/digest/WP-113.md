# WP-113 — what an entity takes from its enclosing namespaces besides its name

What `crates/slip_digest` does so that a rule can move an entity's name
and nothing else: the row `enclosing` (`spec/digest-kinds.md` §1.7, tag
1538). Kiln references are at the pinned Kiln (`kiln/`, `913a490bb`).
Symbol evidence is `clang++-19 -std=c++20 -c` on the host (AArch64 ELF),
read with `llvm-nm-19` and `readelf -sW`.

## Item 2: the row

```
tag 1538, enum Linkage, bool in_unnamed,
opt<uv> vis, opt<uv> type_vis      the pair every declaration shares;
                                   pairs that differ: indeterminate (visibility_by_use)
```

(the row form after the review's fix round; the first form, a pair for
the first declaration and one for the definition where it differed, is
replaced, "Fix round" below) written last in the unit of every entity
that is not a namespace and not content-keyed and whose representative's
semantic context
(through linkage specifications and `export`) is a namespace or the
translation unit, and of every entity of a block-scope `extern`
declaration (keyed in its namespace). `crates/slip_digest/src/enclosing.rs`,
called from `units.rs` after the declaration's stream.

**Why the effective linkage and the bool, not one of them.** "Inside an
unnamed namespace: yes or no" is not enough: the linkage of a name
depends on more than the namespace (`static`, `const`, `extern`, a named
module, an unnamed class with no typedef name), and what reflection reads
is `Ast::linkage`, so a rule table under which every key is equal must
not hide a change of it. `Ast::linkage` alone is not enough either: for
a block-scope `extern` declaration in a function of an unnamed namespace
it says `External` (`linkage.rs:349-362`, [basic.link]/6 taken
literally) while the mangler and clang give an internal symbol
(`enclosing/local-extern-out-of-unnamed`: `t _ZN12_GLOBAL__N_11n1fEv` →
`T _ZN1n1fEv`); and for `extern "C"` in an unnamed namespace it says
`Internal` while the mangler keeps it external (`mangle.rs:754-757`).
The two readers disagree, so the row holds both; the bool is what
`has_internal_linkage` reads. The cost: an entity that has no linkage
either way (a type alias, `enclosing/alias-out-of-unnamed`) still
differs when moved out of an unnamed namespace (known cost 1).

**Why per opening and per declaration.** (As first written; the fix
round below corrects which declarations count and where the walk
starts.) Visibility is the opening's,
not the namespace's: `namespace __attribute__((visibility("hidden")))
h { int f(); } namespace h { int g() … }` gives `h::f` `HIDDEN` and
`h::g` `DEFAULT`. A function declared in a hidden opening and defined in
a plain one is `DEFAULT`; declared plain, defined in a hidden opening,
`HIDDEN` (`enclosing/definition-in-other-opening`,
`definition-moved-from-declaration`: both differ with no rule at all;
before, equal: a wrong equal without rules). Kiln reads the first
declaration for some symbols and the definition for others
(`decl_visibility(first, …)` at `module.rs:3666`, `:3908`, `alias.rs:175`;
`decl_visibility(d, …)` at `module.rs:3730`, `:4249`, `class.rs:1008`),
so both are written, the definition's only when it differs: a
redeclaration that is neither (`differ/_/key-extern-c-in-two-namespaces`)
and a definition in an opening that gives what the first's gives
(`equal/_/var-extern-before-definition`) change nothing. The walk starts
at the opening the declaration is written in, as clang's does; Kiln
starts at the semantic context ("For Kiln" 3), which for an explicit
specialisation written in another opening is the first opening
(`enclosing/specialisation-in-hidden-opening`: clang `HIDDEN
_ZN1d1gIiEEiv`). The entity's own visibility attribute, which wins over
the namespace's, is in its attributes already; the row is written
whether or not it has one (known cost 2).

### The chain

An entity whose semantic context is a class or a function has no row.
That no property of item 1 then escapes:

- **A class member** takes linkage from its class ([basic.link]/4,
  `decl_linkage` `:367-370`) and visibility from its class
  (`compute_lv` dispatches a member to the class's; clang: a member
  defined out of line in a hidden opening of `n` stays `DEFAULT`,
  `_ZN1n1S1fEv`). The class's unit has the row, and the member's key
  holds the class's key, so a rule cannot move the member without
  moving the class, whose unit then differs
  (`needs-wp113/class-out-of-unnamed`: `changed (anonymous
  namespace)::Impl`, and `Impl::f()` equal, as its stream is).
- **A class with no unit**: a specialisation only named (digest §2.1)
  has no symbol and nothing generated; its linkage is its template's and
  its arguments', each a unit with its own row. Once it has members it
  has a unit, at namespace scope: the row.
- **A local class, a closure**: local entities are digested inside the
  unit that contains them (digest §4.3): a function's or a variable's,
  at namespace scope, with the row; their symbols are the function's
  (`_ZZN12_GLOBAL__N_11gEvEN1L1fEv`). `enclosing/local-class-out-of-unnamed`,
  `closure-out-of-unnamed` (the closure of a namespace-scope variable's
  initialiser: the variable's unit).
- **A friend defined in a class**: its semantic context is the
  namespace ([namespace.memdef]/3); it has its own unit, with the row
  (`enclosing/friend-out-of-unnamed`: `t _ZN12_GLOBAL__N_11fENS_1SE` →
  `W _Z1f1S`).
- **A specialisation whose template is in an unnamed namespace**: an
  explicit or implicit specialisation's semantic context is the
  template's namespace; it is a unit of its own with the row
  (`enclosing/specialisation-out-of-unnamed`: `changed …::S<int>`; the
  member functions of `S<int>` and `S<char>` take theirs from the class).
- **A template argument with internal linkage**: a specialisation's
  symbol is internal when an argument is (`_Z1gIN12_GLOBAL__N_14ImplEEiv`,
  `t`). The argument is in the specialisation's unit by key, and its own
  unit has the row: moved, the argument's unit differs
  (`enclosing/template-argument-out-of-unnamed`: `changed (anonymous
  namespace)::Impl`).
- **A block-scope `extern` declaration** names an entity keyed in its
  namespace (digest-kinds §2.4): that entity's unit has the row,
  computed from its representative. Where it is declared only in a
  templated function it has no unit and no symbol here; the function's
  unit, with the row, holds the reference.
- **A namespace** has no symbol; it has no row, and its members do.
  Relocating a namespace changes each member's row
  (`needs-wp113/namespace-*`).

## Fix round (review of WP-113)

The review (four wrong equals, F1-F4) found three things clang does that
the first row did not model; each is checked with `clang++-19 -std=c++20
-c` and `readelf -sW`, the lines in each case's `expect.txt`:

- (a) **A declaration written qualified outside its namespace**
  (`int n::f() {}` at file scope, `struct n::S {…};`, a friend
  `int n::f(S) {}`, `template <> int d::g<int>() {}`) takes the
  visibility of the **latest opening of its namespace written before it**,
  then that opening's own lexical chain. Nested, `int a::b::f() {}` in an
  opening of `a`: the latest opening of `b` before it, then the opening of
  `a` *that* opening of `b` is written in, not the one the definition is
  written in (`nested-latest-inner-opening`, `nested-later-outer-opening`,
  `nested-opening-in-hidden-outer`; nine probes n1-n7, q1, q2, all as the
  rule says).
- (b) **An undefined reference takes the visibility of the declaration
  most recent at the use** (`UND HIDDEN` / `UND DEFAULT`), for functions
  and variables; an ELF link takes the most constraining visibility of
  all references, so a hidden reference hides the symbol.
- (c) Hence **which declaration counts depends on where the use is**
  (F4): a use before a plain redeclaration and one after it differ.

**The row now** (`enclosing.rs`, `digest-kinds.md` §1.7 items 3-4): the
pair is computed for every declaration of the chain (`Ast::redecls_of`,
in declaration order), each starting at [`opening`]: the opening the
declaration is written in when it is an opening of its semantic
namespace (through linkage specifications and `export`), else the latest
opening of the semantic namespace with a smaller `DeclId` (Kiln allocates
them in parse order), else none: `Unaccounted("enclosing/opening")`
(a declaration before every opening of its namespace is not valid C++).
**If the pairs are not all equal the unit is indeterminate**, cause
`visibility_by_use` (`Cause::VisibilityByUse`, `digest.md` §10, counter
`digest.indeterminate.visibility_by_use` §12, `model.md` counters), on
each side independently. If they are equal the one pair is written.

**Deviation from ruling 1, said here.** The ruling asked for the pair of
every declaration, in declaration order. Once pairs that differ make the
unit indeterminate, a determinate unit's list is its one pair repeated
N times: writing the list adds only N, the number of declarations, which
no symbol depends on, and it breaks two existing equals that only move a
redeclaration (`equal/_/var-extern-before-definition`,
`differ/_/key-extern-c-in-two-namespaces`). So the pair is written once;
what ruling 1 protects (no declaration's pair is ignored) holds, as each
is computed and compared.

**How ordinary the indeterminate shape is.** It needs one namespace with
two openings whose attributes give different pairs, and one entity
declared in both (or declared in one and defined qualified after a later
one). In the corpus sources (`.corpus/llvm/src`, read, not run):
libc++ opens `std` only through `_LIBCPP_BEGIN_NAMESPACE_STD`, every
opening with `type_visibility("default")`, so libc++ alone has no such
entity. LLVM has one namespace attribute, `namespace
LLVM_LIBRARY_VISIBILITY gvn` (`GVN.h:59`), whose entities are defined
qualified in `GVN.cpp` (`struct llvm::gvn::AvailableValue {`) after the
one (hidden) opening: consistent, determinate. The shape that can occur
in LLVM is an entity of `std` redeclared in one of LLVM's plain `namespace
std {` openings (about 500 such openings in `llvm/` and `clang/`, nearly
all declaring specialisations or new overloads, which are entities of
their own); and known cost 4 below, an explicit specialisation of a
function template that Kiln chains to a declaration in the template's
opening. The counter makes the count visible in the corpus baseline
(left to the supervisor): a large value there means known cost 4, not
user code.

**A cheaper exact rule (proposal only, not implemented).** The pairs
differ only when some use or the definition is reached under different
declarations. Exact and cheaper than failing closed: write the
definition's pair in the entity's unit (the symbol's definition), and in
each *user's* unit, with the resolved reference, the pair of the
declaration most recent at that use (a value of the user's place,
computed on each side); the entity's unit is then determinate and a use
whose most recent declaration moved differs in the user. Cost: one
`opt` pair per reference to a namespace-scope function or variable
whose chain has more than one pair (zero for the common case, as the
pair is written only when the chain's pairs differ).

**Known costs added by the round** (`# pending` where the case expects
what clang does, and Slip does otherwise):

4. An explicit specialisation of a function template written in a

   (`enclosing/specialisation-in-hidden-opening`): Kiln chains it to a

5. An explicit instantiation definition in a hidden opening

## Decisions

1. **Namespaces get no row.** No symbol; `has_internal_linkage(^^n)` is a
   reflection value in the unit that asks; a merged namespace's unit is
   shared (verify §2.1), and a row there would make every merge differ.
2. **Content-keyed units get no row**: they declare no entity with
   linkage or a symbol.
3. **The row is not mapped**: it holds values, not keys. That is the
   point: it is computed on each side and a rule cannot rewrite it.
4. **`abi_tag` on a namespace is a name.** It reaches a symbol only
   through the tagged namespace's members, as part of how their names are
   mangled, and implicitly through types into other symbols
   (`enclosing/abi-tag-is-a-name`: moving `a::S` out of the tagged
   inline namespace makes `g()`'s symbol `_Z1gB1xv` → `_Z1gv`; equal).
   That is the same as a relocated type's name in a template argument's
   mangling: a declared change of names, which a whole rebuild makes
   consistently. The namespace's own unit holds the tag.
5. **`deprecated` and `unavailable` on a namespace** change diagnostics,
   never generated code or a constant: equal.
6. **An `inline` namespace** changes lookup, which every resolved
   reference already holds, and the mangled name, which is a name: equal.
7. **The scheme moves** (item 4), though `spec/digest.md` §11 said it stays
   1 until the first release; the brief asked for it, and a baseline of
   the old scheme recorded on the corpus could otherwise be read as
   current. §11 now says when it moves before the release.

## Item 6: `RULE_UNNAMED_NAMESPACE`

**Kept.** With the refusal switched off, the three cases of
`rules/wrong/` that it refuses all differ under their rule tables
(`unnamed-namespace-renamed-to-named`: `(anonymous namespace)::v`;
`named-namespace-renamed-to-unnamed`: `foo::v`;
`named-namespace-merged-onto-unnamed`: the namespace and `b`): item 2
catches each. What the refusal still refuses that the comparison would
pass is a rename to or from the unnamed namespace of a namespace with no
member that has a row (empty, or holding only content-keyed declarations
or other such namespaces): `namespace { }` renamed to `namespace foo { }`
compares equal without the refusal. That is a correct transform the
refusal refuses, and the only kind: it changes no symbol, and no one
needs to declare it.

The reasons to keep it: a rule table that renames a namespace into or
out of the unnamed namespace is wrong for every namespace that has
members, and the refusal says so when the table is made (`slip
declare`), naming the rule, where the comparison says it after a full
run, as one `changed` per member, on every observer. It costs one
comparison per rule. Removing it would also churn `RuleTable::refused`,
the container reader and three `wrong/` cases for no gain in soundness.
`spec/verify.md` §2.1 now gives this reason instead of soundness.

## Known costs (false differences)

1. An entity with no linkage either way moved out of or into an unnamed
   namespace differs (the bool): `enclosing/alias-out-of-unnamed`
   (`using T = int;`: no symbol on either side). Also a `static`
   function moved out of an unnamed namespace (internal both, the bool
   changes; the symbols are local both ways).
2. An entity with its own `visibility` attribute moved between openings
   of different visibility differs, though its own attribute decides.
3. A declaration in a hidden opening of an entity whose symbol is
   internal anyway differs (visibility does not apply to local symbols).

Each is conservative: a difference that a reader of the finding can
dismiss, never an equal that hides one.

## For Kiln

1. **`Ast::linkage` gives external linkage to a block-scope `extern`
   function of a function in an unnamed namespace.**
   `kiln_ast/src/linkage.rs:349-362` returns `External` for a
   block-scope function declaration (or `extern` variable) that is its
   entity's first declaration. [basic.link]/6 makes it a member of the
   innermost enclosing namespace, here the unnamed one, so it has
   internal linkage ([basic.link]/4); clang and Kiln's own mangler agree
   (`t _ZN12_GLOBAL__N_11fEv`).
   ```cpp
   namespace { int g() { extern int f(); return f(); } int f() { return 1; } }
   int u() { return g(); }
   ```
   `Ast::linkage(f)` is `External` (both declarations; `first` is the
   block-scope one), `in_anonymous_namespace(f)` true. Reflection's
   `has_external_linkage(^^f)` reads it. Slip writes both values, so is
   not affected.
2. **`Ast::linkage` and the mangler disagree on `extern "C"` in an unnamed
   namespace.** `namespace_scope_linkage` (`linkage.rs:378-386`) returns
   `Internal` for anything in an unnamed namespace;
   `kiln_abi::mangle::has_internal_linkage` (`mangle.rs:754-757`) keeps a
   function or variable first declared in an `extern "C"` context
   external, as clang does (`getLVForNamespaceScopeDecl`).
   ```cpp
   namespace { extern "C" int cf() { return 1; } }
   ```
   One of the two is wrong for reflection or for the symbol; which is
   Kiln's decision. Slip writes both.
3. **Code generation's namespace visibility starts at the semantic
   context, which for an explicit specialisation written in another
   opening is the first opening** (by reading; Kiln's code generation was
   not run). `kiln_codegen/src/visibility.rs:239` `ns_lv` starts its walk
   at `parent_ctx(d)` (`:454`), `d.ctx()` for a function; for the
   explicit specialisation below the definition's `ctx` is the first,
   plain opening of `d` and its `lexical_ctx` the hidden one, so Kiln
   finds no attribute and makes the symbol `DEFAULT`, where clang makes it
   `HIDDEN _ZN1d1gIiEEiv`.
   ```cpp
   namespace d { template <class T> int g() { return 0; } }
   namespace __attribute__((visibility("hidden"))) d { template <> int g<int>() { return 1; } }
   int u() { return d::g<int>(); }
   ```
   Either the specialisation's `ctx` should be the opening it is written
   in (clang's semantic context is that `NamespaceDecl`), or `ns_lv`
   should start at the lexical context when that is a namespace. Slip
   starts at the lexical context (`enclosing.rs` `namespace_visibility`).

4. **Code generation's namespace visibility for a declaration written
   qualified outside its namespace starts at the wrong opening** (by
   reading; Kiln's code generation was not run). `ns_lv`
   (`visibility.rs:239`) starts at `parent_ctx(d)` (`:454`), `d.ctx()`,
   for `int n::f() {}` written at file scope; clang starts at the latest
   opening of `n` written before the definition (its semantic
   `DeclContext`), then that opening's lexical chain. Below, clang gives
   `HIDDEN _ZN1n1fEv`; if `ctx` is the first opening of `n` (as Slip
   found it before the fix round), Kiln gives `DEFAULT`.
   ```cpp
   namespace n { int f(); }
   namespace __attribute__((visibility("hidden"))) n { }
   int n::f() { return 1; }
   ```
   The same for `struct n::S {…};` (vtable, type info, members), an
   explicit specialisation `template <> int n::g<int>() {}` and a friend
   defined `int n::f(S) {}` at file scope.
   (`rules/enclosing/qual-def-latest-opening`, `qual-class-def`,
   `spec-qualified-after-hidden`, `friend-qualified-after-hidden`.)
5. **A reference's visibility is the first declaration's, where clang
   uses the declaration most recent at the use** (by reading).
   `decl_visibility(first, false)` at `kiln_codegen/src/module.rs:3666`

   ```cpp
   namespace h { int f(); }
   namespace __attribute__((visibility("hidden"))) h { int f(); }
   int u() { return h::f(); }   // clang: GLOBAL HIDDEN UND _ZN1h1fEv
   ```
   (`rules/enclosing/mid-redecl-hidden`, `use-before-plain-redecl`,
   `var-mid-redecl-rule`.)
