# WP-039 — the declaration header, the names and the keys

What `crates/slip_digest` reads into digest §3, §4.3 and digest-kinds
§3.2, §5.3, §10.2 where the specs leave it open, found while testing the
header, the names and the keys.

## Unnamed classes and enumerations (§3.3)

- **The first declarator is the first in source order.** In
  `typedef struct {} *P, *T;` the class is named by `P` (the typedef name
  for linkage purposes is absent: neither declarator names the class
  itself). Writing `*T, *P` instead names it by `T`: the class's key
  changes, and `differ/_/key-typedef-unnamed-first-declarator-order` holds
  it. This is the conservative reading of "else its first declarator": the
  order of declarators is a fact of the source, and a tool that reorders
  them changes which name the class has, so the key says so.
- A typedef name for linkage wins over the first declarator
  (`typedef struct {} S, *P;` is named by `S`); a declarator that changes
  after the first does not move the class; pointer, reference, array and
  member-pointer declarators all name it (`declarator_of` looks through
  them). These are `differ/_/key-typedef-*` and `key-unnamed-*`.

## Display names (`names.rs`)

Display names are in no digest; they are what a verify report prints
and what an `expect.txt` line names, so two units of one output should
not share one. The forms:

- a function template: `template <class, int, template <class> class,
  class...>`, then its return type (not for a constructor, destructor or
  conversion function), then the qualified name and the pattern's
  signature: `template <class> void f(type-parameter-0-0)`;
- a member-like friend: its befriending class first,
  `A<int>::friend template <class> void m(type-parameter-0-0)`;
- a non-template deduction guide: its signature,
  `<deduction guide for S>(char)`;
- an unnamed class or enumeration: by what names it (§3.3),
  `(anonymous struct for P)`, else its ordinal, `(anonymous enum 1)`;
  its members are written below that name;
- an unnamed field or variable of an anonymous class:
  `(object of (anonymous union for a))`; an unnamed bit-field
  `(unnamed n)`;
- a holding variable of a structured binding: `x (holding variable)`;
  the decomposition itself `[a, b]`;
- the repeatable kinds: `<using n::f>` (an inheriting constructor
  `<using P::P>`), `<shadow n::f()>`, `<using_directive n>`,
  `<using_enum E>`, `<friend f()>`, and the content-keyed `<static_assert>`,
  `<asm>`, `<consteval_block>`, which have no printed content: two of
  them in one scope share a name, and the uniqueness test accepts it.

Names print no expressions. What differs in an expression alone (a
requires-clause, a null pointer's type in an argument, which Kiln's
argument printer writes as `nullptr`) gives two units one name; the
uniqueness test lists each such directory (`tests/determinism/keys.rs`
`SAME_NAME`).

## The uniqueness test

`tests/determinism.rs` `keys_and_names_are_unique` checks, on both sides
of every directory of `differ`, `equal`, `demand` and `indeterminate`
(pending ones included), that no key is counted a collision
(`digest.collisions`), that no key holds two digests unmarked, and that
no display name names two keys. It reuses the first parse of the
determinism test (one walk, shared through a `OnceLock`), so it costs no
parse of its own. What is known is listed per directory with its reason
(`SAME_KEY`, `SAME_NAME`); an entry that no longer matches fails, so the
lists only shrink.

## Collisions accepted

Two entities that differ only in an expression the key profiles (a
trailing requires-clause, a type-constraint, a partial specialisation's
requires-clause, a decltype operand, a dependent array bound) have one
key while the expression area is pending: both profile as
`Pending(Expr)`. The walk marks the key a collision, so both units are
indeterminate and nothing is called the same falsely. The probes are
`# pending`, `# needs: expr`.
