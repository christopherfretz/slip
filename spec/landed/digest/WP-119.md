# WP-119 — a rule on an instantiated member that agrees with its pattern's; hidden using-shadows are no units

What `crates/slip_digest` and the rename (`crates/slip_refactor`) do
beyond `spec/landed/digest/WP-103.md` (instantiated members follow their
pattern) and `spec/landed/edits/WP-120.md` (hidden shadows as followers).
Kiln references are at the pinned Kiln (`kiln/` in the checkout).

## Item 1: the acceptance (`keys.rs`, `follow_patterns`)

The condition, as built: for an owned instantiated member with plain key
`key` (its own name, its parent and discriminator mapped) and
`followed = Key { name: <the patterns' mapped name>, ..key }`,

```rust
match self.rules.map_traced(key.clone()) {
    (mapped, Some(_)) if mapped == followed => Ok((key, cause)),
    (_, Some(_)) => Err(Some(RULE_ON_INSTANTIATED_MEMBER)),
    (_, None) if self.rules.map_traced(followed.clone()).1.is_some() => {
        Err(Some(RULE_ON_INSTANTIATED_MEMBER))
    }
    (_, None) => Ok((followed, cause)),
}
```

As a spec sentence (`spec/digest.md` §3.4): a rule that matches the
member's plain key and produces exactly the key following gives (the
patterns' mapped name with the plain key's parent, kind and
discriminator) gives the member that key; any other rule on the plain
key, and a rule that matches the followed key when none matches the
plain key, makes the key indeterminate.

In the accepted case `follow_patterns` returns the **plain** key: the
caller maps it once (`rule_use::map`), which gives `followed` through the
rule and records the member in that rule's `via`. Every other place that
maps the key again (`mapped_name`, `key_bytes`, `records::key_again`)
maps the plain key, as for any entity. The cause (patterns that
disagree) is kept as before.

**Why no new collision and no wrong equal.** An accepted rule gives the
member the key it has without the rule (the followed key): the set of
keys a unit can produce is unchanged, only an indeterminate key became
the followed one. Two programs in which an instantiated member is bound
to different entities differ as they did before WP-119: the member's key
is the pattern's mapped name with its own parent and discriminator, so
another pattern (another name or another class) or another
specialisation (another parent) gives another key; a rule that would
give it any other key is still refused. A rename that leaves one of a
friend's declarations behind does not verify: in a unit that does not
instantiate the class, the namespace declaration kept as `f` keeps the
key the rule produces with no rule applied, `direct(r) != 0`, the
observer is stale (`rule_use/templates/wp119-friend-left-behind`); in a
unit that does, the kept `f(S<int>)` is another entity than the renamed
friend `g(S<int>)` (`rules/instantiated/wp119-swap-one-instantiated-rule`:
the swap undone on one function only is indeterminate and a removal).
End to end, `wp119_friend_over_two_observers_end_to_end` (rename.rs):
each wrong edit is a difference.

## Item 2: a rule on the followed key

Stays indeterminate when no rule matches the plain key
(`direct-rule-on-followed-name`, `wp119-swap-one-instantiated-rule`). It
says that some entity is renamed to or from the followed name, which is
not a statement about the member (its own source name is the plain
one), so it is not the same statement as item 1. When a rule matches the
plain key and gives the followed key, a rule on the followed key is not
applied after it: a table maps a key once (`spec/verify.md` §2.1). The
swap (`wp119-swap-friends-instantiated-rules`, rules `f → g` and `g → f`
on the patterns and on the instantiated friends) is equal with every
use `via 1`; no two entities share a key, so no collision is hidden.

## Item 3: rule use (`rule_use.rs`, documentation only)

An accepted member is in `via(r)` of the rule that matched its plain
key and in no rule's `direct` (a rule was applied); it is not counted
for the pattern's rule. Units A (declares `n::f(S<int>)`, no
instantiation) and B (instantiates and calls) give the rule on
`n::f(S<int>)` the same use, `via 1 direct 0`
(`rule_use/templates/wp119-friend-rule-unit-a`, `-unit-b`).

## Item 4: the rename

`followers.rs` no longer flags followers of instantiated members
(`followed_patterns` is gone); `spec_members.rs` no longer flags members
of explicit specialisations' followers `unsupported` (their `unreachable`
stays). `instantiated_unfollowed_using` flags only when a party has no
key. F3 (an explicit instantiation after the member's explicit
specialisation, recorded nowhere at the pin) is no longer refused: the
run is accepted, its post-image keeps `template void S<int>::f();`,
which names no member, and does not compile, so verification fails it
(`f3_post_image_does_not_compile`); the directory stays `# pending` with
the flag wanted `unreachable`. F4 (a namespace redeclaration of a
defined friend before or after the instantiation) renames and verifies
in both orders (`wp119_friend_redeclared_both_orders_end_to_end`).

## Item 6: hidden using-shadows (`units.rs`, `decl_class.rs`)

`units::hidden_shadow(w, e)`: a using-shadow (or constructor
using-shadow) every declaration of which Kiln marks hidden
(`ast.decls.hidden_shadow`) by a member that is not implicit. Such a
shadow is no unit (`class_of` returns `None`) and its class does not
list it (`unit_class`, and `decl_class::local_member` for local
classes).

A shadow hidden by an implicit member (an assignment operator or a
constructor declared on use) is kept: whether Kiln declares the implicit
member depends on what the unit uses, so leaving the shadow out would
make the digest of one class depend on a use elsewhere
(`spec/digest.md` §1 rule 5). Such a shadow and its hider are an
`operator=` or a constructor, which no rename reaches, so the rename never
looks at it (`differ/_/wp119-shadow-hidden-by-implicit-member` pins the
digest's side).

Pairs: `differ/_/wp119-hidden-shadow-made-visible-hider-removed` and
`-signature-changed` (the shadow's unit appears and the class changes),
`equal/_/wp119-hidden-shadow-declaration-order` (the two orders are
equal now; right, since in both the using-declaration does not introduce
the hidden function, [namespace.udecl]/14),
`differ/_/wp119-using-declaration-every-shadow-hidden` (the
using-declaration is still written as a unit, with no shadow). One
existing pair moved: `differ/ColdDeclData/hidden_shadow` now shows the
shadow `removed`, not `changed`.

**The recorded LLVM baseline can move**: a class with a using-declaration
beside a member that hides or overrides what it names loses the hidden
shadow's unit and lists one member less. A re-record is needed after
merging; nothing over `.corpus/` was run here.

## Known mismatches after the review

Each is loud (the run fails verification, never `verified`); the rename
should refuse or rewrite them, which is WP-127, not this package.

- **F1, a dependent call left behind.** Until WP-119 the followers'
  `unsupported` refused these runs; now the rename is accepted and
  verification reports the difference
  (`wp119_known_mismatch_f1_dependent_call`):

  ```cpp
  namespace n { struct Base { int f() { return 2; } };
  template <class T> struct S : Base { int f() { return 1; } }; }
  template <class T> int call(T t) { return t.f(); }
  int u() { return call(n::S<int>()); }
  ```

  Renaming `n::S::f` to `g` leaves `t.f()`, which in the post-image binds
  `Base::f`: `changed call<n::S<int>>(n::S<int>)::<definition>`. The same
  holds for `T::f()` on a static member and for `&T::f`. Without `Base`
  the post-image does not compile.
- **F2, the overrider before the using-declaration** (`spec/edits.md`
  §9.2, `wp119_known_mismatch_f2_member_first_using`):

  ```cpp
  namespace n { struct A { void f(int); }; struct B : A { virtual void f(); };
  struct D : B { void f() override; using B::f; }; }
  void h(n::D& d) { d.f(); }
  ```

  Renaming `n::B::f` or `n::D::f` to `g` is accepted, `using B::f;` stays
  as written and now names `A::f(int)`: `changed n::D`, `added
  n::D::<shadow n::A::f(int)>`. Without `A` the post-image does not
  compile. The using-declaration first: rewritten to `using B::g;`,
  verifies.
- **F3, a cost (a false difference).** A using-declaration whose shadows
  are all hidden, moved from `public` to `private`, shows `changed
  D::<using Base::f>`, though no name it introduces changes access: the
  using-declaration is still a unit and writes its access.

## For Kiln

- The hidden mark depends on declaration order (no shadow when the
  member comes first, a hidden one when it comes second); the digest now
  makes the two alike, but one recorded shape would be simpler:
  `struct B { void f(); }; struct D : B { using B::f; void f(); };`.
- An implicit member declared on use sets the hidden mark:
  `struct B { B& operator=(const B&); }; struct D : B { using B::operator=; };`
  with and without `D d; d = d;`.
- An explicit instantiation of a member after its explicit
  specialisation is recorded nowhere:
  `template <class T> struct S { void f() {} }; template <> void S<int>::f() {} template void S<int>::f();`.
