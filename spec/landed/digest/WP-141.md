# WP-141 — a reference redirected into a namespace that has two views

## Proposal (phase 1; nothing is built)

This is item 1 of `docs/wp/WP-141.md`: the design, for the supervisor's
ruling. It was written from `main` and from WP-140's proposal and
fixtures on its branch (`wp/140-dependency-opens-target`, proposal
`c3d6524a`; its build was not on `main`). Function names are given
instead of line numbers where WP-140 moves the lines. Fixture names
without a directory are under `crates/slip_digest/tests/rules/views/`.

The short form:

- **A namespace named in order to find members** (a qualifier, the scope
  of a using-declaration) is written with the key it has **from the
  point of view of what the lookup found**. This is rule 2 of
  `spec/digest.md` §3.4 carried from keys to qualifiers. Plain equality,
  no declaration, no digest of unchanged source moves.
- **A namespace named whole** (a using-directive at namespace scope, a
  namespace alias) has one **reading** per view key, and a reading
  counts only if the reference names **all** of that key. The unit is
  written with the own-key reading as ruled for WP-140; the other
  reading is an **alternate**, and the comparison takes it where the
  pre-image has it. This also closes a wrong equal that exists today
  (§7, T3).
- The central case: both directives verify; only `using namespace
  acme;` is a finding where `legacy` keeps a dependency part; only
  `using namespace legacy;` is a finding.

## 1. The question, and the words used below

With `relocate legacy => :: acme`, keys of the post-image are mapped back
to the pre-image's names for owned entities only (§3.4, rules 1 and 2).
A namespace that owned code and a dependency both open is one entity of
the program and two things for the rule:

- a **part** of a namespace is what it holds in one view: the **owned
  part** (its openings in owned files, the owned entities keyed under
  it) and the **dependency part**;
- its **view keys** are its keys in the views that exist (WP-140's
  ruling says when a view exists): the owned view's key has the rules
  applied, the dependency view's has none;
- `E(k)` is the set of namespaces of the image that hold something
  under the key `k`: in a view whose key is `k`, a read-only opening or
  an entity keyed under the namespace. An owned opening with nothing in
  it puts its namespace in no `E(k)` (it gives a lookup nothing to
  find; §9 Q5 is why this matters).

In the central case of the package, in an observer that includes both
dependencies, the post-image has two namespace entities, written `Na`
(spelled `acme`) and `Nl` (spelled `legacy`):

| entity | part | view key |
|---|---|---|
| `Na` | owned (`namespace acme { int g(int); }`) | `legacy` |
| `Na` | dependency (`new_dep.h`) | `acme` |
| `Nl` | dependency (`old_dep.h`) | `legacy` |

so `E(legacy) = {Na, Nl}` and `E(acme) = {Na}`. The pre-image is
digested under the empty table, where every namespace has one view and
`E(k)` is one namespace: its `legacy` is the post-image's `E(legacy)`
taken together, its `acme` is `Na`'s dependency part.

C++ has no way to name a part. A post-image reference to `Na` names
both parts. So for every key the pre-image named, two questions are
separate:

- **Is all of it still named?** A pre-image reference to `legacy` named
  everything keyed `legacy`. A post-image reference that names `Na`
  alone names half of it.
- **What else is named now?** The other part of `Na` comes along. It is
  the **surplus**: forced by the language once the rule merges the two
  namespaces, and present in every reference to `acme`, redirected or
  untouched.

Three observers are used in the tables: `O0` includes neither
dependency, `O1` only `new_dep.h` (the first example of the package),
`O2` both (the central case).

## 2. What naming a namespace does for lookup

By section name of the C++ standard.

- **[namespace.udir], [basic.lookup.unqual].** A using-directive makes
  the names of the nominated namespace visible to unqualified lookup
  from the scopes it reaches, after it, as if declared in the nearest
  enclosing namespace of both. It declares nothing. Transitively: a
  directive in a nominated namespace is followed.
- **[namespace.qual].** Qualified lookup into `N` looks in `N` and its
  inline namespace set, and, if it finds nothing there, through the
  using-directives written in `N`. So a directive at namespace scope
  also affects every `N::x` where `N` holds the directive.
- **[basic.lookup.argdep].** Argument-dependent lookup ignores
  using-directives in the associated namespaces. A directive or an alias
  never changes what ADL finds. What ADL finds in a namespace depends on
  which namespace a type's declaration is a member of, which is the
  type's key (rule 2), not a reference.
- **[namespace.alias].** An alias is another name of the namespace. Its
  uses are qualifiers, directives and aliases; each resolves to the
  namespace.
- **[temp.res], [temp.dep.candidate].** In a template, a name that is not
  dependent is bound at the definition. A call with a dependent argument
  and an unqualified name keeps the declarations found at the definition
  and adds ADL at the instantiation. A call with a namespace-qualified
  name (`legacy::h(t)`) has no ADL: its candidates are those found at
  the definition. Kiln does this (`kiln_sema`
  `templ/subst/exprs.rs`, `callee`: with no ADL the rebuilt callee is
  made from the recorded declarations, not looked up again).
- **[namespace.udecl].** A using-declaration names, for a namespace
  scope, the declarations found by qualified lookup at that point; each
  is a using-shadow.

What the digests of uses already record, and what they do not:

| lookup | affected by | recorded in |
|---|---|---|
| unqualified name, resolved | directives in scope | the referent's key, in the user's unit (`refs.rs` `write_ref`) |
| qualified name, resolved | the qualifier; directives inside it | the referent's key; the qualifier is not written (§6) |
| unqualified or qualified name left unresolved in a template | as above, at the definition | the found set, sorted refs, and the ADL bit (`expr_dep.rs` `unresolved_lookup_expr`) |
| ADL at an instantiation | never a directive or an alias | the instantiation, a derived unit |
| the name of a using-declaration | the qualifier | the using-shadows, each a unit keyed by the entity it stands for |

There is no negative record for name lookup and none is needed in a
parsed translation unit: a declaration that a changed nomination newly
makes visible either changes a referent or a found set (a difference in
that unit), makes the lookup ambiguous (the post-image does not parse),
or changes nothing. WP-135's found lookups and WP-117's negatives are
about **file** lookups (`#include`, `__has_include`), not names; they
are not part of this argument.

So in every observer the run parses, every effect of a directive or an
alias on a lookup is in the unit that performs the lookup, templates
included (their definition-time lookups are written whether or not they
are instantiated). **What only the reference itself holds is the
nomination**: what a lookup would see that no parsed unit performs. That
is a lookup in a translation unit the run does not parse (another
includer of the header, another configuration), or in code written
later. `spec/verify.md` §8 already says the claim is about analysed
observers. The question of this package is therefore how much of the
nomination the reference's own unit must keep fixed, and the answer
proposed is: **every key the pre-image named stays named whole; the
surplus is the rule's.**

fail the other (§6).

## 4. What no rule on the post-image alone can do

A pre-image is digested under the empty table with no ownership, so its
units are fixed before any rule is known. In `O1`:

```cpp
// a.h, owned; before            after
using namespace legacy;       // using namespace acme;     (redirected)
// b.h, owned; before            after
using namespace acme;         // using namespace acme;     (untouched)
```

The two post-image declarations are the same text in the same kind of
scope, each in a file of its own, and nothing else in the post-image
tells them apart. Their pre-images differ. So no function of the
post-image writes one unit for each that equals its pre-image: with one
unit per directive, either the redirected one or the untouched one
differs (WP-140's ruling chose which). For rows 1 and 2 the comparison
has to take part, or the user has to say which is which. Rows 3 to 5 do
not have this problem: `acme::g(t)` and `acme::d(t)` differ in what they
found.

## 5. The options

The package's four, and the one recommended.

1. **Both keys.** A reference to a two-view namespace is the pair of its
   view keys; a directive is a unit under each reading.
2. **Either key, accepted by the comparison.** Every reference to a
   two-view namespace has two readings; the verifier accepts the
   pre-image under either. Per unit: all references read one way (2
   readings) or each independently (`2^n`).
3. **A declaration: the referrer's view.** With the rule in the table,
   an owned reference to a two-view namespace is written by the owned
   view.
4. **Left out where uses decide.** Rows 4 and 5 stop writing the
   namespace; rows 1 to 3 stay as WP-140 leaves them.
5. **Recommended: the referent's view, and whole readings.**
   - **R1** (rows 3, 4, 5). The namespace is written with the key it has
     as the enclosing namespace of each declaration the lookup found
     (rule 2, from that declaration's point of view: the owned view for
     an entity rules reach, else the dependency view). One key: an
     ordinary `Ref`. Several keys (the found set is in both parts), or
     nothing found: a form that equals no pre-image.
   - **R2** (rows 1, 2). In an owned file the reference has a reading
     for each view key `k` of the namespace, and the reading is `k`
     itself only if the reference is **whole for `k`**: every namespace
     of `E(k)` is named, by this alias, or by the using-directives of
     the same scope in the same file taken together. Otherwise the
     reading is a form that equals no pre-image (`part`). The unit is
     written with the own-key reading; a second whole reading is an
     **alternate**. The comparison, per group: an alternate the
     pre-image's group has is added; a written reading the pre-image's
     group lacks, whose alternate it has, is taken out (§8.2). In a
     read-only file there is one reading, the dependency view's, never
     `part`.
   - **R3** (row 14). An obligation on a piece that names a namespace
     holds if its key is one of the namespace's view keys.

Option 5 is option 3 with the question it leaves answered (the
untouched reference is told apart by what it found, or by the
pre-image), option 2 confined to declarations (never inside a stream or
a key, so nothing is exponential) and given the completeness condition
it lacks, and option 4's observation used without removing anything
from a digest.

## 7. The attacks

For each: is it a change of meaning in a translation unit the run
parses (**P**), in one it does not (**U**: another includer of a header,
another configuration, later code), or in none (**N**)?

**T1. The surplus on an untouched reference** (D2, A2; every option but
3 accepts it). Pre-image `using namespace acme;` named the dependency's
`acme`; the same text now also names the owned members the rule moved
in. This is the reviewer's sentence read literally. **U.** In a parsed
unit every lookup after the directive is recorded (§2); a `g` now found
through it changes a referent, a found set, or does not compile. No edit
avoids it: the only reference to the dependency's part that C++ allows
names the owned part too, and so does every `acme::x` in every unparsed
file. It is a consequence of the declared rule, not of an edit. Option 3
"closes" it by refusing every untouched reference, which is every such
directive in the codebase, with nothing the user can fix. Under 5 it is
accepted, stated in `spec/verify.md` §8, and counted in the report (§8.5).
**Not closed, and not closable by a verdict.**

**T2. The surplus on a redirected reference** (D1, A1). The same, for
the dependency's `acme` that comes with the owned part. **U**, same
argument.

**T3. A part dropped** (C2, C3, A4, A5; today C3 and A5 verify, and 1,
2, 3 add C2 and A4). A pre-image reference named everything keyed
`legacy`; the post-image names one namespace of the two. **U** when no
parsed unit uses the dropped part through the reference (else the
post-image fails or a unit differs). **C3 and A5 are equal on WP-140's
branch as ruled, and were before it**: an untouched `using namespace
legacy;` after the owned part left writes the same reference to the
same key. (Read from the code, not run: the build's first fixture
should pin it as it is before changing it.) Under 5 closed by "whole for `k`": the reading that drops a
namespace of `E(k)` is `part`, which no pre-image has. What remains: a
run in which no observer sees the dropped part at all (`O0` only) cannot
know of it. That is §8's limit; an observer that includes `old_dep.h`
reports it.

**T4. Whole by a directive placed elsewhere in the file.** C1 with
`using namespace legacy;` at the end of the file and the lookups in
between. **N** for the file's own code (parsed: recorded), **U** for
another configuration of the same file. A pre-image directive moved
within its file is equal today for the same reason (a content-keyed unit
has no position). Scope and file are required to be the same because
those are what the unit's key and group hold; a directive in another
file is not counted (a header's includers differ), nor one in another
scope, nor a directive reached transitively through one written inside
`acme`.

**T5. An alternate taken for an unrelated pre-image unit.** The
pre-image deleted `using namespace legacy;` and the post-image added an
unrelated `using namespace acme;` in the same scope of the same file.
**N**: that is a redirect; a directive has no identity beyond scope,
file and target.

**T6. An alternate used to absorb a deletion in another file.** The
pre-image has `using namespace acme;` in `x.h` and `using namespace
legacy;` in `y.h`; the post-image deletes the one in `y.h`. If the step
of §8.2 were stated on the multisets of the whole image, the untouched
directive of `x.h` would be read as both and the deletion would vanish:
**U** (the includers of `y.h` alone). Closed by stating the step **per
group**. Cost: a directive that is redirected and moved to another file
in one edit is `removed` and `added`.

**T7. Both readings taken when the pre-image had one.** Needs the
alternate to be added only when the pre-image's group has it; then the
post-image's set equals the pre-image's or the alternate is not there.
**N.**

**T8. A read-only referrer.** `old_dep.h` holds `using namespace
legacy;`. After the edit it no longer names the owned part. **P or U,
and the rule's**: no owned edit can change a read-only file, and a
lookup in the dependency's code that found an owned member is a unit
that differs. Under 5 a read-only reference has one reading and is never
`part`, so C9 is equal; anything else would be a finding in a file the
user cannot edit.

**T9. A retarget through a re-export, same found set** (Q4, Q5, Q8).
**N** for the lookup (the same functions, [namespace.udecl]). Option 4
accepts all three, and options 2 and 3 accept Q5 and Q8, with the
re-export declared `created`. Under 5 all three differ: Q4 because
`other` has one key whatever was found; Q5 and Q8 because the found
declarations are taken as entities (a shadow as the entity it stands
for, as `write_ref` does), so the dependency's function gives `acme`
its dependency view's key, not `legacy`. This refuses an edit whose
meaning is the same; §9 Q4 is whether to accept it later.

**T10. A found set in both parts, unchanged** (Q8 again, and a
pre-image that already has it under a table with two views). Under R1
the two-key form is written and equals no pre-image. Fails closed.

**T11. Nothing found.** A namespace-qualified name with an empty found
set is ill-formed ([basic.lookup.qual]), so no valid program reaches it.
R1 writes every view key: fails closed, with a counter.

**T12. Rules made to order.** A user rule that gives a namespace a
second view is a rule the report shows; not this package (§2.1 of
`spec/verify.md`).

**Per option, the wrong `verified` found:**

- 1: C2 (the same units as C1), and every `changed f` it asks for hides
  the rest of the unit. Its `created` line for a directive is keyed by
  content, which the tool that made the edit cannot compute without the
  walk.
- 2: C2, C3, A4, A5 (**U**), unless given the condition of R2; and `2^n`
  readings, or Q10 refused.
- 3: C2, C3, A4, A5 (**U**); and D2, A2, Q2 refused with no remedy.
- 4: Q4 (a retarget the package says must differ), and digests of
  unchanged source move.
- T: C3, A5 (**U**).
- 5: none found. T1 and T2 are accepted by design and argued above.

## 8. Recommendation: option 5

### 8.1 `spec/digest.md` §3.4, after "Ownership" and WP-140's views

> **A reference to a namespace.** A namespace is referred to by a view
> key (WP-140). With one view key there is nothing to choose.
>
> *Named to find members*: the scope of a using-declaration in its key,
> and the qualifier of a name left unresolved when the qualifier is a
> namespace, in a stream or in a profile. Take the declarations the
> lookup found (the using-declaration's shadows; the unresolved name's
> set), each as the entity it stands for. The namespace is written with
> the key it has as an enclosing namespace of each (rule 2: from that
> entity's point of view), the keys sorted and duplicates removed. One
> key is written as `Ref::unit`. Two or more, or none found (then every
> view key), are written as `Ref::views`: the count and the keys. A
> found entity that is not a member of the namespace or of its inline
> namespace set (found through a using-directive written in the
> namespace) is taken by its own ownership all the same.
>
> *Named whole*: the namespace a using-directive at namespace scope
> nominates, and the target of a namespace alias. In a read-only file it
> is written with its key in the dependency view (its one view key if it
> has no dependency part). In an owned file it has a **reading** for
> each of its view keys `k`. A namespace **holds something under `k`**
> if, in a view of it whose key is `k`, it has a read-only opening or an
> entity keyed under it. The reference is **whole for `k`** if every
> namespace of the image that holds something under `k` is named: by
> this alias; or, for a using-directive, by the using-directives of the
> same enclosing namespace in the same file, taken together. The
> reading for
> `k` is `Ref::unit(k)` if the reference is whole for `k`, else
> `Ref::part(k, view)`. The unit is written with the reading of the
> namespace's own key. Each other reading that is whole is an
> **alternate** of the unit: the key and digest the unit would have with
> that reading, and the unit's group (§11).
>
> Under the empty table, and under a table that maps no namespace of the
> chain, every namespace has one view key and every key one namespace,
> so every reference is `Ref::unit` of the own key and there is no
> alternate (the invariant of WP-131).

`Ref::views` and `Ref::part` are two new variants of §4.1
(`spec/digest-kinds.md` §2.2). Neither is ever written for a pre-image.

§11 gains: the alternates of an image (in the `digests` section,
ascending by group, written unit, alternate unit); for each group that
has one, the **alternate sum**, the group's sum with every alternate put
in place of its written unit; and `tu_alt`, the `tu` digest over the
alternate sums.

### 8.2 `spec/verify.md`

**§2.1**, replacing the bullet "A dependency that itself opens `acme`"
as WP-140 leaves it:

> A reference from owned code to a namespace that has an owned and a
> dependency part needs no declaration. Where it finds members it is
> written from the point of view of what it found. Where it names the
> whole namespace (a using-directive, a namespace alias) it is compared
> under each key the reference names whole (§4 step 1a). A reference
> that names only some of the namespaces that share a key names less
> than the pre-image's did, and differs.

**§4**, a step between 1 and 2:

> 1a. **Alternates.** For each group, let `Pg` and `Qg` be its declared
> units in the pre-image and the post-image, and let `(a, b)` range over
> the post-image's alternates of the group, `a` the written unit and `b`
> the alternate. `Qg` is replaced by
> `(Qg − {a : a ∉ Pg and b ∈ Pg}) ∪ {b : b ∈ Pg}`,
> each unit once (§11: two units of one group with one key and digest
> are one). Steps 2 to 4 use the result. An indeterminate `a` has no
> alternate.

Each alternate is decided by the pre-image's group alone, a unit taken
out is never one put in (the first needs it absent from `Pg`, the second
present), so the result does not depend on any order.

**§4.1**: step 1 also verifies when the post-image's `tu_alt` equals the
pre-image's `tu` (and no group has an indeterminate unit); a group is
outside `G` also when its alternate sum equals the pre-image's sum.
Restricting to `G` stays exact: a group whose sums are equal has `Qg =
Pg`, where step 1a changes nothing (`a ∈ Pg`, and a `b ∈ Pg` is already
in `Qg`); a group whose alternate sum equals the pre-image's sum is the
case "every `a` out, every `b` in", which is what step 1a gives then
(equal sums mean every `b` is in `Pg`, and an `a` that is in `Pg` too
is then one of the units already counted, so keeping it adds nothing).

**§8** ("What this does not show") gains:

> A rule that moves owned members into a namespace a dependency opens
> makes every reference to that namespace name both. The run shows that
> every key a pre-image reference named is still named whole, and that
> no lookup in an analysed observer changed. It does not show that a
> lookup in code it did not analyse is unchanged by what a reference
> names in addition; no edit could keep that.

**§10.2 step 4**: the origin of a piece that names a namespace answers
with every view key the namespace has; the obligation holds if its key
is one of them (R3). The lookup the piece serves is decided by the next
piece's obligation or by the unit's digest.

**"Open questions"**: "A move into a namespace that a dependency opens"
is reduced to what §8.6 below leaves.

### 8.3 What the user declares

- Using-directives, qualifiers, using-declarations: **nothing**.
- An alias that named both parts where the old namespace keeps a
  dependency part: `changed <alias>` (by key; structural). The tool that
  made the edit knows it split the alias and can emit it.
- A function whose dependent call's candidates are in both parts (Q7):
  no declaration makes the call the same; `changed f` is the user's
  statement that the change is intended.
- Nothing is a text pattern. No new declaration form is needed (§9 Q1
  asks about one).

### 8.4 What moves

- Under a table that gives a namespace two view keys, post-image units

  whole-namespace reference that is not whole to `part`.
- **`scheme` stays 2.** One class of units now differs that compared

  `tu_alt`: a change of the shard's layout, present only for an image

- **WP-140's fixtures that turn over to no finding:**

### 8.5 Costs and bounds

- R1: one key lookup per found declaration, at a place that already
  writes the found set. Linear in what is written today.
- R2: `E(k)` is one map built from WP-140's view table (one entry per
  namespace view); the namespaces named per (scope, file) one pass over
  the namespace-scope using-directives. An owned whole-namespace
  reference has at most one alternate per view key beyond the own key:
  one, with two views. **The number of alternates is at most the number
  of owned using-directives and aliases; step 1a is one set operation
  per alternate. Nothing is exponential**, because a reading is never
  taken inside a stream or a key: a function body with `n` qualifiers
  has `n` keys chosen by R1 and one digest.
- Parses: an observer whose alternates are all taken, in every group
  that has one, verifies by `tu_alt` or by alternate sums with one
  parse, as an untouched one does. A group with a mix (one directive
  redirected and one untouched in the same file) needs its unit lists,
  so the pre-image is parsed again as for any differing group today.
  The existing open question "storing unit lists for owned files at map
  time" would remove that for every such case.
- Memory: the alternates of the groups being compared.
- An informational line of the report, not part of the verdict: per
  rule, the number of owned references that name a namespace with a part
  the pre-image's reference did not name (the surplus, T1 and T2).

## 9. Open questions for the supervisor

**Q1. Is a dropped nomination a finding when no parsed lookup needs it
(C2)? Recommended: yes.** The edit that keeps both directives always
exists and always verifies. A waiver would be a declaration by key,
`narrowed <namespace>` ("owned whole-namespace references to this
namespace need not keep the part the rule leaves"), which a transform
can emit and which the report would count per use. It changes what
`verified` says and how the migrated code looks (one directive, not
two). **The operator's to decide**; I recommend not offering it until a
real run shows the kept directives are a burden.

**Q2. One build or two (§8.8)? Recommended: two**, R1 with `part` first:
it is the half that removes a wrong equal.

**Q3. Which reading is the written one? Recommended: the own key, as
ruled for WP-140**, so its untouched fixtures and the units of read-only
files do not move. The other choice (the owned view) only swaps which
case needs the alternate.

**Q4. Should a re-export make Q5 and Q8 equal?** R1 could take a found
using-shadow as the member it is (owned, in `acme`) and not as the
entity it stands for. Then `acme::k(t)` with `namespace acme { using
legacy::k; }` declared `created` has the pre-image's found set and the
pre-image's qualifier, and the package's "no correct respelling" would
have one. The lookup's result is the same set of functions. It would
also make Q5 equal, which the reviewer's question names.
**Recommended: no for now** (fail closed, as the package expects);
revisit with the transform that would emit the re-export. It needs the
front end's found set to keep the shadow, which the build should check
either way.

**Q5. The edit must be the same text for every observer.** In a header,
C1's `using namespace legacy;` does not compile for an includer that
never sees `legacy` once the owned part has left. The edit that works
everywhere is both directives and an owned `namespace legacy {}` before
them; it verifies in every kind of observer (V2; the guard's unit is
the pre-image's `legacy`, and an empty owned namespace is not counted
`direct`, §9.2 of `spec/verify.md`). A guard holds nothing, so it does
not make another file's lone `using namespace acme;` less than whole;
that is why `E(k)` leaves empty owned openings out. Whether Slip's
transform always emits the guard, or only where some observer lacks
the dependency (a per-observer fact the reducer would unite), is the
transform's design and **partly the operator's (what the migrated code looks like)**.
Recommended: emit it only where needed, later; always, first.

**Q6. Owned code that is already in `acme` before the edit** (the
operator: the new root may be shared "before it too"). Not this
package, and the most important neighbour: a namespace rule maps every
owned member of the post-image's `acme`, so an owned `acme::x` that was
there before is `removed acme::x` and `added legacy::x` (`spec/verify.md`
§2.1, "A pre-existing entity that a rule would capture"), and R1 writes
references to it from the same point of view, so they differ with it,
consistently. It needs its own design (a rule that excludes entities, or
ownership by repository and not by file), beside WP-116 and "Ownership
differs between observers". Recommended: a package of its own before
the first real run.

**Q7. Does an alternate taken count as a use of the rule (§9.1)?**
Recommended: no. Rule use is counted on keys, WP-140's view units
already give `via`, and the line is informational.

**Q8. Row 6 (a namespace by its name bytes in a signature).** Differs
under any relocation, two views or not. Recommended: pin it with a
fixture here (Q12) and fix it in a digest-kinds package: the level
should be written as rows 4 and 5 are.

**Q9. Display names.** `<using_directive legacy (the part the rule
leaves)>` and the notes of §8.6 are user-visible text. **The operator's
to word**; the forms above are a proposal.

**Q10. To confirm in the build, not decisions:** that Kiln's found set
of a qualified unresolved name is never looked up again at
instantiation in a way the pattern does not record (read: it is not,
§2); that the unit's spelling holds the found set where the profile
does not (row 5); that a file is owned or read-only as a whole for the
purpose of "in an owned file" where the per-inclusion rule of §2.1
applies (recommended: the group's file by its own path).
