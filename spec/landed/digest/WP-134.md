# WP-134 — inert rules: the tests the review of WP-131 asked for

## Item 1: names that follow their pattern are pinned

`spec/digest.md` §3.4 (WP-103, WP-119, WP-131): an operator, a
constructor and `unnamed_by` of an identifier follow their pattern. Each
case below has identical sides but for the last, and a rule written field
by field (`rule` lines of `tests/common/rules.rs`).

| Case (`rules/instantiated/`) | Holds |
|---|---|
| `wp134-operator-rule-on-instantiated-member` | a rule on the plain key of `W<int>::operator==` giving another name: the member, its definition and `f` indeterminate, `key/rule-on-instantiated-member` |
| `wp134-constructor-rule-on-instantiated-member` | the same for `W<int>::W(int)` (declared only, WP-124) |
| `wp134-unnamed-by-rule-on-instantiated-member` | the same for `W<int>::(anonymous enum for E)`, `unnamed_by(E)`: an enumeration, because at the Kiln pin an instantiated unnamed class has no `instantiated_from` link (WP-131, For Kiln) and so follows nothing under any predicate |
| `wp134-pattern-operator-rule-reaches-instantiation` | a rule on the pattern's operator (`W::operator==` in the post-image, `W::eq` in the pre-image, call `a.operator==(b)` against `a.eq(b)`) reaches `W<int>::operator==`: equal. Beside it a rule on the pattern's constructor (`relocate … => W :: =`) is accepted and changes no key |

A constructor's name cannot be made another name by a declared change
(`slip declare` gives a new name only to an identifier, and a constructor
renamed to an identifier is not the same entity on the other side), so
the rule on the pattern's constructor in the last case is the identity
relocation: it shows the rule accepted, not a name carried over. That
the constructor follows is pinned by the second case.
