# WP-131 — a rule that matches nothing changes nothing; conversion names do not follow their pattern

What `crates/slip_digest` does beyond `spec/landed/digest/WP-103.md`
(instantiated members follow their pattern) and
`spec/landed/digest/WP-119.md` (a rule on an instantiated member). The
package is Demo 1's failure: under any non-empty rule table, the
conversion function of an instantiation (`W<bool>::operator bool`) was
keyed with its pattern's name (`operator T`, a conversion name whose
digest is the pattern's type), and under the empty table with its own.
Every key under it and every unit that named it (`f(W<bool>)`, the
namespace holding `f`) then differed between a verify with rules and the
same verify without, though no rule matched anything there.

## What was built

- `keys.rs`, `compute_key_by_value`: the pattern-following branch is
  taken only when `follows_pattern(&key.name)` holds (a new private free
  function beside `merge`). Nothing else in `follow_patterns`, the
  WP-119 acceptance, `mapped_name`, `map_key` or the namespace views
  changed.
- `tests/inert.rs`: the invariant of item 3 (below).
- `keys.rs` unit test `wp131_names_that_follow_their_pattern`: the
  predicate's table, including the forms no walk reaches today.
- `tests/rules/inert/`: 16 cases, one per name kind of item 2 and one per
  probe the invariant suggested, each the relocation `a::detail => a ::
  impl` beside the member in question, with the expectation "equal" (or,
  for `unnamed-ordinal`, the state as it stands; see Follow-ups).
- `crates/slip_verify/tests/pitfalls/n45-relocation-beside-conversion-function/`
  and `spec/pitfalls.md` row N45: the end-to-end form of Demo 1's case.
- `spec/digest.md`: §3.4 says which name forms follow their pattern and
  what a conversion-named rule means; the paragraph "A rule that matches
  nothing changes nothing"; §14 lists the invariant.

## Decisions

1. **A name follows its pattern only when it is the same name in the
   pattern and in the instantiation by construction**: an identifier, an
   operator, a constructor, a destructor, a literal operator, a deduction
   guide, and `unnamed_by` of one of these. A conversion name is a digest
   of the type converted to, which in the pattern is a dependent type
   (`T`) and in the instantiation the argument (`bool`); a `local` name
   is an ordinal among the local declarations the walk sees, which a
   discarded `if constexpr` branch changes between the pattern and the
   instantiation; an `unnamed_ordinal` is an ordinal among the scope's
   unnamed types. Those keep their own name: such a member is keyed as a
   member that follows no pattern (its parent is mapped, its name is its
   own). A rule on the type converted to still reaches the name, because
   the conversion's digest is a type digest computed in mapped terms.
2. **A rule whose name is a conversion name** comes only from `relocate
   … :: =` (the declare layer refuses a new name for a non-identifier)
   and matches a key like any rule: on an instantiation's own conversion
   key it is a rule on that member (WP-119's
   `key/rule-on-instantiated-member` checks apply only to members that
   follow, so here it is simply a rule that matches the plain key). The
   case `rules/inert/conversion-rule-on-instantiated-member` shows it
   used once (`use 2 via 1 direct 0`).
3. **`digest.bytes` is a measure of work, not a finding**, and the
   invariant checks it as "no smaller under rules" rather than "equal".
   A walk under a non-empty table keys a namespace again in the view of
   the other ownership (`namespace_parent`, whenever a file is
   read-only) and computes a pattern's or a template's key again for its
   mapped name (`mapped_name`); those streams are hashed and counted. I
   first made `mapped_name` save and restore the counter, then reverted
   it: it would touch the WP-103/119 path for a counter, and the views
   cost real work that the counter is meant to show. **Reviewer
   decision**: if `digest.bytes` must be equal, both sites need a "count
   only the first computation" rule; the invariant then compares it in
   full by deleting the `BYTES` exclusion.

## Item 2: the name kinds that are not identifiers

| Name | Same in pattern and instantiation? | Follows | Case |
|---|---|---|---|
| `operator(op)` | yes | yes | `special-members` |
| `constructor`, `destructor` | yes | yes | `special-members`, `implicit-members` |
| `literal_operator(s)` | yes | yes | `special-members` |
| `deduction_guide` | yes | yes | `member-deduction-guide` |
| `conversion(T)` | no: a type digest, dependent in the pattern | **no** (the fix) | `conversion-of-instantiation`, `conversion-function-template`, `conversion-to-relocated-type`, `conversion-in-dependency` |
| using-shadow of a conversion | its name is the conversion name | no (by its name) | `conversion-using-shadow` |
| `unnamed_by(n)` | as `n` | as `n` | `unnamed-by-member`, `unnamed-by-conversion-cxx26` (no pattern link today: see Mutations), unit test |
| `local(n)` | no: a discarded branch renumbers, and one expansion statement instantiates its local class once per element | **no** (found by probe; and by WP-124) | `local-class-after-discarded`, `lambda-after-discarded`, `expansion-local-class` |
| `unnamed_ordinal(n)` | not reliably | no | `unnamed-ordinal` (see Follow-ups) |
| `anonymous`, `content`, `property`, `order`, `parameter` | name no instantiated member's own key | no | (no member has them) |

Closure members (`operator()`, the conversion to a function pointer of a
lambda in a template) are covered by `conversion-closure-in-template`;
implicit members have no pattern link or the same name
(`implicit-members`).

## The invariant (`tests/inert.rs`) and what it excludes

Every directory of `tests/equal`, `differ`, `demand`, `indeterminate`,
`resolved` (pending ones included) and `tests/rules` (both subjects), both
sides: one parse, three walks (empty table; one namespace rule; a rule of
each kind with every file but `main.cpp` read-only), the `Output`
compared in full. Excluded:

- `digest.bytes`, checked as no smaller (decision 3).
- A side that does not parse in a pending directory (it has no walk).
- The records are not walked again: a record's id, kind, class, name and
  flag are in the `Output`, and its `Key` is the preimage of its id.
- The tables are fixed; a rule that matches a key would make the
  comparison meaningless, so each rule names an entity no source
  declares (`slip_inert_*`, a class id no source has, a discriminator no
  walk computes).

Over 3360 directories on 4 threads it takes about 18–20 s.

## What the invariant found beyond conversion functions

- `local(n)`: a local class or a lambda declared after a discarded `if
  constexpr` branch in a member function template is numbered
  differently in the instantiation; reproducers
  `rules/inert/local-class-after-discarded`, `lambda-after-discarded`;
  fixed by the predicate.
- `local(n)` in an expansion statement (C++26 `template for`; reported by
  WP-124's implementer): the local classes instantiated from one
  expansion statement are distinct entities, and under a rule table both
  followed their one pattern onto one key (`<order>` collision);
  reproducer `rules/inert/expansion-local-class` (no mem-initializer, so
  it does not depend on WP-124); fixed by the predicate (a `local` name
  keeps its own number). WP-124's pending pair
  `indeterminate/_/mem-initializer-expansion-local-class` should no
  longer need its "pending" once both are on `main`.
- `digest.bytes` (decision 3).

## Follow-ups

- `unnamed_ordinal` in a class template: `W` and its anonymous enums are
  indeterminate with `key/name` and `collisions 1` under no rule at all,
  because `ordinal_in_scope` reads the members of `entity(scope)`, the
  class template, not its pattern. Not a rules problem; the case records
  the state as it is so that a fix shows as a changed expectation.

## For Kiln

- An instantiated unnamed member class (`template <class T> struct W {
  struct { operator T() const; T v; } _; };`, `W<bool>`) has no
  `instantiated_from` link, where an unnamed member enumeration does. Not
  a defect Slip depends on today (the class keeps its own name either
  way); recorded so the link, if added, is tested against
  `unnamed-by-conversion-cxx26` and the predicate's unit test.
