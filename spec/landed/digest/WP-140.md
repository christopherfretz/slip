# WP-140 — a relocation into a namespace a dependency opens

What was built, after the supervisor's ruling on the phase 1 proposal
(`c3d6524a`; the ruling is §2). Case directories are under
`crates/slip_digest/tests/rules/` unless said.

## 1. The question

```cpp
// dep.h, read-only
namespace acme { struct Dep {}; }
// a.cpp, owned; before
#include "dep.h"
namespace legacy { int g(int); }
int u() { return legacy::g(1); }
// after
#include "dep.h"
namespace acme { int g(int); }
int u() { return acme::g(1); }
```

with `relocate legacy => :: acme`. Before WP-140 the post-image's `acme`
(one read-only opening, so a dependency namespace) had one unit, keyed
`acme`; the owned `g` was keyed under `acme`'s owned view (`legacy`),
which was a parent and no unit. So the pre-image's unit `legacy` had no
partner (`removed legacy`), and the rule was `via 0`: reported `unused`
in a run whose every observer includes `dep.h`, though it mapped every
owned member.

## 2. The ruling: option B

- **A namespace has a unit under the key of each view in which it holds
  something** (as amended by the review's ruling F3, §10). Its own
  ownership's view is its own unit. The other view (owned: the rules
  applied along the chain; dependency: none) exists where an entity that
  is not a namespace is keyed with it as its namespace parent in that
  view, or a nested namespace that itself holds something there. An
  opening alone gives no view. (Phase 2 as first built also made the
  view from an owned opening alone; the review showed that wrong, F3.)
- **One digest.** Every such unit has the namespace's digest: its own
  unit's, over every opening (the `inline` bit and the attributes of the
  whole chain), and its own unit's cause (merged with the view key's,
  which is always the own key's: a guard, §10 F5).
- **A view unit is written only when its key differs from the own key.**
  So a table that maps nothing of the chain adds none, and the dedup of
  `groups::build` is not relied on.
- **No member key or digest changes. The scheme stays 2**: B adds units
  only. A view unit is not always the partner of a pre-image unit (the
  first sentence written here said it was, which was false: an
  untouched observer with an owned using-directive in the dependency's
  `acme` has `added legacy (the owned part of acme)`). The comparisons
  that change: the pre-image's namespace unit with no partner (`removed
  legacy`) gets one, equal when the digests agree and `changed` when
  they do not; a view unit with no partner is `added`, only in an
  observer that already differs (the entity keyed under it has no
  partner either); a view key that is another unit's with another digest
  is a collision, indeterminate. No comparison of a member goes from a
  difference to equal. No baseline of scheme 2 is recorded
  (`spec/digest.md` §11), so the change shares the number.
- **Rejected:** A (a digest per view) and C (one unit compared without
  presence). A would put on one opening what belongs to the namespace;
  the three cases below verify under A and are differences, and they are
  kept as tests with a comment saying they are why the digest is not per
  view: `views/inline-reopened-plain` (`changed legacy::v1`: an owned
  plain reopening of the dependency's inline `acme::v1`, so the owned `g`
  is now found as `acme::g`), `views/deprecated-owned-opening` (`changed
  acme`: the moved opening's `[[deprecated]]` deprecates the
  dependency's `acme`), `views/deprecated-dependency-opening` (`changed
  legacy`: the owned members are now in a deprecated namespace). C loses
  a pre-image `[[deprecated]] legacy` merged into a plain `acme`.
- **Not B+.** An attribute that applies only to the declarations of its
  own opening (`visibility`) is in the one digest, so a correct move of
  such an opening differs: a stated limit that fails closed
  (`views/visibility-owned-opening`, `changed acme`).
- **References keep the namespace's own key, option (ii).** Nothing in
  the post-image says which pre-image namespace an owned reference meant,
  and a reference to a dependency's namespace by the dependency's name is
  what rule 1 already promises. §5.

## 3. The code

- `keys.rs` `namespace_parent`: a member keyed in the view `b` records
  `(namespace, b)` in `OwnedState::member_views` (`owned.rs`), or, for a
  member that is itself a namespace, `(namespace, b, member)` in
  `OwnedState::nested_views`, before keying the namespace in that view. `view_key`, `compute_view_key`: the view's key, through the
  memo `OwnedState::views` and without.
- `units.rs` `view_units`, called by `walk.rs` right after
  `apply_taints` (so the own unit's cause is final) and before the
  collision marking: for each own namespace unit with a key, the other
  view exists if the namespace holds something there (`holds`:
  `member_views`, or `nested_views` down to a namespace that does); its
  key is formed; if it differs from the own key, a copy of the unit is
  written with that key, `view: Some(b)` (`Written::view`), the merged
  cause and `denotes`, the name its key denotes (`denoted`, from the key
  and its parents' keys). A view whose key cannot be formed would make
  the own unit indeterminate (`key/view`): a guard (§10 F5). No rule, no
  work.
- `names.rs` `names`: a view unit is named `<denotes> (the owned part of
  <namespace>)` or `(the dependency's part of …)` (§10 F4).
- `rule_use.rs`: `view_unit` records each namespace with a unit in the
  owned view (`Counting::view_units`); `finish` counts the trace of that
  view's key in `via`, once per namespace entity (also one that has no
  entry of its own). `direct` and `kept_via` are WP-111's, unchanged.
- `records.rs` `key_again`: a view unit's records recompute the key in
  its view (`compute_view_key`, `map_key` with the view).

## 10. Review fix round

The second review (no wrong `verified` from this package) and the
supervisor's rulings on it.

- **F3 (ruled): the owned view exists where the namespace holds
  something.** An untouched observer that opens the dependency's `acme`
  only to specialise its template, or with an empty opening, reported
  `added acme`: the first build made the owned view from an owned opening
  alone. Now a namespace has its other view's unit only where an entity
  that is not a namespace is keyed under it in that view, or a nested
  namespace that itself holds something there (§2, §3). That covers, as
  `docs/wp/WP-141.md` Addendum A4 does, the using-directive, alias,
  using-declaration and `static_assert` written in an owned opening:
  each is keyed by content (or its own key) with the namespace as its
  parent through `parent_in`, so it records the view like a function
  (`views/untouched-directive-in-opening`, `-alias-`,
  `-using-declaration-`, `-static-assert-`; each, untouched, differs, as
  an owned function there does: rule 2). An owned opening holding only
  an empty nested namespace gives no view (`views/untouched-nested-empty`;
  the nested namespace's own unit is keyed under the owned view, rule 2).
  The dependency-view clause by opening could never fire for an owned
  namespace (owned means no read-only opening; review F7) and is gone.
  Consequences: the reviewer's shapes are equal (`views/untouched-empty-opening`,
  `untouched-specialisation`) and Verified in a three-observer run
  (`verify_job.rs`
  `wp140_untouched_observers_that_open_the_dependency_namespace`);
  `views/empty-owned-opening` is `removed legacy` again, a stated limit
  declared as a removal, which `slip declare` takes and which verifies
  (`verify.rs` `wp140_empty_opening_moved_is_a_declared_removal`);
  `owned/owned-forward-then-dependency` has `removed legacy` again (its
  owned opening holds only a dependency entity's forward declaration).
- **F4: a view unit's name.** `<the name its key denotes> (the owned
  part of <namespace>)`, or `(the dependency's part of <namespace>)`:
  `legacy (the owned part of acme)`. One form, from `names::names`, so
  findings, record errors and `slip units` use it. `slip declare` takes
  it: `created old (the owned part of fresh)` exempts the view unit, and
  with the directive moved under it declared the run verifies; `kept`
  of it is accepted (`kept 1`) and exempts nothing (`verify.rs`
