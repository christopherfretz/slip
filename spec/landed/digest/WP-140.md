# WP-140 — a relocation into a namespace a dependency opens

## Proposal

Phase 1 of `docs/wp/WP-140.md`: the design, for the supervisor's ruling.
Nothing here is built. This section is replaced by the record of what
was built.

### 1. The question

```cpp
// dep.h, read-only
namespace acme { struct Dep {}; }
// a.cpp, owned; before
#include "dep.h"
namespace legacy { int g(int); }
int u() { return legacy::g(1); }
// after
#include "dep.h"
namespace acme { int g(int); }
int u() { return acme::g(1); }
```

with `relocate legacy => :: acme`, i.e. `Rule { root, namespace, acme
=> root, legacy }`.

What the walk does today (code, not the spec's words):

- **One entity, one key, one unit.** A namespace is one entity per
  translation unit (Kiln's redeclaration chain of its openings). It is
  owned iff none of its openings lies in a read-only file
  (`Walk::owned`, `owned.rs`: every declaration by expansion location
  and name-token spelling, per inclusion). Its unit is keyed by its own
  key (`Walk::key`, view `None`): mapped if it is owned, unmapped if
  not. In the post-image above `acme` has one read-only opening, so it
  is a dependency namespace and its unit is keyed `acme`.
- **Members see it in their own view** (rule 2, `namespace_parent`):
  the owned `g` is keyed under `key_in(acme, Some(true))`, which applies
  the rule: `legacy::g(int)`, as in the pre-image. That key is the
  parent of `g` and of nothing else; **it is no unit**
  (`OwnedState::views` memoises it, `units::write` never writes it).
- **So the pre-image has the units `legacy` and `acme`, the post-image
  only `acme`**: `removed legacy`.
- **The counts.** `in_owned_view` records the owned view's trace in
  `Counting::views`, which `chain` reads as a level of `g`'s chain
  (WP-111) but `finish` never counts as `via`. The rule is `via 0`; in a
  run whose every observer includes `dep.h` it is reported `unused`
  although it mapped every owned member.
- **What a namespace unit digests** (`decl_scope::namespace_data`,
  `attrs::decl_attrs`, `units::write`): the `DeclNode` rows, the bit
  `inline` ORed over every opening ([namespace.def]: a reopening need
  not repeat it), the attributes of the whole chain (`entity_attrs`
  over `redecls`), no row `enclosing` (digest-kinds §1.7: a namespace
  has no symbol), no location (`loc` is `out`), and the group `tu`
  whatever file opens it first (digest §11). Its members are not listed.
  So today **nothing of a namespace unit depends on which opening comes
  first**, and everything in it is computed over all openings, owned
  and read-only alike.
- **References to a namespace** (a namespace alias's target, a
  using-directive's, a `spelled-nns` `ref`, a reflection) are written
  with its own key (`write_ref` → `Walk::key`, view `None`).

The pre-image is digested under the empty table, where ownership is not
consulted: there every namespace is one unit, whoever opens it.

### 2. The options

Every option keeps rule 1 and rule 2 of `spec/verify.md` §2.1 as they
are: no member's key changes, owned or dependency. They differ only in
what units a namespace has in a walk under rules.

- **D, do nothing.** The user declares `removed legacy` (the comment of
  `rules/owned/dependency-opens-destination` already calls it "a
  declared removal"). Cost: an exemption per namespace level opened by a
  dependency (`removed legacy`, `removed legacy::detail`, …), which also
  exempts the unit `legacy` in observers where it has a partner; the
  rule stays `via 0` and `unused` in every observer that includes the
  dependency; the WP's "Done when" is not met.
- **A, one unit per view, each view digesting its own openings.** A
  namespace with openings of both ownerships is two units: the
  dependency view (unmapped key, the stream of its read-only openings)
  and the owned view (mapped key, the stream of its owned openings).
  Cost: two streams per such namespace; and it puts on one opening what
  belongs to the namespace (below, the `inline` and `deprecated`
  attacks): a fact the dependency's opening gives the whole namespace is
  missing from the owned view's unit, and the reverse.
- **B, one unit per view, one digest (recommended).** A namespace has a
  unit under the key of **each view in which it has an opening or a
  member**; every such unit has the **same digest**, the namespace's as
  today (all openings). Views whose keys are equal are one unit (the
  dedup of digest §11, already built in `groups::build`), so under a
  table that maps nothing of the chain, and always under the empty
  table, nothing changes.
- **B+, B with the per-opening facts left out of the namespace's unit.**
  As B, and the attributes that apply to the declarations of one
  opening rather than to the namespace (`VISIBILITY`, `TYPE_VISIBILITY`)
  are not written in the namespace's unit: each member's row `enclosing`
  already holds what they give it (digest-kinds §1.7 item 3), and a
  namespace has no symbol. Cost: every namespace unit with such an
  attribute changes its digest, in every image.
- **C, one unit, compared without presence.** One unit per namespace
  whose digest holds only what no opening can change, and a namespace
  absent from one image is not a finding. Cost: it changes the
  comparison (`spec/verify.md` §4, outside this package), and loses
  facts: a pre-image `namespace [[deprecated]] legacy` merged into a
  non-deprecated `acme` has no partner to differ from, so the change is
  silent. Rejected.

### 3. What each view is (B, B+)

For a namespace entity `N` of the post-image under a non-empty table:

- **The owned view** exists iff an opening of `N` lies in an owned file
  (`in_owned_file`, per inclusion), or an owned entity is keyed with `N`
  as its namespace parent (rule 2; an owned nested namespace included).
  Its key is `key_in(N, Some(true))`: the rules applied along the
  chain and to `N` itself.
- **The dependency view** exists iff an opening of `N` lies in a
  read-only file, or a dependency entity is keyed with `N` as its
  namespace parent. Its key is `key_in(N, Some(false))`: unmapped.
- `N`'s **own key** is unchanged (owned iff no read-only opening) and is
  what every reference to `N` writes (§6, open point 1).
- The units are keyed by the views' keys; equal keys are one unit. Each
  is in the group `tu`, has `N`'s digest and cause.
- **Members as well as openings**, both ways, because an opening can be
  read-only while its members are owned: owned code that opens the
  dependency's namespace with the dependency's macro (`ACME_BEGIN`, the
  name token `acme` spelled in `dep.h`) has no owned opening, yet owned
  members (`views/dependency-macro-opens-target`); and an owned opening can hold only dependency
  members (a read-only header included inside an owned block,
  `views/owned-namespace-dependency-member`, N34 subject 3).
- **The counts.** The owned view's trace (`Counting::views`) counts
  `via` for the rule that matched it, once per namespace entity, when the
  view exists; `direct` and `kept_via` are WP-111's, unchanged.

**The unit of a namespace that both own** is then: one entity; one
digest, of what the namespace is over all its openings; one key per
ownership that has something in it. The owned view is "what the owned
code calls this namespace in pre-image terms", the partner of `legacy`;
the dependency view is "what the dependency's binary calls it", the
partner of the pre-image's `acme`.

### 5. Attacks on B

The reviewer's question: an edit that moves a declaration between the
owned and the dependency view of a namespace, or between two
namespaces one of which a dependency opens, and `verified`, while the
dependency's binary and the owned code no longer name one entity.

B changes **no member's key**, owned or dependency, and **no unit's
digest**; it adds namespace units, which hold no symbol. So an edit
starts to verify under B only if the one difference today was a
namespace unit with no partner, and that unit now has one: the owned
view of a namespace keyed as the pre-image's namespace was. Every
entity the binaries name is a unit of its own, keyed as before:

- **A dependency's declaration moved into `acme`** (N34): by a
  dependency header included inside the moved block (`n34-include-moved`,
  N34 subject 3) or by a dependency macro that opens the namespace,
  redefined by owned code (`n34-macro-redefined`, N34 `bad`, `bad-2`;
  `owned-forward-then-dependency`). The moved entity is a dependency
  entity, keyed in the dependency view: `acme::Dep` against the
  pre-image's `legacy::Dep`, `removed` and `added` as today. B only
  removes `removed legacy` from the redefined-macro case (its `acme`
  has an owned opening, whose view is `legacy`), and adds a unit `acme`
  to the included-header case (a dependency member of an owned `acme`);
  both stay `mismatch`.
- **An owned declaration moved into a dependency's opening** cannot be
  made without editing a read-only file, except through an owned header
  included inside it, which is read-only per inclusion: a dependency
  entity, keyed in the dependency view, a difference.
- **A dependency's declaration redeclared by owned code in `acme`** (an
  owned function the dependency also declares): one entity with a
  read-only declaration, a dependency entity (rule 1), `removed
  legacy::f` as in N20.
- **Owned code and the binary disagree on a namespace fact.** The
  namespace's `inline` and its attributes are in every view's unit (B),
  so an owned plain reopening of the dependency's inline `acme::v1`
  (`views/inline-reopened-plain`: the owned `g` is now found as
  `acme::g`) differs, as does
  a dependency's `[[deprecated]] acme` now enclosing the owned members
  (`views/deprecated-dependency-opening`), and an owned `[[deprecated]]` opening that makes the
  dependency's `acme` deprecated (`views/deprecated-owned-opening`). Under A, all three verify:
  the reason A is not recommended.
- **The key of a view colliding with another namespace.** Two namespace
  units of one key are merged (§2.1), as today: equal digests are one
  unit, different ones are a difference. The converse case (the
  dependency keeps `legacy`) already merges the owned `acme` onto the
  dependency's `legacy`; B adds nothing there (the dependency's `legacy`
  has no owned view once everything owned has left; with a member left,
  its owned view's key is its own).
- **A member left behind** in `legacy` (`views/member-left`): `direct 1` (WP-111),
  stale, as today.
- **Two observers, one without the dependency** (`views/target-opened-observer-without-dependency`,
  `views/converse-observer-without-dependency`): the owned
  view's key is the same whether or not the observer sees a read-only
  opening, so the observer that includes `dep.h` and the one that does
  not give the same units for the owned part and the same counts.
- **Inert** (WP-131): under a table none of whose rules matches, every
  view's key is the own key, so no extra unit is written at all (a view
  unit is written only when its key differs from the own key; the dedup
  of `groups::build` is not relied on, so no counter sees one).
  `tests/inert.rs` holds unchanged, and now also walks `views/`.

What B cannot decide, and so fails closed (§6): references to a
namespace that has two views.

### 6. Decisions left to the supervisor

1. **Which key a reference to a two-view namespace writes.** A
   using-directive, a namespace alias, a reflection of `acme` in owned
   code: the post-image's `acme` is both the pre-image's `acme` and its
   `legacy`, and nothing in the post-image says which one an owned
   reference meant (`views/alias-redirected`,
   `alias-to-dependency-untouched`, `directive-redirected`,
   `directive-to-dependency-untouched`). Either choice
   refuses one correct edit:
   - **(ii) its own key (today; recommended).** An untouched `using
     namespace acme;` or `namespace A = acme;` in owned code still
     verifies; one redirected from `legacy` to `acme` is a difference
     (`directive-redirected`, `alias-redirected`). Consistent with rule 1 (a dependency entity keeps its
     name), and no code changes.
   - **(i) the referrer's view.** The redirected one verifies, the
     untouched one differs; references are then not the entity's own
     key, which `key_agreement` assumes.
   A redirected using-directive is common in a namespace migration (row
   N08's edit), and with (ii) it cannot be declared (a using-directive
   is keyed by content, so not `changed`). A stated limit with fixtures
   either way; I could not find a sound third answer.
2. **B or B+.** B fails closed on a correct move of an opening with a
   `visibility` attribute into a namespace the dependency opens without
   one (`views/visibility-owned-opening`); B+ verifies it, at the cost of moving every namespace
   digest that has such an attribute. I recommend B now and B+ only if
   a use needs it.

### 7. Item 3: a rule no observer used

§9.2 "Unused rules" already reports a rule whose `via`, `direct` and
`kept_via` are 0 in every observer, as `unused rule <i>` in the report
and `"unused"` in JSON (`Report::unused`, `run.rs`); it changes no
verdict. Decision: **keep it a report line, not a failure.** A rule that
matched nothing in an observer changed nothing there (digest §3.4,
WP-131's invariant), so it cannot be the cause of a `verified`; it says
the declaration names something no observer has (a typo, an observer
set that misses the code). Under B a namespace rule used only through
the owned view of a dependency namespace counts `via`, so `unused` no
longer names a rule that mapped every owned member (today it does,
for `dependency-opens-target-moved` in a run of such observers).
§9.2 gains that sentence and a fixture.

### 8. What moves

- **No digest moves** under B (B+ moves those of namespaces with a
  visibility attribute). Units are added only in a post-image digested
  under a table that maps the chain of a namespace with openings or
  members of both ownerships. Pre-images and map shards are unchanged.
- **The scheme stays 2**: B opens equalities and closes no wrong equal,
  and no baseline of scheme 2 is recorded (digest §11: such changes share
  the current number).
- **Fixtures** (rules suite): `stale/dependency-opens-target-moved`
  (equal, `via 1`), `-kept-moved` (`removed legacy` gone, `via 1
  kept_via 1`: still stale), `owned/dependency-opens-destination` and
  `nested-views` (equal), `owned/n34-macro-redefined` and
  `owned-forward-then-dependency` (`removed legacy` gone, still
  differ), `owned/n34-include-moved` (`added acme` too). Every
  `expect-owned.txt` is unchanged (every file owned: no two views).
  Rows of `rule_use` with a dependency-opened target gain `via`.
- **Pitfall catalogue**: N34 `bad` and `bad-2` lose `removed legacy`
  (if listed), N42 `good-2` stays `verified`; every row of §2 whose
  dependency opens only `legacy` is unchanged (no view key differs).
- **Goldens**: the slip_verify report goldens are built from shards,
  not from parses; none should move. To be confirmed by the gate.
