# WP-140 — a relocation into a namespace a dependency opens

What was built, after the supervisor's ruling on the phase 1 proposal
(`c3d6524a`; the ruling is §2). Case directories are under
`crates/slip_digest/tests/rules/` unless said.

## 1. The question

```cpp
// dep.h, read-only
namespace acme { struct Dep {}; }
// a.cpp, owned; before
#include "dep.h"
namespace legacy { int g(int); }
int u() { return legacy::g(1); }
// after
#include "dep.h"
namespace acme { int g(int); }
int u() { return acme::g(1); }
```

with `relocate legacy => :: acme`. Before WP-140 the post-image's `acme`
(one read-only opening, so a dependency namespace) had one unit, keyed
`acme`; the owned `g` was keyed under `acme`'s owned view (`legacy`),
which was a parent and no unit. So the pre-image's unit `legacy` had no
partner (`removed legacy`), and the rule was `via 0`: reported `unused`
in a run whose every observer includes `dep.h`, though it mapped every
owned member.

## 2. The ruling: option B

- **A namespace has a unit under the key of each view in which it has an
  opening or a member.** The owned view (the rules applied along the
  chain) exists if one of its declarations lies in an owned file
  (`Walk::in_owned_file`, per inclusion) or an owned entity is keyed with
  it as its namespace parent; the dependency view (no rule) if one of its
  declarations does not, or a dependency entity is keyed under it. Its
  own ownership's view is its own unit.
- **One digest.** Every such unit has the namespace's digest: its own
  unit's, over every opening (the `inline` bit and the attributes of the
  whole chain), and its own unit's cause, merged with the view key's.
- **A view unit is written only when its key differs from the own key.**
  So a table that maps nothing of the chain adds none, and the dedup of
  `groups::build` is not relied on.
- **No member key or digest changes. The scheme stays 2**: B adds units
  only, each the partner of a unit the pre-image already has; it makes
  equal what was a namespace unit with no partner, and no comparison that
  was a difference for a member becomes equal. No baseline of scheme 2
  is recorded (`spec/digest.md` §11), so the change shares the number.
- **Rejected:** A (a digest per view) and C (one unit compared without
  presence). A would put on one opening what belongs to the namespace;
  the three cases below verify under A and are differences, and they are
  kept as tests with a comment saying they are why the digest is not per
  view: `views/inline-reopened-plain` (`changed legacy::v1`: an owned
  plain reopening of the dependency's inline `acme::v1`, so the owned `g`
  is now found as `acme::g`), `views/deprecated-owned-opening` (`changed
  acme`: the moved opening's `[[deprecated]]` deprecates the
  dependency's `acme`), `views/deprecated-dependency-opening` (`changed
  legacy`: the owned members are now in a deprecated namespace). C loses
  a pre-image `[[deprecated]] legacy` merged into a plain `acme`.
- **Not B+.** An attribute that applies only to the declarations of its
  own opening (`visibility`) is in the one digest, so a correct move of
  such an opening differs: a stated limit that fails closed
  (`views/visibility-owned-opening`, `changed acme`).
- **References keep the namespace's own key, option (ii).** Nothing in
  the post-image says which pre-image namespace an owned reference meant,
  and a reference to a dependency's namespace by the dependency's name is
  what rule 1 already promises. §5.

## 3. The code

- `keys.rs` `namespace_parent`: a member keyed in the view `b` other
  than its namespace's own records `(namespace, b)` in
  `OwnedState::member_views` (`owned.rs`) before keying the namespace in
  that view. `view_key`, `compute_view_key`: the view's key, through the
  memo `OwnedState::views` and without.
- `units.rs` `view_units`, called by `walk.rs` right after
  `apply_taints` (so the own unit's cause is final) and before the
  collision marking: for each own namespace unit with a key, the other
  view exists by member (`member_views`) or by opening (some declaration
  of the chain, within `REDECL_LIMIT`, in that view's ownership); its key
  is formed; if it differs from the own key, a copy of the unit is
  written with that key, `view: Some(b)` (`Written::view`) and the merged
  cause. A view whose key cannot be formed makes the own unit
  indeterminate (`key/view` when no cause is given). No rule, no work.
- `rule_use.rs`: `view_unit` records each namespace with a unit in the
  owned view (`Counting::view_units`); `finish` counts the trace of that
  view's key in `via`, once per namespace entity (also one that has no
  entry of its own). `direct` and `kept_via` are WP-111's, unchanged.
- `records.rs` `key_again`: a view unit's records recompute the key in
  its view (`compute_view_key`, `map_key` with the view).

## 5. References to a namespace: the stated limit

A reference to a namespace writes its own key (`refs.rs` `write_ref`,
`types.rs` `write_canonical_nns`), so after the move an owned reference
redirected from `legacy` to `acme` writes the dependency's `acme`, and
its unit differs from the pre-image's, which wrote `legacy`. Every site
that writes a namespace as a reference (all paths to `write_ref` and to
the namespace level of `write_canonical_nns`), with the fixture under
`views/`:

| Site | Holding unit | Keyed | Per unit | Redirected: reported | Declarable today |
|---|---|---|---|---|---|
| A namespace alias's target (`decl.rs` `decl_data`) | the alias | its own key | 1 | `changed L` (`alias-redirected`) | `changed L`: verifies (tested) |
| A using-directive's target (`decl.rs` `decl_data`) | the directive | content (the target is the key) | 1 | `removed <using_directive legacy>`, `added <using_directive acme>` (`directive-redirected`) | the removal and `created <using_directive acme>`: verifies (tested) |
| A using-declaration's qualifier (`keys.rs`, the key of a using-declaration) | the using-declaration | content | 1 | `removed <using legacy::g>`, `added <using acme::g>` (`using-declaration-redirected`) | the removal and `created`, as for a directive (not tested) |
| A qualifier in a body, of a name not resolved at the definition (`templ.rs` expression qualifiers, `expr_dep.rs` dependent-scope references, `expr.rs` member-overload qualifiers) | the function | its own key | any number | `changed template <class> int f(type-parameter-0-0)` (`qualifier-dependent-overloaded`: two `h`) | `changed` of the function (not tested) |

| A qualifier in a signature's profile (`expr_profile.rs` `nns_opt`) | the function, whose key holds the profile | content of the key | any number | `removed`/`added template <class> decltype(legacy::h(t)) f(…)` (`profile-qualifier-overloaded`); with one `h`, equal (`profile-qualifier-redirected`) | the removal and `created` of the signature (not tested) |
| A qualifier in a type (dependent name, dependent template specialisation, dependent template name: `types.rs`) | whatever unit writes the type | as that unit | any number | differs where the namespace level is written; a level that is a type writes the type, and it is equal (`dependent-type-redirected`, `member-qualifier-spelled`) | as the holding unit |

`crates/slip_cli/tests/verify.rs` `wp140_redirected_references_declared`:
a relocation with an alias and a using-directive redirected is
`not_verified` with `changed L` and the two directives; declared
`changed L`, `removed <using_directive old>`, `created <using_directive
fresh>`, it verifies with `rules 1 stale 0 unused 0`. Each declaration
is per unit, so the cost grows with the references, not with the
namespaces. The motivating migration meets this wherever owned code
aliases the moved namespace, has a `using namespace` of it, or
qualifies a name with it that is not resolved at the definition. Open:
`spec/verify.md` "Open questions", "References to a namespace that two
views key".

## 6. Item 3: a rule no observer used

`unused` stays a report line (`spec/verify.md` §9.2): a rule that
matches nothing changes no key, so it cannot make a comparison equal.
Under B a rule used only through the owned view counts `via`
(`stale/dependency-opens-target-moved`: `via 1`, before 0; and the two
observers of `verify_job.rs`: no `unused`).

## 7. Pitfall row N46

`crates/slip_verify/tests/pitfalls/n46-move-into-a-namespace-a-dependency-opens/`,
`spec/pitfalls.md` §2: the move, nested, the dependency's inline
`acme::v1` (`good-3: none`), a member left declared `kept`, and `dep/`
also opening `legacy` verify; the `[[deprecated]]` opening and the move
into the inline namespace are `mismatch`. Not rows, and why: a member
left with no `kept` is the run's stale check (verdict `not_verified`,
the observer `verified`), which the catalogue has no line for
(`views/member-left`); a tree that edits `dep/` is refused (`dep/` must
not differ), so a dependency's declaration moved into `acme` stays
row N34's macro shape (`owned/n34-*`, which still differ).
