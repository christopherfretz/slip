# WP-104 — values that come from names; qualified arguments in names

What `crates/slip_digest` does for digest §9 (as corrected here) and for
`spec/verify.md` §6.1's names of specialisations, where the specs left it
open. Kiln references are at the pinned Kiln (`kiln/` in the checkout).

## What Kiln's values hold

| Construct | Kiln | What the value holds |
|---|---|---|
| `__func__`, `__FUNCTION__` | `kiln_sema/src/predefined.rs:29-42`, `compute_predefined_name` `:70-84` | the unqualified name (`names.write_name`); a conversion function's names its type as stored, canonical (`operator Widget` for `operator Handle()`; `kiln_ast/src/dump/names.rs:187-198`) |
| `__PRETTY_FUNCTION__` | `predefined.rs:83`, `kiln_ast/src/dump/pretty.rs:57-130` | `virtual`/`static`, the qualified name with the scopes' arguments canonical and scoped, the parameter types of the pattern **as written** (`:152`, `PrintOptions::SUGARED`), cv and ref qualifiers, `[T = …]` (canonical arguments, plain names), the return type **as written** (`:116`, `:125`); a lambda's `auto`; an unnamed tag with its location |
| `std::source_location::current()`, `__builtin_source_location()` | `kiln_sema/src/builtins.rs:3612` `record_source_loc`, `:3680` `srcloc_string`, `:3752` `source_location_object` | one string object per content (`frozen_string`, a `StringLiteral` with no parent), and an `__impl` object pointing to the file and the **pretty** function name; `:3660` `finish_source_locs` refreshes a deduced return type |
| `function_name()` | `builtins.rs:3628`, `:3835` `predefined_function_names` | `__PRETTY_FUNCTION__`'s text |
| `__builtin_FUNCTION()` | `builtins.rs:3626` | `__func__`'s text |
| a dependent context | `predefined.rs:24-28` | no literal (`a` absent), the type dependent; instantiation builds it again (`templ/subst/exprs.rs:488`) |

The literal is the expression before its `PredefinedExpr` and is named by
its `a`, which Kiln itself relies on (`kiln_sema/src/templ/args.rs:2022`
`predefined_of`); the walk checks both. The Oven evaluates a
`PredefinedExpr` as that literal (`kiln_oven/src/compile.rs:5960`).

## What is written

| Construct | Before | Now |
|---|---|---|
| `PredefinedExpr` `ty`, the operand of an implicit `ArrayToPointerDecay` | `const char[N]` by value | `const char[]` (digest-kinds §4.2 rule 8; `expr_core.rs` `cast` pushes `Item::Decayed`, `expr_misc.rs` `name_type`, `types.rs` `unbounded_array`) |
| `PredefinedExpr` `ty` anywhere else (`sizeof`, `alignof`, `decltype`, `typeid`, `__typeof__`, a trait, a reference or `auto &` bound to it, a deduced bound, a range-`for`, a kept parenthesis) | by value | by value |
| `PtrBase::StringLit` to a `PredefinedExpr`'s string | the bytes | `bytes` empty, `uv 0`, `uv 1`, the `PredefinedKind` tag (`value.rs` `write_name_string`) |
| `PtrBase::StringLit` to a source-location string | the bytes | `bytes` empty, `uv 0`, `uv 2` |
| `PtrBase::Const` to an `__impl` object | its content | `H(VALUE_TAG, uv 0, uv 3, type)` (`location_digest`) |
| `Pointer.designated` into a name string | `const char[N]` | `const char[]` |
| any of these in a key, a type, a block-scope variable's value, a `static_assert` condition, the operand of a `ConstantExpr` with no stored value | — | by value (`Walk::by_value`: `keys.rs` `compute_key`, `types.rs` `type_digest`, `decl_func.rs` `var_data`, `decl_scope.rs` `static_assert_data`, `expr_core.rs` `constant`); content digests in that mode are memoised apart (`const_memo_by_value`) |
| a block-scope variable's evaluated value (`VarData` `eval`) | not written anywhere | `value?` in its stream, by value (digest-kinds §11.3) |
| `SourceLocExpr.a`, `SourceLocValues` | symbolic (WP-057) | unchanged |

Why a block-scope variable's value: `unsigned long f() { constexpr
unsigned long n = len(__PRETTY_FUNCTION__); return n; }` returns 16 under
`legacy` and 14 under `acme`, the use of `n` is `non_odr_use_constant`,
and no stream held the number. It is written by value, so `constexpr auto
l = std::source_location::current();` at block scope is a spurious
difference under a relocation, never an equal (the brief's rule). A
namespace-scope variable's `value` unit stays symbolic: each use stores
its own result.

Why keys and types: two `C<std::source_location::current()>` are two
specialisations; a symbolic argument made them one key (a collision,
`equal/_/name-value-source-location-template-arguments`).

## Left indeterminate, and known wrong equals

- Nothing new is indeterminate: where the walk could not tell a
  pass-through from a consumer it writes by value.
- **Known wrong equal** (`differ/_/name-value-pretty-alias-parameter`,
  `…-pretty-alias-return`, `…-source-location-alias-parameter`, pending,
  `# needs: WP-041`): `const char *f(Widget)` against `const char
  *f(Handle)` with `using Handle = Widget`, the body `return
  __PRETTY_FUNCTION__;` (or `function_name()`): Kiln's strings are
  `const char *f(Widget)` and `const char *f(Handle)`, the digest says
  equal. The symbolic write must hold the enclosing function's parameter
  and return types with the sugar Kiln prints (entities by key, so a rule
  maps them); that is the unit's own spelling, WP-041's. Before this
  package the same respelling was equal whenever the two spellings had
  one length.
- A local class or a closure type as an argument prints without its
  function (`legacy::store<Local>`); two such specialisations collide by
  key today (`Area::Local`, the local package's), so their names cannot
  be told apart either.

## N18 by hand

The three shapes of `crates/slip_verify/tests/pitfalls/n18-names-as-values`
(`pre`/`good`, `pre-2`/`good-2`, `pre-3`/`good-3`), digested in process
with `dep.h` beside the main file, side B under the rule of
`relocate legacy => :: acme`: all three are equal, digests and all
(`where()` and `user()` have one digest on both sides; `void
legacy::where()` and `void acme::where()` have two lengths, which the
decayed operand no longer writes). `cargo test -p slip_verify` passes.

## The test harness

`tests/common/mod.rs`: side B of a pair is digested under the rules of
the directory's `relocate.txt`: `relocate <a> => :: <b>` (a namespace) and
`rename <record> => <a>` (the entity side B's record names `<record>`,
its rule made from that record's key: a function's discriminator is only
in a parse). `relocate.txt` is not a source file.

## Mutations

Each made alone, `cargo test -p slip_digest --test equal --test differ`,
then `git checkout`.

| Mutation | Result |
|---|---|

| non-decayed type symbolic | killed: `differ/_/name-value-sizeof-body`, `-alignof`, `-new-array` |

| `ConstantExpr` with no value symbolic | survives: no non-dependent `ConstantExpr` without a stored value holding a name-derived constant was found; the guard is kept as the safe default |

## Part 2: qualified arguments in names

`names.rs` prints a specialisation's arguments with Kiln's
`write_arg_list_scoped` (`kiln_ast/src/types/print.rs:596`) and a
specialisation in a scope with `AstNames::scoped_spec_args`
(`kiln_ast/src/dump/names.rs:415`), the policy Kiln's own
`__PRETTY_FUNCTION__` uses (`predefined.rs:77`). No wrapper was needed:
declarations (`&legacy::fn`, `&legacy::S::m`), enumerators
(`legacy::F::Y`), templates (`legacy::store`) were qualified already;
types, packs and nested specialisations now are
(`names::tests::specialisation_arguments_are_qualified`,
`local_class_argument`; `equal/_/names-qualified-arguments` for
`keys_and_names_are_unique`). No expectation line of the pair tests
moved; N06's line (`legacy::store<legacy::Mine>::put(legacy::Mine &)`)
is what the walk prints.

## Spec changes

- `spec/digest.md` §9, corrected: the array type is symbolic only where
  the array is converted to a pointer; the list of consumers; constants
  computed from names; where a name-derived value is written by value
  (keys, types, block-scope values, `static_assert`, a `ConstantExpr`
  with no value); `__PRETTY_FUNCTION__` and `function_name()` hold the
  written signature, a known wrong equal until WP-041.
- `spec/digest-kinds.md`: §4.2 rule 8 (name-derived arrays); the
  `PredefinedExpr.a` note; the symbolic forms under `PtrBase`; `VarData`
  `eval`'s note and §11.3's paragraph on block-scope variables.
