# WP-104 — values that come from names; qualified arguments in names

What `crates/slip_digest` does for digest §9 (as corrected here) and for
`spec/verify.md` §6.1's names of specialisations, where the specs left it
open. Kiln references are at the pinned Kiln (`kiln/` in the checkout).

its `a`, which Kiln itself relies on (`kiln_sema/src/templ/args.rs:2022`

`PredefinedExpr` as that literal (`kiln_oven/src/compile.rs:5960`).

## What is written

| Construct | Before | Now |
|---|---|---|
| `PredefinedExpr` `ty`, the operand of an implicit `ArrayToPointerDecay` | `const char[N]` by value | `const char[]` (digest-kinds §4.2 rule 8; `expr_core.rs` `cast` pushes `Item::Decayed`, `expr_misc.rs` `name_type`, `types.rs` `unbounded_array`) |
| `PredefinedExpr` `ty` anywhere else (`sizeof`, `alignof`, `decltype`, `typeid`, `__typeof__`, a trait, a reference or `auto &` bound to it, a deduced bound, a range-`for`, a kept parenthesis) | by value | by value |
| `PtrBase::StringLit` to a `PredefinedExpr`'s string | the bytes | `bytes` empty, `uv 0`, `uv 1`, the `PredefinedKind` tag, `ref` of the function whose name it holds: the innermost function whose compound body holds the `PredefinedExpr` and whose name of that kind (printed again with Kiln's printer, `value.rs` `is_kiln_name`) the bytes are; else the bytes (`value.rs` `name_string`, `write_name_string`) |
| `PtrBase::StringLit` to a source-location function name (`SourceLocValues` `function`, or the pretty name an `__impl` object points to) | the bytes | `bytes` empty, `uv 0`, `uv 2`, `uv 0` plain or `uv 1` pretty, `ref` of the context of the first use pointing to it (`ExprId` order), if the bytes are that context's name of that kind; else the bytes |
| `PtrBase::StringLit` to a source-location file name | the bytes | the bytes (no declared rename changes a file name) |
| `PtrBase::Const` to an `__impl` object | its content | `H(VALUE_TAG, uv 0, uv 3, type)`, `ref?` of the function of the use that built it (`Ref::none` outside one), `uv` the use's ordinal among that function's uses that build one (among all non-function contexts' outside one), `ExprId` order (`write_location`) |
| `Pointer.offset` into a name string | by value | by value |
| `Pointer.designated` into a name string | `const char[N]` | `const char[]` |
| any of these in a key, a type, a `static_assert` condition, the operand of a `ConstantExpr` with no stored value | — | by value (`Walk::by_value`: `keys.rs` `compute_key`, `types.rs` `type_digest`, `decl_scope.rs` `static_assert_data`, `expr_core.rs` `constant`); content digests in that mode are memoised apart (`const_memo_by_value`) |
| a block-scope variable's evaluated value (`VarData` `eval`) | not written anywhere | `value?` in its stream, in the function's mode (digest-kinds §11.3); a `DeclRefExpr` naming it where `by_value` is raised is followed by `value?`, by value (`expr_core.rs` `local_value`) |
| `SourceLocExpr.a`, `SourceLocValues` | symbolic (WP-057) | unchanged |

Why a block-scope variable's value: `unsigned long f() { constexpr
unsigned long n = len(__PRETTY_FUNCTION__); return n; }` returns 16 under
`legacy` and 14 under `acme`, the use of `n` is `non_odr_use_constant`,
and no stream held the number. The value is written with the
declaration in the function's mode: a number computed from a name is a
number in either mode, and a pointer to a name passes it on
(`constexpr const char *p = __PRETTY_FUNCTION__; take(p);`,
`static constexpr auto loc = current();` are equal under a relocation,
`equal/_/name-value-local-constexpr-pointer`, `-local-static-location`).
Where a use is read by value, the use writes the value by value, so the
consumer carries the cost (`differ/_/name-value-local-pointer-static-assert`,
`-source-location-static-assert`). A namespace-scope variable's `value`
unit is in the function's mode too; each use stores its own result.

Why the identity of the object (review F1): a compile-time computation
that consumes a name or a line and returns one of two strings or
objects (`consteval const char *pick(const char *p) { return p[0] ==
'f' ? n1() : n2(); }`) made a different program equal when every such
string was written as its builtin alone. Why the name check: a string is
written as `(kind, entity)` only where its bytes are Kiln's name of that
kind for that entity, so two strings written alike hold the names of
one entity on the two sides, mapped by the rules, and differ by nothing
but what §9 leaves out of the digest, whichever function the lookup
picked; where the lookup finds no such entity, or two of one extent
(the `__func__` of two instantiations), the bytes are written, a
spurious difference at worst. A file name is written by its bytes: no
declared rename changes it, and an object some use points to as a file
name is never a function name.

Why keys and types: two `C<std::source_location::current()>` are two
specialisations; a symbolic argument made them one key (a collision,
`equal/_/name-value-source-location-template-arguments`).

## Left indeterminate, content left out by §9, and pending tests

- Nothing new is indeterminate: where the walk could not tell a
  pass-through from a consumer it writes by value.
- **Content left out by §9** (the coordinator's ruling on review F2):
  what `__PRETTY_FUNCTION__` and `function_name()` print beyond entity
  names (an alias as written, an elaborated keyword, a qualifier as
  written, a template parameter's name) is the string's content; where
  the string is only passed on it is equal in the unit digest by the
  rule, not by a defect. WP-112 adds the informational digest of the
  bytes that tells them apart. Its six pairs, pending with `# needs:
  WP-112` (each `expect.txt` says the unit digests are equal by §9 and
  the names digest must differ), for WP-112 to turn into tests of that
  digest: `differ/_/name-value-pretty-alias-parameter`,
  `-pretty-alias-return`, `-source-location-alias-parameter`,
  `-pretty-elaborated`, `-pretty-qualified`,
  `-pretty-template-param-name`.
- **Pending, so not evidence** (review F4): `equal/_/name-value-lambda`
  (`# needs: WP-040`: `legacy::f()` is `Pending(Local)` on both sides)
  and `equal/_/name-value-implicit-instantiation` (`# needs: demand`:
  `g<long>(long)` is `Pending(Demand)`); the explicit instantiation stays
  in `equal/_/name-value-template-instantiation`. The equal tests that do
  exercise a symbolic write are those a mutation of one kills (below,
  "Which equal tests exercise a symbolic write").
- `__FILE__`, `__LINE__`, `__COUNTER__`, `__DATE__`, `__TIME__`: §9's
  second list stays unimplemented, its literal and its type (`const
  char[M]` for a `__FILE__` of another length) written by value
  (digest-kinds "Literals from builtin macros"): Kiln's AST does not say
  that a `StringLiteral` or `IntegerLiteral` came from a builtin macro.
  This errs to a spurious difference (a moved file, a moved line), never
  an equal; it is for the next batch to Kiln.
- A local class or a closure type as an argument prints without its
  function (`legacy::store<Local>`); two such specialisations collide by
  key today (`Area::Local`, the local package's), so their names cannot
  be told apart either (left out of `equal/_/names-inline-namespace-unnamed-arguments`).
- `const_memo_by_value` has no test: a constant of the store reached by
  `PtrBase::Const` that holds a name-derived pointer, in both modes, was
  not found (the `__impl` object is written by its identity in one mode
  and never memoised there). The split is kept: without it a content
  digest computed in one mode would be read in the other.
- "Types symbolic" and "`ConstantExpr` with no value symbolic" have no
  reachable case today (a `__func__` in a generic lambda is dependent,
  with no literal): revisit when WP-040 walks lambdas.

## Part 2: qualified arguments in names

`names.rs` prints a specialisation's arguments with Kiln's
`write_arg_list_scoped` (`kiln_ast/src/types/print.rs:596`) through a
`TypeNames` wrapper (`TypedNull`) that, with the walk's names, writes
every entity an argument or a parameter type names as the walk
qualifies it (`Names::qualified`): every enclosing namespace, an inline
one too (Kiln's `write_scope_chain` and `append_scope` leave inline
namespaces out, `kiln_ast/src/dump/names.rs:404`, `:552`), each class in
the scope with its arguments, and an unnamed class or enumeration by its
key (`(anonymous struct for u1)`, where Kiln prints
`legacy::(unnamed struct)`). A unit's own name is built the same way
(`legacy::v2::Mine`, `spec/verify.md` §6.1). `display_name`, which has
no walk, prints as Kiln does. Tests:
`names::tests::specialisation_arguments_are_qualified`,
`local_class_argument`, `walk_names_inline_namespace_and_unnamed_arguments`;
`equal/_/names-qualified-arguments` and
`equal/_/names-inline-namespace-unnamed-arguments` (the reviewer's
source without its closures) for `keys_and_names_are_unique`. No
expectation line of the pair tests moved, no verdict moved; N06's line
(`legacy::store<legacy::Mine>::put(legacy::Mine &)`) is what the walk
prints.
