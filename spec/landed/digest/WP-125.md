# WP-125 — a consumed `__PRETTY_FUNCTION__` in a function template whose signature is respelled

What `docs/wp/WP-125.md` found about WP-041's G3 and its neighbours, and
the pairs that pin it. Normative text: `spec/digest.md` §9. Kiln
references are at the pinned Kiln (`kiln/` in the checkout); clang is
clang 19.1.7 (`clang++-19`, the only clang on the host); Kiln parses at
its default `-fclang-compat=22`. Pair directories are under
`crates/slip_digest/tests/`.

## Item 1: neither defect; the pending pair's expectation was wrong

The G3 source, `template <class T> unsigned long h(T,
decltype(ns::S::value)) { return sizeof(__PRETTY_FUNCTION__); }` against
`decltype(::ns::S::value)`, with `h(1, 1)`:

- **Kiln's strings are clang's.** Under Kiln, `static_assert(h(1, 1) ==
  N)` holds with clang's values on each side (a probe pair, not kept,
  whose constexpr `h` returned `sizeof(__PRETTY_FUNCTION__)`; a
  `static_assert(false, msg)` with a C++26 message printed the strings).
  Kiln and clang both print `unsigned long h(T, decltype(ns::S::value))
  [T = int]` (53 bytes with the NUL) and `unsigned long h(T,
  decltype(::ns::S::value)) [T = int]` (55).
- **The digest writes them.** The instantiation's `PredefinedExpr` has
  Kiln's literal and the type `const char[53]` against `const char[55]`;
  `sizeof` reads the array's type, which `expr_misc.rs` `name_type`
  writes by value (not decayed), in `h<int>(int, int)::<definition>`.
  That derived unit differs, and the string itself, left symbolic beside
  its length, is fed to `h<int>(int, int)`'s names digest. The pattern's
  `__PRETTY_FUNCTION__` is dependent (Kiln makes no literal for it,
  `kiln_sema/src/predefined.rs:17-18`): the pattern holds no string and
  is rightly equal.
- **Why it looked like nothing changed.** The `differ` runner ignores a
  derived unit that differs unless a line names it
  (`common::pairs::differ`); the pending pair expected `changed` on the
  pattern, which §9 does not ask for. WP-112 had found the same
  (`docs/wp/WP-112.md` "G3 (for WP-125)",
  `differ/_/name-value-template-pretty-written-read`).

So the pair `differ/_/name-value-pretty-template-written-qualifier` is
un-pended with `exact derived`, `derived-changed h<int>(int,
int)::<definition>` and `names-changed h<int>(int, int)`. No change in
`crates/slip_digest/src/`, so no mutation: there is no symbolic writing
to restore. `spec/digest.md` §9 needs no new case.

**The pattern of the source-location pair differs.** The bound's call
`current()` uses its default `__builtin_source_location()`; Kiln records
the values at that use in the pattern too, with the pattern's own name
(`unsigned long h(T, decltype(ns::S::value))`, no `[T = int]`;
`kiln_sema/src/builtins.rs` `note_default_arg_use` marks the use
instantiation-dependent but keeps its values). The use is inside a type,
where the walk writes by value, so by the by-value bullet of §9
"Defaults at a use" the reached builtin is written as (c), with that
name's bytes: the pattern's unit differs. This is the rule as written,
and the instantiation differs anyway, so it is no wrong verdict; but
clang evaluates nothing there (a `static_assert(len(...) == 999)` in an
uninstantiated template is accepted by clang 19 and by Kiln, so Kiln
does not evaluate the bound itself either). Inferred from the rule and
the dump of both sides, not traced in the walk. Open point below.

**WP-112's two second-round mechanisms.** The last pair is where a
local type inside a constant evaluation (`local_type`'s save, zero and
restore of `in_constant`) would have shown a consumed value written
symbolically: it does not, `f` and `h<int>`'s definition differ. No
pair of this package reached a default whose memoised reach differs
between uses. Neither effect was seen; the reviewer's attack is not
done here.

## Open points

- A default's use in a dependent context carries Kiln's values of the
  pattern (above), so a pattern whose bound, key or type reaches a
  source-location default differs under any respelling of its own
  signature, a difference clang's model does not have. Whether the walk
  should treat a use Kiln marked instantiation-dependent as (d) is the
  coordinator's to rule; this package left the rule as it is.
- The names report for the lambda and local-class shapes cannot note
  the respelling until For Kiln 1 is done.
