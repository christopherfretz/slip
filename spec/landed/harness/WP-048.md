# WP-048 — module units in snippets: what Kiln's front end allows

Landed behaviour of `docs/wp/WP-048.md`. Case **(b)** was taken: Kiln at
the pin (`913a490bb`) imports a named module only from a file on the
host's disk. The request is
[`docs/requests/KF5-module-sources-in-memory.md`](../../../docs/requests/KF5-module-sources-in-memory.md);
the pair tests that need it are written and marked `# pending` /
`# needs: kiln`. `slip_kiln` is not changed.

## Step 1: how Kiln's front end takes a module from source

Line references are to Kiln at the pin (`kiln/` in this repository).

1. **In the same process, from source, with no module file.** A unit that
   imports a named module builds it in-process from its interface source,
   with the same `Preprocessor`, parser, Sema and `Ast` as the importer,
   its tokens spliced in at the import (Kiln `spec/modules.md` §1, lines
   11-19). Nothing is written to disk for it: a module file is written only
   under `--precompile` / `-fmodule-output` (`ModuleOptions::record`,
   `kiln_driver/src/pp_cmd.rs:551-555`).
2. **The source is found by path, on disk, never through the
   `IncludeResolver`.** `Preprocessor::import_module`
   (`kiln_pp/src/modules.rs:773`) asks `find_module_where`
   (`modules.rs:720`), which returns a `PathBuf` from
   `ModuleOptions::module_files` (`modules.rs:723`; the
   `-fmodule-file=<name>=<path>` list, `modules.rs:31-33`), then from the
   prebuilt paths by `Path::is_file` (`modules.rs:727-733`), then from the
   paths a module file read so far recorded, then libc++'s `std` directory.
   The path is then opened twice on the host's file system: `bmi::sniff`
   (`modules.rs:792`, `kiln_pp/src/bmi.rs:628-630`, `std::fs::File::open`)
   to tell a module file from a source, and `SourceManager::load_file`
   (`modules.rs:824`; `kiln_source/src/manager.rs:791`, which ends in
   `fs::File::open` at `manager.rs:854`). There is no hook between the two
   and no lookup among the buffers already in the source manager:
   `add_virtual` buffers are "never deduplicated" and not found by path
   (`manager.rs:883-887`). A module file found the same way is read with
   `bmi::read_file` (`modules.rs:809`), also from disk; the one in-memory
   entry, `Preprocessor::enter_main_capsule(path, bytes)`
   (`modules.rs:1209`), is for the main input, not an import.
3. **`module m;`** (an implementation unit) imports `m`'s primary
   interface through the same `import_module` (Kiln `spec/modules.md` §3,
   "Performing an import"; [module.unit]/8), so it needs the same path.
4. **The library entry reaches that path, with the files of the command
   line.** `kiln_driver::front_end::run_front_end`
   (`kiln_driver/src/front_end.rs:281`) runs `run_here`
   (`front_end.rs:552`), which runs the `-fsyntax-only` job
   (`SyntaxJob(job).run_hooked`, `front_end.rs:581`); the job's
   preprocessor gets `module_options` (`pp_cmd.rs:526-560`, used at
   `pp_cmd.rs:750`) built from `Args::module_files` as `PathBuf`s
   (`pp_cmd.rs:532-533`). So `slip_kiln::parse_observer_with`
   (`crates/slip_kiln/src/parse.rs`, `run_front_end` at its line 271)
   would import a module named by `-fmodule-file=` in a compile command,
   from disk. The snippet front end does not use the entry: it drives
   `kiln_pp` and `kiln_parse` itself (`crates/slip_kiln/src/snippet.rs`,
   `front_end`), with `ModuleOptions::default()` from C++20
   (`snippet.rs:626-628`), so an `import m;` or `module m;` is `fatal
   error: module 'm' not found` (checked at the pin).
5. **Header units are different: they are found through the
   `IncludeResolver`.** `import "h.h";` and `import <h.h>;` resolve the
   header with `resolve_include` (`modules.rs:683`, `:699`), which asks
   the preprocessor's resolver (`modules.rs:1316`): in a snippet, the
   snippet's own in-memory files. The unit is then built from that buffer
   (`import_header`, `modules.rs:1423`, `begin_unit`). At the pin a
   snippet already imports a header unit from memory: `import "h.h";`
   gives unit 1 of kind `Header`, key `"h.h`, its macros visible after the
   import, and no diagnostic. But on the way `import_header` asks
   `header_unit_file` (`modules.rs:1472`), which computes
   `header_unit_key(sm.file_name(file))` (`modules.rs:1477`) before it
   looks for a header-unit module file, and `header_unit_key` calls
   `std::fs::canonicalize` on the buffer's name (`modules.rs:1636-1638`):
   for a snippet buffer `h.h`, a lookup of `<working directory>/h.h` on the
   host. The answer is used only to find a module file among
   `module_files` (empty in a snippet), so it does not change the parse;
   it is still a read of the host's file system (metadata), which a snippet
   must not do. Reported to Kiln (KF5 §4).

**Case.** Not (a): no file loader `slip_kiln` controls is asked for a
named module. Not (c): the adapter cannot run a second front end for the
interface and hand it over, because an import is the imported unit's
tokens spliced into the importer's own preprocessor and `Ast` (item 1),
and the only hand-over Kiln has, a module file, is read from disk
(item 2). So (b): no module file is written from a test.

## What this package changed

- **Nothing in `slip_kiln`.** `Snippet` keeps its four fields; a snippet
  with or without modules parses exactly as before (`git diff main --
  crates/slip_kiln` is empty), and the goldens do not move.
- **The pair runner reads `// module: <name>=<file>`**
  (`crates/slip_digest/tests/common/mod.rs`, `Header::modules`): a header
  line that may be given once per module unit, the name a module name (an
  identifier or identifiers joined by `.`, then optionally `:` and a
  partition of the same form), the file another file of the test
  directory (not `t.cpp`, `a.cpp`, `b.cpp`, `expect.txt`, `side.h`), a
  name or a file at most once. A malformed line, a name twice and a file
  twice are errors of the test, as for the other keys. `Header::line`
  shows each as `-fmodule-file=<name>=<file>`. A side whose header names a
  module unit is an `Err` of `digest_side_with`, naming KF5, until the
  snippet front end can import one; the line is read now so that the
  pending tests are checked for form and need no edit when it can.
- **Pending pair tests**, `# pending` and `# needs: kiln`. Those with a
  `// module:` line are listed under `UNPARSED` of
  `tests/determinism/keys.rs`, per side (the key sweep digests pending
  directories too, and these sides do not digest):
  - `differ/UnitKind/Implementation`
  - `differ/UnitInfo/imports` (the same two imports in the other order:
    §10.7 says `imports` is "in order: the order fixes that of the module
    initialisers", so a reordering is a difference, `changed <order>`)
  - `differ/_/module-import-added` (a second import)
  - `differ/Owner/unit` (one exported function moved from an imported
    interface into the main interface unit)
  - `differ/_/module-explicit-def-across-units` (`ModuleTable`
    `explicit_defs` naming an imported unit against the main unit)
  - `differ/_/module-imported-unit-as-main` (the "`Ast` like its own"
    promise: a declaration of `m` reached through `import m;` digests as
    when `m` is the main file; only `<order>` differs, by the import)
  - `equal/_/module-linkage-one-name-two-modules` (step 6, below)
  - `differ/UnitKind/Header`: a function of a header included in the
    global module fragment of an imported `m` against owned by the header
    unit `m` imports. The header unit is imported by `m`, not by the main
    file, on purpose: an import of a header unit by the main file makes
    the order unit indeterminate (`order.rs` `HEADER_IMPORT`, the path
    rule of digest §9 not yet applied to its key), and a `differ` test
    admits no indeterminate unit. Run at the pin with the header unit
    imported by the main file, the test fails for exactly that reason on
    both sides; so `UnitKind/Header` needs a named module too.
  - `indeterminate/_/header-unit-import`: that indeterminate order unit.
    It runs at the pin (its expectation held with `# pending` removed),
    but its parse makes Kiln look the header's name up on the host (item
    5): pending on KF5 §4, the stricter reading of "nothing reads the
    host's file system".

## Step 6: keys and modules

A key does not hold the module an entity is attached to: `Key` is kind,
parent, name and discriminator (`spec/digest.md` §3), `Parent` is `root`,
`c_linkage`, `builtin` or an enclosing entity, and `keys.rs` reads no
`ModuleTable` (its only mention of an owner is the owner of a local
entity, `keys.rs:219`, `:438`). Two declarations of one name with module
linkage in two named modules are two entities ([basic.link]/8), so a
translation unit importing both has two units under one key: a collision
the walk marks. `equal/_/module-linkage-one-name-two-modules` shows it
when it can run; until then it is a finding for `keys.rs`'s owner (the
handback), not fixed here.

## Rows still untested, and why

- `ModuleOwnership/Visible`, `VisibleWhenImported`, `ReachableWhenImported`,
  `ModulePrivate`: Kiln never sets them, with or without modules.
  `DeclMisc::with_module_ownership` (`kiln_ast/src/decl.rs:512`) has no
  caller at the pin; ownership is kept in `ModuleTable` instead (the one
  reader, `kiln_sema/src/bmi_image.rs:4159`, refuses a declaration whose
  bits are not `Unowned`). An imported declaration is `Unowned` like every
  other (`equal/_/module-ownership-unowned` says the same for the main
  unit). They stay in `untested.txt`; `Unowned` stays too (its one test is
  an `equal/_/` test, which names no row).
- Every row the pending tests name is removed from `untested.txt` by
  `SLIP_BLESS=1`, as the ratchet counts a directory with files, pending or
  not (the precedent: `differ/TemplateTables/pack_index_origin`).
