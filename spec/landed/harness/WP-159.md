## The trees (item 2)

Demo 1 (`xtask/src/demo.rs`) and `crates/slip_cli/tests/names_relocation.rs`
compute what a case's edits write before the tree exists (`plan_edit`;
the test's `apply_edit` into a map), then walk the source tree: a file
an edit writes is created new (`create_new`), every other file is a hard
link, and created files go in last; every written file is read back.
A derived case (`base`) is built from its base's tree, whose edited files
are then linked into it unless the derived case writes them too: a file
the base wrote is then a file with two names, neither replaced.

## The product's own links (item 4)

A *sequence* is what a code path does to names, in order. The question
for each: is a name ever made again while another name of its old file
is alive? That is the pattern of the rows that fail
(`link-unlink-create`, `tmp-again-after-link`).

1. **Publish** (`slip_exec::store::Inner::publish`: plans, declared
   changes, shards, run records, transform run records, `VERSION`;
   `publish_once`: objects and blobs). Create `tmp/<pid>.<t>.<n>.tmp`
   (`create_new`), write, rename it to the final name. The final name's
   old file, if any, had that name only. Before this package the
   temporary was `tmp/<pid>.<n>.tmp`, which a later process with the same
   pid makes again while the final name, the temporary's old file, is
   alive (the `tmp-again-after-rename` row, clean); with the token it is
   never made again. `publish_once` reads the final name first and
   compares bytes: a wrong read only makes it publish again.
2. **The lock** (`take_lock`). Create a temporary as in 1, hard-link it
   to `lock`, unlink the temporary. `lock` is then its file's one name
   (`the_lock_is_one_name_of_its_file`). Before this package the
   temporary's name was made again by a later process with the same pid
   while a stale `lock` (a killed owner's) was alive: the
   `tmp-again-after-link` pattern, a read of `lock` then able to return
   the new temporary's bytes. Read as a pid (`parse_lock`), never against
   a digest: a wrong read gives `Io` (`InvalidData`) or `Busy`, or a
   wrong owner. With the token the name is never made again.
   **Take-over**: rename `lock` to a fresh temporary name, read it,
   remove it, or hard-link it back to `lock` and remove it. The link back
   makes `lock` again while the temporary (the same file) is alive: both
   names are one file with one content, so no read can return another
   file's bytes. **Closing** reads `lock` and removes it if it holds this
   process's pid.
3. **The journal** (`slip_cli::transform::store::StoreJournal::publish`).
   Create `tmp/<pid>.d/journal.<t>.<n>.tmp`, write, sync, hard-link it to
   `write.journal`, unlink the temporary; `remove` unlinks the journal.
   Before this package the name was `journal.<n>.tmp` in a scratch
   directory that a later process with the same pid has again; only an
   exclusive opener can publish a journal and an exclusive open of a
   store with a journal is refused, so the name was not made again while
   a journal was alive, but nothing but that argument kept it so; with
   the token it is never made again
   (`the_journal_temporary_is_never_made_again`). The journal is read
   by `apply --recover`, decoded and not checked against a digest.
4. **`apply --patch`** (`slip_cli::transform::apply::write_patch`).
   Create `.<name>.slip-tmp.<pid>` beside the patch file, write, sync,
   rename it over the patch file. No link. The temporary's name is made
   again by a later process with the same pid while the patch file, its
   old file, is alive: the `tmp-again-after-rename` pattern, which is
   clean on the mount; the reader is the user, not Slip. Unchanged: the
   name is spelled in `spec/edits.md` §7.2's leftovers rule.
5. **`apply --write`** (`slip_apply::write` over `DiskTree`): the staged
   name `.<file>.slip-<overlay>` created, renamed over the file. A file
   with a second hard link is refused (`hard_linked`), so no rename is
   ever made over a name whose file has another. The staged name is made
   again only by another write of the same overlay, after the file it
   became was renamed into place (the `tmp-again-after-rename` pattern;
   clean).

**Reads not checked against a digest** (`spec/exec.md` §2.1 "Which reads
are checked"): the plan read by `--plan <id>`, the declared changes read
by `check --declared <id>`, the map shards `slip map` counts failed runs
in, run records, `write.journal`, the lock. With the sequences above
none can return another entry's bytes through the mount's confusion:
no sequence makes a name again while another name of its old file is
alive. Before this package two could, in principle: a plan or declared
changes published by rename from a temporary name a later process with
the same pid made again (the rename form, clean on the mount), and the
lock (the link form). These two unchecked reads (`--plan <id>`,
`check --declared <id>`) are reported to the supervisor, not changed.
