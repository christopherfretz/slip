# WP-051 — xtask: corpus invariants (a) and (b)

Decided by work package WP-051: `cargo xtask invariants a|b <corpus>`
(`spec/harness.md` §9). The code is `xtask/src/invariants.rs` and
`xtask/src/slip_run.rs`; the tests are `xtask/tests/invariants.rs`.

## Where §9 was silent, and what the code does

1. **"Configured"** (§9, first bullet) is what `corpus status` reports as
   configured *and* generated, with a database that reads: the configure
   stamp is current for the stamped commit, the generate stamp is
   current, and `build/compile_commands.json` parses. Otherwise the one
   line is ``corpus `<name>` is not configured: run `cargo xtask corpus
   configure <name>` ``, before `slip` is looked for.
2. **A `slip` status it does not accept** (0 and 1; for `verify` also 4)
   is the error ``slip <command>` exited with status <n>`` and xtask's
   exit status 1: §9's list of exit statuses (0, 1, 2) is exhaustive, so
   "fails the command with the status" names the status, it is not
   passed through. A `slip` killed by a signal, or whose standard output
   is not UTF-8, is an error too (nothing is guessed from a lossy
   decoding).
3. **Errors** print `xtask invariants: <message>` on standard error and
   exit 1, with nothing on standard output; usage errors add the usage
   text and exit 2. The options are taken only in the form §9 writes
   (`--only <s>`, not `--only=<s>`); `--slip`, `--limit` and `-j` given
   twice are usage errors; `--limit` must be decimal digits fitting
   `u64` (leading zeros allowed, as `slip` reads it) and is passed on as
   written; `-j` is passed on unread.
4. **The selection.** xtask computes the selection itself from the plan,
   as `slip` does (`spec/exec.md` §8.2: main files containing one of the
   `--only` substrings, then the first `--limit` in plan order), so that a
   selected observer the run left out is seen (`no job`). A run record
   with a job for an observer outside that selection is an error, not a
   count. A run is "over a selection" when `--only` or `--limit` is given
   (even a `--limit` above the plan's size).
5. **Which run record.** After each `slip parse`, the run read is the
   store's latest map run of the printed plan (`Store::latest_run`), and
   it must be the record `slip` printed on its `run` line (the two paths
   compared as real paths); the `run` lines of the output are those
   `slip` printed.
6. **This run's shard.** An observer's result is the `shard` of its last
   `Job` entry; the shard the store holds is read as it only if its
   content id (of `Shard::to_bytes`, the canonical encoding) is that
   digest — the rule `slip verify` applies to its own run
   (`spec/verify.md` §7). The sides of a `different` line are
   `<status> <shard id>`, or `no job` (no entry), `no shard <end>` (the
   last entry wrote none: `no shard crashed`), `absent <id>` (the store
   has no shard of the observer), `other <id>` (the store's shard is
   another one). None of the last four is ever equal, also when both runs
   show it. A shard file with an unknown ignorable section would
   re-encode to another id and show as `other`: the map task writes none.
7. **Over nothing, an invariant does not hold** (stricter than "holds
   when `different` is 0"): (a) over no selected observer ends
   `invariant a: FAILED (no observer selected)`, and (b) with no `map_ok`
   observer `invariant b: FAILED (no observer with an ok map shard)`;
   both exit 1. `spec/harness.md` §9.1 and §9.2 say so.
8. **The lists** stop at 50 lines with no line saying how many more: the
   count above them says it.

### Invariant (b)

9. **Reusing `stores/a1`.** The plan id of the corpus is what
   `slip plan --db <database> --store stores/a1` prints (run only when
   `stores/a1` is a directory). The store is reused when its latest map
   run of that plan has the tools of `slip --version`, is round 0, has a
   shard for every observer of its record, and its observers are exactly
   the selection; otherwise it is made as §9.1 makes it (removed, then
   `slip parse`). The observers of the map run are then the selected
   observers, which is what `check_identity` relies on: the report names
   only the observers that are not verified.
10. **`stores/b.json`** is removed before `slip verify` runs, so a report
    an earlier run left is never read.
11. **The counts.** `observers` is the report's `observers.selected`;
    `map_ok` the selected observers whose map shard is `ok` and the map
    run's own (6). `verified`, `indeterminate_only`, `different`,
    `not_parsed`, `unverifiable` and `failed` partition `map_ok`: an
    `unverifiable` or `failed` observer whose map shard is not `ok` is
    counted in none of them and not listed (it is not against the
    invariant); `never_parsed` counts every selected observer in that
    state. A `mismatch` is `indeterminate_only` when its `findings` equals
    its `indeterminate`. The list lines are
    `<state>: <main file>: <message>`, the state as the report names it
    (`mismatch`, `not_parsed`, `unverifiable`, `failed`), the message's
    first line, and for a `mismatch`
    `<findings> finding(s), <indeterminate> indeterminate` (the report's
    message is empty there), as `slip verify` writes it on standard error.
12. **The report is checked, never trusted to count.** It must be a JSON
    object with `report` `slip.verify.v1`, the map run's `plan`, `round`
    0, `declared` the content id of `Declared::none()`, an empty `image`
    (the identity), and a `run` path; numbers are `uv`s and paths
    `bytes` of `spec/model.md` §10 (a string; `{"hex": …}` only for bytes
    that are not UTF-8; a number from 2^53 a decimal string). Then:
    `observers.selected` is the number of the map run's observers;
    `observers.unchanged` is 0 (an unchanged observer was not compared,
    and the report does not name it, so (b) cannot count it either way);
    each `not_verified` entry is an observer of the map run, once, in
    plan order, with the plan's main file, a state of `spec/verify.md` §7
    other than `verified` and `unchanged`; the entries of each state are
    as many as `observers.<state>`; `observers.verified` is the selected
    observers not listed; `observers.indeterminate_only` is the listed
    `mismatch`es whose findings are all indeterminate; a `mismatch` has
    at least one finding and no more indeterminate ones than findings;
    and the states agree with the map shards: `mismatch`, `not_parsed`
    and every unlisted (verified) observer have an `ok` map shard,
    `never_parsed` has not. Anything else is an error naming the report
    file and what disagrees.

### `slip_run`

13. `find_slip` requires a regular file with an execute bit (`--slip` or
    the default) and returns its real path; the errors are `<path> does
    not exist`, `is not a file`, `is not executable`, the default path's
    followed by ``: run `cargo build --release -p slip_cli` ``. An empty
    `$CARGO_TARGET_DIR` counts as unset.
14. `line(stdout, key)` is the rest of the first line that is the key,
    one space and more; a line that is the key alone does not match.
15. `remove_tree(under, dir)` refuses a `dir` that is not strictly below
    `under` (both absolute, no `..`), or whose parent's real path is not
    under `under`'s real path (a symbolic link leading out); it removes a
    tree depth first without following links (a link is removed as a
    link), a file as a file, and an absent path is not an error.

### Before WP-045: one complete map run (old base, not the invariant)

A first `cargo xtask invariants a llvm` ran with a release `slip` built
from `366e0b5` (this branch merged with `main` after WP-050, before
WP-045; `slip 0.0.0 (kiln 1.3.0)`). Its first store, `stores/a1`, was
complete: plan `aee0a833…`, 4061 observers, 4059 `ok` and 2
`diagnosed` (the two fuzzers of `spec/harness.md` §8.7), every job
`completed` on its first attempt, `wall_s` 11159.091, `cpu_s`
10332.760, `workers_max` 1 (the shared jobserver had no idle token;
load 10 to 14), `peak_rss_max` 683 372 544. The host was restarted
while the second store was being written (2617 shards, no run record,
a `lock` naming a process that no longer existed), so (a) has no result
on that base. What that store left can mislead nothing: with no run
record, `perf::load`, `slip verify` (`Store::latest_run`) and (a)
(which removes both stores first) never read it, and the stale lock is
taken over by the next exclusive open (`spec/exec.md` §2.1). A lock
whose pid is reused by an unrelated process in a restarted container
would read as live; the corpus lock has the same limit
(`spec/harness.md` "Open questions").
