# WP-047 — the pair runners: derived units named exactly, and a pool

Decided by work package WP-047. What a pair test's `expect.txt` says —
its lines, `derived-added` / `derived-removed`, the directive
`exact derived`, what each runner reads, and what `equal` does about a
unit only one side has — is in `spec/digest.md` §14.1, with the per-row
rule in `spec/digest-kinds.md` §1.5. This file holds the decisions
behind it and the runner's mechanics (`spec/harness.md` §6.1 is the
reader's summary). The code is `crates/slip_digest/tests/common/mod.rs`
(`expect`, `exact_derived`, `derived_differences`, `pool_size`,
`pool_map`, `run_dirs`, `run_all`) and `common/pairs.rs` (each runner's
judgment, the report mode).

## Decisions

1. `derived-changed` keeps, without `exact derived`, its meaning before
   WP-047 (any difference, presence included), so that no open branch's
   test changes meaning. The closing package of the digest narrows it to
   "both have it and it differs" and rewrites the lines that mean an
   appearance; the report below lists them.
2. `exact derived` is not the default. The closing package decides from
   the report.
3. Lines are compared by name only (digest §14.1 rule 2), as before: no
   test today needs to tell two derived keys of one name apart.
4. Stricter than before WP-047, and no directory needed a change for it:
   a line written twice is an error; an `equal` test's `expect.txt` has
   no line and an `indeterminate` test's only `indeterminate` lines;
   `equal` and `indeterminate` refuse the directive. A unit only one side
   of an `equal` test has was a failure already.
5. A `differ` test whose `expect.txt` holds only `exact derived` is the
   error "a differ test needs at least one line in expect.txt besides
   `exact derived`".

## The report of unnamed derived differences

With `SLIP_DIGEST_DERIVED=report` the `differ` runner prints, for each
passing directory, `<dir>: unnamed <line>` for each derived difference
(as `derived_differences` gives it) that no line of the directory names
exactly; one that only a `derived-changed` line covers (an appearance or
a disappearance) ends in ` (written derived-changed)`. It then prints the
count by kind and the twenty directories with the most (ties by
directory). The report fails nothing.

## The pool

1. `common::run_all` runs its directories on a pool of threads and
   reports what it reported before, in directory order: the
   `skipped (pending)` lines, the count line, and the failures joined in
   directory order in the panic. The report does not depend on the
   pool's size or the order the threads finish.
2. The pool's size is `SLIP_TEST_THREADS` when set — a positive decimal
   number, anything else an error naming the variable
   (`SLIP_TEST_THREADS=<value>: not a positive number`) — otherwise the
   smaller of 4 and `std::thread::available_parallelism()`. A test takes
   no token from the jobserver.
3. A panic in one directory's work is that directory's failure,
   `<dir>: panicked: <text>`; the other directories still run.
4. Nothing is shared between directories but the support files
   (`tests/support/`), read once. The parse and the walk keep their own
   threads, so a pool of `n` has at most `n` parses and `n` walks at a
   time. A pool thread has an 8 MiB stack: it runs what ran on libtest's
   test thread before (the comparison of the sides, and whatever a
   caller's closure does), and libtest's threads have 2 MiB or
   `RUST_MIN_STACK`; 8 MiB, Linux's usual main-thread limit, keeps that
   work from depending on either, at the cost of address space only.
5. `SLIP_DIGEST_TIMES=1` prints, after the report, the twenty slowest
   directories of the runner with their milliseconds (a panicking one
   included; ties by directory).
6. The determinism test walks its directories on the same pool, in both
   processes; the two walks of one directory run one after the other.
   The tables test parses nothing and is unchanged.
7. `cargo xtask ci` removes `SLIP_DIGEST_ONLY`, `SLIP_TEST_THREADS`,
   `SLIP_DIGEST_DERIVED` and `SLIP_DIGEST_TIMES` from the environment of
   what it runs.
