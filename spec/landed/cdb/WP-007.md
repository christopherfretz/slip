# WP-007 — slip_cdb: database reader and plan builder

Behaviour landed by WP-007 that `spec/cdb.md` §2 and §7 do not state. Each
choice is the conservative reading of a gap; the supervisor folds or revises
them at the end of M0.

## §2 Reading a JSON compilation database

- **Error details.** A `DatabaseError` is `not JSON: <json error>` (the
  `slip_model::json` error, with line, column and byte; invalid UTF-8 is one
  of these) or `the top level is <type>, not an array`.
- **Order of checks** for one entry, first failure decides: not an object;
  `directory` missing or not a string; `directory` not absolute
  (`Path::is_absolute`, so the empty string is relative); `file` missing or
  not a string; then the command line.
- `Defect.file` is the entry's `file` whenever it is a string, whatever the
  defect (so a bad `directory` still reports the file).
- **`arguments` wins strictly.** When `arguments` is present it alone is
  used: if it is malformed (not an array, empty, a non-string element) the
  entry is a defect even when `command` would split. When `arguments` is
  absent, `command` must be a string and split by §3.
- `output` and every unknown key are ignored whatever their type.
- Detail texts: `` `<key>` is missing ``, `` `<key>` is <type>, not a string ``,
  `` `directory` `<d>` is not an absolute path ``, `` `arguments` is empty ``,
  `` `arguments[<i>]` is <type>, not a string ``,
  `` neither `arguments` nor `command` is present ``,
  `` `command` cannot be split: <message> (byte <offset>) ``.

## §7 Building the plan

- **Usage** is checked before any database is read: no source at all, an
  empty configuration name, or a name given twice.
- **Database errors.** `PlanError::Database.path` is the path as given. The
  file is read whole (only main files are streamed), then its real path is
  resolved; failure of either is `Database` (`cannot be read: <os error>`,
  `its real path cannot be resolved: <os error>`), as are the two §2
  `DatabaseError`s (their detail unchanged). The first failing database, in
  the order given, is reported. The configuration's `FileRef` is the real
  path, the byte count read and the content digest of those bytes.
- **Merging.** Entries are keyed by `ObserverId`. The first entry's
  normalised main path and language are kept for the observer; later
  entries with the same id cannot differ unless the file system changes
  while the plan is built, which is not detected.
- **Hashing.** Each distinct real main path is read once, in pieces of
  `READ_CHUNK` (64 KiB), and its size is the number of bytes read (not file
  metadata). A main file that cannot be opened or read (a directory, say) is
  `missing_file` for every origin of every observer naming it, each keeping
  its own entry's `file` as spelled, with detail
  ``main file `<real path>` cannot be read: <os error>``.
- **Threads.** `min(threads, distinct main files)` scoped threads claim
  files by an atomic counter; results are stored by index, so the plan is
  the same for every `threads`. 0 and 1 hash on the calling thread.
- `Excluded.detail` for a rejection is the rejection's text unchanged
  (`-fbad`, `.f90`); for a normalisation exclusion, `Exclusion.detail`.

## Tests

`crates/slip_cdb/tests/database.rs` (§2) and `tests/plan.rs` (§7), with
golden plans `tests/golden/plan_mixed.json` and `plan_merged.json`
(`SLIP_BLESS=1` rewrites them). The goldens replace observer ids by
`"<observer id>"` (after checking each against `Command::observer_id`),
each database's `size` and `content` by `"<size>"` and `"<digest>"`, and
the fixture root by `$ROOT`.
