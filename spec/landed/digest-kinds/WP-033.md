# WP-033 — scopes, cold maps, modules and the order unit

What `crates/slip_digest/src/decl_scope.rs`, `other.rs` and `order.rs`
read into `spec/digest-kinds.md` §5.6, §5.7, §5.8 and §10.7, and digest
§2.1 (the order unit), where the tables are silent. Kiln sites are at the
pinned `kiln/` revision.

## §5.6 Scopes and the rest

- **`NamespaceData` `flags-inline`** is one `bit`, set if any declaration
  of the namespace has `INLINE` (`w.redecls(first)`): a reopening need
  not repeat `inline` ([namespace.def]/5), so the namespace unit does not
  depend on which declaration is read (`equal`: none needed, the unit
  test `namespace_inline_is_merged_over_reopenings`). A bit other than
  `INLINE` and `ANONYMOUS` is `Unaccounted("NamespaceData/flags")`.
  `flags-anonymous` is `keyed`: the key moves (`differ/NamespaceData/
  flags-anonymous`).
- **`StaticAssertData`** is read with `DeclArena::static_assert`, which
  serves `StaticAssert` and `ConstevalBlock` (`kiln_ast/src/decl.rs:220`).
  A missing payload is `Unaccounted("StaticAssertData/missing")`.
- **`FileScopeAsm.data`** is Kiln's `Ast::file_scope_asm_string`, a
  string-literal expression (`kiln_ast/src/ast.rs:350`), written as
  `child`.
- **`FriendTarget`** is read with `DeclArena::friend_target`, which
  panics on another kind (`kiln_ast/src/decl.rs:3234`): the walk checks
  the kind first and writes `Unaccounted("FriendTarget/kind")`.
- **`ScopeData` `aux-braceless` is `out`** (decided, WP-033 review). For
  a function it means nothing: `extern "C" { void f(); }` and `extern "C"
  void f();` are equal (`equal/ScopeData/aux-braceless`). For a variable
  its effects are whether the declaration is a definition, which the unit
  holds (`DeclMisc` `definition`, through `units::is_var_definition`), and
  its linkage, which the key holds (`Walk::in_c_linkage`,
  `kiln_ast/src/decl.rs:2366` `is_single_line_linkage`). It was written at
  one site, `decl_func::linkage` (functions and variables), now dropped.
  A braceless variable declaration is written with `VarSpec` `0-storage`
  `Extern` when it wrote none ([dcl.link]/8: it is treated as `extern`),
  so `extern "C" { extern int x; }` and `extern "C" int x;` are equal
  (`equal/_/c-linkage-braceless-extern-variable`), while `extern "C" {
  int x; }` against `extern "C" int x;` differs (`differ/_/
  c-linkage-braceless-variable`: a definition against a declaration).
  `aux-lang` is WP-026's and unchanged.

- **`lexical_ctx` is `ref*sorted`** (decided, WP-033 review). For a
  declaration, the written scope is the entity of the nearest lexical
  context that is not transparent (through `LinkageSpec`, `Export` and the
  other non-entity roles); the semantic scope is that of `ctx` the same
  way, except that for a block-scope function or `extern` variable
  (`Walk::is_local_extern`) it is the innermost enclosing namespace
  ([basic.link]/7, §2.4). A declaration counts when the two differ, and
  writes a `ref` to its written scope; the global namespace has no key and
  is `Ref::none` (`differ/_/lexical-ctx-member-out-of-line`). The refs
  are sorted by their bytes, duplicates removed. With at most one ref the
  bytes are those of the former `ref?`.
- **Which declarations count.** With a definition, the declaration read
  alone (at most one ref). Without one, every declaration: the row then
  does not depend on their order (`equal/FriendKind/Declared`,
  `equal/_/lexical-ctx-friends-swapped`), and a friend in A differs from a
  friend in A and in C (`differ/_/lexical-ctx-friend-added`). So a
  function declared at namespace scope and befriended by X gains X: the
  friend tests list `changed f()`. A class declaration that a friend
  declaration made does not count: Kiln makes one for `friend struct H;`
  only when no `H` is found (`FriendKind::Undeclared` on it), so it would
  make the row depend on the order (`equal/FriendTarget/Type.owned_tag`).
- **The definition class (§11.9).** For an entity defined only on use
  (`decl_func::definition_class`), every declaration counts except a
  definition that is not the first declaration: that one the use made.
  Kiln puts the definition it instantiates for a static data member
  defined outside its class template at namespace scope, so with the
  definition rule a use moved the row (`[0]` against `Ref::none`). The
  unit test `lexical_ctx_of_a_member_defined_on_use` pins it. A friend
  defined in a class template, whose definition is its friend
  declaration, and a member function defined outside its class template
  do not move (`demand/_/lexical-ctx-friend-defined-on-use`,
  `lexical-ctx-member-defined-on-use`). `demand/_/lexical-ctx-static-
  member-defined-on-use` stays pending, `# needs: units`: the unit still
  moves with the use, outside this row. The declaration read becomes the
  instantiated definition, whose `VarData` `templ` is empty while
  `TemplateTables` holds its link (`decl_maps`).
- **The definition class (§11.9).** `ctor_inits`, `friends` and
  `record_pack` write their empty forms with `Pending(Demand)` for a
  constructor or class of the class (`decl_func::definition_class`),
  whether or not Kiln made the definition, as `FunctionData` `body` does.
- **`ctor_inits`** is a count, then `decl_class::ctor_init` of each.
- **`friends`** is `key*sorted`: each key encoded alone, sorted by bytes,
  duplicates removed. Kiln's list holds the befriended entities' first
  declarations, not the `Friend` declarations (see "Rows wrong about
  Kiln" in the handback): the keys written are theirs.
- **`instantiated_from`**: absent writes `Ref::none`; an entry writes its
  `ref` and `Unaccounted("ColdDeclData/instantiated_from")`. The unit
  test `instantiated_from_is_never_filled` fails if an entry appears.
- **`compound_literal`**: an entry makes the unit
  `Unsupported("ColdDeclData/compound_literal")`. The implicit variable
  is a unit only when referred to, and it is referred to only by the
  compound literal expression: the test waits for the expression area.
- **`decomp_bindings`** at namespace scope writes each binding's `key`;
  in a block, `local::write_decl` of each. `binding_var` is `decl?`
  through `local::write_decl`.
- **`init_fp` of a parameter of an instantiated function** is absent: its
  default argument is the `default_argument` derived unit's (§11.4), the
  reading of `ParamData` `default_arg`.
- **`gnu_lib_twin`** is `bool`. The snippet's library is libstdc++
  (`kiln_driver/src/toolchain.rs:308`), so the map is filled, but only a
  change of the function's name or signature changes it, and that
  changes the key: no pair differs in it alone. The unit test
  `gnu_lib_twin_is_written` compares `fabs` (with a twin) and `fabx`
  (without) in one source.

### Rows redundant with another at the pin

Each of these rows is written; a mutation of it alone is caught by no
pair test because another row carries the same fact.

- **`asm_label`**: Kiln adds the `ASM_LABEL` attribute along with the
  entry (`kiln_sema/src/decl.rs:4415-4425`); `AttrArena` `decl_attrs`
  carries it (§10.1).
- **`delete_message`, `overrides` read from `d` instead of the chain**:
  Kiln inserts `delete_message` on the function and on its first
  declaration (`kiln_sema/src/class/special/mod.rs:528-533`) and reads
  `overrides` on the first (`kiln_abi/src/vtable/classes.rs:396`). A
  redeclaration that could tell them apart carries no entry of its own.
- **`contracts` empty**: a function with contract assertions against one
  without also differs by another row of its unit (the reviewer's probe;
  Kiln keeps the assertions apart from the declaration,
  `Ast::function_contracts`, `kiln_ast/src/ast.rs:593`, and which other row
  sees them was not traced). Main's `differ/ColdDeclData/contracts`
  varies only the predicate; `contracts` is the row that holds it.
- **`NamespaceData` `inline` "last wins"**: a reopening that repeats
  `inline` is the only well-formed case ([namespace.def]/5: `inline` on
  a later declaration requires it on the first). The bits agree.
- **`explicit_defs`**: the unit that holds an explicit instantiation
  definition is unit 0 in every compilable snippet, and `SpecInfo` `kind`
  (`ExplicitInstantiationDefinition`, §9.4) already differs whenever the
  row does (`kiln_ast/src/modules.rs:150`).
- **`FriendTarget` tag and `Type.ty`**: the befriended entity reaches the
  stream through the class's `friends` (`key*sorted`) and through the
  `Friend` declaration's `DeclNode` `ty` (`kiln_ast/src/decl.rs:3235`).
- **`gnu_lib_twin`**: see above.
- **`demand` rows** (`key_function`, `dtor_delete`, `dtor_delete_this`,
  `builtin_id`, `lib_builtin`, `inheriting_ctor`, `inherited_ctor`, and
  `DeclArena` `completed_records`, `fn_def_insts`) write nothing; each has
  a demand test whose use is in a function body.

## §5.8

Every row is `out`; nothing is written. No row hides a fact: the
redeclaration table is how §2.3 finds the first declaration and the
definition, and the lookup tables index what each scope declares, while
what a lookup found is held by the node that used it.

## §10.7 Modules

- **`points`** is `record Owner?`, `ModuleTable::owner` of the first
  declaration (§10.7 calls it `owner_of`; Kiln's method is `owner`,
  `kiln_ast/src/modules.rs:95`): `record UnitInfo` of `unit`, then one
  flag word `[purview, exported]`. **`explicit_defs`** is `record
  UnitInfo?` of `explicit_inst_def_unit(first)`
  (`kiln_ast/src/modules.rs:150`). Both are absent when `active` is
  clear. A `unit` index with no `UnitInfo` is `uv 0` and
  `Unaccounted("Owner/unit")`.
- **`UnitInfo` for an owner** writes `kind`, `module` and `partition` as
  `bytes?`; no imports.
- **What the runner compiles.** The snippet has no module files, so
  `module m;` (an implementation unit) and `import n;` fail ("module 'm'
  not found"). Interface units, partition interface and implementation
  units, the global module fragment, `export` blocks and `module
  :private;` compile. `Implementation`, `Header`, `imports` and `Owner`
  `unit` have no test. `Owner` `unit` is the index of the owning unit, 0
  for a declaration of the translation unit itself: `UnitInfo/module` and
  `UnitInfo/kind` pass through unit 0 but test the record it names, not
  the index. Another index needs a declaration of an imported unit, and
  the runner cannot import one.
- **Activation is textual; the rows do not follow it** (decided, WP-033
  review). Kiln sets `active` when any line of the main file starts with
  `module`, `import` or `export` (`kiln_pp/src/modules.rs:403-411`,
  `kiln_parse/src/parser.rs:444`), even a line the preprocessor skips or
  a variable named `module` at the start of a line. A translation unit
  that is not a module unit then has `active` set and one `UnitInfo` of
  kind `NonModule`. When unit 0 is `NonModule` with no imports, both
  rows write their empty forms whatever `active` says (`other::tracked`;
  `equal/_/module-skipped-line`, `equal/_/module-line-start`, unit test
  `textual_activation_writes_empty_forms`). `differ/UnitKind/NonModule`
  is now a non-module unit against the global module fragment of an
  interface unit. `points` is read from the first declaration:
  `equal/ModuleTable/points-first-declaration` (a definition that repeats
  `export`).

## Made by instantiation (one helper)

`templ.rs` has the one rule, in two forms:

- **`templ::governing_kind(w, d)`**, entity level: climbing from `d`
  through lexical contexts, the first kind found, where each step reads
  the declaration's own `SpecInfo` or `MemberSpecInfo` and else its
  entity's. Kiln keys a member specialisation by the entity's first
  declaration (in the implicit instantiation of the class), not by the
  out-of-line definition written in source: `template <> struct
  A<int>::N {...}` has no kind of its own, its entity has
  `ExplicitSpecialization`. The climb stops at the first kind, so an
  explicit specialisation and what is written in it are written in source
  (digest §2.1). `decl_class::governing_kind` calls it, after its own
  rule that a local entity has none.
- **`templ::instantiated_declaration(w, x)`**, declaration level: the
  declaration's own `SpecInfo` kind; else the `MemberSpecInfo` kind of
  `x` or of its entity unless it is `ExplicitSpecialization`; else
  `governing_kind` of its lexical context. `decl_func::instantiated_decl`
  (default arguments), `decl_scope::init_fp` and the order unit call it.
  These copies need the declaration-level answer because an explicitly
  specialised member keeps in its chain the declaration Kiln made in the
  implicit instantiation of its class. That declaration was made by
  instantiation, but its entity's kind is `ExplicitSpecialization`
  (`demand/_/explicit-specialisation-member-default-arg`). And Kiln puts
  the definition it instantiates for an out-of-line static data member at
  namespace scope, so only the member kind tells it apart
  (`demand/_/order-static-member-instantiation`).

## The order unit (digest §2.1)

- **The walk** is Kiln's code generation walk
  (`kiln_codegen/src/module.rs:657`): the lexical member lists from the
  translation unit, into `Namespace`, `LinkageSpec`, `Export` and every
  `CXXRecord`. Function bodies are not entered: their variables are not
  at namespace or class scope. Every `DeclKind` is matched by name
  (`order::visit`). `ClassTemplateSpecialization` and
  `VarTemplateSpecialization` are `Unaccounted("order/kind")`: Kiln makes
  neither (`kiln_ast/src/decl.rs:74`, `:117`; a specialisation is a
  `CXXRecord` or a `Var`). A pattern, a closure type or an instantiation
  is entered and nothing in it is listed: the guards are those of
  `listed`.
- **Listed**: a `Var` member that `units::is_var_definition` calls a
  definition (tested first: it reads the declaration alone, so a
  variable declared R times costs one walk of its chain, unit test
  `redeclarations_cost_linear_time`). It must not be a tuple-like
  binding's holding variable (`binding_var` targets; the object of an
  anonymous union, also implicit, is listed, `differ/_/
  order-anonymous-union`). It must not be a pattern, a partial
  specialisation or in a dependent context. It must not be made by
  instantiation (`templ::instantiated_declaration`). And it must be the
  definition of its entity (`units::defining_decl`).
- **Explicit specialisations.** An explicit specialisation and a member of
  one are listed, the static members of a member class's explicit
  specialisation too (`differ/_/order-member-class-explicit-
  specialisation`). `template <> int A<char>::s;` is a declaration
  ([temp.expl.spec]/14), so the definition with the initialiser is
  listed, where it is (`differ/_/order-member-explicit-specialisation-
  definition`, `equal/_/order-member-explicit-specialisation-declaration-
  moves`). `units::is_var_definition` now mirrors Kiln's
  `Sema::is_var_definition` (`kiln_sema/src/decl.rs:7582`):
  `Ast::is_member_spec_declaration` (`kiln_ast/src/templates.rs:1011`),
  `DeclArena::is_single_line_linkage`, and `selectany`
  (`Ast::has_own_selectany`). Kiln keeps no per-variable definition in
  the AST (`Ast::set_definition` is called for records, enumerations and
  functions only, `kiln_ast/src/builder.rs:586`, `:666`, `:909`), so the
  rule is Slip's. The variable's unit reads the same declaration
  (`differ/_/member-explicit-specialisation-read-from-definition`). An explicit
  instantiation definition is not: its initialisation is unordered
  ([basic.start.dynamic]/1), as Kiln emits it (`weak_odr`,
  `kiln_codegen/src/module.rs:4318-4343`; its own `llvm.global_ctors`
  entry, `kiln_codegen/src/global_init.rs:379`). An implicit
  variable is not: the holding variables of a tuple-like binding are
  initialised with the decomposition, which is listed. A non-inline
  static data member declared in its class is listed where it is defined
  outside it; an in-class `static const` member with no definition is
  not.
- **Stream**: `count` and `key` of each listed variable, then `count`
  and, per import of `units[0]` in stored order, `bytes` of its key and
  `bool` for `export import`; none when `active` is clear. A header unit's
  key (`"` and a path, `kiln_pp/src/modules.rs:161`) is written as is and
  makes the order unit `Unaccounted("UnitInfo/imports")`: the path rule
  of digest §9 is not applied yet.
- **Order of the stream.** The unit test `the_stream_is_the_keys_in_
  definition_order` compares the bytes with those written by hand. In
  that test `b` is declared before `a` and defined after it, so sorting
  by the first declaration, or reversing, fails. Sorting the listed
  declarations by `DeclId` is the same order for every source: Kiln
  creates declarations in source order, and the walk is in source order.
- **Consequences for other tests.** A source that adds, removes or
  renames a variable definition changes the order unit. The differ tests
  that do so list `changed <order>`. A demand test adds its use in a
  function body, so the order unit is compared like every unit and
  `tests/demand.rs` is main's.
