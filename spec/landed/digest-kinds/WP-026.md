# WP-026 — slip_digest: the payload records of functions and variables

What `crates/slip_digest/src/decl_func.rs` and `local::write_decl` read
into `spec/digest-kinds.md` §2.3, §2.4, §5.4, §5.6 (`ScopeData`) and §11.9
where they are silent. Each paragraph is one decision; the tests named
back it.

## Order of the rows

- `FunctionData` writes `params`, `body`, `spec`, `templ` in table order,
  then the language linkage of §5.6 (`enum LinkageLang?`, then
  `aux-braceless` as `bool` when present). `VarData` writes `init`,
  `spec`, `templ`, then the linkage. The linkage is last because the
  table's note puts it after the record's rows. The tests are
  `differ/ScopeData/*` and `differ/LinkageLang/*`, plus the unit test
  `decl_func::tests::linkage_is_an_optional_language_then_braceless`.
- The `bit` rows of `FnSpec` form one flag word, in table order, at the
  place of the first bit row (`0-inline`, after the `0-storage` tag). The
  `0-constexpr-kind` and `0-defaulted` tags follow the word, in table
  order. `VarSpec` likewise writes the `0-storage`, `0-tls` and
  `0-init-style` tags, then one word of its seven bit rows.
- `ParamData` writes `default_arg`, `original_ty`, one word
  [`flags-explicit-object`, `flags-pack`, `flags-static-array`], then
  `flags-scope-depth` as `uv`.

## Language linkage

- The linkage is that of the innermost `LinkageSpec` around the entity's
  first declaration. The walk goes through namespaces, classes and
  functions, so a local variable and a class member hold one too. It is
  written for every function and variable stream, `static` ones
  included: it says what the enclosing language is, not whether the
  entity has C language linkage. `extern "C++"` is written `Cxx`, which
  differs from no `LinkageSpec` at all (`differ/LinkageLang/Cxx`). The
  reading is `Walk::linkage_spec(d, true)`, shared with the key's
  `c_linkage` rule (`linkage_spec(d, false)`, §5.2).
- `ScopeData` `aux` bits other than the language byte and
  `LINKAGE_BRACELESS` make the unit `Unaccounted("ScopeData/aux")`.

## The declaration read (§2.3)

- A variable's defining declaration is the first declaration of its
  chain that is a definition ([basic.def]/2), the search Kiln makes for
  a variable's initialiser (`kiln_oven/src/value.rs:89`). A declaration
  is a definition unless it is a non-inline static data member declared
  in its class, a block-scope `extern`, or `extern` (written, or by a
  braceless linkage specification) with no initialiser. Kiln records
  `definition` only for classes, enumerations and functions
  (`kiln_ast` builder.rs:586, :666, :909), so `units::defining_decl`
  computes it. `units::read_decl` and DeclMisc `0-definition`
  (`decl.rs`) both use it. Tests: `differ/_/var-defining-decl-init`,
  `differ/_/var-defining-decl-init-style`,
  `equal/_/var-extern-before-definition`,
  `differ/_/var-static-member-out-of-line` and
  `differ/_/var-definition-flag`.
- `init`, `0-init-style` and the `eval` state are read from the
  declaration of the chain that holds the initialiser, which need not be
  the defining one: `struct S { static const int x = 1; };` with
  `const int S::x;`. Kiln reads the initialiser, its evaluation state and
  its type from that same declaration (`kiln_oven/src/value.rs:89-98`).
  Block-scope `extern`s are left out. Two declarations holding one is
  ill-formed ([basic.def.odr]) and makes the unit
  `Unaccounted("VarData/init")`. Every other row is read as before. Tests:
  `differ/_/var-in-class-init-style`, `differ/_/var-in-class-init-value`
  (`# pending`, expr), unit test `the_initialiser_comes_from_its_holder`.
- The initialiser written in the class or on the out-of-line definition
  (`static const int x = 1;` and `const int S::x;`, against
  `static const int x;` and `const int S::x = 1;`) gives **equal** units
  (`equal/_/var-init-in-class-or-out-of-line`). §2.1 makes the unit the
  entity as its declarations together define it, and both pairs define
  `x` with the initialiser `1`. What the in-class form adds is that `x`
  can be used in constant expressions before the definition. A use that
  needs this is written where it is: in another unit, or in another
  translation unit that sees only the class.
- A variable's type is the type of the declaration read, unless that is
  an array of unknown bound that another declaration of the chain (not a
  block-scope `extern`) completes ([basic.types.general]/6). Then it is
  the first such declaration's type, first declaration first
  (`decl_func::var_type`, used by `decl.rs` for the `ty-type` row). With
  `extern int a[]; extern int a[3];` there is no definition and the
  first declaration is read, so without this rule the unit would hold
  `int[]`. Tests: `differ/_/var-incomplete-array-completed`,
  `differ/_/var-incomplete-array-defined`, unit test
  `a_variable_type_is_the_completed_one`.
- A template's pattern is written from its defining declaration,
  `units::defining_decl`, in `templ::template_info`. Before, that code
  used Kiln's `definition`, which is never recorded for a variable. The
  test is `differ/_/var-template-defining-decl`. It passed on the old
  line too: `read_decl` already hands `template_info` the template that
  describes the defining variable, and the rule above carries the
  initialiser even from another pattern. The other uses of Kiln's
  `definition` are never reached by a variable:
  - `keys.rs` `unnamed_tag_by` is called only for an unnamed class or
    enumeration;
  - `units.rs` `unit_class` reads it only for function kinds.

## Merging over redeclarations (§2.3)

- `FnSpec` `0-inline` is set if any declaration has `inline`.
  `0-implicit-inline` is set if no declaration has `inline` and any has
  `implicit_inline`. Kiln marks a declaration that follows an `inline`
  one as `implicit_inline`, not `inline`, so without this rule the entity
  would carry both bits. Tests: `equal/_/merge-inline` and
  `equal/_/merge-implicit-inline`.
- `0-constexpr-kind` is `Consteval` if any declaration says `consteval`,
  else `Constexpr` if any says `constexpr`. Kiln rejects declarations that
  disagree. If both are seen anyway, the unit is
  `Unaccounted("FnSpec/0-constexpr-kind")`.
- `0-storage`: `Static` when the declaration read is `static`; Kiln
  copies `static` forward with `storage_inherited` (kiln_sema
  decl.rs:6018). Otherwise it is `Extern` when some declaration says
  `extern` and the function is inline (`inline` or `implicit_inline` on
  any declaration), else `None` (`differ/FnStorage/Extern`,
  `equal/_/fn-extern-not-inline`).
- Each `FnSpec` bit row below is set if any declaration of the chain sets
  it, because Kiln sets several of them on one declaration only:
  - `0-virtual`, `0-pure`, `0-deleted`, `0-explicit`, `0-final`: where
    written. `final` is merged over the chain only in codegen
    (`kiln_codegen/src/vtable.rs:2010`); test
    `differ/_/final-on-declaration-only`.
  - `0-has-contracts`: on the declaration with the contract sequence
    (`kiln_sema/src/contracts.rs:434`); test
    `differ/_/contracts-on-declaration-only`.
  - `0-trivial`, `0-not-selected`, `0-immediate-escalating`: on the
    declaration the class or the BMI marks.
  - `0-is-coroutine`, `0-escalated`, `0-return-deduced`: on the
    declaration whose body is analysed.
  - `0-variadic`, `0-explicit-object`: on every declaration, from its
    type, so OR-ing them changes nothing.

  OR-ing is the conservative choice for all of them: none can be set on
  one declaration of an entity and be false of the entity.
- `0-defaulted` is read from the declaration the walk reads, the
  definition. A function defaulted on a later declaration is defaulted
  where it is defined, and that is the one read.
- `VarSpec` `0-constexpr`, `0-constinit` and `0-inline` are set if any
  declaration sets them. `0-inline-implied` is set when the variable is
  inline and every declaration that has `inline` also has the implied bit,
  that is, when `inline` is written on no declaration
  (`equal/_/merge-constinit`, `equal/_/merge-static-member-constexpr`,
  `differ/VarSpec/0-inline-implied`).
- The other `VarSpec` rows are read from the defining declaration:
  - `0-storage`: at most one declaration is the definition, and the
    definition of a `static` variable is a `static` declaration (an
    `extern` redeclaration refers back to it).
  - `0-tls`: `thread_local` must appear on every declaration if on any
    ([dcl.stc]/1).
  - `0-init-style`: the form of the initialisation, which only the
    declaration with the initialiser has.
  - `0-nrvo`, `0-exception-var`, `0-cxx-for-range`: local variables,
    which have one declaration (kiln_sema `range_for.rs:157`,
    `try_stmt.rs:132`).
- `ParamData` `default_arg` is the parameter's own, else the default the
  first declaration of the function that gives one at the same index
  gives (`equal/_/merge-default-arg-later`, unit test
  `param_default_merge`). Kiln copies defaults forward, so this matters
  only for a declaration that precedes the one that gives the default.
  Two kinds of declaration are left out:
  - block-scope declarations, whose defaults are their own
    ([dcl.fct.default]/4; Kiln merges them within the block only,
    kiln_sema decl.rs:6755-6770); test
    `differ/_/block-scope-default-not-merged`;
  - instantiated declarations (below).
- A default argument taken from another declaration names that
  declaration's parameters (Kiln copies the `ExprId` forward, kiln_sema
  decl.rs:6782-6784). `function_data` therefore first gives the
  parameters of the declaration read their ordinals, in order, and then
  makes parameter i of every other declaration of the chain the same
  local entity, before it writes the parameters. Unit test
  `parameters_of_the_chain_share_ordinals`; pair test
  `equal/_/default-arg-names-first-declaration` (`# pending`, expr).
- If `FnSpec` or `VarSpec` of any declaration is not equal to its rebuild
  from Kiln's accessors and `with_*` setters, the unit is
  `Unaccounted("FnSpec/0")` or `Unaccounted("VarSpec/0")`. Such a bit or
  value is one that no row accounts for. Unknown `ParamData` `flags` bits
  make the unit `Unaccounted("ParamData/flags")`.

## The definition class (§11.9)

- A function or variable is **defined on use** when its own `SpecInfo`
  or `MemberSpecInfo` kind is `ImplicitInstantiation` or
  `ExplicitInstantiationDeclaration`. With no kind of its own, the kind
  of the nearest enclosing context that has one decides
  (`decl_func::instantiated_on_use`). Kiln instantiates the members of a
  class named by `extern template` with `MemberSpecInfo`
  `ImplicitInstantiation`, and defines them on use
  (`demand/_/eid-class-member-use`, `demand/_/eid-function-use`).
- A function is of the definition class when it is defined on use, when
  every declaration is implicit, or when its first declaration is
  explicitly defaulted (`Defaulted::Explicit`). Kiln defines a function
  defaulted on its first declaration only when it is odr-used, the same
  as an implicit member (`demand/_/defaulted-ctor-use`; unit test
  `definition_class`). A function defaulted on a later declaration is
  defined there and is not of the class. A variable is of the class when
  it is defined on use. Any other entity (a class, an enumeration) is of
  the class when it is an implicit instantiation
  (`decl_func::definition_class`).
- For a function of the class these rows are written in their empty form
  in the own stream, and the unit is `Pending(Demand)` until the resolved
  unit `definition` exists (unit test
  `definition_class_body_is_pending_demand`):
  - `body`, absent;
  - `0-escalated`, clear: set when the body is analysed (kiln_sema
    consteval.rs:1566); test `demand/_/escalated-on-demand`;
  - `0-is-coroutine`, clear: set the same way (kiln_sema
    coroutine.rs:202); test `demand/_/coroutine-on-demand`.

  `0-escalated` and `0-is-coroutine` are rows §11.9 must gain.
- `0-return-deduced` is written clear only for a function defined on
  use, whose return type is deduced when its body is instantiated. A
  function defaulted on its first declaration deduces at the class's end
  (kiln_sema class/compare/default.rs:430-436), so it writes the bit
  (`differ/_/defaulted-spaceship-return-deduced`). §11.9 moves the bit
  only when the pattern's return type holds a placeholder; without one
  the bit is never set, so the two rules agree.
- DeclMisc `0-definition` is written false for an entity of the
  definition class: Kiln makes the definition on use
  (`demand/_/instantiated-member-body`, `demand/_/defaulted-ctor-use`).
  This is a row §11.9 must gain.
- For a variable of the class, `init` is written absent, `0-init-style`
  as `C` (the first tag, the empty form), and `0-inline` and
  `0-inline-implied` clear. The unit is `Pending(Demand)`.

## Default arguments of instantiated declarations (§11.4)

- A default argument is written in a unit only when a declaration that is
  not itself instantiated gives it. A declaration is instantiated when
  its own `SpecInfo` kind is an instantiation of any of the three forms,
  or, with none, when the nearest lexically enclosing context with a kind
  is one (`decl_func::instantiated_decl`). An explicit specialisation,
  and the out-of-line definition of a member explicitly specialised, are
  not instantiated; the declaration Kiln instantiated in the same chain
  is.
- A parameter of an instantiated declaration writes an absent child,
  whatever Kiln holds: its default is the `default_argument` derived
  unit's. Its `DEFAULT_ARG_PENDING` flag is never `Unaccounted` (tests:
  `demand/ParamData/flags-default-arg-pending`,
  `demand/_/implicit-instantiation-default-arg`,
  `demand/_/explicit-instantiation-default-arg`,
  `demand/_/explicit-specialisation-member-default-arg`).
- Elsewhere, a parameter whose `DEFAULT_ARG_PENDING` bit is set and that
  has no default makes the unit
  `Unaccounted("ParamData/flags-default-arg-pending")`. Kiln leaves the
  bit set after the late parse, so the bit alone is not read.

## Evaluation (§11.3)

- `VarData` `eval` is not written. In state `Value` or `NotConstant`,
  and in `NotEvaluated` when the variable has an initialiser, the unit
  is `Pending(Demand)`, because the value belongs to the resolved unit
  `value`. Kiln's timing does not decide it: Kiln evaluates an
  out-of-line `const int S::x = 1;` at once, but the in-class
  `static const int x = 1;` later. Kiln fills `eval` at the declaration
  (`check_constexpr_init`, kiln_sema decl.rs:8870), not on a later use.
  The `demand` tests of `VarData` `eval`, `VarEval` and `VarEvalState`
  therefore show only that a later use leaves every unit alone. The state
  `Evaluating`, which cannot outlive the translation unit, makes the
  unit `Unaccounted("VarEvalState/Evaluating")`.
- `LetData` `value`, when Kiln holds one, is not written and the unit is
  `Pending(Demand)`.

## Language linkage, an unknown language

- A `LinkageSpec` whose language byte is no `LinkageLang` makes the unit
  `Unaccounted("ScopeData/aux-lang")`. The key's `c_linkage` rule treats
  such a specification as not C.

## `decl` in a block (`local::write_decl`, §2.4)

- `Var` with `local_extern` writes `ref`. `Function` writes `ref`, then
  `count` and one `child?` per parameter: the default arguments that
  declaration holds. This is an addition to §2.4. A block-scope
  declaration's defaults are its own ([dcl.fct.default]/4) and are not
  in the entity's unit, so without it they would be nowhere (unit test
  `a_block_scope_entity_with_linkage_is_a_ref`; pair test
  `differ/_/block-scope-default-own`, `# pending`, stmt).
- `Var`, `ParmVar`, `Binding`, `Label` and `ContractResultName` write
  their ordinal, then their stream. `StaticAssert`, `ConstevalBlock`
  (legal at block scope in C++26; Kiln builds it, kiln_sema
  templ/subst/stmts.rs:927; unit test `a_consteval_block_in_a_block`),
  the three template parameter kinds and `LifetimeExtendedTemporary`
  write their stream and no ordinal.
- These kinds write nothing: `Typedef`, `TypeAlias`, `NamespaceAlias`,
  `Using`, `UsingShadow`, `ConstructorUsingShadow`, the three
  `UnresolvedUsing*` kinds, `UsingEnum`, `UsingDirective` and `Empty`.
  Each one names an entity, and the uses that follow are written by what
  they resolve to.
- A local type and what only a local type holds (`CXXRecord`, `Enum`,
  `EnumConstant`, `Field`, `IndirectField`, the four method kinds,
  `Friend`, `AccessSpec`, `FunctionTemplate`) are `Pending(Local)`.
- The kinds Kiln does not build are `Unsupported("DeclKind/<row>")`:
  `UsingPack`, `FriendTemplate`, `ImplicitParam` and
  `ImplicitConceptSpecialization`. Any other kind is
  `Unaccounted("decl/kind")`. Each of these writes the placeholder
  `uv 0`. Unit tests are in `local::tests`.

## Tests whose pair changes more than the row

- `differ/FnSpec/0-defaulted`, `differ/Defaulted/No` and
  `differ/Defaulted/Implicit` cannot change the tag alone. Their
  `expect.txt` says what else changes. The unit test
  `fn_spec_defaulted_tag` isolates the tag.
- `differ/FnSpec/0-trivial` changes only the bit: its member's copy
  constructor is constexpr and noexcept on both sides.
