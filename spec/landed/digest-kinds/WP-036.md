# WP-036 — dependent expressions, profiles and requires-expressions

What `crates/slip_digest/src/expr_dep.rs` reads into
`spec/digest-kinds.md` §7 (the names and constructs of templates), §9.3
(`RequiresData`, `Requirement`) and digest §4.4 (canonical expression
operands) where they are silent, and where it departs from the letter of
WP-036. Where a fact could not be settled, the unit is indeterminate.

## Profiles (§4.4)

- **The state put aside.** `profile_expr` takes the stream's expression
  state with `Walk::take_expr_state` (opaque numbering, dependent depth,
  the frame of an enclosing profile), installs a fresh
  `expr_dep::Frame` in `walk::ExprState::profile`, walks the expression,
  and puts the saved state back. A profile therefore gives the same bytes
  wherever it is written, whatever the enclosing unit has numbered.
  `ExprState::is_fresh` is false while a frame is installed.
- **What a frame numbers.** Entities declared inside the profile (a
  requires-expression's parameters) are numbered from 0 in order of
  declaration and written as `Ref::local` with that number
  (`profile_local`, reached from `Walk::write_ref`'s local-object branch).
- **Function parameters declared outside.** A `ParmVar` that is not the
  frame's is `Ref::param` (function-scope depth, position: `ParamData`),
  what Kiln's own profile words (`kiln_ast` `types/profile_expr.rs:27`)
  and the Itanium `fL<L>p` mangling read (`kiln_ast` `decl.rs:1495`):
  `decltype(a + b)` in `f(T a, T b)` and `decltype(b + a)` in `g(T b, T a)`
  are equal, `decltype(b + a)` in `h(T a, T b)` differs.
- **Any other local entity** takes the unit's ordinal (`local::ordinal`)
  and counts as a local use; in a key it is
  `Unaccounted("key/local-ref")`. A frame that numbered entities and also
  wrote a unit ordinal is `Unaccounted("profile/local-mix")`: two
  numberings in one stream could collide.
- **A requires-expression in a key** with no frame opens its own frame
  for its parameters, since a key holds no ordinal of a unit.
- **Known limitation.** A type digested inside a profile puts the frame
  aside with the rest of the expression state, so a frame parameter named
  from a nested type (`decltype(x)` in a requirement's type) is written
  as `Ref::param`; correct for equality, coarser than the frame.
- **Parentheses (departure).** The outermost parenthesis of every profile
  is kept (`expr::child_keep_paren`), not only `DependentDecltype`'s:
  Kiln's profile keeps parentheses (`profile_expr.rs:27`), and for a
  trailing requires-clause or a default argument it costs nothing.
- **`ProfileEntry.first_expr` absent.** Only the sentinel entry 0 of the
  profile table lacks one (`kiln_ast` `types/profile.rs`
  `ProfileTable::new`; `types/context.rs:1422`, and `:1426` returns id 1
  on exhaustion, never 0). No `ProfileId` names it: `uv 0` and
  `Unaccounted("ProfileEntry/first_expr")`; the row stays in
  `tests/tables/untested.txt`.

## Stored results (`RequiresExpr.aux`, `ConceptSpecializationExpr.aux`)

- **Decision: `in`, written as `uv` 0, 1, 2** (`ExprArena::satisfied`,
  `kiln_ast` `expr.rs:3134`). A value over 2 is `Unaccounted`.
- **Where it is set.** At the expression's own analysis
  (`kiln_sema` `sat.rs:1321`, `actions.rs:1737-1738`, `requires.rs:257`),
  write-once (`kiln_ast` `expr.rs:3130-3165`). The result can move with a
  use elsewhere only through the satisfaction cache, and only for a
  program that is ill-formed, no diagnostic required
  ([temp.constr.atomic]/3); a use elsewhere checked afterwards does not
  change it (`demand/_/requires-result-checked-elsewhere`,
  `demand/_/concept-result-checked-elsewhere`).
- **Tests.** The instantiated initialiser of a variable template lives in
  its `definition` unit, which is pending demand: the pair tests of the
  two `aux` rows are pending, and `expr_dep_tests::stored_results` checks
  0, 1 and 2 at the stream.

## Kinds

- **Names.** `expr_dep::decl_name` turns a raw `DeclName` into the
  `Name` of §3.2 exactly as `Walk::plain_name` names a declaration
  (checked over every kind of name by
  `expr_dep_tests::a_raw_name_is_the_declarations_name`). A destructor
  name carries no type (`Name::Destructor`), as a declaration's does.
- **`UnresolvedLookupExpr.b`** is written sorted (`write_refs_sorted`):
  the set found at the definition, not Kiln's order.
- **`CXXDependentScopeMemberExpr.aux`.** `arrow` is `in`;
  `template-keyword` is `out` by the table and untested: Kiln rejects
  `t->f<int>()` without `template` in a dependent context, so the bit
  cannot change alone (`differ/_/dependent-member-template-keyword`
  changes the parse instead).
- **`SubstNonTypeTemplateParmExpr`, `SubstNonTypeTemplateParmPackExpr`,
  `FunctionParmPackExpr`** are built in keep mode (`kiln_sema`
  `subst/exprs.rs:2616`, `:2748`); their pair tests reach them through a
  member template of an instantiation's `decltype` profile. The pack of
  `FunctionParmPackExpr.a` is `Ref::param`, as `size_of_pack_origin`.
- **`SizeOfPackExpr`.** The instantiated form is `TemplateTables`
  `size_of_pack_origin` and `size_of_pack_partial`, written by
  `templ::expr_maps` (`kiln_sema` `pack.rs:860-955`); `b` non-zero is
  `Unaccounted`.
- **`CXXExpansionSelectExpr`.** Kiln builds the node only with
  `ExpansionForm::Dependent` or `Enumerating` (`kiln_sema`
  `expansion.rs:248`, `:1142`); `Iterating` and `Destructuring` are the
  statement's, and their rows stay untested for the statements' package.
  The node is in function bodies only: its pair tests are pending stmt,
  `expr_dep_tests::expansion_select_form_and_depth` checks form and depth.
- **`LambdaExpr`** writes its closure whole through `local::write_decl`;
  pending local.

## Hooks outside the file

- `walk.rs`: `ExprState::profile: Option<expr_dep::Frame>`, and
  `is_fresh` requires it `None`.
- `refs.rs`: `Walk::write_ref`'s local-object branch defers to
  `expr_dep::profile_local` while a frame is installed.

## Tests found broken by this package

- `differ/FnSpec/0-not-selected` compared two destructors whose trailing
  requires-clauses differed: the clause is now in the key (§3.3), so the
  two were different entities. Rewritten so the constraint's variable
  template changes, not the clause.
