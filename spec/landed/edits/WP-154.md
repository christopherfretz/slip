# WP-154 — a rename declares the dependent tokens it respelled; nothing is withdrawn

The design proposal of stage 0 ([docs/wp/WP-154.md](../../../docs/wp/WP-154.md)),
**as revised after its independent design review and the supervisor's
rulings** (the section "The design review and the rulings" maps each
finding to where it landed). Nothing here is built. It answers the
package's eight items in their order, then gives the build's stages,
what is asked of Kiln, where each finding of the review landed, and
what is still the supervisor's to rule. Kiln was read at `4a83f6e3c`
(Slip's pin). Three throwaway probes were run by the designer and six
runs by the reviewer; what they showed is in §0.3 and is cited where a
decision rests on it.

Words used throughout:

- A **dependent name** is a name in a template's (or a generic
  lambda's) pattern that has no entity until instantiation. In Kiln's
  tree it is the name word of an expression of kind
  `UnresolvedLookupExpr` (the unqualified callee of a dependent call,
  `f(t)`), `DependentScopeDeclRefExpr` (`T::f`) or
  `CXXDependentScopeMemberExpr` (`t.f`, `t->f`, `this->f` with a
  dependent base). These three are the **dependent name nodes**. A
  rename of a function or a variable never binds a name written in a
  type-name context (`typename T::f`), so type contexts are not part of
  this design.
- An **entry** is an entry of Kiln's written-reference table (Kiln
  `spec/ast.md` §18). An entry **without a referent** and with the flag
  `DEPENDENT` is a dependent name as it was written. Its **name range**
  is the file range of its name token as `spec/verify.md` §10.2 rule 2
  defines it (one file, tier 0 or 1, through Kiln's
  `editable_file_range`).
- A **pattern node** of an entry (Kiln `spec/ast.md` §18.9.4) is a node
  Kiln made from that entry's name: the node the parser built, and each
  node a substitution rebuilt from it that is still dependent.
- **Full walk** and **profile mode** are the digest's two ways of
  writing an expression: in a unit's stream as written
  (`crates/slip_digest/src/expr_dep.rs`), and inside a canonical type or
  a key, where Kiln's profile decides what is told apart
  (`crates/slip_digest/src/expr_profile.rs`, `spec/digest-kinds.md`
  §4.4). A **canonical operand** (the operand of `decltype`, an array
  bound, a dependent template argument) is identified by its
  **profile**: Kiln's canonical form of the expression, which two
  spellings of the same structure and the same names share. Kiln keeps,
  per profile, the expression of the **first spelling** the translation
  unit has of it; each use keeps its **own operand**, the expression
  node written at that use (§2.3).
- A **row** is a row of Kiln's per-specialisation table (Kiln
  `spec/ast.md` §18.9, `WrittenRefs::specs()`): for a dependent entry
  and one specialisation the observer made, the entity the name denotes
  there, or none if the name stayed dependent.
- An instantiation **keeps** an expression when the unit of the
  instantiation writes the substituted expression, so that a name in it
  is a reference to an entity. Where the instantiation's unit writes
  only the expression's **outcome** (the type a `decltype` gave, the
  value a bound had, whether a constraint was satisfied), the context
  is **outcome-only** (§3.2).
- `was` and `now` are the old and the new name of a rename.

## 0. The design in one page

### 0.1 What is proposed

**By site, on the post-image only.** `Declared` gains a list `tokens`.
A token says: *the bytes `[lo, hi)` of this file of the post-image are
the identifier `now`; where they are a dependent name, that name was
spelled `was`.* The walk of the post-image writes the name of a
dependent name node as `was` when the node is a pattern node of an
entry whose name range is a token's and whose name is that token's
`now`. No unit is exempt for a token: `Declared.changed` is not used by
the rename at all.

- The pre-image is not walked again: its digests are the map phase's,
  made before the transform runs (`spec/edits.md` §8.1). The mapping is
  applied to the post-image only, as a rule is (`spec/digest.md` §3.4).
- The decision is per node, through the relation Kiln already records
  (entry to pattern nodes). There is no holder. The unit whose stream
  writes the node gets the old name, whichever unit that is.
- **A name inside a type is respelled per use, from the operand the
  unit itself wrote** (§2.3). Kiln keeps, beside the canonical type
  that all spellings of one profile share, the expression each use
  wrote (probe 3, §0.3). The walk writes a type's bytes from the use's
  own operand where that operand holds a declared node, and from the
  canonical form, unchanged, everywhere else. The first spelling of a
  profile decides nothing. The first version's mark `respelled`, its
  list entry `undeclared` and its four-row table are withdrawn.
- A key is made from the same types by the same writer, so a token in
  a trailing return type, a parameter type or a trailing
  requires-clause gives the post-image entity its pre-image key. No
  key-to-key rule exists.
- **The pattern's spelling is one thing; what the name binds is
  another.** Mapping the token makes the pattern's unit equal. Whether
  the name still binds what it bound is shown only by an instantiation
  whose unit keeps the expression. So three things are added to the
  trusted base (§3, §6):
  1. **The kept list.** The specification marks the contexts in which
     an instantiation's unit writes the substituted expression. A
     context that is not marked is **outcome-only**. The list fails
     closed: a context nobody listed is outcome-only.
  2. **The obligation.** For every specialisation Kiln's rows give for
     a declared entry, the entity the name binds there must be the
     subject of a declared rule that renames `was` to `now`. Otherwise
     the run is not verified, and the finding names the specialisation
     and the entity.
  3. **Vouching, computed by the verify job from its own parse.** A
     token is vouched in an observer when every entry declared for it
     there has a row with an entity and sits in a kept context. A token
     some observer reads and does not vouch is residue; the result is
     `verified_with_residue` at best. Nothing is decided from the edit
     set.
- **The rename edits a dependent name only in a kept context.** A site
  in an outcome-only context stays `unresolved`, with that reason
  (§5.2).
- What the walk reads that it did not read before: once per parse, the
  entries without a referent, their pattern nodes and their rows; per
  dependent name node written, one lookup by node id; per written type
  that is instantiation-dependent, its own operands. With no token it
  reads none of it and no byte moves; `scheme` stays 2 (§7).

### 0.2 What it gives

For the reviewer's question (a name other than the declared tokens
binds another entity, or a declared token was edited wrongly, and the
run says `verified`):

- A name other than a declared token is written exactly as it is
  written today. `h(0)` in the holder of B1 is a resolved reference; its
  key moves; the holder is `changed`.
- A declared token edited wrongly, by where it is:

  | The token is | What the run says |
  |---|---|
  | in a kept context of a pattern the observer instantiates | the instantiation's unit is `derived_changed`, or the post-image does not parse |
  | in an outcome-only context, and some specialisation binds an entity no declared rule renames | `not verified`: the obligation fails and names the specialisation and the entity (§6.2) |
  | in an outcome-only context, every row passing | `verified_with_residue`: the token is residue, reason `outcome_only` (§6.3) |
  | in a pattern, or a copy of one, that an observer reads and does not instantiate | `verified_with_residue`: residue, reason `not_instantiated` |

- **`verified`, with a wrong token: no case is known.** A run is
  `verified` only when every token is vouched in every observer that
  reads it, and then every specialisation's unit holds the name as a
  compared reference.
- **`verified_with_residue`, with a wrong token**: the two residue rows
  above, which is what the state is for. §6.4 says exactly what is not
  seen.
- **The first version of this proposal claimed more.** It said that an
  instantiation always holds a resolved reference in the token's place
  and that one thing only stays unverified. The review showed a class
  of contexts where the instantiation holds only an outcome (§6.1); the
  five statements that said otherwise are corrected (the section "The
  design review and the rulings" lists them).
- **Loud for a correct rename** (a difference is reported, nothing is
  silent): a type Kiln computed and holds in canonical form only, where
  the unit has no operand of its own to read (no source is known to
  reach one; the enumeration the review found is closed in §2.3); one
  written type that holds two operands of one profile respelled
  differently; a name formed by a macro invocation. §6.5 lists them.
  The first version's false mismatch 2 (a second spelling of the same
  profile elsewhere in the translation unit, such as `<iterator>`'s
  `std::size` beside an owned `-> decltype(c.size())`) is gone: no
  unit's bytes depend on another unit's spelling.

## 1. What is declared

### 1.1 The four candidates

Each candidate is taken in the only form that fits the pipeline: the
pre-image's digests are made in the map phase before the transform runs,
so a candidate changes the walk of the post-image and writes the old
name there. (A symmetric form, "one word for both spellings in both
images", needs the pre-image walked again under the declaration and
makes every dependent `was` equal to every dependent `now`; it is not
considered further.)

- **S, by site.** `Declared` lists tokens (file, range, `was`, `now`).
  The walk writes `was` for a dependent name node made from the entry at
  a token's range.
- **H, by holder and name.** `Declared` lists `(holder key, was, now)`.
  While the walk writes the stream of the unit with that key, every
  dependent name spelled `now` is written `was`.
- **N, by name everywhere.** `Declared` lists `(was, now)`. Every
  dependent name spelled `now`, in every unit of every observer, is
  written `was`.
- **E, by entry.** `Declared` lists `(owner key, ordinal, was, now)`:
  the `ordinal`-th dependent entry of the declaration `owner`, as
  WP-153's proposal names an entry (`spec/landed/digest/WP-153.md`
  §3.5, on that package's branch).

### 1.2 The programs

`S::f` (or `n::f`) is renamed to `h` in each. "Good" is the correct
rename; a "bad" edit is named where one is used.

**P1, the reviewer's B1.**

```cpp
int h(int) { return 10; }
namespace n {
struct S { static int f(int) { return 1; } };
struct U : S {
  int u() { auto l = [](auto t) { return t.f(1); }; return l(S()) + h(0); }
};
}
```

**P2, its namespace form.**

```cpp
int h(int) { return 10; }
namespace n {
struct A {};
int f(A) { return 1; }
int f(int) { return 2; }
int u() { auto l = [](auto t) { return f(t); }; return l(A()) + h(0); }
}
int w() { return n::u(); }
```

**P3, B2: a discarded branch.**

```cpp
int h(int) { return 10; }
namespace n {
struct S {
  static int f(int) { return 1; }
  template <class T> static int call(T) { if constexpr (sizeof(T) > 100) return h(0); else return T::f(1); }

int w() { return n::S::call(n::S()); }
```

**P4, B2: a default argument no call uses.**

```cpp
int h(int) { return 10; }
namespace n {
struct S {
  static int f(int) { return 1; }
  template <class T> static int call(T, int k = h(0)) { return T::f(1) + k; }
};
}
int w() { return n::S::call(n::S(), 3); }
```

**P5, B2: another observer's copy.** `t.h` is read by two observers;
`b.cpp` defines `B_SIDE` and instantiates nothing.

```cpp
// t.h
int h(int) { return 10; }
namespace n {
struct S {
  static int f(int) { return 1; }
  template <class T> static int call(T) {
#ifdef B_SIDE
    return h(0) + T::f(1);
#else
    return T::f(1);

  }

}
// a.cpp:  #include "t.h"            int a() { return n::S::call(n::S()); }
// b.cpp:  #define B_SIDE  #include "t.h"   int b() { return 0; }
```

**P6, a mixed holder.** `X::f` is not renamed. Good edits the first
name only.

```cpp
struct S { int f(int) { return 1; } };
struct X { int f(int) { return 2; } };
template <class T, class U> int m(T t, U u) { return t.f(1) + u.f(2); }

```

**P7, a holder that already has a dependent `h`.**

```cpp
struct S { int f(int) { return 1; } };

```

**P8, a wrong edit.** P6 with both names edited and both declared
(`u.f` should have been kept). P8a: as written, `m(S(), X())` is

**P9, a name in the key.**

```cpp
template <int N> struct Arr {};
```

P10b: one template declared twice with `decltype(t.f(1))`; a bad edit

**P11, a generic lambda inside a function template.**

### 1.3 The walk through

"equal" and "differ" are the comparison of the unit that holds the
name in the post-image against the pre-image, with the rename's rule
`S::h` written as `S::f`. **Bold** marks a wrong answer: a false equal,
or a false mismatch of a correct rename.

| Program | S, by site | H, by holder and name | N, by name | E, by entry |
|---|---|---|---|---|
| P1 | `n::U::u` differs: the token is written `f`; `h(0)` is a reference whose key is now `S::f`'s, was `::h`'s | differs, the same way | differs, the same way | differs, the same way |
| P2 | `n::u` differs: `h(t)` is written `f` and its found set `{n::h(A), n::h(int)}` maps to the pre-image's `{n::f(A), n::f(int)}`; `h(0)` now names `n::f(int)`'s key | differs | differs | differs |
| P3 | `S::call` differs: `h(0)` in the discarded branch is a reference resolved at the definition | differs | differs | differs |
| P4 | `S::call` differs: `h(0)` in the default argument | differs | differs | differs |

### 1.5 The decision

**S, by site.** It is the only one of the four that says what the
ruling says ("these tokens change their spelling") and nothing more. It
is exact where H and N are loose (P6, P7), needs no holder where H needs
one per shape (P11, P12), and is independent of how an observer
preprocesses the file where E is not (P5): a token is a range of a
file, and a file is the same bytes for every observer.

What the alternatives would have bought, and why it was not enough:

- **H** avoids reading places. But the walk under rules already reads
  places to decide whether a rule applies (ownership reads where an
  entity is declared, `spec/verify.md` §2.1), and the spelled-entity
  check reads the post-image's written-reference table by name range
  (`spec/verify.md` §10.2). S reads the same table by the same function.
  H's price is a notion of holder that Kiln does not give reliably (the
  refusal `no_holder` of WP-139's first round existed because of it), a relation to derived
  units, type digests kept per holder, and a cycle for keys.
- **N** needs no list. Its false mismatch is not rare and its false
  equal is the whole program.
- **E** names an entry without a position, which is right for WP-153
  (`docs/wp/WP-153.md`), whose rows are compared between two images of
  one observer. Here the list is made once for a run and read
  by every observer, and ordinals are per observer. E also needs the
  join from an entry to the nodes the walk writes, which is all of S's
  machinery.

### 1.6 What "position-free" means after this

A digest still holds no position, and a unit's bytes do not depend on
where its text is. What the walk writes for a declared token is a name
(`was`). A place decides *whether a declared change applies to a node*,
as the place of a declaration decides whether a rule applies to an
entity. The pre-image's digests are untouched. Inserting a line above a
token changes the token list (it is derived per edit set), not a digest.

### 1.7 The rule

For a walk given a token list that is not empty (the post-image of a
verify job, and no other walk):

0. **The table must be there.** If the parse has no written-reference
   table with pattern nodes (Kiln's recording is off for the image, or
   it was made with `no_nodes`, Kiln `spec/ast.md` §18.8), no node can
   be told from another: the walk maps nothing and the verify job's
   verdict is `unverifiable` (§5.5).
1. **Declared entries.** For each entry of the unit's written-reference
   table that has no referent and the flag `DEPENDENT`, take its name
   range (`spec/verify.md` §10.2 rule 2: one file, tier 0 or 1; no range
   in a file Kiln re-encoded or in a buffer with no subject path). The
   entry is **declared for** token `T` if the range is exactly
   `(T.file, T.lo, T.hi)`, the file compared by subject path. One token
   can have several entries (a name in a macro argument substituted
   twice; a header included twice; a macro that defines two templates
   from one argument).
2. **Declared nodes.** For each pair `(PatternNode::Expr(e), entry)` of
   the table's pattern nodes whose entry is declared for `T`: node `e`
   is **declared for** `T`.
3. **Writing a name.** Where the walk writes the name of a dependent
   name node `e` that a unit holds itself, if `e` is declared for `T`
   and its name is the identifier `T.now`, the walk writes the
   identifier `T.was`. "Holds itself" is:
   - the full walk (the rows `ExprNode/UnresolvedLookupExpr.a`,
     `DependentScopeDeclRefExpr.b`, `CXXDependentScopeMemberExpr.b`);
   - profile mode over an expression the unit or the key was given as
     written (a trailing requires-clause, a template argument written
     straight into the stream);
   - profile mode over an own operand of a written type (step 4).

   It is never the canonical form: where the walk writes a profile from
   the expression Kiln kept of its first spelling, every name is
   written as it is, whatever is declared.
4. **Writing a type** that holds an own operand with a declared node:
   §2.3.
5. **What the token is worth** is recorded per declared entry, not
   written into any stream: whether the entry's nodes sit in a kept
   context (§3.2), and its rows with their entities (§6.2). They go to
   the shard section `token_use` (§5.5).
6. Nothing else is read or written differently. In particular: the
   found set of an unqualified call, the qualifier, the template
   arguments, the base of a member access, and every node that is not a
   dependent name node are written as today.

A token is **read** in a parse if step 1 finds an entry declared for
it.

**The failure mode of the join, stated once.** A node of the three
kinds that is *not* a pattern node of an entry declared for a token is
written as today, whatever its location and whatever its name. If it is
in truth the token's name (Kiln made the node from the entry and did
not record it), the unit that writes it has `now` where the pre-image
had `was`: the unit differs, and a correct rename is reported as a
difference. The join can fail loud; it cannot map a node Kiln did not
make from the entry.

The join is Kiln's own relation and not the node's location, although
at the pin the two agree for every parsed node (§0.3): `ExprNode::loc`
is documented as "the operator / start location", not as the name's;
and a node that is not dependent can share the location (the `f(t)` of
an instantiation, §0.3).

**Which nodes are pattern nodes: open until Kiln's list arrives.**
At the pin, every dependent node of the three kinds was a pattern node
of an entry in the eight shapes of probe 1, the twenty-three of the
review and the shapes of probe 3. No run found a node that is the
token's name and is not a pattern node, so no pair pins one; the
failure mode above is what such a pair would show. Kiln's
`spec/ast.md` §18.9.4 does not
say so today, and Kiln has given a **draft** of the exceptions it will
write there (its WP-3591). This subsection depends on that list; the
answers below are to the draft and are to be read again when the list
lands ("For Kiln" 1).

| # | Kiln's draft exception | Can a declared token's node fall in it? What the walk then does |

**Names the rule does not reach, each loud or inert:**

- **An overloaded member on an object that is not dependent**
  (`s.f(t)` in a template, `s` of a class type). The node is a pattern
  node of an entry (the review's `k11`), but the walk writes a
  reference to the member found and no name word. A token there maps
  nothing and needs nothing: the rule maps the reference.
- **A name formed by a macro invocation** (`t.ID(g)(1)`). The entry's
  name range is the invocation `ID(g)`. No token can equal it; the
  pattern is written with the new name and differs.
- **A name in a macro body.** No name range of tier 0 or 1; no token.
- **A name in a constructor template's pattern** in a class template:
  the pattern's unit is `Unsupported("kiln/pattern-mem-initializers")`
  on both sides today, with or without a token, so the comparison is
  indeterminate. An `UnresolvedMemberExpr` is `Unsupported` in the full
  walk in the same way.

## 2. Keys

### 2.1 The declaration reaches the key

A key's discriminator is made from types and expressions the entity
wrote (`spec/digest-kinds.md` §3.3, §3.4): the parameter types, a
function template's return type and template head, a trailing
requires-clause written in profile mode. The trailing requires-clause
is the entity's own expression, so step 3 of §1.7 respells it node by
node. The types are written by the rule of §2.3, from the signature as
the entity wrote it. So the post-image entity whose signature holds a
declared token gets the key its pre-image had. **No key-to-key rule is
needed, and none is proposed.** A specialisation's key has the
template's key as its parent and follows it.

Probe 2 shows what happens today without it (P9): the template's key,
the specialisation's and its definition's are each in one image only,
and every unit that refers to them differs by a reference.

That the key comes back says nothing about what the name binds in a
specialisation: the contexts that are in a key are outcome-only today
(§3.3 rows 25, 26, 35, 36, 40, 42, 43).

### 2.2 Collisions fail closed

- **Two templates that the edit makes one (P10a).** Kiln sees one
  template with two declarations in the post-image (their signatures
  are equivalent). It has one key, written from the entity's
  declaration the walk reads the signature of (the canonical
  declaration): `K(f)` if that declaration holds the declared token,
  `K(h)` if not. The pre-image has both keys. One is `removed` either
  way; if both declarations are definitions the post-image does not
  parse.
- **One template that a bad edit splits (P10b).** The post-image has
  two templates. One is written with `f` because it is spelled `f`; the
  other because its token is declared. Two entities with one mapped
  key: the collision of `spec/digest.md` §3.4, indeterminate.
- **One entity cannot get two decisions.** Its key is written once,
  from one declaration's signature.

### 2.3 A name inside a type: each use is respelled from its own operand

**What Kiln keeps.** A dependent type that holds an expression (the
operand of `decltype` or `typeof`, an array bound, an expression
template argument) is canonical by its profile. All spellings of one
profile in a translation unit share one canonical type, and Kiln keeps
for it the expression of the first spelling
(`TypeContext::expr_origins`, `arg_origins`). Beside that, the type
*as written* at each use is sugar over the canonical type and holds
the expression that use wrote: `TypeView::Decltype { expr, underlying }`,
`TypeOfOperand::Expr`, `ArgView::Expr { expr, profile }`, a dependent
array bound's expression. That expression is the use's **own operand**.
The digest reads own operands today, for the facts a profile leaves
out (`spec/digest-kinds.md` §4.4 "Spellings", `own_spelling.rs`).

Probe 3 (§0.3) ran the question at the pin. Each use had an operand
node of its own, with the dependent name under it recorded as a
pattern node of its own entry, in every shape tried: a trailing return
type, a member typedef and the uses of its name, a field, a local, an
enumeration's underlying type, a conversion function, an alias
template's pattern and a specialisation of it, an expression template
argument, an array bound in a parameter, a member template in its
pattern and in the instantiated class, and two operands of one profile
inside one written type. The canonical type was one, shared, with the
first spelling's node, in both include orders.

**The first version** had the walk respell the first spelling's
expression, so that one use's declaration decided the bytes of every
use of the profile, and closed what that opened with a mark and a list
entry. The review showed that this contradicts two sentences of the
specification (`spec/digest-kinds.md` §4.2 rule 1 and §4.4: the bytes
of a profile are not a function of the spelling Kiln met first), that
it reports one cause in two ways in two observers that include in
different orders, and that its "rare" false mismatch is met in every
translation unit that includes `<iterator>` when a member is renamed to
`size`, `begin`, `end`, `empty` or `data`. It is withdrawn whole.

**The rule.** In a walk given tokens, where the walk writes the digest
of a type it holds **as written** (the type of a declaration, a
signature, a cast, a friend: every place the walk has the type with the
sugar Kiln kept):

1. **Collect the own operands.** Walk the written type through all its
   sugar: elaborated types, the written arguments of a template
   specialisation, pointee, element, return and parameter types, and
   also *into* what a typedef, an alias or an alias template
   specialisation aliases, as written. (The own-spelling walk stops at
   a typedef, rule 4 of "Spellings", because another unit writes those
   facts. A type's bytes are written by every unit that uses the type,
   so this walk does not stop.) Only a type that is
   instantiation-dependent is walked. Each own operand is filed under
   the profile Kiln gives the use (the profile of the canonical form of
   that piece of sugar).
2. **No own operand holds a declared node: today's path.** The
   canonical type's digest, from the parse's memo, byte for byte as
   without tokens.
3. **Some do: the canonical type's stream is written again with an
   override.** The writer walks the canonical type as it does today.
   Where it would write profile `p` from the first spelling's
   expression and an own operand is filed under `p`, it writes that own
   operand instead, in profile mode, with step 3 of §1.7 applied to
   each node. A profile with no own operand filed is written from the
   first spelling, with no name respelled. The result is memoised per
   written type, never in the memo of canonical types (as the digest
   of an over-aligned type is memoised per written type today,
   `aligned_sugar_digest`).
4. **The mix is indeterminate.** If two own operands filed under one
   profile give different bytes under step 3 (one holds a declared node
   and the other, at the same place of the expression, a name that is
   not declared, or declared for another `was`), the writer cannot say
   which place of the canonical type each belongs to: sugar and
   canonical form need not line up place for place (an alias template
   may reorder its arguments). The unit that writes the type is
   `Unaccounted("spelling/respelled-mix")`: indeterminate, loud.
5. **A type Kiln derived from a written one takes that one's
   operands.** Three places hold a type in canonical form that Kiln
   derived from a type the same declaration wrote. Each is written with
   the override collected from its written source, and each is a row of
   the specification with a pair:

   | The canonical type | Its written source |
   |---|---|
   | a function's type in its key and its unit, where a parameter's type was adjusted (an array or a function type decays, and the adjusted type holds the canonical element type) | the return type as written and each parameter's type before adjustment (`ParamData::original_ty`) |
   | an enumeration's promotion type (`EnumData.promotion_type`) | its underlying type as written (`EnumData.int_type`, which keeps the sugar: probe 3) |
   | the type in a conversion function's name (Kiln interns the name by the canonical type) | the function's return type as written |

6. **Any other canonical form is never respelled.** A type the walk
   holds only in canonical form, with no written source this rule
   lists, is written as today, with `now`.

What follows from it:

- **A profile's bytes are again a function of the profile.** In a walk
  given tokens, what a unit writes for a type is a function of the
  profile and of the declared nodes of the spelling that unit holds; in
  no walk is it a function of the spelling Kiln met first. The two
  sentences the review cited are amended to say exactly this
  (stage 1's specification list).
- **An undeclared respelling cannot ride a declared one.** In

  ```cpp
  template <class T> auto k1(T t) -> decltype(t.f(1)) { return 0; }
  template <class T> auto k2(T t) -> decltype(t.f(1)) { return 0; }
  ```

  with both names respelled `h` and only `k1`'s declared, `k1`'s key is
  written from `k1`'s operand (`f`, declared) and `k2`'s from `k2`'s
  (`h`, not declared). `k2`'s pre-image key is `removed` and a key with
  `h` is `added`. Each name is judged where it was written, by the unit
  that wrote it.
- **A shared profile costs nothing.** An owned
  `template <class C> auto n(const C& c) -> decltype(c.length())` is
  renamed to `size`, in a translation unit that includes `<iterator>`.
  In the post-image the owned template and `std::size` share one
  canonical type. The owned template writes its own operand, respelled:
  `length`, the pre-image's bytes and key. `std::size` holds an operand
  in which nothing is declared: today's path, the canonical bytes,
  which are the bytes it had in the pre-image. That holds also where
  the first spelling Kiln kept for the shared type is the owned
  template's node, which is declared: the canonical path respells
  nothing (§1.7 step 3). Neither depends on which was first, so two
  observers that include in different orders agree.
- **The override cannot hide an undeclared respelling.** Every
  dependent name written inside a type is written by some declaration,
  and that declaration's unit either reads the name's node in its own
  operand, where it is judged alone (`was` if declared, `now` if not),
  or holds the type in canonical form only, where it is written `now`.
  Either way a name that was respelled and not declared makes the unit
  of the declaration that wrote it differ from the pre-image. Another
  unit that reaches the same profile through a declared operand is
  written `was` there; that is the declared token's doing, and the
  undeclared one is reported where it stands.
- **Several `(was, now)` pairs** (the review's S4). A node is respelled
  with the `was` of the token it is declared for and with no other. Two
  operands of one profile declared for different `was` give different
  bytes and are a mix (step 4). No rule tests a name against "the `now`
  of some token".

**Where the walk holds a type as written.** Every place the
own-spelling walk reads today (rule 3 of "Spellings": `absorb_type` in
a unit stream, from the written type its caller holds; a template
argument list and a default template argument as the unit holds them; a
partial specialisation's arguments as written), and the key writer for
a signature. The rule sits in the type writer, so it needs no list of
holders of its own: a caller that passes a type with sugar gets the
rule, a caller that passes a canonical type gets step 6.

**The three decisions of the existing mark.** The existing mark of a
type digest (`spec/digest-kinds.md` §4.4 "The mark") decides three
things. No second mark is added, and the mark itself is read as today.
With tokens:

| The mark's decision | The site | With a declared token there |
|---|---|---|
| `spelling/<site>`: a unit holds a canonical operand and no spelling of its own (rule 5 of "Spellings") | of 45 sites the review tried, one: **an enumeration** (`enum E : decltype(T().mf(1))`). Probe 3 shows which of its two types it is: the underlying type is kept as written, the promotion type is canonical. The other sites are those rule 2 of "Spellings" names as canonical-only: a bound, an address space or a pack index held as a profile; a canonical `noexcept`; a deduced type; a dependent `_BitInt` width. No source is known to reach one of them with a dependent name inside | the enumeration: step 5, the promotion type is written from the underlying type's operand; the unit is equal for a correct rename (pair `enum-underlying`). Any other such site: step 6, written `now`; the unit differs from the pre-image, which had `was`, and **a correct rename is reported `changed`** (loud limit 1) |
| `spelling/profile`: a profile written by its id into a unit stream | `expr_dep::profile` in a unit stream, which has the first spelling only | step 6, the same: written `now`, the unit differs. Part of loud limit 1 |
| `spelling/conversion-name`: a conversion function's name, which Kiln interns by the canonical type | `operator decltype(T::f())()` | the declaration's key and unit: step 5, from the return type as written, which has its own operand (probe 3); pair `conversion-name`. A *reference* to a conversion function by its name in a dependent expression has the canonical type only: step 6, loud |

So the loud limits of a name inside a type are three, each a reported
difference for a correct rename and none silent:

1. a canonical operand with no spelling of the unit's own and no
   written source (step 6; the rows above; no source is known to reach
   it);
2. the mix of step 4;
3. an own operand whose rebuilt node Kiln did not record as a pattern
   node (§1.7's failure mode). At the pin the one rebuilt operand
   tried, an alias template's specialisation, is recorded (probe 3).

Names in bodies (the full walk) are exact per node and have none of the
three.

**Alternatives that lost.**

- *The first spelling decides, with a mark and a list entry* (the first
  version). Withdrawn above.
- *The review's fallback for a shared profile*: the rename looks,
  before verification, for a dependent piece inside a type whose new
  name already occurs as a dependent name in a profile of the same
  structure, and leaves the site `unresolved` with that reason. The
  supervisor ruled it the fallback if the own node were not there. It
  is there (probe 3), so the fallback is not used: it would keep the
  order dependence in the trusted base and have the rename leave a
  name in every signature of the `size`, `begin`, `end` family.
- *Descend the written type and the canonical type side by side*, so
  that each place of the canonical type meets its own operand and the
  mix disappears. Sugar and canonical form do not line up through an
  alias template or a typedef without a second writer that follows
  both; it is the natural follow-up if a corpus meets the mix.
- *Type digests per holder.* Splits the memo by context and still needs
  a holder. Lost with H.

## 3. Units made from the holder, and what an instantiation keeps

### 3.1 Which units the declaration reaches

**"The holder" does not survive as a notion.** Nothing in `Declared`
names a unit, and the walk does not ask which unit it is in. The
relation that reaches a unit is: *the unit's stream, its key or a type
digest it holds writes a node that is a pattern node of a declared
entry.*

| Shape | The unit that holds the name | How the rule reaches it |
|---|---|---|
| a function or member function template's body | the template's unit | the parsed node, full walk |
| a generic lambda in an ordinary function (P1) | the enclosing function's unit | the parsed node, full walk |
| a generic lambda in a function template, instantiated (P11) | the template's unit, and `call<S>::<definition>` | the parsed node; the node rebuilt for `call<S>`, a pattern node of the same entry (§0.3) |
| a member template of a class template, the class instantiated | the member of the instantiation | the node rebuilt in its signature (§0.3) |
| a member alias (P12) | `M::type` | the alias's type as written, its own operand (§2.3) |
| an enumerator (P12) | `M::e` | the parsed node, full walk |
| `alignas` of a class template (P12) | `AL` | the parsed node, full walk |
| a default argument of a member (probe 2) | `D::d(int)` | the parsed node, full walk |
| a signature (P9) | the entity's key and unit | the signature as written, its own operands (§2) |
| an alias template's pattern, a template head's requires-clause | the alias template's unit; the template's key | profile mode over the unit's own expression. Kiln records the translation unit as the entry's enclosing declaration there; the rule does not read it |

This table says where the *spelling* of the token is compared. It does
not say that anything compares what the name *binds*. That is the next
three subsections, and the first version of this proposal had it wrong:
it said that every instantiation holds a resolved reference in the
token's place. It holds one only where the instantiation keeps the
expression.

`Keys::unit_of` and the refusal `no_holder` are gone from the rename
since WP-139's second review (`spec/edits.md` §4.2: value 12 is
unlisted). Nothing here brings them back.

### 3.2 Kept and outcome-only contexts

An instantiation is a derived unit of both images. Where its stream
writes the substituted expression, a name in it is a reference to the
entity it bound, the rule maps that reference, and a token that binds
something else is `derived_changed`. That comparison is what vouches
for a token. But Kiln does not keep every substituted expression, and
the digest does not write every one Kiln keeps: of a `decltype` the
instantiation's unit holds the type, of an array bound the value, of a
requires-clause the fact that the declaration was viable. There the two
images' instantiations are equal whatever the token binds, as long as
the outcome is the same (the review's case, §6.1).

So the walk must say, for each declared node, whether it sits where an
instantiation keeps the expression. **The rule is stated so that it
fails closed: a context is kept only when the specification lists it.**

- The walk reaches a node of a pattern's unit by a **path**: a *root*
  (the field of a declaration that holds an expression or a written
  type: a function's body, an initialiser, an enumerator's value, a
  bit-field's width, a default argument, the operand of `alignas`,
  `explicit` or a `static_assert`), then *steps* down (a child field of
  a statement or an expression; from WP-156 on, the holder of a written
  type and an operand site inside it).
- `spec/digest-kinds.md` gains a column **`instance`** on exactly these
  rows. They are rows the tables already have, one per field, because
  the completeness test of `spec/digest.md` §13 needs them. A row is
  marked **`kept`** when the specification asserts, and a pair shows,
  that the unit of an instantiation writes what the row holds as an
  expression walked in full.
- **Every other row is outcome-only**: a row nobody marked, a row Kiln
  adds at a later pin, every row of profile mode until a package marks
  it. No list of outcome-only contexts exists anywhere; a context is
  outcome-only by not being on the kept list.
- A declared node is **kept** if its root and every step of its path
  are marked. A declared node that the walk writes by a path with an
  unmarked step, or does not write at all, is outcome-only, and the
  first unmarked step is its **reason** (the row's name, printed in the
  report).
- An entry declared for a token is kept in a parse if every pattern
  node of it that the walk writes is kept (the parsed node, and each
  node a substitution rebuilt in a pattern nested in an instantiation).

In the walk this is one flag of the expression state: false at the
start of a unit, set at a marked root, cleared at an unmarked step and
on entering profile mode, read when step 3 of §1.7 respells a name.
With no token the flag is not computed.

- **The build of this package comes after WP-155 and WP-156 on the

## 4. Unqualified dependent calls

For `f(t)` the full walk writes: whether argument-dependent lookup
applies, the name, and the declarations found at the definition as
sorted references (`unresolved_lookup_expr`). In profile mode the name
is in the profile and the found set is an entry of the unit's own list.

Under a rename's declaration:

- **The name** is written `was` when the node is declared (§1.7).
- **The found set is written as it is**: the references of what the
  post-image found, each mapped by the rules. Nothing is added for it.
  - Every found declaration is a renamed subject (P2): the set maps to
    the pre-image's keys. Equal.
  - The set is empty in both images, the subject being found only by
    argument-dependent lookup (P13a). Equal.
  - Another declaration named `now` is visible at the definition
    (P13b), or one named `was` no longer is found: the sets differ and
    the pattern is `changed`. That is a true difference, since the set
    is what overload resolution starts from in every instantiation.
- **In an instance** the callee is a resolved reference. No name is
  written and no token applies; the rule maps the reference, and a call
  that now selects another function is `derived_changed`, where the
  call is in a kept context (§3.2).
- **Where Kiln records no row.** By Kiln's own statement (§0.3), an
  unqualified call resolved by argument-dependent lookup inside a
  constraint or a generic lambda has no per-specialisation row until
  its WP-3584. A token at such a name is "not instantiated" in every
  observer (§6.3): residue, and the rename leaves the name (§5.2).

Row 1 of `spec/edits.md` §9.4 (decide by the found set) is not built at
the pin; this design does not need it and does not change it.

## 5. Where it is written

### 5.1 `Declared`

```
Declared := rules, changed, created, removed, kept, files     as today (spec/verify.md §2)
            tokens: list<Token>     version 3: dependent names of the post-image that were spelled otherwise

Token := file: bytes     the subject path of the file (spec/verify.md §5.1): a canonical absolute path
         lo:   uv
         hi:   uv        lo < hi: the bytes [lo, hi) of that file in the post-image
         was:  bytes     the name before: one plain identifier (spec/api.md §6.1 rule 1)
         now:  bytes     the bytes [lo, hi): one plain identifier, hi - lo bytes long, not equal to `was`
```

- **Places are the post-image's.** The walk that reads them walks the
  post-image, as a rule matches the post-image's names and a `created`
  line is resolved in the post-image. In the overlay form the subject
  path is the real path; in the tree form it is the path the subject
  has for the post tree's file.
- **A `Declared` with tokens is bound to one post-image.** A rule holds
  for any image in which the entity has the new name; a token is a
  range of bytes of one image. The specification says so in
  `spec/verify.md` §2: a container with tokens is for the post-image it
  was derived from, and a token that does not fit another image is
  inert there (it declares no node, §7), never wrong.
- **Order.** Sorted by `(file, lo)`; within one file no two tokens
  share a byte. A list may hold several `(was, now)` pairs.
- **Version rule.** `tokens` is version 3 of `DECL`. A reader reads
  versions 1 and 2 as today, with `tokens` empty. **A writer writes
  version 3 only when `tokens` is not empty**, and a version 3 container
  with no token is refused, so that every value has one encoding and no
  container that exists today changes a byte or its id. (The
  alternative, always writing version 3 as WP-110 did for version 2,
  moves the id of every declared container, the empty one included,
  for nothing.) `dump` and `undump` keep a file's version.
- **JSON.** A member `tokens` after `files` in version 3: a list of
  `{"file": bytes, "lo": n, "hi": n, "was": bytes, "now": bytes}`.
- **The reader's checks**, after the six of `spec/verify.md` §2, each
  at the token: 7. `not a canonical absolute path`; `lo is not below
  hi`; `was is not a plain identifier`; `now is not a plain
  identifier`; `now is not hi - lo bytes long`; `was is now`.
  8. `tokens are not strictly ascending` and `two tokens share a byte`,
  at the later token. 9. `a version 3 container without a token`.
- **Identity.** `tokens` is not part of `rules_id`: it is not a rule. A
  verify shard names the `DECL` container it was made with
  (`Binding.declared`, `spec/verify.md` §9.1), and the container's id
  covers the tokens.
- `tokens` does not need `rules` or `files` to be read. A token with no
  rule that renames `was` to `now` fails its obligation wherever it has
  a row (§6.2).

**Ruled (question 1): the tokens live in `Declared`.** The alternative
was the overlay, where apply derives obligations: a declared change
would then live outside the declared container, the tree form (which
has no overlay) and with it every pitfall row could not use it, and a
verify job would have two containers to reconcile.

### 5.2 The edit set, the rename, and `slip_reduce::declared`

- **A new piece**, `dependent = 4: (text: bytes, was: bytes)`: `text`,
  written as a dependent name that was spelled `was`. Both are plain
  identifiers and differ. It is added as the identifier piece was
  (WP-132): no change of format version; a reader of before refuses the
  unlisted tag as Malformed. It carries no key (§6.2: several rules can
  claim one token) and gives no spelled-entity obligation; the
  obligation of a dependent token is derived from the token itself.
- **Landings.** Each time the text of a dependent piece is written into
  a post-image, at its edit's own place or in a copy that carries the
  edit, that is one landing: the file, the range in the post-image,
  `was`, `text`, and the edit it came from. This is step 5 of
  `spec/edits.md` §7.1 for another kind of piece. Landings are a
  function of the edit set alone: every expansion's length is known
  without reading a file (`slip_apply::plan` computes the lengths so
  today).
- **§6.2 gains: `tokens` = the landings of the set's dependent
  pieces.** `slip_reduce::declared(set, ownership)` computes them, so
  `Declared` stays a function of the edit set and `check` can derive it
  again. The computation of where pieces land moves from `slip_apply`
  to `slip_model` beside the edit set (one implementation, used by
  apply for obligations and by reduce for tokens).
- The edit set keeps `changed` for a programmable transform's
  declarations. A rename has none (`spec/edits.md` §9.6, as WP-139
  merged).

**What the rename does (ruled, questions 3 and 5).**

- **It edits a dependent name only where the context is on the kept
  list.** In the map phase the digest's walk of the pre-image is asked
  for the context of each dependent entry (§3.2: kept, or the first
  unmarked step); the rename reads it beside Kiln's rows. Row 2 of
  `spec/edits.md` §9.4 is decided as today for a kept site, with a
  dependent piece where it wrote a literal one. **A site whose context
  is outcome-only is `unresolved`, with the reason `outcome_only`**,
  whatever its rows say. It is then residue `dependent` by
  `spec/edits.md` §8.4, and the report says why it was left.
- **Format.** `Reason` gains `outcome_only` (the next free value; 12
  stays unlisted). It is the one reason a claim of stance `unresolved`
  may carry; reduce keeps it per place with the row's name, in a list
  of the edit set beside `unresolved` (a new version of `EDTS`, written
  only when the list is not empty, by the version rule of §5.1; the
  exact record is stage 4's). An observer that reads the site as kept
  and one that reads it as outcome-only (two preprocessings of one
  file) join as `replace` and `unresolved` do today: the edit is made,
  and verification makes the token residue in the observer where it is
  outcome-only (§6.3). The rename's reading is a convenience; the
  verify job decides on its own.
- **The default.** `dependent: offer` becomes the default again when
  stage 4 passes: it now edits kept sites only, and a run that edits
  them can end `verified`. `leave` and `refuse` stay.
- **No holder.** The refusal `no_holder` is not needed for anything:
  an alias template's pattern and a template head's requires-clause are
  outcome-only contexts (rows 46 and 35 of §3.3) and are left
  `unresolved` for that reason.
- **A site Kiln gives no row.** By Kiln's own statement (made at its
  queue tip, 31 commits past Slip's pin; not run here), an unqualified
  call resolved by argument-dependent lookup inside a constraint or a
  generic lambda records no row, at the pin and at the tip; a qualified
  call does; Kiln's WP-3584 adds the row. Until then the rename, which
  plans from rows, leaves such a name `unresolved`; a hand-made token
  there is "not instantiated" (§6.3), residue. A pair pins it (§8.1).

### 5.3 `check --declared` given

**Ruled (question 4): refuse.** A declaration given with an edit set
must have exactly the tokens the set derives (equal in file, range,
`was` and `now`). A token the set does not derive, or a derived token
that is missing, makes the input inconsistent: the command stops with
an input error that names the token,

```
slip: <declared file>: token <path>:<lo>-<hi> <was> -> <now> is not derived from the edit set
slip: <declared file>: the edit set derives token <path>:<lo>-<hi> <was> -> <now>, which the declaration lacks
```

and nothing is verified. Nothing is dropped in silence. The harness's
oracle, which gives a mutated edit set to `check` with the original's
declaration (`spec/harness.md` §6.4), must derive the declaration again
when the mutation changes a dependent piece.

In the tree form (`slip verify --declared` on two trees) there is no
edit set: the tokens are simply given.

A token cannot do more than its words say, whoever wrote it: the most a
token excuses is that a dependent name at its range, spelled `now`, is
read as `was`; and it brings its own obligation with it (§6.2).

### 5.4 `slip verify --declared` on two trees

**Usable.** There is no overlay and no edit set, and none is needed:
the places are the post tree's. `slip declare` (`spec/verify.md` §2.3,
outside the trusted base) gains a line

```
respelled <was> => <now> @ <path>:<line>:<column>
```

resolved in the post-image: `<path>` relative to the root, the place
that of the token's first byte. The raw-lexed token there must be the
identifier `<now>`; if it is not, the line fails with a new error
`NoToken`, which a pitfall row's runner treats in a `bad` tree as it
treats `NoUnit` (the line is left out; a missing declaration can only
add findings).

### 5.5 The verify job, the shard, the run

- **The parse.** §5.2 step 1 of `spec/verify.md`: the walk is given
  `Declared.tokens`. The parse records written references with pattern
  nodes when the list is not empty, as it records them when the overlay
  has obligations. Step 6 walks the same way. The pre-image parse of
  step 4 is given none.
- **A new guard.** If the token list is not empty and the post-image
  parse has no written-reference table with pattern nodes (Kiln's
  recording is off for the image, or `no_nodes`, Kiln `spec/ast.md`
  §18.8), the walk cannot tell a declared node from any other. The
  verdict is `unverifiable`, reason `post-image: no pattern nodes
  recorded; the declaration has tokens`. No token is mapped.
- **A new section of a verify shard, `token_use`** (the next free id,
  33 at this writing), present when the outcome is `ok` and `tokens`
  is not empty:

  ```
  TokenUse  := tokens: list<TokenSeen>     the tokens this parse reads (§1.7), strictly ascending by `token`
  TokenSeen := token:   uv                 index into Declared.tokens
               entries: list<EntrySeen>    one per entry declared for it, in the table's order; at least one
  EntrySeen := rows:    uv                 rows of the entry that have an entity
               kept:    bool               §3.2
               reason:  str                the first unmarked step when not kept, else empty; for the report
               failed:  list<FailedRow>    §6.2; in the rows' order; at most `rows`
  FailedRow := spec:      opt<KeyId>       the specialisation's key under the rules, if it has one
               spec_name: str              the specialisation as a person would write it (spec/verify.md §6.1)
               found:     opt<KeyId>       the key, under the rules, of the origin the name binds there
               name:      str              that entity; both names for the report only
  ```

  An entry is **vouched** when `rows` is not 0 and `kept` is true;
  **not instantiated** when `rows` is 0; **outcome-only** otherwise
  (§6.3). Everything in the section is read from the parse the job
  made; nothing is read from the edit set.
- **The run folds it** (`slip_verify::run`), over this run's `ok`
  shards whose state is `verified` or `mismatch`, as §10.3 of
  `spec/verify.md` folds spellings. Per token: `read`, the observers
  that read it; `vouched`, those in which every entry is vouched;
  `not_instantiated` and `outcome_only`, those with an entry in that
  state; the failed rows, grouped by (specialisation, entity) with
  their observers. A token with `read` 0 is **unused**.
- **The verdict.** A run with a failed row is **not verified**: one
  more condition of `spec/verify.md` §9.3, beside a failed spelled
  entity. An unvouched token does not change the run's verdict, which
  is about the comparison; the run report carries the counts, and what
  a command makes of an unvouched token is the command's (§5.6): a
  transform concludes `verified_with_residue`, and `slip verify` on
  two trees does not exit with status 0.
- **A shard is this run's** only if its `token_use` is present exactly
  when the declaration has tokens, names no token past the list, and
  names only tokens whose file its `inputs` list; else the observer is
  `failed` (as §9.3 does for `spellings`).
- The comparison (`spec/verify.md` §4) does not change at all.

### 5.6 The reports

**The verify phase's report** (`spec/verify.md` §7.1), which is all a
tree-form run has. A JSON member `"tokens"`, present when the
declaration has tokens, and in the text:

```
tokens: <n> declared, <n> unused, <n> not vouched, <n> failed
token <was> -> <now>: <path>:<lo>-<hi>: read <r>, vouched <v>[, not instantiated <u>][, outcome only <o> (<reason>)][ (unused)]
token failed <was> -> <now>: <path>:<lo>-<hi>: <specialisation> binds <entity>, which no declared rule renames (<n> observer(s), first <main file>)
```

`read`, `vouched`, `not instantiated` and `outcome only` count
observers; a token line is printed for every token (at most 200, then a
count). A failed row makes the verdict `not_verified` and status 1.

**The tree form has no state for residue**, and its status 0 must not
come to mean less than it means today: without the token the respelled
pattern is a mismatch. So `slip verify` given a declaration with tokens
ends **`incomplete`, status 4** (`spec/exec.md` §8.5), when every
comparison is `verified` and some token is read and not vouched; the
summary line says `verified, <n> token(s) not vouched` and the token
lines say where. This is the designer's choice within the ruling (both
forms print the counts) and is open question 2; the alternative is
status 0 with the same lines. A pitfall row's `good` tree must
therefore have its tokens vouched, which a row in an outcome-only
context cannot have until that context is kept (§8.4).

**The transform's report** (`spec/edits.md` §10.5). A rename has no
`exempt` line (WP-139 as merged). It gains:

```
declared <id>: rules <n>, exempt <n>, tokens <n>
tokens: <n> respelled, <n> unused, <n> not vouched, <n> failed
token <was> -> <now>: <path>:<line>:<column>: read <r>, vouched <v>[, not instantiated <u>][, outcome only <o> (<reason>)][ (unused)]
token failed <was> -> <now>: <path>:<line>:<column>: <specialisation> binds <entity>, which no declared rule renames (<n> observer(s), first <main file>)
left outcome-only <path>:<line>:<column>: <reason> (<n> observer(s), first <main file>)
residue dependent: <path>:<line>:<column>[ (not instantiated)][ (outcome only)]
```

- One `token` line per edit that has a dependent piece, at the edit's
  pre-image place (lines and columns from the pre-image file, as every
  other line); its counts are the fold's, summed over the edit's
  landings (an observer that reads two landings of one edit counts
  once, and vouches only if it vouches both).
- **The result.** `RSLT` gains the fold's token records (a new version;
  conclude copies them from the trusted run report and decides none,
  as it does for `spellings`). A token that some observer reads and
  does not vouch adds a residue entry of category `dependent` at the
  edit's place, with its reason; so the state is
  `verified_with_residue` (row 4 of `spec/edits.md` §8.5) and writing
  needs `--allow-residue`. A failed row gives `not_verified` through
  the verdict (row 2).
- The `instances:` heading and its `instance` lines are WP-139's and
  stay: they are the rename's evidence, from the map phase. They decide
  nothing here. The heading loses its last clause ("the run cannot
  verify a name edited here until dependent names are compared
  mapped").
- A `left outcome-only` line per site the rename left for that reason
  (§5.2), with the row of §3.3 that would have to be kept.
- An unused token is reported and changes no state.

## 6. What is verified, what is residue, what stays unverified

The first version of this section said "one thing stays unverified, and
nothing else". The review showed a class it had missed (§6.1). This
version states three layers: a check that fails hard (§6.2), two
conditions that make a token residue (§6.3), and what is left when all
three pass (§6.4).

### 6.1 The case the first version missed

```cpp
// pre-image
template <int N> struct Arr {};
struct S { static constexpr int f() { return 1; } };
struct X { static constexpr int f() { return 1; }
           static constexpr int h() { return 1; } };
template <class T> struct M { using type = Arr<sizeof(T::f())>; int a[T::f()]; };
template <class T> int b(T t) { decltype(T::f()) x = 0; Arr<T::f()> y; return x; }
M<S> ms; M<X> mx; M<S>::type v1; M<X>::type v2;
int w() { return b(S()) + b(X()); }
```

An edit set renames `S::f` to `h` and respells all four `T::f` as
`T::h`, each a declared token. `X` is not touched. Every token is
wrong: in `M<X>` and `b<X>` the name bound `X::f` and now binds `X::h`.
With the tokens mapped the pattern units are equal; `M<S>::type`,
`M<X>::type`, `M<X>::a`, `b<X>::<definition>` write `Arr<4>`, `int[1]`,
`int x`, `Arr<1> y` in both images, with no reference to either
function. Every unit is equal. Without this section the run would be
`verified`, where today, with no mapping, it is loud because the
patterns differ. (The review ran it: `c4-outcome-only`; only the three
pattern units differ at the pin.)

The rename itself would not make this edit set (the sites are
contested: the rows say `S::f` in one specialisation and `X::f` in the
other). That is no defence. An edit set is not trusted, and `check`
exists to give the trusted base one that is wrong on purpose.

### 6.2 The obligation of a dependent token (trusted base)

`spec/verify.md` §10.2 rule 5 fails a spelled-entity obligation that an
unresolved name answers, because "the table does not say per
instantiation" what a dependent name denotes. Kiln's rows now say it,
and the walk of the post-image reads them for every declared entry:

> For each entry declared for token `T` in this parse, and each row of
> that entry that has an entity: take the entity's **origin**
> (`spec/verify.md` §10.2 rule 4, `slip_kiln::written::origin`: the
> template or the member of the template it was made from, a
> using-declaration taken to what it names). The row **passes** if the
> walk, under the run's rules and ownership, gives the origin its key
> through a rule that applies to the origin itself, whose `name` is the
> identifier `T.now` and whose `to_name` is the identifier `T.was`: a
> declared rule that renames `was` to `now`, in force. Otherwise the
> row **fails**: the specialisation's name binds something the run did
> not rename.

- **Several rules can claim one token.** The token names no entity and
  no key. A site where one specialisation binds `S::f` and another
  `X::f` is contested for a rename of `S::f` alone; a run that renames
  both has two rules, each row's origin is the subject of one of them,
  and every row passes.
- **A failed row is a hard finding.** It is recorded beside the verdict
  as a failed spelled entity is (`spec/verify.md` §10.2, last
  paragraph): it does not change the observer's digest verdict, and
  **a run with a failed row is not verified**. The record names the
  token, the specialisation (its key and its display) and the entity
  found (its key under the rules, if it has one, and its display).
- In §6.1 the rows `M<X> => X::h()` and `b<X>(X) => X::h()` fail:
  `X::h` is reached by no rule. The run is `not verified` and the
  report names `M<X>` and `X::h`.
- It reads the post-image only, the table the same parse recorded, and
  nothing from the edit set.

**It is one-sided, and this is what it misses.** It checks that what
the name binds *now* is a renamed subject. It does not check what the
name bound *before*.

```cpp
struct S { static constexpr int f(int)  { return 1; }     // renamed to h
           static constexpr int f(long) { return 1; } };  // kept
template <class T> struct M { using type = Arr<sizeof(T::f(1L))>; };
M<S> m;
```

Respell `T::f(1L)` as `T::h(1L)` and declare it. Before, the name bound
`S::f(long)`, which is not renamed; now it binds `S::h(int)` by a
conversion, which is the subject. The row passes. In a kept context the
instantiation's unit would differ (a reference to another function). In
this one, a member alias, the outcome is `Arr<4>` both times. The
two-sided check compares the pre-image's row with the post-image's per
specialisation; the pre-image's rows are at pre-image places and are
what the substitution units of WP-153 compare. It is not built here;
§6.3 is why the case is not silent.

It also checks nothing where Kiln has no row with an entity (§6.3
"not instantiated"), and it trusts the entity Kiln wrote in a row as
the spelled-entity check trusts a referent.

### 6.3 What makes a token residue

For a token `T` and an observer whose post-image parse has at least one
entry declared for `T` (the observer **reads** the token), each such
entry is in exactly one state, decided by the verify job from that
parse alone:

| State | When | What it means |
|---|---|---|
| **not instantiated** | the entry has no row with an entity | this observer made no specialisation in which the name was resolved: the pattern was not instantiated; or the name is in a branch every instantiation discards, in a default argument no call uses, in a member no one uses, in a generic lambda never called; or the header is included twice and this is the copy nobody instantiates; or Kiln records no row for the shape (an unqualified call resolved by argument-dependent lookup inside a constraint or a generic lambda, until Kiln's WP-3584) |
| **outcome-only** | it has such a row, and it is not kept (§3.2) | specialisations exist, and their units hold only the outcome of the expression around the name |
| **vouched** | it has such a row and it is kept | every specialisation the observer made holds the name as a reference in a unit that is compared |

The token is **vouched in an observer** when every entry declared for
it there is vouched. Over the run:

- A token that some observer reads and does not vouch is **residue of
  category `dependent`**, with the reason `not_instantiated` or
  `outcome_only` (both, if both occur). The result is
  `verified_with_residue` at best.
- A token no observer reads is **unused**: reported, and no state
  changes, because nothing was mapped on its account.
- Nothing here is decided from the edit set. The first version counted
  the edit set's `instances`; the review showed three ways that count
  is not zero while a copy of the pattern is not instantiated, and that
  the count is written by the rename and compared with nothing.

**Why outcome-only is residue and not a finding.** Nothing is known to
be wrong: the pattern is compared with the token mapped, the obligation
of §6.2 passed, and what remains is the one-sided gap. The state says
that the run did not see everything, which is what
`verified_with_residue` is for. The rename does not produce such a
token (§5.2): it leaves the name `unresolved`, which is residue
`dependent` already. A hand-made edit set can.

### 6.4 What stays unverified, exactly

**A declared token is verified in an observer only where an
instantiation of that observer keeps the expression that holds it.**
There, each specialisation's unit is compared and each row's entity is
checked. Outside that:

1. **Not instantiated.** Whether `now` denotes what `was` denoted when
   the pattern is instantiated is shown by no observer that does not
   instantiate it (P8b). Residue, per observer that reads the token.
2. **Outcome-only, one-sided.** The post-image's binding is checked
   against the rules (§6.2); the pre-image's is not. A token whose old
   binding was not the subject and whose new binding is, with an equal
   outcome, is not detected. Residue (§6.3); closed row by row as the
   contexts are kept (§3.4).
3. **A specialisation only a translation unit outside the run makes**:
   the limit of every reference, `spec/edits.md` §10.5.
4. **What Kiln's rows do not say.** A specialisation for which Kiln
   records no row although the name was resolved there is not checked
   by §6.2. If the entry has no row at all it is "not instantiated"
   (residue: fails closed). That is the state today of an unqualified
   call resolved by argument-dependent lookup inside a constraint or a
   generic lambda, by Kiln's own statement; its WP-3584 adds the row,
   and a pair pins the shape until Slip's pin has it. If an entry has
   some rows and lacks others, the missing ones are checked only by
   their units, where the context is kept. A row with a wrong entity
   is believed. ("For Kiln" 2.)

Limits that exist today and are not changed:

- What `now` finds in an instantiation other than the renamed entity (a
  capture) is loud today and is `docs/wp/WP-152.md`.
- A dependent name the rename leaves `unresolved` is residue
  `dependent`, as today.

### 6.5 What is loud rather than verified

A correct rename is reported as a difference in these shapes. Each is
stated where it arises; none is silent.

- A unit that holds a canonical operand by a type Kiln computed, with
  no operand of its own and no written source (§2.3 step 6; `changed`).
  No source is known to reach it.
- One written type with two operands of one profile that are respelled
  differently (§2.3 step 4, the mix: indeterminate).
- A name whose node Kiln made from the entry and did not record as a
  pattern node (§1.7, the failure mode of the join: `changed`).
- A post-image parse with no pattern nodes recorded, given a
  declaration with tokens: `unverifiable` (§1.7 step 0, §5.5).
- A name inside a macro invocation that forms the name's token
  (`t.ID(g)(1)`): the entry's range is the invocation, no token can
  equal it, and the pattern differs.
- A constructor template's pattern in a class template is
  `Unsupported("kiln/pattern-mem-initializers")` on both sides today,
  with or without a token: indeterminate. An `UnresolvedMemberExpr` is
  `Unsupported` in the full walk in the same way.

## 7. Inertness and scheme

- **With no token no digest moves.** Every change to the walk is behind
  "the token list is not empty": the entry scan, the name writers, the
  collection of own operands and the override of §2.3, the kept flag of
  §3.2, the reading of rows. A walk of a pre-image, of `slip parse`, of
  a verify job whose declaration has no token reads none of it. The
  post parse does not record written references on this account.
- **The column `instance`** of `spec/digest-kinds.md` (§3.2) is read
  only to classify a declared node. It changes no stream: a row's
  bytes are the same whether it is marked or not.
- **A token that matches nothing changes nothing** (the inertness of
  `spec/digest.md` §3.4 for rules, `crates/slip_digest/tests/inert.rs`):
  a token at a range where no dependent entry is, or whose `now` is not
  the node's name, declares no node; no name is written otherwise, no
  type takes the override path (step 2 of §2.3 is today's path, from
  the same memo), and the shard's `token_use` does not list it.
- **`scheme` stays 2.** No stream, key or table row changes for a walk
  without tokens, and no existing unit changes. Under a token list the
  only comparison that changes is that of a unit that writes a declared
  node (different before; equal now if nothing else moved). The rule of
  `spec/digest.md` §11 changes `scheme` before the first release only
  when units that compared equal under some rule table are made to
  differ; no comparison was ever made under a token list, and no
  baseline of scheme 2 is recorded. The cause
  `Unaccounted("spelling/respelled-mix")` can arise only under a token
  list.
- **Formats.** `DECL` version 3 only when there are tokens; a new piece
  tag; a new shard section present only when there are tokens; a new
  version of `EDTS`, written only when an `unresolved` entry carries a
  reason; a new version of `RSLT` (§5). A container written today is
  read as today. A run with no token and no such entry writes the
  bytes it writes today, except the version number of its result.
- **Cost with tokens.** Once per post-image parse: one pass over the
  entries without a referent (a name range each, the function the
  spelled-entity check already calls), one over the pattern nodes, one
  over the rows of the declared entries (an origin and a key each); a
  map from node id to token with one entry per declared node. Per
  dependent name node written: one lookup. Per written type that is
  instantiation-dependent: one walk of its sugar, memoised per written
  type, which is the traversal the own-spelling walk makes today for
  the same types. Recording written references in the post parse is a
  cost a rename's verify phase already pays for its obligations.

## Open questions

The six questions of the first version are ruled (the table above).
Two are new. The proposal is written with the rulings as given and
with the recommendation of each, so nothing waits for them:

1. **How much residue S1 makes on a real code base.** A token in a
   header template is read by every observer that includes the header
   and vouched only by those that instantiate the template with a
   class the rename touches. By the rule of §6.3, one observer that
   includes and does not instantiate makes the token residue. On a
   large code base that is most tokens in shared headers, so most
   renames that edit a dependent name would end
   `verified_with_residue` and need `--allow-residue`. The rule is
   right about what was seen: that observer's copy of the pattern was
   not shown to bind anything. A refinement the supervisor may want:
   *an unvouched (token, observer) is covered when every unit that
   writes a declared node of the token in that observer has the key
   and the digest it has in an observer that vouches the token* (the
   same pattern, preprocessed to the same thing, instantiated
   elsewhere in the run). It is sound in the sense of the run's
   whole-program statement and unsound for a pattern whose lookup
   differs per observer although its unit does not; the found set of
   an unqualified call is in the unit, the visible specialisations are
   not. **Recommendation: build §6.3 as ruled; measure the residue on
   the corpus in stage 3; rule on the refinement with the number in
   hand.**

2. **What `slip verify` on two trees says of an unvouched token.**
   The ruling says both report forms print the vouched and read
   counts. The tree form has three verdicts and no state for residue.
   §5.6 is written with: a run whose comparisons are all `verified`
   and that has a token read and not vouched ends `incomplete`, status
   4, with the lines. The alternative is status 0 with the lines.
   **Recommendation: status 4.** Without the token the same trees are
   a mismatch (the pattern differs), so status 0 would make silent, for
   a script that reads the status, what is loud today; and the
   transform already refuses to write such a result without
   `--allow-residue`. The price: a hand-made declaration for a header
   template that some observer does not instantiate cannot reach
   status 0, which is question 1 again.
