# WP-154 — a rename declares the dependent tokens it respelled; nothing is withdrawn

The design proposal of stage 0 ([docs/wp/WP-154.md](../../../docs/wp/WP-154.md)).
Nothing here is built. It answers the package's eight items in their
order, then gives the build's stages, what is asked of Kiln, and the
questions that are the supervisor's to rule. Kiln was read at
`4a83f6e3c` (Slip's pin). Two throwaway probes were run and deleted;
what they showed is in §0.3 and is cited where a decision rests on it.

Words used throughout:

- A **dependent name** is a name in a template's (or a generic
  lambda's) pattern that has no entity until instantiation. In Kiln's
  tree it is the name word of an expression of kind
  `UnresolvedLookupExpr` (the unqualified callee of a dependent call,
  `f(t)`), `DependentScopeDeclRefExpr` (`T::f`) or
  `CXXDependentScopeMemberExpr` (`t.f`, `t->f`, `this->f` with a
  dependent base). These three are the **dependent name nodes**. A
  rename of a function or a variable never binds a name written in a
  type-name context (`typename T::f`), so type contexts are not part of
  this design.
- An **entry** is an entry of Kiln's written-reference table (Kiln
  `spec/ast.md` §18). An entry **without a referent** and with the flag
  `DEPENDENT` is a dependent name as it was written. Its **name range**
  is the file range of its name token as `spec/verify.md` §10.2 rule 2
  defines it (one file, tier 0 or 1, through Kiln's
  `editable_file_range`).
- A **pattern node** of an entry (Kiln `spec/ast.md` §18.9.4) is a node
  Kiln made from that entry's name: the node the parser built, and each
  node a substitution rebuilt from it that is still dependent.
- **Full walk** and **profile mode** are the digest's two ways of
  writing an expression: in a unit's stream as written
  (`crates/slip_digest/src/expr_dep.rs`), and inside a canonical type or
  a key, where Kiln's profile decides what is told apart
  (`crates/slip_digest/src/expr_profile.rs`, `spec/digest-kinds.md`
  §4.4). A canonical operand (the operand of `decltype`, an array bound,
  a dependent template argument) is written from the **first spelling**
  the translation unit has of that profile, not from each use.
- `was` and `now` are the old and the new name of a rename.

## 0. The design in one page

### 0.1 What is proposed

**By site, on the post-image only.** `Declared` gains a list `tokens`.
A token says: *the bytes `[lo, hi)` of this file of the post-image are
the identifier `now`; where they are a dependent name, that name was
spelled `was`.* The walk of the post-image writes the name of a
dependent name node as `was` when the node is a pattern node of an
entry whose name range is a token's and whose name is that token's
`now`. Nothing else in the walk, in the comparison or in a key changes.
No unit is exempt for a token: `Declared.changed` is not used by the
rename at all.

- The pre-image is not walked again: its digests are the map phase's,
  made before the transform runs (`spec/edits.md` §8.1). The mapping is
  applied to the post-image only, as a rule is (`spec/digest.md` §3.4).
- The decision is per node, through the relation Kiln already records
  (entry to pattern nodes). There is no holder. The unit whose stream
  writes the node gets the old name, whichever unit that is: the
  enclosing function, a member alias, an enumerator, the class
  (`alignas`), an instantiation's definition that keeps a generic
  lambda.
- A key is made from the same canonical types by the same writer, so a
  token in a trailing return type, a parameter type or a trailing
  requires-clause gives the post-image entity its pre-image key. No
  key-to-key rule exists.
- A canonical operand is written from its first spelling, so inside a
  type the decision is the first spelling's. Two things close what that
  would open: a second mark on the type digest (`respelled`), and one
  new entry kind in the unit's own-spelling list, written when a unit's
  own spelling holds a name spelled `now` that is not a declared token
  while the type around it was respelled. §2.3 has the cases.
- What the walk reads that it did not read before: once per parse, the
  entries without a referent and their pattern nodes; per dependent name
  node written, one lookup by node id. With no token it reads nothing
  and no byte moves; `scheme` stays 2 (§7).

### 0.2 What it gives

For the reviewer's question (a name other than the declared tokens
binds another entity, or a declared token was edited wrongly in a
pattern an observer instantiates, and `verified`):

- A name other than a declared token is written exactly as it is
  written today. `h(0)` in the holder of B1 is a resolved reference; its
  key moves; the holder is `changed`.
- A declared token edited wrongly in an instantiated pattern: the
  instantiation is a derived unit of both images whose reference is
  resolved; it is `derived_changed`, or the post-image does not parse.
- **False equal: none**, beyond the one thing the ruling permits: the
  spelling of a declared token in a pattern that no observer
  instantiates.
- **False mismatch: two shapes**, both loud and both stated in §2.3: a
  canonical operand that holds a declared token and also another
  dependent name spelled `now`; and a second spelling of the same
  profile elsewhere in the translation unit that already used `now`.
  Both need the new name to be in use already, as a dependent name, in
  an expression of the same structure inside a type or a key.

### 0.3 What was run

Two throwaway tests, run narrowly and deleted before the commit.

**Probe 1** (over `slip_kiln`, the production parse with written
references on): for eight sources, every dependent entry with its name
range, every pattern node, and every node of the three kinds with its
location and its entry. What it showed at the pin:

| Shape | Finding |
|---|---|
| `t.f(1)`, `T::f()`, `f(t)` as parsed | the node is a pattern node of its entry; the node's own location is the first byte of the name token |
| generic lambda in a function template, `call<S>` instantiated | the body rebuilt for `call<S>` has a second node; it is a pattern node of the same entry |
| member template of a class template, `M<S>` instantiated | the node rebuilt in the member template's signature is a pattern node of the same entry (Kiln's §18.9.4 says such a signature "needs no further node"; the pin records one) |
| a name in a macro argument substituted twice | two entries with one name range, one node each |
| a name in a macro body | an entry whose spelling is in the `#define` line; it has no name range of tier 0 or 1 |
| `f(t)` in an instantiation | the node there is not dependent and belongs to no entry |
| a non-dependent overloaded call (`h(0)`) | an `UnresolvedLookupExpr` with no dependent entry |

**Probe 2** (over `slip_digest`, with stream traces): twelve pairs,
each a source with dependent names spelled `f` and the same source with
some of them spelled `h`, a class that has both members, no rule. For
every unit of one key with two digests, the two streams were compared
byte for byte. What it showed:

| Pair | Units that differ, and how |
|---|---|
| generic lambda in an ordinary function (B1's shape) | `U::u()`: one byte, the name. The closure's instantiated call operator: one 32-byte field (a resolved reference) |
| generic lambda in a function template | the template: the name byte. `call<S>()::<definition>`: the name byte (the nested pattern). The closure's call operator: a reference |
| member alias, enumerator, `alignas` | `M::e`: the name byte. `AL`: the name byte. `M::type`: two 32-byte fields (type digests that hash the name). Instantiations: references |
| trailing return type | the template's key, the specialisation's key and its definition's: one side only, each way. The caller: a reference |
| trailing requires-clause of a member | the member's key, the instantiated member's and its definition's: one side only. The class and the caller: a reference |
| unqualified call `f(t)` | the template: the name byte. The instantiation: a reference |
| macro argument substituted twice | the template: two name bytes. The instantiation: two references |
| two `t.f` in one holder, one changed | the template: one name byte |
| two templates with one profile `decltype(t.f(1))`, the first changed | the first template's key: one side only. The second: untouched |
| `decltype(t.f(1)) x` in a body | the template: three 32-byte fields (type digests) |
| default argument of a member of a class template | `D::d(int)`: the name byte. The instantiated default argument: a reference |

So in every pattern the difference a respelled dependent name makes is
the name's bytes, or a type digest or key that hashes them; and in every
instantiation it is a resolved reference, which a rule maps. That is the
premise the mechanism stands on, and it held for every shape tried.

## 1. What is declared

### 1.1 The four candidates

Each candidate is taken in the only form that fits the pipeline: the
pre-image's digests are made in the map phase before the transform runs,
so a candidate changes the walk of the post-image and writes the old
name there. (A symmetric form, "one word for both spellings in both
images", needs the pre-image walked again under the declaration and
makes every dependent `was` equal to every dependent `now`; it is not
considered further.)

- **S, by site.** `Declared` lists tokens (file, range, `was`, `now`).
  The walk writes `was` for a dependent name node made from the entry at
  a token's range.
- **H, by holder and name.** `Declared` lists `(holder key, was, now)`.
  While the walk writes the stream of the unit with that key, every
  dependent name spelled `now` is written `was`.
- **N, by name everywhere.** `Declared` lists `(was, now)`. Every
  dependent name spelled `now`, in every unit of every observer, is
  written `was`.
- **E, by entry.** `Declared` lists `(owner key, ordinal, was, now)`:
  the `ordinal`-th dependent entry of the declaration `owner`, as
  WP-153's proposal names an entry (`spec/landed/digest/WP-153.md`
  §3.5, on that package's branch).

### 1.2 The programs

`S::f` (or `n::f`) is renamed to `h` in each. "Good" is the correct
rename; a "bad" edit is named where one is used.

**P1, the reviewer's B1.**

```cpp
int h(int) { return 10; }
namespace n {
struct S { static int f(int) { return 1; } };
struct U : S {
  int u() { auto l = [](auto t) { return t.f(1); }; return l(S()) + h(0); }
};
}
```

**P2, its namespace form.**

```cpp
int h(int) { return 10; }
namespace n {
struct A {};
int f(A) { return 1; }
int f(int) { return 2; }
int u() { auto l = [](auto t) { return f(t); }; return l(A()) + h(0); }
}
int w() { return n::u(); }
```

**P3, B2: a discarded branch.**

```cpp
int h(int) { return 10; }
namespace n {
struct S {
  static int f(int) { return 1; }
  template <class T> static int call(T) { if constexpr (sizeof(T) > 100) return h(0); else return T::f(1); }

}
int w() { return n::S::call(n::S()); }
```

**P4, B2: a default argument no call uses.**

```cpp
int h(int) { return 10; }
namespace n {
struct S {
  static int f(int) { return 1; }
  template <class T> static int call(T, int k = h(0)) { return T::f(1) + k; }
};
}
int w() { return n::S::call(n::S(), 3); }
```

**P5, B2: another observer's copy.** `t.h` is read by two observers;
`b.cpp` defines `B_SIDE` and instantiates nothing.

```cpp

int h(int) { return 10; }

  static int f(int) { return 1; }
  template <class T> static int call(T) {
#ifdef B_SIDE
    return h(0) + T::f(1);
#else
    return T::f(1);

  }

}
// a.cpp:  #include "t.h"            int a() { return n::S::call(n::S()); }
// b.cpp:  #define B_SIDE  #include "t.h"   int b() { return 0; }
```

**P6, a mixed holder.** `X::f` is not renamed. Good edits the first
name only.

```cpp
struct S { int f(int) { return 1; } };
struct X { int f(int) { return 2; } };
template <class T, class U> int m(T t, U u) { return t.f(1) + u.f(2); }
int w() { return m(S(), X()); }
```

**P7, a holder that already has a dependent `h`.**

```cpp
struct S { int f(int) { return 1; } };
struct X { int h(int) { return 2; } };
template <class T, class U> int m(T t, U u) { return t.f(1) + u.h(2); }
int w() { return m(S(), X()); }
```

**P8, a wrong edit.** P6 with both names edited and both declared
(`u.f` should have been kept). P8a: as written, `m(S(), X())` is
instantiated. P8b: without `w`, nothing instantiates `m`.

**P9, a name in the key.**

```cpp
template <int N> struct Arr {};
struct S { static constexpr int f(int = 0) { return 1; } };
template <class T> auto k(T t) -> decltype(t.f(1)) { return t.f(1); }   // trailing return type
template <class T> int p(T, Arr<sizeof(T::f())>) { return 0; }           // a parameter type
template <class T> struct R { int g() requires(T::f() == 1) { return 1; } };  // trailing requires-clause
int w() { return k(S()) + p(S(), Arr<4>()) + R<S>().g(); }
```

**P10, two declarations that would collide.** P10a: two different
templates before the rename; the edit makes them one.

```cpp
template <class T> auto k(T t) -> decltype(t.f(1));
template <class T> auto k(T t) -> decltype(t.h(1));
```

P10b: one template declared twice with `decltype(t.f(1))`; a bad edit
respells the first declaration and leaves the second.

**P11, a generic lambda inside a function template.**

```cpp
struct S { static int f(int) { return 1; } };
template <class T> int call() { auto l = [](auto t) { return t.f(1); }; return l(T()); }
int w() { return call<S>(); }
```

**P12, a member alias, an enumerator, `alignas`.**

```cpp
template <int N> struct Arr {};
struct S { static constexpr int f() { return 1; } };
template <class T> struct M { using type = Arr<sizeof(T::f())>; enum { e = sizeof(T::f()) }; };
template <class T> struct alignas(sizeof(T::f())) AL { char c; };
M<S> m; AL<S> al;
```

**P13, an unqualified dependent call.** P13a as written. P13b: with
`int h(int);` declared at namespace scope before `c`.

```cpp
namespace n { struct A {}; int f(A) { return 1; } }
template <class T> int c(T t) { return f(t); }
int w() { return c(n::A()); }
```

**P14, macros.** P14a: the name in a macro argument that is substituted
twice. P14b: the name in a macro body.

```cpp
#define TW(x) ((x) + (x))

struct S { int f(int) { return 1; } };
template <class T> int m(T t) { return TW(t.f(1)); }      // P14a
template <class T> int b(T t) { return BODY(t); }         // P14b
int w() { return m(S()) + b(S()); }
```

### 1.4 What each candidate can get wrong

| | False equal (source) | False mismatch (source) |
|---|---|---|
| **S** | none beyond a declared token in an uninstantiated pattern (P8b) | a canonical operand with a declared token and another dependent `now` in it; a second spelling of the same profile that already used `now` (§2.3). Rare: both need `now` already in use as a dependent name in an expression of the same structure, inside a type or a key |
| **H** | any dependent `was` → `now` change in a declared holder, declared or not (P6's second row), verified only if instantiated, and reported under another token's name | a holder that already has a dependent `now` (P7); every shape where the holder is not the unit (P11, P12) |
| **N** | any dependent `was` → `now` change anywhere in the program | every unit, in every observer, that already has a dependent name `now`: a rename to `size`, `begin`, `get` or `value` fails in every translation unit that includes a standard header. Not rare |
| **E** | as S when the observers agree | two observers that preprocess the owner differently (P5); the owner is the lexical context for an alias, an enumerator, a head requires-clause |

### 1.5 The decision

**S, by site.** It is the only one of the four that says what the
ruling says ("these tokens change their spelling") and nothing more. It
is exact where H and N are loose (P6, P7), needs no holder where H needs
one per shape (P11, P12), and is independent of how an observer
preprocesses the file where E is not (P5): a token is a range of a
file, and a file is the same bytes for every observer.

What the alternatives would have bought, and why it was not enough:

- **H** avoids reading places. But the walk under rules already reads
  places to decide whether a rule applies (ownership reads where an
  entity is declared, `spec/verify.md` §2.1), and the spelled-entity
  check reads the post-image's written-reference table by name range
  (`spec/verify.md` §10.2). S reads the same table by the same function.
  H's price is a notion of holder that Kiln does not give reliably (the
  `no_holder` refusal exists because of it), a relation to derived
  units, type digests kept per holder, and a cycle for keys.
- **N** needs no list. Its false mismatch is not rare and its false
  equal is the whole program.
- **E** names an entry without a position, which is right for WP-153
  (`docs/wp/WP-153.md`), whose rows are compared between two images of
  one observer. Here the list is made once for a run and read
  by every observer, and ordinals are per observer. E also needs the
  join from an entry to the nodes the walk writes, which is all of S's
  machinery.

### 1.6 What "position-free" means after this

A digest still holds no position, and a unit's bytes do not depend on
where its text is. What the walk writes for a declared token is a name
(`was`). A place decides *whether a declared change applies to a node*,
as the place of a declaration decides whether a rule applies to an
entity. The pre-image's digests are untouched. Inserting a line above a
token changes the token list (it is derived per edit set), not a digest.

### 1.7 The rule

For a walk given a token list that is not empty (the post-image of a
verify job, and no other walk):

1. **Declared entries.** For each entry of the unit's written-reference
   table that has no referent and the flag `DEPENDENT`, take its name
   range (`spec/verify.md` §10.2 rule 2: one file, tier 0 or 1; no range
   in a file Kiln re-encoded or in a buffer with no subject path). The
   entry is **declared for** token `T` if the range is exactly
   `(T.file, T.lo, T.hi)`, the file compared by subject path.
2. **Declared nodes.** For each pair `(PatternNode::Expr(e), entry)` of
   the table's pattern nodes whose entry is declared for `T`: node `e`
   is **declared for** `T`.
3. **Writing a name.** Where the walk writes the name of a dependent
   name node `e`, in the full walk (the rows
   `ExprNode/UnresolvedLookupExpr.a`, `DependentScopeDeclRefExpr.b`,
   `CXXDependentScopeMemberExpr.b`) or in profile mode (the three arms
   of the same kinds): if `e` is declared for `T` and its name is the
   identifier `T.now`, the walk writes the identifier `T.was`. In
   profile mode it also sets the mark `respelled` of the type digest
   being written (§2.3).
4. **The unit's own spelling** gains one entry kind (§2.3).
5. Nothing else is read or written differently. In particular: the
   found set of an unqualified call, the qualifier, the template
   arguments, the base of a member access, and every node that is not a
   dependent name node are written as today; a node of the three kinds
   that is no pattern node of a declared entry is written as today,
   whatever its location.

A token is **used** in a parse if step 1 finds an entry declared for
it.

The join is Kiln's own relation and not the node's location, although
at the pin the two agree for every parsed node (§0.3): `ExprNode::loc`
is documented as "the operator / start location", not as the name's;
and a node that is not dependent can share the location (the `f(t)` of
an instantiation, §0.3). With the relation, a node Kiln did not make
from the entry is never mapped. A node Kiln did make from it and did not
record is written `now`, and the unit differs: loud.

## 2. Keys

### 2.1 The declaration reaches the key

A key's discriminator is made from canonical types
(`spec/digest-kinds.md` §3.3, §3.4): the parameter types, a function
template's return type and template head, a trailing requires-clause
written in profile mode. Those are written by the profile-mode writer
of §1.7 step 3. So the post-image entity whose signature holds a
declared token gets the key its pre-image had. **No key-to-key rule is
needed, and none is proposed.** A specialisation's key has the
template's key as its parent and follows it.

Probe 2 shows what happens today without it (P9): the template's key,
the specialisation's and its definition's are each in one image only,
and every unit that refers to them differs by a reference.

### 2.2 Collisions fail closed

- **Two templates that the edit makes one (P10a).** Kiln sees one
  template with two declarations in the post-image (their signatures
  are equivalent). It has one key: the first spelling of the profile
  decides, `K(f)` if the declared token is first, `K(h)` if not. The
  pre-image has both keys. One is `removed` either way; if both
  declarations are definitions the post-image does not parse.
- **One template that a bad edit splits (P10b).** The post-image has
  two templates. One is written with `f` because it is spelled `f`; the
  other because its token is declared. Two entities with one mapped
  key: the collision of `spec/digest.md` §3.4, indeterminate.
- **One entity cannot get two decisions.** An entity has one canonical
  type and its key is written once from it.

### 2.3 Canonical operands: the first spelling decides, and what closes it

Kiln interns a dependent type by its profile and keeps the expression
of the first spelling. The digest writes the type's bytes from that
expression (`ProfileEntry.first_expr`) and memoises them for the parse.
So inside a type, step 3 asks whether the *first spelling's* node is
declared, and the answer holds for every use of the type.

`spec/digest-kinds.md` §4.4 "Spellings" already has this problem for
the facts a profile leaves out (the found set of an unresolved name) and
solves it with a mark on the type digest and a list of the unit's own
facts. This design does the same:

- The type digest gets a second mark, **`respelled`**: some name of its
  profile was written as a token's `was`. It propagates to an enclosing
  type digest as the existing mark does.
- **A new entry kind of the unit's own-spelling list, `undeclared`**
  (tag 7, no payload). The walk of a unit's own spelling
  (`crates/slip_digest/src/own_spelling.rs`) meets every dependent name
  node the unit itself wrote inside a canonical operand. It adds
  `undeclared` when the node's name is the `now` of some token, the node
  is **not** declared, and the operand around it is `respelled`. The
  entry always makes the list due.
- A unit that holds a `respelled` operand and has no spelling of its own
  for it is `Unaccounted("spelling/<site>")`, as rule 5 of "Spellings"
  says for the existing mark.

Where profile mode writes an expression of the unit's own straight
into its stream or its key (a trailing requires-clause, a template
argument), the nodes written are the unit's own and the decision is
exact per node, as in the full walk.

The four combinations, for a unit `U` whose own spelling has a name
spelled `now` inside a type:

| The type's first spelling is | `U`'s own node is | `U` in the post-image | Against the pre-image |
|---|---|---|---|
| declared | declared | type written `was`, no entry | equal (the correct rename) |
| declared | not declared | type written `was`, entry `undeclared` | differs: `changed U` |
| not declared | declared | type written `now` | differs: the pre-image had `was` |
| not declared | not declared | type written `now`, no entry | equal iff the pre-image had `now` |

Row 2 is what stops an undeclared change from riding a declared one:

```cpp
template <class T> auto k1(T t) -> decltype(t.f(1)) { return 0; }
template <class T> auto k2(T t) -> decltype(t.f(1)) { return 0; }
```

Both names are respelled `h`; only `k1`'s is declared. The two types
are one profile, written `f` on `k1`'s say-so, so `k2`'s key and type
bytes are the pre-image's. `k2`'s own spelling has an undeclared `h` in
a respelled operand: `changed k2`.

**The two false mismatches**, stated exactly:

1. *An operand that mixes.* One canonical operand holds a declared
   token and another dependent name spelled `now` that is not declared
   (`decltype(t.f() + u.h())` with the first respelled). The type is
   `respelled`, the other name is `undeclared`: `changed`. The mark is
   per type, not per name of the type.
2. *A profile that is shared.* The post-image's translation unit has
   two spellings of one profile, one with a declared token and one that
   spelled `now` before the rename (an owned
   `-> decltype(t.size())` made by a rename to `size`, and a library
   template with the same expression over the same parameter position).
   If the declared one is first, the library's units are row 2; if the
   library's is first, the owned unit is row 3. Either way a unit is
   `changed`, or `removed` and `added` where the type is in a key.

Both are loud, both name the unit, and both need the new name to be in
use already as a dependent name in an expression of the same structure
inside a type or a key. Names in bodies (the full walk) are exact per
node and have neither.

**Alternatives that lost.**

- *Map every dependent `now` inside a type, and let the own-spelling
  list say which were not declared.* The type's bytes would then be a
  function of the profile alone, as "Spellings" wants. But every unit
  with a dependent `now` in a type, in every observer, would gain an
  entry the pre-image does not have: candidate N's false mismatch,
  confined to types. Lost.
- *Type digests per holder.* Splits the memo by context and still needs
  a holder. Lost with H.
- *A mark per name position of the profile*, to remove false mismatch 1.
  The own-spelling walk and the profile walk visit names in the same
  order (the lists "line up entry for entry"), so it can be built. It
  is not proposed: it buys one rare loud case for a positional protocol
  between two walks. It is the natural follow-up if the case is met on
  a corpus.

## 3. Units made from the holder

**"The holder" does not survive as a notion.** Nothing in `Declared`
names a unit, and the walk does not ask which unit it is in. The
relation that reaches a unit is: *the unit's stream, its key or a type
digest it holds writes a node that is a pattern node of a declared
entry.*

| Shape | The unit that holds the name | How the rule reaches it |
|---|---|---|
| a function or member function template's body | the template's unit | the parsed node, full walk |
| a generic lambda in an ordinary function (P1) | the enclosing function's unit | the parsed node, full walk |
| a generic lambda in a function template, instantiated (P11) | the template's unit, and `call<S>::<definition>` | the parsed node; the node rebuilt for `call<S>`, a pattern node of the same entry (§0.3) |
| a member template of a class template, the class instantiated | the member of the instantiation | the node rebuilt in its signature (§0.3) |
| a member alias (P12) | `M::type` | the type digest of the alias's type, profile mode |
| an enumerator (P12) | `M::e` | the parsed node, full walk |
| `alignas` of a class template (P12) | `AL` | the parsed node, full walk |
| a default argument of a member (probe 2) | `D::d(int)` | the parsed node, full walk |
| a signature (P9) | the entity's key and unit | profile mode (§2) |
| an alias template's pattern, a template head's requires-clause | the alias template's unit; the template's key | profile mode. Kiln records the translation unit as the entry's enclosing declaration there; the rule does not read it |

An instantiation in which the name is resolved (`call<S>`'s closure
call operator, `M<S>::e`, `D<S>::d`'s default argument) holds a
reference, not a name. It is mapped by the rename's rule and is
compared in full; that comparison is what vouches for the token.

`Keys::unit_of` and the `changed` entry it fed
(`crates/slip_refactor/src/rename/dependent.rs`, `holder`) are no
longer needed by the rename. Whether the `no_holder` refusal goes with
them is open question 3: the digest no longer needs a holder for those
two shapes, but what the name binds in their substitutions is seen only
by its outcome until WP-153 (`docs/wp/WP-153.md`) lands.

## 4. Unqualified dependent calls

For `f(t)` the full walk writes: whether argument-dependent lookup
applies, the name, and the declarations found at the definition as
sorted references (`unresolved_lookup_expr`). In profile mode the name
is in the profile and the found set is an entry of the unit's own list.

Under a rename's declaration:

- **The name** is written `was` when the node is declared (§1.7).
- **The found set is written as it is**: the references of what the
  post-image found, each mapped by the rules. Nothing is added for it.
  - Every found declaration is a renamed subject (P2): the set maps to
    the pre-image's keys. Equal.
  - The set is empty in both images, the subject being found only by
    argument-dependent lookup (P13a). Equal.
  - Another declaration named `now` is visible at the definition
    (P13b), or one named `was` no longer is found: the sets differ and
    the pattern is `changed`. That is a true difference, since the set
    is what overload resolution starts from in every instantiation.
- **In an instance** the callee is a resolved reference. No name is
  written and no token applies; the rule maps the reference, and a call
  that now selects another function is `derived_changed`.

Row 1 of `spec/edits.md` §9.4 (decide by the found set) is not built at
the pin; this design does not need it and does not change it.

## 5. Where it is written

### 5.1 `Declared`

```
Declared := rules, changed, created, removed, kept, files     as today (spec/verify.md §2)
            tokens: list<Token>     version 3: dependent names of the post-image that were spelled otherwise

Token := file: bytes     the subject path of the file (spec/verify.md §5.1): a canonical absolute path
         lo:   uv
         hi:   uv        lo < hi: the bytes [lo, hi) of that file in the post-image
         was:  bytes     the name before: one plain identifier (spec/api.md §6.1 rule 1)
         now:  bytes     the bytes [lo, hi): one plain identifier, hi - lo bytes long, not equal to `was`
```

- **Places are the post-image's.** The walk that reads them walks the
  post-image, as a rule matches the post-image's names and a `created`
  line is resolved in the post-image. In the overlay form the subject
  path is the real path; in the tree form it is the path the subject
  has for the post tree's file.
- **Order.** Sorted by `(file, lo)`; within one file no two tokens
  share a byte.
- **Version rule.** `tokens` is version 3 of `DECL`. A reader reads
  versions 1 and 2 as today, with `tokens` empty. **A writer writes
  version 3 only when `tokens` is not empty**, and a version 3 container
  with no token is refused, so that every value has one encoding and no
  container that exists today changes a byte or its id. (The
  alternative, always writing version 3 as WP-110 did for version 2,
  moves the id of every declared container, the empty one included,
  for nothing.) `dump` and `undump` keep a file's version.
- **JSON.** A member `tokens` after `files` in version 3: a list of
  `{"file": bytes, "lo": n, "hi": n, "was": bytes, "now": bytes}`.
- **The reader's checks**, after the six of `spec/verify.md` §2, each
  at the token: 7. `not a canonical absolute path`; `lo is not below
  hi`; `was is not a plain identifier`; `now is not a plain
  identifier`; `now is not hi - lo bytes long`; `was is now`.
  8. `tokens are not strictly ascending` and `two tokens share a byte`,
  at the later token. 9. `a version 3 container without a token`.
- **Identity.** `tokens` is not part of `rules_id`: it is not a rule. A
  verify shard names the `DECL` container it was made with
  (`Binding.declared`, `spec/verify.md` §9.1), and the container's id
  covers the tokens.
- `tokens` does not need `rules` or `files`: a declaration may hold
  tokens and no rule.

**The alternative: the overlay holds them.** Apply derives obligations
(where spelled text landed) into the overlay; the tokens' places could
be a second list there, and `Declared` would hold nothing, or the
pre-image places. It lost for three reasons. A declared change would
live outside the declared container. The tree form has no overlay, so
`slip verify` on two trees, and with it every pitfall row
(`spec/pitfalls.md` rows are tree-form), could not use it. And a verify
job would have two containers to reconcile. It is sound, though, and it
is open question 1.

### 5.2 The edit set and `slip_reduce::declared`

- **A new piece**, `dependent = 4: (text: bytes, was: bytes)`: `text`,
  written as a dependent name that was spelled `was`. Both are plain
  identifiers and differ. It is added as the identifier piece was
  (WP-132): no change of format version; a reader of before refuses the
  unlisted tag as Malformed. It claims nothing about what the name
  denotes and gives no obligation (`spec/verify.md` §10: an obligation
  fails when a dependent name answers, which is why WP-139 used a
  literal piece here).
- The native rename writes this piece where it wrote a literal one for
  a dependent name it edits, and makes no `changed` entry. The
  programmable API (`spec/api.md`) does not get the piece in this
  package.
- **Landings.** Each time the text of a dependent piece is written into
  a post-image, at its edit's own place or in a copy that carries the
  edit, that is one landing: the file, the range in the post-image,
  `was`, `text`, and the edit it came from. This is step 5 of
  `spec/edits.md` §7.1 for another kind of piece. Landings are a
  function of the edit set alone: every expansion's length is known
  without reading a file (`slip_apply::plan` computes the lengths so
  today).
- **§6.2 gains: `tokens` = the landings of the set's dependent
  pieces.** `slip_reduce::declared(set, ownership)` computes them, so
  `Declared` stays a function of the edit set and `check` can derive it
  again. The computation of where pieces land moves from `slip_apply`
  to `slip_model` beside the edit set (one implementation, used by
  apply for obligations and by reduce for tokens).
- The edit set keeps `changed` (a programmable transform's
  declarations); the rename leaves it empty. `Declared.changed` of a
  rename is empty.

### 5.3 `check --declared` given

WP-076's ruling, applied to this part: of a given declaration's tokens,
only those the edit set derives (equal in file, range, `was` and `now`)
are used. The verify phase runs with the given declaration less the
others, published as a container of its own, and the command prints
`token not derived: <path>:<lo>-<hi> <was> -> <now>` for each one
dropped. Dropping and saying so is proposed over refusing the command,
because the harness's oracle gives a mutated edit set to `check` with
the original's declaration (`spec/harness.md` §6.4) and expects a
result. If the fix round of WP-076 refuses for `changed`, this part
should do as that does; what matters is that no token the set does not
derive reaches the walk. (Open question 4.)

A token cannot do more than its words say, whoever wrote it: the most a
token excuses is that a dependent name at its range, spelled `now`, is
read as `was`. That is why the list needs no trust beyond this check.

### 5.4 `slip verify --declared` on two trees

**Usable.** There is no overlay and no edit set, and none is needed:
the places are the post tree's. `slip declare` (`spec/verify.md` §2.3,
outside the trusted base) gains a line

```
respelled <was> => <now> @ <path>:<line>:<column>
```

resolved in the post-image: `<path>` relative to the root, the place
that of the token's first byte. The raw-lexed token there must be the
identifier `<now>`; if it is not, the line fails with a new error
`NoToken`, which a pitfall row's runner treats in a `bad` tree as it
treats `NoUnit` (the line is left out; a missing declaration can only
add findings).

### 5.5 The verify job, the shard, the run

- §5.2 step 1 of `spec/verify.md`: the walk is given `Declared.tokens`.
  The parse records written references when the list is not empty, as
  it does when the overlay has obligations. Step 6 walks the same way.
  The pre-image parse of step 4 is given none.
- A new section of a verify shard, **`token_use`** (the next free id,
  33 at this writing), present when the outcome is `ok` and `tokens` is
  not empty: `TokenUse := used: list<uv>`, the indices into
  `Declared.tokens` of the tokens used in this parse (§1.7), ascending.
- The run folds it: a token used by no observer is **unused**.
- The comparison (`spec/verify.md` §4) does not change at all.

### 5.6 The report: what replaces the `exempt` lines

A rename has no `exempt` line any more. In the transform's report
(`spec/edits.md` §10.5):

```
declared <id>: rules <n>, exempt <n>, tokens <n>
tokens: <n> respelled, <n> unused, <n> without an instantiation
token <was> -> <now>: <path>:<line>:<column>: read in <n> observer(s); <k> specialisation(s) seen[ (unused)][ (no instantiation seen: not verified)]
instance edited <path>:<line>:<column>: <display of the specialisation>: <subjects> (<n> observer(s), first <main file>)
```

- One `token` line per edit that has a dependent piece, at the edit's
  pre-image place (lines and columns from the pre-image file, as every
  other line). `read in <n>` counts the observers that used any landing
  of the edit. `<k>` counts the `instances` of the edit set at that
  place. The `instance` lines are WP-139's, unchanged: they are the
  instantiations that vouch for the token.
- **A token with no specialisation seen is residue of category
  `dependent`** (`spec/edits.md` §8.4): the result is
  `verified_with_residue`. The rename never makes one today (it edits a
  dependent name only on the instantiations it saw); a hand-made edit
  set can.
- An unused token is reported and changes no state: nothing was mapped
  on its account.

The verify phase's own report (`spec/verify.md` §7.1), which is all a
tree-form run has: `tokens: <n> declared, <n> unused` and, per token,
`token <was> -> <now>: <path>:<lo>-<hi>: read in <n> observer(s)`.

## 6. What stays unverified

**One thing.** For a token and an observer that reads its range as a
dependent name: whether `now` there denotes, when the pattern is
instantiated, what `was` denoted, is shown by the instantiations that
observer makes, each compared as a derived unit, and by nothing else.
If no observer of the run instantiates the pattern that holds the token
(as that observer preprocesses it), the token's edit is not verified
(P8b). The report shows it: the token's line with its count of
specialisations seen, each `instance` line with its observers, and
residue `dependent` when the count is 0.

This is per observer's copy of the pattern. In P5 the token after
`#else` is read by both observers and instantiated by one; `b.cpp`'s
copy of `S::call` is compared in full with that one name read as `f`.

**Nothing else is left unverified by this design.** Three limits that
exist today are not changed by it, and are named so that no one reads
this package as closing them:

- What a token inside a signature binds when the signature is
  substituted (`k<S>`'s return type `decltype(t.h(1))`) is seen by the
  digest through its outcome, the type, not through what the name
  bound: `spec/edits.md` §9.4 "What the digest sees of a substitution",
  `docs/wp/WP-153.md`. The pattern and its key are compared;
  a body that uses the name is compared in every instantiation.
- What `now` finds in an instantiation other than the renamed entity (a
  capture) is loud today and is `docs/wp/WP-152.md`.
- A dependent name the rename leaves `unresolved` is residue
  `dependent`, as today.

Two shapes are loud rather than verified: the false mismatches of
§2.3. An `UnresolvedMemberExpr` is `Unsupported` in the full walk
today (indeterminate), with or without a token.

## 7. Inertness and scheme

- **With no token no digest moves.** Every change to the walk is behind
  "the token list is not empty": the entry scan, the six writers, the
  mark, the own-spelling entry. A walk of a pre-image, of `slip parse`,
  of a verify job whose declaration has no token reads none of it. The
  post parse does not record written references on this account.
- **A token that matches nothing changes nothing** (the inertness of
  `spec/digest.md` §3.4 for rules, `crates/slip_digest/tests/inert.rs`):
  a token at a range where no dependent entry is, or whose `now` is not
  the node's name, declares no node; no name is written otherwise, no
  mark is set, and `undeclared` needs a `respelled` operand.
- **`scheme` stays 2.** No stream, key or table row changes for a walk
  without tokens, and no existing unit changes. Under a token list the
  only comparisons that change are a unit that held a declared token
  (different before, equal now if nothing else moved) and a unit that
  gets `undeclared` (different either way: its type bytes were
  different before). The rule of `spec/digest.md` §11 changes `scheme`
  before the first release only when units that compared equal under
  some rule table are made to differ; no comparison was ever made under
  a token list, and no baseline of scheme 2 is recorded. The new
  entry kind is a row of `spec/digest-kinds.md` §4.4 that is written
  only under a declaration, as WP-140's view units are written only
  under a table.
- **Cost with tokens.** Once per post-image parse: one pass over the
  entries without a referent (a name range each, the function the
  spelled-entity check already calls) and one over the pattern nodes; a
  map from node id to token with one entry per declared node. Per
  dependent name node written: one comparison of the name with the
  tokens' `now` names (usually one), then one lookup. Recording written
  references in the post parse is a cost a rename's verify phase
  already pays for its obligations.

## For Kiln

Nothing is missing at the pin: every shape tried has the pattern nodes
the rule needs (§0.3). One thing is asked, and it is **implementation,
not design**: a sentence in Kiln's `spec/ast.md` §18.9.4 and tests that
hold it.

1. **A contract for pattern nodes of expressions.** *Every expression
   node of kind `UnresolvedLookupExpr`, `DependentScopeDeclRefExpr` or
   `CXXDependentScopeMemberExpr` that Kiln makes from the name of a
   dependent entry, and that is still dependent, is a pattern node of
   that entry: the node the parser builds, and every node a
   substitution rebuilds from one (the body of a generic lambda in an
   instantiated function, the signature of a member template of an
   instantiated class).* §18.9.4 says today that a member template's
   signature "needs no further node"; the pin records one, and Slip
   will rely on it. **The Slip need**: the walk of the post-image
   writes a dependent name as its old spelling only for a pattern node
   of the entry at a declared token. A rebuilt node that is not
   recorded is written with its new spelling and the unit that holds it
   (an instantiation's definition, a member of an instantiation) is
   reported as changed for a correct rename. That fails closed, so
   this is completeness, not safety.
2. **For information, no request.** The rule does not read a dependent
   entry's `enclosing`, so the two shapes of
   `spec/landed/edits/WP-139.md` "For Kiln" item 2 no longer block the
   digest side. They still matter to WP-153's owner.

## Open questions

1. **Where the tokens live.** In `Declared`, with the post-image's
   places, derived by `slip_reduce::declared` from the edit set (§5.1,
   §5.2); or in the overlay, derived by apply beside the obligations,
   with `Declared` unchanged. Both are sound. The first keeps every
   declared change in one container, works on two trees, allows pitfall
   rows, and costs moving the computation of where pieces land into
   `slip_model`. The second moves nothing and has no tree form.
   **Recommendation: `Declared`.**
2. **The two false mismatches of §2.3 are accepted as loud limits.**
   The alternative is the mark per name position, which removes the
   first and not the second. **Recommendation: accept; pin both with
   tests; build the positional mark only if a corpus meets the case.**
3. **`no_holder`.** The digest no longer needs a holder, so the rename
   could edit a dependent name in an alias template's pattern and in a
   template head's requires-clause. The pattern would be compared with
   the token mapped; what the name binds in each substitution there is
   seen only by its outcome until WP-153. **Recommendation: keep
   refusing those two shapes until WP-153 lands, under the same reason
   value with its text changed to say why; then edit them.**
4. **`check --declared` with a token the set does not derive**: dropped
   and reported (§5.3), or the command refused. The text of WP-076's
   ruling is not in this branch. **Recommendation: drop and report, or
   whatever the fix round of WP-076 does for `changed`, the same for
   both.**
5. **The rename's default.** The ruling made "leave dependent names as
   residue" the default until this package lands. **Recommendation:
   when stage 4 passes its tests and mutations, the offering form
   (edit on the instantiations seen) is the default again.**
6. **A token with no specialisation seen is residue `dependent`**
   (§5.6), which makes a hand-made edit set of that kind
   `verified_with_residue`. The rename makes none. **Recommendation:
   yes; it is the one unverified thing, and the state should say so.**
