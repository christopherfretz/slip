# WP-154 — a rename declares the dependent tokens it respelled; nothing is withdrawn

The design proposal of stage 0 ([docs/wp/WP-154.md](../../../docs/wp/WP-154.md)),
**in its second revision**: revised after its independent design review
and the supervisor's rulings (the section "The design review and the
rulings" maps each finding to where it landed), and again after the
delta review of that revision and the rulings on it (the section "The
second revision"). Nothing here is built. It answers the package's
eight items in their order, then gives the build's stages, what is
asked of Kiln, where each finding of the two reviews landed, and what
is still the supervisor's to rule. Kiln was read at `4a83f6e3c` (Slip's
pin). Four throwaway probes were run by the designer and ten runs by
the reviewer; what they showed is in §0.3 and is cited where a decision
rests on it.

**The part to attack first is §6.6**, the witness: it is the one place
of this design from which a wrong `verified` could come.

Words used throughout:

- A **dependent name** is a name in a template's (or a generic
  lambda's) pattern that has no entity until instantiation. In Kiln's
  tree it is the name word of an expression of kind
  `UnresolvedLookupExpr` (the unqualified callee of a dependent call,
  `f(t)`), `DependentScopeDeclRefExpr` (`T::f`) or
  `CXXDependentScopeMemberExpr` (`t.f`, `t->f`, `this->f` with a
  dependent base). These three are the **dependent name nodes**. A
  rename of a function or a variable never binds a name written in a
  type-name context (`typename T::f`), so type contexts are not part of
  this design.
- An **entry** is an entry of Kiln's written-reference table (Kiln
  `spec/ast.md` §18). An entry **without a referent** and with the flag
  `DEPENDENT` is a dependent name as it was written. Its **name range**
  is the file range of its name token as `spec/verify.md` §10.2 rule 2
  defines it (one file, tier 0 or 1, through Kiln's
  `editable_file_range`).
- A **pattern node** of an entry (Kiln `spec/ast.md` §18.9.4) is a node
  Kiln made from that entry's name: the node the parser built, and each
  node a substitution rebuilt from it that is still dependent.
- **Full walk** and **profile mode** are the digest's two ways of
  writing an expression: in a unit's stream as written
  (`crates/slip_digest/src/expr_dep.rs`), and inside a canonical type or
  a key, where Kiln's profile decides what is told apart
  (`crates/slip_digest/src/expr_profile.rs`, `spec/digest-kinds.md`
  §4.4). A **canonical operand** (the operand of `decltype`, an array
  bound, a dependent template argument) is identified by its
  **profile**: Kiln's canonical form of the expression, which two
  spellings of the same structure and the same names share. Kiln keeps,
  per profile, the expression of the **first spelling** the translation
  unit has of it; each use keeps its **own operand**, the expression
  node written at that use (§2.3).
- A **row** is a row of Kiln's per-specialisation table (Kiln
  `spec/ast.md` §18.9, `WrittenRefs::specs()`): for a dependent entry
  and one specialisation the observer made, the entity the name denotes
  there, or none if the name stayed dependent.
- An instantiation **keeps** an expression when a unit of the observer
  writes the substituted expression, so that a name in it is a
  reference to an entity. Where no unit does, or a unit writes only the
  expression's **outcome** (the type a `decltype` gave, the value a
  bound had, whether a constraint was satisfied), the name is
  **outcome-only** there. This is a property of one use in one
  observer, not of the context the name is written in (§3.2).
- A **witness** of a row is the walk's own record that it wrote, in a
  unit's stream, the reference the row speaks of: the name of that
  entry, in that specialisation, as a reference to that entity (§6.6).
- A unit of the post-image is **matched** when the pre-image of the
  same observer has a unit of the same class and key with the same
  digest (§6.6).
- An entry is **vouched** in an observer when every row of it that has
  an entity has a witness in a matched unit; **covered** when the
  observer does not instantiate it and its pattern is, unit for unit,
  the pattern another observer vouches (§6.3, §6.7).
- `was` and `now` are the old and the new name of a rename.

## 0. The design in one page

### 0.1 What is proposed

**By site, on the post-image only.** `Declared` gains a list `tokens`.
A token says: *the bytes `[lo, hi)` of this file of the post-image are
the identifier `now`; where they are a dependent name, that name was
spelled `was`.* The walk of the post-image writes the name of a
dependent name node as `was` when the node is a pattern node of an
entry whose name range is a token's and whose name is that token's
`now`. No unit is exempt for a token: `Declared.changed` is not used by
the rename at all.

- The pre-image is not walked again: its digests are the map phase's,
  made before the transform runs (`spec/edits.md` §8.1). The mapping is
  applied to the post-image only, as a rule is (`spec/digest.md` §3.4).
- The decision is per node, through the relation Kiln already records
  (entry to pattern nodes). There is no holder. The unit whose stream
  writes the node gets the old name, whichever unit that is.
- **A name inside a type is respelled per use, from the operand the
  unit itself wrote** (§2.3). Kiln keeps, beside the canonical type
  that all spellings of one profile share, the expression each use
  wrote (probe 3, §0.3). The walk writes a type's bytes from the use's
  own operand where that operand holds a declared node, and from the
  canonical form, unchanged, everywhere else. The first spelling of a
  profile decides nothing. The first version's mark `respelled`, its
  list entry `undeclared` and its four-row table are withdrawn.
- A key is made from the same types by the same writer, so a token in
  a trailing return type, a parameter type or a trailing
  requires-clause gives the post-image entity its pre-image key. No
  key-to-key rule exists.
- **The pattern's spelling is one thing; what the name binds is
  another.** Mapping the token makes the pattern's unit equal. Whether
  the name still binds what it bound is shown only by a unit that
  writes the name as a reference and is compared. So three things are
  added to the trusted base (§6):
  1. **The obligation** (§6.2). For every specialisation Kiln's rows
     give for a declared entry, the entity the name binds there must be
     the subject of a declared rule that renames `was` to `now`.
     Otherwise the run is not verified, and the finding names the
     specialisation and the entity.
  2. **The witness** (§6.6). A row is vouched only if the walk of this
     parse wrote, walking an expression in full in a unit's own stream,
     a reference to the row's entity from a resolved name node at the
     entry's name location, inside a declaration chain that contains
     the row's specialisation; and only if that unit is matched in the
     pre-image. Anything ambiguous is no witness.
  3. **Vouching and cover, computed by the verify job and the run's
     fold from the parse and the comparison** (§6.3, §6.7). An entry is
     vouched when every row with an entity is witnessed. A token some
     observer reads and neither vouches nor has covered is residue; the
     result is `verified_with_residue` at best. Nothing is decided from
     the edit set.
- **The kept list is not in the trusted base.** The first revision
  decided vouching from the context a pattern's node is written in. The
  delta review showed that one pattern node, on one path, has a unit in
  one use and none in another (§3.2). The table of contexts (§3.3)
  stays as the rename's planning aid and as the report's reason text; a
  wrong entry in it can cost residue or an edit not made, never a wrong
  `verified`.
- **The rename edits a dependent name only where its pre-image rows
  are witnessed** (§5.2). Any other site stays `unresolved`, with the
  reason `outcome_only`.
- What the walk reads that it did not read before: once per parse, the
  entries without a referent, their pattern nodes, their rows and the
  name location of each; per dependent name node written, one lookup by
  node id; per resolved name node written in full, one lookup by
  location; per written type that is instantiation-dependent, its own
  operands. With no token it reads none of it and no byte moves;
  `scheme` stays 2 (§7).

### 0.2 What it gives

For the reviewer's question (a name other than the declared tokens
binds another entity, or a declared token was edited wrongly, and the
run says `verified`):

- A name other than a declared token is written exactly as it is
  written today. `h(0)` in the holder of B1 is a resolved reference; its
  key moves; the holder is `changed`.
- A declared token edited wrongly, by where it is:

  | The token is | What the run says |
  |---|---|
  | written as a reference by a unit of each specialisation the observer made, and that unit is in both images | that unit is `derived_changed`, or the post-image does not parse |
  | bound, in some specialisation, to an entity no declared rule renames | `not verified`: the obligation fails and names the specialisation and the entity (§6.2) |
  | bound in some specialisation whose unit does not write the name, or writes it in a unit the pre-image does not have, every row passing | `verified_with_residue`: the token is residue, reason `outcome_only`, naming the specialisation (§6.3) |
  | in a pattern, or a copy of one, that an observer reads and does not instantiate, and no observer vouches the same pattern | `verified_with_residue`: residue, reason `not_instantiated` |
  | the same, and another observer vouches the same pattern, unit for unit | counted `covered`, no residue (§6.7) |

- **`verified`, with a wrong token: no case is known.** A run is
  `verified` only when every token is vouched or covered in every
  observer that reads it. Vouched means that for every specialisation
  Kiln's rows give, a unit both images have with one digest holds the
  name as a reference. The delta review found a case that the first
  revision's rule passed (a generic lambda named only in `decltype`,
  §3.2); under the witness it is `outcome_only`. What the argument
  assumes is listed in §6.6 (A0 to A2).
- **`verified_with_residue`, with a wrong token**: the two residue rows
  above, which is what the state is for. §6.4 says exactly what is not
  seen.
- **The first version of this proposal claimed more.** It said that an
  instantiation always holds a resolved reference in the token's place
  and that one thing only stays unverified. The review showed a class
  of contexts where the instantiation holds only an outcome (§6.1); the
  five statements that said otherwise are corrected (the section "The
  design review and the rulings" lists them).
- **Loud for a correct rename** (a difference is reported, nothing is
  silent): a type Kiln computed and holds in canonical form only, where
  the unit has no operand of its own to read (no source is known to
  reach one; the enumeration the review found is closed in §2.3); one
  written type that holds two operands of one profile respelled
  differently; a name formed by a macro invocation. §6.5 lists them.
  The first version's false mismatch 2 (a second spelling of the same
  profile elsewhere in the translation unit, such as `<iterator>`'s
  `std::size` beside an owned `-> decltype(c.size())`) is gone: no
  unit's bytes depend on another unit's spelling.

## 1. What is declared

### 1.1 The four candidates

Each candidate is taken in the only form that fits the pipeline: the
pre-image's digests are made in the map phase before the transform runs,
so a candidate changes the walk of the post-image and writes the old
name there. (A symmetric form, "one word for both spellings in both
images", needs the pre-image walked again under the declaration and
makes every dependent `was` equal to every dependent `now`; it is not
considered further.)

- **S, by site.** `Declared` lists tokens (file, range, `was`, `now`).
  The walk writes `was` for a dependent name node made from the entry at
  a token's range.
- **H, by holder and name.** `Declared` lists `(holder key, was, now)`.
  While the walk writes the stream of the unit with that key, every
  dependent name spelled `now` is written `was`.
- **N, by name everywhere.** `Declared` lists `(was, now)`. Every
  dependent name spelled `now`, in every unit of every observer, is
  written `was`.
- **E, by entry.** `Declared` lists `(owner key, ordinal, was, now)`:
  the `ordinal`-th dependent entry of the declaration `owner`, as
  WP-153's proposal names an entry (`spec/landed/digest/WP-153.md`
  §3.5, on that package's branch).

### 1.2 The programs

`S::f` (or `n::f`) is renamed to `h` in each. "Good" is the correct
rename; a "bad" edit is named where one is used.

**P1, the reviewer's B1.**

```cpp
int h(int) { return 10; }
namespace n {
struct S { static int f(int) { return 1; } };
struct U : S {
  int u() { auto l = [](auto t) { return t.f(1); }; return l(S()) + h(0); }
};
}
```

**P2, its namespace form.**

```cpp
int h(int) { return 10; }
namespace n {
struct A {};
int f(A) { return 1; }
int f(int) { return 2; }
int u() { auto l = [](auto t) { return f(t); }; return l(A()) + h(0); }
}
int w() { return n::u(); }
```

**P3, B2: a discarded branch.**

```cpp
int h(int) { return 10; }
namespace n {
struct S {
  static int f(int) { return 1; }
  template <class T> static int call(T) { if constexpr (sizeof(T) > 100) return h(0); else return T::f(1); }
};
}
int w() { return n::S::call(n::S()); }
```

**P4, B2: a default argument no call uses.**

```cpp
int h(int) { return 10; }
namespace n {
struct S {
  static int f(int) { return 1; }
  template <class T> static int call(T, int k = h(0)) { return T::f(1) + k; }
};
}
int w() { return n::S::call(n::S(), 3); }
```

**P5, B2: another observer's copy.** `t.h` is read by two observers;
`b.cpp` defines `B_SIDE` and instantiates nothing.

```cpp

int h(int) { return 10; }

struct S {
  static int f(int) { return 1; }
  template <class T> static int call(T) {
#ifdef B_SIDE
    return h(0) + T::f(1);
#else
    return T::f(1);
#endif
  }

}
// a.cpp:  #include "t.h"            int a() { return n::S::call(n::S()); }
// b.cpp:  #define B_SIDE  #include "t.h"   int b() { return 0; }
```

**P6, a mixed holder.** `X::f` is not renamed. Good edits the first
name only.

```cpp
struct S { int f(int) { return 1; } };
struct X { int f(int) { return 2; } };
template <class T, class U> int m(T t, U u) { return t.f(1) + u.f(2); }
int w() { return m(S(), X()); }
```

**P7, a holder that already has a dependent `h`.**

```cpp
struct S { int f(int) { return 1; } };
struct X { int h(int) { return 2; } };
template <class T, class U> int m(T t, U u) { return t.f(1) + u.h(2); }
int w() { return m(S(), X()); }
```

**P8, a wrong edit.** P6 with both names edited and both declared
(`u.f` should have been kept). P8a: as written, `m(S(), X())` is
instantiated. P8b: without `w`, nothing instantiates `m`.

**P9, a name in the key.**

```cpp
template <int N> struct Arr {};
struct S { static constexpr int f(int = 0) { return 1; } };
template <class T> auto k(T t) -> decltype(t.f(1)) { return t.f(1); }   // trailing return type
template <class T> int p(T, Arr<sizeof(T::f())>) { return 0; }           // a parameter type
template <class T> struct R { int g() requires(T::f() == 1) { return 1; } };  // trailing requires-clause
int w() { return k(S()) + p(S(), Arr<4>()) + R<S>().g(); }
```

**P10, two declarations that would collide.** P10a: two different
templates before the rename; the edit makes them one.

```cpp
template <class T> auto k(T t) -> decltype(t.f(1));
template <class T> auto k(T t) -> decltype(t.h(1));
```

P10b: one template declared twice with `decltype(t.f(1))`; a bad edit
respells the first declaration and leaves the second.

**P11, a generic lambda inside a function template.**

```cpp
struct S { static int f(int) { return 1; } };
template <class T> int call() { auto l = [](auto t) { return t.f(1); }; return l(T()); }
int w() { return call<S>(); }
```

**P12, a member alias, an enumerator, `alignas`.**

```cpp
template <int N> struct Arr {};
struct S { static constexpr int f() { return 1; } };
template <class T> struct M { using type = Arr<sizeof(T::f())>; enum { e = sizeof(T::f()) }; };
template <class T> struct alignas(sizeof(T::f())) AL { char c; };
M<S> m; AL<S> al;
```

**P13, an unqualified dependent call.** P13a as written. P13b: with
`int h(int);` declared at namespace scope before `c`.

```cpp
namespace n { struct A {}; int f(A) { return 1; } }
template <class T> int c(T t) { return f(t); }
int w() { return c(n::A()); }
```

**P14, macros.** P14a: the name in a macro argument that is substituted
twice. P14b: the name in a macro body.

```cpp
#define TW(x) ((x) + (x))
#define BODY(t) t.f(1)
struct S { int f(int) { return 1; } };
template <class T> int m(T t) { return TW(t.f(1)); }      // P14a
template <class T> int b(T t) { return BODY(t); }         // P14b
int w() { return m(S()) + b(S()); }
```

### 1.5 The decision

**S, by site.** It is the only one of the four that says what the
ruling says ("these tokens change their spelling") and nothing more. It
is exact where H and N are loose (P6, P7), needs no holder where H needs
one per shape (P11, P12), and is independent of how an observer
preprocesses the file where E is not (P5): a token is a range of a
file, and a file is the same bytes for every observer.

What the alternatives would have bought, and why it was not enough:

- **H** avoids reading places. But the walk under rules already reads
  places to decide whether a rule applies (ownership reads where an
  entity is declared, `spec/verify.md` §2.1), and the spelled-entity
  check reads the post-image's written-reference table by name range
  (`spec/verify.md` §10.2). S reads the same table by the same function.
  H's price is a notion of holder that Kiln does not give reliably (the
  refusal `no_holder` of WP-139's first round existed because of it), a relation to derived
  units, type digests kept per holder, and a cycle for keys.
- **N** needs no list. Its false mismatch is not rare and its false
  equal is the whole program.
- **E** names an entry without a position, which is right for WP-153
  (`docs/wp/WP-153.md`), whose rows are compared between two images of
  one observer. Here the list is made once for a run and read
  by every observer, and ordinals are per observer. E also needs the
  join from an entry to the nodes the walk writes, which is all of S's
  machinery.

### 1.6 What "position-free" means after this

A digest still holds no position, and a unit's bytes do not depend on
where its text is. What the walk writes for a declared token is a name
(`was`). A place decides *whether a declared change applies to a node*,
as the place of a declaration decides whether a rule applies to an
entity. The pre-image's digests are untouched. Inserting a line above a
token changes the token list (it is derived per edit set), not a digest.

### 1.7 The rule

For a walk given a token list that is not empty (the post-image of a
verify job, and no other walk):

0. **The table must be there.** If the parse has no written-reference
   table with pattern nodes (Kiln's recording is off for the image, or
   it was made with `no_nodes`, Kiln `spec/ast.md` §18.8), no node can
   be told from another: the walk maps nothing and the verify job's
   verdict is `unverifiable` (§5.5).
1. **Declared entries.** For each entry of the unit's written-reference
   table that has no referent and the flag `DEPENDENT`, take its name
   range (`spec/verify.md` §10.2 rule 2: one file, tier 0 or 1; no range
   in a file Kiln re-encoded or in a buffer with no subject path). The
   entry is **declared for** token `T` if the range is exactly
   `(T.file, T.lo, T.hi)`, the file compared by subject path. One token
   can have several entries (a name in a macro argument substituted
   twice; a header included twice; a macro that defines two templates
   from one argument).
2. **Declared nodes.** For each pair `(PatternNode::Expr(e), entry)` of
   the table's pattern nodes whose entry is declared for `T`: node `e`
   is **declared for** `T`.
3. **Writing a name.** Where the walk writes the name of a dependent
   name node `e` that a unit holds itself, if `e` is declared for `T`
   and its name is the identifier `T.now`, the walk writes the
   identifier `T.was`. "Holds itself" is:
   - the full walk (the rows `ExprNode/UnresolvedLookupExpr.a`,
     `DependentScopeDeclRefExpr.b`, `CXXDependentScopeMemberExpr.b`);
   - profile mode over an expression the unit or the key was given as
     written (a trailing requires-clause, a template argument written
     straight into the stream);
   - profile mode over an own operand of a written type (step 4).

   It is never the canonical form: where the walk writes a profile from
   the expression Kiln kept of its first spelling, every name is
   written as it is, whatever is declared.

   An expression can hold a written type of its own (the type of a
   cast, of `sizeof(type)`, of a `new`, an explicit template argument),
   and profile mode writes that type through the type writer with its
   sugar. Which way the type writer then goes is stated in §2.3 step 3:
   inside an own operand the rule of §2.3 applies again to the nested
   type; inside the canonical walk of a first spelling it does not.
4. **Writing a type** that holds an own operand with a declared node:
   §2.3.
5. **What the token is worth** is recorded per declared entry, not
   written into any stream: its rows with their entities (§6.2), the
   witnesses of those rows (§6.6), the units that write its name
   (§6.7), and, as a reason text only, the context its node was met in
   (§3.2). They go to the shard section `token_use` (§5.5).
6. Nothing else is read or written differently. In particular: the
   found set of an unqualified call, the qualifier, the template
   arguments, the base of a member access, and every node that is not a
   dependent name node are written as today.

A token is **read** in a parse if step 1 finds an entry declared for
it.

**The failure mode of the join, stated once.** A node of the three
kinds that is *not* a pattern node of an entry declared for a token is
written as today, whatever its location and whatever its name. If it is
in truth the token's name (Kiln made the node from the entry and did
not record it), the unit that writes it has `now` where the pre-image
had `was`: the unit differs, and a correct rename is reported as a
difference. The join can fail loud; it cannot map a node Kiln did not
make from the entry.

The join is Kiln's own relation and not the node's location, although
at the pin the two agree for every parsed node (§0.3): `ExprNode::loc`
is documented as "the operator / start location", not as the name's;
and a node that is not dependent can share the location (the `f(t)` of
an instantiation, §0.3).

**Which nodes are pattern nodes: open until Kiln's list arrives.**
At the pin, every dependent node of the three kinds was a pattern node
of an entry in the eight shapes of probe 1, the twenty-three of the
review and the shapes of probe 3. No run found a node that is the
token's name and is not a pattern node, so no pair pins one; the
failure mode above is what such a pair would show. Kiln's
`spec/ast.md` §18.9.4 does not
say so today, and Kiln has given a **draft** of the exceptions it will
write there (its WP-3591). This subsection depends on that list; the
answers below are to the draft and are to be read again when the list
lands ("For Kiln" 1).

| # | Kiln's draft exception | Can a declared token's node fall in it? What the walk then does |
|---|---|---|
| 1 | A rebuild that resolves records a row, not a node. | Yes, and it is the ordinary case of an instantiation: the name is then a reference, not a name; step 3 does not apply, the rule maps the reference, and the row is what §6.2 and §6.6 read. Kiln's draft also says where nodes are added: a generic lambda's body
adds one further node per rebuilt node that stays dependent (in an
instantiated function, a nested generic lambda, a generic lambda in a
member template specialisation); a member template's signature and
body add none, because they are substituted from the pattern (exception
2).

**Names the rule does not reach, each loud or inert:**

- **An overloaded member on an object that is not dependent**
  (`s.f(t)` in a template, `s` of a class type). The node is a pattern
  node of an entry (the review's `k11`), but the walk writes a
  reference to the member found and no name word. A token there maps
  nothing and needs nothing: the rule maps the reference.
- **A name formed by a macro invocation** (`t.ID(g)(1)`). The entry's
  name range is the invocation `ID(g)`. No token can equal it; the
  pattern is written with the new name and differs.
- **A name in a macro body.** No name range of tier 0 or 1; no token.
- **A name in a constructor template's pattern** in a class template:
  the pattern's unit is `Unsupported("kiln/pattern-mem-initializers")`
  on both sides today, with or without a token, so the comparison is
  indeterminate. An `UnresolvedMemberExpr` is `Unsupported` in the full
  walk in the same way.

## 2. Keys

### 2.1 The declaration reaches the key

A key's discriminator is made from types and expressions the entity
wrote (`spec/digest-kinds.md` §3.3, §3.4): the parameter types, a
function template's return type and template head, a trailing
requires-clause written in profile mode. The trailing requires-clause
is the entity's own expression, so step 3 of §1.7 respells it node by
node. The types are written by the rule of §2.3, from the signature as
the entity wrote it. So the post-image entity whose signature holds a
declared token gets the key its pre-image had. **No key-to-key rule is
needed, and none is proposed.** A specialisation's key has the
template's key as its parent and follows it.

Probe 2 shows what happens today without it (P9): the template's key,
the specialisation's and its definition's are each in one image only,
and every unit that refers to them differs by a reference.

That the key comes back says nothing about what the name binds in a
specialisation: the contexts that are in a key are outcome-only today
(§3.3 rows 25, 26, 35, 36, 40, 42, 43).

### 2.2 Collisions fail closed

- **Two templates that the edit makes one (P10a).** Kiln sees one
  template with two declarations in the post-image (their signatures
  are equivalent). It has one key, written from the entity's
  declaration the walk reads the signature of (the canonical
  declaration): `K(f)` if that declaration holds the declared token,
  `K(h)` if not. The pre-image has both keys. One is `removed` either
  way; if both declarations are definitions the post-image does not
  parse.
- **One template that a bad edit splits (P10b).** The post-image has
  two templates. One is written with `f` because it is spelled `f`; the
  other because its token is declared. Two entities with one mapped
  key: the collision of `spec/digest.md` §3.4, indeterminate.
- **One entity cannot get two decisions.** Its key is written once,
  from one declaration's signature.

### 2.3 A name inside a type: each use is respelled from its own operand

**What Kiln keeps.** A dependent type that holds an expression (the
operand of `decltype` or `typeof`, an array bound, an expression
template argument) is canonical by its profile. All spellings of one
profile in a translation unit share one canonical type, and Kiln keeps
for it the expression of the first spelling
(`TypeContext::expr_origins`, `arg_origins`). Beside that, the type
*as written* at each use is sugar over the canonical type and holds
the expression that use wrote: `TypeView::Decltype { expr, underlying }`,
`TypeOfOperand::Expr`, `ArgView::Expr { expr, profile }`, a dependent
array bound's expression. That expression is the use's **own operand**.
The digest reads own operands today, for the facts a profile leaves
out (`spec/digest-kinds.md` §4.4 "Spellings", `own_spelling.rs`).

**"Own" is the use's, not the unit's.** The operand a unit reads is not
always one that unit's declaration wrote. A unit that uses a member
reads the type of the expression `m.fld` with the sugar Kiln kept, and
that sugar leads to the operand node of the *field's* declaration:
`M::use()` and `M::fld` read one node. So for the type of an
expression, the own operand is **the referenced declaration's node**.
"Own operand" means: the operand node of the written type the walk
holds at this use, whichever declaration wrote it. **Two units that
share one written operand are the normal case**, not an exception (the
delta review, 25 shapes; the table at the end of this subsection).
Nothing in the rule below depends on an operand being read by one unit
only: every unit that reads it writes it by step 3, from the same node
with the same decision per name, so all of them write `was` for a
declared node and `now` for any other.

Probe 3 (§0.3) ran the question at the pin. Each use had an operand
node of its own, with the dependent name under it recorded as a
pattern node of its own entry, in every shape tried: a trailing return
type, a member typedef and the uses of its name, a field, a local, an
enumeration's underlying type, a conversion function, an alias
template's pattern and a specialisation of it, an expression template
argument, an array bound in a parameter, a member template in its
pattern and in the instantiated class, and two operands of one profile
inside one written type. The canonical type was one, shared, with the
first spelling's node, in both include orders.

**The first version** had the walk respell the first spelling's
expression, so that one use's declaration decided the bytes of every
use of the profile, and closed what that opened with a mark and a list
entry. The review showed that this contradicts two sentences of the
specification (`spec/digest-kinds.md` §4.2 rule 1 and §4.4: the bytes
of a profile are not a function of the spelling Kiln met first), that
it reports one cause in two ways in two observers that include in
different orders, and that its "rare" false mismatch is met in every
translation unit that includes `<iterator>` when a member is renamed to
`size`, `begin`, `end`, `empty` or `data`. It is withdrawn whole.

**The rule.** In a walk given tokens, where the walk writes the digest
of a type it holds **as written** (the type of a declaration, a
signature, a cast, a friend: every place the walk has the type with the
sugar Kiln kept):

1. **Collect the own operands.** Walk the written type through all its
   sugar: elaborated types, the written arguments of a template
   specialisation, pointee, element, return and parameter types, and
   also *into* what a typedef, an alias or an alias template
   specialisation aliases, as written. (The own-spelling walk stops at
   a typedef, rule 4 of "Spellings", because another unit writes those
   facts. A type's bytes are written by every unit that uses the type,
   so this walk does not stop.) Only a type that is
   instantiation-dependent is walked. Each own operand is filed under
   the profile Kiln gives the use (the profile of the canonical form of
   that piece of sugar).
2. **No own operand holds a declared node: today's path.** The
   canonical type's digest, from the parse's memo, byte for byte as
   without tokens.
3. **Some do: the canonical type's stream is written again with an
   override.** The writer walks the canonical type as it does today.
   Where it would write profile `p` from the first spelling's
   expression and an own operand is filed under `p`, it writes that own
   operand instead, in profile mode, with step 3 of §1.7 applied to
   each node. A profile with no own operand filed is written from the
   first spelling, with no name respelled. The result is memoised per
   written type, never in the memo of canonical types (as the digest
   of an over-aligned type is memoised per written type today,
   `aligned_sugar_digest`).

   **A written type nested in an operand** (the delta review's S2).
   An operand can hold a written type of its own, which profile mode
   writes through this same type writer with its sugar:

   ```cpp
   template <class T> auto k(T t) -> decltype(static_cast<decltype(t.mf(1))>(0));
   ```

   The two directions are both part of the rule:

   - *Inside an own operand the rule recurses.* While the writer writes
     an own operand under the override, a written type it meets in that
     operand is written by this rule from step 1: its own operands are
     collected, and a declared node in them is respelled. Without this
     the inner `mf` above is written `now`, and the key of `k` is in
     one image only (the review ran the shape by spelling, `u20`: the
     key is removed and added).
   - *Inside the canonical walk of a first spelling the rule is
     suppressed.* While the writer writes a profile from the first
     spelling's expression (no own operand is filed under the profile,
     or the type has no declared node at all), a written type it meets
     in that expression is written in canonical form, by today's path,
     whatever is declared in it. Without this a declaration that is not
     edited and shares the profile would get `was` in the nested place
     whenever the owned declaration was the first spelling: a false
     difference that depends on the include order.

   In the walk this is one value of the type writer's state: "under an
   own operand", set while an override operand is being written,
   cleared while a first spelling is being written, saved and restored
   around each. Step 1 is entered for a nested written type only when
   it is set, or at the top (a type the walk holds as written, outside
   any profile).
4. **The mix is indeterminate.** If two own operands filed under one
   profile give different bytes under step 3 (one holds a declared node
   and the other, at the same place of the expression, a name that is
   not declared, or declared for another `was`), the writer cannot say
   which place of the canonical type each belongs to: sugar and
   canonical form need not line up place for place (an alias template
   may reorder its arguments). The unit that writes the type is
   `Unaccounted("spelling/respelled-mix")`: indeterminate, loud.
5. **A type Kiln derived from a written one takes that one's
   operands.** Three places hold a type in canonical form that Kiln
   derived from a type the same declaration wrote. Each is written with
   the override collected from its written source, and each is a row of
   the specification with a pair:

   | The canonical type | Its written source |
   |---|---|
   | a function's type in its key and its unit, where a parameter's type was adjusted (an array or a function type decays, and the adjusted type holds the canonical element type) | the return type as written and each parameter's type before adjustment (`ParamData::original_ty`) |
   | an enumeration's promotion type (`EnumData.promotion_type`) | its underlying type as written (`EnumData.int_type`, which keeps the sugar: probe 3) |
   | the type in a conversion function's name (Kiln interns the name by the canonical type) | the function's return type as written |

6. **Any other canonical form is never respelled.** A type the walk
   holds only in canonical form, with no written source this rule
   lists, is written as today, with `now`.

What follows from it:

- **A profile's bytes are again a function of the profile.** In a walk
  given tokens, what a unit writes for a type is a function of the
  profile and of the declared nodes of the spelling that unit holds; in
  no walk is it a function of the spelling Kiln met first. The two
  sentences the review cited are amended to say exactly this
  (stage 1's specification list).
- **An undeclared respelling cannot ride a declared one.** In

  ```cpp
  template <class T> auto k1(T t) -> decltype(t.f(1)) { return 0; }
  template <class T> auto k2(T t) -> decltype(t.f(1)) { return 0; }
  ```

  with both names respelled `h` and only `k1`'s declared, `k1`'s key is
  written from `k1`'s operand (`f`, declared) and `k2`'s from `k2`'s
  (`h`, not declared). `k2`'s pre-image key is `removed` and a key with
  `h` is `added`. Each name is judged where it was written, by the unit
  that wrote it.
- **A shared profile costs nothing.** An owned
  `template <class C> auto n(const C& c) -> decltype(c.length())` is
  renamed to `size`, in a translation unit that includes `<iterator>`.
  In the post-image the owned template and `std::size` share one
  canonical type. The owned template writes its own operand, respelled:
  `length`, the pre-image's bytes and key. `std::size` holds an operand
  in which nothing is declared: today's path, the canonical bytes,
  which are the bytes it had in the pre-image. That holds also where
  the first spelling Kiln kept for the shared type is the owned
  template's node, which is declared: the canonical path respells
  nothing (§1.7 step 3). Neither depends on which was first, so two
  observers that include in different orders agree.
- **The override cannot hide an undeclared respelling.** Every
  dependent name written inside a type is written by some declaration,
  and that declaration's unit either reads the name's node in its own
  operand, where it is judged alone (`was` if declared, `now` if not),
  or holds the type in canonical form only, where it is written `now`.
  Either way a name that was respelled and not declared makes the unit
  of the declaration that wrote it differ from the pre-image. Another
  unit that reaches the same profile through a declared operand is
  written `was` there; that is the declared token's doing, and the
  undeclared one is reported where it stands.
- **Several `(was, now)` pairs** (the review's S4). A node is respelled
  with the `was` of the token it is declared for and with no other. Two
  operands of one profile declared for different `was` give different
  bytes and are a mix (step 4). No rule tests a name against "the `now`
  of some token".

**Where the walk holds a type as written.** Every place the
own-spelling walk reads today (rule 3 of "Spellings": `absorb_type` in
a unit stream, from the written type its caller holds; a template
argument list and a default template argument as the unit holds them; a
partial specialisation's arguments as written), and the key writer for
a signature. The rule sits in the type writer, so it needs no list of
holders of its own: a caller that passes a type with sugar gets the
rule, a caller that passes a canonical type gets step 6.

**The three decisions of the existing mark.** The existing mark of a
type digest (`spec/digest-kinds.md` §4.4 "The mark") decides three
things. No second mark is added, and the mark itself is read as today.
With tokens:

| The mark's decision | The site | With a declared token there |
|---|---|---|
| `spelling/<site>`: a unit holds a canonical operand and no spelling of its own (rule 5 of "Spellings") | of 45 sites the review tried, one: **an enumeration** (`enum E : decltype(T().mf(1))`). Probe 3 shows which of its two types it is: the underlying type is kept as written, the promotion type is canonical. The other sites are those rule 2 of "Spellings" names as canonical-only: a bound, an address space or a pack index held as a profile; a canonical `noexcept`; a deduced type; a dependent `_BitInt` width. No source is known to reach one of them with a dependent name inside | the enumeration: step 5, the promotion type is written from the underlying type's operand; the unit is equal for a correct rename (pair `enum-underlying`). Any other such site: step 6, written `now`; the unit differs from the pre-image, which had `was`, and **a correct rename is reported `changed`** (loud limit 1) |

So the loud limits of a name inside a type are three, each a reported

1. a canonical operand with no spelling of the unit's own and no

2. the mix of step 4;
3. an own operand whose rebuilt node Kiln did not record as a pattern
   node (§1.7's failure mode). At the pin the one rebuilt operand

Names in bodies (the full walk) are exact per node and have none of the
three.

## 3. Units made from the holder, and what an instantiation keeps

### 3.1 Which units the declaration reaches

**"The holder" does not survive as a notion.** Nothing in `Declared`
names a unit, and the walk does not ask which unit it is in. The
relation that reaches a unit is: *the unit's stream, its key or a type
digest it holds writes a node that is a pattern node of a declared
entry.*

| Shape | The unit that holds the name | How the rule reaches it |
|---|---|---|
| a function or member function template's body | the template's unit | the parsed node, full walk |
| a generic lambda in an ordinary function (P1) | the enclosing function's unit | the parsed node, full walk |
| a generic lambda in a function template, instantiated (P11) | the template's unit, and `call<S>::<definition>` | the parsed node; the node rebuilt for `call<S>`, a pattern node of the same entry (§0.3) |
| a member template of a class template, the class instantiated | the member of the instantiation | the node rebuilt in its signature (§0.3) |
| a member alias (P12) | `M::type` | the alias's type as written, its own operand (§2.3) |
| an enumerator (P12) | `M::e` | the parsed node, full walk |
| `alignas` of a class template (P12) | `AL` | the parsed node, full walk |
| a default argument of a member (probe 2) | `D::d(int)` | the parsed node, full walk |
| a signature (P9) | the entity's key and unit | the signature as written, its own operands (§2) |
| an alias template's pattern, a template head's requires-clause | the alias template's unit; the template's key | profile mode over the unit's own expression. Kiln records the translation unit as the entry's enclosing declaration there; the rule does not read it |

This table says where the *spelling* of the token is compared. It does
not say that anything compares what the name *binds*. That is the next
three subsections, and the first version of this proposal had it wrong:
it said that every instantiation holds a resolved reference in the
token's place. It holds one only where a unit of the instantiation
writes the expression, and whether one does is a fact of each use
(§3.2).

`Keys::unit_of` and the refusal `no_holder` are gone from the rename
since WP-139's second review (`spec/edits.md` §4.2: value 12 is
unlisted). Nothing here brings them back.

### 3.2 Kept and outcome-only: decided per use; the kept list is a planning aid

An instantiation is a derived unit of both images. Where its stream
writes the substituted expression, a name in it is a reference to the
entity it bound, the rule maps that reference, and a token that binds
something else is `derived_changed`. That comparison is what vouches
for a token. But Kiln does not keep every substituted expression, and
the digest does not write every one Kiln keeps: of a `decltype` the
instantiation's unit holds the type, of an array bound the value, of a
requires-clause the fact that the declaration was viable. There the two
images' instantiations are equal whatever the token binds, as long as
the outcome is the same (the first review's case, §6.1).

**The first revision decided this from the context of the pattern's
node**: the path by which the walk reaches the node in the pattern's
unit (a function body, then a generic lambda's body, and so on),
checked against a list of contexts in which an instantiation's unit
writes the expression. **The delta review showed that this is not a
property of the context.** The same pattern node, reached by the same
path, has a unit in one use and none in another:

```cpp
struct X { int mf(int) { return 1; }      // the rule renames this one to mh
           int mf(long) { return 2; } };  // kept
int w() {
  auto l = [](auto u) { return u.mf(1L); };  // edited to u.mh(1L), declared as a token
  int (*p)(X) = l;                           // or: decltype(l(X())) x = 0;
  return p(X());
}
```

The pre-image returns 2 and the post-image 1. The name's path is a
function body and then a generic lambda's body, row 9 of §3.3, whose
pair (the lambda called directly) shows the instantiated call
operator's unit differing. Here the call operator is instantiated, Kiln
has the row `operator()<X>(X) const => X::mh(int)`, the obligation
passes because `X::mh(int)` is the subject, and **no unit of either
image holds the instantiated call operator**: the lambda is named only
in `decltype`, or reached only through its conversion to a function
pointer. Every unit is equal. The first revision's rule said `vouched`.
The shapes the review ran, each with the row present and no unit that
differs:

| Shape | Row of §3.3 |
|---|---|
| a generic lambda named only in `decltype(l(X()))`, in an ordinary function and in a function template (`e01b`, `e01`) | 9 |
| a generic lambda reached only through the conversion to a function pointer; the body runs (`e07`) | 9 |
| one entry, two instantiations: `decltype(l(X())) x = l(Y());` has rows for `X` and `Y` and a unit for `Y` only (`e21`) | 9 |
| a default argument of a lambda's call operator, in an instantiated function (`e02`, `q09c`) | 16 |
| a default argument of a local class's member, in an instantiated function (`e03c`) | 16 |

No rule on the path can tell the first three from the lambda that is
called: the pattern node and its path are the same.

**So vouching is decided per row, by a witness of the walk** (§6.6):
whether this parse's walk wrote the reference in a unit, for this
specialisation. It is not decided from any list of contexts.

**The kept list leaves the trusted base.** The table of contexts (§3.3)
and the flag below stay for two uses, both outside the trusted base:
the rename, together with the witness on the pre-image, plans with them
which sites to edit and which to leave (§5.2), and the reports print a
context's row as the reason text of a site left or of an entry not
vouched (§5.6). Nothing in the verify job, the run's fold or the
verdict reads the list or the flag. A wrong kept list can therefore
cost only residue (the rename edits a site that verification then does
not vouch) or an edit not made (the rename leaves a site that
verification would have vouched). It cannot make a run `verified`. For
the same reason the delta review's S1 (the wording of the flag) and S3
(which rows of `spec/digest-kinds.md` the contexts are) are notes now,
not conditions of the trusted base.

**The list, as an aid.**

- The walk reaches a node of a pattern's unit by a **path**: a *root*
  (the field of a declaration that holds an expression or a written
  type: a function's body, an initialiser, an enumerator's value, a
  bit-field's width, a default argument, the operand of `alignas`,
  `explicit` or a `static_assert`), then *steps* down (a child field of
  a statement or an expression; entering profile mode; from WP-156 on,
  the holder of a written type and an operand site inside it).
- A root or a step is **marked** when an instantiation's unit is
  expected to write what it holds as an expression walked in full. The
  marks are a column `instance` of the rows `spec/digest-kinds.md`
  already has for these fields; a row nobody marked is unmarked. The
  column changes no stream.
- The **context** of a node is the row of §3.3 its path ends in when
  every root and step is marked ("kept"), else the first unmarked step
  ("outcome-only", with that step's name as the reason text).

**The flag, worded so that it can be built one way** (the delta
review's S1). It is one value of the expression state, computed only
in a walk given tokens or a watch list (§5.2). At a root it is set to
the root's mark. At each step down it becomes its value ANDed with the
step's mark, and the value it had before the step is restored when the
walk returns from the step; so the value at a node is the root's mark
ANDed with the mark of every step on the current path from the root to
that node, and a later root of the same unit starts again from its own
mark. Entering profile mode is a step like any other: its mark is
unmarked today, and a package that makes an operand site witnessed
marks it. Where the walk takes a digest from a memo (a type's, a
key's, the override's of §2.3 step 3) it walks no node and reads no
value: the context recorded for an entry is the value at the first of
its nodes the walk met, in the walk's order, and an entry whose nodes
are met only through a memo has none. The recorded context therefore
depends on the order of the walk where a node is reached by two paths
(the normal case for an operand in a member's type, §2.3). That is
harmless because the value is advisory: it is a reason text and a
planning hint, and no state, verdict or residue is computed from it.

## 4. Unqualified dependent calls

For `f(t)` the full walk writes: whether argument-dependent lookup
applies, the name, and the declarations found at the definition as
sorted references (`unresolved_lookup_expr`). In profile mode the name
is in the profile and the found set is an entry of the unit's own list.

Under a rename's declaration:

- **The name** is written `was` when the node is declared (§1.7).
- **The found set is written as it is**: the references of what the
  post-image found, each mapped by the rules. Nothing is added for it.
  - Every found declaration is a renamed subject (P2): the set maps to
    the pre-image's keys. Equal.
  - The set is empty in both images, the subject being found only by
    argument-dependent lookup (P13a). Equal.
  - Another declaration named `now` is visible at the definition
    (P13b), or one named `was` no longer is found: the sets differ and
    the pattern is `changed`. That is a true difference, since the set
    is what overload resolution starts from in every instantiation.
- **In an instance** the callee is a resolved reference. No name is
  written and no token applies; the rule maps the reference, and a call
  that now selects another function is `derived_changed`, where a unit
  writes the call (§3.2).
- **Where Kiln records no row.** At the pin an argument-dependent
  call in a generic lambda's body has its row (§0.3, the reviewer's
  second runs). The shape seen without one is a call in a
  requires-clause written on a lambda. A token at such a name is "not
  instantiated" (§6.3): residue, and the rename leaves the name (§5.2).
  A call in a concept's definition has a row keyed on the concept,
  which is outcome-only (§6.6 step 2).

Row 1 of `spec/edits.md` §9.4 (decide by the found set) is not built at
the pin; this design does not need it and does not change it.

## 5. Where it is written

### 5.1 `Declared`

```
Declared := rules, changed, created, removed, kept, files     as today (spec/verify.md §2)
            tokens: list<Token>     version 3: dependent names of the post-image that were spelled otherwise

Token := file: bytes     the subject path of the file (spec/verify.md §5.1): a canonical absolute path
         lo:   uv
         hi:   uv        lo < hi: the bytes [lo, hi) of that file in the post-image
         was:  bytes     the name before: one plain identifier (spec/api.md §6.1 rule 1)
         now:  bytes     the bytes [lo, hi): one plain identifier, hi - lo bytes long, not equal to `was`
```

- **Places are the post-image's.** The walk that reads them walks the
  post-image, as a rule matches the post-image's names and a `created`
  line is resolved in the post-image. In the overlay form the subject
  path is the real path; in the tree form it is the path the subject
  has for the post tree's file.
- **A `Declared` with tokens is bound to one post-image.** A rule holds
  for any image in which the entity has the new name; a token is a
  range of bytes of one image. The specification says so in
  `spec/verify.md` §2: a container with tokens is for the post-image it
  was derived from, and a token that does not fit another image is
  inert there (it declares no node, §7), never wrong.
- **Order.** Sorted by `(file, lo)`; within one file no two tokens
  share a byte. A list may hold several `(was, now)` pairs.
- **Version rule.** `tokens` is version 3 of `DECL`. A reader reads
  versions 1 and 2 as today, with `tokens` empty. **A writer writes
  version 3 only when `tokens` is not empty**, and a version 3 container
  with no token is refused, so that every value has one encoding and no
  container that exists today changes a byte or its id. (The
  alternative, always writing version 3 as WP-110 did for version 2,
  moves the id of every declared container, the empty one included,
  for nothing.) `dump` and `undump` keep a file's version.
- **JSON.** A member `tokens` after `files` in version 3: a list of
  `{"file": bytes, "lo": n, "hi": n, "was": bytes, "now": bytes}`.
- **The reader's checks**, after the six of `spec/verify.md` §2, each
  at the token: 7. `not a canonical absolute path`; `lo is not below
  hi`; `was is not a plain identifier`; `now is not a plain
  identifier`; `now is not hi - lo bytes long`; `was is now`.
  8. `tokens are not strictly ascending` and `two tokens share a byte`,
  at the later token. 9. `a version 3 container without a token`.
- **Identity.** `tokens` is not part of `rules_id`: it is not a rule. A
  verify shard names the `DECL` container it was made with
  (`Binding.declared`, `spec/verify.md` §9.1), and the container's id
  covers the tokens.
- `tokens` does not need `rules` or `files` to be read. A token with no
  rule that renames `was` to `now` fails its obligation wherever it has
  a row (§6.2).

**Ruled (question 1): the tokens live in `Declared`.** The alternative
was the overlay, where apply derives obligations: a declared change
would then live outside the declared container, the tree form (which
has no overlay) and with it every pitfall row could not use it, and a
verify job would have two containers to reconcile.

### 5.2 The edit set, the rename, and `slip_reduce::declared`

- **A new piece**, `dependent = 4: (text: bytes, was: bytes)`: `text`,
  written as a dependent name that was spelled `was`. Both are plain
  identifiers and differ. It is added as the identifier piece was
  (WP-132): no change of format version; a reader of before refuses the
  unlisted tag as Malformed. It carries no key (§6.2: several rules can
  claim one token) and gives no spelled-entity obligation; the
  obligation of a dependent token is derived from the token itself.
- **Landings.** Each time the text of a dependent piece is written into
  a post-image, at its edit's own place or in a copy that carries the
  edit, that is one landing: the file, the range in the post-image,
  `was`, `text`, and the edit it came from. This is step 5 of
  `spec/edits.md` §7.1 for another kind of piece. Landings are a
  function of the edit set alone: every expansion's length is known
  without reading a file (`slip_apply::plan` computes the lengths so
  today).
- **§6.2 gains: `tokens` = the landings of the set's dependent
  pieces.** `slip_reduce::declared(set, ownership)` computes them, so
  `Declared` stays a function of the edit set and `check` can derive it
  again. The computation of where pieces land moves from `slip_apply`
  to `slip_model` beside the edit set (one implementation, used by
  apply for obligations and by reduce for tokens).
- The edit set keeps `changed` for a programmable transform's
  declarations. A rename has none (`spec/edits.md` §9.6, as WP-139
  merged).

**What the rename does (ruled, questions 3 and 5; revised for the
witness).**

- **It edits a dependent name only where the pre-image shows the
  witness.** The map phase walks the pre-image before the transform
  runs, in the same job (`spec/edits.md` §8.1). That walk is given a
  **watch list**: the plain identifiers the rename's subjects are named
  by (`Options.watch`; empty for every other transform and for `slip
  parse`). For each dependent entry of the parse whose name is on the
  list and that has a row with an entity, the walk computes the witness
  of §6.6 on the pre-image: its steps 1 to 7, reading "declared for a
  token" as "named by a watched name", and without step 8, because
  there is no second image yet.
  - *What is recorded*: per watched entry, by its name range: for each
    row with an entity, the specialisation and whether the row has a
    witness; and the entry's context (§3.2), as a reason text.
  - *Where it is stored*: in the walk's output, in memory
    (`Output.watched`). The rename runs in the same job and reads it
    there (`slip_refactor` depends on `slip_digest` already), beside
    Kiln's rows, and turns it into its claim, which is in the edit
    shard as today. No shard section and no format is added for it,
    and the digests of the map shard do not depend on the list (a test
    of stage 1: any walk with a watch list gives the digests it gives
    without one).
  - *What it is expected to cost*: one hash lookup by location for each
    resolved name node the walk writes in full, and one for each
    dependent name node, only while the watch list is not empty; a map
    with one entry per watched entry (the dependent names spelled like
    a subject, a small part of the table); the rows of those entries
    read once. The map-phase parse of a rename records written
    references with rows already (WP-139 reads them). It need not
    record pattern nodes on this account: the witness reads none, and
    the context, being advisory, joins the pattern's node to its entry
    by location. The expectation is well under one percent of the
    walk's time and no measurable memory; stage 4 shows it with the
    counters `digest.watch.entries`, `digest.watch.rows` and
    `digest.watch.lookups` and the map phase's `cpu_s` and
    `peak_rss_max` on the corpus with and without the list
    (`spec/harness.md` §7.1).
- **The decision.** Row 2 of `spec/edits.md` §9.4 is decided as today,
  with one more condition for `replace`: every row of the entry that
  has an entity is witnessed in this observer's pre-image. The edit is
  then written with a dependent piece where it wrote a literal one.
  **A site whose rows all bind a subject and of which some row has no
  witness is `unresolved`, with the reason `outcome_only`**; its reason
  text names the specialisation whose unit does not write the name and,
  where one was recorded, the context. It is then residue `dependent`
  by `spec/edits.md` §8.4, and the report says why it was left.
- **It is a prediction, and verification does not rely on it.** The
  witness on the pre-image says what the pre-image's walk wrote. The
  verify job computes the witness on the post-image on its own, and
  decides "matched" from the comparison, which the rename cannot know.
  Where the two disagree, verification decides: a site the rename
  edited and verification does not vouch is residue (§6.3); a site the
  rename left is residue `dependent` already. Neither can make a run
  `verified` wrongly.
- **Format.** `Reason` gains `outcome_only` (the next free value; 12
  stays unlisted). It is the one reason a claim of stance `unresolved`
  may carry; reduce keeps it per place with the reason text, in a list
  of the edit set beside `unresolved` (a new version of `EDTS`, written
  only when the list is not empty, by the version rule of §5.1; the
  exact record is stage 4's). An observer that reads the site as
  witnessed and one that does not (two preprocessings of one file, or
  one observer that calls a generic lambda and one that names it only
  in `decltype`) join as `replace` and `unresolved` do today: the edit
  is made, and verification makes the token residue in the observer
  where it is outcome-only (§6.3).
- **The default.** `dependent: offer` becomes the default again when
  stage 4 passes: it now edits witnessed sites only, and a run that
  edits them can end `verified`. `leave` and `refuse` stay.
- **No holder.** The refusal `no_holder` is not needed for anything:
  an alias template's pattern and a template head's requires-clause
  have rows no unit can witness (rows 46 and 35 of §3.3; §6.6 step 2)
  and are left `unresolved` for that reason.
- **A site Kiln gives no row.** The rename plans from rows, so a name
  an instantiation resolved and Kiln recorded no row for is left
  `unresolved` as "no instantiation is evidence" (`spec/edits.md`
  §9.4), and a hand-made token there is "not instantiated" (§6.3),
  residue. At the pin that is a name in a requires-clause written on a
  lambda and a name in a generic lambda's body that depends only on a
  parameter of the enclosing template (§0.3); pairs pin both (§8.1).
  An argument-dependent call in a generic lambda's body has its row at
  the pin.

### 5.3 `check --declared` given

**Ruled (question 4): refuse.** A declaration given with an edit set
must have exactly the tokens the set derives (equal in file, range,
`was` and `now`). A token the set does not derive, or a derived token
that is missing, makes the input inconsistent: the command stops with
an input error that names the token,

```
slip: <declared file>: token <path>:<lo>-<hi> <was> -> <now> is not derived from the edit set
slip: <declared file>: the edit set derives token <path>:<lo>-<hi> <was> -> <now>, which the declaration lacks
```

and nothing is verified. Nothing is dropped in silence. The harness's
oracle, which gives a mutated edit set to `check` with the original's
declaration (`spec/harness.md` §6.4), must derive the declaration again
when the mutation changes a dependent piece.

In the tree form (`slip verify --declared` on two trees) there is no
edit set: the tokens are simply given.

A token cannot do more than its words say, whoever wrote it: the most a
token excuses is that a dependent name at its range, spelled `now`, is
read as `was`; and it brings its own obligation with it (§6.2).

### 5.4 `slip verify --declared` on two trees

**Usable.** There is no overlay and no edit set, and none is needed:
the places are the post tree's. `slip declare` (`spec/verify.md` §2.3,
outside the trusted base) gains a line

```
respelled <was> => <now> @ <path>:<line>:<column>
```

resolved in the post-image: `<path>` relative to the root, the place
that of the token's first byte. The raw-lexed token there must be the
identifier `<now>`; if it is not, the line fails with a new error
`NoToken`, which a pitfall row's runner treats in a `bad` tree as it
treats `NoUnit` (the line is left out; a missing declaration can only
add findings).

### 5.5 The verify job, the shard, the run

- **The parse.** §5.2 step 1 of `spec/verify.md`: the walk is given
  `Declared.tokens`. The parse records written references with pattern
  nodes when the list is not empty, as it records them when the overlay
  has obligations. Step 6 walks the same way. The pre-image parse of
  step 4 is given none.
- **A new guard.** If the token list is not empty and the post-image
  parse has no written-reference table with pattern nodes (Kiln's
  recording is off for the image, or `no_nodes`, Kiln `spec/ast.md`
  §18.8), the walk cannot tell a declared node from any other. The
  verdict is `unverifiable`, reason `post-image: no pattern nodes
  recorded; the declaration has tokens`. No token is mapped.
- **A new section of a verify shard, `token_use`** (the next free id,
  33 at this writing), present when the outcome is `ok` and `tokens`
  is not empty:

  ```
  TokenUse  := tokens: list<TokenSeen>     the tokens this parse reads (§1.7), strictly ascending by `token`
  TokenSeen := token:   uv                 index into Declared.tokens
               entries: list<EntrySeen>    one per entry declared for it, in the table's order; at least one
  EntrySeen := rows:      uv               rows of the entry that have an entity
               witnessed: uv               of them, those with a witness in a matched unit (§6.6); at most `rows`
               missing:   opt<Missing>     the first row, in the rows' order, that has none; present exactly when witnessed < rows
               context:   str              §3.2: the context the entry's node was met in, or empty; a reason text, read by no state
               homes:     list<Home>       §6.7: the units that write the entry's name; strictly ascending by (key, ordinal)
               failed:    list<FailedRow>  §6.2; in the rows' order; at most `rows`
  Missing   := spec:      opt<KeyId>       the specialisation's key under the rules, if it has one
               spec_name: str              the specialisation as a person would write it (spec/verify.md §6.1)
               why:       no_unit = 1 | unit_not_matched = 2 | ambiguous = 3      §6.6
               unit:      opt<KeyId>       for `unit_not_matched`: the unit that holds the witness
               unit_name: str              that unit's name, else empty
  Home      := key: KeyId, digest: Digest, ordinal: uv      §6.7
  FailedRow := spec:      opt<KeyId>       the specialisation's key under the rules, if it has one
               spec_name: str              the specialisation as a person would write it (spec/verify.md §6.1)
               found:     opt<KeyId>       the key, under the rules, of the origin the name binds there
               name:      str              that entity; both names for the report only
  ```

  An entry is **not instantiated** when `rows` is 0; **vouched** when
  `rows` is not 0 and `witnessed` equals it; **outcome-only** otherwise
  (§6.3). The walk gives, per row, the units that hold a witness; the
  verify job, which has both images' units, decides which of them are
  matched and writes the counts. Nothing in the section is read from
  the edit set, and `context` is the only member that comes from the
  kept list.
- **The run folds it** (`slip_verify::run`), over this run's `ok`
  shards whose state is `verified` or `mismatch`, as §10.3 of
  `spec/verify.md` folds spellings. First per entry: an entry that is
  not instantiated is **covered** or not (§6.7). Then per token:
  `read`, the observers that read it; `vouched`, those in which every
  entry is vouched; `covered`, those in which every entry is vouched or
  covered and at least one is covered; `not_instantiated` and
  `outcome_only`, those with an entry in that state that is not
  covered; the failed rows, grouped by (specialisation, entity) with
  their observers. A token with `read` 0 is **unused**. A token is
  **not vouched** when `read` is greater than `vouched` plus `covered`.
- **The verdict.** A run with a failed row is **not verified**: one
  more condition of `spec/verify.md` §9.3, beside a failed spelled
  entity. A token that is not vouched does not change the run's
  verdict, which is about the comparison; the run report carries the
  counts, and what a command makes of such a token is the command's
  (§5.6): a transform concludes `verified_with_residue`, and `slip
  verify` on two trees ends `incomplete`.
- **A shard is this run's** only if its `token_use` is present exactly
  when the declaration has tokens, names no token past the list, names
  only tokens whose file its `inputs` list, has `witnessed` at most
  `rows` in every entry, has `missing` exactly when `witnessed` is
  below `rows`, and names in `homes` only keys of units the shard has
  with that digest; else the observer is `failed` (as §9.3 does for
  `spellings`).
- **Counters of the shard** (`spec/verify.md` §7.2; present when the
  declaration has tokens): `verify.tokens.read`, `verify.tokens.entries`,
  `verify.tokens.rows`, `verify.tokens.rows.witnessed`,
  `verify.tokens.rows.unmatched` (rows whose only witnesses are in
  units that are not matched), `verify.tokens.writes` (resolved name
  nodes the walk looked up by location, §6.6 step 3) and
  `verify.tokens.failed`. They are deterministic, and the harness sums
  them (§7).
- The comparison (`spec/verify.md` §4) does not change at all. The
  verify job reads its result for one new purpose: which units are
  matched.

### 5.6 The reports

**The verify phase's report** (`spec/verify.md` §7.1), which is all a
tree-form run has. A JSON member `"tokens"`, present when the
declaration has tokens, and in the text:

```
tokens: <n> declared, <n> unused, <n> not vouched, <n> failed
token <was> -> <now>: <path>:<lo>-<hi>: read <r>, vouched <v>, covered <c>[, not instantiated <u>][, outcome only <o> (<reason>)][ (unused)]
token failed <was> -> <now>: <path>:<lo>-<hi>: <specialisation> binds <entity>, which no declared rule renames (<n> observer(s), first <main file>)
```

`read`, `vouched`, `covered`, `not instantiated` and `outcome only`
count observers (§5.5); `covered` is always printed, beside `vouched`
and `read`. A token line is printed for every token (at most 200, then
a count). `<reason>` is that of the first observer, in the plan's
order, in which an entry is outcome-only:

```
<specialisation>: no unit writes the name[; <context>]
<specialisation>: the unit <unit> is not in the pre-image with this digest
<specialisation>: more than one name can be meant
```

**The tree form has no state for residue** (ruled: open question 2 of
the first revision, accepted), and its status 0 must not come to mean
less than it means today: without the token the respelled pattern is a
mismatch. The verdict of `slip verify` given a declaration with tokens
is decided in this order:

1. **`not verified`, status 1**: some observer is `mismatch` or
   `not_parsed`, or the run has a failed row (or a failed spelled
   entity, or the observers disagree, as today). A failed row comes
   ahead of everything below.
2. **`incomplete`, status 4** (`spec/exec.md` §8.5: "nothing was found
   to differ, and not everything could be checked"): some observer is
   unverifiable or failed, as today; or every comparison is `verified`
   and some token is read and not vouched.
3. **`verified`, status 0**: otherwise.

**The output tells the two causes of `incomplete` apart.** Before the
`verdict` line the text has one line for each cause that holds, and
the JSON report a member `"incomplete"` listing them:

```
incomplete: <n> observer(s) could not be checked
incomplete: <n> token(s) read and not vouched
```

The first is today's case and is followed, on standard error, by the
observers' own lines as today; the second is followed by the token
lines above. A pitfall row's `good` tree must therefore have its
tokens vouched, which a name whose instantiation's unit does not write
it cannot have (§8.4).

**The transform's report** (`spec/edits.md` §10.5). A rename has no
`exempt` line (WP-139 as merged). It gains:

```
declared <id>: rules <n>, exempt <n>, tokens <n>
tokens: <n> respelled, <n> unused, <n> not vouched, <n> failed
token <was> -> <now>: <path>:<line>:<column>: read <r>, vouched <v>, covered <c>[, not instantiated <u>][, outcome only <o> (<reason>)][ (unused)]
token failed <was> -> <now>: <path>:<line>:<column>: <specialisation> binds <entity>, which no declared rule renames (<n> observer(s), first <main file>)
left outcome-only <path>:<line>:<column>: <reason> (<n> observer(s), first <main file>)
residue dependent: <path>:<line>:<column>[ (not instantiated)][ (outcome only)]
```

- One `token` line per edit that has a dependent piece, at the edit's
  pre-image place (lines and columns from the pre-image file, as every
  other line); its counts are the fold's, summed over the edit's
  landings (an observer that reads two landings of one edit counts
  once; it vouches the edit only if it vouches both, and has it covered
  only if each is vouched or covered).
- **The result.** `RSLT` gains the fold's token records (a new version;
  conclude copies them from the trusted run report and decides none,
  as it does for `spellings`). A token that is not vouched (some
  observer reads it and neither vouches it nor has it covered) adds a
  residue entry of category `dependent` at the edit's place, with its
  reason; so the state is
  `verified_with_residue` (row 4 of `spec/edits.md` §8.5) and writing
  needs `--allow-residue`. A failed row gives `not_verified` through
  the verdict (row 2).
- The `instances:` heading and its `instance` lines are WP-139's and
  stay: they are the rename's evidence, from the map phase. They decide
  nothing here. The heading loses its last clause ("the run cannot
  verify a name edited here until dependent names are compared
  mapped").
- A `left outcome-only` line per site the rename left for that reason
  (§5.2); `<reason>` names the specialisation whose unit does not
  write the name and, where one was recorded, the context of §3.3.
- An unused token is reported and changes no state.

## 6. What is verified, what is residue, what stays unverified

The first version of this section said "one thing stays unverified, and
nothing else". The review showed a class it had missed (§6.1). The
first revision closed it with a check that fails hard (§6.2) and a
state decided from the context of the pattern's node; the delta review
showed that the context does not decide (§3.2). This version states: a
check that fails hard (§6.2); the states that make a token residue
(§6.3), which rest on the witness (§6.6) and on cover (§6.7); what is
left when all of it passes (§6.4); and what is loud (§6.5).

### 6.1 The case the first version missed

```cpp
// pre-image
template <int N> struct Arr {};
struct S { static constexpr int f() { return 1; } };
struct X { static constexpr int f() { return 1; }
           static constexpr int h() { return 1; } };
template <class T> struct M { using type = Arr<sizeof(T::f())>; int a[T::f()]; };
template <class T> int b(T t) { decltype(T::f()) x = 0; Arr<T::f()> y; return x; }
M<S> ms; M<X> mx; M<S>::type v1; M<X>::type v2;
int w() { return b(S()) + b(X()); }
```

An edit set renames `S::f` to `h` and respells all four `T::f` as
`T::h`, each a declared token. `X` is not touched. Every token is
wrong: in `M<X>` and `b<X>` the name bound `X::f` and now binds `X::h`.
With the tokens mapped the pattern units are equal; `M<S>::type`,
`M<X>::type`, `M<X>::a`, `b<X>::<definition>` write `Arr<4>`, `int[1]`,
`int x`, `Arr<1> y` in both images, with no reference to either
function. Every unit is equal. Without this section the run would be
`verified`, where today, with no mapping, it is loud because the
patterns differ. (The review ran it: `c4-outcome-only`; only the three
pattern units differ at the pin.)

The rename itself would not make this edit set (the sites are
contested: the rows say `S::f` in one specialisation and `X::f` in the
other). That is no defence. An edit set is not trusted, and `check`
exists to give the trusted base one that is wrong on purpose.

### 6.2 The obligation of a dependent token (trusted base)

`spec/verify.md` §10.2 rule 5 fails a spelled-entity obligation that an
unresolved name answers, because "the table does not say per
instantiation" what a dependent name denotes. Kiln's rows now say it,
and the walk of the post-image reads them for every declared entry:

> For each entry declared for token `T` in this parse, and each row of
> that entry that has an entity: take the entity's **origin**
> (`spec/verify.md` §10.2 rule 4, `slip_kiln::written::origin`: the
> template or the member of the template it was made from, a
> using-declaration taken to what it names). The row **passes** if the
> walk, under the run's rules and ownership, gives the origin its key
> through a rule that applies to the origin itself, whose `name` is the
> identifier `T.now` and whose `to_name` is the identifier `T.was`: a
> declared rule that renames `was` to `now`, in force. Otherwise the
> row **fails**: the specialisation's name binds something the run did
> not rename.

- **Several rules can claim one token.** The token names no entity and
  no key. A site where one specialisation binds `S::f` and another
  `X::f` is contested for a rename of `S::f` alone; a run that renames
  both has two rules, each row's origin is the subject of one of them,
  and every row passes.
- **A failed row is a hard finding.** It is recorded beside the verdict
  as a failed spelled entity is (`spec/verify.md` §10.2, last
  paragraph): it does not change the observer's digest verdict, and
  **a run with a failed row is not verified**. The record names the
  token, the specialisation (its key and its display) and the entity
  found (its key under the rules, if it has one, and its display).
- In §6.1 the rows `M<X> => X::h()` and `b<X>(X) => X::h()` fail:
  `X::h` is reached by no rule. The run is `not verified` and the
  report names `M<X>` and `X::h`.
- It reads the post-image only, the table the same parse recorded, and
  nothing from the edit set.

**It is one-sided, and this is what it misses.** It checks that what
the name binds *now* is a renamed subject. It does not check what the
name bound *before*.

```cpp
struct S { static constexpr int f(int)  { return 1; }     // renamed to h
           static constexpr int f(long) { return 1; } };  // kept
template <class T> struct M { using type = Arr<sizeof(T::f(1L))>; };
M<S> m;
```

Respell `T::f(1L)` as `T::h(1L)` and declare it. Before, the name bound
`S::f(long)`, which is not renamed; now it binds `S::h(int)` by a
conversion, which is the subject. The row passes. Where a unit of
`M<S>` writes the name, that unit differs (a reference to another
function) and is not matched. Here, in a member alias, no unit writes
it: the outcome is `Arr<4>` both times. The two-sided check compares
the pre-image's row with the post-image's per specialisation; the
pre-image's rows are at pre-image places and are what the substitution
units of WP-153 compare. It is not built here. The case is not silent
because the row has no witness (§6.6), so the entry is outcome-only
and the token residue (§6.3).

It also checks nothing where Kiln has no row with an entity (§6.3
"not instantiated"), and it trusts the entity Kiln wrote in a row as
the spelled-entity check trusts a referent.

### 6.3 What makes a token residue

For a token `T` and an observer whose post-image parse has at least one
entry declared for `T` (the observer **reads** the token), each such
entry is in exactly one state, decided by the verify job from that
parse and from its own comparison of the two images:

| State | When | What it means |
|---|---|---|
| **not instantiated** | the entry has no row with an entity | Kiln recorded no specialisation of this observer in which the name was resolved: the pattern was not instantiated; or the name is in a branch every instantiation discards, in a default argument no call uses, in a member no one uses, in a generic lambda never called; or the header is included twice and this is the copy nobody instantiates; or Kiln records no row for the shape. At the pin the shapes of the last kind are a requires-clause written on a lambda (the review's `a11`) and a name in a generic lambda's body that depends only on a parameter of the enclosing template (probe 4) |
| **vouched** | it has such a row, and every such row has a witness in a matched unit (§6.6) | for every specialisation the observer made, a unit that both images have with one digest holds the name as a reference to the entity the row gives |
| **outcome-only** | it has such a row, and some such row has no witness in a matched unit | for that specialisation no compared unit holds what the name binds: no unit writes the name (the unit holds only the outcome of the expression around it, or the specialisation has no unit at all); or the unit that writes it is not in the pre-image with the same digest; or the join is ambiguous. The reason names the specialisation and which of the three it is |

**The state belongs to an entry in an observer, not to a context.** One
pattern node is vouched where the lambda that holds it is called and
outcome-only where the lambda is named only in `decltype` (§3.2). One
entry with two instantiations, one with a unit and one without, is
outcome-only, and the reason names the one without. The kept list is
not read here.

The token is **vouched in an observer** when every entry declared for
it there is vouched. Over the run:

- An entry that is not instantiated in an observer can be **covered**
  by another observer that vouches the same pattern (§6.7). An
  outcome-only entry is never covered.
- A token is **not vouched** when some observer reads it and has an
  entry that is neither vouched nor covered. It is then **residue of
  category `dependent`**, with the reason `not_instantiated` or
  `outcome_only` (both, if both occur). The result is
  `verified_with_residue` at best.
- A token no observer reads is **unused**: reported, and no state
  changes, because nothing was mapped on its account.
- Nothing here is decided from the edit set. The first version counted
  the edit set's `instances`; the review showed three ways that count
  is not zero while a copy of the pattern is not instantiated, and that
  the count is written by the rename and compared with nothing.

**Why outcome-only is residue and not a finding.** Nothing is known to
be wrong: the pattern is compared with the token mapped, the obligation
of §6.2 passed, and what remains is the one-sided gap. The state says
that the run did not see everything, which is what
`verified_with_residue` is for. The rename tries not to produce such a
token (§5.2): it leaves the name `unresolved` where the pre-image shows
no witness, which is residue `dependent` already. A hand-made edit set
can, and so can a rename whose prediction was wrong.

### 6.4 What stays unverified, exactly

**A declared token is verified in an observer only where, for every
specialisation Kiln's rows give, a unit that both images have with one
digest writes the name as a reference.** There the binding is part of
what was compared, and each row's entity is checked. Outside that:

1. **Not instantiated, and not covered.** Whether `now` denotes what
   `was` denoted when the pattern is instantiated is shown by no
   observer of the run (P8b). Residue, per observer that reads the
   token.
2. **Outcome-only, one-sided.** The post-image's binding is checked
   against the rules (§6.2); the pre-image's is not. A token whose old
   binding was not the subject and whose new binding is, with an equal
   outcome, is not detected. Residue (§6.3); closed use by use as units
   come to write the names (§3.4, WP-156, WP-158).
3. **A specialisation only a translation unit outside the run makes**:
   the limit of every reference, `spec/edits.md` §10.5. Cover (§6.7)
   does not reach past the run either.
4. **What Kiln's rows do not say** (assumption A2 of §6.6). The states
   of §6.3 are computed over the rows Kiln recorded.
   - *An entry with no row at all* is "not instantiated": residue,
     unless covered. Where the observer did in truth instantiate the
     name and a unit holds it, the unit is compared as any unit is and
     the residue is only caution (the shape of probe 4: a name in a
     generic lambda that depends on the enclosing template's parameter
     only). Where it instantiated the name and no unit holds it, and
     another observer covers the entry, that instantiation's binding is
     seen by nothing. No such shape is known at the pin: the shapes
     with no unit (§3.2) all have their row.
   - *An entry with some rows and not others*: the specialisations
     without a row are checked only by their units, where they have
     one. A specialisation with neither a row nor a unit that writes
     the name is seen by nothing, and the entry can be vouched on the
     rows it has.
   - *A row with a wrong entity* is believed by the obligation. It is
     not believed by the witness: a row whose entity is not the one a
     unit wrote has no witness.

   "For Kiln" 2 asks for the sentence that says which substitutions
   give a row.
5. **What the witness assumes** (A0 and A1 of §6.6): that a resolved
   name node at an entry's name location was made from that entry's
   name, and that the nodes one row stands for are written together.
   Both go when Kiln gives the substituted node per row ("For Kiln" 5).

Limits that exist today and are not changed:

- What `now` finds in an instantiation other than the renamed entity (a
  capture) is loud today and is `docs/wp/WP-152.md`.
- A dependent name the rename leaves `unresolved` is residue
  `dependent`, as today.
- An instantiation that no unit of either image holds is not compared
  at all, token or no token (the review's `g1` to `g4`):
  `docs/wp/WP-158.md`. A token there is outcome-only.

### 6.5 What is loud rather than verified

A correct rename is reported as a difference in these shapes. Each is
stated where it arises; none is silent.

- A unit that holds a canonical operand by a type Kiln computed, with
  no operand of its own and no written source (§2.3 step 6; `changed`).
  No source is known to reach it.
- One written type with two operands of one profile that are respelled
  differently (§2.3 step 4, the mix: indeterminate).
- A name whose node Kiln made from the entry and did not record as a
  pattern node (§1.7, the failure mode of the join: `changed`).
- A post-image parse with no pattern nodes recorded, given a
  declaration with tokens: `unverifiable` (§1.7 step 0, §5.5).
- A name inside a macro invocation that forms the name's token
  (`t.ID(g)(1)`): the entry's range is the invocation, no token can
  equal it, and the pattern differs.
- A constructor template's pattern in a class template is
  `Unsupported("kiln/pattern-mem-initializers")` on both sides today,
  with or without a token: indeterminate. An `UnresolvedMemberExpr` is
  `Unsupported` in the full walk in the same way.

### 6.6 The witness (trusted base)

This subsection is the one place of the design from which a wrong
`verified` could come, and it is written to be attacked: the rule, the
facts it reads, the argument, what a wrong join gives in each
direction, what it assumes, the pairs.

**What has to be shown.** A row says: in specialisation `S`, the name
of entry `E` binds entity `D`. The obligation (§6.2) shows that `D` is
a renamed subject. What nothing has shown yet is that the pre-image's
name bound the same subject there. That is shown when, and only when,
the binding is written as a reference into the stream of a unit that
the comparison finds equal in both images. A **witness** is the walk's
own record that it wrote that reference into a unit; **matched** is the
verify job's finding that the unit is equal on both sides.

**The rule.** In a walk given tokens, in this order.

1. **Rows.** Take every row `(E, S, D)` of Kiln's table whose entry `E`
   is declared for a token (§1.7 step 1) and whose `entity` is present.
   `S` and `D` are taken to the entity the digest names them by:
   `Walk::entity` (the first declaration), and for `D` first
   `Ast::strip_shadow` (a using-declaration taken to what it names),
   which is what `Walk::write_ref` does to a declaration before it
   writes a reference to it.
2. **Rows that cannot be witnessed.** A row `(E, S, D)` is
   **unwitnessable**, whatever the walk writes, when one of these
   holds:
   - (a) `S` is templated: a template, a template's pattern, a partial
     specialisation, or a declaration inside one
     (`own_spelling::templated`). These are the rows whose `spec` is a
     key that several argument lists share (Kiln `spec/ast.md`
     §18.9.2: an alias template, the template of a default template
     argument, a concept, a constrained templated declaration).
   - (b) the name location of `E` (`WrittenRefs::name_lo(E)`) is also
     the name location of another entry of the table, declared or
     not.
   - (c) another entry declared for the same token also has a row with
     an entity for the same `S` (the ruling: one token, two entries of
     one range, one specialisation).
3. **Writes.** A **write** is recorded when the expression walk writes
   the declaration field of a node `n` and all of these hold:
   - (a) `n` is a `DeclRefExpr`, or a `MemberExpr` whose type is not
     `QualType::OVERLOAD`; the field is `ExprNode/DeclRefExpr.a` or
     `ExprNode/MemberExpr.b`. Nothing else is a write: not a member of
     the found set of an `UnresolvedLookupExpr`, not the first
     candidate of an overloaded access, not a `found` declaration, not
     the declaration of a template argument, not a reference inside a
     key or a type digest.
   - (b) the reference is written as a key: `Walk::write_ref` gave the
     declaration a key and wrote `REF_UNIT`. A local object, a template
     parameter and an indeterminate reference are no write.
   - (c) the walk is in **full-walk mode in a unit's own stream**: the
     stream being written is one that becomes a unit of this walk's
     output (those `units::write` and `demand::write_resolved` make),
     not a candidate stream of `units::canonical_decl`, not a content
     digest, not a key; `in_key`, `type_nesting` and `by_value` are 0;
     there is no profile frame (`unit.expr.profile` is none); the walk
     is not numbering locals. This is the state in which the names
     digest collects (`Walk::feed`, `names_start`, `names_off`), and
     the collector is built beside it, in the unit state, so that
     `take_unit` sets it aside with the rest.
   - (d) `n.loc()` is the name location of an entry declared for a
     token.

   The write is `(U, L, D′, P)`: `U` the unit being written, `L =
   n.loc()`, `D′` the entity whose key `write_ref` wrote, `P` the
   declaration path of step 4.
4. **The declaration path** `P` is a set of entities:
   - the entity of `U`; for a resolved unit (`<definition>`,
     `<default_argument N>`, `<exception_spec>`, `<value>`) the owner
     the unit is named after;
   - every declaration whose stream the walk has entered in place
     inside `U`'s stream and not yet left: a local class, a closure
     type, a member of either (at the pin through `Walk::decl_stream`
     from `local.rs`; pushed on entry, popped on return);
   - for each of those, every declaration that encloses it: for a
     local entity its owner (`local::owner`: the function, variable or
     field whose stream holds its declaration), else its semantic
     parent in Kiln's tree (`DeclData::ctx`), up to the namespace.

   The template a specialisation was made from is not an enclosing
   declaration.
5. **The match.** A write `(U, L, D′, P)` **matches** a row `(E, S, D)`
   that is not unwitnessable when `L` equals `name_lo(E)` (as Kiln
   `Loc`s, which are different for two expansions of one macro), `D′`
   equals `D`, and `S` is in `P`.
6. **The witness.** A write that matches exactly one row is a
   **witness of that row in `U`**. A write that matches two or more
   rows is a witness of none.
7. **Determinate units only.** A witness in a unit that ends
   indeterminate is dropped.

The verify job, which has the units of both images:

8. **Matched.** A unit of the post-image with class `c`, key `k` and
   digest `d` is **matched** when the pre-image shard of the same
   observer has, in class `c` at key `k`, the digest `d` at least as
   many times as the post-image has it there. In the terms of
   `spec/verify.md` §4: `d` is not in `A(k)`. A unit of a group that
   §4.1 did not open is matched, because the group's sums are equal.
9. **A row is witnessed** when it has a witness in a matched unit. An
   entry is vouched when it has a row with an entity and every such
   row is witnessed (§6.3). For the first row that is not, `missing`
   says why: `no_unit` (no witness at all, or the row is unwitnessable
   by 2a), `ambiguous` (2b, 2c, or step 6 took its only writes),
   `unit_not_matched` (it has witnesses, none in a matched unit).

**The facts it reads.**

| Fact | Whose | Step |
|---|---|---|
| the rows: `WrittenRefs::specs()`, and of each `SpecRef` the members `entry`, `spec`, `entity` | Kiln, `spec/ast.md` §18.9; through the new function of `slip_kiln::written` (stage 1) | 1 |
| which entries are declared: an entry's referent, its flag `DEPENDENT`, its name range | Kiln's table; §1.7 step 1 | 1, 2c, 3d |
| `WrittenRefs::name_lo(id)` for every entry of the table. Kiln documents it: "Where the name of entry `id` begins as an expression stores it: the `~` of a destructor name, else `range.lo`. The location of a `DeclRefExpr` or `MemberExpr` built from an id-expression or a member name equals it" | Kiln | 2b, 3d, 5 |

**Why a witness in a matched unit is enough** (item 4 of the ruling).

- The post-image's unit `U` wrote, in its own stream, the field
  `REF_UNIT ‖ key(D)`, the key taken under the rules. By §6.2 the
  origin of `D` is the subject of a rule that renames `was` to `now`,
  so that key is the key the subject had in the pre-image.
- `U` is matched: the pre-image has a unit of the same class and key
  with the same digest. A digest is the hash of the unit's stream, so
  the two streams are the same bytes; this is the comparison's own
  premise for every unit. A stream is written field by field in a fixed
  order after each node's tag, so equal bytes are equal trees with
  equal references. The pre-image's unit therefore holds, at the same
  place of the same tree, a resolved name node with a reference to the
  same key.
- So what the specialisation's unit binds at that place is the same
  entity in both images, up to the rename. **Had the pre-image's name
  bound another entity there** (`X::mf(long)`, where the post-image
  binds `X::mh(int)`), the pre-image's stream would hold another key in
  that field, the digests would differ, and `U` would not be matched:
  it is `derived_changed`, a finding, and the row is not witnessed.

That step needs `U` to be compared. **Each way a unit that holds a
witness can fail to be, and what the entry's state is then:**

| The unit that holds the witness | Finding today | After WP-155 | The row |
|---|---|---|---|
| is derived, has its key in both images, and the digests differ | `derived_changed`; no exemption exists for it | the same | not witnessed; the run is not verified in any case |
| is declared (an explicit instantiation; an ordinary function that holds the name in a local class), has its key in both images, and the digests differ | `changed`, unless `Declared.changed` exempts the key: then no finding | the same | not witnessed |
| is derived and its key is in the post-image only: a specialisation only the post-image instantiates (the edit changed which specialisation a call selects, or added a use); or the key moved because a parent's did | **none**: counted in `verify.derived.only_post` | `derived_only_post` if the unit is marked "emitted unreferenced"; **none** if it is unmarked | not witnessed |
| is declared and its key is in the post-image only | `added`, unless `created` exempts it | the same | not witnessed |
| is indeterminate in the post-image, or its key is indeterminate in the pre-image | `indeterminate` or `derived_indeterminate` | the same | not witnessed (step 7; an indeterminate unit of the pre-image has no digest to equal) |
| twice in the post-image with one digest and once in the pre-image | whatever §4 says of the multiset | the same | not witnessed: step 8 cannot say which of the two is the pre-image's |

In every row the witness is not counted, so **no one-sided unit holds a
counted witness, whether or not it gives a finding**. An entry with
such a row is `outcome_only`, reason `unit_not_matched`, naming the
unit and the specialisation. The cells printed in bold are the cases
with no finding, where the witness rule alone keeps the run from
`verified`; the rule does not depend on WP-155's mark.

A specialisation only the *pre-image* instantiates has no row in the
post-image, so this package claims nothing for it. That it vanished is
WP-155's subject (a marked derived key in one image only) and, where no
unit held it, WP-158's.

**A wrong join, in each direction.**

- **A witness missed**: the walk wrote the binding and the rule did not
  count it. The row is not witnessed, the entry is `outcome_only`, the
  token is residue, and the result is `verified_with_residue` at best.
  Loud, never wrong. Every strictness of the rule (2a to 2c, 3b, 3c, 6,
  7, 8) and every incompleteness of the path (a declaration entered in
  place and not pushed, a parent not followed) can only do this.
- **A false witness**: the rule counts a write for a row whose binding
  no matched unit holds. This is the wrong `verified`. The argument
  that the three-part match cannot give one:

  Let the write `w = (U, L, D, P)` match the row `r = (E, S, D)` and no
  other row, with `U` matched. `w`'s node `n` is a resolved name
  node at the name location of `E`, and by 2b that location is no other
  entry's. Kiln gives a `DeclRefExpr` or a `MemberExpr` the location
  `name_lo` of an entry when it builds the node from that entry's name
  (the sentence quoted above), so `n` was built from the name of `E`
  (assumption A0 below is the converse: nothing else at that location
  carries `D`). `E` is dependent, so the parser's own node for it is
  one of the three dependent kinds or an overloaded access, which 3a
  excludes; `n` is therefore a node a substitution made for `E`. It is
  resolved to `D`, and it is written inside a declaration at or under
  `S`, because `S` is in `P`. Now either

  - `n` is the node the substitution for `S` made, or a copy a later
    substitution inside `S` made of it (a nested lambda or local class
    instantiated again; a name already resolved is not looked up
    again). Then `U`'s stream holds the binding `r` speaks of, and the
    witness is true. Or
  - `n` was made by the substitution for another specialisation `S′` of
    the same entry. `n` is written in `U`, so `S′` is on `P` as `S` is,
    and one of the two encloses the other. If Kiln has the row
    `(E, S′, D)`, `w` matches two rows and is a witness of none (step
    6). If it has not, the name was resolved in the outer of the two
    and copied into the inner, which is the first case again.

  A path that is too long (a declaration in `P` that does not enclose
  the walk's place) could put a wrong `S` in reach; it would also need
  the true specialisation's row to be missing (else step 6), and the
  path is built from parent links only, never from the template a
  specialisation came from.

**The cases the ruling names, one by one.**

- **A macro expansion that puts two nodes at one location.** Each
  expansion of a macro owns a range of `Loc`s of its own, so the nodes
  made from two expansions of one argument have different `Loc`s
  although their spelled range is one (probe 4: `TW(t.mf(1L))`, two
  entries, each entry's node at its own `Loc`). Should two entries ever
  have one `Loc`, 2b takes both out. One token with two entries in one
  specialisation is taken out by 2c whatever their `Loc`s: at the pin
  that makes `TW(t.mf(1L))` and `TWO(mf)` `outcome_only`, although each
  write there matches one row (the open point at the end of this
  subsection). Two nodes of *one* entry at one `Loc` are the elements
  of a pack expansion (A1 below).
- **A default argument instantiated at several call sites.** Kiln
  instantiates a default argument once for its function, and the row's
  specialisation is the called function. The digest writes the
  expression in one unit, `<default_argument N>` of that function,
  whose owner is in `P`. A caller writes a `CXXDefaultArgExpr`, which
  names the parameter, and never walks the default's nodes (`expr.rs`,
  "Shared nodes"; probe 4: three call sites in two functions, and a
  default used inside its own function: one unit begins the node, and
  no caller's). So there is one write, in one unit, for one row. A
  default argument of a function that has no such unit (a lambda's call
  operator, a local class's member) is written by no unit: no write,
  no witness, `outcome_only`.
- **A lambda in a default member initialiser.** The row's
  specialisation is the field of the class specialisation. The
  initialiser is the unit `DM<X>::x::<default_argument 0>`; the closure
  type and the body are walked in place there, so `P` holds the field.
  A constructor that uses the initialiser writes a `CXXDefaultInitExpr`
  and not the nodes. A *generic* lambda there has rows keyed on its
  call operator's specialisations, and a unit of its own
  (`DM<X>::x::local(0)::operator()<X>(X) const::<definition>`) when it
  is called; named only in `decltype` it has none, and no witness.
- **A node reached by two paths.** Within one stream the second reach
  is written as a back-reference: no field, no write; the first reach
  is the write. In two units (a generic lambda's body that names the
  enclosing function's parameter is written by the function's unit and
  by each call operator's): each is a write in its own unit, each unit
  truly holds the binding, and the row is witnessed by any of them that
  is matched. Through a type (the sugar of an expression's type that
  leads to an operand, §2.3), a key or a content digest:
  `type_nesting`, `in_key` or `by_value` is not 0, or a profile frame
  is open, so 3c records nothing. Through a candidate stream: not a
  unit's stream.
- **The pattern's own nodes.** The found set of the pattern's
  `UnresolvedLookupExpr` is written as references that can include `D`:
  not a write (3a), and the pattern's path holds no specialisation in
  which the name is resolved. An overloaded access on an object that is
  not dependent is a `MemberExpr` that names the first candidate and
  is written like any member: excluded by its type (3a).
- **Two instantiations that bind the same entity, one with a unit.**
  With `struct X2 : X {};` and `decltype(l(X2())) x = l(X());` the rows
  are `(E, operator()<X>, X::mh)` and `(E, operator()<X2>, X::mh)`. One
  unit writes the name, `operator()<X>`'s; its path holds
  `operator()<X>` and not `operator()<X2>`. The second row has no
  match, and the entry is `outcome_only`. Only the specialisation
  decides this pair (the review's `e21` binds two different entities,
  which the entity check decides).
- **A pack.** `fo(X(), Y())`: two rows for one entry and one
  specialisation, with different entities; each write matches the row
  of its entity. `fo(X(), X())`: Kiln keeps equal rows once, so one row
  stands for two nodes, both written by the same unit (A1).

**What it assumes.** Each is stated so that it can be shown false by a
source.

- **A0, the location.** A resolved name node at the name location of
  entry `E` whose declaration is the entity `E`'s name resolves to was
  made from `E`'s name. What would break it: Kiln placing, at a name's
  location, a resolved node it made from something else, with the same
  declaration. The implicit nodes Kiln places at an operand's start (a
  conversion function's, `operator->`, `operator()` of an object) name
  an operator or a conversion function, which a plain identifier never
  denotes. The implicit `begin` and `end` calls of a range-for name a
  function by an identifier and stand at the range's place; they are
  written in the same statement of the same unit as the range
  expression itself.
- **A1, one row for several nodes.** Kiln keeps equal rows once, so a
  row can stand for several nodes rebuilt from one entry for one
  specialisation, and the witness needs only one of them to be written.
  It is right if such nodes are written together or not at all. The
  only way known to get several nodes from one entry in one
  specialisation is a pack expansion or a fold, whose elements are
  children of one node and are written by the same units. What would
  break it: two rebuilds of one entry for one specialisation in
  different places, one written and one not, that bound different
  entities in the pre-image and the same in the post-image.
- **A2, the rows are complete.** It is not needed for the witness of a
  row; it is needed for "every row" to mean "every specialisation"
  (§6.4 item 4) and for cover (§6.7).

**The later form, to ask of Kiln** ("For Kiln" 5; the supervisor
carries it): each row names the expression node the substitution made
for the entry in that specialisation, one row per substituted node
(equal rows of different nodes no longer kept once). The witness is
then "the walk wrote, in full-walk mode in a unit's own stream, the
declaration field of exactly that node". Steps 2b, 2c, 4 and 5 and the
assumptions A0 and A1 go; the entity stays as a cross-check, and steps
7 to 9 stay as they are.

**What the pin shows** (probe 4, §0.3; the units that begin a resolved
name node at the entry's place, against the rows):

| Witness expected | Shapes |
|---|---|
| yes, in the specialisation's own unit | a member call, an argument-dependent call, `T::sf(1L)`, `&T::sf`, `this->mf(1L)` in a function template's body; a generic lambda called, or named only in `sizeof`; a member template of a class template; a constructor's initialiser; a friend defined in a class template; a variable template; a static member's initialiser; an explicit instantiation; a using-declaration; a callee that is a function template; a redeclared member |
| yes, in the unit Kiln keys the row on | a member's and a function template's default argument (the function; the unit is its `<default_argument N>`); a default member initialiser and a lambda in one (the field) |
| yes, in the enclosing unit, in place | a member of a local class in a function template (`lc<X>(X)::<definition>`) |
| no: no unit begins the node | a generic lambda reached only through the conversion to a function pointer; the `decltype`-only instantiation of two; a default argument of a lambda's call operator and of a local class's member; `noexcept(noexcept(e))` on a function template; a trailing return type |
| no, by 2c | a macro argument substituted twice; `TWO(mf)` |
| no row at all | a name in a generic lambda that depends only on the enclosing template's parameter; an unused member |

Not probed for the join: rows 10 to 13 of §3.3 (a `static_assert`, an
enumerator, `alignas`, a bit-field's width in a class template). Their
units are known from the first review's run and their rows' key from
Kiln's §18.9.2 (the class specialisation, which encloses the unit's
entity); stage 1's pairs decide.

**How it is built so that each part can be tested alone.** The match
is a pure function over plain data, in a module of its own in
`slip_digest`:

```
Row   := entry, spec, entity, unwitnessable        steps 1 and 2
Write := unit, loc, entity, path                   step 3, recorded by the walk
join(rows, name_lo of each declared entry, writes) -> for each row, the units that hold a witness     steps 5 and 6
```

The walk only records writes; the verify job only decides "matched".
So each part of the match has unit tests on tables made by hand
(§8.2), and the pairs of §8.1 show the whole on sources.

**Open point.** Step 2c is the ruling's and is redundant with 2b at the
pin, where `Loc` already separates two expansions. Dropping 2c would
vouch `TW(t.mf(1L))` and `TWO(mf)`; it would rest on `Loc` equality
alone to tell the two entries' nodes apart. The proposal keeps 2c
("Open questions" 1).

### 6.7 Cover: a copy of a pattern that another observer vouches

**Ruled** (open question 1 of the first revision, as the supervisor
proposed, with the delta review's conditions). A token in a header
template is read by every observer that includes the header and
instantiated only by some. By §6.3 alone, one observer that includes
and does not instantiate makes the token residue, which on a large code
base is most tokens in shared headers.

**The homes of an entry.** For an entry `E` declared for token `T` in
an observer, a **home** is a triple `(k, d, i)`:

- `(k, d)` are the key and the digest of a determinate unit of the
  post-image whose digest depends on a name of `E` that the walk
  respelled (§1.7 step 3): the walk respelled a declared node of `E`
  while writing the unit's stream or its key, or a type digest the
  unit holds. The memo of §2.3 step 3 keeps, with each digest, the
  entries respelled under it, so that a unit that takes a type's digest
  from the memo has the same homes as the unit that computed it.
- `i` is the **ordinal**: the rank of `E` among the entries declared
  for `T` that have this unit as a home, in the order of their name
  locations (Kiln's `Loc` order, which within one buffer or one
  expansion is source order). It tells apart the two entries of one
  token in one unit (a macro argument substituted twice).

The homes go to `token_use` (§5.5). An entry with no determinate home
has none and cannot be covered.

**The rule**, in the run's fold (`slip_verify::run`). An entry `E_B` of
observer `B` that is **not instantiated** (§6.3) is **covered** when
there is another observer `A` of the run, whose shard is this run's and
whose state is `verified`, with an entry `E_A` declared for the same
token such that

1. `E_A` is **vouched** in `A` by §6.3 and §6.6: by witnesses, not by
   cover; and
2. `E_B` has at least one home, and every home of `E_B` is a home of
   `E_A`: the same key, the same digest, the same ordinal.

The entry is identified across observers by (token, the writing unit's
key and digest, the ordinal). The inclusion goes one way because the
instantiating observer writes the name in more units than the other
does (a pattern nested in an instantiation, §3.1).

- **Per entry, not per token.** A token with two entries (a header
  included twice, one copy instantiated) is covered entry by entry.
- **Never `outcome_only`.** An outcome-only entry has specialisations
  of its own in this observer, and another observer's units say
  nothing about what the name binds in them.
- **Never instantiated anywhere stays residue.** If no observer vouches
  the entry, it stays `not_instantiated`.
- **No chains.** A covered entry covers nothing.
- **The report** gives `covered` beside `vouched` and `read` (§5.6).

**Why it is right, and what it rests on.**

- Observer `B` has no row for `E_B`, so `B` made no specialisation in
  which the name was resolved: `B`'s program binds nothing through this
  name. All that `B` holds of the name is the units that write it as a
  name, and those are, key and digest, units of `A`. A unit's stream
  holds the pattern as written and, for an unqualified call, the
  declarations found at the definition (§4), so `A`'s copy of the
  pattern is the same pattern with the same found set.
- In `A`, every specialisation Kiln's rows give has a witness in a
  matched unit. **Cover rests on the witness rule**: if `A`'s vouching
  were the first revision's (by context), a `decltype`-only use in `A`
  would cover `B` with nothing compared.
- It rests on A2 in `B`: "no row" must mean "not resolved". If `B` did
  resolve the name in a specialisation Kiln recorded no row for, that
  binding is compared only if a unit of `B` writes it (§6.4 item 4).
- It says nothing of a specialisation that no observer of the run
  makes (§6.4 item 3).

## 7. Inertness and scheme

- **With no token no digest moves.** Every change to the walk is behind
  "the token list is not empty": the entry scan, the name writers, the
  collection of own operands and the override of §2.3, the reading of
  rows, the record of writes for the witness (§6.6 step 3), the homes
  (§6.7), the flag of §3.2. A walk of `slip parse`, of a verify job
  whose declaration has no token, and of a map job with no watch list
  reads none of it. The post parse does not record written references
  on this account.
- **The witness and the watch list write nothing into a stream.** A
  write is recorded beside the stream, as the names digest collects
  beside it. A walk with a watch list (the map phase of a rename,
  §5.2) gives the digests it gives without one; a test of stage 1.
- **The column `instance`** of `spec/digest-kinds.md` (§3.2) is read
  only for the context of a node, which is a reason text. It changes
  no stream: a row's bytes are the same whether it is marked or not.
- **A token that matches nothing changes nothing** (the inertness of
  `spec/digest.md` §3.4 for rules, `crates/slip_digest/tests/inert.rs`):
  a token at a range where no dependent entry is, or whose `now` is not
  the node's name, declares no node; no name is written otherwise, no
  type takes the override path (step 2 of §2.3 is today's path, from
  the same memo), and the shard's `token_use` does not list it.
- **`scheme` stays 2.** No stream, key or table row changes for a walk
  without tokens, and no existing unit changes. Under a token list the
  only comparison that changes is that of a unit that writes a declared
  node (different before; equal now if nothing else moved). The rule of
  `spec/digest.md` §11 changes `scheme` before the first release only
  when units that compared equal under some rule table are made to
  differ; no comparison was ever made under a token list, and no
  baseline of scheme 2 is recorded. The cause
  `Unaccounted("spelling/respelled-mix")` can arise only under a token
  list.
- **Formats.** `DECL` version 3 only when there are tokens; a new piece
  tag; a new shard section present only when there are tokens; a new
  version of `EDTS`, written only when an `unresolved` entry carries a
  reason; a new version of `RSLT` (§5). A container written today is
  read as today. A run with no token and no such entry writes the
  bytes it writes today, except the version number of its result.
- **Cost with tokens.** Once per post-image parse: one pass over the
  entries without a referent (a name range each, the function the
  spelled-entity check already calls), one over the pattern nodes, one
  over the rows of the declared entries (an origin and a key each); a
  map from node id to token with one entry per declared node. Per
  dependent name node written: one lookup. Per resolved name node
  written in full-walk mode in a unit's stream: one lookup by location
  in a map with one entry per declared entry, and for a hit the match
  of §6.6 (the path is a short stack; its parents are followed only on
  a hit). Per written type that is instantiation-dependent: one walk of
  its sugar, memoised per written type, which is the traversal the
  own-spelling walk makes today for the same types. In the verify job:
  one look, per unit that holds a witness, at the comparison's result
  for its key. Recording written references in the post parse is a cost
  a rename's verify phase already pays for its obligations; the pattern
  nodes and the rows are recorded on top of that whenever the
  declaration has tokens.
- **The cost is tracked, from stage 3 on** (the delta review's S5).
  Recording pattern nodes and rows on every post-image parse of a run
  with tokens is time and memory of the verify job. Stage 3 puts it
  into the harness's tracked numbers (`spec/harness.md` §7.1):
  - *deterministic*, summed over the verify shards: the counters
    `verify.tokens.*` of §5.5, and the parse's counts of what was
    recorded (`parse.written.entries`, `parse.written.rows`,
    `parse.written.nodes`; added by stage 3 if `spec/model.md` has no
    such counters yet);
  - *measured*, of the verify phase of a transform test on a corpus
    (`spec/harness.md` §6.5): `cpu_s`, `wall_s`, `peak_rss_max` and
    `peak_rss_p99`, set beside the same corpus's identity run (§9.2 of
    that specification), whose verify jobs record nothing. The
    difference is the cost of this package on that corpus, and the
    baseline of §7.3 there holds it from then on.

Each is a package that can be launched as written. **Order on the

- the guard of step 0; the entry scan and the node map; the name

- for a watch list (the map phase of a rename, §5.2): steps 1 to 7 of

## Open questions

The six questions of the first version and the two of the first
revision are ruled (the two tables above). Three points are new; the
proposal is written with a choice for each, so nothing waits for them.

1. **Step 2c of §6.6 against `Loc`.** The ruling takes a token with
   two entries of one range in one specialisation out of the witness.
   At the pin Kiln's `Loc` already tells the two expansions' nodes
   apart (probe 4), and step 2b catches two entries at one `Loc`. So 2c
   costs the two macro shapes their `vouched` (a macro argument
   substituted twice; one macro parameter used as a name twice) and
   buys independence from `Loc` equality across expansions. **Written
   with 2c, as ruled.** Dropping it later is a one-line change with two
   pairs to turn around; the node per row ("For Kiln" 5) makes the
   question go away.
2. **A write that matches two rows of one entry** (one entity, two
   specialisations, one enclosing the other) witnesses neither (step
   6). The argument of §6.6 says it could witness both: the inner
   binding is a copy of the outer. No shape with two such rows is known
   at the pin (Kiln records the row at the specialisation that resolved
   the name and none at the others). **Written strict.**
3. **Where the planning marks live.** The flag of §3.2 reads a column
   of `spec/digest-kinds.md`, which is otherwise the trusted base's
   table. The column is advisory and changes no stream; the
   alternative is a list in the rename's specification that names
   fields of that table. **Written with the column**, because the
   generated tables are the only place the walk's steps have names.
