# WP-157 — `reduce` gives no edit set for an unfinished map phase

`crates/slip_cli` (`spec/edits.md` §8.2, §10.2; `docs/wp/WP-157.md`):
`src/transform/{store,reduce,check}.rs` and `tests/rename.rs`. Nothing
outside `slip_cli` changed. `spec/edits.md` §10.2 now says that an edit
set is always of a finished map phase and that this is `reduce`'s
promise.

## What moved

- **One check, one wording.** WP-076's check (in `check::map_pass`) is
  `transform::store::map_shard_of_round`: the selected observer's map
  shard of the round, read and decoded once
  (`verify_cmd::read_map_shard`). None, or bytes that are not its shard
  (another observer's, phase or round, or no shard at all), is the input
  error `<main file>: no|an unusable map shard of round <r>: the round's
  map phase did not finish for this observer (interrupted?); run `slip
  map` again`. `check::map_pass` calls it for each selected observer, as
  before.
- **`transform::store::map_phase_finished`** calls it for every observer
  the round's map phase selected (`selected_of_round`: the jobs of the
  latest map run record, not the plan's observers), on up to the
  threads `reduce` has, and gives the error of the least selected
  position that has one, so the message does not depend on the threads.

## Decisions

1. **Where `reduce` checks.** `slip reduce` runs `map_phase_finished`
   after `selected_of_round` and before `request_of_round`: a shard that
   cannot be decoded is this error, not the request's, and nothing is
   folded or published. No transform run record is published by
   `reduce` (as before), so no record names an edit set.
2. **`rename` does not check again.** Its reduce step follows the map
   step only when `pool::run_with` returned a summary, which it builds
   only when every observer given to it has its shard
   (`Summary::outcomes`, an `unreachable!` otherwise). An interrupted or
   failed map phase returns an error and `rename` stops before reduce.
   `rename::s10_6_rename_interrupted_in_map` shows it: no edit set, the
   record names none. Checking again would decode every shard once more
   on the main path of every rename.
3. **`check` of a refused set** (item 4 of the WP). `map_pass` runs only
   after the apply step, which a refused set does not have: such a set
   of an unfinished round (made by a `reduce` before this WP, or given as
   a file) was concluded as a `refused` result that counted the missing
   observers as unparsed (the set's `unparsed`). `check`'s `prepare` now
   runs `map_phase_finished` for a refused set (one thread), so the round
   is refused with the same error, and the record is published with no
   step (WP-076 decision 1). An accepted set is checked by `map_pass` as
   before.
4. **`reduce --allow-unparsed`** is a usage error (status 2): it is not
   among `reduce`'s options (`spec/exec.md` §8), so the WP's test "the
   same with `--allow-unparsed`" is that usage error for `reduce` (no
   edit set either), and status 3 for `check` with the flag.
5. **Cost.** `reduce` decodes every selected shard once more before its
   two passes, in parallel. `slip_reduce` itself is unchanged.

## What else reads a round's map shards

Each reader of a transform round's map shards, and what it does with a
missing one:

- `slip_reduce::reduce` (`Shards::open` returning `None`): takes it for
  an unparsed observer, as its contract says. Outside `slip_cli`; both
  callers now guarantee it does not happen (`reduce` by the check,
  `rename` by decision 2). Reported, not changed.
- `transform::store::request_of_round`: skips it while looking for the
  first shard with `edits`. Harmless (the request is still the round's),
  and in `reduce` it runs after the check.
- `transform::map::map` (the `failed runs` count): reads only after a
  finished phase.
- `check`'s verify step (`map_shard`, `verify_cmd::map_status`), and the
  verify job's `read_pre` in `verify_job.rs`: they read again after
  `map_pass`, and a shard gone by then goes to the trusted base as no
  map shard, which never makes it `unchanged` or `verified`
  (`never_parsed` or `failed`).
- `check` with a refused set: fixed (decision 3).
- `apply`: reads no shard; not changed (§10.2).
