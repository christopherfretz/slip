# WP-072 — rename: virtual families, using-declarations and the other followers

`crates/slip_refactor/src/rename/families.rs` and `followers.rs`
(`spec/edits.md` §9.2, the parts `docs/wp/WP-071.md` left
conservative), one addition to `subjects.rs` (`Subjects::add_ruled`),
two reduce tests and a wider post-image check in `tests/rename.rs`, and
38 directories under `crates/slip_refactor/tests/rename/` named
`s9_2-*` (four of them the core's `conservative-*` directories,
renamed). `rename/mod.rs` is unchanged: no hook signature changed. Kiln
sites are at Slip's pin, under `kiln/crates/`.

## What was built

- **Virtual families** (`families::collect`). The functions looked at
  are, in id order, every `decl_names` entry named like the old
  identifier that is a member function (`DeclKind::CXXMethod`, named by
  an identifier), and every function of Kiln's overriding record so
  named. One that overrides nothing and is not virtual is skipped (its
  name is `decls::claim`'s). Each is taken to its origin
  (`written::origin`) and the digest's entity and added as a
  `candidate` (a seed stays one); each function it overrides directly is
  added the same way and linked to it.
- **Where overriding is read**: `DeclArena::cold.overrides`
  (`kiln_ast/src/decl.rs:1686-1688`, "virtual member function → the
  methods it overrides"), written by `Sema::finish_virtual_decl`
  (`kiln_sema/src/class/virtual/mod.rs:255-259`) from the list
  `Sema::virtual_decl` computes (`overridden_methods`, near `:130-150`).
  A redeclaration shares its first declaration's list, so the record is
  read on `Ast::first`. A member declared when a class template is
  instantiated goes through the same path (`kiln_sema/src/decl.rs`
  near 6237-6249), so an instantiated class's overrides are recorded
  too. Kiln's own reader is `graph.rs:77` (`overridden(ast, m)` on
  `ast.first(m)`). Nothing compares names or signatures.
- **Using-declarations** (`followers::using_declaration`), for each
  `decl_names` entry of kind `UsingDeclaration`: the shadows are
  `Ast::using_shadows(u)`, else those of its redeclarations
  (`Ast::redecls_of`: Kiln links a repeated namespace-scope
  using-declaration to the first, which holds the shadows). Each
  shadow's target (`Ast::using_target`) is taken to its origin's key
  id. Naming no subject: nothing (`decls::claim` keeps it). Otherwise
  the declaration is settled and becomes a follower with `of` every key
  id named, subject or not, and its name is claimed `replace` with a
  literal piece; each shadow whose target is a subject becomes a
  follower `of` that subject.
- **Unnamed classes and enumerations** (`followers::unnamed_types`):
  for each subject, the tag its type declares an object of, through
  pointers, references, arrays, member pointers and qualifiers
  (`declared_tag`), when that tag is unnamed, its key's name is
  `unnamed_by(identifier(old))` and its parent is the subject's: a
  follower `of` the subject, with the rule `unnamed_rule` makes from its
  `Key` (the name `unnamed_by(identifier(new))`, the parent, kind and
  discriminator kept, called by the name it has now).
- **`Subjects::add_ruled`**: `add` with the rule made by a closure in
  place of `Keys::rename_rule` (`None`: `unsupported`). `add` calls it.
  `Subjects::link` lost its `dead_code` allowance.
- **Tests**: `rules_give_the_ids_in_the_post_image` also expects, in the
  post-image, the key ids of the shadows of every using-declaration
  named new and of the unnamed tag a declaration named new declares.
  The two reduce tests (below) run `slip_reduce::reduce` on two
  observers' `Edits`.

## Decided where the spec was silent

Each is now in `spec/edits.md` §9.2 or §9.5.

1. **The two sources of functions looked at.** `decl_names` alone misses
   a member of an instantiated class (no extent) and a name a macro
   pastes; the overriding record alone misses a virtual function that
   overrides nothing and is overridden in no unit this observer parses
   (`s9_2-virtual-pure-seed-no-override`). Both are read.
2. **A family member with no key** (`Keys::key_id` refuses) cannot be a
   subject, so its link cannot be recorded: the function at the other
   end is `unsupported`. A function reached that the AST does not name
   like the old identifier makes the one reaching it `unsupported`
   (cannot arise; kept so that a front end that did would refuse).
3. **A candidate or follower declared in a template's pattern** (a key
   of kind class template, partial specialisation or function template
   among its enclosing entities) is `unsupported`, as a seed member of
   a class template is: its followers in the specialisations are
   `docs/wp/WP-073.md`'s. An explicit specialisation's member is not in
   a pattern (`s9_2-virtual-in-explicit-specialisation`).
4. **A using-declaration's `of` is every entity it names**, a non-subject
   by its key id: so an overload set partly selected is
   `mixed_follower` in reduce, which reads `of` against the selection
   (`s9_2-using-partly-selected`). A target with no key makes the
   follower `unsupported`.
5. **A using-declaration with no key** (one at block scope: no key
   kind) is no follower; its name is claimed `replace` for the subjects
   it names when it names only subjects, else `refuse(mixed_set)`
   (`s9_2-using-block-scope`, `-block-scope-mixed`).
6. **A using-declaration with no shadow of its own** is taken through
   its redeclarations; with none there either, its name is claimed
   `unresolved`. A repeated one is the same entity (one follower,
   `s9_2-using-twice`).
7. **An unnamed tag's parent must be the subject's.** The key decides
   which declaration names an unnamed class (`digest.md` §3.3); a
   variable of another scope's unnamed class by `decltype` is no follower
   (`s9_2-unnamed-class-of-another-scope`), nor is the second declarator
   of `struct {} a, b;` (`-second-declarator`).
8. **An unnamed tag whose key `Keys::key` refuses** cannot be listed (no
   key id): the subject gets `unsupported` instead.
9. **A reference found through a shadow** (`via_using`) is claimed for
   its referent as any reference is (§9.3); nothing more is needed,
   since the shadow is a follower already. A shadow not reached this way
   (a using-declaration whose name a macro pastes) is not missed
   silently: the name is refused as a macro's, and a shadow's key
   changes with its target's name, so verification sees it.

## The core's conservative rows

Gone: `families.rs`'s "a virtual function is `unsupported`"
(`conservative-virtual` is now `s9_2-virtual-one-override`);
`followers.rs`'s "a subject named by a using-declaration is
`unreachable`" (`conservative-using-declaration` is
`s9_2-using-namespace-scope`; WP-071's "Stage 3 roles" For Kiln entry
is answered: the name is read from `decl_names`, kind
`UsingDeclaration`); "a variable of an unnamed class is `unsupported`"
(`conservative-unnamed-class*` are `s9_2-unnamed-class*`).

Kept, each a refusal: a candidate or follower in a template's pattern
(decision 3; WP-073's); a dependent using-declaration is `unresolved`
(`conservative-dependent-using-declaration`; WP-073 needs the found
set, WP-071 For Kiln K4); a keyless family member (decision 2); a
using-declaration with no shadow anywhere (decision 6).
