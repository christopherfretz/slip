# WP-061 — slip_model: the edit set, overlay, result and transform run record

Implemented by `slip_model::editset`, `slip_model::overlay`,
`slip_model::result`, `slip_model::transform_run` and their codecs under
`slip_model::formats` (`editset.rs`, `overlay.rs`, `result.rs`,
`transform_run.rs`). This file fixes what `edits.md` §5.4, §6, §7.1,
§8.4, §8.5 and §10.6 leave open, so that a second implementation reports
the same error at the same place. Tests: `crates/slip_model/tests/editset.rs`
and `crates/slip_model/tests/editset_properties.rs`.

Every violation is `Malformed` at the offset named, and `validate` and
`from_json` give `<path>: <message>` with the message below, verbatim.

## 1. Geometry (`edits.md` §5.4)

A range `(lo, hi)` is the bytes `lo..hi`. A range with `lo >= hi` has no
byte, and is decided so:

- `share_byte(a, b)`: both have a byte and `a.lo < b.hi && b.lo < a.hi`.
  An empty range shares a byte with none, itself included.
- `within(a, b)`: `a` has a byte and `b.lo <= a.lo && a.hi <= b.hi`. An
  empty range is within none; a range is within no empty range.
- `properly_inside(a, b)`: `within(a, b) && a != b`.
- `cross(a, b)`: `share_byte(a, b) && !within(a, b) && !within(b, a)`.

So for any two ranges exactly one holds: they share no byte, one is
within the other, or they cross. Two ranges that touch at one end
(`a.hi == b.lo`) share no byte.

of the shards, `rule_conflict` of the rules. A refusal of a site may
have a `subject` or none ("the least subject of the site, if any"), and
`other` is optional for its three causes (`contested` by a `keep` at
the site itself has none). Not checked: that `other` is present when
the conflict was with another range, which needs the claims.

Paths are under `sections.set`. Rows 2, 4, 9, the `changed` emptiness and
the refusal `hi` of row 11, 12, 13, 16, 17, 18 and the second rule of 19
are corrections the spec now states (§2.1, §6, §6.1): each holds of every
set reduce makes, and without them two values could mean one set, or a
set made by hand could say something false (an entry `in_force` that
§6.2 would exempt from comparison). The rule: whatever the file alone
can decide, the reader checks; "not checked by the format" is only what
needs the plan, the request, the shards or another object.

The crossing checks are `O((E + C) log C)`: the edits of a file, in
index order, against a stack of the open (containing) edits; the copies
through two segment trees, by start and by end. They report the least
index that breaks a rule, as a check against every earlier edit would.

## 5. The transform run record (`RUNT`)

Section `run`, id 1. No invariants beyond the encodings. Not
deterministic; the type derives `Eq` and `Hash` for tests, which claim
nothing about two runs. `formats::transform_run_names` decodes the whole
file as `TransformRun::from_bytes` does and returns `(plan, round,
started_unix_ns)`; the store calls it (`exec.md` §2.2). The store's
`publish_object` validates `TRFM`, `EDTS`, `OVLY` and `RSLT` in full the
same way, through `formats::content_id` over the bytes.

## 6. JSON forms (`model.md` §10)

Members are named and ordered as the fields of the spec, `macro` for
`macro_site`; enumerations by their names in the spec, `snake_case`
(`accepted`, `no_observer`, `site_refused`, `not_compiled`,
`denotes_other`, `verified_with_residue`, `load`, …).

- `EditSet`: `{scheme, plan, round, transform, basis, state, files,
  subjects, rules, edits, groups, changed, kept, unresolved, refusals,
  reports, failures, unparsed, counters}`; `files`, `subjects`, `rules`
  and places as in WP-060; `groups` an array of arrays of numbers.
  - `Edit`: `{file, lo, hi, pieces, subjects, tiers, macro, notes,
    observers, votes, first}`.
  - `Exempt`: `{key, place, reason, in_force, observers, first}`.
  - `Refusal`: `{cause, file, lo, hi, reason, subject, macro, other,
    observers, first}`; absent fields `null`.
  - `Reported`: `{report, observers, first}`; `Failed`: `{failure,
    observers, first}`, the inner records as in WP-060.
  - `Counter`: `{name, value}`.
- `Overlay`: `{edits, files: [{path, pre: {size, content}, post: {size,
  content}}], spellings: [{file, lo, hi, key}]}`.
- `TransformResult`: `{scheme, plan, round, transform, edits, declared,
  overlay, state, partial, allow_unparsed, verdict, tally, agreement,
  unused, spellings, residue, exempt}`; `tally` an object of its eleven
  fields in order; `agreement` `[{rule, observer, direct}]`; `spellings`
  `{obligations, passed, failed: [{obligation, why, observers, first,
  found, name}]}`; `residue` `[{category, file, lo, hi, line, column}]`.
- `TransformRun`: `{tool_slip, tool_kiln, plan, round, transform, edits,
  declared, overlay, result, started_unix_ns, wall_ns, steps: [{name,
  wall_ns, cpu_ns, peak_rss, run}]}`.

## 7. Paths

`transform::is_canonical` refuses a NUL byte (no file has one), for
every user: the request's ownership entries too. Where the spec says
"real path" of a file the reader requires `transform::is_file_path`,
canonical and not `/`: the edit set's `files`, the overlay's `files`, a
residue's `file`. `/` stays canonical, a valid ownership entry, but names
no file. A non-canonical path would name a file the rest of the pipeline
cannot match by bytes, so it is refused rather than normalised. A
`Failure`'s source place (`SourcePlace.file`) is not a real path of the
build and is not checked, as in WP-060.

## 8. Follow-up

The shard's `edits.files` (WP-060) does not check canonical paths, so an
edit set reduced from such a shard would be refused by its own reader:
reduce must refuse a shard whose path is not canonical (or WP-060's
reader should, a later package's choice). It is a line of
`docs/wp/WP-062.md`'s scope.
