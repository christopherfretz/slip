# WP-127 — rename: what a using-declaration names; dependent names bound by an instantiation

`crates/slip_refactor/src/rename/followers.rs` and `dependent.rs`, the
call in `rename/mod.rs`, one `allow` dropped in `claims.rs`, the docs of
`crates/slip_refactor/src/lib.rs`, `spec/edits.md` §9.2, §9.4 and §9.7,
end-to-end tests in `crates/slip_refactor/tests/rename.rs` (the two
known-mismatch tests of WP-119 replaced), and new directories under
`crates/slip_refactor/tests/rename/` (`s9_2-using-named-set-*`,
`s9_4-dependent-*-bound-by-instantiation`,
`s9_4-dependent-member-two-instantiations`). Kiln sites are at Slip's
pin.

## What Kiln records at the pin

Read with a probe over the parsed unit (`Ast::exprs`, `lookup_local`,
`using_qualifier`, `using_shadows`, `decls.hidden_shadow`):

| Source | Kiln records |
|---|---|
| `template <class T> void call(T t) { t.f(); }` instantiated with `n::S<int>` | a `MemberExpr` whose member is `n::S<int>::f()` and whose location is the byte of the dependent entry's name token `f` |
| `T::f()` in the same pattern | a `DeclRefExpr` of `S::f` at the dependent name's token |
| `&T::f` in a variable's initialiser in the pattern | a `DeclRefExpr` at the dependent name's token |
| `struct D : B { void f() override; using B::f; };` (member first) | no shadow of `B::f()`; `lookup_local(B, f)` gives `B::f()` and the others |
| `struct D : B { using B::f; void f() override; };` (using first) | a shadow of `B::f()` with `hidden_shadow` = `D::f()`; the digest writes no unit for it (WP-119 item 6) |
| `using Base<T>::f;` in a class template (dependent base) | an `UnresolvedUsingValue`: no qualifier record, no shadow |
| `struct B : A {}; struct D : B { using B::f; };` | `B` declares no `f`; the shadow is of `A::f(int)` |

## What was built

1. **Item 1: a using-declaration read by its named set.**
   `followers::named_set` starts from the shadows and, for a
   using-declaration at class scope whose qualifier names a record N,
   looks `name` up in N (`member_lookup`: what N declares, a shadow
   taken to its target, a hidden shadow left out, using kinds left
   out; when N declares none, the one set its bases give, bases giving
   different sets unknown; depth capped at 64). A shadow whose target is
   not in the set makes it unknown. Each declaration found with no
   shadow is hidden: by the member of the class that overrides it
   (`cold.overrides`), recorded as its hider, or, when none does, by the
   members of the class named like the declarator that may correspond
   to it (`may_correspond`, below), all of which become possible
   hiders. `of_using` is the introduced declarations plus, for each
   hidden one with possible hiders, it and its hiders, so a mix is
   `mixed_follower` at the using-declaration. An unknown set is
   `unsupported` when relevant (a subject named, hiding, or a member of
   the class named like it), and its `of` holds every member of the
   class named like it besides the shadows' targets (`unknown_of`, in
   `using_declaration` and `instantiated_unfollowed_using`), so that the
   follower is selected or mixed whenever the rename touches it. A
   dependent base is WP-120's rule, unchanged.
2. **Item 2, refusing form.** `dependent::bound` makes one pass over the
   expression arena and keeps, for each dependent name's token, the
   declarations named like the old name that a `DeclRefExpr` or
   `MemberExpr` at that token refers to (`strip_shadow` first).
   `dependent::claim` takes them to their origin and subject: none is
   `unresolved` as before; some is `refuse(mixed_instances)` with those
   subjects at the dependent name. The refusal names the site (the
   pattern's name token), the subjects and the observer.
3. **Item 3.** `wp119_known_mismatch_f1_dependent_call` and
   `wp119_known_mismatch_f2_member_first_using` are replaced by the
   `wp127_*` tests below: F1 is now refused, F2 rewritten and verified.

## Decisions

- **The reason is `mixed_instances`.** No `Reason` says "an
  instantiation binds this dependent name"; the nearest is
  `mixed_instances` (one site, several instances). Adding one means
  editing `slip_model`, outside the package: proposed below.
- **The specialisation is not in the refusal.** A `Refusal` has no
  field for it and notes do not reach refusals; the refusal names the
  pattern's site and the observer. Naming the specialisation needs
  either a field or Kiln's stage 4 (per-instantiation entries).
- **Non-virtual hiding: correspondence, exact where it can be told**
  (review F2). Without a recorded hider, a member is a possible hider
  of a named declaration when it may correspond to it
  ([namespace.udecl]/14). `hiding_signature` tells it exactly for a
  non-static `CXXMethod` whose function type is not dependent: the
  canonical parameter types, variadic-ness, cv- and ref-qualifier of
  its prototype. Between two such, differing signatures are no hider;
  any other member (a template, a static or dependent one, a non-function)
  counts as one. So the answer no longer depends on member order where
  the comparison is exact: `struct D : A, B { void f(int) override;
  void f(); using B::f; }` from `n::A::f` is accepted and verifies in
  both orders (member first it was `MixedFollower`). Where it is not
  exact it over-refuses, and may then still differ by order.
- **An unknown set is refused, in both orders** (review F1). Its
  follower's `of` was the shadows only; with a member-first hider that
  is a subject (no shadow for what it hides) nothing in `of` was
  selected, the `unsupported` flag never applied, and
  `struct D : C { void f(); using C::f; }` over a dominance hierarchy
  was accepted and did not verify. The class's members named like it
  now join `of`: renamed all, the follower is selected and
  `unsupported`; renamed in part, `mixed_follower`. The same held, and
  is fixed alike, in `instantiated_unfollowed_using` (an instantiation
  whose dependent base is that hierarchy; refused in both orders now).
- **Two observers cannot disagree on a class's named set.** The set is
  read from the nominated class's members and bases and the
  using-declaration's own class, all in class definitions, which are
  one in every observer that sees them (ODR); a using-declaration is
  only read in an observer that sees its class. What can differ is
  whether an observer instantiates a class template; the observer that
  does refuses, and the refusal holds over the other
  (`wp127_named_set_two_observers`, both orders, both shapes).
- **Every dependent entry, not the three forms only.** The rule is read
  for any dependent name an instantiation binds, so `n::v<T>` (a
  variable template-id Kiln records as dependent) is refused when
  instantiated with the subject, where it was `unresolved` (accepted
  with a residue whose post-image does not compile). Not instantiated it
  stays `unresolved` (`known-dependent-variable-template-id`). This is
  safe but not the ideal: `n::v` there is a qualified, non-dependent
  template name (only the template-id is dependent) and the right claim
  is `replace`, and the reason `mixed_instances` is a misnomer (one
  instance, one subject). Why the rename cannot tell: Kiln records
  `n::v<T>` as one dependent entry of `written::dependent_names`, with
  no referent (K4, `spec/landed/edits/WP-067.md`), and no written
  reference to the variable template `n::v` at the name token, though
  it resolved the template name at the definition. See "For Kiln" and
  "For WP-139".
- **Dominance is not built** (review F3, a limit). `member_lookup`
  takes the one set every base gives, and bases that give different
  sets make it unknown; lookup that a virtual base decides by dominance
  ([class.member.lookup]/6) is therefore unknown and refused:
  `struct A { void f(); }; struct B1 : virtual A { void f(); }; struct
  B2 : virtual A {}; struct C : B1, B2 {}; struct D : C { using C::f;
  void f(int); };`, renaming `n::B1::f`, is refused (`MixedFollower`,
  in both orders; the right edit is `using C::g;`). It fails closed;
  `wp127_dominance_limit_refused` records it.
- **The location join over-approximates.** An expression Kiln built and
  dropped (an overload candidate) at the dependent name's token refuses
  more. One that binds the name and does not carry the token's
  location would be missed: the run is accepted and verification
  reports it, as before this package.

## The offering form (a proposal; not built)

The ruling on it is the supervisor's.

- **What it reads.** The same join as the refusing form, per observer:
  for each dependent name, the declarations every instantiation the
  observer made binds it to, and the set of specialisations (from
  `instantiated_from` of the enclosing function or variable the
  expression lies in). Reduce gathers them across observers.
- **When it offers the edit.** When, across every observer, the name is
  bound by at least one instantiation, and every instantiation binds it
  to a selected subject (each its origin taken, as a written reference
  is). The claim is then `replace` at the name token, built as the
  rename builds any replacement. Bound to a subject in one
  instantiation and to a non-subject in another (any observer) is
  `mixed_instances`, refused. Bound by none is `unresolved`, as now.
- **What the report says about instantiations it did not see.** The
  edit is stated as "offered on the instantiations the observers made":
  the report lists each pattern edited this way, with the
  specialisations seen and their observers, and says that a
  specialisation made only by a translation unit outside the run (a
  dependent project, a header-only user) is not checked. A flag
  (`--dependent=refuse`) keeps the refusing form for runs whose
  observers are not the whole program.
- **What verification checks.** The post-image is parsed in every
  observer; each specialisation the pre-image made must be made again
  and bind the name to the renamed entity (the digest's per-entity
  comparison already shows a call that resolves elsewhere: an
  instantiation that binds it to a different entity, or fails to
  compile, fails the run). Nothing checks specialisations no observer
  makes.
- **What it costs.** The arena pass of the refusing form, plus per
  matching expression a walk up to its enclosing declaration to name
  the specialisation (once per declaration, memoised), and a set of
  specialisations per dependent name carried in the claim to reduce.
  Memory is one entry per (name, specialisation) bound to a subject.

**The question to be ruled:** may Slip edit a pattern's dependent name
on the evidence of the instantiations the run's observers made, saying
in the report that others are unchecked, or must it refuse unless
every possible instantiation is known (which no run can show)?

## For Kiln

- **Stage 4 (K-e, WP-1933).** Per-instantiation entries for a
  dependent name would replace the location join (which rests on an
  instantiation's expressions carrying the pattern's token location,
  which `spec/ast.md` does not promise) and name the specialisation.
- **Hidden shadows in both orders.** With the hider declared before
  the using-declaration Kiln makes no shadow; after, it makes one
  marked `hidden_shadow`. One recorded shape for both (a hidden shadow
  in both orders, naming its hider) would let the rename read the
  named set from the shadows alone and drop `member_lookup`.
- **The non-virtual hider.** `hidden_shadow` names the hider when the
  shadow exists; with no shadow, nothing names which member hides a
  base's non-virtual `f`, so every member named like it is taken.

- **A using-declaration through a virtual-base lattice is exponential
  in Kiln's parse** (review F4). The lattice, `n` levels, each level
  two classes inheriting virtually from both of the level below, and a
  using-declaration naming `f` from the top:

  ```cpp
  namespace n {
  struct L0a { void f(); }; struct L0b : virtual L0a {};
  // for k = 1..n, p = k - 1:
  struct Lka : virtual Lpa, virtual Lpb {}; struct Lkb : virtual Lpa, virtual Lpb {};
  struct D : Lna { void f(int); using Lna::f; };
  }
  void h(n::D& d) { d.f(1); }
  ```

  At `n = 10`, debug build, one parse of the unit through the tests'
  `Tree::parse` (the code path of `slip parse`), one test thread:
  **8.90 s** with `ParseOptions::default()`; **8.60 s** parse and
  digest together (`digest_units`, 30 units); with the written tables
  and the preprocessing record 9.13 s, and 8.99 s with the key map
  (`map::with_input`) besides. Without the using-declaration (`struct D
  : L10a { void f(int); };`) the parse takes **18 ms** and parse with
  digest **21 ms**. So the time is in Kiln's parse of the
  using-declaration (its lookup of `f` through the lattice, every path
  walked), not in the digest or the rename. The reviewer's whole
  end-to-end runs (several parses) took 1.4 s at depth 8 and 26 s at
  depth 10, over 8 minutes at depth 12, also when renaming an
  unrelated name. `member_lookup` is also unmemoised on such a
  lattice (2^(n+1) calls), negligible beside the parse at the depths
  Kiln parses; a visited set for virtual bases would make it linear.
- **A dependent template-id's template name** (review F6). In
  `template <class T> int g() { return n::v<T>; }`, Kiln records
  `n::v<T>` as a dependent entry with no referent and no written
  reference to the variable template `n::v` at the name token. A
  written reference to the template the qualified, non-dependent
  template name resolves to at the definition would let the rename
  claim `replace` there (`known-dependent-variable-template-id`,
  `s9_3-variable-template-partial-specialisations`).

## For WP-139

- The refusal of a dependent name an instantiation binds should name
  its specialisation, and its reason is `mixed_instances` for want of a
  fitting one (a misnomer for one instance and one subject, F6).
