# WP-120 — rename: virtual families and using-declarations in templates; the unhide idiom

`crates/slip_refactor/src/rename/families.rs`, `followers.rs` and
`spec_members.rs`, one guard in `target.rs` (outside the package's list
of files: see "Disagreements"), `spec/edits.md` §9.1, §9.2 and §9.5,
an end-to-end harness and seven end-to-end tests in
`crates/slip_refactor/tests/rename.rs`, and 21 directories under
`crates/slip_refactor/tests/rename/` (`s9_2-pattern-*`, `s9_2-unhide-*`,
`s9_2-using-beside-another-member`,
`s9_2-virtual-local-class-in-variable-template`,
`-in-member-of-class-template`). Five existing directories were
re-blessed (their flags dropped, their followers added). Kiln sites are
at Slip's pin.

## What Kiln records at the pin

Read with a probe over the parsed unit (`Ast::cold.overrides` read on
`Ast::first`, `instantiated_from`, `templ_link`, `using_shadows`,
`using_target`, `decls.hidden_shadow`):

| Source | Kiln records |
|---|---|
| (a) `template <class T> struct B { virtual void f(); }; struct D : B<int> { void f() override; };` | `D::f` overrides `[B<int>::f]`, the member of the instantiated class (`instantiated_from` the pattern's `B<T>::f`, link `MemberOfSpecialization`); `written::origin` takes it to `B<T>::f`. The pattern's `B<T>::f` overrides nothing and is virtual |
| (b) `template <class T> struct E : Base { void f() override; };` | the pattern's `E<T>::f` overrides `[Base::f]` whether or not `E` is instantiated; `E<int>::f` overrides `[Base::f]` too |
| (c) `template <class T> struct F : Base { using Base::f; };` | the pattern's using-declaration has its shadow of `Base::f`. `F<int>`'s using-declaration is `instantiated_from` the pattern's (no `templ_link`); **its shadow is linked to nothing**, so its key holds its own plain name and it needs a rule of its own |
| `template <class T> struct G : T { void f() override; };` | the pattern records no override. `G<B>::f` (instantiated) overrides `[B::f]`, and is `instantiated_from` `G<T>::f` |
| `struct D : B { using B::f; void f() override; };` | a shadow for every `B::f`, the one for the hidden `B::f()` with `hidden_shadow` = `D::f()`. With `void f() override;` declared **before** `using B::f;`, no shadow for `B::f()` at all |
| the idiom in a class template `D<T>` | `hidden_shadow` in the pattern and in the instantiation |
| a local class in a function template, a generic lambda, a variable template's initialiser, a member function of a class template | each instantiated local class's member is `instantiated_from` the pattern's member (`MemberOfSpecialization`), with a key of its own (its parent chain holds the instantiated function or variable) |

## What was built

1. **Item 1: the pattern refusals lifted.** `families::candidate` adds
   `written::origin(d)` and no longer flags a candidate in a pattern;
   `followers` no longer flags a using-declaration in one. `in_pattern`
   is replaced by `families::in_class_pattern` (a class template or a
   partial specialisation encloses it before any function).
   `spec_members` now runs over every subject in a class pattern
   (candidates and using-declarations included, not seeds alone), so
   the members of instantiated specialisations become followers by
   WP-073's rule and carry its `unsupported` until WP-119. The
   using-declaration of an instantiated class follows the pattern's,
   and `followers::instantiated_using` makes its shadows followers of
   their targets. `spec_members::unlinked_member` skips using-shadows
   (never linked, never specialised: without this every pattern subject
   was flagged as soon as an instantiated using-declaration existed).
2. **Item 2.** A virtual seed in a pattern is not flagged (it was by
   `candidate`'s pattern test, now gone); §9.5 says so.
3. **Item 3: the unhide idiom.** `followers::shadows_named` records
   `hidden` per shadow (`hidden_shadow`); `introduced` gives the
   using-declaration's `of` without the hidden targets unless every one
   is hidden; `shadow_followers` makes a hidden shadow follow its three
   parties (fix round, decision 6). `target::classify` makes a
   using-declaration in the target's scope no seed (§9.1).
4. **Item 4.** A local class is in no class pattern (`in_class_pattern`
   stops at a function), so its members have no followers and no flag,
   whatever encloses the function.

## Decisions

1. **The idiom (item 3), the rule.** For each class, from what each
   observer records: a shadow that Kiln marks hidden is not introduced
   ([namespace.udecl]/14) and leaves the using-declaration's `of`; the
   hidden shadow follows its target, the using-declaration and its
   hider (decision 6). Reduce decides it with §5.2 unchanged: the
   using-declaration is selected iff every non-hidden target is; a
   hidden shadow is `mixed_follower` iff its three parties are not all
   selected or all unselected. A shadow hidden in `D` says nothing about
   `E : B { using B::f; }`, whose shadow is not hidden, keeps `B::f()`
   in `E`'s `of`, and refuses (`mixed_follower`).
2. **Why the hidden shadow keeps `mixed_follower`.** The kept
   using-declaration is right in C++ (no selected entity is reached
   through it), but the digest writes every using-shadow, the hidden
   one included, as a unit (`spec/digest.md` §2.1). After `B::f()` →
   `g`, the kept `using B::f;` no longer makes a shadow of `g()`, and
   the post-image shows the unit removed and `n::D` changed (checked
   under the digest before deciding). So the rule cannot show the kept
   declaration verifies, and the refusal stays (For the digest, below).
   Inserting `using B::g;` would verify but is an insertion of text that
   the transform API's rule (structural edits only) and the package do
   not provide; not done.
3. **Item 4.** Not a pattern: the pair under the digest
   (`wp120_local_classes_of_templates_end_to_end`) renames a local class
   of a variable template's initialiser, of a function template, and of
   a member function of a class template, each instantiated twice, with
   the pattern's candidate alone, and verifies with no WP-119
   simulation; the local class's member left behind is a difference.
   The reason: the instantiated member's key has the instantiated
   function's or variable's key as parent, which maps with the subject
   (`spec/digest.md` §3.4), and no declaration outside the pattern can
   name it. `s9_2-virtual-local-class-in-function-template`, refused
   before, is now accepted.
4. **The dependent base.** Instantiated in the observer: the
   instantiation's link, taken to its origin, links the pattern member
   (`s9_2-virtual-dependent-base`). Instantiated nowhere: no link, no
   subject, the name is `keep` (`s9_2-pattern-dependent-base-not-instantiated`),
   and §9.5 states it as what the rename does not see, beside §8.4's
   `kept` row. One observer instantiating and one not: `contested`
   (`wp120_dependent_base_over_two_observers_is_contested_simulated`).
5. **Unnamed-tag followers in a pattern** were never flagged in the
   code (only the spec said so); nothing changes for them.
6. **Fix round: a hidden shadow has three parties** (review F1, F2;
   the coordinator's ruling). Its target, its using-declaration and its
   hider (the member `hidden_shadow` names), each taken to its origin
   and its key id, subject or not; a party with no key makes the shadow
   `unsupported`. The shadow is a follower whatever its target, and a
   using-declaration is looked at when a subject hides what it names as
   well as when it names a subject. While the digest writes hidden
   shadows, all three renamed or none; any mix refuses. What it fixes:
   - F1: `struct A { virtual void f(); }; struct B : A { void f()
     override; void f(int); }; struct D : B { using B::f; void f(int);
     };`, `n::A::f` to `g`, was accepted (`using B::g;`) and the shadow
     of `B::f(int)` vanished; now `mixed_follower`
     (`s9_2-unhide-hidden-target-not-a-subject`, `-static`,
     `-member-template`, `wp120_hidden_shadow_three_parties_end_to_end`).
   - F2: `struct B { void f(); void f(int); }; struct D : B { using
     B::f; void f(); };`, `n::D::f` or `n::B::f` to `g`, was accepted and
     made `B::f()` visible in `D` (a real change of the program); now
     `mixed_follower` both ways (`s9_2-unhide-non-virtual-from-the-derived-class`,
     `-from-the-base`, the same end-to-end test).
   The three forms pinned before keep their results (the idiom from the
   base verifies; from the derived class refuses; the second derived
   class refuses: `wp120_unhide_idiom_end_to_end`). I found no shape
   where "all three or none" refuses what verifies today, or accepts
   what does not: of the eight combinations, the two uniform ones are
   the only ones in which the using-declarator still makes the shadow
   and the hider still hides it. Not covered by a shape: a hider that is
   a subject of another kind (refused by its own flag first).
   Inheriting constructors beside a hidden shadow
   (`s9_2-unhide-beside-inheriting-constructors`): another name, no
   follower, no change. A using-declaration naming a class and a
   function of one name (`s9_2-using-names-a-type-and-functions`): both
   in its `of`; the class is a seed of another kind, so the run is
   refused (`unsupported`) before the mix matters.
7. **Fix round, question 3: an instantiated dependent
   using-declaration.** `struct X { void f(int); }; template <class U>
   struct Base : X { void f(); }; template <class T> struct F : Base<T>
   { using Base<T>::f; };` with `F<int>` used, `n::Base::f` to `g`. The
   premise that its shadows are partly selected does not hold: in
   `Base<int>`, `f()` hides `X::f(int)`, so `F<int>`'s using-declaration
   introduces `Base<int>::f()` alone (a use of `x.f(1)` does not
   compile). The wrong edit is elsewhere: the pattern's name is claimed
   `unresolved` and kept, and after the rename `using Base<T>::f;` names
   `X::f(int)`. `followers::instantiated_using` was never reached (the
   pattern's using-declaration is no subject, so `spec_members::resolve`
   gives nothing). Built: `followers::instantiated_unfollowed_using`
   makes the instantiated using-declaration a follower of what it
   introduces **and** of the pattern's using-declaration, so with a
   subject selected it is `mixed_follower`, with or without WP-073's
   flag (`s9_2-pattern-dependent-using-instantiated`,
   `wp120_dependent_using_partly_selected_end_to_end`). Limit:
   `spec_members` runs only when some subject is in a class pattern, so
   `template <class T> struct F : T { using T::f; };` with `F<B>` and a
   plain seed `B::f` is not looked at here: its name is `unresolved`
   (WP-073 part A's gap) and verification sees the instantiation.

## What the `target.rs` change no longer blocks

Before this package a using-declaration in the target's scope made the
run `unsupported` (a seed of another kind), which incidentally refused
`namespace a { void f(long); } namespace m { using a::f; void f(int); }
template <class T> void t(T x) { m::f(x); }`, `m::f` to `g` (review
F3). Now the run is accepted: the dependent call's name is claimed
`unresolved` (residue only), and after the rename `t<int>` calls
`a::f(long)`. Verification catches it (`t` changed, also when `t` is
instantiated nowhere). The same happens on `main` with no
using-declaration at all (`struct B { void f(long); }; struct D : B {
void f(int); void f(long); };` with `template <class T> void t(n::D& d,
T x) { d.f(x); }`), so it is the open gap of `docs/wp/WP-073.md` part A
(dependent names), not this package's; no code change.

## For Kiln

- **Hidden shadows depend on declaration order.** `struct D : B { using
  B::f; void f() override; };` makes a shadow of `B::f()` marked
  hidden; `struct D : B { void f() override; using B::f; };` makes
  none. The two classes are the same ([namespace.udecl]/14). Either
  form would do for Slip if it were the same for both; making no shadow
  for a hidden declaration would also close the digest item below.
- **An instantiated using-declaration's shadows are not linked to the
  pattern's** (`instantiated_from` is recorded on the using-declaration
  only). Worked around (`instantiated_using`); not a defect, but a link
  would let the shadows map through the pattern as members do.

## For the digest

Owned by the coordinator's item in `docs/wp/WP-119.md` (hidden shadows
left out of the digest).

- **A hidden shadow is written as a unit.** With it, renaming a virtual
  family that a using-declaration unhides beside (the idiom seeded at
  `D::f`) cannot verify with the using-declaration kept, which is the
  right C++ edit. Smallest source: `struct B { virtual void f(); void
  f(int); }; struct D : B { using B::f; void f() override; };`, rename
  `n::D::f` to `g`.
- **What the rule relaxes to** once hidden shadows are left out: a
  hidden shadow is then no unit, so its using-declaration no longer
  matters; what still matters is that the hider still hides the target
  (or the hidden declaration becomes visible, review F2). The rule
  becomes: target and hider renamed together, or neither; the hidden
  shadow's `of` is `{target, hider}`, without the using-declaration
  (`followers::shadow_followers`, one party dropped). The idiom from
  the derived class then renames and verifies; F1's source is then
  accepted (`using B::g;`, target and hider not renamed); F2 stays
  refused.
