# WP-063 — slip_apply: the overlay, the patch and the journaled write

Implemented by the crate `slip_apply` (`crates/slip_apply/src/`:
`splice.rs`, `build.rs`, `compose.rs`, `patch.rs`, `write.rs`,
`journal.rs`, `fs.rs`). This file fixes what `edits.md` §7 leaves open
and records where the package departs from §7.4; §7 is amended to point
here. Tests: `crates/slip_apply/tests/{splice,compose,patch,write}.rs`.

## 1. `splice`, `plan`, `build`

**`splice`.** An edit is `(lo, hi, text)` with `lo <= hi <= len`. The
list is ascending and disjoint: each `lo` is at or after the `hi` of the
one before, and `(lo, hi)` is strictly greater than the one before. An
empty range is an insertion; an insertion may sit at the `lo` of the
next replacement (it is written first), but two insertions at one offset
have no order and are `Invalid`. A range past the end is `Invalid`.

**The layout.** Edits are numbered as in the set (sorted by `(file, lo,
hi)`). Each file has a root. A sweep over each file's edits and copied
ranges in pre-order (`lo` ascending, `hi` descending; an edit before a
copied range of the same bounds) with a stack of open edits gives every
edit its parent (the innermost edit, or the root, that it is properly
inside) and every copied range its container (the innermost edit
strictly containing it, or the root). The edits a copy **carries** are
the children of its container whose `lo` lies in the copied range; by
§6.1 (no edit crosses a copied range) they lie wholly inside it. An edit
whose range is exactly the copied range is the container's child only if
it is properly inside the container, and then its range equals the
copied range, so it is not carried: §7.1's "an edit of exactly the
copied range is not applied to the copy".

**Draws on.** Edit `e` draws on its children (nesting) and on the edits
its copies carry. §5.4's cycle is a cycle of this graph. It is found by
an iterative depth-first search (an explicit stack; no recursion), whose
post-order is the build order. The first edit found on a cycle is named:
`sections.set.edits[<i>]: the edit draws on itself, directly or through
a chain of copies`.

**Effective** (§5.5): the outermost edits, then, to a fixpoint, every
edit carried by a copy piece of an effective edit. The first edit that
is not: `sections.set.edits[<i>]: the edit is not effective: it is
inside another edit and no copy carries it`. Checked after the cycle.

**Lengths.** In build order, saturating at `u64::MAX`: a literal or
spelled piece its byte length; a copy its range length, less the ranges
of the edits it carries, plus their expansions' lengths. A post-image is
its file's size (the `FileRef`'s, not the bytes: `plan` reads nothing)
less its outermost edits' ranges plus their expansions. One of more than
2^31 bytes is `TooLarge(path)`; exactly 2^31 is built. So a chain of
doubling copies is refused before anything is allocated.

**Order of checks.** `build` and `build_into`: `NotAccepted` for a set
not `accepted`; `set.validate()` (`Invalid` with its message); the set
id is the content id of `set.to_bytes()`, else `Invalid: the edit set id
is not the content id of the edit set` (§7.4 does not say `build` checks
the id it is given; it does, so the overlay's `edits` is never wrong);
cycles; effectiveness; lengths (`TooLarge`); then the files.

## 2. Reading, the sink, the obligations

The overlay files (those with an edit) are taken in path order. For
each, the files its post-image needs are its own and those its needed
edits' copies copy from, transitively through copies (a copy carries
edits whose copies may name a third file). They are read in path order
and each is checked against its `FileRef` (size, then content digest)
as it is read: `StaleFile(path)` for a file that cannot be read or does
not match. A file copied from by several post-images is read again for
each: `build` holds one post-image's inputs at a time (§7.4), not a
cache. Nothing else is read.

**The sink.** `build_into` calls the sink once per overlay file, in path
order, after that file's post-image is built. A later file may still
fail (`StaleFile`, or the sink's own error, which is `Io(path,
message)`): earlier calls have then happened, and no overlay is
returned. A sink that publishes blobs loses nothing by this (blobs are
addressed by content and an unreferenced one is garbage); §7.1 step 1's
"nothing is published" holds for the overlay, not for blobs. `build` is
`build_into` with a sink that collects.

**Expansions.** Each needed edit's expansion is built once per
post-image, after those it draws on, and released after its last use
(a use count per edit), so a long chain holds only the live ones.

**Obligations.** An expansion carries its landings: for each spelled
piece, `(lo, hi, key)` in its own offsets, and those of the expansions
it copies, shifted. The landings of the outermost edits, shifted to the
post-image's offsets, are the file's obligations. They are sorted by
`(file, lo, hi, key)` and `build` asserts them strictly ascending (two
landings occupy disjoint bytes unless a spelled text is empty, which
`EditSet::validate` refuses). A spelled piece whose edit is carried to
three places gives three obligations.

## 3. The patch

**Lines.** A line is the bytes up to and including `\n`; a last line
without one is a line. Lines are compared as bytes, so a `\r` before
`\n` is part of the line and a line with `\n` differs from the same text
without it.

**The diff.** Any common subsequence of lines gives a correct patch;
which one only changes its size. Taken: the common prefix and suffix;
then, recursively (an explicit stack), the lines unique on both sides as
anchors, their longest run ascending on both sides (patience); between
anchors where none are unique, Myers' algorithm, bounded: a region whose
search would pass `MYERS_WORK` = 2^26 cells of work (`d * (n + m)`), or
`MYERS_CELLS` = 2^22 cells of memory (32 MiB of `isize`: the frontier of
`2 * dmax + 3` cells, `dmax` the greatest distance the bounds allow, and
the rows kept for the trace back, `(d + 1)^2` cells by distance `d`),
is written as removed and added whole. The review measured 514 MiB for
4096 lines against 4096 other lines when only the work was bounded. A
bound with the fallback the code already had was chosen over the
linear-space variant (Myers' middle snake): the result is the same kind
(a correct patch, larger only for a region that hard), the code stays
the one loop the spec describes, and the fallback is already tested. A
unit test (`patch.rs`, `myers_memory_is_bounded`) counts the cells held
at once, the review's case included. `CONTEXT` = 3. Two hunks are one when the
unchanged lines between them are at most `2 * CONTEXT` (their context
touches or overlaps); 7 lines make two hunks.

**Hunk headers** in GNU form: `@@ -<a> +<b> @@` where a range of one
line is its 1-based start, of `n > 1` lines `<start>,<n>`, of no line
`<start>,0` with `start` the line before which nothing is (0 at the top).

**Names.** `<path>` is the overlay path; with `relative_to = Some(dir)`
the path less `dir/`, and with `Some("/")` the path less its leading
`/`. `relative_to` must itself be canonical (`Invalid` otherwise), and an
overlay file outside it is `Invalid` (§7.4 has no usage error; the CLI
maps it). The bytes are written as they are, except:

- a name containing a space is followed by a tab (`--- a b\t`): GNU
  `patch` ends an unquoted name at the first space or tab, `git apply`
  at a tab; both read a name ended by a tab. §7.2 is silent.
- a name containing a tab, `\r` or `\n`, starting with `"` (which
  both tools read as a C-quoted name), or starting or ending with a
  space (GNU `patch` 2.8 drops it and finds no file; found by the
  review) is `Invalid`: it cannot be written as its bytes. §7.2 is
  silent; amended.

Every name is checked before the first byte is written, so a refused
patch writes nothing. The pre-image is read and checked (`StaleFile`),
the post-image blob fetched and checked (`Io(path, "…does not hash…")`).

**Which `-p`.** §7.2 says `patch -p0`. That holds for names relative to
a directory (applied in that directory). For absolute names the test
applies with `-p1` in a directory standing for `/`: `patch -p0` with an
absolute name is refused by GNU `patch` unless allowed, and `git apply`
refuses absolute names. Both are tested.

**What the tools do.** Over 150 generated pre/post pairs each (CRLF and
LF mixed, missing final newline in either image, names with spaces),
relative with `-p0` and absolute with `-p1`, GNU `patch` and `git apply`
give the post-image byte for byte. A file with NUL bytes or invalid
UTF-8 is written the same way; both tools apply it (a traditional diff
has no binary marker). A file name that is not UTF-8 is written as its
bytes; the round trip cannot be run on a volume that refuses such names.

## 4. The journal

**Record** (§7.3 step 2): the encoding of `model.md` §2 with no
container: `overlay: digest`, `count`, then per file `path: bytes`,
`staged: bytes`, `pre.size: uv`, `pre.content: digest`, `post.size: uv`,
`post.content: digest`. Any byte after the record is `Malformed`.

**Reader** (`Journal::from_bytes`). The decoding, then these rules, each
over the whole list, in this order, messages verbatim:

1. not empty: `journal: files: a journal names no file`;
2. every path `transform::is_file_path`: `journal: files[<i>]: not a
   canonical absolute path of a file`;
3. strictly ascending by path: `journal: files[<i>]: files are not
   strictly ascending by path`;
4. every staged name is `staged_name(path, overlay)`: `journal:
   files[<i>]: the staged name is not the one of its path and overlay`;
5. `pre != post`: `journal: files[<i>]: pre and post are equal`.

Rule 4 matters: recovery removes and renames staged names, so a journal
cannot make it remove or rename anything but a name of the form
`<dir>/.<name>.slip-<16 hex digits>` beside a file the journal names.
`recover` takes the ownership the write was given and refuses
(`Refused::JournalNotOwned(path)`, the first such path) a journal naming
a path that ownership does not own, before any operation of the tree,
the blobs or the journal's removal: the journal is kept. So a journal
that names `/etc/passwd`, however it came to be in the store, changes
nothing (the review's forged-journal probe).

**Staged name.** `<dir>/.<file name>.slip-<first 16 hex digits of the
overlay id>`; `/x` gives `/.x.slip-…`. Names of this form are reserved
for Slip in an owned tree: step 1 refuses a write if anything (a file, a
link, a directory) has one (`StagedExists`), and `recover` removes a file
it finds at one, whosever it is (the review found that a file placed at
a staged name during a write whose undo is then interrupted is removed
by `recover`; that is the reservation). A staged name longer than the
file system allows fails the create of step 3, which is undone.

## 5. Writing the tree

### 5.1 Where §7.4 is departed from (all now in §7.3 and §7.4)

- `Refused` has five more cases:
  - `NotRegular(path)` (steps 1, 4, and before each rename): a symbolic
    link, a directory, a device, or a path reached through a linked
    directory;
  - `StagedExists(staged path)` (step 1): anything at the staged name;
  - `ReadOnly(path)` (steps 1, 4, before each rename): the owner's write
    bit is clear (`mode & 0o200 == 0`): a Perforce file not opened for
    edit, a file protected on purpose. Slip does not replace it;
  - `OwnerChanged(path)` (step 4): the staged file's owner or group is
    not the file's, so the rename would change them. A create by another
    user than the file's owner gives that user's uid; a create in a
    setgid directory gives the directory's group, so in a setgid
    directory whose group is not the file's the write is refused. A root
    `write` over a user's file is refused the same way (no `chown` is
    attempted);
  - `JournalNotOwned(path)` (`recover`, §4).
- At step 4 and before each rename, a staged file that is not a regular
  file of one link with the post-image's bytes (step 4) or with what step
  4 saw (before the rename) is `StaleFile(staged path)`.
- `WriteError::Invalid(message)`: the overlay fails `validate`,
  `overlay_id` is not its content id, or the ownership is not valid: no
  owned entry, an entry that is not canonical (`""`, which `covers`
  every path, `w`, `/w/`, `/w/../x`), or an entry both owned and
  readonly. `slip_model::transform::Ownership` has public fields and no
  validating constructor, so `write` and `recover` check it themselves
  (`check_ownership`), before any operation.
- `recover(ownership, tree, blobs, journal)`: the ownership the write
  was given (callers: WP-075 and the command packages).
- `Tree::create(path, mode, bytes)` has no `exclusive` parameter: every
  create is exclusive (`AlreadyExists` if anything has the name; nothing
  is followed or truncated). The non-exclusive path was unused and, in
  `DiskTree`, truncated and followed links.
- `Stat` has `uid`, `gid`, `dev`, `ino`, `size`, `mtime` and `ctime`
  (seconds, nanoseconds).
- `JournalStore::publish` is exclusive: `AlreadyExists` if a journal
  exists, changing nothing. `write` reads the journal first (an
  unfinished write is `Journal("the store has an unfinished write")`)
  and treats an `AlreadyExists` publish the same way, without removing
  the journal (it is another write's). A failure to read the journal is
  `Io` with `journal_left: false`.
- An overlay whose every entry has `post == pre` returns `Ok(0)` and
  performs no operation, not even the journal read (after the overlay
  and the ownership are validated).

### 5.2 The operations

For the `k` files whose `post` differs from `pre`, in path order (`F`
each file, `S` its staged name, `D` the distinct directories, sorted):

| Step | Operations |
|---|---|
| 0 | `journal.read` |
| 1 | per file: ownership (no operation), `stat F`, `stat S`, `read F` |
| 2 | per file: `read F` (checked against `pre` again), `blobs.put`; then `journal.publish` |
| 3 | per file: `blobs.get post` (checked), `create S` (exclusive, `F`'s mode, synced) |
| 4 | per file: ownership, `stat F`, `stat S`, `read S`, `read F` |
| 5 | per file: `stat F`, `stat S` (the re-check), `rename S → F`; per directory `sync_dir`; `journal.remove` |

For three files in two directories that is 47 operations.

The re-check before each rename compares, for the file and for its
staged file, what `stat` gives now with what step 4's `stat` gave:
regular, one link, owner write bit (the file), and then device, inode,
size, modification and change time with nanoseconds. A difference is
`StaleFile` naming the file or the staged file (`NotRegular`,
`HardLinked`, `ReadOnly` for those). The write is then rolled back
(`restore`, as for any failure of step 5): `Refused(r)` if the rollback
finished with nothing reported, else `Io` with `journal_left: true` (a
file saved in place has neither image and is reported and kept, with
the journal). §7.3 says what it catches and what it cannot.

`recover` (and the rollback of a failed step 5): ownership checked and
`journal.read` (absent: `Ok(None)`; malformed: `Journal`; a path not
owned: `JournalNotOwned`, nothing done); per file: `remove S`
(`NotFound` is fine), `stat F`; missing or not regular: reported; else
`read F`; `pre` image: left; `post` image: `blobs.get pre` (checked),
`create S` exclusive with `F`'s current mode, `rename S → F`: restored;
anything else: reported. Then `sync_dir` each directory, and
`journal.remove` if nothing was reported.

### 5.3 What an interruption at each point leaves

"Interrupted" is any of: the operation fails and does nothing; it takes
effect and then reports a failure; power is lost before it (it and all
later fail); power is lost after it.

- Steps 0 and 1: nothing was created. `Refused` or `Io` with
  `journal_left: false`.
- Step 2, before the journal is published: blobs only (content
  addressed, harmless). `journal_left: false`. A `publish` that fails
  with `AlreadyExists` is another write's journal: the unfinished-write
  refusal, nothing removed. Any other failure is followed by a `remove`
  (it may have published): `journal_left` is whether that remove failed.
- Steps 3 and 4: the journal and some staged files exist; no original
  was replaced. `write` undoes: removes the staged files it created
  (never a staged name whose exclusive create failed with
  `AlreadyExists`: that file is not ours), syncs the directories,
  removes the journal; `journal_left: false` if all of that succeeded.
  If the undo fails or power is lost, the journal is left; `recover`
  removes every staged file and finds every original `pre`: all left.
- Step 5, after some renames: some originals are post, the others pre,
  each whole (a rename is atomic). A failed rename, re-check or
  directory sync makes `write` run the recovery itself (journal still
  present): back to the pre-image, `journal_left: false` if it finished
  with nothing reported. On power loss the journal is left and `recover`
  restores the renamed files.
- The journal remove fails after every rename and sync: the tree is the
  post-image, `Io` with `journal_left: true` and no rollback; `recover`
  then returns it to the pre-image (§7.3: "an interrupted write returns
  to the pre-image"). This is the one case of a post-image with an `Io`
  error; if the remove took effect before failing, the tree is the
  post-image and no journal remains.
- `recover` interrupted anywhere: its effects are a subset of its own
  idempotent steps (a staged file it created is removed by the next
  run, a file it restored is found `pre` and left), so the next
  `recover` finishes, and the one after it finds no journal (`Ok(None)`,
  one operation).

The sweep tests every interruption of these four kinds at every one of
the 47 operations of `write` (188 runs) and at every operation
of `recover` from each of the 30 states with a journal that an
interrupted write leaves (1,776 runs), and checks after each: every
file is wholly pre or wholly post; a mix of files only while a journal
exists; after `recover`, the pre-image byte for byte, modes kept, no
staged file, no journal, nothing reported; a second `recover` does
nothing. The review's own sweeps of two faults (a failure, then a second
failure or power loss during the undo or rollback: 1,532 runs of
`write`, 74,880 of `recover`) passed.

### 5.4 What depends on the file system

Regardless of the file system: the order of operations; that no
original is opened for writing (originals are only renamed over); that
every file is at every moment one of its two images, given atomic
rename; that `write` removes and renames only names the journal holds;
the refusals.

Assumed of the file system and the stores (the in-memory model performs
operations in order and durably, so the tests cannot show these):

- `rename` within a directory is atomic (POSIX).
- `create` of `DiskTree` calls `sync_all`, so a staged file's bytes are
  durable before step 4; `sync_dir` (`fsync` of the directory) makes
  renames durable before the journal is removed. A file system that
  ignores directory `fsync`, or reorders a rename after the journal's
  removal across a crash, can leave a renamed file reverted with no
  journal: each file still whole, but the write half done with no
  record. Nothing in std can detect it.
- Timestamps advance on a write (the re-check before a rename).
- A file's device and inode numbers stay the same while it is not
  replaced. Not so on every volume: on this host's (a FUSE-backed host
  mount, `fakeowner`), renaming a directory gives every file under it a
  new inode number, reported on a later `lstat` (all 3,000 files of a
  probe changed after one rename of their directory, and none without
  it). Two consequences, both found by the gate: `DiskTree::create`
  keeps the write handle open while it reopens the name (an open file
  keeps its number), and the re-check before a rename can refuse
  (`StaleFile`) a write nobody touched when a directory on the path was
  renamed shortly before. The refusal rolls back like any other and the
  next write succeeds; `s7_3_disk_refusals`, whose setup renames
  directories, accepts exactly that. Comparing the inode is kept: on a
  file system with coarse timestamps it is the only field that tells a
  same-size replacement from the original.

### 5.5 Checks and races

- `..`, a relative path, `/`, a NUL: refused by `Overlay::validate`
  (`is_file_path`), before any operation.
- Not owned: lexical, over the path bytes, at steps 1 and 4, and over
  the journal's paths in `recover`.
- A symbolic link at the path, or a directory on the path that is a
  link: `DiskTree::stat` uses `symlink_metadata` (the last component is
  not followed) and compares `canonicalize(dir)` with `dir`; either is
  `NotRegular`, at steps 1 and 4 and just before each rename. A symbolic
  link elsewhere that names an overlay file is untouched (§7.3); after
  the write it names the post-image.
- Hard links: `links != 1` is `HardLinked`, steps 1, 4 and before each
  rename.
- `DiskTree::create`: `create_new` (exclusive, `O_EXCL`, which does not
  follow a link at the name), written and synced; then the name is
  opened again for reading and that handle's device and inode compared
  with the write handle's before the bits are set through it. The
  review's race (the staged name swapped for a link to a 0600 victim
  between the create and the reopen) made the victim 4755 in 3 of 739
  tries with the earlier code; now a swap makes `create` fail and the
  victim is never touched (`s7_3_disk_create_does_not_follow_a_swapped_name`
  runs the race 1,500 times and checks the victim after each). `fs.rs`
  reopens no other file by path to change it: `read` and `stat` name the
  path once and change nothing, and `sync_dir` opens a directory only to
  `fsync` it, which changes nothing wherever the name leads.
- The race, a recorded decision (operator, 2026-11-23): no dependency.
  std has no `openat`/`renameat` on an opened directory, so between a
  file's re-check and its rename (two `lstat`s and a `canonicalize`; the
  full check of step 4, which hashes two files per file, stays before
  the first rename) a concurrent writer of the tree can still change the
  file within the times' granularity, or replace a directory on the path
  by a symbolic link, which the rename follows (possibly out of the
  tree). `rustix` and `cap-std` would close the directory swap with safe
  directory-relative operations (it is not true that safe Rust cannot);
  the operator decided against the dependency because Slip is an
  interactive tool on a tree its user controls, and the window stays a
  documented limit (`spec/edits.md` §7.3 step 5). What holds regardless:
  every file is wholly its old or wholly its new bytes, and the journal
  rolls the write back. The realistic harm of the wider window was a
  lost update (an editor's or a build step's save overwritten by the
  rename); the re-check now refuses it (§5.2).
- `dir_writable` is the directory's permission bits granting a write to
  someone (`!readonly()`), not `access(2)`; a directory writable only by
  another user passes step 1 and fails the create of step 3, which is
  undone.

### 5.6 What is kept besides the bytes

The permission bits (`0o7777`, setuid, setgid and sticky included): the
staged file is written and synced, then opened again for reading (the
handle checked as in §5.5) and given the bits with `set_permissions`
(so the umask does not narrow them), synced, and the bits read back; if
the file system did not keep them, the create fails and the write is
undone. The second handle is read-only because the file system this was
built on (a host volume shared into a container) drops setuid when the
bits are set through a handle open for writing; the test with a setuid
file found it. The bytes themselves are copied, so line endings, a
missing final newline and any encoding are kept. The owner and group
are kept by refusal: a staged file of another owner or group is
`OwnerChanged`. Not kept: extended attributes, ACLs, timestamps (a
replaced or restored file has the current time), and the inode (a hard
link would be broken, hence `HardLinked`).

## 6. What the store must provide (WP-064, WP-075)

`JournalStore` over the store: `publish` atomic, durable and exclusive
(`AlreadyExists` if a journal exists, nothing changed; the tests' store
writes a temporary, syncs it, hard-links it to the journal's name, which
fails if the name exists, removes the temporary and syncs the
directory); `read`; `remove` durable. `Blobs::put` durable when it
returns. The command that runs `recover` passes the ownership of the
write's request (from the run's plan), and maps `JournalNotOwned` and
the other refusals to its exit statuses.
