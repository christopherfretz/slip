## What was built

- **`spec_members::collect`.** The seeds in a pattern
  (`families::in_pattern`: a class template, a partial specialisation or
  a function template among their enclosing entities; fix round) are
  memoised as their own subjects. If there are none, nothing else runs.
  Otherwise one pass over the unit's declarations takes each one named
  by the old identifier that Kiln links to a pattern
  (`instantiated_from`, not a `Specialization` or `PartialSpecialization`
  link) and resolves its entity. An entity's patterns are the entities
  `instantiated_from` gives for each of its declarations
  (`redecls_of`), without the entity itself, and without a friend
  pattern that does not define the function. The digest asks the same
  question (`Walk::instantiated_patterns`,
  `crates/slip_digest/src/keys.rs:494`). An entity whose patterns
  resolve to subjects, and whose key is named `identifier(old)`, is
  added as a follower. Its `of` is those subjects, which are the direct
  pattern: the member of the template, or the follower in between for
  a member of a member class template's specialisation. The memo marks
  an entity `None` before descending, so a malformed cycle ends; depth
  is bounded by `CTX_LIMIT`.
- **Flags.** Every follower is flagged `unsupported` (decision 2). A
  follower is also flagged `unreachable` when a declaration of it is an
  explicit instantiation of the member (`SpecKind::ExplicitInstantiation{Declaration,
  Definition}`), when one has an extent row but no `decl_names` entry, or
  when it is explicitly specialised and no declaration of it is named.
- **`dependent::claim`** is unchanged: `unresolved` at the name token
  `Sites::name_token` locates. Its documentation now states what parts A
  and D wait for, with Kiln's lines.

## Decided where the spec was silent

1. **What a follower is** (§9.2, now stated there). "Instantiated from"
   means Kiln's `instantiated_from` link. It is asked of every
   declaration of the member and followed through the whole chain, as
   `digest.md` §3.4 follows it, and `of` is the direct pattern's subject.
   A member of an implicit or explicit instantiation of the class is a
   follower, and so is a member that is explicitly specialised
   (`template <> void S<int>::f() {}`). A member of an explicit or
   partial specialisation of the class is not a follower: it is linked to
   nothing, it is another entity, and its names are `keep`s. A
   specialisation of a member function template has a `Specialization`
   link and is not a follower: its key is named by its template.
2. **`unsupported` on every follower, not on the seed** (§9.5, the row
   rewritten). A follower keeps the rule `Keys::rename_rule` gives for
   its own key, because a rule is a function of the key and the request
   (§4.1). The digest makes any rule on an instantiated member's key
   indeterminate (`key/rule-on-instantiated-member`,
   `crates/slip_digest/src/keys.rs:552-556`), so the run must refuse
   where such a follower exists. Flagging the follower, rather than the
   seed as the core did, means that a unit which does not instantiate
   the class has no follower and refuses nothing. A seed's rule and
   flags do not depend on instantiation (tested). The test
   `followers_of_class_template_members_map_with_their_seed` shows the
   flag is needed: with the seeds' rules alone, every follower maps
   right in the post-image; with every subject's rule, a key is
   indeterminate.
3. **The key-name check.** A follower must have a key named
   `identifier(old)` (§9.2: "when its key has the old name"). The AST
   name is compared first only to keep the pass cheap.
4. **Part B splits by what Kiln records.** An explicit specialisation
   of a member has an extent row, so `decls` claims it (a `replace` with
   a literal piece; through a macro name it is refused `macro_body`). An
   explicit instantiation of a member has no row, no declaration of its
   own and the pattern's location (probed), so its name is in neither
   table. The follower it instantiates is therefore flagged
   `unreachable` (§9.5 row extended), and the run refuses instead of
   leaving a name unedited.
5. **§9.4 read precisely** (written into `spec/edits.md` §9.4, "Read
   precisely"). An entity is taken to its origin before the subject
   test. "Every", "none" and "mixed" are over what this observer gives.
   A claim's subjects are the subjects among the entities found. The
   holder is `Keys::unit_of` the entry's enclosing declaration. There is
   no `changed` entry when there is no enclosing declaration, no unit or
   no key, or when `sites` turns a `replace` into a `refuse`. At this
   pin every row is `unresolved`. The pending tests are written to these
   readings.
6. **Part A's exemption.** The spelling rule is not settled, so the
   pending tests implement §9.4 as written: a `changed` entry for the
   holder's key.

## For the digest

For `unsupported` to go from followers, `follow_patterns`
(`crates/slip_digest/src/keys.rs:533-559`) must accept a rule on an
instantiated member's key `k` when the rule maps `k` to exactly the
followed key: the name the followed pattern's rule gives (`mapped_name`
of the pattern) and the parent `k` has, with every other component of
`k` unchanged. It must also accept a rule on the followed key that maps
it to itself. Today any rule that changes `k` or the followed key is
`key/rule-on-instantiated-member`. With that change `spec_members`
drops the `UNSUPPORTED` flag, and
`followers_of_class_template_members_map_with_their_seed` flips its
second assertion (no key indeterminate with every rule). The same
change is what WP-071's "For the digest" asks for friends defined in
class templates.

## Holes

- A member of a class template reached only through a dependent name
  (inside another template) is `unresolved` (parts A and D), not
  followed.
- F1's flag is on every seed in a pattern: a friend template of a
  member of a dependent specialisation of another class, with the old
  name, refuses the run (over-refusal; Kiln does not record the
  class). A friend whose name `sites` refuses as `not_plain` with the
  old bytes (tier mismatch only) is taken as spelled otherwise.
- F2's flag is on every seed in a pattern, for the same reason. Both
  flags go on every seed in a pattern whatever the class: a friend of
  another class's dependent member spelled like the old name, or an
  unlinked member of any class template, refuses the run. For example,
  a friend of the partial specialisation's own `n::S<T*>::f`, a
  different entity, refuses a rename of `n::S::f`.
- A unit that forward-declares `S` and befriends `n::S<T>::f` without
  seeing `S`'s definition has no seed. No scan runs there, and the
  friend's name has no claim and no flag. It is caught only if a
  planned unit sees the friend together with `S`'s definition (likely,
  since the member's body needs the befriending class complete, but not
  guaranteed). Otherwise the residue scan lists the token as
  `not_compiled`.
- `rename::origin_of` differs from `written::origin` for a variable
  with no link of its own (F4). It is limited to variables because the
  wider form made a function's subject depend on instantiation order
  (the review's r16/r17, now `s9_3-friend-redeclared-after-instantiation`
  and `-before-`). The redeclaration is now claimed for the seed in
  both orders. The call `f(s)` after it still spells the seed when the
  redeclaration follows the instantiation and the friend follower when
  it precedes it. That comes from `written::origin` of the call's
  referent, as before this package (WP-071). Both keys map to the new
  name, and the seed's `unsupported` refuses the run today. WP-119
  should look at it when that flag goes.
- The followers come from one observer's instantiations. A unit that
  instantiates the class differently makes other followers, and reduce
  joins them by key.
