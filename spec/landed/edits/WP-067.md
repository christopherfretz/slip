# WP-067 — slip_kiln: the written references and the declaration names of a unit

What `slip_kiln::written` (`crates/slip_kiln/src/written.rs`) does where
`spec/edits.md` §9.3 and §9.7, `spec/verify.md` §10.2 and
`docs/wp/WP-067.md` leave it open. Kiln sites are at the pin
`913a490bb`, under `kiln/crates/`. Tests: `crates/slip_kiln/tests/written.rs`
and the unit tests of `written.rs`.

## Switching the tables on

`ParseOptions::written` adds two words to the command line the front end
is given, right after `-fsyntax-only` (so before a `--` of the command's
own): `-fkiln-dump-written-refs` (`kiln_driver/src/args.rs:2056`) and
`-fkiln-decl-extents` (`:2057`). They are never words of the plan: the
observer, its id and the shard do not change (the shard of a parse with
`written` is byte-identical to the shard without it, test
`s8_4_written_off_records_nothing_and_changes_no_shard`).

At this pin Kiln's `FrontEndOptions` has no switch for the
written-reference table (Kiln WP-2320, `docs/requests/KR1-amendment-1.md`
§1). The dump flag is the only one, but through the front-end library
entry it records and prints nothing: the entry returns before any dump is
formatted (`kiln_driver/src/syntax_cmd.rs:692-696`; Kiln
`spec/driver.md` "Front-end library entry": "no dumps"). So `written` is
in effect a recording-only switch spelled as the dump flag. The one
function that makes the words is `written_words` in
`crates/slip_kiln/src/parse.rs`; when Kiln's switch lands it is the one
place that changes.

`-fkiln-decl-extents` is part of the module cache's key (Kiln
`spec/ast.md` §19.6): a unit that does `import std;` misses a cache entry
built without it and builds the module in process. No LLVM unit imports a
module.

The cost, measured with a release `slip parse -j 1` over one-entry
compilation databases of the LLVM corpus, the "on" database's command
carrying the two words (the same work the front end does under
`written`), two runs each: `llvm/lib/Support/raw_ostream.cpp` 0.63 and
0.87 s, 47 MiB off; 0.54 and 0.78 s, 51 MiB on (peak +8 %);
`llvm/lib/IR/Verifier.cpp` 2.01 and 1.94 s, 114 and 117 MiB off; 2.02 and
1.90 s, 125 and 128 MiB on (+10 %); `clang/lib/Sema/SemaExpr.cpp` 6.41 and
6.74 s, 327 and 326 MiB off; 6.78 and 6.80 s, 351 and 338 MiB on (+4 to
+8 %, wall +1 to +6 %). The wall-time difference is within the noise of a
shared host; the memory is the tables'.

## Order

"Unit order" is `slip_kiln::ranges::unit_order` (WP-084), not on `main`
when this package landed. Until it is, every list is in the table's own
order: the written-reference table's recording order (Kiln `spec/ast.md`
§18.1: a qualifier's components before the name, template arguments
before the template name) and the declaration-extent table's
declaration-id order. Each list is sorted, stably, by the comparator
`written::ORDER`, which is the table's order (every pair equal) today;
WP-084 replaces that one constant.

## Written references

- A reference is an entry with an `entity`; an entry with `REF_DEPENDENT`
  and an entity (Kiln prints it `dep`) is a reference. That rule never
  applies at this pin: Kiln clears the flag when it patches an entity in
  (`kiln_ast/src/written_refs.rs:270-277`). The code keeps it for when
  Kiln records one.
- Entries equal in role, range (both raw ends) and referent are one; the
  first is kept. At this pin Kiln records a name of a default member
  initialiser or of a default argument once, at its written site, however
  many constructors or calls use it (Kiln `spec/ast.md` §18.5; the test
  `s9_3_default_initialiser_and_argument_are_one_reference` checks the raw
  table too): the joining is kept as the package asks, and unit-tested on
  a table built by hand.
- A name in a macro argument that the macro substitutes twice is two
  entries whose ranges are two macro locations; they are two references
  (`spec/verify.md` §10.2).
- `first` is the start of the outermost component the qualifier chain
  links to. A leading `::` is not a component and its location is not
  recorded (`KR1-amendment-1.md` §3): `global` says it is there and
  `first` is the component after it. A component the table does not link
  (the one after `decltype(x)::`, Kiln `spec/ast.md` §18.4) ends the
  chain. A qualifier entry is a reference like any other and has its own
  `first` and `global` (for `::a::b`, `b`'s `first` is `a`).
- `via_using`: `found` is a `UsingShadow` or a `ConstructorUsingShadow`;
  the shadow's target is not compared with the referent (Kiln records
  `found` only when it differs from the entity). A shadow comes from a
  using-declaration **or** a using-enum-declaration: an enumerator named
  after `using enum E;` is `via_using` (test
  `s9_3_via_using_through_using_enum`). A `found` that is the template of
  a specialisation is not a using (`s9_3_found_template_is_not_via_using`).
  No recorded name is found as a `ConstructorUsingShadow` at this pin: a
  constructor is reached by overload resolution, not by a written name;
  the sweep counts such entries and pins the count at 0
  (`wp085_9_…`); the kind stays in the test so that the day Kiln records
  one it is `via_using`.

## Dependent names

The entries without an entity, joined as above on role, range and
`unresolved` (`REF_UNRESOLVED`; otherwise the entry is `REF_DEPENDENT`);
the first entry's `enclosing` is kept. `enclosing` of a name in a function
template's body is the template's pattern (the `Function`), as Kiln
records it.

**No found set.** `spec/edits.md` §9.4 row 1 is decided by "the
declarations found at the definition". Kiln's dependent entry has no
entity and links no overload set: `ov(x)` with one visible overload,
`f(x)` with two, `a(t)`, `this->a(t)` and `C::a(t)` in the current
instantiation are all bare dependent names. The found set is not
available at this pin; WP-073 needs it from Kiln (finding K4 below).

## Declaration names

One per declaration-extent row with a valid `name`, in declaration-id
order, except:

- the pattern of a template, which shares the template's row: the
  template is given;
- a `Friend` / `FriendTemplate` row: the function or class it declares
  has the same row and is given (the `Friend` node's own name is empty,
  `kiln_ast/src/builder.rs:1090`);
- rows whose name names another declaration: `UsingDirective`,
  `UsingEnum`; and `LinkageSpec`, `Export`;
- a name that is not one identifier: an operator, a conversion function,
  a literal operator.

A constructor and a deduction guide are given, each written as one
identifier (the class's, the template's). A destructor is given: its name
is the identifier after `~` (`~C();`, `~ C();`, `S::~S() {}`), as a
written reference to it is (`p->~S()`: the `S`); a rename of the class
edits it. The span is cut from Kiln's `~T`: its last bytes, when the text
is `~`, blanks and the identifier and `kiln_lex::token_end` ends the token
there.

An inheriting constructor's using-declaration is given: Kiln names it as
a constructor of the class that declares it; what is written is the name
of the qualifier's last component **as written**, read from the type's
sugar: the typedef's (`using AT::AT;`), the alias's (`using AU::AU;`), the
template's (`using B<T>::B;`, an `UnresolvedUsingValue` in the pattern),
the class's (`using A::A;`). Not the record it resolves to: the typedef's
name is what a rename of the typedef edits.

The span is Kiln's `name` when its text is the identifier. Otherwise (a
specialisation written as a template-id, `t<int>`, `S<int>`) it is the
first token, ended by Kiln's `kiln_lex::token_end` with default lexer
options, when that token's text is the identifier byte for byte; else the
declaration is absent (nothing is guessed; over the pair tests and the
package's shapes no row is dropped this way except a specialisation whose
name a macro spells, `template <> struct NAME<int> {};`).

The kind: `UsingDeclaration` for `Using`, `UsingPack` and the unresolved
using kinds; else by the declaration's own `SpecInfo` or `MemberSpecInfo`
kind: `ExplicitSpecialization` is `ExplicitSpecialisation` (a member of a
class template specialisation explicitly specialised, `template <> void
S<long>::m() {}`, by its `MemberSpecInfo`), either explicit instantiation
is `ExplicitInstantiation`; anything else (a partial specialisation
included) is `Declaration`.

## One declaration: `row`

`row(unit, d) -> Option<DeclNameKind>` says whether `d` has a row in the
extent table and of which kind, read from `decl_extents.get(d)` for every
row, those `decl_names` leaves out included (patterns, a friend's own row,
unnamed declarations, operators, conversion functions, using-directives,
`using enum`). It answers WP-085's `written(d)` ("has a row and it is not
an explicit instantiation's") without building the list. Two variants
were added so that a row whose name names another declaration is not
taken for a declaration: `UsingDirective` and `UsingEnum`; `decl_names`
never gives them. For every name `decl_names` gives, `row` is its kind
(asserted over the sweep).

## Origin

`origin(unit, d)` repeats, at most 256 times, until none applies: a
specialisation (`Ast::spec_info`, of any kind: implicit, explicit
specialisation, explicit instantiation) goes to `SpecInfo::template`; the
pattern of a template (`Ast::described_template`: a class, function,
variable or alias template) goes to the template; anything else goes to
`Ast::instantiated_from` (a member of a class template specialisation to
the member it was instantiated from, by its `MemberSpecInfo` or Kiln's
sparse map: fields, enumerators, member templates). So the
injected-class-name `W` inside `template <class T> struct W` and `W<T>`
there have one origin, the class template; a member template's pattern
(`M* m` inside `M`) has the member template; a specialisation of a member
template of an instantiated class has the member template of the class
template. A declaration that is none of these is its own origin, and an
origin is its own.

## Findings for Kiln

- **K1.** An explicit instantiation of a function template, a variable
  template or a member function of a class template has no extent row
  (only its parameters do); a class template's has one. Against Kiln
  `spec/ast.md` §19.1. Site: the explicit-instantiation branch of
  `parse_template_declaration`, `kiln_parse/src/templ.rs:157-167`.
  Reproducer:
  ```cpp
  template <class T> void t(T) {}
  template <class T> T vt = T();
  template <class T> struct S2 { void m() {} };
  template void t<double>(double);
  extern template void t<long>(long);
  template long vt<long>;
  template void S2<long>::m();
  template void t(short);
  ```
  Expected: a row per explicit instantiation. Observed: none.
- **K2.** `extern template struct S<int>;` then `template struct S<int>;`
  is one row, the second's.
- **K3** (wider than K2). A later construct that Kiln resolves to an
  existing declaration overwrites that declaration's row
  (`kiln_parse/src/extents.rs:68-79` gets or creates the row by
  declaration; `kiln_ast/src/decl_extents.rs:164-171` overwrites), against
  Kiln `spec/ast.md` §19.1:
  ```cpp
  struct S;
  struct T { friend struct S; };      // S's row: name at the friend's S
  class K; class K;
  struct U { friend class K; };       // the second K's row: at the friend's K
  template <class X> struct Q;
  template <> struct Q<int>;
  template <> struct Q<int> {};       // one row, the definition's
  ```
  Expected: each declaration keeps its own row. Observed: the module
  gives, for the earlier declaration, a correct token of the later
  construct, and the earlier declaration's name is absent. The lost
  declarations are the holes: `struct S;` (1:8), the second `class K;`
  (3:16), `template <> struct Q<int>;` (6:20).
- **K4.** A dependent entry carries no found set (the declarations found
  at the template's definition, `spec/edits.md` §9.4 row 1): Kiln leaves
  the entity empty and links no overload set. WP-073 needs it.
- Stage 3 roles (using-declaration, using-directive, namespace alias,
  friend elaborated, specialisation target, designator, type-constraint)
  are not recorded (Kiln WP-1932).

- **M13.** Kiln builds a using-directive with `DeclName::EMPTY`
  (`kiln_sema/src/decl.rs`, `act_on_using_directive`), so `identifier` drops
  it before the kind skip is reached. The skip stays as documentation; the
  sweep and `s9_3_row_of_every_row` assert that no using-directive is ever a
  declaration name. `using enum` does carry the enum's name
  (`kiln_sema/src/using.rs`, `using_enum_of`), and removing its skip is caught.
- **M11.** A constructor is reached by overload resolution, not by a written
  name, so no written entry's found set is a ConstructorUsingShadow. The sweep
  (3909 sides plus the shapes) counts such entries and asserts 0. The branch is
  kept so that a later Kiln that records one is still read as a using.
- **M04.** A name whose text is not its identifier is, at this pin, a
  template-id starting with the identifier; destructors and inheriting
  constructors take their own paths, and a macro-spelled name fails the raw
  location comparison first. The text check is defensive and kept.
