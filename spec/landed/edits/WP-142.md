# WP-142 — slip_reduce: the memory bound is checked by what reduce holds, not by resident pages

This file is the inventory of item 1 of `docs/wp/WP-142.md`: everything
`crates/slip_reduce/src/` holds in memory whose size is a function of the
number of shards, of runs, or of observers, with its cost at 10,000 and at
1,000,000 shards. (The package names `spec/landed/reduce/`; there is no
spec `reduce.md`, and `cargo xtask lint` takes a landed file only under an
existing spec, so it is under `edits`, whose §5.6 it is about.)

Sizes are of a 64-bit build: a `Digest` is 32 bytes, a `Vec` that grows by
pushes has a capacity of up to twice its length. "Runs" are the first
pass's runs, `ceil(shards / fan_in)`.

## 1. Held per observer, per shard or per run

| # | What (where) | Grows with | At 10,000 shards | At 1,000,000 shards |
|---|---|---|---|---|
| 1 | The unparsed observers, `Vec<Digest>` (`lib.rs`, `basis_of`), which become `EditSet.unparsed` (§6: `list<digest>`) | unparsed observers | 32 B each: 312 KiB if all are unparsed (capacity up to 625 KiB) | 30.5 MiB (capacity up to 61 MiB) |
| 2 | The runs' joined states waiting to be folded in run order, `BTreeMap<usize, Joined>` (`lib.rs`, `run`, `folding`) | runs that finish before an earlier one; with one thread at most one | `fan_in` 64: up to 156 states; `fan_in` 2: up to 4,999 | `fan_in` 64: up to 15,624; `fan_in` 2: up to 499,999 |
| 3 | The number of files of each merge level, `Cleanup::levels: Vec<usize>` (`runs.rs`) | `log_fan_in(runs)` | `fan_in` 2: 14 levels, 112 B | `fan_in` 2: 20 levels, 160 B |

Item 2 needs several threads: the pool hands out runs in order, and a run
that is slow (one large shard) while the other threads finish the runs
after it leaves every one of those runs' `Joined` in the map until it
finishes. A `Joined` is empty maps (about 170 B) plus that run's joined
subjects (a `SubjectJoin` holds five `Sample`s, a rule and a display: a few
hundred bytes each), links, rules, ties, and one entry per shard counter
name (`api.*`, `edits.*`: eleven or more). For a rename's run, about 1 to
3 KiB: at 1,000,000 shards with `fan_in` 64, up to 15 to 45 MiB in the
worst case. It is not reached with one thread, and it is not reached when
the runs finish in about their order, which is the usual case.

What became of them (the supervisor's ruling, `docs/wp/WP-142.md`):

1. The unparsed list is the edit set's (§6) and stays: §5.6 states it as
   the one term of the observers, 32 bytes each. `reduce.peak.unparsed`
   counts it, and `tests/memory.rs`
   (`unparsed_observers_are_the_one_term_of_the_observers`) checks it.
2. The waiting runs are bounded by a window (§4 below): at most `W =
   WINDOW_PER_THREAD × threads` states, whatever the shards.
3. `Cleanup` holds the number of runs of the first pass and `fan_in`, and
   computes the files of each level when it removes them.

Nothing else grows with the shards, the runs or the observers:

- The plan's "one observer once" check is not a set in memory: every run
  writes a record `Key::Observer` per index into its temporary file, the
  merges join them, and the final stream reads them one at a time
  (`lib.rs`, after the merge). Memory: `fan_in` of them in a run's map.
- The basis is a file of 65 bytes per observer (`runs.rs`), read
  sequentially; the second pass reads `fan_in` entries of it per run.
- A run holds its records (`BTreeMap<Key, Val>`, at most `fan_in` shards'
  collapsed records) and `fan_in` basis entries; a merge holds `fan_in`
  readers (one record and one 8 KiB buffer each), their paths, a heap of
  `fan_in` keys, and one writer. The pool keeps nothing per job.
- Every `Sample` (`first` of a claim, a report, a subject's `seen` and
  `flag_seen`, a failure) holds at most 8 indices.
- The second pass's union `seen` is one set per checked file, of the
  distinct `(size, content)` the shards gave it; the runs' parts are
  folded into it as they finish (a union, in any order).
- The test's `Lazy` store makes each shard when opened and holds nothing;
  its `observer(i)` is computed.

## 3. The resident readings of the gate

With one thread and every shard `ok` (the gate's test,
`one_site_ten_thousand_shards_fan_in_two`), items 1 and 2 of §1 are empty
and item 3 is 112 B against 80 B: nothing reduce holds explains about
300 KiB more for 10,000 shards than for 1,000. As far as reading can tell
the difference is the measurement's: on Linux 6.2 and later a process's
resident counters are per-CPU counters read approximately (up to a batch
of pages per CPU is not yet folded in, and a run that lasts 20 s instead
of 1.5 s migrates over more of the 24 CPUs), and the `VmHWM` the test reads
after `clear_refs` is already off from `VmRSS` by 200 KiB in the failing
log. The allocator's slack (the 8 KiB buffers of 15,000 temporary files
made and dropped in turn) and the scratch directory's entries (kernel
memory, not resident pages of the process) are the other candidates; the
reading cannot tell them apart.

## 4. The window of the first pass (`edits.md` §5.6)

`first_pass` in `crates/slip_reduce/src/lib.rs` replaces the first
pass's use of the plain pool. The runs' joined states are folded in run
order exactly as before; only when a run may start changes.

- **State**, under one mutex: `started` (runs handed out), `folded` (the
  earliest run not yet folded), `waiting` (finished runs not yet folded),
  the fold `joined`, `stop`, the first error. One condition variable,
  `wake`.
- **Who may block.** Only a worker that holds no run, and only while
  `started >= folded + W`. A worker never waits while it runs a run, and
  never holds the mutex while it runs one.
- **Who wakes whom.** The worker that finishes run `folded` folds it and
  every run after it that is waiting, and if `folded` moved, wakes every
  waiting worker (`notify_all`); each checks the condition again under the
  mutex. A failed run sets `stop` and wakes everyone. A worker that panics
  sets `stop` and wakes everyone from a drop guard (`WakeOnPanic`) as it
  unwinds; `std::thread::scope` joins the workers and resumes the panic in
  the caller.
- **Why the earliest run always proceeds.** If `started == folded`, the
  condition `started >= folded + W` is false (`W >= 4`), so the next
  worker to look starts run `folded`. If `started > folded`, run `folded`
  has been handed out to a worker that is running it and does not wait for
  anything (a run needs no other run), so it finishes, fails or panics,
  and each of the three wakes the waiters. So no state is reached in which
  every worker waits.
- **The bound.** A run `r` is started only when `r < folded + W`, and
  `folded` only grows, so every finished run not yet folded is in
  `folded .. folded + W`: `waiting` holds at most `W` states, the run just
  finished included (`reduce.peak.waiting_runs`).
- **An error** stops the hand-out: the workers finish the runs they hold
  and return, and the first error is the result, as before. An `Input`
  error of a shard is not a run's error (it is offered to the least
  index, as before), so the pass goes on, and the error of the least index
  wins as with one thread.
- **One thread.** The runs are run in order on the caller's thread; each
  is folded before the next starts, so the condition is never true and
  nothing waits: as before.
- **Tests**: `crates/slip_reduce/tests/window.rs`. A store whose first run
  is slow (it waits for a run twice the window ahead, which the window
  forbids, or 150 ms): no run at or past `W` is opened before it is let
  go, `waiting_runs <= W`, and the result's bytes are the one-thread
  result's. The same with the slow run last, with two threads (most
  workers wait on the window: the call returns), with a shard that cannot
  be read inside a full window (the `Input` error of the one-thread call),
  and with a worker that panics inside a full window (the panic reaches
  the caller). Every call runs on its own thread with 60 s to return.
  `tests/order.rs` passes unchanged.

## 5. The counters `reduce.peak.*` (`edits.md` §5.6, §5.7)

`Reduced::peak: Peak`, from `crates/slip_reduce/src/meter.rs`. A gauge
counts what is held and its most at once: `sections` are counted from
the decoding of a shard to its drop, in either pass; `files`
from each open to its close (run writers and readers, the basis file's
creation, writes and readers); `records` is the size of a run's map
before it is written, and in a merge the records of its inputs plus the
one being joined; `waiting_runs` the size of `waiting` after a finished
run is put in it; `unparsed` the length of the set's list. They are not
in `EditSet.counters` and change no edit set and no golden.

`tests/memory.rs` asserts, for one site claimed by 1,000 and by 10,000
shards, `fan_in` 2, one thread: `sections` 1, `files` 3, `records` 4,
`waiting_runs` 1, `unparsed` 0, for both. The resident reading is made
only by the `#[ignore]`d tests and is checked only against 1 MiB of growth.
