# WP-075 — `reduce`, `apply`, and the store behind them

`crates/slip_cli` (`spec/exec.md` §8.12, §8.14; `spec/edits.md` §7,
§10.2, §10.5; `docs/wp/WP-075.md`): `src/transform/{mod,store,lines,
reduce,apply}.rs`, the parsing of `reduce` and `apply` and of the
options a transform's commands share (`TransformOptions`, for WP-076)
in `src/args.rs`, two dispatch arms in `src/commands.rs`, and
`tests/stages.rs` (20 tests, through the executable over a store the
test fills with `slip_model`). Outside `slip_cli`: `name()` on
`slip_model::formats::edits::{Reason, Severity, FailureKind}`, with
the test `s10_5_enumeration_names` in `crates/slip_model/tests/edits.rs`
(the lines print the names of §10.5, and only `State` and `Cause` had
them).

## Differences from the WP's interface

- `edit_set_summary` takes `indivisible: bool` (the request's): the
  `groups` line is omitted for an indivisible request (§10.5), and the
  edit set does not say which it is.
- `edit_set_details` takes `record: &Path`, the edit set's file in the
  store: the cut line is `<kind>: <n> more (slip dump <file>)`.
- `reduce_round` returns `Reduced`, an alias of the WP's tuple (Clippy's
  `type_complexity`).
- `apply_result` writes only `written <n> file(s)` or `patch <path>` to
  `out`; `result <id>` and `state <State>` are printed by the command
  before it, so they are printed also when `permits` says no.
- `ReduceArgs::plan` is the WP's `PlanSource`; `reduce` accepts only its
  `Plan` form (`--plan <id or file>`).

## Decisions where the spec is silent

1. **The selected observers only.** `StoreShards` covers the observers
   of the round's latest map run record (`selected_of_round`), not
   every observer of the plan: an observer the phase did not select is
   not one of the run's, and is neither read nor counted as unparsed.
2. **The request is the first `edits` shard's**, in plan order of the
   selected observers; every other shard is checked against it by
   `slip_reduce` (§5.7), not by the command. A first shard naming a
   request the store lacks is an input error naming the `TRFM` file.
3. **`reduce` opens the store exclusively** (it publishes, and its runs
   use the scratch directory), so a store with a journal is refused
   with `StoreError::UnfinishedWrite` (status 3). It prints no `plan`
   line; its output starts with `edits <id>`.
4. **Threads.** `-j` bounds the CPU tokens `reduce` takes without
   waiting (at least one thread), as `plan` does; `fan_in` is 64. The
   output does not depend on either (§5.3; tested with `-j 1`/`-j 4`).
5. **Counts and groups.** The counts of the summary come from the
   edit set's records; the `groups` line from its group counters.
   `nested` is counted by a sweep over the edits of each file.
6. **Detail lines without a place.** A refusal with a site and no
   subject omits the display; one with neither prints
   `refusal <cause> (<observers part>)`. Places are `line:column` from
   the file on disk when its size and digest still match the
   `FileRef`, otherwise `:@<lo>`.
7. **Status 1 for a written `verified_with_residue` result.** §10.5
   says so for the transform commands; `apply` follows it: a result
   written (or patched) under `--allow-residue` exits 1, `verified`
   exits 0.
8. **A stale file under `--patch` is status 3** (§10.5 lists a stale
   file as an input error); under `--write` it is §7.3 step 4's
   refusal, status 1, the tree untouched.
9. **`permits` first.** Nothing beyond the result and its edit set is
   read before `permits` answers. A no is
   ``slip: result <id>: its state `<s>` does not permit `--write` with
   the options given; nothing was written``, status 1. The overlay must
   be the result's and of its edit set, or it is an input error.
10. **The patch is written to a temporary beside it and renamed**; a
    file outside `--relative-to` is a usage error (status 2, §7.2)
    found before anything is written.
11. **`--recover`.** Its output is
    `recovered: restored <n>, left <n>, reported <n>`, or
    `recovered: no unfinished write`; each reported path gets one
    standard-error line and the journal is kept (status 3). The
    ownership it checks is that of the write's request, found from the
    journal's overlay → its edit set → `set.transform` → `TRFM`; when
    that chain cannot be followed it is an input error and the journal
    is kept. `journal_not_owned` is an input error, nothing changed.
12. **Durability of the store's side.** `StoreBlobs::put` syncs the
    blob and `blobs/`; `StoreJournal::publish` writes a temporary in
    the process's scratch directory, syncs it, hard-links it to
    `write.journal` (failing if one exists) and syncs the store's root;
    `remove` syncs the root after removing.
13. **`--result`** is 4 to 64 hexadecimal digits, lower-cased, and
    must name exactly one result of the store.

## Mutations

Each mutant was applied alone to one file, run against the named test
of `cargo test -p slip_cli --test stages`, and restored.

All ten were caught.

| # | Mutant | File | Caught by |
|---|---|---|---|
| M1 | the `permits` check skipped | `slip_cli/src/transform/apply.rs` | `s8_5_apply_permits_table` |
| M2 | `--allow-residue` ignored (always false) | `slip_cli/src/transform/apply.rs` | `s8_5_apply_permits_table` |
| M3 | the journal check skipped (`apply` opens the store shared) | `slip_cli/src/transform/apply.rs` | `s10_5_journal_refused_by_reduce_and_apply` |
| M4 | the ownership not the request's (everything owned) | `slip_cli/src/transform/apply.rs` | `s7_1_apply_not_owned_and_unchanged_entries` |
| M5 | entries with `post == pre` written | `slip_apply/src/write.rs` | `s7_1_apply_not_owned_and_unchanged_entries` |
| M6 | the round's request not checked against each shard's | `slip_reduce/src/pass1.rs` | `s10_5_reduce_shard_of_another_request` |
| M7 | `-j` changes the output (a `threads` line) | `slip_cli/src/transform/reduce.rs` | `s5_3_reduce_is_deterministic_across_j` |
| M8 | a status swapped (accepted 1, refused 0) | `slip_cli/src/transform/reduce.rs` | `s10_5_reduce_contested_site` |
| M9 | the patch keeps entries with `post == pre` | `slip_apply/src/patch.rs` | `s7_1_apply_not_owned_and_unchanged_entries` |

M5, M6 and M9 mutate the crates whose checks the command relies on (the
WP says the command does not compare requests itself); the tests reach
them through the executable.

## Open questions

- Decision 7 (status 1 for a written `verified_with_residue` result
  under `apply`) and decision 8 (status 3 for a stale file under
  `--patch`, 1 under `--write`) read §10.5 one way; the spec could say
  so.
- Decision 1: whether an observer the map phase did not select should
  count as unparsed is §5's to say.
- The output lines of `apply --recover` (decision 11) are not in
  §10.5.
