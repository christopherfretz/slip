## Decisions

1. **A row whose entity is not named like the old name** is counted with
   those that do not bind a subject, but alone makes no `keep`: it is the
   table's row for something this rename does not read (the type of a
   nested-name-specifier component), not evidence the name means another
   declaration.
2. **Item 5 by join, not by a field of `Refusal`.** A site refusal is
   one record joined over observers; the specialisations behind it are
   many and per observer. They are carried once, as `EditSet.instances`
   at the refusal's place, and the report joins them by place. Adding
   them to `Refusal` would repeat what `instances` holds. A format change
   all the same (EDTS 2), under `spec/model.md`'s version rule.
3. **Format versions.** TRFM 1 → 2 (`dependent`, after `new`); EDTS
   1 → 2 (`instances`, last). Both refuse version 1
   (`UnsupportedVersion`): no reader of v1 exists outside this tree.
   `Reason::Instantiated` is a new value of an enum whose unknown values
   are already refused, so no version of its own.
4. **The edits section moves from 17 to 32.** Its payload changed shape
   (`instances` last); id 17 is retired and reads as an unknown section,
   so an old shard is refused at its section, not misread. Written and
   checked after `found` (31).
5. **Instances kept** only at the range of an accepted edit or of a
   site refusal (`keep`, `unresolved` and rejected edits drop theirs):
   what the report says is the evidence for an edit, or why a site was
   refused. A refused set has no edits (§6.1; `set.rs` empties `finals`
   when the set is not accepted), so in a refused set the instances
   that survive are those at site refusals only.
6. **The heading counts places**, the lines count specialisations; the
   observer count of a line is the number of observers whose shard made
   that specialisation there.
7. **Residue of their own kind, not §8.4 `dependent`**, and the result's
   state does not change (`spec/edits.md` §10.5 gives the reason).
8. **`--dependent`** is parsed but no command of this version accepts
   it: `map` and `rename` are `docs/wp/WP-076.md`'s.
9. **New name in the tests is `h`**, not `g`: `D::g` and `W::g` capture
   `this->g()` (Findings, 1).
10. Pre-existing: `slip_reduce`'s `reason_of` lacked `Directive`; added.
11. **`leave`, the default** (second review). Named `leave` (it leaves
    the name as it was, `unresolved`), not `residue` (residue is what
    verification makes of it, not what the rename does). TRFM stays at
    2: the value is new and version 2 is not on `main`.
12. **No unit is withdrawn from the comparison for a token** (second
    review). A row-2 `replace` adds nothing to `changed`; the holder is
    compared as every unit is, so it differs. The sound replacement, a
    comparison of the holder with dependent names mapped, is
    `docs/wp/WP-154.md`'s. Until it lands `offer` edits and the run is
    not verified; the report says so at the heading of the names edited
    on instances (§10.5).
13. **One record for two local specialisations with one display**
    (second review, N1): an instance whose specialisation has no key
    (`spec: None`, a local class or a lambda) is joined by its display,
    so two with the same display at one place are one record, their
    observer counts summed. A stated limit of the report (§10.5): it
    changes no claim and no acceptance, and keying them apart needs a
    key the digest does not give a local specialisation.

## Findings (for the supervisor)

As handed back, then as ruled (06:35 ET):

1. **The new name captured at an instantiation.**
   `template <class T> struct D : T { int g() { return this->f(); } };`,
   renaming `n::S::f` to `g`: `this->g()` finds `D::g`. Accepted, not
   verified (`wp139_new_name_captured_in_an_instantiation_is_not_verified`).
   **Ruled**: accepted as it is (loud, fail closed, stated in §9.4); a
   check of what the new name finds per instance is a package of its own.
2. **No holder.** A dependent name in an alias template's pattern or a
   head requires-clause is enclosed by the translation unit in Kiln's
   table, so there was no holder and no `changed` entry: accepted, not
   verified. **Ruled and built**: the site is refused, `no_holder` (12),
   where row 2 would `replace` and there is no holder. **Undone by the
   second review**: no holder is exempt, so a missing one is no reason;
   `no_holder` is dropped and the shape is accepted and not verified
   under `offer`, like every edited dependent name
   (`wp139_name_with_no_holder_is_not_verified`, both shapes). Kiln's
   enclosing declaration still matters to WP-154 (For Kiln, 2).
3. **No row, with a fallback.** A dependent name in a default template
   argument has no row; it is `unresolved` (the right claim: no
   evidence). Where the post-image has no other `s`, it fails to compile
   (`wp139_no_row_fails_verification_loudly`). Where it has one
   (`Base::s`), the binding moves; the digest's verdict is `verified`,
   and the result's state is `verified_with_residue` (the token is an
   `unresolved` range, residue `dependent`, §8.4, named by the report)
   (`wp139_no_row_with_a_fallback_is_residue`; the helper runs the rename
   and the digest only; the command-level test is a later package's).
   **Ruled**: a limit of the digest, not of the rename, and wider than
   this shape: a substitution whose expression is not kept (a default
   template argument, an alias template's pattern, a constraint's
   satisfaction, a signature substituted during deduction) is seen by its
   outcome, never by what its names bound (`spec/edits.md` §9.4, "What
   the digest sees of a substitution"). A design package for the digest
   follows.
4. **A dependent name in its holder's key** (asked by the ruling): a
   trailing return type `auto f() -> decltype(T::s())`, a parameter type
   `int f(T, decltype(T::s()) x)`, a trailing requires-clause
   `int f() requires (sizeof(T::s()) > 0)`. Each has a row and a holder
   (the function), every row binds the subject: `replace`. The
   edit changes the holder's key: the post-image adds `template <class>
   decltype(T::h()) f()` (and the like), and the specialisation's key is
   removed and added. **Accepted and not verified** (loud;
   `wp139_finding_name_in_the_holders_key_is_not_verified`). Not refused:
   telling a name in the key from one in the body before the claim needs
   the extents of the body, of each default argument and of the
   exception specification (`noexcept(...)` is in the declarator and not
   in the key; that shape is edited and verifies), and a short search of
   Kiln's AST at the pin found no extent for the exception
   specification's expression. Left to the supervisor, as ruled. No
   key-to-key rule built. Since the second review the holder is not
   exempt anyway (`exempt == 0` in the test); the keys still change
   (`removed`/`added`), which a mapped comparison of the holder
   (WP-154) does not cover either.

From the second review (S1), loud, each a `replace` under `offer` whose
difference is not where a holder would be (the review's probes, with
`Base::s` a fallback observably different from `S::s`); none is silent:

5. **Member alias** `using type = decltype(T::s());`: `changed
   M::type`. **Enumerator** `enum { e = sizeof(T::s()) };`: `changed
   EN::e`. **`alignas(sizeof(T::s()))`** on a class template: `changed
   AL`. The name's unit is not the function the dependent entry is

6. **A dependent name in a function template's signature** (a trailing

   So for a constraint and an alias, the row's `spec` names the pattern,

4. **No row for a dependent name in a deduction guide's parameter**

## Second review

The review of `0a63141e` found two blockers. Their sources, verbatim
(`docs/wp/WP-154.md` cites them from here):

### B1 (blocker): the holder exemption hides a rebinding in a NON-template function. Verified; the program changed.
A generic lambda in an ordinary function holds a dependent name. Its holder (`Keys::unit_of` of the lambda's
operator()) is the enclosing ordinary function, which is then exempt in every observer. Anything else in that
function that changes meaning goes unseen.

```cpp
int h(int) { return 10; }
namespace n {
struct S { static int f(int) { return 1; } };
struct U : S { int u() { auto l = [](auto t) { return t.f(1); }; return l(S()) + h(0); } };
}
int w() { return n::U().u(); }
```

Rename n::S::f to h. Result: accepted, `differences: []`, exempt 1. In the post-image, `h(0)` in `U::u` binds
`S::h` (was `::h`), so `u()` returns 2 instead of 11. Control: the same code with `[](S t)` (no dependent name)
gives `changed n::U::u()` (rv139_generic_lambda_control). Namespace form (n::f(A)/n::f(int) renamed to h,
`h(0)` in non-template `n::u` moves from ::h(int) to n::h(int)): also silent (rv139_generic_lambda_holder_hides_rebinding_namespace).
`name_taken` does not catch it: ::h is outside every scope the subject's name enters.
This is a non-template function that every observer compiles, so the change is in code each observer runs.
Code: dependent.rs `holder()`; spec §9.4 "The exemption of a holder ... what is still checked inside the
holder is every spelled piece". That sentence is true, but it hides that non-claimed names of the holder are
not checked at all. Any fix must not exempt a whole non-template unit for one dependent token. For example, the
digest could compare the holder with the dependent identifier masked, rather than skipping the unit.

### B2 (blocker, same mechanism, template code): non-dependent rebindings in parts of an exempt pattern that no instantiation contains
The new name captures a non-dependent name of the holder that no instantiation of the run contains. Each
case is accepted and verified:
- an `if constexpr` discarded branch (rv139_discarded_branch_in_holder):
  `template <class T> static int call(T) { if constexpr (sizeof(T) > 100) return h(0); else return T::f(1); }`
  as a member of `n::S`, with a global `int h(int)`. Renaming `S::f` to `h` moves the discarded `h(0)` to `S::h`.
- an unused default argument of the function template (`int k = h(0)`; rv139_unused_default_argument_in_holder).
- another observer's preprocessing (rv139_exemption_from_other_observer): t.h has `call` with
  `#ifdef B_SIDE return h(0) + T::f(1); #else return T::f(1); #endif`. a.cpp instantiates without B_SIDE (replace
  plus exemption). b.cpp defines B_SIDE and does not instantiate. In b.cpp, `h(0)` moves silently, in both plan
  orders. The exemption one observer earned is applied to another observer's different copy of the holder.
In a non-template function each of these is a `changed` unit. Spec §9.4 names only "an error in a dependent
name of an exempt pattern that no observer instantiates" as undetected. Non-dependent names are not mentioned,
so the spec's own account of the guarantee is wrong. Same fix area as B1.
