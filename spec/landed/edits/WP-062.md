# WP-062 — slip_reduce: from the claims of every observer to one edit set

Implemented by the crate `slip_reduce` (`crates/slip_reduce/src/`:
`lib.rs` the interface and the two passes, `pass1.rs` the checks of §5.1
and the fold of one shard, `records.rs` the collapsed records and their
joins, `runs.rs` the temporary files, `subjects.rs` §5.2, `outcome.rs`
§5.4's table, `set.rs` the stream, the geometry, the groups and the
records of the set, `geometry.rs` the sweeps, `groups.rs` ties and
effect, `declared.rs` §6.2). This file fixes what `edits.md` §5, §6.2
and §6.3 leave open or say twice. Tests: `crates/slip_reduce/tests/`
(`reduce.rs`, `pieces.rs`, `groups.rs`, `order.rs` with the naive model
in `tests/common/model.rs`, `memory.rs`).

## 1. Interface (`edits.md` §5.7)

As §5.7, with these differences, which §5.7 now states:

- `Shards: Sync`. The first pass, the merges and the second pass run on
  up to `threads` threads, each reading shards.
- `Shards::open(index) -> Result<Option<Vec<u8>>, String>`: the bytes
  of the stored shard, not a decoded `Shard`. Reduce decodes them, and
  the `shard` of the observer's `Basis` is their trailer (the content id
  the container checks on decoding), so the id is of the very bytes
  read. A shard whose stored bytes hold an ignorable section (id 64 or
  above) decodes to the same `Shard` as one without, so re-encoding is
  not that id (`reduce.rs` `basis_is_of_the_bytes_read`). An earlier
  draft had `Shards::shard_id(index)` beside an `open` that returned a
  `Shard`: the id was then the store's word for bytes reduce never saw.
- `fan_in < 2` and `threads == 0` are `ReduceError::Options` (`reduce:
  the options: …`), not a panic (`options_out_of_range`).
- `Options::new(scratch)`: `fan_in` 64, one thread. `ReduceError`
  implements `Display` and `Error`; `Reduced` and `ReduceError` derive
  `Clone` and `Debug`.
- `reduce` returns `declared(&edits)`: one derivation, which `slip
  check` calls on a set it is handed.

## 2. Inputs (`edits.md` §5.1, §4.7)

Each shard is checked in this order; the first failing check is the
shard's `Input` error, with the message given (the observer is
`Shards::observer(index)`):

1. `open` fails: `the shard cannot be read: <error>`. `Ok(None)`:
   unparsed.
2. The bytes do not decode (`Shard::from_bytes`: the container, its
   trailer, and §4.7's `validate`): `the shard is not valid: <error>`.
   This covers an `edits` section whose `scheme` is not 1, which the
   reader refuses (`input_other_scheme`).
3. `shard.observer` is not the plan's observer at `index`: `the shard is
   of another observer`; `phase` not `map`: `the shard is not of phase
   map`; `round` not the reduced round: `the shard is of round <r>, not
   <round>`.
4. A status other than `ok`: unparsed (§5.1).
5. No
   `edits` section: `an ok shard has no edits section`. `transform` not
   the request id: `the edits section is of another transform request`.
6. For each `inputs[j]` in turn: not `transform::is_file_path`
   (`inputs[<j>] is not a canonical absolute path of a file`); the
   reader does not check it, and a path that is not canonical would
   escape the file agreement of §5. Then for each `files[j]` in turn: not `transform::is_file_path`
   (`edits.files[<j>] is not a canonical absolute path of a file`);
   then, if the shard has `inputs`, absent from them (`… is not in the
   shard's inputs`) or different in size or content (`… disagrees with
   the shard's inputs`). A shard without `inputs` is not checked
   against them. (`model.md` §8 puts the main file in `inputs`, so every
   file a claim names is there.)
7. `links[j]` naming a key that is no subject of the shard; then for
   each claim `claims[j]` naming one, or replacing bytes of a file the
   request does not own (`transform::Ownership::is_owned`).

Two subjects of one id with different `rule` (§5.2 rule 1) are an
`Input` error of the later of the two observers that disagree: the
least index `i` such that a shard at an index below `i` gives the id
another rule (`the subject <id> has a rule other than an earlier shard
gives it`).

A plan that names one observer at two indices is an `Input` error of
that observer at the second index (`the plan names the observer <o> at
index <a> and again here`): §5.1 counts each observer once, and the
second shard would otherwise be joined with the first as one observer
or counted twice (`input_one_observer_twice`). It is found in the
stream, so it competes with the errors above by index like any other.

The error reduce returns is that of the least observer index that shows
one, whatever `fan_in`, `threads` and the order runs finish in: a run
skips a shard once an error at a lower index is known, and every shard
below the least error is read. An `Io` error (the temporary files) is
returned before any `Input` error.

The second pass opens every `ok` shard again and checks that the bytes
it reads decode and have the trailer the first pass recorded; otherwise
(no bytes, bytes that do not decode, or another id) `the shard changed
between the two passes of reduce`, an `Input` error of that observer
(`input_shard_changed_between_passes`). A failed run is a shard of status `ok`: it is in the basis
with its content id and is read by the second pass.

## 3. Subjects (`edits.md` §5.2)

- **`of` of a joined subject that is not a follower.** §5.2 rule 1 says
  `of` is the union; §6.1 (via §4.7) says `of` is empty unless the role
  is `follower`. The joined record keeps the union for selection and
  `mixed_follower`; the set's record has `of` only if its joined role is
  `follower`.
- **`mixed_follower`** is decided for every joined subject with a
  non-empty `of` union, whatever its joined role: refused if some of its
  `of` is selected and some not, or if all are selected and it is not
  (or none and it is). Its `observers` and `first` count the observers
  that have the subject. §5.2 names only "a follower"; an entity that
  one observer sees as a follower and another as a candidate is the case
  this covers.
- A flag's refusal counts the observers whose shard set the flag.
  `no_subject` has no subject and counts nobody.
- A selected id is a subject of the set only if some shard has it among
  its `subjects` (a link's ends always are, by §2 step 7).

## 4. The table of a site (`edits.md` §5.3, §5.4)

- **One cause per site.** When several rows apply, the cause is the
  first of `mixed_set`, `site_refused`, `divergent`, `contested`.
- **Counting observers at a site.** A refusal's `observers` and `first`
  for `mixed_set`, `site_refused`, `divergent` and `contested` (and the
  sample of a range that contests another site, §5 below) count each
  observer once, though it may have made several claims at the site: a
  shard with two or more claims at one site also writes one record of
  the site listing its claims' stances and pieces (as digests), so that
  reduce counts the observers of any set of the site's claims exactly.
  Memory: one record per distinct combination of claims at a site; one
  for a site every observer claims alike.
- `contested` at a site counts the observers of its `keep` claims,
  `replace` claims turned into `keep` by §5.2 included.
- The **least subject** of a site is the least subject of its claims
  after §5.2: claims turned into `keep` count, dropped `refuse` claims
  do not.
- `macro` of a refusal: `site_refused` that of the joined `refuse`
  claim; `divergent` and `mixed_set` the least of their claims;
  `contested` at a site that of the `replace` claim; a live site
  rejected later, that of its edit.
- **`no_edit`** stands when no `replace` claim remains after §5.2's
  treatment (`mixed_set` ones count as remaining). §5.5 said "no
  observer claimed a `replace`": a set whose only `replace` claims were
  turned into `keep` would then be refused with no refusal, which §6
  forbids. §5.5 now says so.
- **Failures** are joined by `(kind, message, place)` (§6); §5.3 said
  "by its whole record", which contradicts §6 for `rendered` and
  `refusal` (the first observer's). §5.3 now says so. Under a
  permutation of the plan a failure's `rendered` changes with its first
  observer, like `display` (`order.rs` clears both).

## 5. Geometry (`edits.md` §5.4)

- **Ranges that contest.** A live site is `contested` by another range
  when it shares a byte with the range of another site that is not live
  and has `keep` or `unresolved` claims (a rejected site included), or
  with the range of a live site that also has `unresolved` claims. The
  latter is an extension: §5.4 names kept and unresolved ranges, and an
  `unresolved` claim at a live site is one (`pieces.rs`
  `unresolved_at_a_live_site_contests`; with `replace` and `keep` at the
  same site, `reduce.rs` `replace_keep_and_unresolved_at_one_site`).
  `other` is the least such range, and `observers` and `first` count
  that range's `keep` and `unresolved` claims.
- **Every claimed site blocks** (the ruling of this package's review,
  now §5.4's text). A claimed site is a site with a `replace` claim that
  remains after §5.2, live or rejected, whatever rejected it. `overlap`
  rejects a live site that crosses a claimed site or a range one copies,
  and a live site that copies a range a claimed site crosses; `cyclic`
  follows the relation over every claimed site; the effect of §5.5 counts
  every claimed site as a container. The cause and `other` are those the
  live site would get if the claimed site were live. Before, these rules
  ran over the live sites only: an observer that disagreed about an edit
  (so `divergent`) let through a crossing or nested edit that agreement
  would have rejected, so more disagreement could accept more
  (`pieces.rs` `crossing_a_divergent_site`, `inside_a_divergent_site`,
  `inside_an_overlap_rejected_site`, `copies_and_a_divergent_site`,
  `cyclic_through_a_divergent_site`). A `replace` that §5.2 turned into a
  `keep` is not a claim of a claimed site: it blocks as a `keep`, by
  `contested`. Cost: a crossing is found by the sweep of `geometry.rs`
  over the claimed sites and their copies, in `O(n log n)` with `n` those
  ranges, plus, for `cyclic`, the ranges crossing a copied range (each
  splits the copy it crosses), which is zero in a family without
  crossings.
- **More shards refuse no less.** `order.rs`
  `more_shards_refuse_no_less` reduces each generated case less each one
  shard and checks that every site the smaller plan rejects the whole
  plan rejects too, or that the rejection is one of two exceptions, which
  it counts and checks are of that kind: the effect (the smaller plan's
  cause is `buried` or `with_group`, and the dropped shard's edit copies
  a range the site is properly inside, which an edit of the whole set
  does too: the edit carries it); and §5.2 (the selection, or the
  subjects a claim names, differ between the two plans, so a `replace`
  is a `keep` in one, or a `mixed_set` an edit). It runs on the case as
  generated and on the case with every subject removed, where only the
  first exception can apply. Over seeds 0 to 7 (160 cases each, about
  2,000 smaller plans): no exception of the effect, 1 to 11 of §5.2. The
  smallest exception of the effect, `pieces.rs`
  `buried_then_carried_by_one_more_shard`: `{[0,10)→"v", [2,3)→"z"}`
  buries both; one more shard with `[20,30)→copy([0,10))` makes all
  three accepted, since the copy carries `[2,3)`.
- **Order.** `contested`, then `overlap` (applied at once), then
  `cyclic`, then file agreement (`file_differs`); a site keeps the first
  cause. §5.4 lists file agreement after the table without an order.
  Since every rule rejects live sites against every claimed site,
  whatever an earlier rule rejected, and file agreement against the
  shards' files, which sites §5.4 rejects does not depend on the order;
  the order picks only the cause, and taking file agreement last keeps
  the more specific ones. (An earlier text said taking it last "rejects
  the same sites as any other place". Without the rule above that was
  not so: a site an earlier rule rejected stopped blocking, so another
  order could reject other sites.)
- **`overlap`'s `other`.** For a site that crosses another claimed site
  or a copied range: the least of those ranges. For a live site that
  copies a range a claimed site crosses: the least such site.
- **File agreement** compares, for each file named by a live site or
  copied by a live edit, every `(size, content)` that an `ok` shard
  gives the path in `files` or `inputs`, failed runs included. The set's
  `FileRef` for a path is the one of greatest `size`, then least
  `content`, among those the shards' `files` give it (any choice is
  within every place a shard gave in it; all agree unless the file
  differs, and then no edit is in the file).

## 6. Groups and effect (`edits.md` §5.5)

- Ties are kept by the identity `(file path, lo, hi, pieces)` of each
  grouped `replace` claim, as a digest, in a union-find whose root is the
  least digest. A member turned into a `keep` by §5.2 leaves the group
  but its ties stay: if `a` and `b` were tied only through it, they stay
  one group. This is more conservative than "leaves any group it was
  in" read as removing the edges.
- **`with_group`** (cause 17, a format change of this package's review:
  §6's `Cause`, its `other`, the causes of a site and the rows of
  `edits.md`'s table of §6 that name causes and `other`, and the
  messages of `spec/landed/edits/WP-061.md`'s rows that list them). A
  live site rejected only because its group was is refused with
  `with_group`; its `other` is the least site of a member of the group
  that has a refusal of its own (`Some` wins over the case of a refusal
  of §5.2, which leaves it absent), and `observers` and `first` are its
  edit's. Before, such an edit had no refusal: a `replace` the set did
  not hold and did not explain. Now every `replace` is explained (§5.5's
  last paragraph): `order.rs`'s `explained` checks it of every
  generated set, and `groups.rs` `whole_and_part_and_a_rejected_member`
  and `two_groups_joined_by_a_third` check the records. None under an
  `indivisible` request, whose `refused` state says it.
  `reduce.groups.rejected` counts the group; `reduce.sites.rejected`
  counts the site.
- **`indivisible`.** All edits are one group, rejected if any live site
  is rejected, if any site is refused by the table (a site with only
  `refuse` claims included), or if there is any refusal of a subject.
  §5.5 rejects a group for "an edit of the group at a rejected site";
  under a rename a refused site that holds no `replace` claim would not
  reject the rename, which is what `indivisible` is for.
- **`buried`.** Each round rejects every remaining edit that is not
  effective, and the innermost container of every claimed site that is
  not effective if that container is an edit that remains, each with
  `other` the least range of the other (the container's: the least of
  the sites it buries); then the groups of both; then the next round,
  until a round rejects nothing. Containers and the sites they hold are
  every claimed site; carriers (the edits whose copies make a site
  effective) are the edits that remain. The **innermost container**
  among claimed sites, which may cross, is the one that starts last, and
  of those the shortest: in a family without crossings it is the
  innermost, and among crossing containers it is one choice, by
  position, independent of order (`geometry.rs` `effect`, checked
  against a fixpoint by `effect_agrees_with_a_fixpoint`).

## 7. Rules (`edits.md` §6.2)

The union of §6.2 is the `renamed` rules of every `ok` shard without a
failure and the `rule` of every subject of the set. When it conflicts
the set has one `rule_conflict` refusal. The set's `rules` must be a
rule table (§6.1) even then: it holds the `renamed` rules whose
`(parent, kind, name, disc)` no other `renamed` rule has. `reduce.rules`
is the size of the union.

## 8. Counters (`edits.md` §6.3)

- **`reduce.runs` is not written.** It counts the temporary files, which
  depend on `fan_in`; §1 rule 3 and this package's order test require
  the edit set not to. §6.3 no longer lists it.
- `reduce.shards`: `ok` shards, failed runs included; `reduce.unparsed`:
  observers without one; `reduce.claims*`: the claims of the `ok`
  shards.
- `reduce.sites`: distinct sites with a claim; `.live`, `.kept`,
  `.unresolved`: by §5.4's first table; `.rejected`: distinct sites with
  a refusal of a site in the set, `with_group` included.
- `reduce.subjects`: joined subjects; `.selected`: subjects of the set.
- `reduce.groups`: the classes of edits (every `replace` claim that
  remains after §5.2, at any site) under the ties, an edit tied to
  nothing a class of its own; one under an `indivisible` request with
  any edit. `.rejected`: those with no edit in the set (all of them in a
  refused set).
- `reduce.edits.nested`: edits within another edit of the set.

## 9. Cost (`edits.md` §5.6)

- The temporary files are named `slip-reduce-<pid>-<call>-<level>-<run>`
  and `slip-reduce-<pid>-<call>-basis` under `Options::scratch`, created
  new, and removed when `reduce` returns, whatever it returns. The run
  files hold length-prefixed records sorted by key; the basis file one
  65-byte entry per observer at its index. Neither format is specified.
- The first pass holds one shard per thread at a time, the records of
  its run (at most `fan_in` shards' collapsed claims) and the joined
  state; a merge holds one record and one 8 KiB buffer per input. The
  stream holds the live sites and the ranges that contest (one record
  each), not the claims; the second pass holds the paths it checks.
- **Measuring.** The workspace forbids `unsafe` code in tests as well,
  so the counting global allocator `docs/wp/WP-062.md` asks for cannot be
  written. `tests/memory.rs` measures the growth of the resident
  high-water mark (`VmHWM`, reset by `/proc/self/clear_refs`) across one
  call instead, an upper bound on live heap, and checks it where Linux
  provides it.
- **What grows with the runs.** Nothing: the states of the first pass's
  runs and the file versions of the second pass are folded into one as
  each run finishes (the first pass in run order, holding only runs that
  finish before an earlier one; the second pass is a union), not collected
  per run. Collecting them grew the peak by about 1 MiB per 5,000 runs.
- **Measured** (debug build, `tests/memory.rs`): one site claimed by
  1,000 and by 10,000 shards with `fan_in` 2 and one thread grows the
  high-water mark by 8 KiB both times (bound 1 MiB, and 256 KiB from one
  to the other), in about 1.5 s and 20 s (the 15,000 temporary files).
  A rename-like run of 10,000 shards and 200,000 claims (8 shared sites,
  12 of each shard's own; `fan_in` 64, 8 threads) takes 3.5 s and grows
  it by 118 MiB, 26 MiB for 2,000 shards: the set's 120,008 edits and
  10,001 files, and their live records, which §5.6 holds.

7, `order.rs` 2, `memory.rs` 2 and one ignored large run, 5 unit tests
