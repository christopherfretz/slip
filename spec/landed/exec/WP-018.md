# WP-018 — what the CLI had to work around in slip_exec and slip_model

What `slip_exec` and `slip_model` now do so that `slip_cli` need not
(`docs/wp/WP-012.md`, Handback). Normative until folded into
`spec/exec.md` and `spec/model.md`. Builds on
`spec/landed/exec/WP-008.md`, `WP-009.md` and `WP-012.md`; it
**supersedes** the paragraph "Dead workers' scratch directories" of
`WP-012.md` and the sentence there that the signal callback "removes the
dead workers' `tmp/` entries": `parse` no longer does either, the pool
does (below). Tests: `crates/slip_exec/tests/pool.rs` (`s2_cleaning_*`,
the §7 probe, `check_run`), `crates/slip_exec/tests/store.rs`
(`s2_remove_entries_of_one_process`), `crates/slip_model/tests/formats.rs`
(`s7_s9_enumeration_names_and_all`); `crates/slip_cli/tests/cli.rs`
unchanged.

## Interface

```rust
// slip_model (additions; the names are those of spec/model.md §7–§9, as in JSON)
impl Reason { pub const ALL: [Reason; 6]; pub fn name(self) -> &'static str; }
impl Status { pub const ALL: [Status; 4]; pub fn name(self) -> &'static str; }
impl End    { pub const ALL: [End; 5];    pub fn name(self) -> &'static str; }

// slip_exec::store (addition)
impl Store { pub fn remove_entries_of(&self, pid: u32) -> Result<(), StoreError>; }

// slip_exec::pool (additions)
pub struct Summary { /* as before */ pub outcomes: Vec<ObserverOutcome> }
pub struct ObserverOutcome { pub observer: Digest, pub status: Status, pub message: String }
```

`ALL` lists every value once in code order. `ALL` is beyond the brief's
`name()`: without it a caller printing one line per value (§8.1, §8.2)
would keep a list of the values of its own.

## Workers' `tmp/` entries (§2 "Cleaning", §7)

- **`Store::remove_entries_of(pid)`** removes every `tmp/` entry whose name
  is `<pid>.…` with `<pid>` the canonical decimal of `pid` (the rule of
  WP-008 for stale entries), directories recursively. The caller vouches
  that the process is gone: `/proc` is not consulted. Either access mode.
  This process's own id is a no-op. No `tmp/`, or an entry that vanishes
  meanwhile, is not an error; any other failure is returned (the first
  one) after the remaining entries have been tried.
- **When the pool removes them.** In the loop, at the moment
  `Child::try_wait` first returns the worker's status (whatever ended it),
  before anything else is started, so the pid cannot have been given to a
  new worker of this run. In `abandon` (cancellation or an error of the
  store), for every worker still known, reaped or not: each has been sent
  `SIGKILL` and runs no more user code. Each worker's entries are removed
  once. Failures are ignored: the next exclusive open removes what is left
  (§2). The worker's process group is not searched for descendants (a
  worker runs the front end in its own process).
- **The signal path.** Each run in progress registers the pids of the
  workers it started whose entries it has not removed yet.
  `pool::cleanup_on_signal`, after waiting (at most 3 s) for the cancelled
  runs, removes the entries of every pid still registered (the signal path
  has killed every child by then, §7), and only then runs
  `store::cleanup_on_signal`. A run that finishes `abandon` in time has
  emptied its registry, so this matters only for a run that does not.
- **The fake worker** (`slip-fake-worker`, a test fixture) gains
  `--scratch 0|1`: with 1, each job first makes `tmp/<pid>.d/f` and a loose
  file `tmp/<pid>.fake.tmp`, names both on standard error, and removes the
  loose file only if the behaviour returns.

## Per-observer outcomes (§5.4, §8.2)

`Summary::outcomes` has one element per observer given to `pool::run`, in
that order (plan order), for the final shard: its observer id, its
`outcome.status`, and the first line of its `outcome.message` as
`str::lines` gives it (empty for an empty message). For a shard the
worker wrote, it comes from the shard the coordinator already reads to
check a `Done` (§5.2); for one the coordinator writes, from the message it
writes (clipped as written). `statuses` counts the same statuses.

`parse` prints the line of §8.2 for each outcome that is not `ok` and no
longer reads the shards again: the case of an observer with no shard in
the store (`no shard in the store`) cannot arise from a run that returns.
