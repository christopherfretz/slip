## 1. Why the lock needed a new mechanism

Before WP-161 the lock was written under `tmp/` and linked to `lock`
(exclusive: the link fails if `lock` exists), and a stale lock was taken
over by renaming it aside, checking that what was moved was the stale
lock, and linking it back if it was not. Without a link there is no
exclusive "put back": a rename back replaces whatever is at `lock`, and
`create_new` + write of the moved pid fails if a third opener created
`lock` meanwhile. The sequence that breaks every variant of "move aside,
check, put back" without a link:

1. `A` and `B` read `lock` = `<X>\n`, `X` dead.
2. `A` renames `lock` aside, finds `X`'s, removes it, creates `lock` and
   writes `<A>\n`: `A` holds.
3. `B` renames `lock` (now `A`'s) aside and finds `<A>\n`, not `X`'s.
4. `B` must put `A`'s lock back. Meanwhile `C` found `lock` absent and
   created it: a rename back replaces `C`'s lock (`A` and `C` both
   hold); a `create_new` back fails and `A`'s lock is gone (`A` and `C`
   both hold).

So the take-over cannot be a lone opener's reasoning about one name. It
is decided by **claims** (`exec.md` §2.1 "The lock", steps 1 to 5): an
opener creates `tmp/<pid>.<t>.<n>.claim`, lists `tmp/`, and goes on to
read and act on `lock` only if no other live process has a claim. This is
Dekker's entry protocol with a listing for the flag reads; the backoff
(steps 2 and the at most 8 rounds) gives up liveness under contention
(`Busy`), never safety.

## 2. The argument

Assumptions (each named where it is used):

- **(L)** The store's file system is linearizable for `create_new`,
  `unlink`, a read by name and a listing of one directory: an operation
  that has returned is seen by every operation of any process of the
  host that starts after it. This is the row `create-new-read` of
  `cargo xtask fscheck` (§4 below for the mount).
- **(P)** `/proc/<pid>` exists exactly while process `pid` (or a process
  that has reused the pid) exists.
- **(S)** Every exclusive opener of the store is a Slip following these
  rules; within one process, the takes are serialised by the mutex of
  the registry and a lock held by the process is in the registry.

Definitions: `P` is **inside** from the return of its listing (step 2)
to the return of the removal of its claim (step 5, or any exit from the
round). `P`'s claim exists from the return of its creation (step 1) to
the start of its removal; it is created before the listing and removed
after the last action inside, so it exists throughout `P`'s inside.

**Lemma 1 (inside is exclusive between live processes).** Let `P ≠ Q`,
both alive, be inside at one moment `m`. Each one's listing returned
before `m`, and each one's claim was created (returned) before its
listing started and is removed (starts) after `m`. Two cases:

- `Q`'s listing started after `P`'s claim was created. `P`'s claim is
  removed after `m`, so after `Q`'s listing returned: it existed
  throughout `Q`'s listing, which (L) lists it; `P` is alive (P), so `Q`
  saw a contender and did not go inside. Contradiction.
- `Q`'s listing started before `P`'s claim was created, so before `P`'s
  listing started. `Q`'s claim was created before `Q`'s listing started
  and is removed after `m`, after `P`'s listing returned: it existed
  throughout `P`'s listing, and `P` did not go inside. Contradiction.

Within one process (S) serialises the takes, so `P` and `Q` are never of
one pid (and a claim of one's own pid is not a contender: it is an
earlier process's with this pid, dead, or this take's own). A process
that dies inside does nothing more, so an overlap with a dead process's
inside is harmless.

**Lemma 2 (a lock is made only inside, and is whole when its maker
leaves).** `lock` is created only at step 4, which is inside. Its maker
leaves only after the write and the sync of `<pid>\n` returned, or after
it removed the file (a failed write or sync), or failed and returned an
error having tried to remove it. So a lock that reads empty, or as one to
ten digits without the newline, to a process inside has a maker that is
not inside (Lemma 1: no other live process is) and never will write to
it again: its maker is dead, or failed and gave up on it. No process
holds such a lock (a process holds the lock only after a step 5 that
followed a whole write).

**Lemma 3 (a held lock is never removed by another).** While `H` holds,
`lock` is the file `H` created and it reads `<H>\n` (L): nothing writes a
lock after its step 4, and the only removals of `lock` are `H`'s close,
step 3's removal of a stale lock, and a failed step 4's removal of its
own file (which happens before that opener leaves, so not while `H`, who
created the current file, holds it — Lemma 1 puts that opener's inside
before `H`'s creation). Step 3 removes only a lock read as stale: an
opener inside reads `<H>\n` with `H` alive (P), and is `Busy` if it is
another process, or (in `H`'s own process) finds `H`'s lock in the
registry (S) and is `Busy`. The close removes only a lock that reads its
own pid and only while it is held by this process.

**Theorem (two processes never both hold the lock).** A process holds
only after a step 4 that created `lock`. `create_new` succeeds only if
`lock` does not exist. If `H` holds when `P` creates `lock`, `lock` is
`H`'s file then (Lemma 3: it was not removed by another), so `P`'s
`create_new` fails. Within one process, a second exclusive open finds
the lock in the registry (S) and is `Busy`, and the close unregisters
only after its removal, under the same mutex.

**After a crash at any one step** (each step of §2.1 "The lock", and of
the close): the next opener alone takes the lock. A dead process's claim
is not a contender (P). Its lock is stale to whoever is inside next:
absent, empty or partial (Lemma 2), or its pid, dead. A process that is
alive and failed (an error returned from a take) has removed its lock or
tried to; a claim whose removal failed stays a contender until that
process ends (it ends: an error of `open` ends the command). A lock this
process left (its close read it as absent, or could not remove it) is
`Busy` naming this process to the others until it exits, and stale to
its own next exclusive open (not in the registry). The unit test
`a_crash_at_any_step_never_wedges_the_lock` crashes the taker before
every one of its operations, from eight starting stores, and the close
before every one of its operations; `a_failure_at_any_step_leaves_the_lock_takeable`
fails each operation once.

**What can still be `Busy` while the store is free.** Two live openers
that see each other's claims both back off; each tries 8 rounds, so both
can end `Busy` (never both holding). A dead process's claim or lock
whose pid a live process has since reused is a contender, or a live
owner, until that process ends: `Busy`, as for any lock of a live pid
before WP-161. A store shared across pid namespaces is out of scope
(the lock and the claims name pids of the opener's namespace; (P) fails
across namespaces). Nothing here makes that worse than before.

### What each observer sees

| Moment | Another opener inside reads `lock` as | It does |
|---|---|---|
| no lock | absent | creates it (step 4) |
| `H` between `create_new` and its write | — (Lemma 1: no other process is inside while `H` is) | — |
| `H` dead after `create_new`, before or during the write | empty, or digits without `\n` | removes it, creates its own |
| `H` holds | `<H>\n`, `H` alive | `Busy { pid: H }` |
| `H` dead while holding | `<H>\n`, `H` dead | removes it, creates its own |
| `H`'s close read it as absent and left it | `<H>\n`, `H` alive | others: `Busy { pid: H }`; `H`'s next open: removes it, creates its own |
| a lock not of this form | anything else | `Io InvalidData`, left alone |

An opener that is not inside (a live claim of another pid listed) reads
nothing and acts on nothing.

### The hazard of the mount

On the workspace mount a name can read as absent for a while after a
link and the unlink of its source (`unique-tmp-link`, WP-159). The lock
and the journal make no link. Were a created name to read as absent
anyway (the fake of the unit tests, `World::lie`), the consequences are
only `Busy` or a lock left: an opener inside that reads `lock` as absent
when it exists fails at `create_new` (`AlreadyExists`, a new round) and
reads it on the next round; a close that reads it as absent leaves it
(the case above). Tests: `two_openers_never_both_hold_the_lock` with 0,
1 and 3 lying reads per created name, `a_close_that_reads_its_lock_as_absent`.

## 3. The journal

- `write.journal` is created exclusively under its name, written, synced,
  and the store's directory synced: `Store::publish_journal`. It is a
  `JRNL` container, version 1, its record section 1: the trailer is its
  digest and the framing its length.
- `slip_apply::write` touches no file of the tree before the publish
  returns: steps 0 to 2 only stat, read, and `put` blobs (the blob store,
  not the tree). `journal.publish` is `crates/slip_apply/src/write.rs`
  line 552; the first operation that changes the tree is `tree.create`
  of the first staged name, line 577 (step 3). The file and the directory
  are synced inside `Store::publish_journal`
  (`crates/slip_exec/src/store.rs` line 1120, `f.sync_all()`, and line
  1122, `sync_dir` of the store's root), before it returns. The test
  `s7_3_a_torn_publish_leaves_an_interrupted_journal` checks that no
  operation of the tree precedes the publish.
- So a journal that is not whole was cut short before its publish
  returned, before anything of the tree was touched: **interrupted**.
  `recover` removes it (`Recovered { interrupted: true, .. }`), `slip apply
  --recover` says `recovered: the write was interrupted before any file
  was touched; the journal is removed` and exits 0; `--write` refuses a
  store with one as it refuses any journal.
- Kinds: a container that fails rule 5 for its length, trailer or
  framing (`Truncated`, `Corrupt`, `Malformed`), and bytes no longer than
  a prefix of the header, are interrupted. `UnsupportedVersion` (a newer
  Slip's journal) and a kind other than `JRNL` are malformed: refused and
  kept. A whole container whose record does not decode, breaks a rule of
  the reader, or has an unknown critical section is malformed.
- An earlier Slip's journal (the record alone, no magic) is still read:
  whole if it decodes and passes the rules, else interrupted. A record
  starting with the magic is a digest starting with those eight bytes:
  not a concern.
- A journal that is whole although its publish did not return (a crash
  after the write, before or during the syncs) is recovered as whole:
  every file is still the pre-image, so recovery leaves them and removes
  the journal.

## 4. Measurements on the workspace mount

See the handback of `docs/wp/WP-161.md` for the runs (logs under
`.build/wp161/`).

Liveness, found by the soak: a first back-off that was a function of the
pid and the round (`1 + (7·pid + 13·round) mod 5` ms, doubled per round)
made two openers whose pids are equal modulo 5 wait alike, meet again in
every round, and end `Busy` after 8 rounds, over and over: a soak of four
tight-looping openers, two of them so, slowed to a crawl (more than 5
minutes, almost all of it asleep, without finishing 2,001 rounds). Safety
was never at stake (a meeting makes both leave). The wait is now random
(`RandomState`'s keys and the clock): 1 ms plus up to 4 ms, the bound
doubled per round up to the sixth, and no wait after the last round.
Under heavy contention two openers can still both be `Busy` (choice 1 of
the handback).

## 5. Reads by id (item 2)

- `load_plan` (`slip_cli::commands`), for every command that takes
  `--plan <id>` (`parse`, `verify`, `declare`, `units`, `map`, `rename`,
  `reduce`, `check`), compares the content id of the bytes read with the
  id: a difference is `Input`, `<path>: the file's content id is not its
  name`. `check --declared <id>` (`load_declared`) does the same. The
  worker already compared the declared changes of a verify job.
- `verify --declared` takes only a file; it is not read by id.
- The map shards `slip map` counts, and the run records, are unchanged:
  `exec.md` §2.1 "Which reads are checked" says what is compared instead
  and why neither can mislead.
