# WP-074 — the worker: the map job of a transform and the verify job through an overlay

Implemented by `slip_cli::worker` (`MapTask` with a transform,
`map_shard`), `slip_cli::worker::transform` (`run_transform`,
`read_transform`, `NO_SCRIPT`), `slip_cli::worker::post` (`Loaded`,
`Read`, `reads`), `slip_cli::image` (`Image::overlay`, `overlay_id`,
`overlay_of`, `from_post` of an overlay, `parse_unit`, the test hook
`with_loading_limit`) and `slip_cli::verify_job` (`overlay_walk`,
`overlay_guards`, `overlay_again`, `spellings_section`). This file fixes
what `exec.md` §5.2, §8.4, §8.6, `edits.md` §8.1 and `verify.md` §5.1,
§5.2, §5.3, §9.1 and §10.4 leave open. The order of the overlay form's
guards is also written into `verify.md` §5.2 step 2 and §5.3.
Tests: `crates/slip_cli/tests/tasks.rs`; the unit test
`map_task_refuses_a_job_that_does_not_fit` (`src/worker.rs`).

## 1. The map job of a transform (`edits.md` §8.1)

- The request is read and checked before anything is parsed: it is
  read from `transforms/<id>.trfm`, decoded with every rule of `TRFM`, and
  its content id must be the job's `transform`. Each failure is the job's
  `Err` (a failed shard, by the coordinator): `the request <id> is not in
  the store (<path>)`, `<path> is not a valid TRFM file: <e>`, `<path> has
  the content id <actual>, not <id>`. A store that cannot be opened fails
  the job first, as without a transform.
- A request of kind `script` is `Err` with `a script transform needs a
  worker built with slip_script` after the request is read and before the
  parse (WP-092 adds its branch at `run_transform`'s dispatch). The test
  that it is refused before the parse: an observer whose main file is not
  there gets this `Err`; a refusal after the parse would leave the parse's
  `diagnosed` shard (`s8_1_map_refusals`).
- The parse asks Kiln for its written-reference tables and its
  preprocessing record (`ParseOptions::written`, `pp_record`) and the
  lookup log, as the map task does. The shard does not depend on the
  first two (`slip_kiln::parse_observer_with`): the test
  `s8_1_map_with_a_rename` shows the shard without `edits` and the
  `edits.*` counters is, byte for byte, the job's without a transform.
- The transform is run inside the parse's closure, after `map_unit`,
  through a second `with_input` over the same unit, only when the walk
  ran and succeeded. Its `Keys` are `Keys::new(input)` (no rules), and
  `files` is the `FileRef` of the input whose path is the buffer's real
  path (`Sites::file_ref`'s answer, without naming `slip_kiln::sites`:
  the `kiln-boundary` lint).
- An `Err` of the transform fails the job whatever the outcome (also on a
  unit whose status turns out not `ok` after the closure: a driver error).
  An `ok` shard gets `edits` and the `edits.*` counters, merged with the
  others and sorted by name; a shard that is not `ok` has neither.
- The request id has one definition: the content id of the `TRFM` bytes
  read from the store (which may hold ignorable sections, `model.md` §5.4,
  that a re-encoding drops). The worker passes it to the transform
  (`run_transform(transform, id, …)`, `slip_refactor::run(transform, id,
  …)` and `run_counted`), which writes it as the section's `transform`
  (`s8_1_a_request_with_an_ignorable_section`). The worker still checks
  that the section names the job's request: a difference fails the job
  (`the edits name the request <x>, not the job's <id>`; unit test
  `checked_edits_names_the_jobs_request`).
- Without a transform the job is M1's: the same options, the same walk,
  nothing else run in the closure (`s8_5_map_without_a_transform_is_m1s`).

## 2. The image of the overlay form (`exec.md` §8.6, `verify.md` §5.1)

- `Image::overlay(id, Arc<Overlay>)`, not `exec.md` §8.6's
  `Image::overlay(id, Overlay, Blobs)`: the blobs are a job's
  (`worker::post::Loaded`), not the image's, so that the image, kept in
  `Params` across jobs, holds no blob (the worker holds the bytes of the
  files one observer reads, and no others). Two overlay images are equal
  and hash alike when their ids are.
- `Image::from_post(store, Overlay(id))` reads `overlays/<id>.ovly`,
  decodes it with every rule of `OVLY` and checks its content id; failures
  are `Err` (`the overlay <id> is not in the store (<path>)`, `<path> is
  not a valid OVLY file: <e>`, `<path> has the content id <actual>, not
  <id>`). The verify task keeps the `Params`, with the `Arc<Overlay>`,
  while the job's `declared` and `image` are the same (as for a tree).
- For an overlay image: no root map, `is_identity()` false, the post
  command is the command, `to_subject` is the identity, the resolver has
  no root, `to_post()` is `Overlay(id)`.
- `Image::parse` and `parse_looking` refuse the post side of an overlay
  image (`Err`: it is never parsed from disk); its pre side is the
  observer's own command, as for a tree (step 4).

## 3. Loading (`verify.md` §5.1)

- Before anything is loaded, `Loaded::index` reads the identity (device,
  inode, links followed) of every overlay file's path: one `stat` per
  entry per job, whatever the observer reads (about a microsecond each:
  ten milliseconds for an overlay of ten thousand files, per job; it is
  not kept across jobs, as a file replaced since, a new inode, would then
  be missed). Two entries of one identity (hard links; two spellings of a
  name on a volume that ignores case) fail the job: `the overlay <id>
  names one file twice: <a> and <b> are the same file`, `<a>` the earlier
  entry. The refusal does not depend on what the observer read
  (`s5_1_two_entries_of_one_file_fail_the_job`). The same refusal where
  an overlay is made is WP-151's.
- An entry with no regular file at its path at that `stat` is *gone*: it
  is never given to the front end (Kiln replaces only a file that is
  there, and fails the parse otherwise). A post-image that reads it does
  not find it: the parse's outcome, `not_parsed`, as in the tree form.
  One that does not: when the pre shard lists it, O2's second part
  (`left_behind`, §5 item 4) makes the observer `unverifiable`, `pre-image:
  <path> is gone since the map phase (run `slip parse` again)`
  (`s5_1_an_overlay_file_gone_since_the_map_phase`). A verdict needs the
  post parse's digests, so "decided before the parse" is the decision not
  to give it; the reason is the guard's.
- "The pre shard is usable" is step 0's: there, `ok`, with `digests`.
  Then the files the overlay names (by path) among its `inputs`, gone
  ones apart, are loaded first; otherwise every file of the overlay that
  is not gone.
- A blob is read with `Store::read_blob` (which checks its hash) and its
  length must be the overlay's `post.size`. A blob that is not there, does
  not hash to its name, cannot be read or has another length is the job's
  `Err`.
- After each parse, with errors or without, the files to give next are
  the overlay files not given that some input of the parse is, read
  other than through the overlay (`Loaded::missing`). An input *is* the
  overlay file whose path is the input's path, or, failing that, whose
  file has the identity (device, inode, links followed) of the file at
  the input's path now (`Loaded::entry_of`). How the unit read an input
  is `Unit::overlaid` for a buffer (`Read::Overlay` or `Read::Disk`) and
  `Read::Consulted` for a path consulted without being entered
  (`worker::post::reads`); never a comparison of path text.
- While some are, they are loaded and the observer parsed again. The walk
  and the checks of §10.2 run only in the last parse; intermediate parses
  run neither. Each iteration gives at least one more file of the
  overlay, so the parses are at most the overlay's files plus one.
- The number of parses is in nothing the job returns: not in
  `verify.reparsed`, not in any counter.
- The test hook `Image::with_loading_limit(n)` (hidden; tests only) stops
  the loop at the `n`th parse, which is then the last.

## 4. Step 1 through the overlay

- The parse is the observer's own command with `ParseOptions::overlay`
  the entries loaded (sorted by path), `written` when the overlay has at
  least one obligation, and the lookup log.
- The shard gets `binding` (overlay = the `OVLY`'s id, declared, pre)
  whenever the parse did not fail, with or without rules; `rule_use` as
  for a tree (in an `ok` shard under rules).
- Section 26 is made in the last parse, after the walk and inside the same
  `with_input`, by `check_spellings(unit, input, rules, read_only,
  obligations)` with the walk's own `ReadOnly`. The obligations are those
  of the overlay files whose path the post `inputs` list (the fold's
  `seen`, `verify.md` §10.4), not of the files given and not read
  (`s10_4_obligations_of_the_files_read`), with `file` the real path (the
  subject path of the overlay form). An obligation whose `lo` or `hi` does not fit a
  `u32` fails the job, never an obligation dropped.
- Encoding: `seen` the number of those obligations; `held` the runs of
  consecutive indices that hold; `failed` each that fails, with `found`
  and the name `check_spellings` gives. The four counters
  `verify.spelling.obligations`, `.holds`, `.fails`, `.not_seen` are
  present exactly when the section is. The section is present when the
  outcome is `ok` and the overlay has at least one obligation, whatever
  the verdict (also `unverifiable`).
- Step 6's second parse uses the same entries and options as the last
  parse (G3 compares them).

## 5. The guards of the overlay form (`verify.md` §5.2 step 2, §5.3)

In this order, over step 1's last parse; the first that fails is the
reason of the `unverifiable` verdict:

1. **G4** on the observer's command.
2. **O1, the unit's part**: no input that is an overlay file (§3's test)
   was read from disk: a buffer `Read::Disk`, or a path consulted that is
   an overlay file not given. Reason: `OverlayGuard::O1`'s, `post-image:
   <path> was not read through the overlay`, `<path>` the input's.
3. **O1 then O2 by path**: `slip_verify::guards::overlay_inputs(pre
   inputs, post inputs, overlay)`, reasons `OverlayGuard::reason()`;
   except that an O2 failure on an input that is an overlay file by
   identity and not by path (another name of it: its bytes are the
   overlay's, not drift) has the reason `pre-image: <path> is another
   name of the overlay's <overlay path>` (`s5_3_another_name_of_an_overlay_file`).
4. **The subject's sums**: every input of the pre shard whose path the
   overlay names has the overlay's `pre` (size and digest); reason
   `pre-image: the overlay was made from another <path> than the map phase
   read`. Then every input of the pre shard whose path the post `inputs`
   do not list is still the file the map parse read (the tree form's
   `left_behind`, with no subject root: every such input is checked);
   reasons `Left::reason`.
5. **N1** over every negative input of the pre shard, then **N2** over
   every place of its `found` (no subject root); a pre shard without the
   record fails closed, as for a tree.

G1, L1, G5 and G6 do not run (no subject root, no map pair). An input
overlaid but reached by another spelling than the overlay's path is not
named by `overlay_inputs` and is compared with the pre shard by O2: when
the edit changed it, the verdict is `unverifiable` (conservative), with
the reason of item 3. Its obligations are not `seen` either (`seen` is by
path, as in the fold): conservative, and `verify.md` §10.4's.

Tests of each guard in this form: G4 `s5_3_g4_in_the_overlay_form`; O1's
unit part `s5_1_loading_an_overlay_file_by_identity` (the stopped loop)
and `s5_1_embed_of_an_overlay_file`; O1/O2 by path `s5_3_o1_and_o2`; the
sums, both halves of the comparison `s5_3_subject_sums_and_n1`;
`left_behind` `s5_3_left_behind_in_the_overlay_form`; N1
`s5_3_subject_sums_and_n1`; N2 alone `s5_3_n2_alone` (a found place
retargeted to a file of the same bytes, the file read still there: no
other guard sees it).

What no test can isolate:

- O1's unit part for a path *consulted* (`Read::Consulted` taken as read
  through the overlay, review R1): Kiln enters a `__has_include` hit as a
  buffer, so only `#embed` or `__has_embed` consult without entering. By
  path, O1 by path gives the same answer with the same reason; only an
  embed under another name of an overlay file would tell them apart, and
  that input is then an alias, which O2 refuses (item 3). Left as it is.
- `reads` keeping `Read::Disk` once a path has a buffer read from disk
  (review R16): it matters only for a path that is two buffers, one read
  through the overlay and one not, in one parse. Within one parse an
  entry is given or not, and Kiln replaces every buffer of the file by
  identity, so no such parse can be built from outside; the rule is kept
  as the conservative answer.
